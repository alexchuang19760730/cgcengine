[engine] The number of rows a comparator may compare is bounded by the OPERAND's size on both sides, not by the depth the capture was ASKED for. A capture that digests 'the first N ids the consumer used' writes fewer rows than N whenever the operand holds fewer ids, and the unwritten rows are pure sentinel -- so a comparison that iterates to N manufactures a 'measurement gap' verdict for a region that never existed. Distinguish three things that all look like a short reading: rows BEYOND the operand (exclude; not part of the question), rows the operand has but the reader did not cover (report as a gap, with the covered prefix named), and rows covered but never written (a genuine instrumentation failure). Record the operand's size in the row so the reader can tell them apart -- a capture depth that is a knob cannot double as the operand's size.

## 為什麼（because）

Running the pool-row capture at depth 12 (needed because a 2-token chunk has 16 ids and the anomaly sits at the second token) produced 4 rows of sentinel on every single-token graph, because a decode step's operand holds only 8 ids. The comparator flagged 15 of 105 keys as PART-READ -- three of the three node names on each of the five decode graphs -- and a PART-READ key has no verdict, so the first A/B of the new instrument appeared to be missing a fifth of its evidence. The capture already printed the operand size (`nsel`), which is what makes min(depth, nsel) the correct row count rather than a guess.
