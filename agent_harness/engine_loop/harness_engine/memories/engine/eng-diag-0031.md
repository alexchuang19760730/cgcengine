[engine] An annotation added to a reading must be sampled at the SAME instant as the reading, and if that instant is not the end of the step, the instrument must be built to run at the earlier one. Concretely: when a row records what a consumer SAW, anything that labels that row (which expert a slot holds, which owner a page belongs to, which generation a pointer came from) must be captured before or at the consumer, never at the synchronize point where the row is printed. The end-of-step state is a valid reading of its own -- but it is a different question, and it must not be used to label a within-step one, because the specific hypothesis such an instrument exists to test is usually 'did the thing that should have been in place before the read actually arrive before the read'.

## 為什麼（because）

The pool-row digest (a POOL row records the id a MoE consumer used and a digest of the bytes that id selected) was extended with the slot->expert map so the comparator could separate 'same slot, different expert' from 'same slot, same expert, different bytes'. The obvious implementation -- look the map up in the dump path, where the ids have just been read -- is wrong here for a reason particular to the investigation: the dump runs at synchronize, i.e. after the whole pass, so it would have read the map as it stood AFTER any background fill that landed late. 'A fill landed after the consumer had already read' is exactly the hypothesis the row was being used to test, so the label would have been produced by the phenomenon under test. The map itself does not depend on the ids, so it can be snapshotted at encode time (immediately before the consuming kernel is submitted) and stored per capture; the ids are consulted later, when they finally exist.

## 反例（counterexample_observed）

Instrument written 2026-09-17 (§9.18.7), not yet run. The contrast is measurable in the design itself: the same run's engine-side counter reports `consumed_changed=192` over one pass -- i.e. the consumed slot->expert map DOES move within a run -- while a hardcoded dump-time lookup would have shown one final value for every row and no way to see the movement at all.
