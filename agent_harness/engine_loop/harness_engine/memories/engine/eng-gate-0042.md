[engine] A driver's closing step must be able to fail the driver. A `python3 - <<'PY'` heredoc inside a bash script inherits no `set -e`, so a traceback in the final analysis step leaves the run's exit status at 0 and the run reads as complete -- and the step that gets skipped is exactly the one the next reader reaches for. Check the status of every heredoc/analysis step explicitly, and treat a traceback printed between two normal lines as a silent failure rather than as noise. Related and easy to miss: a path join written `p / "a" + name` parses as `(p / "a") + name`, so a Path-plus-string TypeError hides inside a line that looks like a path join.

## 為什麼（because）

Adding one counter to the closing heredoc of the capture driver exposed that its last line had been raising `TypeError: unsupported operand type(s) for +: 'PosixPath' and 'str'` on every run since it was written, while `arms.json` (one line above it) was written fine -- so the per-arm copies named `latest_*` never existed and nothing downstream complained. The failure was visible only to someone reading the script's own stderr, and the surrounding output looked complete. A repo-wide grep then showed no consumer of `latest_*`, which is why the impact was a missing artifact rather than a wrong number -- a distinction that could only be made after finding the bug.

## 反例（counterexample_observed）

Run 2026-09-17 09:11: the driver printed both arms' row counts, then the TypeError, then continued through every analysis section and printed its final '=== done ===' banner with exit status 0; the reference to the missing `latest_*` copies is the only thing that was silently absent.
