[engine] When a verdict is about an OPERAND rather than a tensor, the instrument's record budget must cover the operand's full size, and the verdict must name the prefix it actually covered. For a 2-D ids operand the first N rows are NOT a sample -- a ggml tensor is ne0-fastest, so they are exactly TOKEN 0, and the remaining tokens of the chunk are simply not in the reading. 'The ids are identical' then silently means 'token 0's ids are identical', and the difference it hides can be the whole divergence. Widen the budget and re-run before quoting the verdict; if the budget cannot reach the operand's size, state the covered prefix in the conclusion itself.

## 為什麼（because）

The device-side pool-row digest reads the first `rows` ids (default 8 = n_expert_used) and digests the row each selects. At T=1 that is the whole operand, so the 6 decode graphs and the first 2-token graph were fully covered and everything agreed -- and the verdict went out as 'same ids, same rows, on every graph'. At T=2 the operand holds 16 ids and at T=8 it holds 64, so every multi-token graph of the run was a token-0-only reading. Widening to rows=12 exposed it on the next run: at the SECOND graph of the run, token 0's 8 ids are still identical across arms while token 1's differ (the S1 arm returns repeats of slot 0 where the anchor returns distinct slots), which is the real first divergence of the run -- one graph earlier than the localisation had placed it, and it explains a whole-tensor difference at a node (layer 1's MoE output) whose input activations, router logits, routing weights and token-0 rows were all byte-identical. The earlier 'first divergence' reading was not wrong about what it compared; it was wrong about how much it covered.
