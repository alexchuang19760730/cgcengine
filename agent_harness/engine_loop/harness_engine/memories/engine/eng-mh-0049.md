[engine] A build fingerprint assembled by reading several files one at a time is not atomic: if a relink is in progress, it can stamp a combination of versions that never ran together, and it does so silently -- the dict looks complete and every key is a real hash. Take the fingerprint TWICE (at launch and at teardown) and mark the row not-comparable when they differ, or else detect that any of the files changed while the fingerprint was being assembled and refuse it. The reason this matters more than a normal race: the fingerprint is the thing that decides which rows may be compared, so a torn one does not produce a wrong number, it produces a wrong permission -- it licenses a comparison that must not happen.

## 為什麼（because）

The pool-row A/B run at 11:28 on this machine had its binaries replaced underneath it: two libraries were relinked 3 seconds apart (libggml-metal at 11:29:13, libllama at 11:29:16), and the first arm's fingerprint was computed inside that 3-second window. It therefore recorded the NEW libggml-metal hash together with the OLD libllama hash -- a build that never existed as a running configuration -- while the second arm recorded the new pair. Read naively, the two arms 'share' the metal key and differ on llama, which invites the conclusion that only one library changed; in fact the whole run straddled two builds and neither arm is quotable.
