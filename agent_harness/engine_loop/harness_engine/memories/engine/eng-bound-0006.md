[engine] A durable record's effective capacity is set by its weakest consumer, not by the disk, and exceeding it fails silently by losing the TAIL. A canonical file that is read whole by an injection step with a fixed limit therefore degrades from the back end, where the most recently added (and often most actionable) material lives -- and the file keeps reporting its true size, so nothing looks broken. Split the record by topic into an index plus topic files, and before splitting verify that every consumer of it enumerates rather than whitelists, or the new files will be silently missed -- which is the same defect in the other direction.

## 為什麼（because）

Found when the project's cross-day memory file reached 19,240 bytes and began arriving truncated at session start: the tail was simply not there, and the tail is where the live status of the current line sits. The tooling turned out to be glob-based on all three sides (the memory indexer, the asset manifest, and the snapshot importer), so an extra `.md` in the memory directory is a supported shape rather than a schema violation -- but that had to be read out of the three scripts first, because 3 new files would otherwise have been picked up by none of them.

## 反例（counterexample_observed）

After the split the canonical file is 5,660 bytes (was 19,240) while the four files together are 25,581, i.e. the record got larger and the injected part got 3.4x smaller. The query interface still resolves material that moved: `--query SEL-DRIFT` returns `MEMORY_S1.md:8-22` and `:23-44`, and `--query OVERSUBSCRIBED` returns `MEMORY_FACTS.md:6-26`.
