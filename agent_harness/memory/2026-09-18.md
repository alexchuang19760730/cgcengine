### 一：我先做的假設是錯的（**負結果，有持久價值**）

09-17 我從四個觀察推出「draft context 建得太晚（在 depth prefill 之後）」，並據此做了一個位移：
新增 `bench_spec_state` ＋ `bench_spec_setup()`，把 draft context 的建立從 `test_gen_spec` 內部

⇒ **「建得早」不是原因。** 我保留了那個位移（與 server 同序、防禦性），但程式碼註解裡逐字記下了
這個負結果（`HONEST RESULT, measured 2026-09-18 00:22`），並標註**它未經隔離的效能驗證**。

### 二：真因 —— batch 的**位置**（不是 context 的建構時機）

`test_gen_spec` 明確指定 batch 的 pos（`common_batch_add(batch, id_last, n_past++, …)`），
而 **`n_past` 被初始化為 `0`**。同一個 rep 裡 **depth prefill 已經寫過 pos 0..511**
（llama-bench 的順序是 depth → prompt → gen）⇒ 第一個 verify batch 要求的位置已被佔用 ⇒
`llama_decode` 回 **-1 且不印任何訊息**。

**對照組解釋了為什麼只有這條路徑踩到**：非 spec 的 `test_gen` 用 `llama_batch_get_one()`，
由 llama 自己分配位置 ⇒ 自動接在 depth 之後。**只有新寫的 spec 路徑自己管位置。**

修法（1 行）：
```cpp
int n_past = (int) llama_memory_seq_pos_max(llama_get_memory(ctx), seq_id) + 1;
```
空 memory 回 -1 ⇒ `n_past = 0` ⇒ **沒有 depth run 的形狀行為不變**（已用短形狀 `-n 16 -d 0`
回歸驗證：rc=0 ✓）。有 depth ⇒ 512 ✓。順帶修好了 `-p > 0` 的形狀。

⇒ `n_max` 掃描是有價值的下一件事。（⚠️ 代數吻合，非直接量測。）

### 一：第 2 件的機制說明**兩個獨立理由都是錯的**（負結果，有持久價值）

原述句出自 §EN-97：引用 `llama-graph.cpp:2172` 的「layer 0 keeps the host leaf」，推出「L0 是唯一走
host leaf 的層 ⇒ 它 9.46 ms 的 union 是另一條路徑 ⇒ 設 `CGC_S1_MIN_IL=0` 就能省」。

1. **`union` 不是 host 工作。** `ggml-metal-context.m:497` 逐字：
   `out[1] = GPU busy union (ns) -- max(end) - min(start)`，由 `[cb GPUStartTime]/[cb GPUEndTime]`
   （`:526-537`）算出，累加在 `ggml-backend.cpp:2042`。**它是 GPU 時鐘量**；host 側的括號是
   `wait`（`:1949-1962`）與 `cb`（`:2020-2052`）。「host leaf ⇒ host 工作變多」與被量的欄位無關。
2. **`CGC_S1_MIN_IL` 在生產上不會生效，而且 L0 是結構上的永久排除項。**
   `llama-graph.cpp:2146` 只在 `CGC_SLOT_TABLE_GPU` 存在時讀它，而 `run_server.sh:1518` 只在**顯式**
   給值時才傳 ⇒ 生產沒開 S1。`decode_sweep.py:410-412` 明文：L0 永遠不是候選（**它的 MoE 跑 CPU/BLAS，
   GPU 算的 id 向量需要跨 backend 複製 —— 就是 20:18 SIGSEGV 的形狀**）。
3. 而那段註解講的是 **`prod25`（舊 profile）**（`llama-graph.cpp:2156`：blk.0.ffn_gate_exps 82M vs
   45M）。**現行配置 L0 是在池裡的**：23:28 產物的 env 逐字 `LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0: "0"`
   （`cgc_env_on` 把 `"0"` 讀成 off），所以 `llama-context.cpp:5883` 的 early return 不觸發。

### 二：★ 第 3 件落地 —— `CGC_GPU_NODES=1` 的**節點範圍級** GPU 時間

**關鍵發現（讓 `M3_VERDICT` 說的「唯一活路、成本最高」變成小改動）**：**不需要 `MTLCounterSampleBuffer`。**
`ggml-metal-context.m:1304-1315` 的 `idx_start/idx_end` 顯示每個 command buffer 編的是**連續的節點範圍**

而 `n_cb / n_nodes_0 / n_nodes_per_cb / gf` 在 hook 讀取時都還在 ⇒ **範圍可以直接導出**。

實作（296 行跨 5 檔）：`ggml_metal_cgc_gpu_take_cb()`（逐 cb 回 `{start_ns, end_ns, first_node, last_node, ok}`）
＋ `ggml_metal_cgc_node_name()`；兩個 proc-address 註冊；`ggml-backend.cpp` 在 hook 裡把每個 cb 的時長

`CGC_GPU_NODES` 到 allowlist。

per-segment Metal busy time）⇒ 實測 **5 個 step 全部 `delta=0.00%`、`(other)=0.00 ms`** ⇒ **我的節點範圍
與編碼器的切法逐位吻合**。

### ★★ 三：三個踩到的坑（兩個是我的錯，一個是設計缺陷）
