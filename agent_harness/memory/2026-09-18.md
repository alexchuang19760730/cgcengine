## §EN-102 ★★ llama-bench 現在能測 MTP 了 —— 真因是**一個初始化**，而我原本的「順序」假設被實驗否證

**使用者 00:19 的指示**：「要我動那個位移（llama-bench.cpp，兩三行）請修復它 讓llama bench 可以測量mtp」。

### 一：我先做的假設是錯的（**負結果，有持久價值**）

09-17 我從四個觀察推出「draft context 建得太晚（在 depth prefill 之後）」，並據此做了一個位移：
新增 `bench_spec_state` ＋ `bench_spec_setup()`，把 draft context 的建立從 `test_gen_spec` 內部
提到**呼叫點**（target context 建好之後、warmup 之前）。

**量到的結果：仍然失敗，逐字相同**（`verify decode failed: ret=-1 … n_ctx=768 n_past=1 draft=3`）。

⇒ **「建得早」不是原因。** 我保留了那個位移（與 server 同序、防禦性），但程式碼註解裡逐字記下了
這個負結果（`HONEST RESULT, measured 2026-09-18 00:22`），並標註**它未經隔離的效能驗證**。

### 二：真因 —— batch 的**位置**（不是 context 的建構時機）

`test_gen_spec` 明確指定 batch 的 pos（`common_batch_add(batch, id_last, n_past++, …)`），
而 **`n_past` 被初始化為 `0`**。同一個 rep 裡 **depth prefill 已經寫過 pos 0..511**
（llama-bench 的順序是 depth → prompt → gen）⇒ 第一個 verify batch 要求的位置已被佔用 ⇒
`llama_decode` 回 **-1 且不印任何訊息**。

**對照組解釋了為什麼只有這條路徑踩到**：非 spec 的 `test_gen` 用 `llama_batch_get_one()`，
由 llama 自己分配位置 ⇒ 自動接在 depth 之後。**只有新寫的 spec 路徑自己管位置。**

修法（1 行）：
```cpp
int n_past = (int) llama_memory_seq_pos_max(llama_get_memory(ctx), seq_id) + 1;
```
空 memory 回 -1 ⇒ `n_past = 0` ⇒ **沒有 depth run 的形狀行為不變**（已用短形狀 `-n 16 -d 0`
回歸驗證：rc=0 ✓）。有 depth ⇒ 512 ✓。順帶修好了 `-p > 0` 的形狀。

## §EN-103 ★★★ 配對交錯（含反序對）：**MTP 沒有可測的淨增益**；而「臂的位置」本身就值 ±12%

**使用者的指示**：把我上一輪的建議（「需要更乾淨的窗口」）付諸實行。

### 一：設計（判準事先寫定在腳本 docstring 裡）

形狀 `-p 0 -n 64 -d 512 -b 512 -r 4`（生產 decode cell 縮短）、丟掉 sample 0、臂間等 20 s、
**兩輪**：正序 `off,on`×3（6 臂）＋ **反序 `on,off`×2（4 臂）**。
env 兩臂除 `--spec-type draft-mtp` 外完全相同（**刻意不開** GPU_TIMING／DECPROF，它們自己有成本）。

**為什麼一定要反序對**：ABAB 的每一對裡 `off` 總是先跑 ⇒ 若「臂的位置」有效應，`on` 就被系統性偏誤。

### 二：結果

| 對 | ratio (on/off) |
|---|---|
| AB-1 / AB-2 / AB-3 | 1.071 / 1.171 / 1.013 |
| BA-1 / BA-2 | 0.938 / 0.701 |

**★ 純順序效應**：5 個「先跑的臂」中位 **8.387**、5 個「後跑的臂」中位 **9.434**
⇒ **後跑比先跑快 12.5%**（與 treatment 無關）。

**★ 順序校正**：`M = sqrt(中位AB × 中位BA) = sqrt(1.071 × 0.820) = 0.937`（平衡的 2+2 對給 0.959）
⇒ **MTP 的最佳點估計 = −4% ~ −6%，而 5 對的 ratio 範圍是 0.701–1.171**
⇒ **不可與 0 區分，且小於臂間漂移**。

### ★★ 三：方法論級結論（比 MTP 的數字更重要）

**任何單向 A/B 的 MTP 結論都不成立** —— 包括我們報過的 **−23%**（09-17 的 A/B/A，起因是 off1 特別快）、
他們的 **+5.7%**、更早的 **+31%**。手臂的**位置**足以製造 ±12% 的假效果。
⇒ **量 MTP 一律要 ABBA（含反序對）。**

### 四：穩健的計數器（不受漂移影響）

- `accept` **0.626 – 0.795**（5 個 on 臂，變異 **27%**）⇒ 「accept ≥ 60%」那條離開條件的**量測變異
  比門檻還寬** ⇒ 單次 accept 讀數不該當閘門（與另一條線作廢它的結論同向，但理由不同）。
- `emit_tok_per_round` 2.878 – 3.385、`gen_tok_per_round` **3.000**（每臂都吃滿 n_max=3）、
  `ms_per_round`（draft head）25.0 – 31.1。
- 池 `hit rate` **93.7 – 94.8%**（off 是 96.0 – 96.1%）⇒ **MTP 讓命中率降 2.2pp**（與 §EN-102 同向）。

### ★ 五：機制發現 —— 接受是**每顆獨立**的，不是序列相依

實測 `acc_tok_per_round = 2.023`、`n_max=3`、`acc_rate=0.6744`：
- 序列相依（第一顆不接受則後面作廢）⇒ 期望 `p+p²+p³` = 1.436 ❌
- **每顆獨立** ⇒ 期望 `n×p` = **3 × 0.6744 = 2.023** ✅（逐位吻合）

⇒ MTP 的草稿是**平行**產生、各自比對的 ⇒ **加大 `n_max` 的邊際收益是線性的**（不像 chain 投機那樣衰減）
⇒ `n_max` 掃描是有價值的下一件事。（⚠️ 代數吻合，非直接量測。）

### 六：對 25 t/s 的意義

served 生產基準 ≈ **12.0–12.1**（8 GiB）⇒ 25 需要 **2.07×**。本輪量到 MTP 的貢獻 ≈ **0（±10%）**
⇒ **MTP 對 25 沒有貢獻**；決定 25 的仍然只有 **GPU span**（8 GiB 側 75.66 ms/step）。

### 七：立下的定則

1. 量 MTP 一律 **ABBA**（含反序對）；2. 兩臂要**短**；3. 丟 sample 0、用中位數；
4. **計數器優於 t/s**；5. 報兩臂比較時**必須說明誰先跑**。
