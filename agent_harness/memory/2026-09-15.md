### 推翻 1：「per-miss pread 延遲退化 8×」
先前拿 prefill250 profile 的 `us/job=14.5ms` 對比 09-05 的 1.74ms，得出「IO 路徑本身劣化」。

### 推翻 2：「提高 hit rate / 加大 pool 是槓桿」
09-05 用 **71 slots（4GiB）+ L0=32/L1=32 分區** 跑出 27.71 t/s；今天 143 slots 只有 6.5–10.4 t/s。

## 16:30–16:55 — llama-bench 多 context 崩潰：兩個真 bug（已修）

`llama-bench` 每個 (p,n,d) instance 都新建/釋放一個 `llama_context`，所以它天然是多 context harness。
先前「llama-bench 跑我們的模型會 OOM」的根因是**沒帶 `-expert-cache`**（-expert-cache 不是無條件載入，
llama-bench 不帶它就讓 256 experts 全量常駐 13.66GB > Metal 建議工作集 11.2GB → `res = -3`）。
帶上之後暴露兩個**真實的跨 context bug**：

### Bug 1 — `~llama_context` 不還原 M2 slab 的 tensor 重指向（SIGSEGV）
`graph_get_cb` 走 wide-union gather 時把**模型自己的** FFN expert tensor 就地改寫
（`llama-context.cpp:4446-4447`：`wt->data = sl->base; wt->buffer = sl->buf; ne[2] = 256`），
原值存進 `cache_orig` / `cache_gather_orig_buf` / `cache_gather_ne2`，還原只發生在**下一個 step 的
per-layer hook**。最後一層重指向後沒有下一個 step → tensor 永久留在 slab 上：
`data` 指向已釋放的 slab、`buffer` 是**已釋放的 `ggml_backend_buffer_t`**（野指標）、`ne[2]=256`。
`~llama_context` 釋放 slab 後不還原 → 同進程建第二個 context 時 loader 從這些 tensor 認領 L4 pool
→ SIGSEGV（且早於第二個 context 的任何 log）。
**修**：把 `cache_orig` / `cache_gather_orig_buf` / `cache_gather_ne2` 的還原迴圈插到
`~llama_context` 的「釋放 slab」之前，印 `CGC-M2-UNREPOINT: teardown restored N expert tensor(s)
before freeing M slab(s)`。**pool-only 臂不崩**正是因為它根本沒走重指向。
（`--load-mode mmap` 在 prod25 下是 `Bus error: 10` SIGBUS，與此無關，另案。）

### Bug 2 — `pick_slot` 的 SpAc victim 上界假設錯誤（SIGABRT）★根因
還原修好後第二個 context 立即 `abort()`：
```
FATAL ensure_slot layer=1: no usable slot and no fill in flight
FATAL ensure_batch layer=1: 8 distinct experts exceed the 143 usable pool slots
```
「8 > 143」這個荒謬數字是誤導；真正狀態（加了診斷後實測）：
```
slots_l=143 usable=142 zero_slot=1
occupancy: owned=142 loading=0 queued=0 pinned=0 pinned_static=0 decode_reserved=0
last_use: min=0 max=142 tick=142
spac: on=1 victim=1 rows=40 row_size=256 util[layer][0]=4.375 owner[0]=0
```
池子全滿、可驅逐，`pick_slot` 卻三個 pass 全部選不出 victim。原因：
```cpp
double best_util = 2.0;  // > max possible (1.0), so any real utility wins
```
**這個「1.0 上界」是假的。** `spac_update` 是 `u[e] *= alpha; u[experts[i]] += bump`
—— 對 routed union 裡**每次出現**都加一次 bump（同一步選 4 次就加 4 次），
所以 EMA 的固定點是 k 而非 1.0（實測 4.375 = 4 + 0.375）。
一旦某層 utility > 2.0，`util < best_util` 對每個 slot 都為 false → `best_slot` 永遠 -1
→ 三 pass 走完 return -1 → 呼叫端 abort。**只有 `CGC_SPAC=1` 且池子滿時可達**
（所以它躲過了 09-14/09-15 的 SPAC sweep），且與 slab 路徑無關
（MTP-off 走 `ensure_batch`，同樣中招）。
**修**（`llama-expert-cache.cpp` pick_slot）：
1. `best_util` 初始化改 `std::numeric_limits<double>::infinity()`。所有 utility < 2.0 時行為
   **逐位元相同**（第一個 slot 照樣立刻當選），所以 SPAC-off 與 SPAC-normal 路徑不受影響。
2. `spac_victim` 加上 `!cache->spac_util[layer].empty()`（原本只檢查 `size()`，
   空 row 會變成 OOB 讀）。
3. 每個 pass 額外追蹤一個「已通過 flag 過濾的 LRU candidate」`lru_slot`，
   只在 SpAc 分支什麼都沒選到時才使用 → 把 abort 變成正常的 LRU 驅逐，
   不改變任何原本成功的 victim 選擇。
4. 新增 `n_spac_nonfinite` / `n_spac_lru_fallback` 計數器 + 一次性 stderr 警告，
   讓「utility 非有限」不再靜默地把 SpAc 停用。

### 同時修掉的工具問題

## 18:45–19:00 — 寬/窄 chunk：llama-bench 的批次语意 + 为何寬不稳

### llama-bench 用哪个（读源码定案，`tools/llama-bench/llama-bench.cpp`）

### 兩個踩坑（都已修，值得記住）
1. **ABA 競爭**：第一版把取樣放在 `addCompletedHandler` 累加到 atomics，`take()` 用

   數學上不可能）。**指紋：union > sum。** 改成直接讀已完成的 buffer 物件即完全無競爭。

### 真正的根因：**gather 輸出被 ggml-alloc 疊到同一個 buffer**

加上 provenance 欄位後第一次讀就命中（`Backup/cgc_logs/llama_server_20260915_203053.log`）：

```
ids_name='ffn_moe_slots-1'  ids_op=VIEW  ids_view_op=GET_ROWS  ids_data=0x128179d60
ids_name='ffn_moe_slots-2'  …                                 ids_data=0x128179d60

… 11 層裡 10 層同址（只有 layer 3 是 0x1281f12a0）
```

所以 `id_oob=16/16` 幾乎每層都中，而「值」是**上一個佔用該記憶體的 F32 張量**

修法：對 `ggml_get_rows` 的**輸出**（不是 reshape view）呼叫 `ggml_set_output`。
（view 不單獨配置，旗標必須落在 ggml-alloc 真正 sizing 的那個張量上。）

  寫 0 只影響最後寫入的那一層，其餘層讀到的還是別層／上一輪的殘留。

### I. 22:0x dispatcher 中性是「逐圖」性質，不是全域常數

用戶問「你這意思是說不同的 dispatcher 不可能過 m1/m2/m3 oracle bit identical?」。查證後答案是**三分**，
且與直覺相反：

- **基準圖：兩個 dispatcher 都給 `dc055e63`** ⇒ dispatcher 對基準**數值中性**，oracle 兩個都能過。
- 先前看到的 `p25-gputime` 有 3 個 digest（`28097996`/`3d8fa55f`/`dc055e63`）**不是** dispatcher 效應，
  而是**生成長度效應**：N=100 / N=40 / N=24。**所有 N=24 的跑都是 `dc055e63`**，含分段與非分段。
  又一次印證「md5 只在同 build 指紋 + 同 `predicted_n` 下可比」。
- **S1 真臂：兩個 dispatcher 都過不了，形態不同**——分段 = **不穩定**（同 build `131bc531/9729ad35`、
  同 N=24、3 輪 3 值）；非分段 = **穩定但錯**（`ff68c5a2` ≠ 錨）。
- ⇒ 真正的危險不是「一定不過」，而是**擲骰子**：圖不穩定時 bit-identical 閘門**失去判別力**，
  若參考序列來自某一次分段跑，另一跑可能碰巧命中而**假通過**。

**閘門形狀其實是健全的**（查 `scripts/check/m123_oracle_gate.py`）：

- `CGC_OA_ASYNC` **不在** `DIAGNOSTIC_KEYS` ⇒ ref/now 的 dispatcher 不同時 `diff_stamp` 會判 incomparable。
- `CGC_SLOT_TABLE_GPU` **在** `DIAGNOSTIC_KEYS` 是**刻意的且正確**（行 98-104 註解）：它宣稱「不改數值」，
  若宣稱是假的，閘門應該在 **logits** 上失敗——而 S1 現在正是這樣失敗的。
- ⇒ 要補的不是 comparability，而是一條**前置條件**：閘門必須先證明受測圖本身可重現。

### J. 內核側讀數的實作定位（已勘查，未動手）

`mul_mat_id` 有**兩條**路徑，且 **MM 路徑有一個真正的 ids 轉換步驟**：

| 路徑 | 觸發 | kernel | kernel 消費的 ids |
|---|---|---|---|
| **MV**（decode 單 token） | `ne21 < 32` | `kernel_mul_mv_id`（`ggml-metal.metal:11463`） | `ids` = **`bid_src2` 直接**（ops.cpp:3650，buffer 4） |
| **MM**（prefill / 多 token） | `has_simdgroup_mm && ne00>=64 && ne21>=32` | `kernel_mul_mm_id_map0` → `kernel_mul_mm_id` | **`hids`**（=`bid_ids`，ops.cpp:3554/3591），**非** `src2` |

⇒ capture 必須掛**兩個點**；MM 路徑下「kernel 實際解碼出的 ids」是 `hids` 而不是 `src2`。

綁定同一個 ids buffer + 一個**專用、不受 allocator 管理的 shared buffer**，把前 N 個 int32 寫進 `slot`。
理由：不改 graph ⇒ 不擾動 allocator 佈局（避免 `p25-buildleaf` 那種觀察者效應）；同 command buffer
⇒ 執行順序保證在消費 kernel 之後。
