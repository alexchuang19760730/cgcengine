## --install-hook 路徑修復（01:00，commit `00b70bebc` + `bd2ca8a82`）

上一輪列為「只記錄未修」的那一項已落地。

### 缺陷不是理論風險，有活體證據

- `git rev-parse --absolute-git-dir` ⇒ `…/flashkv0516/.git/worktrees/flashkv-devserver`（worktree **私有**目錄）
- `git rev-parse --git-path hooks` ⇒ `…/flashkv0516/.git/hooks`（**common** 目錄，git 讀的那個）
- 舊碼寫到私有目錄裡留下的 `pre-commit`（2026-09-09 12:44）指向

  2026-09-04 的那顆舊動態 hook。與 skip0、LOOP_GUARD 同一家族：**以為 ON 其實從未 ON**。

### 關鍵陷阱：「一行改動」按字面做會更糟

`--git-path` 會回**相對路徑**。基準是 **git 的 cwd**（＝ `$REPO_ROOT`），**不是 script 的 cwd**。
- 從 main worktree 自己看 ⇒ `.git/hooks`（相對）；從 devserver/base 看 ⇒ 絕對。
- 沒錨定就寫 `$HOOK_DIR/pre-commit` ⇒ 落到 shell cwd 的 `<linked-worktree>/.git/hooks`；
  而 linked worktree 裡 `.git` 是**檔案** ⇒ `mkdir`/`cat`/`chmod` 全失敗、**仍印成功、exit 0**。
  實測 `ls: Not a directory`。**比原缺陷更糟**（原本至少留下一個可搬的檔案）。

### 修法（連帶兩件必要事）

1. `--git-path hooks` + `case` 錨定成絕對路徑（相對就接 `$REPO_ROOT/`）。
2. 落點變成**共用**的 common dir ⇒ 產生的 hook 本體必須**執行時**解析 `REPO_ROOT`。
   舊本體寫死 `--repo <安裝當下的 worktree>`，現在從別的 worktree commit 會去驗**錯的 repo**
   ⇒ 在守護 dylib 追蹤的那道閘門上製造偽 PASS。`BIN_DIR` 保持 repo 相對同理。
3. 蓋掉活 hook 前自動留 `.bak.<timestamp>`；新增**死雙胞胎偵測**（私有 hooks 目錄還有 `pre-commit` 就 WARN）。
   偵測要先比對兩目錄——在 main worktree `--absolute-git-dir` **就是** common dir，
   不比對會對活 hook 誤報（我第一版就誤報，測試時抓到才修）。

linked worktree → 寫到 common dir + hook 跑綠（exit 0）；main worktree（相對路徑分支）→ 錨定正確；

### 11. 項目 2（root 的 GPU 頻率）——本輪無法執行，但修掉了儀器的一個真缺陷

**結論先寫：這一步只能由使用者手動執行。** 三條路都實測關閉：

| 途徑 | 實測結果 |
|---|---|
| `sudo`（含關閉沙箱） | `/usr/bin/sudo` 有 setuid，但**執行被拒**：`operation not permitted: /usr/bin/sudo`。這不是工作區沙箱（`dangerouslyDisableSandbox` 亦然）⇒ 特權升級在更外層被封鎖 |
| `powermetrics` 無 root | `powermetrics must be invoked as the superuser`（硬拒絕） |
| `ioreg -c IOAccelerator` | 只有 `Device Utilization %` / `Renderer Utilization %`（利用率），**沒有 clock 鍵**；`sysctl *iogpu*` 只有記憶體水位 |
| IOReport（無特權訂閱） | 已證負面（`ioreport_gpu_pstate_probe.py`） |

⇒ **GPU 頻率在本機確實只有 root powermetrics 一條路。**

**使用者的指令（複製即用）：**
```sh
cd /Users/alexchuang/Documents/flashkv-devserver
sudo -v                                    # 先快取憑證
scripts/check/powermetrics_gpu_freq.sh     # cold/hot 對，約 4 分鐘
# 跑完它自己會 parse；也可事後補看：
scripts/check/powermetrics_gpu_freq.sh --parse Backup/cgc_logs/powermetrics_prefill_*.log
```

**修掉的儀器缺陷（我自己上一輪寫的）：** `--parse` 原本用 `grep -o` 抓四個標籤再 `paste`。
標籤本身是**對的**——本輪用三個獨立來源核對過真實格式（含 production Go parser），實際輸出為：
```
**** GPU usage ****
GPU HW active frequency: 1277 MHz
GPU HW active residency: 99.35% (396 MHz: .06% 528 MHz: 0% 720 MHz: 0% 924 MHz: 0% 1128 MHz: 0% 1278 MHz: 99%)
GPU SW requested state: (P1 : 0% ... P6 : 100%)
GPU idle residency: 0.65%
GPU Power: 8503 mW
```
**但**它有兩個真問題：
1. **丟掉括號裡的 DVFS residency 分佈**——那才是「時脈限制 vs 功耗上限」唯一能分辨的地方。
   單一 `GPU HW active frequency` 會把分佈壓成一個數：兩個狀態可以報同一個 active frequency，
   卻佔用不同的檔位組合。時脈被壓的指紋是**質量整片移出最高檔**。
2. 一次 4 分鐘、`-i 500` 的擷取 = 每條序列約 480 個數，而問題是**冷熱對比**，不是序列 ⇒ 叫人用眼睛做分段與平均。
3. 而且標籤字串**從未對真實輸出驗證過**（在 repo 內只出現在一句敘述性註解裡）。

**修法：** 新增 `scripts/check/powermetrics_gpu_freq_parse.py`，`--parse` 委派給它。
- 以 **GPU Power** 分段成「活動區塊」（**刻意不用頻率或 residency 分段**——那正是待測量，
  用它定義「一次跑」等於竊取結論；功率把 idle 數十 mW 與 prefill 數十 W 分開三個數量級）。
  區塊 0 = cold，其餘 = hot。
- 印 cold/hot 對比表 + **逐檔位 residency 分佈表**（標出移動 ≥5pp 的檔位）+ residency 加權有效時脈。
- 給出三選一判準：**CLOCK（同樣工作、較低時脈）** / **POWER CEILING** / **GPU KEPT OFF THE WORK**。
- **標籤變更時大聲失敗**：印出實際看到的 GPU 行，而不是四條空序列。
- `--selftest` 4/4（四種判準各一）。合成樣本測過真實格式：3 個區塊正確分段、
  最高檔移動 −99.4pp、判準 CLOCK。
- `OUT` 預設從 `~/Desktop/` 改到 `Backup/cgc_logs/`（證據與證據同放；`Backup/` 已 gitignore，不會弄髒樹）。

**教訓 `eng-gate-0017`**：儀器「有在動」不等於「有量到要量的東西」；
而一個**能安靜印出空序列**的解析器與「只能分辨 PASS/FAIL、不能分辨 PASS/SKIP」的閘門是同一類缺陷。

**報告同步修正（§8 第 2 項 + §6 缺陷表）：** 順手抓到一個**會實際誤導使用者**的錯誤——
報告原本寫的指令是
`powermetrics_gpu_freq.sh --seconds 180 --out ~/Desktop/pm_prefill.log`，
但腳本**只認 `--parse`**，`--seconds`／`--out` 會被**靜默忽略**而跑預設值（`IDLE=180 RUNS=3`，

### 13. Blocker B：卡住的是證據，不是難度

`docs/M1_POOL_SPLIT_COST_2026-09-14.md` §4 引的三行：

```
CGC-PRE:  il=1 st[0]=-1 st[1]=1 … st[7]=7
CGC-POST: il=1 st[0]=1  st[1]=1 …
CGC-SLOT: il=1 remap=[1 2 3 4 5 6 7 8]
```

**用程式碼判定：這三行不可能同時為真。** 在 `llama-context.cpp`：
`:5796`（PRE）、`:5853`（POST）、`:5879`（SLOT）各自呼叫同一個
`llama_expert_cache_slot_table(cache, il)` ——同一份 `slot_table` 的同一列；
`:5861-5867` 的 `rd[i + j*n_expert_used] = st[e]` 是 remap 的**唯一**寫入，
且在 `:5855` 與 `:5879` 之間**沒有任何對 `st` 的變動**。
⇒ 同一次 invoke 內 `st[ids[1]]` 與 `remap[1]` **按建構必然相等**。文件卻給出
`st[1]=1`（POST）與 `remap[1]=2`（SLOT），且 POST 那行被 `...` 截斷，
**無法判斷是哪一筆抄錯、或兩行來自不同 invoke**。所以 blocker B 不是「難修」，
是**文件不足以定位**；照它去改 `pick_slot` 是猜。

順帶（**未證實的**第二假設）：`remap=[1 2 3 4 5 6 7 8]` 對 `ids=[0 1 2 3 4 5 6 7]` 而言就是 `ids+1`，
是一個**均勻 +1 位移**——與「兩個 expert 共用一個 slot」是不同的病，更像 pool region 的
讀取基準／stride 差一個 slot。重拍證據時要同時對照這兩個假設。

**修好它換到什麼（誠實版）：不是吞吐。** §5 已 reject work item 1，且 §4 的 blocker A 是**不變式**
（clamp 在兩種模式都成立）⇒ 不會拿回 prefill 吞吐。真正的收益是：
(a) owned pool 從「載入成功、adopt 120 區、然後數值爆炸」變成**可用原語**（配置半邊已證便宜：
6.32 GiB / 3 buffers，無 residency 爆炸）；
(b) 它會回答「既有 pool 路徑的安全性有多少來自 `pool == tensor storage` 這個偶然恆等」——
任何人動 loader shrink／pool 幾何／M2 slab 時都會被問到；
(c) 消掉一個 landmine：`CGC_POOL_SPLIT=1` 目前是「載入成功＋大聲警告＋NaN＋Metal SIGSEGV」。

**下一步（便宜且受限）：不要修，先重拍。** 現成儀器就在 `:5803-5815`：`CGC_EXACT_PATH_DBG=1`
會印出每個 union expert 的 `slot= owner= loading= queued=`，正是「slot 為何被發兩次」所需的欄位。
一次 run：`CGC_POOL_SPLIT=1 CGC_POOL_SPLIT_DBG=1 CGC_IDENT_VERIFY=1 CGC_EXACT_PATH_DBG=1`。

## Blocker B 已解（2026-09-16 下午）：不是需要重拍，是引文抄錯

**上面那個「+1 位移」的第二假設是對的，而「兩個 expert 共用一個 slot」是誤讀。**
原始日誌 `Backup/cgc_logs/llama_server_20260914_094821.log:324` 寫的是 `st[1]=2`，
白皮書與 `M1_POOL_SPLIT_COST_2026-09-14.md` §4 都抄成了 `st[1]=1`。改成 `st[1]=2` 後三行
逐格自洽（`remap[i] == st[ids[i]]`），`CGC-SLOT` 印的四個值就是 `st[0..3]` ⇒ 矛盾消失，
也**不需要重拍**（重拍在這台機器上本來也做不到：split 配置 10 GiB 與 4 GiB 兩預算都在
warmup 掛 `CGC-METAL-FAIL ... Insufficient Memory`）。

**根因（三個都對的設計疊起來）**：
1. `prepopulate` 的 identity 填充把池**填滿**，且每個 `slot_last_use` 都是 0
   ⇒ LRU 犧牲者＝最低未被跳過的那格。
2. `pick_slot` 的淘汰**會清掉被犧牲者的 slot 表條目**
   （`llama-expert-cache.cpp:~555`）⇒ 一次 eviction 對同一 batch 的其餘成員是**可見的**。
3. `ensure_batch` 的 `batch_owned` 是**和 miss 指派同一個迴圈**增量填入的
   ⇒ 只有「已走過」的成員受保護。註解宣稱的 exact-set invariant 從未被實作。

⇒ 一個冷 expert 讓 `ids=[0..7]` 整批變 miss，每個成員拿到後面那個的 slot ⇒ `st[e]=e+1`。

**修法（已實作在出貨碼）**：`ensure_batch` 拆兩趟（pass 1 認領所有 resident，pass 2 才配 miss），
pass 1 另外**收養 in-flight fill**（`slot_owner` 已設、`slot_queued/loading` 已設而
`slot_table[e]` 未發布者，舊判定只看 `slot_table[e]` ⇒ 會給它第二個 slot），
新計數器 `n_hit_adopted_queued` 讓它可見；新增閘門 `LLAMA_EXPERT_CACHE_BATCH_INVARIANT=1`
（已接進 `run_server.sh` 的 `SERVER_ENV` 白名單）。

**證據**：`scripts/check/expert_cache_ensure_batch_order.cpp`（不需模型／伺服器／IO，
直接連 dylib 裡真正的 `ensure_batch`）。HEAD：`st[0]=1 … st[15]=16`、0 hit/16 miss、FAIL
（**逐字重現** 09-14 日誌的映射）；修好：`st[0]=16, st[1..15]=1..15`、15 hit/1 miss、PASS。
D5 閘門 PASS（M1/M2/M3 各 9/9，cross-tab 9/0/0/0）⇒ 非 split 配置下數值惰性是**測到的**。

**兩條誠實界線**：非 split（出貨預設）的池在 warmup 從不填滿 ⇒ 此修法在該配置是 **no-op**
（stash 換臂重跑，新舊二進位 `CGC-PRE/POST/SLOT` **逐位元相同**）；split 的真機驗證做不了（warmup OOM）。
4 GiB 修好臂跑到 **il=39**（09-14 在 il=2 掛）並報 `CGC-BATCH-INVARIANT: il=1/2 OK`，
但同樣 OOM ⇒ 那是存活度改善、不是品質結果。

**verdict 不變**：M1/W3 仍應 reject，但現在只站在**一個** blocker（wide 路徑，結構性）上。

**踩到的坑（值得記）**：在 dylib 兩側以指標傳遞的 struct 加成員是**連結器看不見的 ABI 破壞**。
`git stash` 做 A/B 後 pop 沒重建 ⇒ `build/bin` 留著舊佈局，測試 SIGSEGV 在
`ensure_batch +1068`（讀到 `n_slot_table_unchanged` 當 data pointer）。診斷四步：
`nm -gU` → `offsetof` 探針 → `strings` 找新增字串 → `stat` mtime。

## 15:0x–15:3x：條件找到了 —— 它是一個 11 ms、不需要 root 的讀數

### S.4 為什麼不把 `agent_harness/` 拆成獨立 git repo（證據）

`agent_harness/` **刻意不是自足的子樹**——它的索引機制就是設計來指向**它外面**：

| 腳本 | 硬編的路徑假設 | 拆出去會怎樣 |
|---|---|---|
| `index_assets.py` | `REPO = HERE/../..`；索引 `scripts/check/*`、`docs/*`、`Backup/cgc_logs`、`.workbuddy/memory/*.md` | 全部 `exists:false`，manifest 變成一串 dangling pointer |
| `build_memory_index.py` | `REPO = HERE/../../..`；`MEM_DIR = REPO/.workbuddy/memory` | 指向不存在的目錄，索引直接做不出來 |
| `emit_episodes.py` | `find_repo()` 往上找 `.git` | 一旦 `agent_harness` 有自己的 `.git`，它會**停在那一層**，從此看不到 `Backup/` |

⇒ 巢狀 repo 會讓每一列索引失效並斷掉 episode 匯出。附帶代價：submodule 的 gitlink 讓主 repo 看不到
檔案層變動 ＝ 這個專案最厭惡的**安靜漂移**。
**替代方案**（若真需要一條乾淨的同步線）：維持單一 repo，另開一條只提交 `agent_harness/` 的
**subtree 分支**，或 `git subtree split`。兩者都不引入巢狀、也不破壞相對路徑。
