### ⇒ 機制（這解釋了為什麼控制臂也不合格）
`logits` 是 2048 層 × 256 專家累加的 fp32/bf16 量。**任何**讓 GPU 執行順序改變的東西
（柵欄、submit_ahead、甚至 kernel 排程）都會改變**加法結合順序** ⇒ 末位 ulp 差異
⇒ step N 的 logits 有 1e-3 量級差 ⇒ **下一個 token 的 KV 就不一樣** ⇒ step N+1 偏差更大。
⇒ ★ **這是「逐位元等同」在長跑 decode 上的結構性不可能**，不是某一個 flag 的 bug。
   它與記憶裡 `docs/MTP_BITIDENT_CLOSEOUT_2026-09-28.md` 的結論**同源**。

### ★★ 為什麼控制臂只有 78/222而 `ovlfence-check` 有 222/222
⇒ 那不是柵欄「有時好有時壞」，是**兩條 run 的漂移路徑不同**。
`ovlfence-check` 的 ref 是 `ref_ovlbase_20261002.jsonl`（`ref_md5=0cf5c593…`），
其他 7 份用的是 `ref_nonmtp_longgen_v1_20261002.jsonl`（`ref_md5=a3fbfb0c…`）。
⇒ ⚠️ **兩組用了不同的 reference，所以 78/78/99/6/6/220 彼此不可直接比。**
   真正的對照組只有 `ovl-ctl-8c`(78) / `ovlrep-ctl1`(78) / `ovlbase-check`(78) —— **控制臂穩定在 78**。
⇒ ★★ **修正我 01:0x 的判讀**：不是「非確定性」，是
   **「fence 臂對該 ref 是 6，ctl 臂對該 ref 是 78；換 ref 後 fence 臂可達 222」**。
   仍屬不可引用，但**成因是「ref × 臂」的交互作用＋金際漂移**，不是隨機。

## 14:2x ★★ **`warm-skip 64` 有效，而且**它正是抓「熱 cache performance」的工具

operator 問「能夠讓 warmup 64 還是保留，這樣才能抓到熱 cache performance？」⇒ ★★ **能，而且機制上它是對的工具。**

### ★★★ 決定性證據：**斜坡是 MTP 專屬的，off 臂沒有斜坡**
原始順序（未排序）：
```

a2_t00_n3（MTP on） ：[ 9.93, 13.16, 16.02, 16.72, 16.16]    ← ★ 三個 rep 才爬上去
```
⇒ ★★ **若是「第一個 rep 冷」，off 臂也該有斜坡。它沒有。**
⇒ ⇒★ **斜坡的來源是 MTP 路徑特有的**：MTP 的 draft token 會碰到
   **off 臂永遠不碰的專家**，而 8 GiB 池要**逐rep 填入**那些頁。
⇒ ⇒★ **`warm-skip N` 正是為此設計**（`llama-bench.cpp:474-488`）：
> 「**drops the first N tokens of EVERY rep**」；並明說它與 `platform_ts` 是不同問題
> （後者丟掉整個 rep＝"the first rep is cold"，前者是每個 rep 的前 N token）
⇒ ⇒★ **每個 rep 都先跑 N 個不計時的 token ⇒ 每個 rep 都在計時前把池填好。**

### ★★ 而這解釋了 14:1x 那個「swap 多反而快」的矛盾（機制層）
★ **池的常駐性是跨行程的系統狀態**：

- 13:55 那趟：重開機後 swap=0 ⇒ **冷 page cache** ⇒ 爬得慢、落到 **13.65**
- 而 **off 臂的頁集小到兩種狀態下都常駐** ⇒ 兩次都是 11.5
⇒ ★★ **「重開機才乾淨」是個陷阱**：它給你乾淨的 swap，卻給你**冷的池**。
⇒ ★⇒★ **正確的目標不是「乾淨」，是「熱」。** 而 `warm-skip` **在 run 內**兩者都能給。

### ★ 成本（實測依據）

### ⇒★ 這一步還能順手修掉 14:1x 揭出的第二種失真

- ⇒★ **`avg_ts` 從此可用**，而 gate 讀的正是它
⇒ ★ 這比在 `drift_adjudicate`／`bench_ledger` 事後偵測斜坡**更好**——
