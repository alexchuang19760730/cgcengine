③ 瓶頸分類：SSD 頻寬 / CPU / GPU compute / GPU memory bandwidth

用測量數據逐項排除，答案是 GPU memory-bandwidth-bound（unified memory 讀 MoE weights）。SSD / CPU 已不是瓶頸。

SSD（內建 NVMe）

非瓶頸 · 頻寬利用 ~9%

preads 6.9M usec（8 worker 累計）÷ 8 ≈ 0.86s / 7.9s wall ≈ 11%，且多在冷啟動 + draft。file_reads≈4161 × ~740KB/read ≈ 3.1GB → ~450MB/s，遠低於 M4 內建 NVMe（~5GB/s 級）。CGC_VERIFY_DECODE 已把 verify 同步 pread 藏掉（26M→6.9M usec）。SSD 是 latency-bound 小隨機讀，不是頻寬瓶頸。

CPU（MTL encoding）

非瓶頸 · 已藏

CGC_OA_ASYNC + CGC_N_CB=8 把 MTL encoding（60→30ms）藏在 GPU compute 後面重疊；post_sync ~0.2ms；draft + driver 只剩 ~3.9ms/token。CPU 不在 critical path。

GPU compute（kernel 執行）

低 · 有 bubble

IQ3_XXS 量化後 FLOPs 便宜；M4 Max FLOPs 遠高於需求。但有 ~2000 kernels/step 的 dispatch bubble（~38ms，舊報告）與 encoding 重疊——這是唯一可省的 GPU 側項目（kernel fusion）。

GPU memory bandwidth

原判主瓶頸 · 已被 ⑦ 修正

FFN 每 token 從 unified memory 讀 routed experts weights：30.9ms/token（MTP batch）。全 model 12.3GB 讀一次 @ M4 Max ~546GB/s ≈ 22.5ms，與舊報告 weight-read 24.9ms 一致 → 原本以為 就在 bandwidth envelope 上。quant 越低（IQ3）weight-read 越小，這是「能跑」的關鍵。

已被 ⑦ 證偽 kernel 級 probe（temp/bw_probe.cpp）實測 FFN mmid 有效頻寬只有 5-45 GB/s = peak 的 1-8%，是 latency/occupancy-bound（每 dispatch 固定 ~0.4ms），不是 546GB/s envelope。FFN 的 ~31ms/step 可修（見 §⑦），「不可省的 bandwidth floor」不成立。

一句話：速度由 GPU 讀 MoE weights 的 unified-memory 頻寬決定（~31-35ms/token）。SSD 頻寬只用到 ~9%、CPU 已藏、GPU compute 有 bubble 但被 encoding 蓋住。沒到 SSD bandwidth 瓶頸。 ⑦ 修正 但「頻寬」不是 546GB/s envelope：FFN mmid 只跑到 1-8%（latency floor），見 §⑦。

方法：① isolated（單 op，sync 每 rep，取 min）與 sustained（200 個 graph 串流、每 20 個 sync——排除 per-graph encode 假象）；② in-graph（40 層 × 80 個 mmid op 塞進同一個 graph_compute，最接近真實 verify）。bytes = n_tokens × n_used 個 expert slab。gate/up = IQ2_S（m=512, k=2048）、down = IQ3_XXS（m=2048, k=512）、256 experts、top-8。

結論 1：有效頻寬只有 1-8%，不是「7 成」也不是「envelope」。FFN mmid 的 weight-read 以 5-45 GB/s 在跑——比 §3 主張的 546GB/s envelope 低一個數量級。但「同一批 40 層 × 3 token 的 FFN 總量 ≈ 31.4ms」與 §1 的 FFN 數字吻合，所以 doc 的 FFN 時間對、原因錯：不是 bandwidth-bound，是 latency/occupancy-bound。

結論 2：三個證據指向 latency floor，不是 bandwidth。① 時間不隨 bytes 線性成長：2.69MB→0.52ms、24.18MB→0.66ms（9 倍 bytes 只多 1.27 倍時間）；fit 出每 dispatch 固定 ~0.4ms + marginal ~150GB/s。② sustained ≈ isolated（pipeline 串流沒省到）→ 不是 per-graph encode 假象。③ in-graph 的 per-mmid（0.392ms）≈ isolated per-op（0.29-0.52ms）→ 塞進 40 層大 graph 也攤不掉 → 是每個 kernel 自身的 GPU 固定延遲（小 grid、低 occupancy、memory latency 藏不住）。

結論 3：sequential access 早已成立。每個 expert slab（270-400KB）本身連續，mmid 直接順序讀；FFN 路徑根本沒有 `ggml_get_rows` 式 gather。所以「access-pattern（sequential / aligned）→ 7成→9成 → 28-30」前提錯誤，關閉。正確槓桿是 減少 dispatch 數 + 加大每個 kernel 的 grid（bytes/dispatch 變大時效率上升：5→36 GB/s）——即「併層 mmid」（多層 experts 塞進同一個 kernel）。

對 verify 87.2ms 的重新歸因：FFN mmid ≈ 31ms（36%，latency floor、可修）；其餘 ~56ms 是 10 層 full-attn + 30 層 linear-attn(SSM) + norms + head + ~2000 個小 kernel 的 dispatch/latency——這一塊尚未逐項分解（§⑦ 只證實 FFN 部分）。

⑧ 為何「blk.40 進 cache + 多 token 攤薄」沒自動到 30 t/s

直覺：non-MTP 25 t/s，verify 3-token 攤薄 20-27%，30 應該很容易。答案是 「攤薄有發生，但被兩筆沒進到直覺的成本吃光」。

項目數值說明
verify 跑的是完整 40 層 trunk（不是 blk.40） 87.2 ms/step draft 才是 blk.40 單層（speculative-simple.cpp L383-390：`llama_decode(ctx_tgt, [id_last, drafts])`）。blk.40 進 L4 pool 只省 draft 的 weight-loading（27.5ms/step 仍要跑 5 個 token-run），與 verify 的 87.2ms 無關——verify 必須用「真模型」確認 draft，一定跑全部層。
攤薄確實存在 29.1 vs 39.8 ms/row 3-token verify 87.2/3 = 29.1ms/row，比單 token 39.8ms 低 27%（共享 experts + 攤薄固定成本）——你期待的效益是真的、已入帳。
但 step 只出 2.9 個 token（不是 3） 95.7% accept n=2 的 step = [id_last + 2 drafts]，最多 3 個 output；實測 2.9 → 每 step 有 0.1 個 token 被拒（MTP head 品質）。公式（§1）：(3×29.1 + 5×5.5) / 2.9 = 39.4ms/output-token。
blk.40 MTP head 是 24% 的固定成本 27.5 ms/step draft+process 5 個 token-run × 5.5ms，MTP 架構自帶、與 verify 序列化（依賴 h_nextn），無法藏。這筆不在「攤薄」的直覺裡。

所以「30 很容易」的漏洞：攤薄攤的是「每行成本」（39.8→29.1），但 MTP 每 step 付 3 行的錢 + blk.40 27.5ms，只拿 2.9 個 token。全 accept（3 tokens/step）且 blk.40 免費時：3 / (87.2+8.5) = 31.3 t/s——那才是「30 很容易」的場景，現在兩者都沒達成。

要 30 t/s（= 33.3ms/token）需要省 6.1ms/token = ~17.7ms/step，只有兩個 ~17ms 級來源：
① model 側砍 blk.40 head（27.5ms/step → 砍半 ~13ms）：step → ~98ms → ~29.6 t/s；
② kernel 側修 FFN latency floor（§⑦：31.4ms → ~15ms，併層 mmid）：verify → ~71ms → step → ~98ms → ~29.5 t/s；
③ 兩者都做 → ~34 t/s。不是自動攤薄能到，是上面兩條有界的工程。 ② 已被 §⑨ FFN_GU1 證偽

併層 mmid prototype（a 完成，負面結論）：FFN_GU1 把 gate+up 併成單一 1024-列 mmid（120→80 次 mmid dispatch），40 層只省 0.137ms（每省 1 次 dispatch ≈ 3.4µs）。→ FFN 不是 dispatch-bound，是 per-mmid kernel 的 latency/occupancy-bound（small grid、低佔用，與 §⑦ 的 1-8% 有效頻寬一致）。併層不改「每層要算的 expert 列數」，只是少排幾次 dispatch，而 dispatch 早已藏在 kernel 執行下。⇒ 槓桿②「併層 mmid → 31.4→15ms」證偽、關閉。

turbo 式 per-expert batched GEMM 驗證（c 完成，同樣負面）：既然 ② 併層無效，進一步驗證「單 dispatch 多 expert 加大 grid」（§⑦ 結論 3 的正確槓桿）——FFN_PACK 把 G 層 experts 疊進單一 mmid dispatch（weight [k,m,G×256]、batch=G×3、grid z=24G），掃 G={1,2,4,8}：dispatch 數 80→10、grid z 24→192，總時間只從 22.34→22.14ms（1.01×）。→ 真實 verify 的 chained graph 已被 Metal 同 stream 管線化，GPU 在 dispatch 之間不閒置，isolated 的「每 dispatch 固定 ~0.4ms」早已藏掉（chained 下 per-mmid 只 0.19ms）。FFN floor 是 sustained kernel-throughput bound（~16 GB/s 有效），不是 dispatch 數、也不是 grid size。要動它只剩：① MM 路徑（simdgroup_mm，需 batch≥32，3-token verify 到不了）；② 自訂高佔用 kernel（本 fork 結構上不支援）。turbo 併層也證偽 → 30 t/s 只剩 §⑧ ①「model 側砍 blk.40 head」一條有界路線。
