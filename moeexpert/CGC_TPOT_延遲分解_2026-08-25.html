拆解結論：CGC_VERIFY_DECODE 把 verify 的同步 pread 藏掉/省掉——固定 overhead 58.7→13.6ms/step（-77%），且 per-token 也從 44.5→30.9ms（exact 路徑每 token 還在等 pread，decode 路徑純 compute）。3-token batch 的 marginal FFN 30.9ms/token < base 單 token 39.8ms——batch 共享 experts + 攤薄固定成本，MTP 的 FFN 反而比單 token decode 便宜（overlap 效益）。

③ 瓶頸分類：SSD 頻寬 / CPU / GPU compute / GPU memory bandwidth

用測量數據逐項排除，答案是 GPU memory-bandwidth-bound（unified memory 讀 MoE weights）。SSD / CPU 已不是瓶頸。

SSD（內建 NVMe）

非瓶頸 · 頻寬利用 ~9%

preads 6.9M usec（8 worker 累計）÷ 8 ≈ 0.86s / 7.9s wall ≈ 11%，且多在冷啟動 + draft。file_reads≈4161 × ~740KB/read ≈ 3.1GB → ~450MB/s，遠低於 M4 內建 NVMe（~5GB/s 級）。CGC_VERIFY_DECODE 已把 verify 同步 pread 藏掉（26M→6.9M usec）。SSD 是 latency-bound 小隨機讀，不是頻寬瓶頸。

CPU（MTL encoding）

非瓶頸 · 已藏

CGC_OA_ASYNC + CGC_N_CB=8 把 MTL encoding（60→30ms）藏在 GPU compute 後面重疊；post_sync ~0.2ms；draft + driver 只剩 ~3.9ms/token。CPU 不在 critical path。

GPU compute（kernel 執行）

低 · 有 bubble

IQ3_XXS 量化後 FLOPs 便宜；M4 Max FLOPs 遠高於需求。但有 ~2000 kernels/step 的 dispatch bubble（~38ms，舊報告）與 encoding 重疊——這是唯一可省的 GPU 側項目（kernel fusion）。

GPU memory bandwidth

主瓶頸

FFN 每 token 從 unified memory 讀 routed experts weights：30.9ms/token（MTP batch）。全 model 12.3GB 讀一次 @ M4 Max ~546GB/s ≈ 22.5ms，與舊報告 weight-read 24.9ms 一致 → 就在 bandwidth envelope 上。quant 越低（IQ3）weight-read 越小，這是「能跑」的關鍵。

一句話：速度由 GPU 讀 MoE weights 的 unified-memory 頻寬決定（~31-35ms/token）。SSD 頻寬只用到 ~9%、CPU 已藏、GPU compute 有 bubble 但被 encoding 蓋住。沒到 SSD bandwidth 瓶頸。

④ 剩餘槓桿：還有哪些可以藏、可以省

轉正後 MTP = base（25.4 t/s）。剩餘可動的是「非 FFN 的 8.5ms/token」+ GPU dispatch bubble。按難度排序。

務實結論：轉正已達成（verify 35.4ms < 40ms 門檻）。剩下最大、最可行的是 「藏 draft + verify 固定」（8.5ms/token → ~27-28 t/s）；要再往上走 quant（IQ2，→ ~33 t/s）或 kernel fusion / shared-KV，都是中等以上的工程 + 品質 A/B。若以「MTP ≈ base、不虧」為轉正標準，已收工可繼續 gemma4。

⑤ Quant / Dequant：已是最省 bandwidth 的槓桿，還有剩

既然主瓶頸是「GPU 讀 weights 的 unified-memory 頻寬」，quant 格式直接決定 weight-read 大小；dequant 時間則因為 GPU 是 bandwidth-bound（有閒置 compute）通常不在 critical path。

已省（最大槓桿，已入袋）：IQ3_XXS（3.06bpw）讓 weight-read 只有 FP16 的 1/3——沒有 quant 就無法 full offload（13.2GB > 11.45GB）也撐不起 bandwidth。UD 格式（Unsloth dequant）本身已是最省 dequant compute 的變體。quant 不是「還要省」的項目，是已經省下 3× 的項目。

dequant 時間：GPU 是 bandwidth-bound（等待記憶體），dequant compute 被 wait 蓋住 → 不是 critical path。真正要確認的是 verify FFN 走 inline-dequant matmul（直接吃 quantized weights，不做 separate dequant pass 寫中間 buffer）——若有 separate pass 會多一次 buffer read/write + 一次 dispatch，這才是要省的 dequant「時間」。

定案：MTP 的 batch overlap 效益是真的——3-token verify 的 marginal FFN 30.9ms/token 比單 token 39.8ms 低 22%（共享 experts + 攤薄固定成本）。所以 MTP 的天花板不是 28.6，而是 ~32（全藏 overhead）甚至更高（若 shared-KV 能省 id_last）。現在卡在「overhead 沒藏」與「dispatch bubble」，不是卡在模型。
