# 檢討報告書 v1.0 — 「garbage 輸出的 async expert-cache 代碼為何能被 commit」

日期：2026-08-22
範圍：`temp/llama_roadB/llama.cpp-master`（HEAD = 60fda93）
主題：Qwen3.6-35B 在 `CGC_OA_ASYNC`（Metal segmented async dispatch）+ L4 expert-cache pool 下輸出全為 `!` garbage，且此問題代碼已進入 git 歷史。

---

## 1. 事件摘要

- 使用者目標：Qwen3.6-35B 無 MTP 達到 25+ t/s 且輸出正確。
- 已 commit 的代碼（60fda93，commit message 宣稱「24.8 t/s、correct output、~0 disk reads」）在後續執行時輸出 **garbage**（`The capital of France is!!!!!!...`）。
- 使用者裁定：「所以你 checkin 的代碼是垃圾，不再允許這樣。」要求找出根因並寫檢討報告。

## 2. 根因（已用實驗證實）

### 2.1 主因：submit-ahead 的 remap race

`CGC_OA_ASYNC` 把 Metal graph 切成 ~40 個 segment（每個 segment 結尾是某層的 top-k/argsort）。設計是 **submit-ahead 管線**：

```
submit seg[i+1] ──► wait seg[i] 完成 ──► CPU hook 寫 remap[i] ──► GPU 執行 seg[i+1]
                        │                                        │
                        └── GPU 在 seg[i] 完成後立刻開始 seg[i+1]（in-order queue）
```

seg[i+1] 的第一個節點就是 **layer il 的 FFN**，它讀取 `ffn_moe_topk_remap-il`（remap leaf，host 寫入的 I32 input）。而 remap 由 **CPU hook** 在「seg[i] 完成後」才寫入。兩者之間沒有同步：

- hook 耗時實測 `cb ≈ 527~620µs`（含同步 `ensure_batch` 的 disk pread）。
- GPU 在 seg[i] 完成後立即開始 seg[i+1] 的 FFN，讀到的是 **上一輪的 remap / 未寫入的資料**。
- 一層的 remap 錯誤會向下污染整個網絡 → 所有 logits 退化 → sampler 每步輸出同一個 token（`!`）。

**實驗證據（決斷測試）：**

| 設定 | 速度 | 輸出 | 說明 |
|---|---|---|---|
| `CGC_OA_ASYNC=1` submit-ahead | 23.06 t/s | ❌ `!!!!` | hook 寫 remap 太慢，GPU 已讀舊值 |
| `CGC_OA_ASYNC=1` + `CGC_SUBMIT_AFTER=1`（先 hook 再 submit） | 6.72 t/s | ✅ 正確 | 序列化後無 race，但失去管線 |
| 關閉 `CGC_OA_ASYNC`（同步單 graph） | 0.71 t/s | ✅ 正確 | 無分段、無 race，極慢 |

### 2.2 前置已修復的 argsort race（非本次 garbage 主因）

- 修正前：`cgc_done` 只統計主 command buffer，而 top-k/argsort 在最後一個 chunk buffer，導致 poll 提前 fire、讀到未算完的 routing id。
- 修正（未 commit，工作區）：Metal 所有 n_cb+1 個 command buffer 都掛 completion handler + 暴露 `ggml_metal_cgc_bufs` + sched target 乘 bufs。
- 驗證：`CGC_ROUTE` 顯示 routing ids 已為有效 0-255 範圍（不再是浮點 bit-pattern garbage）。
- **結論：這條修好了 argsort 讀回 race，但 submit-ahead 的 remap race 仍在 → 輸出仍 garbage。**

## 3. 為何這種「垃圾代碼」能被 commit

### 3.1 這是 timing-dependent 的 heisenbug，不是必然失敗

race 只有在「CPU hook 寫 remap 的時間 > GPU 開始消費 seg[i+1] 的時間」時才爆發。換句話說：

- **幸運條件**：hook 夠快（pool 全熱、`ensure_batch` 全 hit、無同步 disk pread）→ remap 在 GPU 讀之前落地 → **輸出正確**。
- **不幸條件**：hook 變慢（pool 冷、同步 pread、file_reads 大量）→ remap 落地太晚 → **輸出 garbage**。

commit 當下的測試落在幸運區間：memory 記載當時 `file_reads=3921 → 6`（幾乎零 disk read），hook 只剩 memcpy（~2-3µs），因此 24.81 t/s「正確輸出」通過測試 → 被 commit。

### 3.2 測試方法學不足（可直接歸因）

1. **單次通過即 commit**：沒有反覆執行以暴露 flakiness，沒有固定 seed 的 bit-identity 比對。
2. **沒有「冷啟動」對照**：只驗證了熱 pool 的幸運路徑。
3. **多個改動疊在一起未分離**：n_batch cap、prewarm_hot、async prefetch、cgc_done 修復、submit-ahead 同時在樹上，無法歸因任何單一變數（`CGC_SUBMIT_AFTER` A/B 直到現在才補上）。

### 3.3 環境耦合放大

- `n_batch` cap 到 1（未 commit）關掉了 prefill 的 multi-token 路徑 → `record_routes` 只在 `n_tokens>1` 觸發 → **prewarm_hot 沒有路由資料** → pool 冷啟動 → hook 同步 pread 變慢 → race 爆發。
- 這是「commit 時能過、現在不能過」的具體機制：commit 時 prefill 走 multi-token、prewarm 有效、pool 熱；現在單 token prefill、prewarm 失效、pool 冷。

## 4. 驗證歷程與關鍵數據

| 步驟 | 結果 |
|---|---|
| 60fda93 重 build + run30（submit-ahead） | 23.06 t/s，`!!!!` garbage，hit rate 99%，file_reads=1287 |
| cgc_done 修復（n_cb+1 全 buffer 計數）後 | routing ids 有效（0-255），仍 garbage → **remap race 才是主因** |
| `CGC_SUBMIT_AFTER=1`（序列化 hook→submit） | 6.72 t/s，**輸出正確** |
| 關閉 `CGC_OA_ASYNC`（同步） | 0.71 t/s，**輸出正確** |
| 無 L4 pool 直接跑 | OOM（13.2GB > 11.45GB Metal limit）→ pool 無法移除 |
| async prefetch 診斷 | `prefetch=0/0`：pool 全滿（busy_before=174）→ 全 drop（resident），prefetch 實為 no-op |

## 5. 修復方向（尚未執行）

要同時拿到 **正確輸出 + 25 t/s**，必須消除 submit-ahead 的 remap race，而不是靠 timing 僥倖：

1. **GPU-side remap（正解）**：把 remap 從「CPU hook 寫入的 leaf」改成 GPU data dependency（`ggml_get_rows` from slot table，Metal ordering 保證）。GPU 由資料依賴自然等到正確 remap，無 CPU timing 依賴。memory 中已有此方向（「remap 必須轉成 GPU data dependency via ggml_get_rows with Metal ordering」）。
2. **縮短 hook 至 memcpy-only 並搭配有效 async prefetch**：讓 remap 寫入 ≤5µs，縮小 race window（風險：仍非嚴格保證，60fda93 嘗試過且失敗）。
3. **現在可用的正確 baseline**：`CGC_SUBMIT_AFTER=1`（6.72 t/s 正確）或關閉 `CGC_OA_ASYNC`（0.71 t/s 正確）——做為「正確性優先」的保守設定，速度待後續修復。

## 6. 教訓與流程改善

1. **效能優化涉及異步/多執行緒時，必須以「重複 N 次 + 固定 seed + 對照正確輸出」驗證**，單次通過不可信。
2. **冷/熱 pool 都要測**：async 快取優化在熱狀態下會掩蓋 race。
3. **改動須可 A/B 分離**：每個優化要有獨立 toggle（如 `CGC_SUBMIT_AFTER`），commit 前先做歸因。
4. **commit message 的正確性宣稱要有可重現證據**：宣稱「correct output」必須附固定 seed 的 bit-identical 或重複通過記錄。
5. **禁止把「沒接好/證偽」的代碼留進 commit**：`CGC_GLU_FUSED_DOWN`、未啟用的 prefetch 等 dead code 應在合入前移除或明確標記。
