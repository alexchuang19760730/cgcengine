llama.cpp fork（Expert Bounded Residency + CGC 優化）· M4 Max 16GB · 2026-08-20 · 對應 LLAMACPP_EXPERT_BOUNDED_RESIDENCY_FORK_方案.md

0. 這份文件是什麼

從源碼重建「生產級 libllama」的完整 build 步驟 + 所有 CGC/Expert-Cache 參數的實作細節。設計原理與 A/B 實驗證據見 moeexpert/LLAMACPP_EXPERT_BOUNDED_RESIDENCY_FORK_方案.md；效能分解見 moeexpert/CGC_TPOT_延遲分解_2026-08-20.html。

  • 目標：16GB M4 上跑 IQ3_XXS（13.2GB）全 offload（-ngl 99）不 OOM，保留真實記憶體餘裕，且 tok/s 貼近全 offload。
  • 核心手段：Expert 權重 Bounded Residency——資料在 CPU 記憶體（L1 index），GPU 上開「bounded pool」（L4 zero-copy Metal pool），active experts 直接從 pool 被 Metal FFN 零拷貝讀取；配合 CGC segmented async dispatch 把 GPU 排程管線填滿。
  • 實測（2026-08-20，qwen36 IQ3_XXS）：compute 34.2ms（= 29.2 t/s，已達 28.6 kernel 地板）、wall p50 38.8ms（≈25.8 t/s）、RSS 8.82GB、hit rate 70%+（file_reads=0，真 I/O 不上線）。

1. 生產級 build 步驟（3 步）

兩段式建構：先用 CMake 把 libllama + ggml 全家 build 成 build/bin 的 dylibs，再手動重鏈 llama-simple 對齊這些 dylibs（確保「源碼實作」與「二進位部署」同一套）。

Step 1 — CMake 建 libllama dylibs（scripts/build_fork_llama.sh）

scripts/build_fork_llama.sh

內部等價命令（關鍵旗標：GGML_BLAS=OFF / GGML_ACCELERATE=OFF / GGML_CPU_REPACK=OFF，這三個只要開 IQ3_XXS/IQ2_S 輸出就會壞）：

cmake -B temp/llama_roadB/llama.cpp-master/build \
    -DCMAKE_BUILD_TYPE=Release \
    -DGGML_METAL=ON \
    -DGGML_BLAS=OFF \           # 必 OFF：Accelerate/BLAS 造成 IQ3 輸出壞
    -DGGML_ACCELERATE=OFF \     # 必 OFF：同上
    -DGGML_CPU_REPACK=OFF \     # 必 OFF：踩 IQ3 tensor boundary
    -DGGML_OPENMP=OFF \
    -DLLAMA_CURL=OFF -DLLAMA_BUILD_SERVER=OFF -DLLAMA_BUILD_TESTS=OFF \
    -DCMAKE_CXX_FLAGS="-DMTP_SUPPORT"   # MTP staging API 進 libllama-common
cmake --build temp/llama_roadB/llama.cpp-master/build -j$(sysctl -n hw.ncpu)

產出 build/bin/{libllama,libggml,libggml-cpu,libggml-metal,libggml-base,libllama-common}.dylib。MTP 隔離：-DMTP_SUPPORT 只進 libllama-common（draft-mtp 需要 release_context()）；llama-simple 本身不帶此宏（見 Step 2）。

Step 2 — 重鏈生產 llama-simple（scripts/build_prod_binary.sh）

scripts/build_prod_binary.sh

用 -O3 -DNDEBUG -arch arm64 把 HEAD 的 simple.cpp（含 expert-cache env 支援 + CGC_STEP_TIMING）鏈到 Step 1 的 dylibs（-Wl,-rpath, 指向 build/bin）。llama-simple 不帶 -DMTP_SUPPORT（純非 MTP binary）；llama-speculative-simple 帶 -DMTP_SUPPORT 供 --mtp 用。

Step 3 — 生產啟動器（scripts/run_n30cache.sh）

./scripts/run_n30cache.sh -m qwen36 -n 128 -p "The capital of France is"

打包所有經 A/B 定案的環境變數 + -ngl 99 --no-mmap -t 8 -c 2048。--no-mmap 是凍機防護（mmap 9GB 冷頁風暴根因）。--mtp [N] 切 graft model（含 blk.40 MTP head）+ speculative-simple + -c 2048（解 OOM）。

2. 源碼實作細節（逐檔案）

commit b23fb51（feat(expert-cache): L4 zero-copy Metal pool + CGC segmented async dispatch）。全部 env 觸發、預設行為零變更。

2.1 llama-model-loader.{h,cpp} — L1 index + L4 pool capacity

  • L1 expert index：expert_cache_skip_load + expert_index——(layer, expert) → (file_offset, bytes, kind, type)，資料全來自 weight->offs（已是檔案絕對位置，含 data_start）+ get_tensor_meta，零新 GGUF 解析。
  • compute_l4_pool_capacity()：掃 GGUF metadata，budget → capacity。容量 = 2 × clamp(budget / (n_layers × per_slot), 8, 256)（per_slot = 各 kind expert bytes 總和）。
  • L4 縮維：create_tensor 對 _exps 且含 blk. 的張量，把 t_meta.ne[2]（expert 維）縮到 expert_cache_pool_capacity，但 保留正常 Metal buft（-ngl>0）——張量自己的儲存就是 pool region（zero-copy）。expert_cache_full_ne2 存真實 expert 數，供 L1 index 仍覆蓋「所有」expert（index 覆蓋 bug 根因修正，§7.9.2）。
  • l4_pool_tensors：記下每個 pool region (layer, kind, tensor, expert_bytes)，load 完由 llama.cpp 採納。
  • LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=1：blk.0 的 expert 張量留在 CPU（pool 排除修正，§8.35/8.36）。

2.2 llama.cpp — L4 採納 + prepopulate

  • L4 路徑 gate：n_gpu_layers > 0 && LLAMA_EXPERT_CACHE_ALLOW_NGL && !LLAMA_EXPERT_CACHE_NOGATHER 才走 L4（否則維持 L3-B CPU gather 或 L3 skip-load CPU buft）。
  • adopt_pool_region：load 完把每個 expert tensor 的 Metal 儲存採納為該 layer/kind 的 pool region——Metal FFN 直接讀 pool，零 host→Metal async copy、零 CPU FFN fallback。
  • prepopulate：把每層前 capacity 個 experts 標 resident——load 時已 pre-read 進 pool，首次存取直接 pool hit（免冷 pread）。

2.3 llama-context.{h,cpp} — hook + ROUTER_CPU pinning + restore

  • expert_cache_eval_cb：sched eval callback 包裝；對 ffn_moe_topk-<il> 非 ask 節點觸發 expert_cache_on_topk（建 union → ensure/fill → remap ids → repoint FFN src0）。
  • ROUTER_CPU pinning：把 ffn_moe_probs / ffn_moe_topk / ffn_moe_topk_remap 鏈 pin 到 CPU split，讓 topk 鏈留在 CPU、hook 在 CPU split 觸發（hit rate 70%+、file_reads=0）。
  • process_ubatch restore：每次 build_graph 前把 FFN 張量 (data, ne[2]) 還原（cache_orig），CGC-PHASE 計時（build/alloc/inputs/compute）亦在此。
  • get_sampled_token_ith：CGC-GST 細分計時（output_reorder/resolve/read），證實 ctx->synchronize() 佔 EOG sync 大頭。

2.4 ggml-backend.cpp — CGC_OA_ASYNC segmented async dispatch

  • 切段：在 ffn_moe_topk-<il> 節點把 Metal split 切成 [0..topk0], [topk0+1..topk1], …, tail（n_segs = n_topk + 1）。
  • 管線前推：先 submit seg[0]，迴圈內「submit seg[i+1] 前進、wait seg[i] 觸發 hook」——GPU 永不排空（submit 下一段時上一段還在跑）。
  • 非阻塞輪詢：用 ggml_metal_get_cgc_done（Metal backend 的完成計數器）spin 等 seg[i] 完成，取代每次 ggml_backend_synchronize；hook 在 CPU 寫 remap leaf 給 seg[i+1] 消費（seg 已 submit、但執行當下才讀 remap 資料，CPU write 來得及）。
  • 無 topk 的 split（prefill/plain graph）直接 fully async。
  • CGC_TAIL_DBG：證實 segmented loop 結束後 GPU 仍有 ~4.4ms tail（末幾層 + final norm + output layer）未等完——此即 EOG sync 本體。

2.5 ggml-metal-{context.m,context.h,cpp} — cgc_done + 計時

  • ggml_metal_cgc_done：non-blocking 完成計數器（addCompletedHandler 遞增），供 sched 輪詢。
  • get_tensor_async / synchronize：CGC_METAL_DBG 計時（blit cmd buffer 建立 ~30µs、waitUntilCompleted ~4.4ms——證實 EOG sync 是 GPU tail 真實計算，非開銷）。

5. 結語

「源碼實作」已 1:1 重現生產二進位的能力（L4 zero-copy pool + CGC segmented async），且多了完整的效能儀表。28.6 t/s kernel 地板已達；要讓 wall 突破 29 t/s，唯一途徑是 MTP 把 step N+1 的早期層與 step N 的 tail 重疊（見 CGC_TPOT_延遲分解_2026-08-20.html）。
