一、Executive Summary

CGC（Compute Graph Compiler）是一個端雲協同的 AI 代碼補全引擎。核心創新在於： 同一套技術棧（MTP Draft + Hermes 智能路由 + Edge Proxy），同時解決三個市場痛點—— 企業的數據主權焦慮、開發者的補全延遲痛點、以及終端設備跑不了大模型的能力鴻溝。

核心論點：現有 AI 代碼助手市場存在一個清晰的缺口——沒有任何產品同時做到「低延遲 + 數據主權 + 大模型能力」。

  • Copilot/Cursor：低延遲但代碼上傳雲端，無數據主權
  • 通義靈碼/Comate/CodeGeeX：有數據主權但延遲 150-300ms，無邊緣加速
  • 所有雲端方案：Mac/筆記本用戶只能跑 2B 小模型，26B+ 大模型是雲端專屬

CGC 是唯一能占據這個缺口的架構。

二、三魚模式

「一魚兩吃」升級為「三魚模式」。同一套 MTP Draft（llama.cpp 路徑）+ Hermes(SFT) 智能路由技術棧， 服務三個獨立的產品價值維度。

魚一：數據主權

~100%

代碼不出域覆蓋率

  • Cache HIT (30%)：代碼不出設備
  • 敏感代碼 MISS：端側 MTP 推理，不出域
  • 非敏感 MISS：雲端 EP8，不出內網
  • Hermes(SFT)：語義級敏感度偵測（非 regex）

魚二：推理加速

128

Local MTP crossover tok/s

  • Local verify 無 HTTP 開銷（vs Path B 45ms/round）
  • Crossover 128 tok/s（Path B 僅 42）
  • M4 base 30-80 tok/s 在 crossover 以下
  • 預期加速 1.4-2.3x（BF16 batch=4）

魚三：端側跑大模型

26B

16GB Mac「感覺」能跑

  • 緩存命中 → 0.3ms（像本地）
  • 敏感代碼 → 端側 2B+MTP（不出域）
  • 非敏感 → 雲端 EP8 26B（13ms）
  • 離線 → 降級 2B（不斷服）

B 端：軍工/金融/政企

痛點：代碼不能出內網，現有私有化方案延遲太高

方案：CGC 私有化部署在企業 GPU 集群

  • 員工 Mac 上的 edge proxy 連接內網 EP8
  • 緩存命中 30% → 0.3ms，零計算
  • 敏感代碼端側推理，不出設備
  • 非敏感走內網 EP8，13ms，不出內網
  • Hermes(SFT) 語義偵測，自動分流

定價：~$15-25/人/月（vs Copilot $39-200）

C 端：個人開發者

痛點：Copilot 延遲打斷心流，訂閱貴，隱私焦慮

方案：CGC SaaS + 本地 edge proxy

  • Mac 上跑 2B + MTP draft（本地加速）
  • 複雜補全走 CGC 雲端 26B（13ms）
  • 用戶感覺 26B 就在本地
  • 離線降級到 2B，不斷服
  • 免費版（本地 2B）+ Pro 版（雲端 26B）

定價：免費 / $8/月（vs Copilot $10-39）

離線/內網場景

痛點：飛機、安全環境、客戶現場無法用雲端 API

方案：CGC 本地模式

  • Mac 本地 2B + MTP（149.8 tok/s via llama.cpp）
  • 緩存常用補全模式
  • 離線時 Hermes 自動降級到 local_only
  • 網路恢復後自動切回端雲協同

價值：無網路也能有 AI 補全

能力技術門檻競爭者複製時間防禦力

防禦力不在單一技術，在於「時間窗 + 整合 + 定位」：

  1. 時間窗：Claude Code 後門事件 → 國產替代需求是現在，不是明年
  2. 整合複雜度：edge proxy + mTLS + SGLang EP8 + 多模型 + Hermes 路由 + MTP draft，完整系統不是 1-2 週能抄的
  3. 三魚定位：「低延遲 + 數據主權 + 大模型」三合一定位目前無競品，先占住
  4. EP8 調優經驗：CUDA_HOME/CCCL/flashinfer JIT 的坑是實測踩出來的，競爭者需要時間

這些是「時間窗」護城河，不是「永久」護城河。關鍵是在窗口期內拿到標桿客戶。

八、產品路線圖

Phase 1 · M1-M2

Local MTP Verify Loop + Hermes D5

目標：端側 MTP verify loop 跑通（llama.cpp hidden states → MTP head → accept/reject）， Hermes D5 內容感知模組（SFT 微調），proxy 代碼過濾/脫敏。

交付：Mac M4 上 2B + MTP 端側推理可用，敏感代碼自動走端側。

風險：llama.cpp hidden states 接口需驗證；accept rate 需實測（離線 98.56%，端側未知）。

Phase 2 · M2-M3

雙 EP8 LB + 企業級審計

目標：Host1+Host2 雙 EP8 + Global LB 部署，企業級審計日誌（結構化日誌 + 管理員 dashboard）， 多租戶緩存隔離。

交付：可交付企業客戶的私有化版本（A 模式 + C 模式）。

Phase 3 · M3-M4

標桿客戶落地 + SaaS Beta

目標：1-2 個 B 端標桿客戶（金融/政企）私有化部署，SaaS Beta 上線。

交付：客戶案例 + 性能報告 + SaaS 免費版開放。

Phase 4 · M4-M6

企業模型微調 + 規模化

目標：企業代碼庫微調封裝（train_mtp.py → 一鍵微調流程），SaaS Pro 版上線。

交付：企業可客製化 draft model，SaaS 付費用戶 5K+。

九、風險評估

風險等級影響緩解措施
llama.cpp hidden states 接口不支持 MTP head 高 Local MTP verify loop 無法實現 M1 早期驗證；備案：自建 C++ 擴展暴露 hidden states
端側 accept rate 低於預期 中 MTP 加速比下降，魚二價值減弱 離線 chain_acc 98.56% 是上界；限制詞表可提升 accept

2B 模型補全質量不足 低 敏感場景補全質量差 MTP draft 增強；定位為「速度優先」場景

十一、結論

CGC 三魚模式的核心邏輯： 不試圖在單一技術上建立護城河（proxy 三件套門檻低，我們承認）， 而是通過同一套技術棧服務三個獨立的產品價值， 在競品定位矩陣上占據一個目前無人占據的位置。

  • 魚一（數據主權）：解決 B 端 #1 痛點，Hermes(SFT) 讓 cache miss 也不破主權
  • 魚二（推理加速）：Local MTP crossover 128 tok/s，端側 2B 加速 1.4-2.3x
  • 魚三（跑大模型）：16GB Mac 用戶「感覺」26B 就在本地，三層疊加消除延遲感知

技術棧不變——MTP Draft（llama.cpp 路徑，149.8 tok/s）+ Hermes(SFT) + Edge Proxy + EP8—— 但產品價值是三維的。這不是技術護城河，是「定位 × 時間窗 × 整合度」的組合護城河。

Claude Code 後門事件創造了國產替代的時間窗。CGC 需要在窗口期內完成 Phase 1-2， 拿到 1-2 個標桿客戶，占住「低延遲 + 數據主權 + 大模型」的三合一定位。
