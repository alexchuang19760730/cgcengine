2. 它要解決的問題：同一句話有幾個答案

2026-09-17 當天，「我們的 decode 是多少」有四個互不相容的答案，而「我們的 prefill 是多少」 有兩個：

問題答案來自哪個儀器
decode10.78 / 10.91llama-bench（暖平台、d512）
12.36decode_bench（HTTP，當日裁定退休）
12.95llama-server 的 HTTP sweep（p25-gputime）
12.62MTP A/B（HTTP /completion）
prefill278.56 / 261.17 / 275.01HTTP 驗收臂（2873-token prompt）
276.25 / 300.43llama-bench pp2048

兩件事讓它們不能並排：儀器不同（decode_bench 與 llama-bench 在同 env／ 同模型／同 n／同場交錯下差 9.4 vs 12.4，而 decode_bench 的離散大得多）， 以及形狀不同（-p 2048 vs 2873-token prompt、-b 歷史值 6144 vs 5632）。 而 repo 裡沒有任何地方列舉過 profile —— 所以「一致性」只能手工從五份文件拼出來， 這正是那些數字當初分岔的方式。

當天的兩條裁定把儀器固定下來：decode_bench 退休， 以及 llama-bench 是 prefill 與 decode 共用的唯一 instrument of record。 本檔案把那個決定的其餘部分機械化。

3. 它定義了什麼（而這是它唯一擁有的東西）

3.1 四個標準 cell

cell-p-n-d-b/-ub為什麼是這個形狀
decode0128512512 本 repo 的 decode 標準。-d 512 才是暖平台（--depths 0 是最冷的格子）。 逐字就是上游的 tg128 @ d512 那一列
decode-up01285122048 同一列，但用上游的預設 batch ⇒ 可以跟外面發表的數字並排
prefill-house2048160profile 與既有的 pp2048 擷取（276.25 / 300.43）保持連續
prefill-up51212802048 逐字就是上游的預設形狀 pp512

上游的預設是 -p 512 -n 128 -d 0 -b 2048 （src/llama.cpp/tools/llama-bench/llama-bench.cpp:367-377），而它的標準輸出列是 pp512 / tg128 / pp512 @ d512 / tg128 @ d512 （src/llama.cpp/tools/llama-bench/README.md:180-187）。

3.2 一個 cell 一次啟動

llama-bench 為每一個 (n_prompt, n_gen, n_depth) 組合建 context， 但模型與專家池是同一份 ⇒ 把 -p 512,2048 寫在一起會讓第二格繼承第一格暖過的池， 兩格就不獨立了。所以每一格都是自己的行程、自己的 --workdir。

3.3 回報規則：丟掉 rep 1

llama-bench 的 tg warmup 只有 1 個 token （src/llama.cpp/tools/llama-bench/llama-bench.cpp），所以 rep 1 跑在空池上、 rep 2..n 跑在暖池上。工具因此同時印 avg_ts 與平台值， 並把平台值標成該引用的那一個（§7 有實測的價差）。

3.4 模型與建置必須隨數字走

tag（臂名）不含模型檔。2026-09-17 用 --dry-run 逐字讀 -m 那一行驗證：--arm prefill250 與 --arm prod25 解析出 同一個檔（Nail-…-denseIQ4X.gguf），只有顯式設 CGC_SERVER_MTP=0 才換成 Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf（ARMS 表裡只有 prod25-stream-mtpoff 設了它）。所以每一列都附 model_filename 與 build_commit —— 這兩個欄位在 llama-bench 的 row 裡本來就有， 是摘要把它們丟掉的。（lesson eng-mh-0055）

3.5 閘門與熱序列

跑之前檢查 8080 有沒有 listener、以及有沒有別條線的量測行程，任一非空就 exit 3 （不是印出來然後照跑 —— 2026-09-17 有一輪把 lsof 與 cmake --build 寫在同一行、 沒有 abort 分支，於是把別條線正在 map 的 dylib 蓋掉，他們那輪 A/B 橫跨了兩個 build）。 熱序列用 thermal_pressure.Sampler，它在 child 存在之前取第一個樣本 ⇒ launch 真的表示「被發射進去的等級」。

4. 它刻意不重新發明什麼

它需要什麼它去哪裡拿為什麼不自己寫
profile 清單從 scripts/run_server.sh 的 CGC_SERVER_PROFILE must be a|b|c 拒絕行解析 手抄的清單在「有人新增 profile 的那一天」就錯了，而且失效是安靜的 —— 新的 profile 只是永遠不會被量到
env、模型、batchllama_bench_matrix.resolve() （即 run_server.sh CGC_DUMP_ENV=1） 只有一條解析路徑。抄一份 env 就是第二個真相來源
熱序列thermal_pressure.Sampler 它的 launch 語意是先在 child 之前取樣，重寫會弄丟這個性質
記憶體地板prefill_certifiability.mem_state() 與驗收臂用的是同一個「可用記憶體」定義
行的解析llama_bench_matrix.parse_rows() 它能救回「mid-run 失敗前已完成的那幾行」

⇒ 這個檔案不 import 任何量測碼，它 import 的是「怎麼解析設定」與「怎麼記錄狀態」。

這張表當場確定了三件事（都不是我推的，是讀出來的）：

  • 7 個 profile 全部載入同一支模型（Nail-…-denseIQ4X）， 而且全部 mtp=1。「MTP=0」不在 profile 集合裡，它只能靠顯式覆寫產生 —— 這與 §3.4 是同一件事的兩面。
  • caps 在 7 個 profile 上都是 40-40:256： M6 那個旋鈕的 profile 預設是統一的（它被改動時是靠 env，不是靠 profile）。
  • 真正分岔的只有 8 個欄位，而且集中在 prefill250（batch／stream／slab） 與 prod25（ctx 4096、spac 開）身上。

MTP 這一格刻意不從 env 讀。CGC_SERVER_MTP 是 run_server.sh 內部的 shell 變數，不會出現在 dump 裡 ⇒ 讀它會讓每一列都印「(default)」而看起來正常。 權威來源是解析後的 server argv：MTP=1 會帶 --spec-type draft-mtp --spec-draft-n-max 3，MTP=0 兩者都沒有 （當天用 prod25 與 prod25:CGC_SERVER_MTP=0 對照驗過）。

6. 它拒絕什麼：24 組能力不符

這是寫這個工具時才看見的東西。prefill-house（-p 2048）在六個 pool-only profile 上解析成 -b 8，而 2048 個 token 塞進 8 的 batch 會觸發 GGML_ASSERT(n_tokens_all <= cparams.n_batch) ⇒ 那個 cell 會 abort， 唯一留下的痕跡是 matrix json 裡的 incomplete: true。 第二種情況更安靜：一個引擎不會照做的 batch，cell 仍然會跑完， 然後產出一個戴著該 cell 標籤的數字 —— 那正是這份文件存在的目的所要防的 「同一個標籤、不同的量」。

$ python3 scripts/check/prod_matrix.py --dry-run | grep -c "^  SKIP"
24

把 4 個 cell 展開成 28 組之後，只有 4 組跑得動，而且全部在 prefill250 上：

$ python3 scripts/check/prod_matrix.py --profiles prefill250 --dry-run | grep "^  prefill250"
  prefill250     decode         -p 0    -n 128 -d 512 -b 512   [cell (argparse)]  -m Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf
  prefill250     decode-up      -p 0    -n 128 -d 512 -b 2048  [cell (argparse)]  -m Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf
  prefill250     prefill-house  -p 2048 -n 16  -d 0   -b 5632  [profile]  -m Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf
  prefill250     prefill-up     -p 512  -n 128 -d 0   -b 2048  [cell (argparse)]  -m Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf

拒絕的理由有兩種，工具逐組說明：

SKIP prod25  prefill-house  -- -p 2048 does not fit -b 8 (GGML_ASSERT n_tokens_all <= n_batch;
                               the engine clamps n_batch to cgc_pool_max_tokens() on this profile)
SKIP prod25  decode         -- profile pins no BATCH and prod25 has no CGC_PREFILL_STREAM, so the
                               engine's pool-path clamp (cgc_pool_max_tokens, default 8) applies --
                               the cell's -b 512 would NOT be the effective batch

要讓 pool-only 的 profile 也能跑，介面是 --extra-env （矩陣的 PROFILE:ENV=VAL 形式），例如 --extra-env 'CGC_PREFILL_STREAM=1;CGC_GATHER_SLAB_CAP=256'； 代價寫在輸出裡：那時量的已經不是「這個 profile 原樣」。 而即使加了它，prefill-house 在 prod25 上仍然被拒 （stream 路徑給 -b 512，裝不下 -p 2048）—— 這是正確的拒絕。

7. 為什麼要丟掉 rep 1（worked example）

取 Backup/phase_decomp/lb_depth_repro_20260916.json 裡的一列 （prod25-stream、-p 0 -n 128 -d 0）：

samples_ts = [8.1907, 9.96428, 10.4123]      avg_ts = 9.522431
platform   = (9.96428 + 10.4123) / 2 = 10.19 t/s
價差       = +7.0%

那一列的三個樣本不算離散：rep 1 是冷的、rep 2/3 一致。 換句話說，avg_ts 少報了 7%，而「少報」不是隨機誤差，是規則問題。 預設 -r 3 時平台值只剩兩個樣本 ⇒ 這份工具會把 n_kept 一起印出來， 讓「只有 1 個 rep」的執行看得出來不是平台值，而不是安靜地長得像一個。

8. 誠實邊界

這份文件不主張：

  • 本輪沒有跑任何一個 cell。這份白皮書交付的是工具與判準，不是數字。 所有 --list 與 --dry-run 的輸出都是零 GPU 產生的 （run_server.sh CGC_DUMP_ENV=1 ＋ 算術）。
  • 它不取代 prefill_certifiability.py。跨啟動離散（同一條 pp2048 指令、四次獨立啟動得 276.59 / 198.84 / 176.18 / 122.68 ＝ 2.25×）仍然由那支 harness 負責 —— 它同時記錄每次啟動的記憶體狀態，那才是離散要相關的變數。 --runs N 只是把這裡變成同一個問題的淺版。
  • 它不決定「哪一個 cell 是生產數字」。那取決於「生產」指什麼（被服務的請求是 2873-token prompt，而 cell 是 pp512 / pp2048）。工具把選項與形狀固定， 選擇權留給引用的人。
  • 它對 MTP 無能為力。llama-bench 對投機是瞎的 （sampler|speculat|draft|MTP 在它的原始碼零命中）。所以歷史上的 12.62 vs 9.82（MTP 由淨負轉淨正）在「只認 llama-bench」之下 目前沒有 instrument of record。兩條路（把 --spec-* 加進 llama-bench，或保留 llama-speculative-simple 當 MTP 臂並且永不並排） 未定。
  • prefill-house 的 batch 不在 cell 手上（batch=None ⇒ 吃 profile）。 這是為了與既有的 pp2048 擷取連續；副作用是它只能在釘了寬 batch 的 profile 上跑。

未跑的東西明寫未跑：本節列的四個 cell 一次都沒執行； --runs 2..N 的跨啟動路徑沒跑過；prefill-up 沒有既有的參考數字 （它的紀錄欄位在 §5 的表裡是空的）。
