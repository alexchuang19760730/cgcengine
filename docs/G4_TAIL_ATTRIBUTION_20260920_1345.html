2.2 ★ 兩個結構性事實（G4 的機制）

  1. 沒有任何單一 kind 超過 12.8% —— 成本攤平在 ~25 個已命名的 kind 上 ⇒ G4 的槓桿是「融合一群同尺寸的 op」，不是「找一個熱 kernel」 （熱點不存在，這正是 G4.no_single_lever 的實測版本）。
  2. 尾部由 gated-delta-net（linear attention）的支撐 op 主導： conv／k_conv／z-／gdn_out／attn_norm／ dnqkv_proj／dnbeta_proj／beta／q_conv／ dn_normg_mul／linear_attn 合計約 15–16% of tot。

⚠ 一條自我更正（讀法上的）。我先寫「那 15 個 0.10 ms 的 kind 在計時解析度下限」， 這個讀法收回 —— 同一份 log 否證了它：k_conv／z-／gdn_out 在 125 段合計逐位元同值 51.98 ms、每段百分比也相同（2.6%）⇒ 這只能是 工作權重與節點數相同，不是量測底噪。正確說法：「它們同值，因為同工作權重」。

殘量 13.1% 仍未命名（低於 1% 門檻）。要再往下只能再放寬（例如 =3 給 0.1% 門檻）， 但那會開始把圖的固定開銷與真正的 op 混在一起 ⇒ 建議先把 §2.2 的融合路線做完再回來。

3. 對 G4 的結論

可及空間（不變） union 104.87 ms vs 權重地板 19.5 ms/步 ⇒ 5.4×； 等效頻寬 22.3 GB/s ＝ M4 的 19%
機制（本節新增） 攤平在 ~25 個已命名的 kind 上，沒有任何一個 >12.8%，而它們分成兩族： MoE FFN 支撐 op（前 3 名 36.1%） 與 GDN 支撐 op（~15%）
所以下一步 融合（node 的未融合 elementwise、ffn_moe_add 的殘差加、 GDN 的一族同尺寸小 op），逐族做，沒有單一槓桿
不是找不到熱點 kernel —— 熱點不存在

4. 儀器改動（+16 / −3）

int kop_topk = 5, kop_floor_div = 20;   // 20 => 5% floor
if (const char * ops_lv = getenv("CGC_GPU_OPS")) {
    if (atoi(ops_lv) >= 2) { kop_topk = 16; kop_floor_div = 100; }
}
  • CGC_GPU_OPS=1 的路徑逐字不變 ⇒ 既有記錄（含 docs/GPU_NODE_ATTRIBUTION_20260918_1500.html §56–§62 的數字）可複現。
  • 刻意複用既有門控、按值分級，而不是新增 env 名：CGC_GPU_OPS 已在 run_server.sh 的 allowlist 裡，而那個區塊正被另一條線編輯； blob-staged 的加法會被他們下一次提交同一區塊時還原。
  • 行緩衝 600 → 1600：16 個 kind 塞不進 600 bytes，而 snprintf 截斷會 靜默丟掉這次要讀的尾巴。

6. 誠實邊界

  • 這是歸因，不是優化。本 commit 沒有移動任何被量測的指標 —— 它把「沒有名字的 45%」變成「有名字的兩族」，並把 no_single_lever 從判斷升級成實測。
  • kind 佔比是在 ns_kop_* 的工作權重上加總的，不是直接量測每個 op 的 kernel 時間； 它回答「哪一族值得融合」，不回答「融合能拿到多少」。
  • 單一 regime：m123_oracle_gate 的 9 個 oracle 比對、pool 8 GiB； 而 union 的 104.87 ms 是 E2b 暖的另一個 regime ⇒ 不要把兩者的百分比相乘。
  • 本輪 沒有驗證任何融合的收益 —— 那需要實作 ＋ 一次配對 A/B（單臂噪音底 ±27%，見 MEMORY_PERF.md）。
