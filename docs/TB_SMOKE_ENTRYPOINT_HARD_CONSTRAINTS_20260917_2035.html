tb smoke 入口的兩個硬約束修復

flashkv-devserver ／ 2026-09-17 20:35 ／ D5 白皮書附件（隨本輪 agent_harness/tb_loop/scripts/run_model_smoke.sh 的修復一起提交）

一句話 第一次 model smoke 回報的 Unresolved 0.00% 不是關於模型或 agent 路徑的證據 —— 它的真因是 --n-tasks 1 會挑「時長最長」的那一題，而那一題光是建置就吃掉整輪。好不容易釘住題目之後， 又連撞 tb 的兩個硬約束（--task-id 與 --n-tasks 互斥；殘骸目錄會被當成續跑）。 本文留下三次失敗的原文、兩個修法、以及產出當時的閘門輸出。

1. 為什麼要單獨為這個寫一份：那個 Unresolved 會被讀成模型判決

前一份白皮書（TB_TOKENHUB_WIRING_20260917_2010.html）的§「誠實邊界」寫著 「smoke 還沒有結果，所以本 commit 只主張到 --probe 200」。smoke 跑完了，結果是 Unresolved 1 / Accuracy 0.00%。若不拆開它的成因，這個數字會被讀成 「deepseek/deepseek-flash 驅不動 prime-agent」—— 而它一個字都沒說那件事。

真因：容器從來沒有起來 
Harness execution failed for .../terminal-bench-core/0.1.1/super-benchmark-upet:
Command '['docker', 'compose', '-p', 'super-benchmark-upet-1-of-1-model_smoke_20260917_195218',
 '-f', '.../super-benchmark-upet/docker-compose.yaml', 'build']' returned non-zero exit status 2.

build 失敗 ⇒ 容器不存在 ⇒ prime-agent 沒有被啟動過 ⇒ Unresolved 只是「沒有容器可以跑」的另一種說法。

1.1 為什麼是這一題：--n-tasks 1 是「最長優先」不是「隨機」

--n-tasks 1 從資料集裡按時長排序、取最長。它挑到 super-benchmark-upet，而那題的 Dockerfile 是 FROM python:3.10-slim-bookworm 加一整串 apt-get install（含 openjdk-17-jdk、jupyter、clang） 再加 pip install —— 建置本身就吃掉整輪。

對照組是後來改釘的 raman-fitting.easy：它的 Dockerfile 只有 FROM ghcr.io/laude-institute/t-bench/python-3-13 加一行 COPY task-deps/， 而那個基礎映像已在快取裡（187 MB），所以建置幾乎不花時間。

未證但並列出現：Docker buildx is not available 日誌裡緊接著出現這一行（colima 沒有 buildx）。它與 exit status 2 的因果未經證明 —— 換題之後同一條 compose build 就成功了，所以「選題」是最小充分解釋。本文不主張 buildx 是近因。

2. 釘題之後，連撞 tb 的兩個硬約束 —— 兩個都是這個入口腳本的 bug

2.1 --task-id 與 --n-tasks 互斥

ValidationError: 1 validation error for DatasetConfig
Value error, Cannot specify both task_ids and n_tasks [type=value_error,

第一版腳本是永遠傳 --n-tasks，然後在 TB_SMOKE_TASK 有值時再傳 --task-id ⇒ 一釘題就必炸。tb 到 Harness.__init__ 內部的 _init_dataset 才發現，所以症狀是一個 pydantic traceback 加 rc=1，訊息裡完全沒有「你多傳了 --n-tasks」這層提示。

2.2 續跑守衛：tb.lock

ValueError: output directory /tmp/tb_modelsmoke/model_smoke_raman exists but no
lock file found. Cannot resume run without lock file.

tb 的續跑語義是「run 目錄裡有 tb.lock 才准續」。而嘗試 2 極早就失敗， 在它失敗之前已經把那個目錄建出來了（實查：目錄是空的）⇒ 嘗試 3 看到目錄存在，就以為使用者要續跑。

這條的一般形式：連續兩次失敗會疊成第三種症狀 第二個錯誤的訊息指向第一個失敗的殘骸，不指向它自己。所以「修好第一個之後再跑一次」不是禮貌， 是必要的 —— 否則會把殘骸的錯當成新發現。本文的三次嘗試就是這個形狀。

2.3 修法

缺陷修法
釘題必炸（參數互斥） 改用 bash 陣列 TB_ARGS=( … ) 組參數：TB_SMOKE_TASK 有值就只加 --task-id，否則才加 --n-tasks。"${TB_ARGS[@]}" 同時消掉 需要 # shellcheck disable=SC2086 的那種字串展開。
殘骸目錄造成假續跑 新增守衛，在啟動 tb 之前判三種情況：空目錄 ⇒ 清掉後繼續；有 tb.lock ⇒ 照 tb 的續跑語義走並印一行提醒；非空又沒 lock ⇒ 明確 abort 並叫你換 run-id （不猜、也不自動刪別人的產物）。
附帶得到的一條：固定 run-id 是風險 TB_SMOKE_RUN_ID 預設是時間戳。先前為了方便診斷而固定成 model_smoke_raman，結果失敗那一次留下目錄，第二次就撞上守衛。 守衛是對的（它把 cryptical 的 tb 訊息換成人看得懂的三行），但「預設用時間戳」本身也是對的。

4. 我造成的一個觀測污染：改動「正在執行中」的腳本

第一次 smoke 的日誌尾端有一行不屬於任何已提交版本程式碼的錯誤： 

/Users/alexchuang/Documents/flashkv-devserver/agent_harness/tb_loop/scripts/run_model_smoke.sh: line 187: -m: command not found

那個 smoke 從 19:52 跑到 20:05，而我在 19:58 改了那支正在被執行中的腳本。已提交版本的第 187 行是 -k timeout_ms="${TB_TIMEOUT_MS}" \（前一行有續行反斜線），不可能變成一個以 -m 開頭的指令。用受控實驗把機制釘死（不靠推論）： 

v1 = 263 行腳本，第 2 行後 sleep 8；跑起來後在 sleep 期間換成 v2（293 行）
v1 的輸出：3 行（截斷在 STEP-1）
  s.sh: line 294: unexpected EOF while looking for matching `"'
  s.sh: line 295: syntax error: unexpected end of file
對照組（完全不動它）：0 錯誤
判準 看到「腳本尾端冒出莫名其妙的 command not found / EOF」時，先問「它跑的時候我有沒有改它」。 而且錯誤行號落在新版檔案的行數上 —— 拿舊版去對會白繞一圈（本輪就是這樣繞了一圈）。 訊息裡的路徑與行號看起來都對，因為 bash 是增量讀取腳本檔，它從錯的位移續讀。
