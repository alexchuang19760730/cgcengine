2. 最終設定：prefill250 profile 的四個要素

250 tok/s 不是單一旗幟的效果，而是四件事同時成立。缺任何一個都不會到 250 —— 這正是它之前「量到過但復現不出來」的原因。

#要素值為什麼
1大 chunk n_batch = n_ubatch = 6144 prefill 一次吃 6144 token，不再被切碎成小 ubatch。 8192 會 GPU OOM（Insufficient Memory, status 5）。
2M2 prefill streaming CGC_PREFILL_STREAM=1 大 chunk 走 whole-layer slab（ne02 = n_expert = 256）而不是 pool。 這條路徑不受 cap=8 限制。
3slab 容量 CGC_GATHER_SLAB_CAP=256 必須 = n_expert(256)，否則 streaming 會被拒 / OOB。
4expert pool = 8 GiB CGC_SERVER_EXPERT_CACHE_BYTES=8589934592 本次新增。264.78 那筆量測跑的是 143 slots/layer（8 GiB）； profile 原本沿用預設 10 GiB（179 slots/layer），多出來的 2 GB 會把 6144-token ubatch 的 compute buffer 擠出 GPU，第一個請求就炸（§3.4）。

復現命令

# 起 server（profile 自帶 MTP、denseIQ4X、8 GiB pool）
CGC_SERVER_PROFILE=prefill250 ./scripts/run_server.sh --detach

# 要看 mul_mat_id 的幾何 vs ids（MTP verify 路徑最可疑）
CGC_SERVER_PROFILE=prefill250 CGC_MMID_MV_DBG=2 ./scripts/run_server.sh --detach

# prefill 量測：需要 ~4.4k token 的 prompt（< ctx 8192）
curl -s --noproxy '*' http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" -d @/tmp/p250_long.json

其他 profile 預設值：CTX=8192、SERVER_MTP=1、 SERVER_DENSE_IQ4X=1、ngl=99、n_cb=8、 glu_fused_down=1、layer_caps=40-40:256。 全部用 ${VAR+x} 守門：顯式給的環境變數永遠蓋過 profile。

3. 本次的四項改動

3.1 run_server.sh：起跑前 preflight pkill（防 GPU OOM ret=-3）

16 GB unified memory 上，前一支 llama 行程就算已經被 kill，Metal 端的 GPU buffer 還沒回收。 這時候立刻起新行程，會在第一次 command buffer 提交時拿到：

ggml_metal_synchronize: error: command buffer 8 failed with status 5
error: Insufficient Memory (00000008:kIOGPUCommandBufferCallbackErrorOutOfMemory)

也就是「GPU 說沒記憶體、但 memory_pressure 看起來還有」的那一種炸法 —— 而且炸在模型載入之後， 整段 load 時間白費。今天第一次跑 prefill250 就是這樣炸的（當下 free 只剩 67 MB、swap 6.1 GB）。

原本的「防護 1」只做「清殘留」，現在升級成四步 preflight：

  1. SIGTERM 優雅退出（讓 Metal buffer 走正常釋放路徑），預設等最長 15 s
  2. 只有等不到的才 SIGKILL（直接 -9 會漏：10 次崩潰累積 ~8 GB，vramFree 剩 15 MB）
  3. kill 之後輪詢 pgrep 真的歸零，而不是 sleep 1 就當沒事
  4. 等 free% 回到門檻（預設 25%，最多 20 s）—— 行程消失 ≠ 記憶體回來

逐 pid 送訊號，不用 pkill -f。 純 pattern 比對會打到「命令列裡剛好出現 llama 路徑」的上層 wrapper shell —— 實測就打到一支 /bin/bash -c … ./bin/llama-cli …，把它 SIGTERM 掉是純粹的附帶傷害。 現在 pgrep -f 只負責蒐集候選，ps 負責確認「第一個 token 的 basename」 真的是一支 llama binary；ps 拿不到資料時保守放行（寧可多清，不要 OOM）。

CGC_PREFLIGHT_KILL=1              # 0 = 關掉（只在確定沒有殘留時用）
CGC_PREFLIGHT_TERM_WAIT_SEC=15    # SIGTERM 後等 graceful 的最長秒數
CGC_PREFLIGHT_MIN_FREE_PCT=25     # kill 後要等到 free% 回到這個值
CGC_PREFLIGHT_SETTLE_SEC=20       # 最多等這麼久
CGC_PREFLIGHT_EXTRA_NAMES="…"     # 額外要清的 binary 名（空白分隔）
CGC_PREFLIGHT_SKIP_STALE_CHECK=1  # 明知有殘留仍要強行啟動（不建議）

另外在 exec 之前加了一道硬性攔截：清完還有殘留就直接 exit 1， 不要讓它炸在模型載入之後。

3.2 mul_mat_id 常開斷言（id_oob + 全零 row）

這兩個檢查原本只掛在 CGC_MMID_MV_DBG probe 底下，現在獨立出來、永遠執行 （ggml-metal-ops.cpp，MM/MV 分支判斷之前，pool 與 slab 兩條路都吃得到）。

斷言意義成本
id_oob_vs_ne02 > 0 ids 必須是「slot index（pool, ne02=143）」或「raw expert id（slab, ne02=256）」。 錯配會讀到真實存在但錯誤的 expert —— 不崩、logit 看起來合理，所以能通過所有資料層檢查。 每個 id 一次 int32 load + 2 次比較（decode ~2k/token，可忽略）
全零 expert row pool/slab 裡還是全零 = fill 沒在 read 之前落地，那個 expert 的貢獻被靜默丟掉。 word-wise 掃描 + early exit，非零只花一次 8-byte load；每 node 只查前 8 個 row 
CGC_MMID_ASSERT=0        # 完全關掉（只在量測極限吞吐時用）
CGC_MMID_ASSERT_FATAL=1  # 第一次違規直接 abort（CI / oracle gate 用）
# 預設：檢查開著、印 CGC-MMID-ASSERT、不 abort
#      （全零 row 是已知缺陷，我們還得在它上面跑吞吐）
# 輸出前 8 次逐筆印，之後每 1000 次印一行 —— 不要再製造 4000 行的 stderr 洪水

成本實測 A/B（同一支長 prompt，server warm，76-token 生成段）

差異落在 run-to-run 雜訊內（decode 此刻被 expert cache miss 支配，不是被 CPU 端檢查支配）。 結論：常開是安全的。

3.3 llama-context.cpp：CGC-SLOT 改 env gate

CGC-SLOT 原本是無條件 fprintf（每 run 40 行，而且是同步 fprintf，在 decode hook 的熱路徑上）。 現在收斂到 CGC_SLOT_DBG，並加進 run_server.sh 的 env allowlist。 它印的 slot table 現在已經被常開斷言覆蓋，留著沒有額外資訊量。

用 CGC_SERVER_PROFILE=prefill250 實跑，第一個請求就炸：

4.1 假說「ids 與 ne02 錯配」—— 否決

整場 run（含 prefill slab、decode pool、MTP verify）id_oob 累計 0。 pool 路徑 ids 全部落在 [0,143)，slab 路徑全部落在 [0,256)，offsets 自洽 （down → gate → up = slots × nb02）。 幾何與 ids 是一致的 —— 壞的不是「選了哪一塊」。

4.2 新定位：layer 1 的 gate/up expert row 全零

常開斷言抓到 8 次全零 row，全部在 ffn_moe_gate-1 / ffn_moe_up-1（= il=1），down 同一個 slot 卻非零。 兩條路徑都中（pool 的 slot 14、slab 的 raw expert 214）。

這就是「gate/up 是零、down 不是」的特徵：不是權重檔壞了（GGUF 比對 941/941 全對）， 而是讀的時候那塊 region 還沒被填 —— fill 與 read 的順序在 layer 1 上被打破。 它是 0.3% 等級的稀疏事件，這解釋了為什麼它能在所有「抽樣比對」檢查下存活。

下一步該看的不是「數值誤差累積」（0.5% 的 std 差比 FP32 重排誤差 1e-7 大五個數量級，不可能是它）， 而是 layer 1 的 ensure_batch / dbuf publish 的時序：誰在 fill 完成之前就把 slot table 發布出去了。

250 tok/s 是真的，但它是「乾淨記憶體」下的數字。 模型 13.6 GB + 8 GiB pool 載進 16 GB 機器之後，free% 會掉到 ~10%， 後續請求就掉到 150–185 tok/s。所以「能在 run_server.sh 復現」這句話必須附帶條件： pkill → 等記憶體回穩 → 才起 server，也就是 §3.1 的 preflight。 preflight 目前在啟動前把關；載入後的掉水位還沒有對應的保護。

6. 已知限制 / 下一步

  1. bit identical 未解決。已排除 ids/ne02 錯配；嫌疑收斂到 layer 1 gate/up 的全零 row。 下一步：把 CGC_MMID_ASSERT_FATAL=1 開起來，讓它停在第一次違規， 再對照 ensure_batch / double-buffer publish 的時序。
  2. decode 2.1–4.5 t/s，離 25 還差 5–10×。MTP draft acceptance 只有 0.55、 mean len 2.66，MTP 目前是淨負擔。要提高 decode，先把 gather 路徑修到與基線 bit identical （NOGATHER 那條 27.18 t/s 的臂才是資產）。
  3. 輸出品質異常。本次幾個 run 都出現 <think> 開頭的重複英文， 即使 reasoning=off。這是 chat template / prefill_text 的問題，與本次改動無關， Qwen3-nothink-ChatML.jinja 有一份未提交的相關修改，需要你確認後再決定去留。
  4. prefill 250 的條件要寫進 guard。目前 preflight 只在啟動前檢查 free%； 建議加一個「載入後 free% 低於 X 就警告」的訊號，否則 250 會被當成穩定值。
