TL;DR。POOL 列（path=POOL，r12 新增的第三條 capture stream：內核在 mul_mat_id 跑完後、同一個 encoder 內，從裝置讀 ids 與它選中的 pool row，逐列寫 5 字 (id, sum, xor, wsum, nbytes)）本身只能說「選了哪些 slot、那些 slot 裝什麼位元組」。 它答不出兩件事，而這兩件事各自是不同的缺陷：

問題欄位答案長什麼樣
那個 slot 裝的是哪個專家？own=[…] llama_expert_cache::slot_owner[il]（主機陣列），在編碼當下拍快照
host 說這個位置該讀哪個 slot？exp=[…] pool 路徑本來就寫的 cache_remap_tensors[il]（rd[i+j·n_expert_used]=st[e]）

兩個欄位都不新增內核、不新增 env：跨 dylib 用既有的 ggml_backend_reg_get_proc_address 掛一組 pull callback，llama 那一側讀、ggml-metal 那一側只存函式指標。

1. 為什麼 own= 是判準而不是裝飾

兩個 arm 各自把專家擺在自己的 slot 裡，所以「兩邊都說 slot 8」不等於「講的是同一個專家」。 少了 owner，比較器分不出這兩句印起來一模一樣的話：

列的情形判決下一步查哪裡
id 同、owner 同、bytes 同SAME—
id 同、owner 同、bytes 異CONTENT ★填充／內容：誰寫了那個 slot、什麼時候寫的
id 同、owner 異SLOT-REUSED帳／映射：同一個索引在兩臂指不同專家
id 異、owner 同、bytes 同RELAYOUT良性重排，不是缺陷
id 異、owner 同、bytes 異CONTENT ★同一個專家的權重，從兩個不同 slot 讀出不同位元組
id 異、owner 異ROUTINGgather 的上游：路由／映射
任一邊沒有 ownerUNCLASSIFIED什麼都不能說；工具會明講有幾列

結果（105 key／1200 列，同臂控制先過 1200/1200 SAME）： ROUTING=477、SAME=723、CONTENT=0、SLOT-REUSED=0、 RELAYOUT=0。逐 graph 分解：g1–g29（所有 prompt chunk）token 0 的 8 列每張圖 24/24 全 SAME， row 8–11（同一個 chunk 第 2 個 token 的前 4 個 id）每張圖 12/12 ROUTING；g31–g35（T=1 decode）每張 8 列全 ROUTING。 ⇒ 池的位元組不是載體，拿到的專家不同才是，而且位置在 gather 的上游。

2. exp=：把「裝置讀的」對上「host 說該讀的」

own= 說「裝置讀的那個 slot 裝的是誰」，它仍答不出「那是不是 host 的意思」—— 而錯的索引也是合法索引（0 是合法 slot，什麼都不會 assert），所以兩句話在列上同形：

情況意義
裝置讀 slot 8（裝 expert 237），host 的表也說 237 在 slot 8 裝置與 host 一致 ⇒ 壞在表的上游
裝置讀 slot 0（裝 expert 163），host 的表說 237 在 slot 8 裝置讀的不是 host 發布的那張表 ⇒ 機器缺陷（stale table／錯 buffer／fill 晚到）

錨臂自帶對齊自檢。來源選的是圖真的會消費的那個陣列（host remap leaf），所以在錨臂上 ids 與 exp 是同一個陣列；那裡出現不等號不是引擎發現，而是儀器壞了。 比較器因此把它印成 INSTRUMENT FAULT，並在結論引用前要求那個數字是 0。

3. 兩個決定，它們不是實作細節而是有效性條件

  • 抽樣時刻 ＝ 編碼當下，不是 dump 當下。dump 在整趟之後，會把「晚到的 fill」算進來 —— 而「fill 有沒有晚於消費者」正是這支儀器要測的假設。用答案去標註問題，量到的就是自己的假設。
  • 每個 capture 自己一格（bump arena），不共用「一層一份」。同層的 gate/up/down 相隔幾微秒， 共用一份會讓最後一次的狀態蓋掉前面兩列 —— 層內漂移會被靜默刪掉，而那正是編碼時刻抽樣想看的東西。

三態不可合併：none（這列沒被標註，不是「沒有專家」）／-1 （有標註，但該 slot 無主／該位置沒有期望）／<值>。兩者都印在行尾 （from= 之後），既有 regex 全部不受影響。

4. 實跑了，然後 exp 給的是 none —— 成因在原始碼裡

banner 說 owner channel ACTIVE, expect channel ACTIVE（通道裝上了），而 6 個 POOL 列 own=[…] 有值、exp=none 全部沒有。讀原始碼（不是推論）就找到了：

llama-graph.cpp:2190-2191
if (cgc_slot_table_gpu && il >= cgc_s1_min_il) {   // S1 臂
    ... slot_table + get_rows(...)  -> remap_ids = slots    // 2228：映射搬進圖裡，用 GPU gather 做
} else {
    ... 建 host remap leaf          -> remap_ids = remap    // 2292/2313：錨臂
}

⇒ S1 臂根本不建立那個 host leaf，所以 cache_remap_tensors[il] 對 il≥1 沒有條目 → callback 回 −1 → exp=none。層 0 仍走 leaf（CGC_S1_MIN_IL 預設 1）， 所以抓層 0 的 MoE 就會看到 exp 有值。

修法（下一步真正的動作）：不要讀 leaf，用同一個定義在 host 現算 exp[j] = st[e_j]（st = 快取的 slot 表、e_j = router 的 top-k）。 需要的只是每層一份 top-k 快照（≤64 個 int32 × 40 層 ≈ 10 KB）。兩點保證這個換法不損失什麼： ① 錨臂的 leaf 本來就是用這個式子寫的（llama-context.cpp:6194-6198），所以對齊自檢照樣成立； ② 換完之後 exp 在兩臂、所有層都有值，而不是只有層 0。

⚠ 本輪沒有任何可引用的 exp 讀數。原因不是「還沒排到窗口」，而是上面的來源要換 ——照現狀再跑一次只會再得到一次 exp=none。 → 後續狀態見 §8（同一個結論，外加一個獨立佐證與一個 M1 的交叉點）。

5. 併行：這一輪撞到別的 session 兩次，而兩次都是同一類 bug

（a）11:29 我把建置與檢查寫在同一行卻沒有 abort 分支：lsof 明明印出別條線的 server 在聽 8080，build 還是跑了 ⇒ 蓋掉他們正在 map 的兩個 dylib ⇒ 他們那一輪的 A/B 橫跨兩個 build。 （b）11:35 修好的閘門真的 abort 了：foreign_procs=1，別條線又起了 runner；我那一臂被殺 （decode 0.00、只有 6 列）⇒ 作廢不引用。

而兩次碰撞的共同根因是「用 pgrep -f 數行程」：它會命中任何命令列裡剛好提到那個路徑的 wrapper（bash -c "… build/bin/llama-server …"、grep、記錄用的 echo）。實測：一個把它自己 pgrep 的 pattern 印在命令列上的監看 shell，就能讓閘門假性 abort。

判準要改成看執行檔（ps -o comm= 的第一個 token），不是看命令列文字。 另一個 session 在 11:38 對 scripts/run_server.sh 的 OTHER_LLAMA_SERVERS 與 Backup/run_req2_retest.sh 的 alive() 做的是同一個修正（他們的註解記著：造兩個 wrapper，舊版回 count=2、本版回 count=0）。 ⇒ 這個坑在本 repo 有三份獨立實作，修的時候要一起想。

6. 順手抓到的第三件事：指紋不是原子操作

build_fingerprint()（scripts/check/decode_sweep.py:40-90）對 8 個檔案各算一次 md5、 逐檔開檔讀取。而一次 cmake --build 的連結是逐個進行的：本輪 libggml-metal 寫於 11:29:13、libllama 寫於 11:29:16。別條線那一輪的 A 臂指紋 就落在這 3 秒之間 ⇒ 記下的是「新 metal ＋ 舊 llama」= 一個從來沒有真正跑過的配置。

而這把尺正是用來決定「兩列能不能比」的 ⇒ 撕裂的指紋不會給錯數字，它給錯的許可。 建議：launch 與 teardown 各取一次，不一致就把該列標成不可比（lesson eng-mh-0049）。 本檔沒有改那支腳本（它屬於另一條線的證據鏈）——這是指出，不是修改。

7. 誠實邊界

  • exp 沒有數字（§4）。own 的數字有，且同臂控制 1200/1200 過。 → §8 是後續：仍未取得讀數，而原因已從「排不到窗口」改成「來源要換」。
  • POOLROWS 上限 12，而 T=2 的運算元有 16 個 id ⇒ 第 2 個 token 只覆蓋前 4 個。 那 4 個已經 100% ROUTING，所以結論不會因擴大覆蓋而翻轉，但措辭必須帶上這個前綴。
  • 不是本檔產出的東西：scripts/run_server.sh 與 Backup/run_req2_retest.sh 的修改屬於另一條 session（11:38），不在本輪的 commit 裡。
  • 本檔與 docs/POOL_ROW_DIGEST_20260917_0355.html 的關係：那一份是 r12 的第三條 stream， 本檔是它的續篇；兩份都保留，因為它們描述不同時間點的同一支儀器。

8. 後續狀態（12:5x 補記；本節之後的述句取代 §4 的「仍未取得」）

§4 停在一句話上：exp=none，成因在原始碼裡，修法是把來源換成 host 現算。 這一節記下那之後發生的事，以及一個獨立佐證。

8.1 這一格仍未取得可引用的讀數（誠實）

沒有量測。原因不再是「排不到窗口」，而是來源要換： cache_remap_tensors[il] 在 il ≥ CGC_S1_MIN_IL 時不存在 （S1 臂不建那張 host leaf，llama-graph.cpp:2190-2191），所以要改成 host 現算 exp[j] = st[e_j]（st = 快取的 slot 表、e_j = router top-k）。 在那之前，任何 exp 的引用都只會是 none。

8.2 而 own= 這一側拿到了獨立佐證（同一條線的另一支儀器）

CGC_IDS_STRIDE 由 8 改成 64、且印表機 clamp 到每列自己的 n_ids 之後， 同一組 A/B 用全寬記錄重讀，第一分歧由「pass 3、114/120」變成 「pass 0、117/120」 （docs/ROUTING_TRACE_2026-09-17.md §10），而形狀是：

A leaf   row0: tok0=[5,1,10,12,8,2,4,0]  tok1=[11,3,50,7,20,55,9,6]
B table  row0: tok0=[5,1,10,12,8,2,4,0]  tok1=[ 0,0, 0,0, 0,0,6,0]   <-- 7 of 8 are slot 0

⇒ token 0 兩臂完全相同、token ≥ 1 大多讀 slot 0。這與本檔 §1 的 own= 判決 （CONTENT=0、SLOT-REUSED=0、ROUTING=477）互相印證： 兩支儀器、兩種讀法、同一個結論 —— 不是池的位元組，是拿到的專家不同。

而 exp= 要回答的仍是那個不同的問題：那些 slot 索引是不是 host 的意思。 own= 只能說「那個 slot 裝的是誰」；一個合法但錯誤的索引會讓兩句話印起來一模一樣。

8.3 與 M1 的交叉點（新增）

同一條線的 CGC_ADD_ORDER=rev 探針給了另一個結果：同一個臂、同一個 build，只把 8 個專家加權和的結合順序反轉，答案 md5 由 2d4e5099 變成 f6718d44 ⇒ 聚合對結合順序敏感。這把 roadmap 的 M1 工作項 4（canonical gather order） 從「審慎」變成「必要」；設計稿見 docs/M1_WORKITEM4_CANONICAL_GATHER_ORDER_2026-09-17.md。
