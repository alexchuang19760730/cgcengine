1. 測的是什麼：一個「未跑過」的標準

上游那份白皮書自己把狀態寫得很清楚（§8 誠實邊界）：

本輪沒有跑任何一個 cell。這份白皮書交付的是工具與判準，不是數字。
所有 --list 與 --dry-run 的輸出都是零 GPU 產生的（run_server.sh CGC_DUMP_ENV=1 ＋ 算術）。

它同時列了四個標準 cell、以及「一個 cell 一次啟動」「丟掉 rep 1」兩條報告規則。 所以「測試這個標準」的具體含義就是：照它自己的復現指令把四格跑完，然後看它產出什麼。 本輪用的就是它文件裡那一行，沒有改任何參數（除了沒加 --runs，預設即 1）。

入口的三件事都是它自己拿的（不是我抄的）：profile 清單解析自 scripts/run_server.sh 的拒絕行； env／模型／batch 由 llama_bench_matrix.resolve()（即 run_server.sh CGC_DUMP_ENV=1）給； 熱序列用 thermal_pressure.Sampler，它的第一個樣本取在 child 存在之前 —— 所以 launch 真的表示「被發射進去的等級」。 本輪四格的 scalars.MODEL 逐格記錄，四格都是同一支 Nail-…-denseIQ4X.gguf。

同一條指令，等機器空了再跑一次（memory_pressure -Q 印 free percentage: 79%）， 7 個 profile 全部解析成功，!! 那四行不再出現。而且其中一個 profile （legacy-25plus）的一次獨立 resolve() 在載入期間掛住超過 60 秒（我用 60 s timeout 才拿回控制權）。

為什麼這算缺陷：那四行訊息把「這台機器現在記憶體不夠」寫成了 「這個 profile 解析不出來」。--list 的說明又自稱是零 GPU、可稽核的對應表； 於是對照表會隨著取樣時刻而缺行，而缺行的樣子與「這幾個 profile 壞了」完全一樣。 這正是同一份白皮書在講的失敗模式（同一個標籤、不同的量）在設定這一側的版本。

6.2 --dry-run（說明寫著「launch nothing」）會產生目錄

prod_matrix.py:249 的 rdir.mkdir(parents=True, exist_ok=True) 在 :259 的 if args.dry_run 之前執行 —— 所以每一組 (profile × cell) 在乾跑時就先建好工作目錄，而乾跑不寫任何產物進去做。後果是 Backup/prod_matrix/ 底下累積了 124 個空目錄（16:23–16:26 那幾輪乾跑留下的）， 命名格式與真的跑完的目錄一模一樣（<stamp>_<profile>_<cell>）。 分辨方法只有「裡面有沒檔案」。

實驗Backup/prod_matrix 的空目錄數結論
乾跑（預設 logdir）124 → 124（本輪未再跑；數字來自 16:2x 的既存狀態）——
乾跑 --logdir /tmp/prod_matrix_dry124 → 124目錄跟著 --logdir 走 ⇒ 證實建立點在乾跑分支之前

本輪因此沒有重跑預設 logdir 的乾跑；改用工具自己的 --logdir 把工作目錄導到 /tmp， 才同時重驗了「24 組不符、4 組可跑」這件事（見 6.3 的原文）。

6.3 閘門涵蓋 8080 與量測行程，不涵蓋「有人在重建」

gate() 的實作是兩條：lsof -nP -iTCP:8080 -sTCP:LISTEN， 以及把 ps -Ao pid=,command= 拿去比對 m123_oracle_gate|decode_sweep|mtp_accept_ab|run_ids_dst_capture|knifeedge_matrix|llama-bench|llama-server。 它不含「建置中」這個狀態 —— 而這個 repo 的所有比較都建立在同一個 build 這個前提上。

本輪就撞上了：我這一輪的四格在 17:48:36 結束，而另一條線在 17:48:30 / 17:48:31 / 17:48:34 / 17:48:37 依序換掉了 libggml-base、libggml-metal、llama-bench、llama-server。

8. 我在這一輪的兩個錯

錯一（比較嚴重）：我把 CGC_DUMP_ENV=1 當成位置引數，結果起了一台真的 server。

我為了查 --list 為什麼有 4 個 profile 解析失敗，手寫了 CGC_SERVER_PROFILE=off bash scripts/run_server.sh CGC_DUMP_ENV=1。 但 run_server.sh 讀的是環境變數 ${CGC_DUMP_ENV:-}（:1925）， 而 llama_bench_matrix.resolve() 是用 env["CGC_DUMP_ENV"] = "1" 傳的。 位置引數被忽略 ⇒ 它走完整條路徑真的啟動了（pid 52916，13.6 GB 模型）， 而那時另一條線正在量測。我在 2 分鐘內發現並 kill 掉（8080 回到 0 listener、0 殘留）。

事後對照才看到：他們那條驅動的第一個動作就是 pkill -TERM -f "build/bin/llama-server" —— 若我那台還活著，會被靜默殺掉，而我會以為是自己的問題。教訓與 skill cgc-prefill-thermal-delivery §5.7 是同一條：動機器之前先問；而且不要用「我以為的介面」去呼叫一支會起 GPU 的腳本。

錯二：我先跑了自己的封閉環探針，四臂全 rc=4。

17:32:39 我用 CLOSED_LOOP_MODEL_CMD='python3 …/llm_client.py' 跑 closed_loop.py --only Q1 --reps 1（4 次呼叫）。結果四臂 rc=4, answer=0 B —— llm_client.py 的 rc=4 是「連線層的例外」。原因是他們的驅動在 17:35:2x 執行了 pkill -TERM -f "build/bin/llama-server"，把我正在用的 server 殺掉了。 那 4 次呼叫沒有產生任何關於 E3 的資訊。

這件事的價值只有一個：它再次證明那個窗不是我的。而使用者在同一時間要求改用標準程序，方向是對的 —— 標準程序自帶閘門（GATE PASS），我的探針沒有。

9. 誠實邊界
