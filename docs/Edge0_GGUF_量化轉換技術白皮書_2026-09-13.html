📊 執行摘要

這份文件記錄的不是一個轉換腳本，而是一條完整的「不被靜默錯誤騙過去」的除錯鏈。把一顆 MLX affine-int4 的 35B MoE 模型搬進 GGUF，一共挖出 7 個缺陷（D1–D6、D9）。它們的共同特徵是：沒有任何警告、沒有任何例外，產物「看起來」完全正常。

最貴的一個（D9）：框架的 conversion/qwen.py:387-388 對所有 *norm.weight 無條件 +1.0，而 Edge0 的 checkpoint 存的是絕對值。結果每一層的 RMSNorm gain 從 1.03 變成 2.03 → 殘差流在每一層被放大兩倍 → 輸出是流暢但無意義的中文。它讓 MTP draft 的 accept rate 變成 0.00%，而我為此連續三輪往錯的方向找（換 MTP head、懷疑精度、懷疑 ne 軸向）。

最有價值的一個（pool 幾何）：修好 D9 之後 base 已經正確，但 MTP 的 accept 卡在 8.97%，而同一顆引擎上的捐贈者模型 Nail 是 52%。根因不在模型：compute_l4_pool_capacity() 用「所有層 per-slot 的最大值」當分母，而 MTP 層（blk.40）也在其中。把 MTP head 存成 F16（更高精度！）反而讓主幹的 expert pool 從 118 slots 塌成 33 slots，主幹的 top-k union 塞不下 → 585 次 buffer is nil → FFN 讀到空的 → 每個 draft token 都被拒。

核心教訓：量化格式是模型屬性，但它會經由引擎的記憶體幾何影響完全不同的層。「精度更高所以品質更好」在這裡是錯的，而且錯得非常徹底。

1. 來源格式與目標格式的語意落差

Edge0 在 HuggingFace 上是一份 MLX affine int4 的權重：每個 group 存一個整數張量 q、一個 scales、一個 biases，還原公式是

w = q * scales + biases          # group_size 預設 64

這與 GGUF 的 k-quant / i-quant 不是同一件事：GGUF 的量化型別是「一整塊 256 個權重共用一個 scale 與一組非線性碼本」，而 affine int4 是「64 個權重共用一個 scale 與一個 bias」。轉換時必須先把 affine 還原成 fp32，再用 GGUF 自己的編碼器重量化。這一步是不可逆的資訊損失，也是後面所有缺陷的溫床：一旦還原錯了，重編碼只會忠實地把錯誤封裝起來。

關鍵陷阱：routers 是 8-bit，不是 4-bit。 config.json 的 quantization 映射只列出與預設不同的張量：80 個條目，全部 bits=8，全部是 mlp.gate / mlp.shared_expert_gate（router）。把 router 當 4-bit 讀，in_dim 會算成 4096 而不是 2048（512 個 packed word 的 4-bit 解讀）。這個錯誤會直接改變張量形狀，但模型仍然「載得進去」——因為 GGUF 的形狀是由 converter 寫入的，不是由來源驗證的。

3. 缺陷帳 D1–D9

編號沿用 convert_edge0_to_gguf.py 的 module docstring（那是本專案對這些缺陷的權威定義）。表中「誰發現的」欄位刻意保留，因為發現方式本身就是這份文件要傳達的知識。

#一句話機制為什麼靜默 / 怎麼被抓到
D1 LoRA 完全沒生效 LoRA 張量是 F16，卻被 bf16_to_f32() 處理。該函式把 16 個 raw bit 當成 float32 的上半部——對 F16 而言是無意義的重解讀，每個 LoRA 值塌成 ~1e-18。 310/310 key 全部匹配、零警告、零例外。merge 確實執行了，只是加了個數值上等於 0 的東西。整個 GGUF 與「不套 LoRA」的版本無法區分。修法：to_f32() 依實際 dtype 分派。
D2 8-bit router 被降回 4-bit patched_add 把每個 2-D *weight 一律寫成 Q4_0，包含 router。讀取端是對的（8-bit），寫入端卻靜默降級。 產物裡 blk.20.ffn_gate_inp.weight = Q4_0，而來源是 8-bit。這是「router 精度」整條線的起點。修法：router 維持 Q8_0。
D3 無法偵測「merge 了個寂寞」 流程缺陷：沒有「LoRA 實際改了幾個張量」的計數，也沒有量級檢查。 正因為 D3 存在，D1 才能活那麼久。修法：合併計數 + |Δ| / |W| 比值 + inert 時硬失敗 + 寫入後重讀 GGUF 斷言 router 型別。
D4 delta-net gates 被 F16 捨入 ssm_alpha/ssm_beta 必須全精度。第一版只擋住了我們的量化器，但框架自己的 F16 pass 仍然會捨入它們。 跑 30/40 層都對，剩下 10 層悄悄變差——典型的「分佈式小錯」。修法：把 gate 強制為 F32，讓框架的量化變成 no-op（30 層 × 2 = 60 個 gate，已驗證）。
D5 寫入端記憶體爆掉 GGUFWriter 在 RAM 裡組裝所有張量資料。 16GB 機器上直接進 swap。修法：走 temp-file streaming（flat memory，代價是約 2× 輸出檔的磁碟）。
D6 「每張量洩漏 70 MB」的真因 conversion/qwen.py 的 Qwen2MoeModel 為「一個 expert 一個檔案」的模型保留累積器；本模型是已合併的 stack，所以計數永遠到不了 768，張量永不釋放。判定用 name.find("experts") != -1 這種裸子字串比對，我們的譯名剛好命中。
實測：每層保留 2.147 GB（每個轉換過的張量 114 MB）；40 層 ≈ 86 GB 匿名記憶體，被 OS 拿去壓縮／交換，直到 jetsam 砍掉行程。而且轉換根本無法完成（prepare_tensors() 拋 "Unprocessed experts"）。		 對任何 Python 物件計數都是隱形的：live numpy/torch array = 0，因為保留者是一個活著的 dict。
另外還有一個量測陷阱：進度列印的是 ru_maxrss，那是單調高水位——它只會上升，所以「每 25 個張量 RSS 又漲了」是必然發生的假象，正是它把上一輪的人送去追一個不存在的洩漏。改用 rss/uss/malloc 三者並列才分得清 mmap 的 file-backed 頁（無害）與匿名記憶體（會逼 swap）。
修法：把已合併的 expert stack 導向 TextModel.modify_tensors。驗證：保留量 114.4 → 0.3 MB/tensor，張量名與形狀不變。
D9 每一層的 RMSNorm gain 都是 2.0 而不是 1.0 conversion/qwen.py:387-388：
elif name.endswith("norm.weight") and not name.endswith("linear_attn.norm.weight"): data_torch = data_torch + 1
這是給「norm 存成 delta（w−1）」的 checkpoint 用的慣例。Edge0 存的是絕對值。結果：attn_norm/post_attention_norm/q_norm/k_norm/output_norm 全部 +1.0（linear_attn.norm 因為被排除所以正確，這正是洩漏的指紋）。
殘差流每層被放大約兩倍 → 輸出流暢但無意義。MTP accept 變 0.00%。		 產物載得進去、跑得出來、文字還是中文字。
**四項獨立證據交叉定案**：
① 來源 safetensors（torch, bf16）input_layernorm = 1.031160
② GGUF blk.0.attn_norm.weight = 2.031160，逐元素 恰好 +1.0
③ 能跑的 Nail GGUF = 1.031111
④ Edge0 自己的 MLX loader 只在 has_mtp_weights or has_unsanitized_conv1d 時才 shift，而兩者皆 False
定案方式：不是在程式碼裡 grep 出來的（我 grep 自己的 converter 三次都乾淨，因為 shift 在框架裡），而是在執行期追蹤數值——post-dequant 1.031160 → at-add 2.031160，夾出它發生在 merge_lora 與 add_tensor 之間。
— 我自己種的錯：nextn.shared_head_norm 我手動把它 +1.0，理由是「Nail 的值比它高 1.06」。 推理無效：MTP head 是模型專屬的，跟另一顆頭差 1.0 只代表「兩顆頭不同」。權威來源 mtp_head_qwen35.py:188-190 明寫 mtp.norm 不需要 shift；npz 的數值結構也印證：被 shift 的家族原始 mean 都是負的 delta（input_layernorm −0.105），只有 mtp.norm 是正常尺度的絕對值 +1.861。
已回滾，並在 merge_mtp_head_edge0.py 加了 runtime guard：若慣例被反過來匯出，建置直接 ValueError 而不是靜默產出一顆 gain 翻倍的 norm。

3.1 一個反覆出現的失敗模式

把 D1、D6、D9 放在一起看，它們是同一個模式的三次重演：

  1. 框架默默做了一件事（重解讀 dtype / 保留參照 / +1.0）；
  2. 沒有警告，產物結構完全合法；
  3. 唯一的偵測方式是「拿數值去對」，不是讀程式碼。

而 D3 與那個 ru_maxrss 陷阱則是這個模式的放大器：缺少計數器與正確的量測定義，讓「無事發生」與「做錯了」長得一模一樣。因此本專案後續所有修復都附帶一條會硬失敗的斷言。

4. 子張量手術：把 MTP head 移植進 blk.40

Edge0 的 MTP head 不在 base GGUF 裡（來源是 models/mtp_heads/qwen35_mtp_head_fp16.npz，1.6 GB）。要讓 llama.cpp 的 --spec-type draft-mtp 能用，必須把它當成 blk.40 的 20 個張量寫進同一個 GGUF。

4.1 GGUF 要求資料區「完全緊密」

最自然的做法——「只把 type 欄位改小、保留原 offset」——會讓模型載不進去：

E gguf_init_from_reader: tensor 'blk.40.attn_k.weight'
                         has offset 19558178304, expected 19533536768

ggml/src/gguf.cpp:770 要求資料區在標頭順序上逐張累加 GGML_PAD(ggml_nbytes(t), alignment)。任何空隙都會被拒。因此改變任一張量的大小，都必須重打包（repack）它之後的所有張量。

可用的槓桿：blk.40 剛好是標頭順序的最後 20 筆（733..752 of 753），所以重打包只涉及檔尾。這讓「F16 → 量化」可以在地縮小檔案（省 1.3 GiB），而「量化 → F16」只需在檔尾長大（+1.5 GiB）。

5. 決定性發現：MTP 層的儲存型別決定主幹的 pool 大小

這一節是整條除錯鏈的終點，也是唯一一個「問題不在模型、而在引擎另一層」的案例。

5.1 症狀

修好 D9 之後，base 用 MTP-off 已經完全正確（15+27=42、巴黎、MoE 解釋），但三臂 A/B 顯示一件反直覺的事：

armaccept rate備註
edge0 base + edge0 head（F16）0.00%（0/63；另一輪 0/2835）輸出塌成 文摘文摘…
edge0 base + Nail head（量化）1.75%
edge0 base + edge0 head（重編碼成 Nail 的型別）8.97%（28/312）第一次答對；兩次獨立執行逐位元組相同
Nail base + Nail head52.1%同一引擎上的已知可用值

更高精度（F16）反而嚴格更差，而把 F16 換成 donor 的量化型別就從 0% 跳到 9%。這不是精度曲線，這是別的東西。

5.2 機制

src/llama-model-loader.cpp:1068 compute_l4_pool_capacity()（修復前）：

per_slot_layer[il] = Σ (ggml_row_size(type, ne[0]) · ne[1])   over layer il 的 *_exps
per_slot          = max over ALL layers        ← 包含 MTP 層 blk.40
capacity          = clamp(budget / (n_layers · per_slot), 8, 256)

而之後每一層都被縮成同一個 capacity。於是「用 MTP 層的 per-slot 去收主幹的費」，就讓主幹 pool 的大小取決於頭部剛好用什麼格式存。

5.5 修法與 A/B 驗證

修法：從 per_slot 的 max 中排除 NextN/MTP 層（讀 <arch>.nextn_predict_layers）。MTP 層的 slot 本來就由 LAYER_CAPS（預設 40-40:256）給定，不該參與主幹的容量計算。若 nextn_predict_layers 不存在則 n_nextn=0，行為與舊版完全相同。

驗證方式：做了一個 blk.40 experts = Q8_0 的 probe 檔（per-slot 3,342,336 B，會支配主幹；磁碟成本只有 F16 的 1/3），同一檔案、同一組參數，只差這個 hunk：

binary主幹 slots/layer與公式預測
修復前62預測 62 ✅
修復後118預測 118 ✅

而修復後的 binary 跑正式出貨檔仍是 118 slots/layer、L0=48 L1=48、total 4976 slots、零 nil 錯誤——即對現行量產配置是逐位元組的 no-op，不影響既有的 M1 一致性閘門。

5.6 教訓

「精度更高所以品質更好」在共享記憶體池的引擎裡是錯的，而且錯得非常徹底。

一個 40 MB 的頭部張量格式選擇，改寫了 40 層主幹的 118 → 33 slots（−72%） 的記憶體配置。要能在這種系統裡除錯，必須把「模型屬性」與「引擎幾何」當成兩個獨立變因，並且可以分別量測——這就是為什麼本專案最終做了：

  • 可 runtime 切換的 flag（同一個 server process 內 A/B，排除機器漂移）；
  • APFS cp -c clone（20 GB 檔案零成本複製，單一變因實驗）；
  • pool 幾何的 log 行（L4 metal pool: N slots/layer）當成第一級觀測量。

6. 工具鏈：為什麼現成的 gguf-py 不夠用

本工作反覆需要「把某幾張張量換成另一種量化型別，其餘不動」。現成工具做不到，原因有三層——每一層都逼出一個自製元件。

6.1 障礙一：gguf-py 不會編碼 IQ 系列與 K-quant

型別gguf-py quantize本工作是否需要
Q8_0 / Q4_0 / F16 / F32✅需要
IQ4_XS / Q2_K / Q3_K❌ NotImplementedError需要（捐贈者的型別集）

解法：寫一支 C shim（qctl）直接連結 libggml-base，呼叫 ggml_quantize_chunk——也就是當初做出那些檔案的同一個 kernel。用 Python 手寫編碼器會產生「看起來對、數值上與 production 不一致」的張量，正是本文件一直在對抗的那類錯誤。

6.2 障礙二：不能只改 type 欄位

見 §4.1。任何大小改變都必須重打包之後的所有張量，否則 ggml 直接拒載。

6.3 障礙三：磁碟

本機可用磁碟長期在 8–11 GiB，而模型 18–20 GB。「複製一份來實驗」不可行。三個對策：

APFS clone — cp -c 產生 copy-on-write 分身，實測磁碟用量不變，只有被改寫的 extent 才配置新塊。這是所有「單一變因 A/B」的前提。

in-place tail repack — blk.40 是檔尾，所以縮小可在地完成、長大只需追加。

zero-temp 寫入順序 — 先建立剛好等於新檔尾長度的暫存檔再 splice；磁碟峰值 = 2× 檔尾。第一次實作時把「絕對 offset」與「相對位移」相減寫成了一個 19.5 GiB 的零填充（把 new_end（絕對）減去 out.tell()（相對）），直接灌爆磁碟；現在有 assert 釘住暫存檔長度。
