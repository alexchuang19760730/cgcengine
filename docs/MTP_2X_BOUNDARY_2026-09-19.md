# MTP 要「轉正到 2×」的邊界條件與最快手段 —— 2026-09-19 01:0x

## §0 一句話

**今天的瓶颈不是速度比 S 还没到 1，而是「谁先动」。** Server 干净窗已经量到 S = **1.09–1.22**
（`mean_len 2.14–2.40 ÷ C 1.97`），也就是 MTP **已经转正**；但从今天的这一组参数出发，
**k 加到多大都到不了 2×**（渐近上限 `a/m = 1.445`）。要到 2×，要么把接受率从 **0.465 拉到 ~0.9**，
要么把每 draft token 边际成本从 **0.322 砍到 ~0.07**，而现实解是**两边各走一半**。

> 「2×」在这里指绝对吞吐翻倍：基准 11.67 t/s（base 步 85.65 ms）→ **23.3 t/s**，
> 等价于 MTP3 文档里那个差 5% 的 25 t/s 目标。

---

## §1 模型与今天的参数（全部有出处，不是拟合出来的自由参数）

| 量 | 值 | 出处 |
|---|---|---|
| base 一步（MTP off） | **85.65 ms** ⇒ 11.67 t/s | `MTP_POOL_CONFOUND_2026-09-17.md:28,56`；独立印证 HTTP 11.75 t/s = 85.1 ms |
| MTP-on verify 一步（干净窗） | **168.4 ms**（mean_len 2.14 那笔 12.71 t/s） | `MTP3_25TPS_ARITHMETIC_2026-09-18.md` §2 |
| ⇒ 步成本倍数 C @ k=3 | **1.966** | 168.4 / 85.65 |
| ⇒ 每 draft token 边际成本 m | **0.322**（server）／**0.474**（bench） | `(C-1)/k`；bench 的 0.474 来自 `SPEC_COST_CURVE` 直接量测 |
| 每步 token 数 mean_len | **2.14–2.40**（acceptance **0.46541**） | V4b server 日志；`mean_len = 1 + k·a` 验证过（1+3·0.46541 = 2.396 ✓） |
| 今天的 S | **1.09**（配对）／**1.22**（模型，mean_len 2.40） | — |

**代入 `S = mean_len / C = (1 + a·k) / (1 + m·k)`：**

```
k=3   S = 2.396 / 1.966 = 1.219     t/s = 14.2
k=7   S = 4.258 / 3.254 = 1.308     t/s = 15.3
k=15  S = 7.981 / 5.830 = 1.369     t/s = 16.0
k→∞   S → a/m = 0.4654/0.322 = 1.445   ← 天花板
```

**⇒ 第一条结论（也是最容易浪费时间的那条）：**
**在今天的 a 与 m 下，k 不管拉到多大，上限只有 1.445×。** 这与「dynamic-k oracle 只有 1.035×」
（`MEMORY_PERF`）互相印证 —— 沿 k 轴没有午餐。⇒ **候选 O5（`n_max 3→5`）就此作废**（约 +4.5%）。

## §2 到 2× 的边界表（k = 3，即現行 draft_n_max）

`S = 2` 要求 `mean_len ≥ 2C` 且 `mean_len = 1+3a ≤ 4` ⇒ **`C ≤ (1+3a)/2` ⇒ `m ≤ ((1+3a)/2 − 1)/3`**

| 接受率 a | 需要的步成本 C | 需要的边际成本 m | 相对今天 m=0.322 要降 |
|---|---|---|---|
| **0.465（今天）** | ≤ 1.198 | ≤ 0.066 | **−79%** ✗ 不现实 |
| 0.60 | ≤ 1.400 | ≤ 0.133 | −59% |
| 0.70 | ≤ 1.550 | ≤ 0.183 | −43% |
| **0.80** | ≤ 1.700 | ≤ 0.233 | **−28%** ← 现实解区间 |
| **0.90** | ≤ 1.850 | ≤ 0.283 | **−12%** ← 现实解区间 |
| 1.00 | ≤ 2.000 | ≤ 0.333 | **−4%（今天已经够）** |

**读法**：今天已经「付过 +4%」了 —— **只要 acceptance 到 ~1.0，今天的成本结构就直接给 2.03×
（4.0 / 0.1684 = 23.75 t/s）**，正是 `MTP3` §3 那条「差 5%、物理上不可达」的墙的另一面：
它不是一个**低于** 2× 的点，它是**刚好等于** 2× 的点。

⇒ **第二条结论： streams 两轴的杠杆率完全不对称 —— 接受率那一格的导数远大于成本那一格。**
把 a 从 0.465 推到 0.70，等价于把 m 砍 43%。

## §3 那么最快手段是什么

### ★ 首选：先把「0.465 是不是真的」搞清楚 —— 这是成本最低、杠杆最大的一件事

理由很直接：**成本那一侧我们反复量过三次（IO bytes → thrash → requests/round），每次都发现
候选主项与 k 共线；而接受率这一侧一次都没被量成过「是不是 bug」。** 而一堆既有线索指向它可能不是真的：

1. **`plain_match = False`**（`MTP_HEAD_PROVENANCE_GATE_2026-09-14.md` §5 第 2 点，**至今未处理**）：
   batch verify 与逐 token 解码**不一致**。这不只压低接受率，它还是个正确性缺陷。
2. 历史教训：r33 nb-aware 修正之前 accept 被记录为 73.81%，修正后 58.25%
   —— 那次经验是「**accept 数字被高估**」，但同一份证据也证明 **batch verify 的 token ≥ 1
   曾经在用别的 token 的专家算** ⇒ 这条轴有过 hate bug，且**只修了一半**。
3. **量化假设**：出貨档 `Nail denseIQ4X` 的专家是 `IQ2_S / IQ3_S / IQ4_XS`。draft head 是按
   fp16/bf16 base 训的，**重量化改 top-1 就要拒** ⇒ 这是一条由量化几何决定的接受率天花板。
   可证伪对照：Ornith 是 `Q3_K / Q4_K`，同一架构 ⟹ **跑一支 Ornith 的 acceptance 就能判**
   （判准：Ornith accept ≥ 0.65 而 Nail 0.465 ⇒ 天花板是量化；两边一样 ⇒ 不是）。

> ⚠️ 注意这条**不是**要引入 Ornith：Ornith 慢 1.49×（`MEMORY_PERF` §Ornith），
> accept +35% 补不回来。它只当作**证伪量化的探针**。

**具体第一步（一天以内，只读）**：在同一支 server 上，把 batch-verify 拿到的 logits 与逐 token
解码的 logits 对齐（`CGC_MM_BITIDENT` 那一套三支柱已经在树上），量 divergence rate。
判准：若 divergence 能解释 ≥15pp 的拒绝 ⇒ 修 bug 是主线（a: 0.465 → ~0.62，S → 1.44）；
若 ≈0 ⇒ 接受率是真值，走 §3 下面的 §3b。

### §3b 如果接受率是真的（≈0.465）：唯一还有量的是把 m 从 0.322 降到 ~0.15

但要注意，**m 是什么至今没有定论** —— 这是本轮最需要点破的一件事：

| 候选主项 | 支持 | 反证（固定 k 的设计） |
|---|---|---|
| expert 字节流量 | `ms/step = 89 + 3.35·MiB`（r²=0.70） | **`--budgets` 双轴**：bytes ×1.46–4.68 时时间只 0.76–1.25×（k=1/3 弹性甚至 −0.38） |
| residency thrash | `evictions/misses = 0.97`、worst 层 217 > 143 slots | 同上：砍预算就是制造 thrash，时间不跟 |
| **每轮的 cache 请求数** | `ms/step ≈ requests × 1.59 ms`，截距 ≈0（09-19 §0 顺带量到） | ⚠ **这个 request 数与 k 同样共线**（union/call = 8.49 + 3.61·k）⇒ **第三次共线陷阱**，尚未被证伪也未被证实 |

⇒ **`MTP_ROUND_COST_OPT_BACKLOG` 的六个候选里，真正还没被排除的只有两个能在实际非零 effect 的量级上做事：**
- **O1 `CGC_PREFILL_PROTECT`（用 FILE 开关，不是 env）**：唯一的「零风险＋有历史读数」项
  （steady 22.2 t/s vs prefill 后首段 8.1–8.9）。⚠️ 但它是**抬两边**，不改善 S。
- **O6 prewarm 从未启用（`req=0`）／prefetch 丢 33% 全因 `drain_cleared`**：写好的部件没接上线，
  先查是谁在 drain（只读诊断）。

**而能「一次性判掉上面三个候选」的实验仍是上一轮就排好的那两支、且都还没跑：**
- **`--spec-type ngram-map-k` 消融**（把 draft 前向整个拿掉）：m 崩 ⇒ 成本住在 draft 前向本身
  （nextn 只有 1 层，却占了一步的 32% ⇒ 强烈暗示路径有问题，可修）；m 不动 ⇒ 住在 verify 每 token 路径。
- **`CGC_P_ROUTE=1`**（探针已在 `llama-context.cpp:5929`，零额外 forward）：量 union 还能压多少。

### §3c 已经排除、不要再做时间预算的

- **加大 k / dynamic-k**：数学上到不了 2×（§1），oracle 也只有 1.035×。
- **练 draft head / RSL-MTP**：RSL 自评为 0.70–0.97×，无一格 ≥1.0（`RSL_MTP_GAIN_ESTIMATE`）。
- **pool 预算 / per-layer 配额 / prefetch 开关**：双轴数据显示上界只剩 **~15%**（`POOL_BUDGET_COST_DECOMP`）。
- **单纯加池（143 → 217 slots）**：机器已经 OVERSUBSCRIBED 4838 MiB，先过 OOM 复测再说。

## §4 建议的顺序（按「每单位时间买到的信息」排）

| # | 动作 | 成本 | 买到什么 |
|---|---|---|---|
| 1 | batch-verify vs 逐 token divergence（`plain_match` 那条） | 0.5–1 天，只读 | 判「0.465 是真是假」；真 ⇒ 立刻拿到 a 0.62–0.7 的路 |
| 2 | Ornith acceptance 对照（只当探针） | 0.5 天 | 判「接受率天花板是不是量化」，决定要不要重排 M6 |
| 3 | `--spec-type ngram-map-k` 消融 | 0.5 天 | 判 m 住在 draft 前向还是 verify 路径 |
| 4 | `CGC_P_ROUTE=1` | 几分钟 | union 压缩还剩多少空间（顺带，不单独排窗口） |
| 5 | O1 `CGC_PREFILL_PROTECT`（FILE 开关） | 0.5 天 | 抬绝对 t/s +10~25%，**但不改善 S**，别拿它交 S 的卷 |
| 6 | O6 drain_cleared 诊断 | 0.5 天 | 修好 prewarm/prefetch，才有可能动 hit 59.8% |

纪律照旧：`--reps 4` + MIN_KEPT=3 + SPREAD_LIMIT=1.10，且**先 `lsof -nP -iTCP:8080 -sTCP:LISTEN`
与 `pgrep -fl 'llama-bench|llama-server|spec_cost_curve'` 确认窗口里没有别条线**。
