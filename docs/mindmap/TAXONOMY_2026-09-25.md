### S 序列化消減（25 條目）

*41 段提交的同步／資料搬運路徑（含 IO、填池、段邊界）*

**41 段提交 88.5 ms（11.30 t/s） → 單段提交 48.2 ms（20.73 t/s，×1.83）**

- 原始報告：[S1 TPOT 分解（2026-09-25）](../S1_TPOT_DECOMPOSITION_2026-09-25.html)

**1 現狀**

- 交付口徑（41 段提交）：<b>88.5 ms/token ＝ 11.30 t/s</b>。
- 單段提交 S1（實測）：<b>48.2 ms ＝ 20.73 t/s（×1.83）</b>。
- 單段 ＋ 保留 fill（估計）：52.2 ms ＝ 19.2 t/s（×1.70）。
- 但 S1 目前<b>不能交付</b>：同一個開關讓 CGC-HOOK 計數 0、<code>file_reads=0</code> ⇒ 拿掉的除了同步，還有<b>正確性前提</b>（權重不進池）。

**2 推論**

- 被消掉的 40.3 ms 裡：<b>41 段提交的序列化 ≈ 36.3 ms（41.0%）</b>、<b>fill 同步 3.96 ms（4.5%）</b>。
- 其餘（單段也躲不掉）：<b>48.2 ms（54.5%）</b>。
- ★ <b>主項是序列化，不是 fill</b> —— 先前把 40.3 ms 全歸給 fill，是把 4 ms 說成 40 ms。
- ⇒ 整層重算判死；只有 <b>per-expert 重算</b>（MoE 輸出線性疊加）值得做：+13%~+18%。

**3 量測**

- 同一 build <code>1ca685490</code>、同一 cell（<code>p2048 / n128 / d512 / r3 / b5632</code>）、同一 pool（8 GiB）、<b>兩臂皆無 spec</b>。
- fill 同步 3.96 ms 出自 <b>EBTIMER</b>；序列化 36.3 ms 為<b>未再分解</b>的差值項。
- 來源：<code>Backup/seg_batch_s1_pairs/abba_212809.json</code>；台帳 <code>docs/DIAGNOSTIC_ARMS_LEDGER_2026-09-25.md</code> §1。

**4 目標**

- <b>可執行目標</b>：fill 若能留在單段提交之下且不進關鍵路徑 ⇒ 48.2 + 3.96 ≈ <b>52.2 ms ⇒ ≈ 19.2 t/s（×1.70）</b>。
- 閘門已判 OPEN：損益平衡點 66.1%~114.3% miss 率，實測區間 4.7%~43.0% 全在平衡點以下 ⇒ per-expert 重算在 0~66% 任一 miss 率下都淨正。
- ⚠ fill 是<b>正確性前提</b>不是速度前提：無 fill ⇒ 權重永不出現 ⇒ 永遠 garbage；背景 fill 決定拿 14.1 還是 19.9，<b>不決定正負</b>。

- <b>k_eff=1</b>（請求 3、<code>SPECDBG draft=1</code> 逐輪皆是）；<b>S = 0.914／0.682／1.050</b>（三輪，中位 0.914）；<b>E = 1.707／1.455／1.620</b>；<code>a = E−1</code>、<code>m = cost−1</code>（<b>僅在 k_eff=1 成立</b>）。
- ⚠ 絕對 t/s（7–8.5）<b>不可引用</b>（無 <code>--warm-skip 64</code>）；可引用輪內比值與整數計數器。交付口徑 MTP off = <b>11.03~12.20</b>；<b>「9.82/12.62/+28.5%」已作廢</b>。

**2 推論**

- 量綱恆等 <code>S = E / cost</code>（三輪誤差 &lt;1e-3）；<code>E = 1 + a·k_eff</code> 是 <b>a 的定義式</b>，不是經驗規律。
- <b>k_eff=1 時 2× 數學上不可達</b>：<code>a≤1 ⇒ E≤2</code>，要 <code>S=2</code> 需 <code>m≤0</code>。<b>僅 k_eff=1 成立</b>。
- <b>k=1 處的局部彈性</b>：<code>dlnS/dlna = +0.383</code> vs <code>dlnS/dlnm = −0.465</code> ⇒ 在 <b>k_eff=1 的現實下</b>，邊際成本 m 的影響略大於 a。⚠ <b>局部值</b>：k 變了兩者都變，不是「m 永遠比 a 重要」。
- 成本主項＝<b>verify 側專家 union 撐破 per-layer 配額</b>（MiB/step <b>+30</b>；worst distinct <b>168~205</b>／slots 143；layers_over_slots <b>0 → 2~4</b>）。<b>批次化省的是權重讀取次數，省不掉「並集變寬」</b> —— 這是原推論的致命傷。
- ★ <b>F24</b>：09-24 的 <code>m(k)</code> = <b>1.176／0.840／0.961／0.920</b>（散佈 1.40×） ⇒ <b>m 不是常數</b>，<code>cost = 1 + m·k</code> 在他批自己的資料上就不成立 ⇒ 所有「把 m 當常數外推到別的 k」的推論都失去支撐。
- ⛔ 因此<b>不再主張</b>「沿 k 軸加到多大都虧」「k=3 的 S」「a 拉滿的 +7%」—— 都屬外推或未量測假設。

**3 量測**

- 本次：<code>spec_cost_curve.py --profile prod-new --ks 0,3 --rounds 3 --prompt 0 --gen 128 --depth 512</code>（selftest 26/26）⇒ <code>Backup/phase_decomp/spec_cost_en-mtp-repro-250925.json</code>。
- 自洽：<b>每一輪 <code>S = E/cost</code> 精確成立</b>（r1 <code>1.7067/1.8683=0.9135</code> ✓、r3 <code>1.6203/1.5429=1.0502</code> ✓）。
- ⚠ 中位是<b>逐列獨立取</b> ⇒ 那一行不是真實的一輪；用中位 a、m 反推的 S 不是實測值。
- 獨立複現：<code>S0_MTP_ONOFF_AB_2026-09-21.md</code> 同形狀配對中位 <b>0.889（−11%）</b> ⇒ 與本次 r1 同向。

- <b>交付 cell 的 MTP 增益 = UNRESOLVED</b>（契約 §7；機檢 <code>void_number_check.py</code>）—— 本輪缺 warm-skip，仍未結案。

**4 目標**

### C kernel／頻寬效率（9 條目）

*GPU 裝置忙碌時間與頻寬效率：MUL_MAT_ID／dequant／dense GEMV 的佔比與 achieved bandwidth*

**交付 step 最大的一塊是裝置忙碌時間（不是 host、不是段序列化、不是 MTP）：MoE 57% ／ attention+GDN 42%；但打滿頻寬也只值 ~2.4% step**

- 原始報告：[那 154 ms 是什麼：裝置忙碌時間，不是 host（2026-09-23）](../DEVICE_BUSY_ATTRIBUTED_2026-09-23.md)

**1 現狀**

- 歸因（<code>DEVICE_BUSY_ATTRIBUTED_2026-09-23.md</code>）：那塊沒人認領的時間<b>是裝置忙碌時間</b>——<b>57% 住在 MoE 區（層內節點 0–39）</b>、<b>42% 住在 attention／GDN 區（40–89）</b>。
- 邊際 verify token 的 <b>+26.3 ms</b> 裝置時間裡，MoE 區只 +14.2（其中 kernel 自己的地板 +7.9），另外 <b>+13.4 是 attention／GDN 的投影與掃描</b>。
- operator 口徑：<b>verify 的 device span（union／MUL_MAT_ID／dequant）佔 step 56–61%，是單一最大塊</b>；dense 部分只跑 <b>47.6 GB/s</b>，屋頂 60–70 GB/s。
- ⚠ 口徑打架要先講：本樹文件另載<b>裝置峰值 100.5 GB/s</b>、該族 kernel 只跑 <b>36–45 GB/s</b>、dense GEMV 實測 <b>56–108 GB/s</b>（DRAM 峰值 108.8）。引用時必須標是哪一份。

**2 推論**

- 這一塊<b>既不是段序列化（S）、也不是 MTP 攤薄（M）</b>，而是「GPU 算得夠不夠快、頻寬打沒打滿」。
- 天花板是硬的：<b>dense GEMV 每步 13.39 ms（13.7–16.8%）</b>，<b>就算每一個都打滿 100% DRAM 峰值也只省 1.92 ms ＝ 2.42% step —— 低於 3% 門檻</b>。
- 已證偽的槓桿：<b>G4 元素級融合</b>（已融合／天花板 8.5%）、<b>K0–K5 融合與小 op 群</b>、<b>dense GEMV 的 NSG 全射程掃描（1..32）</b>（±3% 內、無單調趨勢）、<b>OMLX verify kernel</b>。
- 尚未證偽的唯一免寫 kernel 槓桿：<b>型別替換</b>（kernel 層 gate/up <code>iq2_s→q2_K</code> 1.35×、down <code>iq3_s→iq4_nl</code> 1.46×）—— 端到端收益<b>待估</b>，未量測。

**3 量測**

- 工具：<code>scripts/check/verify_marginal.py --device-split</code>；形狀探針 <code>scripts/check/shape_probe/</code>（獨立二進位，不動共用建置產物）。
- ⛔ <b>step 級 <code>gpu_sum</code>／<code>union_sum</code> 不可引用</b>：每步 2 個假 buffer 在灌同一個累加器（<code>GPUEndTime−GPUStartTime</code> 回傳絕對開機時戳 ≈1.7e14 ns，通過了 <code>s&gt;0 &amp;&amp; e&gt;s</code> 守衛）⇒ 先前「裝置 span 邊際 ~31 ms/token」<b>作廢</b>。
- 可用的是逐 buffer 的 NSM，且要套「<b>buffer 不得長於它自己的 step</b>」這一刀。

**4 目標**

- <b>不設加速目標，只設證偽目標</b>：它是背景約束與天花板，不是與 S／M 並列的活躍攻關軸。
- 對 S／M 的含義：<b>S 消完序列化之後，剩下的地板就是這一塊</b>（單段提交後 48.2 ms 裡的大部分）—— 所以 C 決定了 S 的天花板，不決定 S 的正負。
- 要持續做的是：<b>每次有人聲稱「改 kernel 就能 +X%」，先用 roofline／device-split 證偽</b>；型別替換是唯一還站著的待測槓桿。
