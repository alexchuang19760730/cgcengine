1 一句话结论 Executive Summary
decode 25：顶到了「软件可优化」的边界，剩余空间不在此机器，而在机型/硬件层。 decode 现状最佳 15.19 t/s（交付格锚点 13.72 t/s）；要 25 t/s 需等效权重带宽 29.3 GB/s，仅实测峰值 108.8 GB/s 的 29%（物理带宽远未打满）。真正卡住的是 「延迟型 memory-bound」：每 token 需搬运 1.92 GB 权重，实际仅达到 17.8 GB/s，与 DRAM 行缓冲区局部性可达的水准差 4-6×。历经十六路候选（kernel / 类型 / MTP / pool / 调度）全部结案，没有证实能 +82% 到达 25 的机制。

3 三种 Bound 的物理定义 Concepts
Memory-Bound
延迟 / 局部性
权重搬运部分被 DRAM row locality、bank、page 命中率卡住。decode 落在此类。
Compute-Bound
ALU / GPU
算力占满。本机 kernel/GEMV 全族上限约 5%，不是瓶颈。
Bandwidth-Bound
Si / peak
把峰值带宽 100% 打满仍不够。本机 25 t/s 仅需 29%，远未打满。
decode 本质是「每 token 全量扫过 1.92 GB 权重」 t(s) = bytes / EW_bw ，其中 EW_bw = 等效权重带宽（受局部性折损）
三种 bound　共享同一条 DRAM 通道——统一内存架构下 CPU/GPU 共用同一块内存与带宽，没有「异域并行」的物理基础。
4 我们顶到上限了吗？ Core Answer

答案拆成三条线：

绑定对象现状是否顶到上限剩余潜力
ComputeGPU GEMV 全族上限 ≈ 5%未顶（算力过剩）极小（非瓶颈）
Bandwidth（Si）25 t/s 仅需 29% 峰值未顶（远未打满）物理带宽仍有 ~3.4× 理论余量
Memory（延迟/局部性）等效 17.8 GB/s（16% 峰值）已顶（延迟型瓶颈）四至六条软件路径全部结案
精确表述：这台机器 decode 顶到的并非「带宽上限」，而是 「延迟型 memory-bound」——峰值带宽富余，但权重的读取模式（大量小块、动态 top-k、SSD 换页）使等效带宽被拖至 16%，而非真正吃到 29-100%。

8 量化优化潜力 Quantization Lever

方向成立的数学：更低的每 token 字节 → 更快扫完 → 更高 t/s。但「字节减少」与「读取模式」必须同时成立。

候选每 token 字节变化成效（kernel 层）致命副作用
expert 类型替换（iq4_xs 等）+49%−7.8%footprint 暴涨撞金属闸（+5.36 GB 工作集）
down-only iq3_s→iq4_xs+24%sub-1%footprint 合理但杠杆太小
更低 bit（q2_k 等）↓kernel 快已被 IQ2_S 现状覆盖 + 质量权衡
量化的现代权衡：net 收益必须端到端实测（kernel 快、但 hit 可能降 / footprint 可能撞工作集）。干跑证明亮面类型替换在「既有形状 × 16GB」下的工作集膨胀抵消了 kernel 增益，不采用。
9 取舍与边界 Trade-offs
约束内容影响 decode 25
硬件封顶16GB 统一内存 / 单通道 LPDDR5模型 footprint 已把工作集挤爆（f≈1.5%）

十六路候选的结案清单（简）：kernel 吃干、类型撞闸、S2 带宽受限（顶 18.7）、G4 三叠判死、fence ×1.218、racy spec ×1.31 上界、MTP 轴 DEAD、pool 判死、Strata 整合（平台/n 专家不符）价值归零。

诚实结论：「decode 25」在 16GB M4 + 这个模型上，没有已被证实的机制。所有候选的数学上界（即便叠乘）都不足以 +82%。剩余方向需考虑换硬件（更大内存）或换模型——那正是唯一确定可达 25 的路，但不在 kernel/调度层。
