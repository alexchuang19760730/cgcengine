S1：src[2] 那一格 —— 儀器在 S1 臂上是瞎的

2026-09-17 03:00 · 引擎層 · 承接 S1_MINIL_TRACKING_20260917.html · 跑 r26；另外備好 COLD 交錯 A/B 並排程

這不是答案，是路線被關掉。 上一輪把盒子收到「同一組 ids、同一池佈局、同一反查， gather 讀到的位元組不同」⇒ 候選是 expert 權重運算元的指向。 這一輪去讀那些位元組，發現 主機側的儀器在 S1 臂上量不到東西： 編碼時刻 op->src[2]->data 還沒被填，讀到的是被重用的工作緩衝殘留。

⇒ 「同 ids 讀到不同位元組」仍然未測。 剩下的路線必須在裝置上讀 （在 capture 內核裡對 ids 所選的 pool row 做摘要），不是在主機讀中間運算元。

1. 儀器早就存在（先別寫新的）

CGC_MMID_MV_DBG（在 ggml_metal_op_mul_mat_id，已在 run_server.sh allowlist）逐 MoE 節點印：權重張量形狀 src0 ne=[…]、ids 運算元、以及 ids 所選前 4 列 各前 ≤4096 bytes 的 FNV-1a 指紋。它自己的註解就是判準：

"If the hashes match but the ids differ  -> the remap is wrong.
 If the ids match     but the hashes differ -> the POOL CONTENTS are wrong."

語意陷阱：解析器只看第一個字元 —— =1 是 150 節點（一個完整 pass ＝ 41 層 × 3）， =2 是 512，其他任何值（含 0）是 4096。 所以 run_ids_dst_capture.sh 新增的 MMID=1|2|3 穿透會拒收 0。 新比較器：Backup/compare_mmid_fp.py。

2. 結果：同一節點，兩臂讀到的完全不是同一種東西

ffn_moe_gate-1，r26：

臂ids=id_oob_vs_ne02指紋
錨 p25-gputime-churn [2,105,7,9,5,106,1,84,8,0]
真的是 slot 索引，<143		 0有（id2:b74c2cf9…）
S1 p25-slotgpu-churn [1063628079,-1100333772,1016099937,…]
這是 float 的位元模式		 16 / 16印不出來（全部 OOB）

錨臂的 id_max 是 106/112/116/120/123（都是合法 slot），S1 臂是 1001348352 / 1002426846 / …

⇒ 在 S1 臂，編碼時刻 op->src[2]->data 還沒被填。 讀到的是被重用的工作緩衝 殘留（float）。因此這個「主機側、編碼期」讀數對 S1 臂無效。 這與 repo 既有的註記同源：「CGC-MMID-ASSERT 的 id_oob 不是『消費者讀到什麼』 的證據（編碼期由主機讀 op->src[2]->data）」。 有效的只有內核側讀數（在 command buffer 內、裝置上讀 bid_src2）， 而它說 ids 兩臂相同（§EN-16 的 120/120）。

3. 順帶量到的一個新事實（本身不是缺陷，但很有用）

同一個 ids 運算元，兩臂的填充時序不同：錨臂在編碼時它已經是正確的 slot 索引； S1 臂在同一個時刻還是殘留。裝置讀到的一致（內核側證明），所以數值上無害， 但這是第一次直接看到「兩條對映以不同時序抵達同一個運算元」—— 它也正是這個儀器瞎掉的原因。

4. 修掉一個自己造的比較器缺陷

第一版在 ids 清單不同時短路（判 IDS_DIFFER 就跳過後面的比較）， 於是印出來的 BYTES_DIFFER=0 是空洞的： 117 列全被判 IDS_ONLY，一列的位元組都沒比過。

指紋是按 row id 配對的，必須獨立比較（同一列 id 在兩臂的 hash 不同 ⇒ 位元組不同， 與兩臂各自要求的 ids 清單無關）。修好之後它印出「0 shared rows」， 才讓「讀不到」變成看得見。

通則：「沒有差異」與「沒有比較」必須印得出來。 任何比較器都要能區分這三種狀態：相同 / 不同 / 根本沒有可比。

5. 那條路現在長什麼樣

步驟狀態
ids 是否相同（裝置側）相同（120/120，內核側）
池佈局／被消費集合是否相同相同（40/40，那個 pass）
反查是否一致一致（wrong=0、owner==ids）
權重張量形狀相同（兩臂都 src0 ne=[2048,512,143]）
那些 row 的位元組是否相同仍未測（主機側讀不到）

下一步（真正的儀器工作）：在 capture 內核裡，對 ids 所選的 pool row 做與指紋同構的摘要 （[sum, xor, wsum, n] 或 FNV），在裝置上讀 —— 這樣兩臂的「同一列同一 hash」才有意義。 這是本輪唯一還沒被排除的敘述。
