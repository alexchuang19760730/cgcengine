1. 概述

本文檔記錄了 CGC MoE Engine 實現 Prefill 250+ tok/s 的完整配置、測試方法和復現步驟。核心優化是 M2 Prefill Streaming（整層串流預加載），通過以下三個階段的優化實現：

  1. fe6c0fbf2：M2 prefill streaming + --m2 oracle 模式（102 → 50.7 tok/s，初始實現）
  2. 987e597d6：Contiguous slab read — 每 (layer, kind) 一次 pread，而非 256 次（50.7 → 64.8 tok/s，+28%）
  3. b8220555f：Double-buffer slab fill — I/O 與 graph build 重疊（64.8 → 264.78 tok/s，配合 n_batch 優化）
關鍵發現：M2 路徑突破了 cap 限制。當 CGC_PREFILL_STREAM=1 時，n_batch 不受 cap=8 限制，prefill 使用整層 slab（所有 256 個 experts），而不是 pool 的縮小版本。

4. 測試方法

4.1 精確測量 Prefill 速度

⚠️ 重要：API 的 prompt_per_second 字段只計算實際需要 prefill 的 token 數（排除 cache 複用），不是總 token 數。當 cache 複用率高時，API 顯示 15-20 tok/s，但實際總吞吐可能是 8000-15000 tok/s。

正確的測量方法：

  1. 使用冷啟動請求（無 cache 複用），每次使用不同的 prompt
  2. 計算：usage.prompt_tokens / (timings.prompt_ms / 1000)
  3. 不要依賴 API 的 prompt_per_second 字段

4.2 測試腳本

#!/usr/bin/env python3 # prefill_speed_test.py import requests import time url = 'http://127.0.0.1:8080/v1/chat/completions' headers = {'Content-Type': 'application/json'} proxies = {'http': None, 'https': None} # 生成約 4000-5000 tokens 的長 prompt prompt = "Please analyze the following document:\n\n" + "\n\n".join([ f"## Section {i}: Detailed analysis of topic {i}. " f"This section covers theoretical foundations, practical applications, " f"implementation considerations, performance characteristics, and future directions." for i in range(1, 51) ]) data = { 'model': 'default', 'messages': [{'role': 'user', 'content': prompt}], 'max_tokens': 5, 'temperature': 0, 'top_p': 1, 'stream': False } response = requests.post(url, headers=headers, json=data, proxies=proxies) result = response.json() usage = result['usage'] timings = result['timings'] total_tokens = usage['prompt_tokens'] prompt_ms = timings['prompt_ms'] prefill_speed = total_tokens / (prompt_ms / 1000) print(f"Prompt tokens: {total_tokens}") print(f"Prompt ms: {prompt_ms:.1f}") print(f"Prefill speed: {prefill_speed:.2f} tok/s")

6. 常見問題 (FAQ)

Q1: 為什麼 API 顯示的 prompt_per_second 只有 15-20 tok/s？

A: API 的 prompt_per_second = prompt_n / (prompt_ms / 1000)，其中 prompt_n 是實際需要 prefill 的 token 數（排除 cache 複用）。當 cache 複用率高時，實際需要 prefill 的 token 很少，所以顯示的速度低。正確的測量方法是用總 token 數除以總時間。

Q2: 為什麼有時測不到 250+ tok/s？

A: Prefill 速度受系統內存狀態影響很大。如果系統內存壓力大（free < 15%），可能會使用 swap，導致速度下降到 230-245 tok/s。建議關閉其他應用，確保系統內存充足。

Q3: n_batch=8192 為什麼 OOM？

A: n_batch=8192 需要更大的 KV cache 和中間緩衝區，在 16GB Mac 上會導致 GPU OOM（Insufficient Memory, status 5）。n_batch=6144 是最佳配置。

Q4: M2 prefill streaming 會影響 decode 速度嗎？

A: M2 prefill streaming 主要優化 prefill 階段，對 decode 速度影響較小。Decode 速度主要取決於 MTP acceptance rate、expert cache hit rate 和系統內存狀態。

Q5: 如何確認 M2 prefill streaming 已啟用？

A: 檢查 server log 中是否有 CGC-PREFILL-STREAM 相關輸出，或者使用 ps eww <pid> | grep PREFILL 查看環境變量。
