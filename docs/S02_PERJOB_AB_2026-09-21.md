## 0. 一句話

**(a) 拿到了一個近乎完美的強結論：`-np 4` 的 merge-read 已完全失效（關掉它 job 數只變 0.018%）。
(b) 拿不到結論：所有「時間」讀數在這個 cell 上的單臂漂移是 ±11～31%，而 `ADVISE_ASYNC` 的效應
只有 −7.5%，小於噪音 ⇒ Stage 1 不達 ship 判準。⇒ 槓桿仍在 Stage 2（砍 job 數）。**

---

## 1. 方法：為什麼不能直接 `./scripts/run_server.sh`

`run_server.sh` 有 env allowlist（`:1426` 的 `for _v in ... do SERVER_ENV+=`）：沒列出的
`CGC_*`／`LLAMA_EXPERT_CACHE_*` **靜默丟棄**。

| 旋鈕 | C++ 有 | 在 allowlist |
|---|---|---|
| `LLAMA_EXPERT_CACHE_NO_RDADVISE` | ✅ `:3489` | ✅ `:1552` |
| `LLAMA_EXPERT_CACHE_ADVISE_ASYNC` | ✅ `:3928` | ✅ `:1563` |
| **`LLAMA_EXPERT_CACHE_NO_MERGE`** | ✅ `:3495` | ❌ **沒有** |

而 (a) 那一臂**必須**用 `NO_MERGE`。選項是改共享 launcher（另一條 session 擁有它）或繞過去。
選後者：**讓 launcher 自己把答案吐出來，然後照著它重跑一次。**

```
CGC_DUMP_ENV=1 ./scripts/run_server.sh   ->   CGCENV BIN / ENV k=v / ARG x
Popen([BIN] + rewrite(ARG, -np, --port), env=dumped_env + extra)
```

`CGC_DUMP_ENV` 無副作用（跳過 preflight 與所有閘門），零 GPU、零行程。

**同構性驗證（bypass 值得信任的唯一理由）**：bypass 的 `-np 4` 冒煙跑出
`usec/job = 326.7`，而 np4 原始 log（`20260921_013118.log`，launcher 起的）是
`748901354 / 2218197 = 337.6` ⇒ **差 3.4%**。同一個機制。

> ⚠️ 反面教訓：**launcher 模式不能用來量這個東西。** `run_server.sh` 把 server 自己的輸出
> 導到 `Backup/cgc_logs/llama_server_*.log`，所以本工具抓的那條 pipe 上**沒有 `final stats:` 行**
> ⇒ launcher 臂會靜默回報 `file_reads=None`。冒煙時踩到一次（`base launcher` 那一行全是 0）。

## 2. Cell（五臂全部相同；這不是交付形狀）

`-np 4`、HTTP `/completion`、4 條併發串流、`warmup=0`、`reps=1`、
`CGC_PREFILL_STREAM=1` + `CGC_GATHER_SLAB_CAP=256` + pool 8 GiB（與 np4 原始 log 同口徑）。

Round 1 `--tokens 48`；Round 2 `--tokens 32`（縮短單臂、多換一次順序）。
**絕對 HTTP t/s 不是引擎的 decode 速度**（已知比 llama-bench 高 ~22%）——本階段的交付物是
引擎自己的計數器（`file_reads`／`fill_batch_usec`），它與形狀無關。

## 5. 判準裁決

| # | 判準（跑之前寫死） | 實測 | 裁決 |
|---|---|---|---|
| **(a)** | `NO_MERGE` 讓 `file_reads` 變化 **< 20%** ⇒ merge 在 np4 完全失效 | **+0.018%**（316,083 → 316,140，多 57 個 job） | ✅ **CONFIRMED** |
| **(b)** | `NO_RDADVISE` 或 `ADVISE_ASYNC` 讓降 **≥ 30%** | `ADVISE_ASYNC` **−7.5%**（配對）<br>`NO_RDADVISE` 在噪音內 | ❌ **未達 Stage 1 判準（≥20%）** |

### 5.1 (a) 為什麼是這輪唯一的強結論

關掉 merge 之後，**每層每一步的 job 數一個都沒少**（318 萬個 job 裡只多 57 個）。
⇒ `llama-expert-cache.cpp:3528` 的合併條件（檔案內**嚴格相鄰**）在 `-np 4` 的 union 下
一次都沒命中過。這不是推論：這是引擎自己數出來的，而且**重複三次完全相同**
（Round 1 三個 base 都是 316,083；Round 2 五臂都是 193,251）。

⇒ **Stage 2-a（放寬合併條件，允許跨過小 gap）對症，且是無損改動。**

### 5.2 (b) 必須寫成「不可判」，而不是「無效」

`file_reads` 是**計數器**：確定性、三次重跑一模一樣、對漂移免疫。
`usec/job`／`wall` 是**時間讀數**：Round 1 兩個相同 base 差 **31%**（415.4 → 544.0），
Round 2 三個 base 的 CV = **11.5%**（450.6 / 358.2 / 422.4，而且**非單調**——先變快再變慢）。

⇒ 任何單臂的 −17%（Round 1 的 `advise_async`）都**小於或等於漂移本身**。
只有配對設計才有發言權，而配對後效應只剩 −7.5%，且 4 個局部估計跨過 1.0。

> 這與這條線既有的教訓一致：記憶 §EN-335 記過單臂噪音 ≈ ±27%；那是另一個 cell，同樣的量級。

### 5.3 ⚠️ 更正一份文件的推測（原文不刪，在此更正）

`NP_PERJOB_FIX_PLAN_2026-09-21.md` §1.2 引 `llama-expert-cache.cpp:3593` 的註解
（「同步 `F_RDADVISE` 是 **780 µs/call，佔 submit 的 99%**」）推測它是 np4 per-job 成本的首犯。

**在 `-np 4` 這個 regime 下，這個外推不成立**：

- **完全關掉** rdadvise（`NO_RDADVISE=1`）的 `usec/job` 是 **1.028×**（Round 1），
  即「幾乎沒有變化」——若它真的是 submit 的 99%，關掉應該看到 submit 崩塌；
- `np4` 的帳也算不攏：2,218,197 jobs × 780 µs = **1,730 s**，而實測 `fill_batch_usec` 只有 **749 s**。

**合理的解讀**：780 µs 那個數字是別條線（M-F5）在**別的 regime** 測的，不能外推到這裡。
在本 cell 上，**同步 rdadvise 的成本 ≈ 它自己帶來的 kernel read-ahead 收益**（關掉是平的），
而 `ADVISE_ASYNC` 保留收益、去掉關鍵路徑上的等待 ⇒ 淨賺一點點（−7.5%）。這個故事三者自洽。

⇒ **Stage 1 不 ship。它是免費 env，留下來；但不值得為它花更多單臂樣本。**

## 6. 結論與下一步

**Stage 2（砍 job 數）是唯一主成分，進 Stage 2。**

- Stage 2-a（放寬 merge 條件，`G = 8 × per_expert_bytes`，多讀的中間專家寫進 scratch dst）
  現在有 **(a) 的直接支持**：它打的就是那個 100% 失效的條件。
- **阻塞點**：Stage 2-a 要寫 C++ 並**重建**，而
  ① 建置產物目前含**另一條 session 的未提交熱路徑改動**（`libggml-base`／`libllama*`／
  `llama-context.cpp` 等在 `git status` 裡是 M），② `cmake --build` 會蓋掉別人正在 map 的
  dylib ⇒ **本輪不動手**，等一個乾淨窗口（無 listener、`pgrep -fl llama-server` 為空）。
- `ADVISE_ASYNC` 保留為已知資訊；若日後在**交付形狀**（`prod_profile.py`，np1、llama-bench、
  prefill＋decode 兩軸）上順手跑一次配對且有效，那就是白拿——但那是另一個 cell，
  不能用本輪的 np4 數字替它說話。

## 7. 與其他 session 結論的交叉檢查（寫在收尾之前，不能跳）

本輪量測期間，另一條 session 的記憶寫了兩份審計（`§EN-373`、`§EN-374`），其中三條與本文件直接相關。
逐條處理，**不迴避衝突**：

### 7.1 ✅ build provenance 已驗：本輪的配對是同一個 build

`§EN-374` 警告 tree 上有 872 行未提交引擎改動、四顆 dylib 已變動 ⇒
「今天的 binary ≠ 交付 build，不能跨週直接比」。

實測 mtime：`build/bin/llama-server`、`libllama.0.0.279`、`libllama-common.0.0.279`、
`libllama-server-impl` 全部 = **2026-09-20 23:05:06**，`libggml-base` = 21:42:55。
而本輪 round1（11:02–11:12）、round2（11:25–11:40）、以及 np4 原始 log（01:31）
**全部落在最後一次重建之後** ⇒ 三者同 build：

| 比較 | 是否跨 build | 可否引用 |
|---|---|---|
| round1 五臂彼此 | 否 | ✅ 本輪所有比值的根據 |
| round2 五臂彼此（配對） | 否 | ✅ (b) 的 −7.5% 出自這裡 |
| bypass(base) 326.7 vs np4 log 337.6 | **否**（同 build） | ✅ 同構性驗證成立，但那是跨越 10 小時的兩個行程，**只是巧合地接近**，不能當精密數字 |
| 本輪任何數字 vs 更早的交付基線 | **是** | ❌ 不可比（tree 有 872 行未提交改動） |

### 7.2 ⚠️ `ADVISE_ASYNC` 其實**已被否證過一次**，本輪與它同向

`§EN-374` 指出 tree 裡早有 M-F5 的實測註解（`llama-expert-cache.h`）：
> 「rotated-order A/B，同一 binary：submit 880→9 µs 但 wait 1536→4291 µs，fill 2250→3962
> （+76%），decode 10.3–11.8→8.7–8.9（**−25%**）。Do NOT enable this expecting a speedup.」

⇒ **本輪的 −7.5%（且不顯著）與那個否證不矛盾**：在 np4 這個 job 數爆炸的形狀下，
async 化的收益比交付形狀更不明顯。**維持「不 ship」，且不再為它花樣本。**

### 7.3 🔴 `N ≈ 107` 已失去根據 —— 但本輪的 (a) 不依賴它

`§EN-373` 撤銷了「25 t/s 需要 N≈107」這個數字：混合 regime 的 M 曲線表（M=1 用交付錨點 92 ms、
其餘用 llama-bench，而 llama-bench 自己的 M=1 是 229 ms，差 2.49×），且 server 側唯一第二點
M=4 實測只有 3.71 t/s，比表的 M=1（10.8）還低 ⇒ 表的形狀在 server 上沒有任何一個點支持。

**本輪的結論不受影響**：(a) 是引擎自己的 job 計數器，不經過任何 M→t/s 的換算，
它只回答「 merge條件在這個 union 下有沒有命中過」——答案是**一次都沒有**。
Stage 2-a 的對症性不依賴 N 等於多少。

### 7.4 🔴 但這整條路交付不了 operator 的目標（必須講清楚）

`§EN-362` operator 已裁定 **25 ＝ 單流 decode**，並行／聚合口徑整條出局；
`§EN-374` 因此建議把這帖藥的決策變數從「聚合 decode t/s」改成 **「prefill t/s」**——
理由是 `NP_PERJOB_FIX_PLAN` §2.6 的洞察：**slab 的 2.8 GB/s 是同一個 per-job overhead 病**。

⇒ **本輪成果的正確定位**：它是 **prefill 路線**的機制確認，不是 decode 25 的進度。
下一步若要量它的價值，該量的是 `profile_duo --profile prefill250`（slab 路徑、M 很大、
per-job overhead 正是它的瓶頸），而不是再去量聚合 decode。
