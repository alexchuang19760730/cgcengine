## 二、理想形狀：25 t/s 需要什麼？

### 從屋頂線分析倒推

```
⚠️ 舊寫「理論天花板 M=2-3 時 ~50 t/s」—— 本輪找不到這個數的出處，而且兩個實測的上界比它低很多：
   • 完美 drafter 的天花板 = 19.39 t/s（`DRAFT_BUDGET_K_2026-09-22.md`）
   • 步時地板（eval-sync 鏈）= 146.8–164.5 ms ⇒ 即使 mean_len 拉到 4.0 也只有 24.3–27.2 t/s，
     而 rep 2 的 164.5 ms 在任何 accept 下都過不了 25（`TARGET25_NECESSARY_CONDITIONS` §3）
現在：12.13 t/s（認證窗口、k=2、mean len 2.64）
目標：25 t/s ⇒ S ≤ 106 ms/step，距離 2.06×
```

### 理想 shape 參數

| 參數 | 理想值 | 說明 | 本輪實測的更正 |
|---|---|---|---|
| **M（speculative width）** | 2-3 | 屋頂線甜蜜點，accept 率最高 | ❌ **方向錯**。k=3 每步只多吐 12% token（E 2.47→2.76）卻多付 31% 步時；用同一顆 harness 反解 α=0.654，**今天的最佳 k 是 1**（`DRAFT_BUDGET_K_2026-09-22.md`）|
| **Accept rate** | ~70-80% | M=3 時的典型值 | 實測 **k=2: 73.16%、k=3: 58.25%**，逐位元可重現（`P0_ARMS_2026-09-23.md`）⇒ accept 隨 k **下降**，不是上升 |
| **Expert cache hit rate** | >90% | 減少 compulsory miss | 未直接量；已知 miss 的 **25.6% 是 compulsory**（任何策略都碰不到）、74.4% 才是可政策的（`F1_CB_MISS_REGRESSION_RESULT`）|
| **Dispatch overhead** | <5 ms/步 | 現在 ~12 ms/步，要砍半 | 這個 12 ms 在任何後來的量測裡都找不到出處；見 §三（dense 全族只有 13.39 ms、每層 barrier 12.86 ms）|
| **Graph overhead** | <10 ms/步 | 現在 ~24 ms/步，要砍到一半以下 | 同上，無出處；今天最大的是**最後一層之後的 round remainder**（`VERIFY_MARGINAL_2026-09-22.md`）|
| **Dense GEMV 頻寬利用率** | >90% | 現在 85.7%，已經不錯 | 本輪重掃：**lm_head 84–87% 峰值**、整族上限 **3.09 ms＝2.16% 步時**（`DENSE_NSG_RESCAN_2026-09-23.md`）|

## 三、時間預算分配（每一步）

```
目標步時取決於 mean_len，而這是本輪最重要的一個形式更正：
    25 t/s = mean_len / step   ⇒   step = 40 × mean_len ms
  mean_len 4.0（最寬的 verify）⇒ 160 ms
  mean_len 2.64（今天 k=2）  ⇒ 106 ms
  mean_len 1.0（MTP off）    ⇒ 40 ms（今天 S0 = 93.3 ms ⇒ 2.33×）
所以「每步 80 ms」只在 mean_len=2 時成立；把它當固定靶子是舊表的第二個毛病。

理想的分配（上面那塊的 80 ms）—— 本輪的實測是：這張表裡有兩項**量不到對應物**
（Dispatch 12 ms、Graph 24 ms），而真正的最大一項（round remainder）舊表根本沒列。
```

### 現在的分配（對照）

⚠️ **下面這塊舊數字全部作廢**：它寫「每步 ~80 ms」，但認證窗口裡引擎自己報的是
**k=2 = 218 ms/step**（mean len 2.64、12.13 t/s），k=3 是 266–314 ms
（`CERTIFIED_WINDOW_K_AB_2026-09-23.md` §100–105、`P0_ARMS_2026-09-23.md` §160）。
25 t/s 在 mean len 2.64 下要 **S ≤ 106 ms/step** ⇒ 距離是 **2.06×**，不是「差距不大」。

用**有出處的量測**重寫（同一顆載體，但**每個數字來自不同儀器、不同 regime，因此只能當量級看**）：

| 項 | 量測值 | 佔 218 ms 步 | 出處 |
|---|---:|---:|---|
| dense GEMV 全族 | 13.39 ms | 6.1% | `DENSE_NSG_RESCAN_2026-09-23.md` §58 |
| MoE gather（T=1 / T=3 / T=4）| 8.09 / ≈24（由 T=1、T=4 內插）/ 31.81 ms | 11%（T=3） | `MOE_GATHER_BOUND_2026-09-22.md` §0（只有 T=1 與 T=4 是直讀）|
| draft head | 8.35 ms/token ⇒ k=2 約 16.7 ms | 7.7% | `MTP_K_SWEEP` §3、`P0_ARMS` §1.5 |
| cb（host top-k hook） | 0.695 ms/miss；含每層 barrier 12.86 ms/step | ~23%（temp 0.4、k=3 regime） | `F1_CB_MISS_REGRESSION_RESULT` §0 |
| **round remainder**（最後一層之後） | 邊際 verify token 的 **70–102%**（+29.35 ms/token, rep1） | **最大單項，未定額** | `VERIFY_MARGINAL_2026-09-22.md`、`TARGET25_NECESSARY_CONDITIONS` §2 |

⇒ 五個**已量到**的項加起來約 54%（dense + MoE + head），再加 cb 與 barrier 就接近七成；
剩下的最大一塊是**沒有人認領的 round remainder**。

**瓶頸排序（依本輪）：**
1. **round remainder** → 最大，而且它是 ladder 的**前提列**（拿掉它 step 352→245 ms，但仍有 rung 要 mean_len 5.4–9.6 而天花板是 4.0）
2. **eval-sync 鏈（每層 wait）** → 地板 146.8–164.5 ms，不可移除（不是可拿回的項）
3. **cb / miss** → 是**位元組側**的問題（少一點 miss），不是引擎側（M-F5 已判死 barrier 那一半）

### 六.0 標籤定義（先讀這個，再看表）

| 標籤 | 含義 | 什麼行動 |
|---|---|---|
| 【已判死】 | 有實測出處與數字；不是「還沒測」而是「**已排除**」 | 不要再排程，除非有新的機制假設 |

本地機器的解析度事實（`PAIRED_PROTOCOL_3PCT` §4、`INSTRUMENT_RESOLUTION` §4）：6 blocks（13 啟動）
的地板是 **14.7%**；要 3% 需要 **≈110 次交替啟動**（回歸）或 ≈430（只用括號）；而配對 sd = √2 ×
單臂 sd（2.28 vs 2.18 t/s）⇒ **配對在這台機器上買不到共同模態**。

### 六.1 先說三個舊結論的更正（本輪量到的）

**❌ 「Dense GEMV 已經 76–77%，打滿也只有 +2.4%」——上界比這個還低，而且現在有 reach 驗證。**
本輪把 `CGC_MMV_NSG` 接到三個 dense 型別並用**編譯出來的 pipeline 名**驗證確實到達 kernel
（iq4_xs 預設 nsg=2、q6_k nsg=2、q8_0 nsg=4，五個值全部出現），然後重掃占 98% dense 位元組的六個 shape：
整族上限是 **3.09 ms = 2.16% 步時**，而最乾淨的那條（`lm_head`，也是最大的單項）六臂中位數只差 2.1 個百分點、
最佳臂領先幅度剛好等於它自己的 ±5.4% 地板 ⇒ **平手，不是勝利**（`DENSE_NSG_RESCAN_2026-09-23.md`）。
⇒ 它同時是【已判死】與【3% 軸】：天花板在門檻下方，而先前那次 dense 掃描**根本無從知道自己在量什麼**。

**❌ 「MoE experts 20–30% 峰值，還有很大空間（可省 ~8 ms/步 = 10%）」——利用率是 31–50%，而天花板的
主人是 kernel，不是路由。** 實測每步 8.09 ms（T=1）→ 31.81 ms（T=4），跑在峰值 31–50%（gate/up 45–50%、
down 33%），kernel 側可回收 **5.0 / 19.5 ms**；但同一批資料給了兩個否定：**這個家族沒有批次攤薄**
（第 2 個 token 的成本是第 1 個的 **98%**），而「shared ids vs cycled ids 只差 2%」證明那 31–50% 的天花板
**不是路由散射造成的** ⇒ **pool 暖度、prerouter、prefetch 都動不了它**（`MOE_GATHER_BOUND_2026-09-22.md`）。
⇒ 【3% 軸，T=1】/【~6% 軸，T=4，且要改 kernel 結構】。

**❌ 「M=2-3 是屋頂線甜蜜點，accept 率最高」——方向相反。** k=3 比起 k=2：accept **下降**
（73.16% → 58.25%）、E 只升 12%（2.47 → 2.76）、步時多 31%（218 → 266–314 ms）。用成本律
`cost(T) = 41.74 + 51.56·T`（T = k+1）反解 α=0.654 ⇒ **今天的最佳 k 是 1**（11.42 t/s = 1.066× 基線），
k=3 是 **0.889×（淨虧）**（`DRAFT_BUDGET_K_2026-09-22.md`）。

## 七、現實檢查

### 我們離 25 t/s 還有多少距離？

```
現在：12.13 t/s（k=2、mean len 2.64、218 ms/step；認證窗口）
目標：25 t/s ⇒ S ≤ 106 ms/step（mean len 2.64）
差距：2.06×

但「差距不大」是不對的：地面（eval-sync 鏈 146.8–164.5 ms）本身就高於 106 ms，
而四條 rung 裡有三條要 mean_len 5.4–9.6 而天花板是 4.0（k+1）
⇒ 不是「再加把勁」，是「必須同時成立」的角點：
  [remainder 消失] AND [便宜的 drafter] AND [每層 host 項消失] AND α ≥ ~0.95
```

### 但要注意

```
1. 「測量噪音太大」已經不是一句感覺，是一條規則（本輪的產出）：
   → 同 config 可以散開 2.1×（5.84 → 12.35 t/s，輸出逐位元相同）
   → 根因是啟動當下的盒子狀態（thermal level 分得開極端；三個便宜見證都分不開）
   → 規則：啟臂前蓋 thermal 印章 + 複製 n≥3 並報 sd；≤3% 不准走 server A/B
   （要 ≈110 次交替啟動，或搬進同一個 process）

2. 已經不是「可能真的沒效果」，是「有上界的否定」：
   → NSG dense：天花板 2.16%（reach 已驗，不再是盲掃）
   → draft prefetch：劑量 0 且有機制
   → MMV_FUSE：三個獨立判決一致
   → M/k：方向跟舊文件相反（k=1 才是好的一邊），且從未被分離過

3. 真正的瓶頸現在有名有姓：
   → 最大的那一塊是沒人認領的 round remainder（邊際 token 的 70–102%）
   → 第二是 eval-sync 硬地板（146.8–164.5 ms）
   → 而這兩個都不是之前的 P0（dense / prefetch / M）
```

## 八、雙 Agent 架構：大腦 + 小腦

### 分工原則

就像我們討論的「大腦（理解/想像）+ 小腦（動作跟隨）」架構，我們的優化工作也拆成兩個 agent：

| Agent | 角色 | 做什麼 | 對應什麼 |
|---|---|---|---|
| **大腦 Agent** | 分析、規劃、判讀 | 看數據、寫分析、判斷瓶頸、決定下一步 | 對應我們討論的「視頻生成模型 / 想像力」 |
| **小腦 Agent** | 執行、跑實驗、寫代碼 | 跑 benchmark、改代碼、建 harness、執行掃描 | 對應我們討論的「HoloMotion / 動作跟隨」 |
| **協調者（我）** | 控制兩邊 | 分配任務、檢查結果、決定方向 | 對應「人類的決策中樞」 |

### 大腦 Agent 的職責

```
大腦（負責思考）：
  1. 讀取實驗數據
  2. 分析瓶頸在哪
  3. 判斷哪個方向值得繼續
  4. 寫分析報告
  5. 決定下一個該測什麼

→ 不直接跑代碼
→ 只看數據、做判斷、寫報告
```

### 小腦 Agent 的職責

```
小腦（負責執行）：
  1. 跑實驗（benchmark、harness）
  2. 改代碼（kernel、env、harness）
  3. 建工具（drift 校正、autotuner）
  4. 收集數據
  5. 把結果交給大腦

→ 不做判斷
→ 只執行任務、收集數據
```

### 協調者的職責

```
協調者（我）：
  1. 看大腦的分析 → 決定方向
  2. 給小腦派任務 → 執行實驗
  3. 檢查小腦的結果 → 交給大腦分析
  4. 發現問題 → 及時調整方向
  5. 確保 bit-exact gate 通過
```

## 十、結論

### Shape 世界模型告訴我們的事

```
1. 「25 t/s 做得到」還未被否證，但它的形式變了：
   不是「理論天花板 50、差距不大」，而是必須同時成立的角點
   [remainder 消失] AND [便宜的 drafter] AND [每層 host 項消失] AND α ≥ ~0.95
   而四條 rung 裡有三條今天要 mean_len 5.4–9.6、天花板是 4.0

2. 真正的戰場不是「dense vs MoE 的頻寬利用率」——兩者都已被量到上界：
   - dense 全族：13.39 ms，可拿回的 3.09 ms（2.16%）
   - MoE gather：10–32 ms，跑在 31–50% 峰值，但**沒有批次攤薄**，天花板主人是 kernel
   ⇒ 所以「路由/池子/預測」整族動不了它

3. 最大的槓桿（本輪重排後的真正前三）：
   ★ round remainder（邊際 token 的 70–102%，還沒人認領）——【主軸 + 前提列 + 需新儀器】
   ★ eval-sync 硬地板（146.8–164.5 ms）——【主軸，但屬引擎結構】
   ★ 把「量測」變成可認證的：本輪已完成（閘門 + 協定 + 解析度規則）

4. 已判死的方向（都有數字，見六.3）：
   - dense kernel tile / NSG 重掃（上界 2.16%，最佳臂＝地板）
   - CGC_DRAFT_PREFETCH 與整個「預測下一步專家」家族
   - CGC_MMV_FUSE（三個獨立判決）
   - 每層 barrier 的「可移出臨界路徑」那一半（M-F5 CLOSED negative）
   - overlap the fill（F2 FAIL + F5 REFUTED）、neighbour prefetch R=1

5. 解析度已經是數字，不再是形容詞：
   6 blocks（13 啟動）地板 14.7%；要 3% 需 ≈110 次交替啟動；
   配對買不到共同模態（sd = √2 × 單臂 sd）⇒ ≤3% 一律搬形狀隔離
```
