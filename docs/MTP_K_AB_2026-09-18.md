## 3. 「llama-bench 接好了嗎」與「verify 哪裡能省」

### 3.1 llama-bench 的接線：**只接了能跑的那一半**（原始碼證據）

- **今天的修復是真的**（`2fcf616b9`）：`test_gen_spec` 的 `n_past` 初始化 ⇒ llama-bench 能跑 MTP、rc=0。
- **但 verify 走的是另一條路**。`llama-context.cpp:6065-6090`：

```cpp
const bool verify_fast = getenv("CGC_VERIFY_DECODE") && cgc_phase == CGC_PHASE_VERIFY
                         && cparams.ctx_type == LLAMA_CONTEXT_TYPE_DEFAULT;
const bool draft_fast  = getenv("CGC_DRAFT_DECODE")  && cgc_phase == CGC_PHASE_DRAFT
                         && cparams.ctx_type == LLAMA_CONTEXT_TYPE_MTP && n_tokens == 1;
…
if (cgc_phase != CGC_PHASE_VERIFY && cgc_phase != CGC_PHASE_DRAFT) cgc_fast_eligible = false;
```

  而 `cgc_phase` **由呼叫端在每次 `llama_decode()` 前設定**（註解逐字：*UNKNOWN is the safe default:
  when caller forgets to set phase, we fall back to exact path*）。

- **`llama-bench.cpp` 裡對 phase 的引用是 0**（grep 無命中）⇒ bench 的 target 多 token verify 永遠是
  `UNKNOWN` ⇒ `cgc_fast_eligible=false` ⇒ 走 `ensure_batch` 的**精確填充路徑**。
- **日誌直接印出來**（`Backup/prod_matrix/20260918_15*_prod25_decode-spec/*.stderr.log`）：

```
llama_expert_cache: MTP fast path: calls=395 union=3160 cold(ZERO)=0   verify: calls=0 union=0   draft: calls=395 union=3160
```

  `union/calls = 3160/395 = 8.00` ⇒ **395 次全是單 token 的 draft**，**多 token 的 verify 一次都沒進來**。
  對照服務路徑：`verify: calls=8819 union=164778` ⇒ **18.69 experts/次**。

⇒ **判定：llama-bench 的 MTP 不能代表生產的 MTP。** 這也解釋了樹上「bench 量到 MTP ≈ 1.0／×1.06」與
「server 量到 ×0.695」為何不矛盾 —— **兩條路走的不是同一個池分支**，而這不是「兩人量到不同數字」，
是**量到不同的東西**。（修法方向：讓 llama-bench 的 spec 迴圈也設 phase ⇒ 但那會動 `src/` 且要重新
校準，屬新一輪。）

#### ★★ 但「走 ensure_batch」不等於「一個一個丟」（19:1x 更正一處措辭與一處推論）

上面那句原本接著寫「**它缺的正是最貴的那一段**」—— 那是**未經量測的推論**，而措辭會讓人讀成
「bench 逐個處理 verify」。**兩者都不成立**，證據如下：

**(a) 兩條路都用「本層 union」整批處理，不是逐 token。** `llama-context.cpp:6237-6260`：
union 在分支**之前**就算好，非快路徑也是**一次呼叫一整批**：

```cpp
std::vector<uint32_t> cold;  cold.reserve(uni.size());
for (size_t i = 0; i < uni.size(); ++i) { … }        // ← 走 union，不是逐 token
…
llama_expert_cache_ensure_batch(cache, il, cold.data(), cold.size(), false);   // 一批一次
```

而「串行」是一條**可切換的舊行為**：同處註解寫 `CGC_SYNCFILL_SERIAL=1 restores the old serial loop
for A/B`。**兩次量測都沒設它**（`run_server.sh:1504-1511` 只在你明示時才轉發）。

**(b) 日誌的填充粒度兩邊一樣**：

| | `decode/pool (ensure_slot+batch)` | `read shape` |
|---|---|---|
| bench（`-p 0 -n 128 -d 512 -r 3`） | hits **236284/249746**（94.6%） | jobs 39282、**0.37 MiB/job**、195 MiB/s |
| server（k=3，128 token） | hits 12172/15149（80.3%） | jobs 8400、**0.37 MiB/job**、108 MiB/s |

**job 大小逐位相同（0.37 MiB）** ⇒ 填充粒度一致，沒有「一邊逐個」。

**(c) 那真正的差別是什麼？是策略，不是批次**：
- **fast path（`touch`）**：只 LRU-touch **已 resident** 的專家，**不 fill、不等**（信任池是熱的）。
- **exact path（`ensure_batch`）**：**先把 cold 的補齊（真的去讀）再寫 remap** ⇒ 有 IO／等待成本。
  ⚠ 這兩條的貴賤**沒有量過**。日誌顯示 bench 每次請求的 IO 反而更多（3 rep × 128 token 共 14.08 GiB
  vs server 128 token 3.01 GiB），但那是**兩個不同 fixture**（n_predict／rep 數／窗口都不同），
  **不能正規化成「每 token」來比** —— 所以「bench 這條路是貴是便宜」目前是**未知**，
  不能反過來推論 bench 的 MTP 數字偏樂觀或偏保守。

⇒ 因此**可引用的只剩一句**：**bench 的 verify 與生產的 verify 走不同分支 ⇒ bench 的 MTP 數字不可搬去
生產**。至於「哪條貴」，要等 §3.2-B 那支 ctx 標籤出來才談得上。

### 3.2 verify 哪裡能省：**兩個位置，其中一個現在量不到**

**位置 A：union 本身（已證實有效，且已有一個便宜旋鈕）**
每多一個 distinct expert 約 **+14.5～19 ms**（§1 兩段斜率）。而 union 由「k ＋ draft 品質」決定：
- k=3 → 18.61（4 個 token 攤）；k=1 → 12.27（2 個 token 攤）
- **experts/token**：k=1 **7.13** ＜ MTP off **8.00** ＜ k=3 **8.06**
⇒ 這是今天最有價值的一個數：**k=1 在「每 token 專家讀取」這條軸上已經比不投機更好（−11%）**。
旋鈕就是 `CGC_SERVER_MTP_N_MAX`，**不必動 `src/`**。

**位置 B：draft pass —— 一個與 verify 無關的固定成本（今天量不到，但有證據說它存在）**
把 §1 的三臂放在「experts/token」這條軸上，k=1（7.13）應該**比 MTP off（8.00）快**，但它**更慢**
（10.28 vs 11.75）。那個差額只能是**每步多跑的那一次前向**（draft ctx，`ctx_type=MTP`）。
⇒ 對照 §1 的步時：MTP-off 一步 **85.1 ms**，k=1 一步 **167.3 ms** —— 差 **82 ms**，
而 union 只從 8 漲到 12.27（若照 14.5–19 ms/expert 算只值 62–81 ms）⇒ **正好用完**。
兩種解釋分不開，因為**沒有按 ctx 的逐 decode 分解**。

⇒ **缺的儀器（具名）**：`llama-context.cpp:1971` 的 `CGC-PHASE: n=… build=… alloc=… inputs=…
compute=… fill_wait=… gpu=… ms` **已經印了每次 `llama_decode` 的 compute 與 `n`**，但**沒有 ctx 標籤**
⇒ MTP-on 每步的兩次 decode（draft `n=1`、target `n=1+k`）**混在同一個平均裡**。
**下一步的前置就是給它加一個 ctx 標籤**（或按 `n_tokens` 分桶），那時才知道 82 ms 裡有多少是 draft pass。
**在這支儀器出現之前，「verify 路徑還能省多少」這個問題無法回答** —— 只能說 union 那一半可省。

## 4. 回答「MTP 還有機會轉正嗎」

  量測是 **×0.695**。**「×1.06」那個數今天沒複現**（它來自 `MEMORY_PERF` 的同 launch 配對）。

  這條軸上本來就有賺**，現在被 §3.2-B 那個固定成本吃掉。

  而那需要同時動 union 與 draft pass。
