## 1. P0-2 `CGC_DRAFT_PREFETCH`：它以前到不了引擎，現在到了，而它的劑量是 0

### 1.1 前置修正（可觀測性）

`KNOB_INVENTORY_VERIFIED_2026-09-22.md` §3-C 說它 **INERT** —— 實測確認：`CGC_DUMP_ENV=1` 的
resolved env 在設與不設時完全相同（0 命中）。launcher 從未把它加進 allowlist，所以任何 A/B 讀到的
「沒效果」其實是「沒旋鈕」。已在 `run_server.sh` 的 MTP 區塊補上（含 `_SYNC`），並照
`VERIFY_DECODE` 的既有慣例把 `=0` 翻成「不傳」（引擎的判定是 presence：`getenv() != nullptr && [0] != NUL`，
所以 `"0"` 是**開**）。驗證：

```
CGC_SERVER_MTP=1 CGC_DRAFT_PREFETCH=1  → ENV 命中 1
CGC_SERVER_MTP=0 CGC_DRAFT_PREFETCH=1  → ENV 命中 0   （引擎端本來就沒有 draft ctx，正確）
CGC_DRAFT_PREFETCH=0                   → ENV 命中 0   （off 真的是 off）
```

### 1.2 劑量（prod25 / MTP on / k=3 / 8 GiB，prefetch 臂的 server log）

`Backup/cgc_logs/llama_server_20260923_004018.log`，1086 行 `CGC-DRAFT-PF`：

```
collect il=40 ntok=1   ×341
collect il=40 ntok=4   ×111
collect il=40 ntok=8   ×4      （其餘 ntok=7/2/3 各 1–3）
trigger ASYNC queued=0 experts across 41 layers (total_queued=0)   ×124
```

**462 次 collect，每一次都在 `il=40`；沒有任何一次在 `il<=1`。124 次 trigger，每一次都 queued=0。**

### 1.3 為什麼是零（兩個獨立原因，都在程式碼上）

1. **預測只覆蓋 41 層裡的 1 層。** `src/llama.cpp/src/models/qwen35moe.cpp:576` 有
   `GGML_ASSERT(hparams.n_layer_nextn == 1 && "QWEN35MOE MTP currently only supports a single MTP block")`
   ⇒ draft ctx 的圖只有那一個 nextn block，因此 hook 只在 `il == n_layer`（=40）觸發 —— 與 collect
   註解（`llama-context.cpp:5416`）所說一致，而現在有 462 個讀數而不是一句註解。**draft 並不知道
   trunk 其他 40 層下一步要選誰**，所以「prefetch the EXACT experts the draft predicts will be needed
   next step」（:5378）這個設計意圖，在這顆模型上不可能成立。
2. **它唯一能碰的那一層，冷集合本來就是空的。** trigger 對每一顆 predicted expert 先做
   `if (st[e] >= 0) continue;`（:5628），只把 cold 的送出去。layer 40 每步都在用同樣那 8 顆 expert，
   池子每層 143 槽/256 專家 ⇒ 它們永遠 resident ⇒ `layer_cold` 恆 0。

### 1.4 Token 層的旁證

prefetch ON 與 OFF 兩臂的 draft 計數**逐位元相同**：`180/309`，在四支獨立啟動上重現（round 1 的
prefetch 與 ctl、round 2 的 prefetch 與 ctl）。也就是說這個旋鈕的**全部可觀測效果是零**，不只是速度。

### 1.5 它的天花板（即使修好也是）

唯一能受益的是 MTP block 自己的 forward：per-draft-token 成本 12% 是 head、88% 是 target verify
（`MTP_K_SWEEP_2026-09-22.md` §3），而 head 的 8.35 ms/token 已經在它的 kernel 地板（`mul_mat_id`
家族實測 8.36 ms/token）。⇒ **把預測接到正確的來源可以把這條路救活，但救活的是 8% 那一側。**

## 2. P0-1 M 寬度：accept 逐位元可重現，t/s 不能排序

### 2.1 六臂

| ord | arm | swap_in MB | accept | acc/draft | decode t/s |
|---:|---|---:|---:|---:|---:|
| 1 | k2 | 4224 | 73.16% | 169/231 | 12.47 |
| 2 | prefetch | 4920 | 58.25% | 180/309 | 11.17 |
| 3 | ctl (k3) | 4917 | 58.25% | 180/309 | 8.35 |
| 4 | ctl (k3) | 3416 | 58.25% | 180/309 | 6.26 |
| 5 | prefetch | 4662 | 58.25% | 180/309 | 6.66 |

### 2.2 兩件 drift-free 的事

**① accept 是決定性的、可重現的。** k2 = `169/231` 兩次；k3 = `180/309` **四次**。旋鈕確實到達引擎，
而且 token 流是確定性的。

**② E（每 verify step 的 token 數）是 drift-free 的，但要用引擎自己的欄位。**

⚠ **本文件第一版把 E 從那對計數反推（1.3669 / 1.7167），是錯的，已經被取代。** `mtp_accept_ab`
的 `draft_n`/`draft_n_accepted` 來自 server 的 *timings JSON*，而引擎在 stderr 印的是另一組：
`tools/server/server-context.cpp:674` 定義

```
mean_acc_len = 1 + n_draft_accepted / n_draft_verif_steps        ← 定義上就是 E
```

同一臂裡兩者不可互推（JSON 每請求 103 次 draft、log 是 95 generated），所以**引引擎、不引反推**：

| k | 三個計數請求的 mean len | E |
|---|---|---:|
| 2 | 2.21 / 2.57 / 2.64 | **2.47** |
| 3 | 2.35 / 2.97 / 2.97 | **2.76** |

⇒ **k=3 每步多吐 12% 的 token，不是 26%。** 方向仍與 P0-1 的因果敘述相反（accept% 從 73.16% 掉到
58.25% 而 E 上升），但幅度小得多 —— 而這讓下面 §3 的距離**更遠**，不是更近。

### 2.3 t/s 不能排序（而且這次有 null cell 當尺）

同一輪內的配對差：

| 配對 | true diff | round 1 | round 2 |
|---|---|---|---|
| k2 − ctl | **未知（要測的）** | +4.12 | +1.58 |
| prefetch − ctl | **0（由 §1.4：輸出逐位元相同）** | +2.82 | −0.40 |

null cell 在兩個方向都出現（+2.82 / −0.40），振幅 **2.82 t/s ≈ 25%** ⇒ **單對解析度 ≈ ±2.8 t/s**。
k 的兩對中最弱的那一對是 +1.58，**低於 null cell 自己的散開** ⇒

**判定：NOT SEPARATED。** 兩對同號只能說「k2 可能較快」，不能說分離了。這正是
`M4_PARITY_AB_2026-09-21.md` 自己寫的門檻紀律（全 rep 同號**且最弱 |Δ| ≥ 0.50**）在**同一個工具上**
被 null cell 反過來限制的樣子。

漂移的性質也量到了：t/s 隨啟動序單調下降（12.47 → 11.17 → 8.35 → 6.26 → 6.66 → 7.84），而 ord 4 的
swap 是六臂中**最低**的（3416 MB）卻最慢 ⇒ **不是 carried swap**，是啟動序／session 狀態。

⚠ 這與本線 §158 的結論**衝突**（那裡記的是「free memory 與 t/s 反單調、真變數是 carried swap」）。
兩者都是量到的，所以正確的述句是：**漂移至少有三個成因，不是一個** —— 今天的證據排除了 carried swap
（最低 swap 的那臂最慢）與 thermal（`pmset -g therm`：無任何 warning level 被記錄），剩下啟動序。
任何「等盒子乾淨再量」的處方因此不足，除非它同時釘住**同一序列中的第幾次啟動**。

### 2.4 成本模型說的也是「幾乎平手」

用 llama-bench within-rep fit 的 `C=28.43 ms`、`c_tok=69.56 ms/extra token`（`MTP_K_SWEEP` §2）：

```
step(k3)/step(k2) = (28.43+4·69.56)/(28.43+3·69.56) = 306.7/237.1 = 1.294
yield(k3)/yield(k2)                                  = 1.7167/1.3669 = 1.256
⇒ k2 領先 2.9%
```

⇒ **P0-1 是一個 ~3% 的軸，不是 doc 標的 ⭐⭐⭐「最大」，而這個盒子的工具解析度是 25%。** 要回答它，
先要有能分辨 3% 的工具，或把 k 的比較搬進同一個 process（現在做不到，`--spec-draft-n-max` 是啟動參數）。

## 3. 25 t/s 要的是成本軸，用同一輪的 drift-free 數字算

E 是 drift-free、t/s 是有漂移的，而步時是後者，所以下面每一步都用**同一臂自己的兩個數**（E 與 tps）
相除，比值不跨臂：

```
同臂的 step = E / tps，而 log 的 `eval time` 直接給了同一個東西：
  k3 範例臂：E = 2.97，10153.38 ms / 96 tokens ⇒ 96/2.97 = 32.3 步 ⇒ S = 314 ms（9.45 t/s）
  本輪 k3 臂的 S 落在 266–314 ms（11.17 → 9.45 t/s 那一段）
  最快的一支 k2 臂：E = 2.47，12.47 t/s ⇒ S = 198 ms

25 t/s 且 E = 2.76（k3）⇒ S ≤ 110 ms
⇒ 需要 2.4–2.9×（今天的 S 是 266–314 ms）
```

這與 roadmap 的 M3（100 → 40 ms）是同一句話，而**與 P0 的兩條路無關**：P0-1 是 3% 軸，
P0-2 的天花板在 8% 那一側且現在劑量為 0。

⚠ 同一天稍晚的六臂 null 序列（`docs/INSTRUMENT_RESOLUTION_2026-09-23.md`）在同一個 regime 上
量到 **1.79× 的同 config 散開（5.84–10.46 t/s，輸出逐位元相同）**，所以上面這些 S 值各自攜帶一個
±18% 的儀器項；「k2 的 198 ms」與「k3 的 266–314 ms」相差 34–58%，**大於任一單臂的儀器項**，
但那是跨臂比較，要當成方向而不是數字。

### 誠實欄

- regime 是 **greedy（`temperature: 0`）**、`prod25`、短 prompt（`n_predict 96`）。交付配方的
  temp 0.4 下 accept 會不同（`M4_PARITY_AB` 的 51–60% 就是那一族）⇒ **絕對值不可與 0.4 家族並排**，
