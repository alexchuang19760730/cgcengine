S1 儀器的形狀

2.1 內核側：CGC_TENSOR_CAPTURE 的四個旋鈕

旋鈕作用它回答的問題
CGC_TENSOR_CAPTURE逗號分隔的精確節點名，或 * 要讀哪些節點的輸出
CGC_TENSOR_CAPTURE_WORDS視窗寬度（預設 32，上限 32） 讀多少個元素
CGC_TENSOR_CAPTURE_TAILn_skip = ne - n 視窗錨在張量尾端（新 token），而不是開頭（舊 token）
CGC_TENSOR_CAPTURE_HASH內核走完整個張量，寫 4 個字 [sum, xor, 加權和(i+1), 元素數] 整個張量是否相同；sum／xor 對置換不變而加權和會變 ⇒ 能分辨「重排」與「值真的不同」

每次 dump 都印出 fuse=、ne=（clamp 前的元素數）、off=（視窗起點； 摘要模式為 -1）。沒有 off= 的視窗讀數無法與「整張量都讀了」區分，這是第 3 節第一個缺陷的直接後果。

2.2 引擎側：四個只印不進 gate 的讀數

讀數取樣點量什麼
TABLE-CHURN每次 publish每個 graph 發布幾次、被消費的 id 的對映移動幾次
SEL-DRIFT圖邊界（prev.assign 讓它正好是「上一張圖最後發布的表」） publish 到讀取之間，被消費的 id 其對映有沒有動
SLOT-OWNERexpert_cache_on_topk（填充之後） 整層 slot→expert 反查的摘要
SLOT-SEL同上只取被消費的 id 反查回專家，附 wrong／unowned， 並同列 idsum/idsxor/idwsum 當作它自己意思的對照

兩臂都必須帶 CGC_S1_TABLE_CHURN=1，否則一側空白——而「沒效果」與「沒設到」在 log 上同形。

3. 五個儀器缺陷，與它們各自的失效方式

#缺陷失效方式修法
1視窗恆從 element 0 起算 ggml 張量 ne0 最快 ⇒ 對 (2048,T) 的輸出，head 視窗就是 token 0（該 pass 最舊的）。 於是「dense 投影全同、只有 conv 輸入不同」不是矛盾，是兩個不同的視窗；七輪的 SAME 全是「token 0 相同」 _TAIL=1（n_skip = ne-n）＋ dump 記 off=；分析器 --windows 先印 ne/off
2--upto 24 自己變成盲點 它當初是為了避開尾段槽位溢出造成的併 pass；但它只採 graph 1..23，而那個階段序列 g0:T128, g1-2:T2, g3-27:T8, g28:T2, g29-30:T4, g31-35:T1 ⇒ 1..23 是 100% prefill，而專案服務的是 decode --decode-only（T 由 ne 自校準推出，不手填數字）、 --select-t N（第一個完整該 T 的 stage）、--list-stages
3dst_filter[256] 靜默截斷 23 個名字 ＝ 312 字元，只進 19 個、第 20 個切在名字中間（截斷點落在 attn_residu）， 丟掉的名字裡包含那一輪存在的理由（ffn_moe_logits_raw-2）。更糟的是分析器只列「出現過的名字」 ⇒ 被丟掉的根本不顯示 CGC_DST_FILTER_MAX=2048 ＋ 截斷時 WARNING ＋ 啟動時印生效清單； 分析器列出「CHAIN 中請求過但從未捕獲」的名字
4mul_mat_id 的擷取丟掉 n_tokens 呼叫點寫死 ne0 * ne1，而輸出是三維 [n_embd, n_expert_used, n_tokens] ⇒ 只讀 token 0。簽名：同一組幾何下 down-1 報 ne=16384、 weighted-1 報 ne=32768（正好一半） 拿掉那個參數，一律用 ggml_nelements(op)
5TAIL=1 對 >32 元素的張量只寫哨兵 host 把 n_ids 傳成視窗長度（32），而內核的界是 j < n_ids、 j = n_skip + i ⇒ 一超過就全哨兵。實測 head 0/533 全哨兵、tail 188/205。 而全哨兵列互比是「相等」——一個壞讀數出具了一個自信的「相同」 host 傳完整元素數；修好後 246 列 / 246 含真值 / 0 全哨兵

兩個通則。（a）儀器自己的位置也是儀器的一部分：cgc_dst_capture_at 的宣告曾被放在 「當前第一個呼叫它的 dispatcher」上面，於是每次把鉤子往前加，就要賠一次編譯失敗——三次之後改成放在檔案最前。 （b）「沒有差異」與「沒有比較」必須印得出來：缺陷 3 與 5 都是「讀不到」，而在輸出上都長得像「相同」或 「沒人要求」。

4. S1 的現行結論與已否證的機制

4.1 現行結論

  • 兩臂不是 bit-identical：錨 2d4e5099 vs S1 f0acf7d2（各四輪臂內穩定）。 產出文字的分歧在第 1～2 個生成 token。
  • 分歧＝第一個被 GPU table 服務的層的 MoE gather。該層 router logits 與 top-k 權重逐位元相同， 而 gate/up/down/weighted/out 全部 DIFF；sum 與 xor 都不同 ⇒ 不是重排；窗口真值互相關 0.16–0.18 ⇒ 互相無關，不是微小擾動。
  • 層號由 CGC_S1_MIN_IL 決定（見 §0 第 1 條）。
  • 在那個 pass 上，layer 0 的 15 個節點、mul_mat_id 的 ids（120/120）、池佈局與被消費集合（40/40） 全部相同。

4.2 已否證的機制（累積）

候選處置證據

一個要記的自我修正。SLOT-SEL 這個讀數在數學上退化了：因為 wrong = 0 且 unowned = 0，owner == ids[j] 逐元素成立， 於是「把 slot 反查回身分再摘要」等於摘要 ids 本身。我在同一行加了 idsum/idsxor/idwsum 當對照，440/440 格全部相等 ⇒ 退化確認。通則： 任何「把 A 反查回 B 再摘要」的讀數，都要同時摘要 B 本身，否則測到的是恆等式。

7. 誠實邊界

本檔不主張：

  • 不主張 S1 已定位完成。剩下唯一未測的敘述是「同一組 ids、同一池佈局、同一反查之下，gather 讀到的 位元組不同」。主機側的路已被證明對 S1 臂無效（§4.2 最後一列），要往裝置側走。
  • 不主張「定期上傳 GitHub」有任何形式的恢復。本輪只是把事實查清並刷新快照； 要自動化需要一個決策（推哪條分支、Windows 那份留不留），本輪沒有做。
  • 不主張 D5 的 9/9 證明了 S1 的儀器「正確」。它證明的是加了這些儀器之後，oracle 配置的 logits 沒有變——因為所有新旋鈕預設關閉。它是一條「沒有副作用」的證據，不是功能證據。

未跑的東西：RUN_REPLAY_BENCH=0（依 D2：.replay_bench_baseline.json 自 2026-09-08 起 stale，跑它等於拿舊基線比新程式）。precommit_e2e_gate.sh 刻意沒有接進 hook （00b70bebc），所以缺少 e2e 是既定決定、不是遺漏。

本輪沒有動的：引擎的數值路徑一行未改（四個讀數只印、且預設關閉）；agent_harness/ 只有快照與兩個衍生索引被寫入。
