## 1. M3：依失敗分支結案

**離開條件（`ROADMAP_PREFILL250_DECODE25_2026-09-13.md` §M3 原文）**

- **成功**：decode（**MTP off**）≥ **15 t/s**，且 M1／M2 = 100%
- **失敗**：寫一份「找不到路」的結論，**附上 M0 的剖面表當證據**；允許否定收場，
  但**不允許用沒拆開的數字下去做決策**

**判定：未達。** 今天可引用的 MTP-off 值是 **10.78 t/s**（16:49 的 NOMINAL 剖面，與 09-16 逐字吻合）；
15 需要 **1.39×**。（另註：M3 的**目標**是 `100 ms/token → 40 ms/token` ＝ **2.32×**，
比離開條件嚴得多。17:14 那份 **7.76 t/s 是 HEAVY，不可引用**。）

**失敗分支的交付物 ＝ `docs/M3_VERDICT_2026-09-17.md`**，它比 roadmap 要求的多做了三件事：

1. **附了剖面證據**（`CGC-PHASE` 的相位拆解 ＋ `CGC-GPUTIME` ＋ `CGC-DECPROF`）。
2. **把三條路正式關閉**：圖建構／alloc／inputs ＝ **0.07%**（0.023／0.037／0.026 ms 對比 `compute` 118.5 ms
   —— 差三個數量級，熱不可能改變這個結論）；IO／填槽 ＝ `fill_wait **0.000 ms**`。
3. **把兩個儀器正式關閉，並指出唯一活路**：
   - `CGC_PHASE_TIMING` ❌ 死（`compute == gpu` 逐位相同 ⇒ 拆不開）
   - `CGC_VERIFY_OP_TIMING` ❌ 死（目標判定含 `node->src[2]->ne[1] > 1` ⇒ **只在 T>1 生效**，
     而 M3 的判準是 T=1 ⇒ **對 M3 零輸出**）⇒ `debug-verify-path-breakdown.md` 那組逐型別數字
     （gate／up／down ≈0.8／0.8／1.0 ms）**不能移植到 T=1 的 decode**
   - ✅ 逐節點 GPU 時間（Metal counter sample buffer）是唯一能給 GPU 側答案的機制
     （`CGC-GPUTIME` 的粒度只到 segment ＝ 層）

⇒ **結案**：M3 以否定結果結束，且符合「不允許用沒拆開的數字做決策」。
**重開條件**：逐節點 GPU 時間儀器建立後，用它裁決 `M3_VERDICT` §4.3 那個 **9–22 ms 的儀器盲區**
（`wait` 的 ~50 ms 裡分不清「GPU 在忙但 CPU 在等」與「CPU 在忙」）。

## 2. M5：結案為「已排除的死路」

**離開條件（roadmap §M5 原文）**

- overlap 增益 **≥ 10%** 才保留；**< 10% 記錄為已排除的死路**並把旗標預設關閉
- M1／M2 = 100%

**判定**

- M1／M2 = 100% ✓ —— gate 兩臂都是 `M1 9/9、M2 9/9、M3 9/9`，含 aux `full_fnv1a64` 也 9/9。
- **overlap 增益 < 10%（本輪判為 ≈ 0）**；旗標**已維持預設關**（`CGC_PREROUTER` 必須顯式設定）✓

**判定的依據（三個既有讀數 ＋ 一個機制）**

1. **`fill_wait = 0.000 ms`** —— 池填充不在關鍵路徑（`M3_VERDICT` §3 已據此把「IO／填槽」正式關閉）。
   預取只能省「等待填充」的時間 ⇒ 那一塊本身是 0。
2. **`queued / pred_total = 1062 / 64320 = 1.65%`**（本輪 B 臂實測，4 個請求）
   ⇒ 預取的**量**本身就極小。
3. **`precision = 4.2%`**（B 臂）／12.8%（短序列）⇒ 預測的專家只有 4% 真的被該層選中。
4. **機制（讀 code）**：predictor 排序 `freq` 的 top-K，而 `prewarm_hot`
   （`llama-context.cpp:1928`）在**第一步 decode 之前**就用**同一個 `freq`** 把池填好
   ⇒ 預測的專家**按構造**已經 resident，`prefetch_slot` 對 resident 直接 `return -1`
   （`llama-expert-cache.cpp:1326-1331`）。**預測器與 prewarm 共用同一個資訊源，原理上不可能超越它。**

### ★ 本輪的 A/B 被判定為「功效不足」，**不是「無差異」—— 這一條請勿誤讀**

`CGC_PREROUTER` 開／關，各 **4 個請求**（prompt 208 token、decode 96–112 token），`temperature = 0`，
同一顆 binary、池 8 GiB、**開跑前熱狀態是 COLD（`thermalpressurelevel = 0`）**、無其他量測行程：

| | A（`CGC_PREROUTER` 未設） | B（`CGC_PREROUTER=1`） |
|---|---|---|
| decode t/s（4 個請求，按順序） | 3.64 / 5.25 / 9.30 / 7.30 | 7.59 / 7.33 / 7.66 / 3.97 |
| decode t/s 中位 | 6.28 | **7.50（+19%）** |
| prefill t/s（4 個請求，按順序） | 17.6 / 24.2 / 22.0 / 31.6 | 28.9 / 39.6 / 41.7 / 38.3 |

**這組數字不能用來判 overlap：**

- **A 臂自己的散佈是 2.6×**（3.64 → 9.30），而判準是 **10%** ⇒ 功效不足。
- **B 跑在 A 之後、環境更暖**（prefill 17.6→31.6 對 28.9→41.7）⇒ 「+19%」與暖機方向一致，
  是**混淆**不是增益。
- 因此 **「B 的中位比 A 高 19%」沒有證據價值**。把它寫在這裡的**唯一目的**是防止它日後被引成
  「M5 有 +19%」。

**重開條件（三個都要）**
(i) 先修 `decode-only` gate（見下）；
(ii) 換一個**與 prewarm 不同源**的預測器；
(iii) 在 **`fill_wait > 0`** 的配置上量 —— 那才是預取有空間的 regime。
**並且**任何重開的量測都要走 `M1_WORKITEM4_…` §6 改寫後的那套紀律（交錯 ≥3 輪、配對中位與 IQR、
同 build／同池／同 profile、只有 COLD-STATE 可作交付數字）。

### ⚠️ 實作缺陷（若要重開，必須先修）

本輪的 predictor 呼叫點（`llama-context.cpp:5373` 的 `prerouter_score`、`:5377` 的 `prerouter_predict`）
**沒有 `cgc_is_decode_graph()` gate** ⇒ **prefill／MTP draft／trunk verify 都會跑 predictor**。
這**違反 M5 工作項的「只做 decode、只做 L+1 的 8 顆」**。
（同一位置的 SpAc 註解明寫它「fires on every path that reaches here — large prefill, MTP draft and trunk
verify alike」，我的呼叫點緊鄰它，因此行為相同。）
⇒ 本輪量到的 `calls`／`queued` 是 **prefill 與 decode 混合**的數字，而工作項只允許 decode。
