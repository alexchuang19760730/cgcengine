一句話結論：S1 的分歧由「服務路徑」決定，與層號無關。 由 whole-layer slab 服務的 graph（256/256 experts resident）逐位元相同； 由 partial pool 服務的 graph（143/256）必定分歧，且從第一個池化層起。 這是一條可執行的判別式，不是一個相關性。

本輪同時翻掉兩條先前的判讀，並挖出一個更重的既有缺陷：

  • §9.18 的 decode 探針前提是假的。decode 第 0 步的 layer 0 就已經不同， 而它的輸入是 prefill 留下的狀態——「輸入相同 + ids 相同 ⇒ 輸出不同」跑不起來， 因為沒有「相同輸入」這個起點。（逐專家列拆分另否證了排列假說。）
  • D3 的前提 B 不成立。被消費的 expert→slot 映射在 47.5% 的 decode 步上會動 ⇒ 發布不是冗餘、排序要求真實存在 ⇒ n_segs 由 40 收到 ~1 不由此推出。
  • （新增，權重最重）一條 2026-09-09 的品質修復六天來從未生效。 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0 的三個讀者全部測「存在」， 而 profile 把它設成 0 ⇒ "0" 是非空指標 ⇒ 「關掉」等於打開。blk.0 一直被排除在 pool 之外（CGC-DECPROF 報 layers=39，非 40），而 profile 的註解寫的正好相反。見 §2.3。

1. 分歧由服務路徑決定，與層號無關（本輪核心讀數）

1.1 先立前提：探針自身健全

在解釋任何跨臂差異之前，必須先證明這個探針本身是決定性的——否則跨臂差異可能 只是探針的抖動。做法是同一個臂跑兩個獨立 process：

比對層數比對逐位元不同比率
p25-outcap-base 第 1 跑 vs 第 2 跑480 00.0%
p25-outcap-base 第 1 跑 vs p25-slotgpu-outcap480 480100%
p25-outcap-base 第 2 跑 vs p25-slotgpu-outcap480 480100%

兩次獨立 process 的基準臂逐位元完全相同（480/480）⇒ ggml_set_output 的釘住沒有引入不確定性， 「釘住擾動了讀數」這個疑慮被排除。而 S1 臂在第一個 decode 步的第一層 MoE 就已經不同。

探針形狀：CGC-S1: OUT graph=N il=L ne=[2048 8 1] fnv1a64=…。 2048 = n_embd、8 = n_expert_used、1 = token ⇒ graph 0..11 確實是 12 個連續的單 token decode 步。480 行 = 12 graphs × 40 層，兩臂對齊。

1.2 為什麼 decode 探針不能用，prefill 階梯才行

decode 的層序不可用於定位：decode 第 0 步的 layer 0 輸入由 prefill 產生的 KV cache 導出，而兩臂的 prefill 本來就不同（M1 數值閘門 5/9）⇒ 每一個 decode 層都是「上游早已發生的分歧」的下游， 在那裡看到 480/480 不同不能定位任何東西。

prefill 才是乾淨的梯子：layer 0 的輸入是 embedding，依構造相同。 所以「兩臂第一個不同的層」直接命名載體。CGC_S1_OUT_CAP=pre 選它， 且只釘 CGC_S1_OUT_LAYERS 指名的層（見 §2.1，層窗不是便利，是硬需求）。

1.3 判別式：兩階獨立複現

做兩階，各 4 層深：0-3 與 4-7。8 層、6 個 graph、2 個臂 = 96 個配對， 結果完全同構：

graphntok服務路徑layer 0layer 1–7
0, 12partial pool（143/256 resident） EQNE
2182CGC-PREFILL-STREAM（256/256） EQEQ
322CGC-PREFILL-STREAM（256/256） EQEQ
4, 54partial pool（143/256） EQNE

關鍵是這條 log 行的分布——它恰好只出現在 ntok=182 與 ntok=22， 正是 8 層全同的那兩個 graph：

CGC-PREFILL-STREAM: il=0 kind=0 ntok=182

標記與結果在 96 個配對上完全一致，且有兩階獨立複現。 layer 0 從不分歧，而原因不是相關性、是構造：layer 0 根本不被池化 （CGC-DECPROF 報 layers=39，非 40；同一 log 內 19 次、0 次反例）。 所以「第一個分歧層 = 第一個池化層」是精確的，而 layer 0 不在那個集合裡。 這個「非池化」的成因本身是一個更重的既有缺陷，見 §2.3。

判別式（推理鏈）：

slab 服務 ⇒ bit-identical；partial pool 服務 ⇒ 分歧。 第一個分歧層 = 第一個池化層。

變數是路徑，不是索引。所以「開更深的層窗」價值低於表面—— 它不會改變判別式，只會再確認一次。下一步該量的是被消費 id 背後的 slot 內容（owner-set）。

1.4 排列假說被否證

decode 對的 480/480 全層不同，但「8 個專家的排列」是數值中立的可能解釋 （對該層加權和無影響，剛好能解釋「router logits 相同」）。加印逐專家列雜湊即可分開：

判準層數結果
整張張量雜湊相同4800
列多重集相同（僅順序不同）4800
列多重集不同（內容差異）480480

不是排列。480/480 層的逐專家列值都不同 ⇒ 是內容差異，不是順序假象。

2. 兩個新教訓（已寫成 CONVENTIONS A8 / 修訂 A7）

2.1 A8｜釘住的成本不是它的位元組數

四組配對把「用小算盤估釘住成本」這個做法整條否證：

範圍結果
40 層 × 全 graph（decode + prefill）Metal OOM，fail-stop，連一個請求都服務不了
11 層 × 僅 prefillMetal OOM，fail-stop
4 層 × 僅 prefill通過
40 層 × 僅 decode通過

失敗的那個 graph 是 ntok=2，11 個釘住的層在那裡共約 1.4 MB。 1.4 MB 撐不爆一個 Metal 預算。控制變數候選是「每 graph 被標為 output 的張量個數」， 機制尚未確立。

我先後寫過兩個錯的位元組預算（「50 MB/層 × 40 層 ≈ 2 GB」與 「402 MB/層」），兩個都被同一組配對反駁。任何「釘住很便宜，因為這些張量很小」形式的推理， 都被這幾跑否證。

這也解釋了為何釘住要用相位（ubatch.n_tokens <= 8）而不是位元組預算來限範圍： 某個小到位元組安全的預算，在每個 ubatch 尺寸下都得重新推導一次。

2.2 A7（修訂）｜工具回報成功 ≠ 改動在樹裡，且並行編輯同一檔會靜默丟失

本輪三個對同一檔案的並行編輯全部回報成功，只有一個落盤。 更糟的是同一輪稍早已刪掉那些函式的定義，而其中兩個引用沒有被清掉 ⇒ 檔案一度引用不存在的函式。

辨識這個失敗模式的特徵簽章是：探針被編進 binary、卻可證地從未觸發。 本次的實例是 CGC-S1: OUT 這個字串在 libllama 裡（證明 binary 已建）， 卻從未印出任何一行。追查方式只能是專用搜尋 + git diff 作地面真相。

操作規則（已固化）：單一檔案的多處修改逐一序列化送出； 每次編輯後以 git diff -U0 -- <file> | grep '^@@' 核對 hunk 清單。

2.3 A9｜測「存在」的旋鈕，它記錄下來的值只代表意圖

本輪在解釋「layer 0 為何從不分歧」時，挖到一個與 S1 無關、但權重更重的缺陷。

事實證據
三個讀者全部測「存在」 llama.cpp:396、llama-expert-cache.cpp:1708、 llama-context.cpp:5222 皆為 getenv("LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0") != nullptr
profile 把它設成 0，且真的傳進子行程 run_server.sh:939-945 的 SERVER_ENV，由 :1493 的 env "${SERVER_ENV[@]}" "$BIN" … 送出 ⇒ getenv 回傳 非空的 "0"

更糟的是快照記錄的是意圖、行為卻相反：所有 cap_*.json 與 llama-bench 的 env 區塊都印 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0: "0"。 這與舊 oracle cap（dec-20260915-2233，記錄意圖）同一個病， 也是本專案 presence-vs-value 家族的第三例——前兩例是 CGC_OA_ASYNC （dec-20260915-2142／2215；後者的值感知修正靜默改道四個 profile 並迫使閘門重新基線）。

本輪只記錄、不修。把閘門改成值感知會把 layer 0 拉進 pool ⇒ 改變 M1/M2/M3 閘門正在比較的數值 ⇒ 會讓本輪的閘門基線當場失效。 這正是 CGC_OA_ASYNC 那次修正迫使重新基線的同一個形狀。 修法成本低（3 個站點各一個 predicate），但必須單獨一輪、附自己的閘門基線。 列為下一步第 1 項。

這也讓判別式從「相關性」升級為「構造」： layer 0 相同是因為兩臂在 layer 0 讀同一份全寬權重、同一組原始 id， 相等是被強制的，不是被觀察到的。

5.1 §8.3 地雷：為什麼選「clamp 升為硬前置條件」而不是「強制保留 ZERO slot」

先釘住前提。有兩個 publish 呼叫點，它們獨立分歧：

呼叫點寫 leaf 用什麼非 resident 時 leaf 寫入原本是否保留 clamp 返回值
fast-path（verify_fast || draft_fast 內）slot_table_safe ZERO slot 或 −1丟棄（已修）
pool / slow-path原始 slot table永遠 −1丟棄（已修）

而 zero_slot_enabled() 綁在 MTP fast-path env 上 （CGC_VERIFY_DECODE / CGC_DRAFT_DECODE）。 所有 S1 臂都是 CGC_SERVER_MTP=0 ⇒ zero_slot < 0 ⇒ 走到 §8.3 表格的第三列（leaf 寫 −1 吵，table 夾 0 靜默）。 而 MTP-off 的每個 S1 臂走的正是 pool-path—— 這也同時解釋了先前 LLAMA_EXPERT_CACHE_STEP_DBG 的 0 行 （它的 block 就在 fast-path 分支內）。

實測：clamped_selected = 0。對被實際消費的 id 而言，本次 §8.3 地雷沒有觸發。原因是時序： ensure_batch（填槽）→ publish → 寫 leaf， 所以 publish 時看到的是已填好的槽。

否決的方案：「強制保留 ZERO slot」會改動 usable_slots / pick_slot 的算術 ⇒ 動 pool 布局 ⇒ 移動 S1 閘門要比較的數值本身， 與 bit-identical 不相容。選 clamp-as-hard-precondition（CGC_S1_CLAMP_ABORT）。

B1 提醒（自己剛寫的規則）：clamped_table = 79326 / （4251 × 256）= 44.1% 只是「143 slot vs 256 expert 的非 resident 比例」—— 每次運行都這麼大 ⇒ 不含資訊。所以計數必須按「實際被讀取的 id」拆分： n_slot_table_clamped_selected。

5.2 前提 B（發布是否冗餘）：不成立

要回答的不是「全表動幾次」（1976 次 / 77 graphs），也不是「函式被呼叫幾次」 （退化題：呼叫點全在 hook 內 ⇒ 基準 0 次、S1 每層 1 次）， 而是「被消費的映射會不會動」。用 CGC_S1_TABLE_CHURN=1 拆出來：

量值讀法
publishes1014 = 39 層 × 26 graphs ⇒ 每步每層一次
changed_entries1423 全表變動（不含資訊，見 B1）
consumed_changed389 被消費映射真的變了
consumed_unchanged_publishes430發布了但被消費映射沒變
比例389 / 819 = 47.5% 近一半的 decode 步，被消費映射會動

⇒ 發布不是冗餘的、排序要求真實存在 ⇒ D3 的 n_segs 收縮不由「前提 B」推出。 D3 要成立，必須另找理由（或接受 D3 只買到「圖裡沒有 host 寫入」這一項，而不買到段數）。

6. 誠實的邊界

  • skip0 的缺陷本輪只記錄、未修（§2.3）。它對本輪全部讀數的影響未被評估： 所有 S1 臂與基準臂都在「layer 0 不池化」下量測。判別式不受此影響（兩臂同構）， 但任何「這條路徑生產上會更快/更好」的推論都必須先修好它再量。
  • 本輪沒有修，是因為修它會改變閘門正在比較的數值—— 這不是保守，是被 CGC_OA_ASYNC 那次「值感知修正靜默改道四個 profile」教訓過的流程約束。
  • S1 的 bit-identical 閘門仍未通過。本輪把它收斂成一條判別式 （路徑決定分歧），但尚未指出機制：是 slot 內容（owner-set）刷新時序， 還是 partial pool 下 down 投影讀到的實際權重不同，兩者都與判別式相容。
  • 下一個唯一決定性的測量：在 prefill 階梯上捕捉被消費 id 背後的 slot 內容 （owner-set），以及 ffn_moe_down 在同一個 pool graph 上的 逐層讀數。開更深的層窗價值低於表面——變數是路徑不是索引。
  • §3 的 matrix 讀數不可引用為 regression 或中性（單次 matrix 的重複性帶 −20.3% ~ +32.3%，同 binary）。本輪的貢獻是量到了那個帶的寬度， 不是把某個數字變成結論。
  • S1 臂的吞吐完全不可引用：符號未定（1.403 / 1.243 / 0.834）＋長度混淆（100 vs 58）。
  • 釘住的成本機制未確立。知道「不是位元組」，但「是什麼」只有一個候選 （每 graph 的 output 張量個數），未證。
  • M1 是相對不變量，不是絕對正確性。確定性錯誤依構造不可見。
  • 內核側 ids 儀器的 stride 限制：stride=8 ⇒ n_ids=64 時只看得到 token 0。
  • 本輪沒有動 E1（git mv 進 tb_loop/）與 E2/E3/E4 的任何檔案。
