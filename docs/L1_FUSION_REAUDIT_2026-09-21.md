# L1 复审：bin 融合还能再拿多少？—— 答案 1.33%，低于门槛，不做

日期 2026-09-21 · **0 重建、0 写 C++**（`CGC_FUSE_MAX`／`CGC_FUSE_OFF` 已在 shipped binary 里，
`strings libggml-metal.dylib` 确认；build 指纹跑前跑后一致）
工具 `Backup/phase_decomp/L1/fuse_depth_scan.py`，raw stderr 留于 `Backup/phase_decomp/L1/raw/`

---

## 0. 结论先行

| 问题 | 答案 |
|---|---|
| bin 融合现在值多少？ | **已实现 ~20%**（ADD ratio 0.35–0.37 vs 不熔 1.000） |
| 再加深（cap 7 → 9，把 9-ADD 全熔）能拿多少？ | **0.76%** |
| 把 MUL 纳入 bin 白名单能拿多少？ | **0.57%** |
| DIV 呢？ | **0**（图里 **201 个全是孤立节点**，无从熔起） |
| **L1 合计** | **1.33%** ⇒ **低于 3% 可见门槛 ⇒ 不做** |

**这不是「融合无效」—— 恰恰相反，它已经把能熔的都熔了。**
真正剩下的是**孤立小 op**（每步 ~324 个），它们不成链，融合在原理上救不了。
那批 op 正是 K5（45.6 µs 常数）的作用对象 ⇒ **L1 结案，K5 是唯一主线。**

---

## 1. 方法：为什么这次能绕开 ±27% 噪音

`CEILING_STACK_2026-09-21.md` 里 L1 的 5.6% 是**算术推算**（节点数 × 单价）。推算依赖两个未验证前提：
① 9-ADD 链真的存在；② 链深上限是瓶颈。这两个都是**计数**问题，不是计时问题。

于是这次读的是两个计数仪器：

- **`CGC_DISPATCH_CENSUS`** 的 per-op 行同时印 `dispatches=` 与 `nodes=` ⇒ **比值 = 该 op 的熔合率**
  （1.000 = 没熔，0.35 = 熔掉 65%）
- **图 dump**（`CGC_GRPH_DBG`，K2 那份 `llama_server_20260921_173218.log`，20671 节点）
  ⇒ **可以直接数连续同类型链的长度**

⚠️ **但「计数 = 确定」这个假设本身被测出是错的**（§4.2）。

---

## 2. 读码发现一：bin 融合的 `fops` 被硬编码成 ADD

`ggml-metal-ops.cpp:5770-5778`：

```cpp
if (use_fusion && cgc_fuse_allowed("bin")) {
    fops[0] = GGML_OP_ADD;  fops[1] = GGML_OP_ADD;  ... fops[7] = GGML_OP_ADD;

    for (n_fuse = 0; n_fuse <= 6 && n_fuse < cgc_fuse_max() - 1; ++n_fuse) {
        if (!ctx->can_fuse(idx + n_fuse, fops + n_fuse, 2)) break;
```

⇒ **`can_fuse` 只允许「连续 ADD」**。MUL／SUB／DIV 一个都进不来。
这解释了扫描里 **MUL 与 DIV 的 ratio 恒为 1.000**。

两个上限叠加：`n_fuse <= 6`（硬编码）与 `n_fuse < cgc_fuse_max()-1`（env，默认 8）
⇒ 现状实际熔 **7 个**。要熔 9 个，两处都得改。

## 3. 读码发现二：但 kernel 早就支持 mul/div —— 不需要写新 kernel

`ggml-metal.metal:1279` `kernel_bin_fuse_impl`，融合循环按 `FC_OP` 展开：

```
FC_OP == 0: res += ...     (add)
FC_OP == 1: res -= ...     (sub)
FC_OP == 2: res *= ...     (mul)
FC_OP == 3: res /= ...     (div)
```

而 `ggml_metal_library_get_pipeline_bin(lib, op, n_fuse)` 是拿 `op` 去派生的
⇒ **把 host 端 `fops[]` 从「写死 ADD」改成「跟随当前 op 类型（限 ADD/SUB/MUL/DIV）」，
MUL 链就自动会熔，不用动 shader。**

⚠️ `FC_OP` 是**单一**值 ⇒ 只支持**同类型**连续链，混合 ADD+MUL 不行。这不影响本案（见 §4）。

## 4. 图 dump：链结构（决定性证据）

把 20671 个节点按「极大连续同类型段」切分：

| op | 节点数 | 链结构 | 平均链长 | 最长链 |
|---|---|---|---|---|
| **ADD** | 2160 | **351 孤立 + 201 条长 9** | 3.91 | **9** |
| MUL | 1415 | 1115 孤立 + **150 条长 2** | 1.12 | 2 |
| DIV | 201 | **201 条全孤立** | 1.00 | 1 |

⇒ **「9-ADD 链」确实存在**：201 条，每条正好 9 个。
昨天推断的「平均链长 2.85」是**被 351 个孤立 ADD 拉低的假象** —— 平均值在这里是错的统计量。

按 `ceil(len/cap)` 算 dispatch：

| cap | ADD dispatch | ratio |
|---|---|---|
| 2 | 1356 / 2160 | 0.628 |
| 3–4 | 954 | 0.442 |
| 5–8（**现状 7**） | 753 | **0.349** |
| ≥9 | 552 | **0.256** |

### 4.1 模型验证：整条曲线（端点精确吻合）

| 熔合深度 | 1（=不熔） | 2 | 3 | 4 | **7（现状，默认）** |
|---|---|---|---|---|---|
| **实测** ADD ratio | 1.000（`MAX=1`）／1.000（`FUSE_OFF=bin`） | 0.642 | 0.552 | 0.478 | **0.351 ／ 0.373** |
| **模型预测** | 1.000 | 0.628 | 0.442 | 0.442 | **0.349** |

端点（不熔 1.000、现状 0.349 vs 实测 0.351）**精确吻合**；中段 m3 偏高（0.552 vs 0.442）
落在 §4.2 的窗口噪音里。趋势单调 ✅

⇒ 链结构模型成立，可以用它推算 cap≥9 的收益。

### 4.1b 顺带：bin 融合**已实现**的价值 ≈ 13–21%（但这是 t/s，只在量级上可信）

| 对照 | t/s | Δ |
|---|---|---|
| `CGC_FUSE_OFF=bin`（bin 全关，norm 仍开） | 8.674 | |
| `CGC_FUSE_MAX=8`（现状） | 9.803 | **+13.0%** |
| `CGC_FUSE_MAX=1`（另一对照组） | 8.175 → 9.917 | **+21.3%** |

两次估计 13.0% / 21.3%，差 8 个百分点 ⇒ **落在 ±27% 单臂噪音里，只能当量级**。
对照 `offbin` 更干净（它是真·关闭 bin 融合；`MAX=1` 只是深度 1）。
**这个数字不该被引用于任何 t/s 表** —— 它只用来说明「融合不是没用，是已经用了」。

### 4.2 ⚠️ 但「计数指标确定」这个假设被测出是错的

两次 `CGC_FUSE_MAX=8`：ratio **0.351 vs 0.373**（差 6%），而 `nodes` 67 vs 97、`disp` 34 vs 25。
原因：census 只覆盖前 48–50 个 command buffer = **一步的 ~13.6%**（§EN-402），
**覆盖到哪些 cmd_buf 有随机性**。

反直觉的一点：**同一配置的 t/s 反而更稳**（9.917 vs 9.803，差 1.2%）。
⇒ 计数指标稳在**量级**（1.000 vs 0.36 是鸿沟），不稳在**小数点后第二位**。
**不要用 census 的绝对数外推，也不要指望它重复到 1%。**

## 5. L1 账单

换算比例：dump 的 ADD 2160 ↔ 真 decode 步 ADD 421（`CGC-GPUOPS` 实测）⇒ **5.13**。
⇒ dump 里 201 条 9-链 ≈ **39.2 条/步**（与 39 层吻合 ✅，交叉验证通过）。

单价用 K3 实测的 **0.0195%/dispatch/步**（另一独立估计 0.0228%，同量级，取保守值）。

| 项目 | 条/步 | 省 dispatch/步 | 收益 |
|---|---|---|---|
| ADD：cap 7 → 9（9-ADD 全熔） | 39.2 | 39.2 | **0.76%** |
| MUL：纳入 fops 白名单（只有 2-链） | 29.2 | 29.2 | **0.57%** |
| DIV | — | 0（全孤立） | **0%** |
| **合计** | | **68.4** | **1.33%** |

**1.33% < 3% 门槛 ⇒ L1 不做。**（要改两处代码 + 重建，换不到一个百分点的三分之一。）

### 5.1 顺带修正 K3 的 cluster-1

`K3_PRICE_MEASURED` 估 cluster-1（SUM_ROWS／CLAMP／DIV 各 39）为 2.28%。
但 **DIV 的 39 个全是孤立节点**，bin 融合在原理上救不了它
⇒ 那 2.28% 只有靠**垂直融合**（新 kernel，把三个不同 op 合成一个）才拿得到
⇒ 而那正是 G4 已经判「别写」的东西。**cluster-1 实际可及 ≈ 0。**

## 6. ★ 战略结论：L1 已死，孤立 op 才是主体，而那是 K5 的地盘

按 5.13 换算，真 decode 步里**不成链、融合永远救不了**的小 op：

| | 个/步 |
|---|---|
| 孤立 MUL | ~217 |
| 孤立 ADD | ~68 |
| 孤立 DIV | ~39 |
| **合计** | **~324** |

对比 L1 能救的 **68 个/步**。

而这 ~324 个正是 K5 那个 **45.6 µs 常数**的载体（孤立 MUL 单独就 217 × 45.6 µs ≈ **9.9 ms/步**）。

⇒ **融合是在「把链压短」，K5 是在「把每个节点的固定成本压低」。**
**图里能压的链已经压完（L1 = 1.33%），而每个节点的固定成本一点没动（K5 上界 30–38%）。**

## 7. L3 的分工提醒（本线不该做）

- `CGC-DECPROF` 里的 **`cb` 不是 command buffer，是 expert cache 的填池 IO**
  （`cb_layer = 0.46 ms + 0.695 ms × m`，边际 miss 由 ~1.6 GB/s 服务）。
- 按 09-20 operator 裁定 **`cb`／快取命中归线 I**，本线（线A）拥有 `wait`／`gap`／S1／S2。
- 线 I 今天（13:16）已裁决 **neighbour prefetch 对 decode「有效但太贵」**
  （命中率 +22.1% miss，但读入 1.98× 字节 ⇒ 净亏），F2 实测 null，**F2-R 设计已重写但未跑**。
- ⇒ **「把 cb 藏到 GPU 底下」这件事尚未被证明可行**，而 L3 的 18.59 t/s 完全建立在它之上。

本线在 L3 能碰的只有 `submit`（10.09 ms）与 `wait`（159.77 ms），而 **S2 已结案**。

## 8. 弱点（这份不能当结论的地方）

1. **图 dump 是 prefill 形状**（`CGC_GRPH_DBG` 只 fire 前 6 次）。用 ADD 总数比例 5.13
   换算到 decode 步，假设两种形状的链结构同构 —— 只被「39 条 9-链 ↔ 39 层」这一条交叉验证过。
2. **census 窗口随机性 ±6%**（§4.2），所以 ratio 只在量级上可信。
3. **单价 0.0195% 本身带 k=4.176 外推的误差**（§EN-402 已记：该因子对 per-op 覆盖不均）。
   L1 的 1.33% 因此可能是 0.9%–2.2%，**但上下界都低于门槛**。
4. **未实测 cap≥9**（要改 `n_fuse <= 6` + 重建）。0.76% 是模型推算，不是量测。
5. `n=1` 每档；m4 与第二条 m8 曾被 thermal MODERATE 拒（后补跑）。
6. 未验证「MUL 2-链满足 `can_fuse` 的其余条件」（same layout／same buffer／`f0 == f1->src[0]`）
   ⇒ 0.57% 是**上界**，可能更低。
