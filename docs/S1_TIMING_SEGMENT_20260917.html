S1：時序段落的偵察與量測，以及哨兵複驗

2026-09-17 00:40 · 引擎層 · 承接 S1_DISCRIMINATION_RESULT_20260917.html · 零改碼（只用既有 env 與 ARMS 覆蓋）

三句話：① 機制就在原始碼註解裡——兩臂的 slot 值來自兩個不同函式； ② repo 指定的閘門量 clamped_selected 兩臂皆 0 ⇒「夾成 slot 0 ⇒ 靜默換專家」被否掉； ③ 真正的量 consumed_changed = 192/390 (49%) ⇒ 種族條件被量到。 另外：-l20 這個「門檻外」哨兵已經不成立（與 09-15 記錄衝突）。

1. 兩臂的 slot 值來自兩個不同函式

函式誰吃形狀
llama_expert_cache_publish_slot_table()GPU table一次掃整層
llama_expert_cache_slot_table_safe()host leaf（＝參考檔的來源）逐專家查

llama-context.cpp:4245 的註解開頭就寫：「They are deliberately separate code paths — a bulk export and a per-lookup — so they can drift, and a drift is invisible in the logits oracle until it changes which slot a cold expert reads.」

它同時指名了兩者「were written to disagree on」的情形：非常駐專家在沒有保留 ZERO slot 的層上， publish 把它夾成 0（合法索引 ⇒ 指向另一個專家的權重，**靜默**）， 而 safe 回傳原始的 −1（大聲，id_oob）。並寫死閘門： 「clamped MUST be 0 … S1 is admissible only while this is 0」。

2. clamp 假說：在「被消費的子集」上被否掉

p25-slotgpu-dbg   : publishes=1599  clamped_selected=0  clamped_table=180687  changed_entries=0
p25-keepleaf-dbg  : publishes=1599  clamped_selected=0  clamped_table=180687  changed_entries=0

clamped_selected = 0 兩臂皆然 ⇒ 被讀到的 ids 沒有任何一個被夾成 slot 0。 （clamped_table = 180687 是整表量；repo 自己註明它「large in EVERY run carries no information」，那 16 行 CGC-SLOT-TABLE-CLAMP … EQUIVALENCE BROKEN 印的就是它，屬預期。） changed_entries = 0 也說明**同一輪內整表內容不移動**。

3. ★ 種族條件被量到：consumed_changed = 192

p25-slotgpu-churn : publishes=1599  clamped_selected=0  changed_entries=572
                    consumed_changed=192   consumed_unchanged_publishes=198      ⇒ 192/390 = 49%

這個計數器的定義（llama-context.cpp:4390-4415）：**每次 publish 時，比對「本步被消費的 每一個 id」的對映是否自上次 publish 起移動過**。註解原文：

「Premise B needs “does the mapping of an id the consumer actually READS move”, because only a consumed move can create a per-step host→GPU ordering requirement.」

⇒ 一半的 publish 事件中，消費者讀得到的 id 其對映已經移動。

旗標是純量測，不是擾動：它只讀快照比對；而且該臂的 answer_md5_set 與 純 p25-slotgpu 完全相同（f0acf7d2）⇒ 打開它不改變答案。

⇒ 這正好解釋 r10／r11 的簽名：消費者在**錯的時刻**讀到**舊對映** ⇒ 讀到**另一個專家的權重** ⇒ 值域相近、方向無關；router 逐位元相同（選擇是對的）；md5 **UNSTABLE**（取決於當下誰常駐）。

5. 操作紀律（本輪我自己踩到）

不要讓兩輪 decode_sweep 重疊。 本輪我讓 churn 與 sentinel 兩輪並行 ⇒ 兩者搶 8080 與 GPU ⇒ 其中一臂 n_rounds=0（rounds: []、answer_md5_set: []， 而 thermal_sweep 仍有 launch／teardown ⇒ 看起來像跑過了）。 判準：n_rounds ≥ 1 且 answer_md5_set 非空，否則該列無效。已單獨重跑。

6. 現在的位置與下一步

  • 問題已經從「哪一層」換成「哪一段時序」，而且第一段時序已經有了數字： consumed_changed / (consumed_changed + consumed_unchanged_publishes) = 49%。
  • 下一個要當自變數的是「消費點相對 publish 的位置」：目前只知道「消費得到的 id 有一半會動」， 還不知道**消費實際發生在 publish 之前還是之後**。能裁決的讀數是**同一 graph 內 per-layer 的 CGC-S1: TABLE-CHURN graph=N publishes=.. changed_entries=.. 行**（已有，churn 旗標會逐 graph 印） ——把某一層的「消費時看到的對映」與「該層最後一次 publish 的對映」對齊即可。
  • 錨固定為 p25-keepleaf（＝2d4e5099，可重複）。不要再用 -l20，也不要再加同形狀的分梯（原檔明講）。
