# K0 結果：把「每節點 30–90 µs」拆成 GPU 執行 vs 主機端

**日期**：2026-09-21 16:0x–16:2x，本線（`線A (ace)`）
**成本**：4 次 server 量測（各 ~1.5 分鐘）、**0 行 kernel、0 次重建**
**儀器**：`http_duo.py` ＋ `CGC_DECODE_PROFILE=1 / CGC_GPU_TIMING=1 / CGC_GPU_NODES=1 /
CGC_GPU_OPS=1 / CGC_GPU_NODES_MATRIX=1 / CGC_GPU_NODES_TRACE=1`（＋一次 `CGC_MM_DBG=1`）
**口徑**：本文所有數字都是 **server log 的 ms／µs，只做機制診斷**，**不得進 t/s 表**
（§EN-393：禁止跨儀器相乘）。

---

## 0. 結論先講

> **K1（改 dispatch 幾何）沒有對象。25 t/s 當場下修到 <3%，連 20 都難。**

判決依據是預先註冊的那一個（方案 §10.6 的下修條件）：

| 預註冊條件 | 實測 | 命中 |
|---|---|---|
| `threads ÷ 輸出元素` **≥ 1** ⇒ K1 無對象 ⇒ 下修到 <3% | **16–128**（每一個觀測到的 decode 形狀） | ✅ **命中** |
| 或 `uni` ≪ 10 µs ⇒ 下修 | 13 µs（per-buffer 固定）／11–25 µs（邊際） | ❌ 未命中 |

⇒ **下修條件成立。這是負結果，但它是 K0 存在的理由**：半天、0 行 kernel，就把一個
4–6 週專案從「勝率不知道」變成「<3%」。

## 2. 判決證據 A：GPU 真的在執行，不是主機端空轉

`CGC-GPUTIME`（13 個取樣步，step 80–128，中位數）：

| 指標 | 值 | 相對 `wait` |
|---|---|---|
| `wait`（CPU spin） | 111.6 ms | 100% |
| `gpu_union`（GPU 跨度） | 102.0 ms | **92%** |
| `gpu_busy_sum`（各 buffer 時長和） | 130.7 ms | **117%** |
| `gap` | 37.3 ms | 34% |

- **GPU 跨度吃掉 92% 的步時** ⇒ 主機端沒有在空轉等 GPU ⇒ **K4（主機側）不是主線**。
- `busy_sum/union = 1.17` ⇒ 平均有 1.17 個 command buffer 同時在飛（有重疊，不是完全串行）。

## 4. 判決證據 C：`uni` 正控制**沒有開火**（重要的方法論發現）

`CGC_GPU_OPS` 的 `uni` 欄設計成「只含該 op 的 buffer 的精確 µs/node」。實測 24 個 op 裡
**23 個是 `-1.000`**（從沒出現在單一 op 的 buffer 裡），唯一有值的 `RESHAPE` 是
**826 µs/node**——乘上它的 598 個 node 是 494 秒，而該步總共只有 112.84 ms ⇒ **物理上不可能**。

原因：buffer 組成幾乎是固定的（直方圖：6-node 佔 26,187 個、64-node 佔 5,160 個），
真實 op 永遠跟別人共用 buffer。**per-kind 最小二乘也因此奇異（collinear）**。

⇒ **`uni` 今天不可用。** 方案 §2 的「K0 產出表」那一欄不能靠它填；
本文改用「`wcntw` 模型值」並明確標為**模型，不是量測**。

`wcntw` 模型值（step 605，`total=112.84 ms`，單位 µs/node）：

| op | nd | wcntw% | 模型 µs/node | 備註 |
|---|---|---|---|---|
| MUL_MAT | 426 | 15.1% | 40.0 | ub 獨立，可信 |
| ADD | 421 | 13.8% | 36.9 | |
| MUL | 278 | 11.0% | 44.5 | |
| RMS_NORM | 130 | 7.5% | **65.2** | |
| UNARY | 169 | 7.6% | 50.8 | |
| CPY | 210 | 7.1% | 38.2 | |
| GET_ROWS | 159 | 5.0% | 35.7 | |
| MUL_MAT_ID | 117 | 3.6% | 35.1 | ⚠ 與 GLU/SUM_ROWS/CLAMP/DIV **同 ub=55.85** ⇒ 不可分離 |
| L2_NORM | 60 | 3.5% | 65.0 | |

⚠️ 五個 op 的 `ub` 完全相同（55.85 ms / 49.5%）⇒ 它們永遠共用同一批 buffer ⇒
**35.1 這個數字是「按 node 數分」的產物，不是各自的成本**。

## 5. 判決證據 D：**`threads ÷ 輸出元素` = 16–128**（這條判死了 K1）

### 5.1 decode 期的真實形狀（`CGC_MM_DBG`，20,019 行）

`ne11` 分布：`1 →1193`、`2 →1994`、**`4 →12832`**、`14 →800`、`489/512 →3200`（後兩者是 prefill）。

⇒ **decode 的主導形狀是 `ne11=4`，不是 1** —— 也就是 **MTP verify 的 M=4** 才是交付形狀，
不是純 T=1。這件事本身值得記（它決定了哪條 kernel 路徑在跑）。

decode 期（ne11=4）的 mul_mat 形狀與每步次數：

| ne00(K) | ne01(N) | t0 | 次/步 |
|---|---|---|---|
| 2048 | 512 | iq4_xs | 50 |
| 2048 | 32 | f32 | 30 |
| 2048 | 8192 | iq4_xs | 20 |
| 4096 | 2048 | iq4_xs | 20 |
| 2048 | 256 | f32 | 20 |
| 2048 | 1 | f32 | 20 |
| 512 | 2048 | iq4_xs | 20 |
| 2048 | 4096 | iq4_xs | 15 |

### 5.2 grid 怎麼算（讀碼，不是猜）

- dispatch：`ggml-metal-ops.cpp:2763 / 2765`
  - quantized：`threadgroups = ceil(ne01/(nr0·nsg)) × ceil(ne11/nr1)`，`threads/TG = 32·nsg`
  - f32：`threadgroups = ceil(ne01/nr0) × ceil(ne11/nr1)`，`threads/TG = 32·nsg`
- `nr1 = 1` 恆成立（`ggml-metal-device.cpp:848`）
- `nr0/nsg` 來自 `ggml-metal-device.cpp:858+` 與 `ggml-metal-impl.h`：
  **iq4_xs → nr0=2, nsg=2**（`N_R0_IQ4_XS 2` / `N_SG_IQ4_XS 2`）；
  f32 且 `ne00>=32` → `nsg = min(4, ceil(ne00/128))`, `nr0 = 2`

⇒ **總 threads = ceil(ne01/(nr0·nsg)) × ne11 × 32·nsg**
⇒ **`threads ÷ 輸出元素 = 32·nsg / (nr0·nsg) = 32/nr0`**（量化）／`32·nsg/nr0`（f32）

| 形狀 (K,N,M) | t0 | 總 threads | 輸出元素 | **threads/輸出元素** |
|---|---|---|---|---|
| 2048×512×4 | iq4_xs | 32,768 | 2,048 | **16** |
| 2048×32×4 | f32 | 8,192 | 128 | **64** |
| 2048×8192×4 | iq4_xs | 524,288 | 32,768 | **16** |
| 4096×2048×4 | iq4_xs | 131,072 | 8,192 | **16** |
| 2048×256×4 | f32 | 65,536 | 1,024 | **64** |
| 2048×1×4 | f32 | 512 | 4 | **128** |
| 512×2048×4 | iq4_xs | 131,072 | 8,192 | **16** |
| 2048×4096×4 | iq4_xs | 262,144 | 16,384 | **16** |

### 5.3 這代表什麼

**每一個輸出元素都已經有 16–128 條 thread 在做它**——那 32 條 lane 是在切 **K（歸約軸）**。
輸出軸（`ne01`）已經被完全切開：每一列有自己的 simdgroup。

⇒ 要再加 thread，只能去切 K ⇒ **正是 §EN-391 的永久禁區（`nxpsg`/`N_SIMDWIDTH`/K 分組）**。
⇒ **`nsg` 加大也不會增加總 thread 數**（它只是把更多列塞進同一個 threadgroup）。

**合成的 13.6× 為什麼不適用**：那個探針是純 streaming payload，**沒有歸約軸**。
真實 GEMV 的 grid 已經隨輸出大小長到 524,288 條 thread——§EN-391 使用者的提醒 ① 完全成真。

## 6. 交叉檢查：大 op 已經貼著屋頂

既讀數（§EN-380）：`MUL_MAT_ID` 跑在峰值 **50–61%**、`MUL_MAT` **28%**。
若峰值取 124 GB/s、解量化屋頂取 45 GB/s：

- `MUL_MAT` 28% × 124 = 34.7 GB/s ≈ **77% 的解量化屋頂**
- `MUL_MAT_ID` 50–61% × 124 = 62–76 GB/s（≥ 屋頂）

⇒ 大矩陣 op **沒有 occupancy 問題，它們貼著可達屋頂**；
小 op 是固定成本主導（13 µs/buffer），而它們**小到無法再並行**（`ne01=1` 只有 4 個輸出元素）。

## 8. 本文的弱點（不得事後補）

1. **grid 是讀碼推出來的，不是量出來的。** 公式與常數都有行號，但要把它變成實測，
   需要一支對真實形狀的 microbench（不做也足以判決：公式是同 build 的事實）。
2. **`uni` 不可用** ⇒ §5 的 µs/node 是 `wcntw` 模型值，其中有 5 個 op 不可分離。
3. **server 口徑**：本文全部數字不得進 t/s 表。所有 t/s 結論要回到 llama-bench。
4. **n=1 rep**：BITIDENT 的 4–5% 是「四個指標同號、儀器重現性 0.2%」的單次結果，
   未達配對設計的標準；要用 `paired_ab.py` 才算數。
