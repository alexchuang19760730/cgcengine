判定規則

每一格只被兩條前提決定。CGC_POOL_MAX_TOKENS（cap）不是池子的參數 —— llama-context.cpp 在 L4 pool 啟動時把 n_batch clamp 成它，所以 cap 就是 prefill 的 chunk 大小。

#前提算式不滿足的後果
P1槽位容量 cap × top_k ≤ usable_slots
slot 0 是保留的 ZERO slot，故 usable = min_layer_slots − 1		 union 塞不進該層的格數 → 走到 gather/wide 路徑（本引擎該路徑不可用）
P2存活性 cap ≥ n_keep_tail + 1
n_keep_tail = (n_rs_seq > 0) ? n_rs_seq+1 : 0
n_rs_seq = draft.n_max（MTP/EAGLE3/DFLASH/DSPARK 時）		 載入即 abort：GGML_ASSERT(n_ubatch > n_keep_tail)

槽位數怎麼算（與 loader 同一條式子）

per_slot_layer[il] = Σ over 4 kinds ( row_size(type, ne[0]) × ne[1] )      # 該層每顆 expert 的位元組
per_slot          = max over DECODER layers (il < max_layer − n_nextn)      # MTP/NextN 層不計
capacity          = clamp( pool_bytes / (max_layer × per_slot), 8, 256 )    # llama-model-loader.cpp:1145
min_layer_slots   = min over layers of cgc_layer_cap(l, capacity)          # LAYER_CAPS 可覆寫（後者勝）
usable_slots      = min_layer_slots − 1
cap_max           = usable_slots // top_k

MTP 層刻意不計入 per_slot：把 head 的位元組算進 trunk， 會讓 trunk 的池子幾何取決於 head 剛好怎麼存（實測 F16 head 把 trunk 從 118 格打到 33 格， 並產生 585 次 buffer is nil）。

三個判定

判定條件這一格可以拿去幹嘛
USABLE 可用 cap_max ≥ 8（build 預設 cap） 可以和別格用同一個 cap 跑。跨格比較因此是「只變池子」的乾淨實驗， pool-layout 不變性（固定 cap 下 bit-identical）此刻成立。
PARTITION-REF
只能當 partition 敏感度參考		 floor ≤ cap_max < 8 跑得起來，但只能在那個較小的 cap 上跑。拿它去對 cap=8 的參考比， 量到的是 prefill step partition 的差異，不是池子佈局。 它的 logits 只對「partition 有多敏感」有意義。
UNUSABLE 不可用 cap_max < floor 沒有任何 cap 能同時滿足 P1 與 P2：大到塞得進格數的違反存活性， 小到活得了的塞不進。pool path 直接停擺。

floor = MTP ON 時 5（n_rs_seq = --spec-draft-n-max = 3）， MTP OFF 時 1（無 spec type → n_rs_seq = 0 → n_keep_tail = 0，assert 恆真）。

操作準則

  1. 開機前先看這張表。 ⚠️ 與 ❌ 的格子不該進掃描；尤其不要讓它們和 ✅ 的格子放在同一張對比表的同一句話裡。
  2. 掃 pool 時 cap 必須固定。 只有 ✅ 的格子保證做得到；⚠️ 的格子天生做不到。
  3. 換模型就重跑一次。 這張表對 per_slot 很敏感（+21% 就讓 Ornith 掉一格），而 per_slot 由量化型別與 n_ff_exp 決定，不是「差不多 35B」就能沿用。
  4. 引擎改到池子分配就重跑 --validate。 那筆 09-11 的過期記錄就是這個機制要抓的東西。

第三個檢查：探測結果必須對得上算式（2026-09-14 補）

--pool-cap auto 的探測是整個 sweep 唯一決定 cap 的地方，而它過去只相信自己快取的 cap_probe_*.json。所以現在每一筆探測記錄在被重用的那一刻都要過一次對帳： 實測 slots vs 算式預測 slots。吻合才准用；不吻合就拒絕快取、重新探測，而且分成兩種說法：

判定條件動作
MATCH實測 = 預測重用（記錄裡附 verified_slots；若無 provenance 會註明它靠的是「數字吻合」）
STALE_RECORD不吻合，且記錄的 provenance 與現樹不符 / 根本沒有 provenance拒絕快取並重探，並指出是哪一半動了：pool-geometry 程式碼、權重、或 launch env（layer_caps/mtp/spec_n_max）
PREDICTOR_STALE不吻合，但 provenance 完全符合現樹（或就是剛剛探的）拒跑整個 sweep：程式碼沒動，那就是 pool_feasibility.py 的算式不再描述 loader —— 而它是每一個可行性判定的依據

另外，探測記錄從現在起自帶 provenance（pool-geometry 三個檔案的 digest + 最近 commit、權重 identity、 layer caps、MTP、spec-n-max、extra_env），並把對帳結果寫進 reconciled 欄位。 沒有 provenance 的舊記錄不會被靜默重用 —— 它只能靠「數字吻合」被接受，而且會當場講出來。

[cap-probe] iq3 pool8GB cache REFUSED
  CAP-PROBE MISMATCH (STALE_RECORD): measured 106 slots vs predicted 143 for iq3 pool8GB.
  Cause: the record carries NO provenance, so nothing ties it to this tree (records written
  before 2026-09-14 have none).
  Re-probing instead of reusing it: the cap must come from a geometry this engine actually has.
[cap-probe] iq3 pool8GB trying cap=8 (union <= 64)
[cap-probe] geometry reconciled: measured 143 slots = predicted 143

--allow-geometry-drift 是唯一的逃生口：它只在「探測違背算式」那條路上生效，量測照跑， 但衝突會被蓋進記錄裡。

拒絕的形狀

[iq3_pool2gb] feasibility UNUSABLE  iq3@2GiB cap=8
  cap_max 4 < floor 5: P1 and P2 cannot both hold at any cap (34 usable slots, n_rs_seq=3)
  REFUSING to launch: this cell cannot produce a number comparable with a reference-cap cell.

摘要表：
iq3_pool2gb  -- UNUSABLE at launch: cap_max=4 < cap 8 (usable slots 34, floor 5)
                -> REFUSED, not a pool result; --allow-partition-ref to measure it as partition sensitivity

關鍵性質：拒絕不是結果。 被拒的格子不會寫進 knifeedge_*.json（沿用 low_memory 的規則）。若寫了，之後的 sweep 會把它當「已完成的量測」而 SKIP， 於是表上會出現一個從來沒被量過的 config —— 這正是這條規則存在的理由。 拒絕同時發生在任何遠端程序被殺之前，所以一格不可比的格子不會先弄死別人的 server 再放棄。

覆蓋範圍與自測釘住的東西

  • 覆蓋路徑：run_combo（一般 pool sweep）與 cap_invariance_dump（每個 cap 都 launch 一次的那條）， 各自在 kill_servers() 之前判定。
  • --allow-partition-ref 只放行 PARTITION-REF，--allow-unusable 只放行 UNUSABLE —— 用錯的旗子不開錯的門（自測有這一項）。
  • GGUF 讀不到時警告並照跑：預測器不該成為跑不動的理由。
  • MTP 開關會改變地板（n_rs_seq=3 → floor 5；MTP off → floor 1），自測用合成 layer caps 把三種判定都走一遍真路徑，不依賴任何 GGUF。
  • 探測對帳也在覆蓋範圍內（自測第 6 節）：MATCH / STALE_RECORD / PREDICTOR_STALE / NO_EVIDENCE 四種判定，以及讓 provenance 動起來的三種方式 （pool-geometry 程式碼、權重、launch env）各自有一項。

限制與誠實標註

  • 這是算術預測，不是量測。 它複製 loader 的式子（compute_l4_pool_capacity）與 cgc_layer_cap 的 LAYER_CAPS 解析；若引擎改了分配方式， 預測會先錯、--validate 才會發現。目前對得上 5/6 筆實測 + 3 筆當日 log。
  • per_slot 取 decoder 層的最大值。 這是刻意的（見上）， 但它意味著 MTP head 自己的槽位不在這條式子裡 —— head 的槽位走 LAYER_CAPS。
  • P1 用的是 min_layer_slots，即最緊的那一層。 取平均或 n_slots 會高估空間，可能核准一個仍會溢出的 cap。
  • 「USABLE」只保證這一格能跑，不保證快。 速度由命中率與 I/O 決定； cap 曲線（見白皮書）顯示同一池子內 cap 越小越快，而 cap 是被 P1 推導出來的。
  • Qwen3.6 UD-IQ4_XS 不在表上：檔案不在這個 checkout。
  • top_k 取自 GGUF 的 expert_used_count（此處皆 8）。 不同模型若 top_k 不同，同一格數會給出不同的 cap_max。
