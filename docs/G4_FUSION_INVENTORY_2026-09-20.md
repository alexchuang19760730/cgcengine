## 3. ★ 第一刀能拿多少：三段，只有中段是未知數

### (1) 頻寬那一段：**≈ 1.0 ms/步**（可算，不是估的）

設 activation 為 f16（2 bytes；**這是假設，未驗證**）：`[2048,8]` = 32 KB/張量。

- 未融合：9 個 ADD ×（讀 2 張 ＋ 寫 1 張）× 32 KB = **864 KB/層**
- 融合後（9 輸入 → 1 輸出）：9 讀 ＋ 1 寫 = **320 KB/層**
- 省 **544 KB/層 × 41 = 22.3 MB/步** ÷ **22.3 GB/s**（G4 量測卡上的等效頻寬）= **1.00 ms/步**

⇒ **資料搬運只能解釋 ~1 ms。它解釋不了下面那個 19 ms。**

### (2) 發派那一段：**0 … 19.00 ms/步**（未量測，這是全部的風險）

若歸因到的成本與節點數成正比、且融合後的 kernel 仍要 1 次 launch：

```
可移除 = (328 / 421) × 24.39 ms = 19.00 ms/步 = 165.00 ms 的 11.5%
```

`uni = -1.000`（見 §0）⇒ **每 kernel 的發派成本今天沒有數字**。
若它是 0 ⇒ 拿到 19.00 ms；若它等於現在每節點的歸因成本（57.9 µs = 24.39/421）⇒ 拿到 **0**。
**真實值落在這個區間裡，而且區間的兩端都還沒有人去量。**

### (3) 三群一起：上界 14.1%

| 群組 | 上界（線性外推） | 佔 165.00 ms |
|---|---:|---:|
| ADD 鏈 | 19.00 ms | **11.5%** |
| GLU 對 | (41/78) × 4.38 = 2.30 ms | 1.4% |
| MUL 對 | (30/278) × 18.55 = 2.00 ms | 1.2% |
| **合計** | **23.30 ms** | **14.1%** |

**判讀（這一句是本輪最重要的結論）**：

- **ADD 鏈單獨的上界 11.5% ＜ G4 的門檻 12.8%**（`union ≤ 38 × mean_len`）⇒
  **第一刀只做 ADD 鏈，即使在上界也過不了 G4。**
- **三群一起的上界 14.1% ＞ 12.8%** ⇒ 「過得了」這件事**只有把所有找到的群組做完才成立，
  而且只是在上界成立**。
- 兩個數字都**不是預測**。它們是「若且唯若每一個被移除的節點的歸因成本都是純發派成本」時的算術。

## 4. ★ 更正 `§EN-327`：「三個同值 op」不是融合候選，是歸因產物

`§EN-327` 記載 `k_conv`／`z-`／`gdn_out` 在 125 段**逐位元同值 51.98 ms**，原讀法是
「同工作權重 ⇒ 一族同尺寸 op 的簽名」，並把那三個 op 列為**第一個融合候選**。

**這個讀法要收回。** dump 給的逐 op 明細（每份主圖）：

| kind | 節點數 | op 組成 |
|---|---:|---|
| `k_conv` | **60** | `VIEW 30` ＋ `L2_NORM 30` |
| `z-` | **60** | `MUL_MAT 30` ＋ `RESHAPE 30` |
| `gdn_out` | **60** | `GATED_DELTA_NET 30` ＋ `VIEW 30` |

**三者節點數逐項相同（60 = 30+30）**，而儀器的份額是 `buffer 時長 × 節點佔比`
⇒ **落在同一批 buffer 裡、節點向量相同的 kind，必然得到同一個數字。**
`k_conv` 是 L2_NORM、`z-` 是 MUL_MAT、`gdn_out` 是 GATED_DELTA_NET —— **它們既不同 op、
也不同尺寸，不能互相融合。**「同值」是**歸因的簽名**，不是**可融合的簽名**。

（同一條也順手更正上一則的措辭：`node` 12.3% **不是**「未融合 elementwise」——
它每份主圖 350 個節點裡有 `MUL_MAT 130` ＋ `GET_ROWS 90` = 220 個是取權重／查表，
只有 `ADD 30` ＋ `UNARY 30` ＋ `MUL 60` = 120 個是 elementwise ⇒ **可對付的那一半約 34%。**）

## 5. G2 的約束（動工前就該知道，它決定怎麼寫）

融合 9 個 ADD 會改變浮點加法順序 ⇒ **G2（逐位元閘門）會否決**，除非：

> **融合後的 kernel 必須以與鏈完全相同的順序做加法**（`cur = cur + x_i`，i 依原順序），
> 而不是樹狀歸約、也不是先累加再正規化。同順序 ⇒ 同位元 ⇒ 結果逐位元相同。

這一條把設計空間縮成一句話：**「一個 kernel，9 個輸入，串序累加，1 個輸出」**。
它也順便說明為什麼「換成 `ggml_sum`／樹狀 reduce」這條看似更簡單的路**過不了 G2**。
