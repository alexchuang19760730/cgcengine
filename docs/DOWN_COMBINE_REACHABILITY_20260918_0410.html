down-combine 的可達性：為什麼旗艦模型吃不到它，而另一個模型吃得到

2026-09-18 03:4x–04:1x · flashkv-devserver（llama.cpp CGC fork，引擎層線）· profile prefill250 · pool 8 GiB
受試：Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf（旗艦，41 層）與 Ornith-1.5-35B-A3B-Abliterated-MTPv2-APEX-I-Compact-v2D-lite.gguf（對照，41 層）
D5 PASS ① 只有 Q3_K ② 不是開閘門，是寫 kernel ③ 節點已證，A/B 已重做

一句話：那條「一個 kernel 取代 8 個 down GEMV ＋ 7 個 add」的融合路徑是活的（節點確實 進圖，本文件用新儀器直接印出來了），但它在旗艦模型上只覆蓋 41 層裡的 1 層，而那一層是 MTP nextn head、不在熱路徑上。要真的吃到它，得寫 IQ3_S／IQ2_S／IQ4_XS 的 Metal kernel， 而且還要讓它支援 n_tokens > 1（MTP-on 的 verify 形狀）—— 只改型別檢查是不夠的。

而它值不值得寫？本文件用樹上第二個模型（ffn_down_exps 是 Q3_K ×30）量到了 +25%（覆蓋 trunk 的 75%、兩臂同熱態）。所以「要不要動手」現在有一把尺了。

§0 摘要：三個問題、三個答案

問答證據
① kernel 支援哪些型別 只有 Q3_K，而且名字是硬寫死的 ggml-metal.metal:11744（唯一 impl）、:11886（唯一 host_name）、 ggml-metal-device.cpp:1309（硬字串）
② 把閘門開到 IQ3_S／IQ2_S／IQ4_XS 那不是「開閘門」：要寫新 kernel（IQ 系列還要 lookup table）， 而且還要解 n_tokens == 1 §1 ＋ §4
③ 交錯 A/B 並確認融合節點出現 節點已證出現（CGC-DCFUSED）；A/B 第一版因熱態無效， 正確的受試是另一個模型 ⇒ +25% §3 ＋ §5 ＋ §6

§1 ① 的答案：kernel 只有 Q3_K，而且是硬寫死的

三個獨立的證據，任一個就足以定案：

位置逐字意義
ggml-metal.metal:11744 void kernel_mul_mv_id_down_combine_q3_K_impl(...) 只有一個 impl，名字帶型別
ggml-metal.metal:11886-11887 [[host_name("kernel_mul_mv_id_down_combine_q3_K_f32")]] 只有一個 host_name ⇒ library 裡只有這一個變體
ggml-metal-device.cpp:1309 snprintf(base, 256, "kernel_mul_mv_id_down_combine_q3_K_f32"); pipeline 名字是硬寫死的，getter 沒有型別分支

而且 getter 的其他部分也是 Q3_K 專屬的：

  • :1291-1292 int nsg = N_SG_Q3_K; int nr0 = N_R0_Q3_K;（Q3_K 的 tile 常數）
  • :1307 size_t smem = 0;，註解逐字：「Q3_K does not need lookup table in threadgroup memory」 ⇒ IQ 系列需要 lookup table（smem != 0）， dequant 邏輯也不同。

消費端還有第四個鎖：ggml-metal-ops.cpp:4821 是硬斷言，不是 fallback：

GGML_ASSERT(op->src[0]->type == GGML_TYPE_Q3_K);

⇒ 所以「把閘門開到 IQ3_S／IQ2_S／IQ4_XS」不是改一行型別檢查。 它是實作一個新的 Metal kernel：IQ3_S／IQ2_S／IQ4_XS 各自的 dequant ＋ 8 專家的 GEMV ＋ weighted combine，加上 pipeline getter 的型別分支，再加上把那個 GGML_ASSERT 改成 fallback。

§2 ② 的前半：旗艦模型上只有 1/41 層是 Q3_K

新儀器 CGC_DOWN_COMBINE_AUDIT=1 在建圖時逐層印出閘門六條條件的實際取值 （CGC-DCAUDIT il=.. flag=.. n_tokens=.. down_type=.. has_scale=.. has_bias=.. weight_before_ffn=.. ids=.. => fuse=..）。旗艦模型，1189 行審計、86 個圖：

圖層數型別fuse=1
trunk40（il 0–39） iq3_s ×37、iq4_xs ×30
MTP nextn head1（il=40）q3_K31
上：旗艦模型只有 il=40（MTP nextn head）是 Q3_K。下：對照模型有 30 層是 Q3_K。

這也修正了上一輪用 GGUF header 推的結論。當時讀到 「IQ3_S ×37 ＋ IQ4_XS ×3 ＋ Q3_K ×1」—— 數字對，但誰是 Q3_K 那一層是猜的。 現在有直接證據：是 MTP nextn head（il=40），不是 trunk 的某一層。 trunk 的 1120 行審計裡，down_type == q3_K 的有 0 行。

§3 ③ 的一半：融合節點確實出現（而且只在 il=40）

CGC-GRPH 與 CGC-GPUOPS 看不到它 —— 那兩者都在分段路徑內 （ggml-backend.cpp:2055 在同一個 hook_seg scope），而 MTP nextn head 的圖 不走那條路。所以在建圖處直接印節點本身：

CGC-DCFUSED il=40 op=31(MUL_MAT_ID_DOWN_COMBINE) name=ffn_moe_out_down_combine-40 \
            out_ne=[2048,1,1] n_tokens=1 down_type=q3_K swiglu_src=101(GLU)

7 行，與同一 log 的 CGC-DCAUDIT … => fuse=1 的 7 行完全一致。

方法論：把「閘門為真」與「節點存在」當成兩個不同的宣稱。 audit 說前者（六條條件的取值），DCFUSED 說後者（節點本身：op、名字、形狀、來源 op）。 而 ggml_build_forward_expand(gf, moe_out) 就在那一行之後，所以節點必然進圖。

§4 旗艦模型的 trunk 為什麼永遠不走：兩個獨立的障礙

障礙條件（llama-graph.cpp:2682-2687）生產上的實際取值
型別down_exps->type == GGML_TYPE_Q3_K trunk 是 iq3_s／iq4_xs ⇒ 0/1120 行符合
形狀n_tokens == 1 MTP-on 的 trunk 是 verify 圖（ntok=2/4）；trunk 行裡只有 560/1120 是 ntok==1

⇒ 即使寫了 IQ3_S kernel，MTP-on 下 trunk 的 verify 形狀仍然走不了。 兩個都要解，而第二個（讓 kernel 支援多 token）不是「開閘門」。

§6 正確的受試：樹上第二個模型 ⇒ +25%

第二個模型的 ffn_down_exps 是 Q3_K ×30：

models/gguf/Ornith-1.5-35B-A3B-Abliterated-MTPv2-APEX-I-Compact-v2D-lite.gguf
  down_exps types: {'Q3_K': 30, 'Q4_K': 10, 'Q8_0': 1}   (41 MoE layers)

審計（CGC_SERVER_MTP=0 ⇒ 純 decode，ntok==1）：

  • 30 層（il 5–34）全部 q3_K，10 層（il 0–4、35–39）是 q4_K
  • 若 flag=1：ntok==1 且 type==q3_K 的行數 = 390（30 層 × 13 個 decode 圖）
  • 實測 CGC-DCFUSED = 450（30 層 × 15 圖）⇒ 融合確實生效

ABBA：--arms on,ctl（正序）與 --arms ctl,on（反序），各 --rounds 2：

⚠️ 正序那一組不可引用。on 全程 NOMINAL 而 ctl 有一半是 MODERATE ⇒ AB = 1.0028 是熱態補償的產物（ctl 的 MODERATE round 把它的中位數壓低了）， 不是融合的效果。因此 ABBA 的 M = √(AB×BA) = 1.1196 也不可引用。

★ 反序那一組可用：兩臂都全程 MODERATE（同熱態）⇒ BA = 1.2500。

⇒ 融合的淨效果：+25%（在 30/40 層的覆蓋下）。

為什麼這不是熱態：on 跑在 ctl 之後（熱態只會更差、不會更好）， 而它的 min/max 是 19.56/19.75（±0.5%） —— 比 ctl 的 12.43/19.01（±42%）窄得多。順序效應的方向與結論相反。

池統計在四臂中完全相同（hit 93.3、io 2981.1–2981.5 MB、 file_reads 22668–22671）⇒ 差異不在池。

§7 結論

  1. 收益量級已量到：覆蓋 trunk 的 75%（30/40 層）時，融合的淨效果是 +25%。 它把「值不值得為 IQ3_S 寫 kernel」從猜測變成有一把尺。
  2. 機制：融合路徑是活的、可達的、節點確實被建立（CGC-DCFUSED）， 但在旗艦模型上只覆蓋 1/41 層（MTP nextn head），而那不是熱路徑。
  3. 要真的在旗艦模型上吃到它，要解兩件事：寫 IQ3_S／IQ2_S／IQ4_XS 的 kernel （IQ 系列還要 lookup table），以及讓它支援 n_tokens > 1 （MTP-on 的 verify）。只做前者不足。
  4. 旗艦模型的 A/B 測不出（覆蓋 1/41），而第二個模型可以（覆蓋 30/41） ⇒ 以後這類判據要用對的受試。
  5. 本輪沒有動 kernel：依專案已付兩次學費的「沒有判準就不要實作」 （CGC_MMV_FUSE、離線最小平方），先量出收益量級再決定 —— 現在量到了。

§9 誠實邊界（本文件不主張什麼）

  • 本輪沒有實作任何 kernel。+25% 是在另一個模型（Ornith，Q3_K ×30）上量的， 用的是既有的 Q3_K kernel。它不能直接外推到旗艦模型：後者要的是 IQ3_S／IQ4_XS 的 kernel，那是未寫的，而 IQ 系列的 dequant 成本與 Q3_K 不同 （還要 lookup table）。⇒ 可引用的述句是「同一個融合在覆蓋 3/4 的 trunk 時值 +25% 量級」， 不是「旗艦模型會快 25%」。
  • 反序那一組只有一個配對（BA），而正序那一組因熱態不可用 ⇒ M = √(AB×BA) 不可引用。要更強的結論需要更多組同熱態的配對。
  • 兩臂是先後跑的（不是逐 round 交錯）⇒ 順序效應沒有被完全分離。 緩解：on 跑在 ctl 之後（熱態只會更差）， 而它反而快了 25% ⇒ 順序效應的方向與結論相反。
  • CGC-DCFUSED 證明節點進圖，不證明 kernel 真的執行。 它的旁證是 ggml-metal-ops.cpp:4821 的斷言（型別不符會 abort，而 log 沒有 abort） —— 那是推論。而 +25% 同時是「kernel 真的在做事」的證據： 若它只是讓圖變小而不執行，不會有正向的 t/s。
  • --rounds 0 在 decode_sweep.py 下 n_rounds=0 ⇒ t/s 欄位全為 0.0（探測時踩到）。
  • 本輪的量測全程在 HEAVY／MODERATE 之間**，沒有任何一組達到生產的 NOMINAL 穩定態。 ⇒ 絕對 t/s 不可與生產的 12.0–12.9 比較；可引用的只有同熱態的臂間比值。
