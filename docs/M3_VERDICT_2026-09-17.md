# M3 判定：它與 D3 的 S2／S3 是同一個目標，而那一條已部分被否證（2026-09-17）

**里程碑**：M3 — decode 的 compute 削減（roadmap 標記 **★ 最可能失敗**）
**離開條件（原文，兩個分支）**：成功 ⇒ decode（**MTP off**）**≥ 15 t/s** 且 M1/M2 = 100%；
失敗 ⇒ 寫一份「找不到路」的結論，**附上 M0 的剖面表當證據**。
**本文件**：跑完今天的兩份剖面之後的**判決**。它判的是「15 t/s 從哪裡來」，不是「實作了什麼」。
**前置**：`docs/M3_PRECEDENCE_2026-09-17.md`（三個工作項的判準與否證者，本文件不複述）。

---

## 0. 一句判決

**M3 的離開條件（15 t/s）與 `REMAP_ROUNDTRIP_REMOVAL_PLAN` 的 S2／S3 是同一件事**，
而 S1（位元身分已達成）**結構上不更快**、S3 的前提 B 已被 47.5% 打掉
⇒ **M3 今天沒有可立即執行的路徑：它的兩條路一條與被否證的階梯重合、一條被 M1 阻塞。**
本文件用今天兩個剖面的數字把「重合」這件事量化出來，並指明唯一能裁決它的量測。

## 1. 先把兩個目標分開：這是本判決的關鍵區分

| | 數字 | 需要的加速 |
|---|---|---|
| **M3 的目標**（roadmap 原文） | `100 ms/token → 40 ms/token` | **2.32×**（用今天的 92.8 ms 起算） |
| **M3 的離開條件** | decode（MTP off）**≥ 15 t/s** | **1.39×** |
| **今天的位置** | **10.78 t/s** ＝ 92.8 ms/token（MTP off 的 llama-bench 平台值） | — |

**離開條件比目標鬆得多（1.39× vs 2.32×）。** 這個區分很重要，因為下面會看到：
**1.39× 落在「去序列化」的上界附近**，而 2.32× 完全不在 —— 所以「M3 成功」與「M3 達標」
是兩個不同的問題，而離開條件那一個是**擦邊可及**的。

## 3. 判決 A：host 側**不是**槓桿（這一條對熱不敏感）

`CGC-PHASE` 把每步拆成 build（建圖）／alloc（配置）／inputs（輸入拷貝）／compute（執行）／fill_wait（等填槽）：

| 相位 | 每步 | 佔比 | 它排除了什麼 |
|---|---|---|---|
| `build` | 0.023 ms | 0.02% | **圖重建**不是成本 ⇒「減少 graph rebuild」這條路沒有量 |
| `alloc` | 0.037 ms | 0.03% | 排程器配置不是成本 |
| `inputs` | 0.026 ms | 0.02% | 輸入拷貝不是成本 |
| `compute` | 118.459 ms | **99.9%** | **GPU 執行就是全部** |
| `fill_wait` | **0.000 ms** | 0% | **池填充完全不在關鍵路徑**（快路徑）|

**三者的差距是三個數量級**（0.086 ms vs 118.5 ms）⇒ **熱不可能改變這個結論**：
降頻只會把 `compute` 放大，`build/alloc/inputs` 是固定開銷。
**⇒ 「M3 要去序列化圖建構／配置／IO」這三條路今天可以正式關閉。**

這一條同時解釋了 roadmap 那句「pool 143→179 slots 讓 I/O 少 3.7×，decode 只 +9%」——
不是 I/O 不重要，是**它從來不在關鍵路徑上**（`fill_wait = 0` 是直接證據）。

## 4. 判決 B：去序列化的空間有多大 —— **兩個估計互相矛盾，而那個矛盾是重點**

### 4.1 保守估計（從 `CGC-DECPROF` 的步級三分來）

| 來源 | 每步 | 全消除後 | t/s |
|---|---|---|---|
| `cb` 8% + `submit` 4% | 11.1 ms | 81.6 ms | **12.25**（1.14×） |
| `cb` 10% + `submit` 4% | 13.0 ms | 79.8 ms | **12.53**（1.16×） |
| 再加 `gap` 19%（`CGC-GPUTIME` 下界） | +15.3 ms | 77.4 ms | **12.91**（1.20×） |
| 再加 `gap` 24%（16:49 實測） | +19.4 ms | 73.4 ms | **13.62**（1.26×） |
| 再加 `gap` 36%（17:14 上界） | +29.1 ms | 63.7 ms | **15.70**（1.46×） |

**⇒ 保守估計把 15 t/s 放在「gap 取上界」那一端。** 也就是說：**單靠去序列化，
`cb+submit+gap` 全部歸零，剛好擦過 15 t/s。** 這是樂觀情形，不是預期值。

### 4.2 實測上界（`CGC_SUBMIT_AHEAD`）—— **它比保守估計大得多**

已記錄的實測（`MEMORY_PERF.md`，配對中位）：**每步 82.5 ms → 31–44 ms ⇒ 上限 ×1.711**
（區間 1.327–1.924）。換算成 t/s：`92.8 → 54–61 ms` ⇒ **16.4–18.5 t/s**。

**⇒ 這一條說「15 t/s 是有的」**，而且比 §4.1 的樂觀端還寬。

### 4.3 ★ 矛盾在哪裡，以及它為什麼是重點

`cb+submit+gap` 加總最多解釋 **29.1 ms**，而 SUBMIT_AHEAD 實測省下 **38–51 ms**。
**差額 9–22 ms 沒有被 `CGC-DECPROF` 的步級三分解釋掉。**

**這不是誤差，這是儀器盲區**：`wait`（86–88% 那塊）內部**只有 `gap` 是有 GPU 時鐘證據的**，
其餘 ~50 ms 是「GPU 在忙但 CPU 在等」還是「CPU 在忙」**這份剖面分不出來**
（`M3_PRECEDENCE` §5 的「未排除」項）。SUBMIT_AHEAD 移除的正是那一塊的一部分
—— 它讓 `submit i+1` 與 `hook i` 並行，於是 **CPU 不再串在 GPU 的前面**。

**⇒ 判決 B 的正確述句**：
**「去序列化的空間存在（SUBMIT_AHEAD 證明 ≥38 ms/步，足以讓 15 t/s 擦線過），
但它的量測儀器不足 —— 步級三分只能解釋其中的一半，另一半住在那個盲區裡。」**

## 5. 判決 C：**M3 的離開條件與 D3 的 S2／S3 是同一件事**

這是本文件最重要的一條，理由是一個直接對應：

| | |
|---|---|
| **`CGC_SUBMIT_AHEAD` 為什麼錯** | 它提前提交 segment i+1，於是 top-k hook 讀到的可能是 stale ids ⇒ garbage remap ⇒ 輸出損壞 |
| **為什麼「不提前提交」是目前的設計** | 每一層的最後一段結束後，**host 必須先讀 top-k、再把 expert→slot 的查表寫回圖**，下一段才能提交。這是一個**結構性的 GPU→CPU→GPU 往返** |
| **移除那個往返是什麼** | 就是 `docs/REMAP_ROUNDTRIP_REMOVAL_PLAN_2026-09-15.md` 的題目 |

而那個階梯的現狀（09-17 查證）：

- **S1（GPU slot table，`CGC_SLOT_TABLE_GPU`）已位元身分達成**，但**結構上不更快** ——
  另一條線自己的話：`expert_cache_on_topk` 在**兩個臂都跑**，S1 從沒移除過一個 host step。
  我在 `src/llama.cpp/src/llama-context.cpp:4785` 的註解核到同一件事。
- **S3 的前提 B 已被 47.5% 打掉**。
- **S2／S3 未開始。**

**⇒ 所以 M3 的頭條路徑（去序列化）＝ D3 的 S2／S3，而那一條的兩個關鍵點（S1 無速度、
S3 前提被否）已經判過。這不是「M3 很難」，是「M3 與 D3 重合，而 D3 已經走過一半並且
那一半證明沒有速度」。**

## 7. 離開條件的判定

**未達。** 今天 MTP off 的可引用值是 **10.78 t/s**，離開條件是 **15**。

**且今天沒有可立即執行的路徑**，逐條說：

1. **去序列化（Cell 1）**：空間存在（SUBMIT_AHEAD 實測 ≥38 ms/步），但正確實作＝D3 的 S2／S3，
   而 S1 已證明無速度、S3 前提已被否證 ⇒ **不是一個可執行的下一步，是一個待重新設計的題目**。
2. **圖建構／配置／輸入拷貝**：**今天正式關閉**（§3，0.07%，三個數量級）。
3. **IO／填槽**：**今天正式關閉**（`fill_wait = 0.000`，且短負載命中率 96%＋）。
4. **削 compute（Cell 2／3）**：唯一在數學上還站得住的路（§4 的差額 9–22 ms 只能從這裡來），
   但 **Cell 2 沒有判準、Cell 3 前置未完成**。

## 8. 誠實邊界

- **本文件沒有實作任何東西**，也**沒有跑 A/B**。它跑了**一份新剖面**（17:14，HEAVY），
  其餘是既有剖面的整理與算術。
- **§2.2 的 t/s（7.76）不可引用**；§2.1 的（10.78）可以。**兩份剖面的熱狀態不同，已在表頭標明。**
- **兩個儀器的 per-step total 不一致（118.5 vs 94.1 ms），本文件沒有解決它**，只用各自的比例。
  要解決它得先確定兩個儀器各自覆蓋的窗口邊界 —— 那是一件獨立的事。
- **§4.3 的「差額 9–22 ms」是減法得出的，不是量到的。** 它的地位是「指出儀器盲區」，
  不是「證明那一塊值 22 ms」。**能裁決它的量測在下節。**
- **`CGC_SUBMIT_AHEAD` 的 ×1.711 是記錄值**（`MEMORY_PERF.md`，配對中位，區間 1.327–1.924），
  而**那個臂的輸出必然損壞** ⇒ 它只能當**上界**，不能當「預期收益」。
- **M3 有可能真的沒有 2.32×。** roadmap 自己標 ★ 最可能失敗並允許否定收場。
  本文件的價值是讓「失敗」變成**可稽核的**，而不是用沒拆開的數字做決策。

## 9. 唯一能裁決 §4.3 的量測 —— **而三條候選裡有兩條是死的（其中一條是本次發現）**

**目標**：把 `wait` 那 ~50 ms 的盲區拆開 —— 分清「GPU 在忙但 CPU 在等」與「CPU 在忙」。

| 候選 | 判決 | 依據 |
|---|---|---|
| `CGC_PHASE_TIMING` | **❌ 死** | 它把整步歸成 `compute`（`compute == gpu`，見 §2.2）⇒ 拆不開。**不要重試。** |
| `CGC_VERIFY_OP_TIMING` | **❌ 死 —— 本次發現** | 它的目標判定最後一行是 `node->src[2]->type == GGML_TYPE_I32 && node->src[2]->ne[1] > 1`（`src/llama.cpp/src/llama-context.cpp:3830`）。**`ne[1]` 是 token 數 ⇒ 它只在 T>1（verify 路徑）生效**，而 M3 的判準是 **MTP off（T=1）** ⇒ **它對 M3 產生不了任何輸出**。 |
| **逐節點 GPU 時間**（Metal counter sample buffer） | **✅ 唯一活路**，成本最高 | 唯一能給「GPU 側」答案的機制；`CGC-GPUTIME` 的粒度只到 segment（＝層） |

**⇒ 這解釋了 M3 為什麼「沒有可執行的下一步」：不是缺路，是缺「能量出路在哪」的儀器。**
`src/llama.cpp/debug-verify-path-breakdown.md` 那組逐型別數字（gate/up/down 各 ~0.8/0.8/1.0 ms）
是在 **verify 路徑（T>1）** 量的 ⇒ **不能移植到 T=1 的 decode**。§5 指出的盲區正是 T=1 的那一塊。

**而這也回頭解釋了 Cell 2 的歷史**：`CGC_MMV_FUSE` 是在**沒有判準**的情況下實作的
⇒ 盲試 ⇒ 失敗（輸出損壞且更慢）。**同一個形狀的錯誤不要再犯一次。**

**判準（先寫下來，免得事後移動球門）**：若逐節點 GPU 時間顯示 `ffn_moe_*` 那群佔 `wait` ≥40%
⇒ **Cell 2 有量**，M3 還有一條路；若 < 15% ⇒ **三條路全部不足，正式走「找不到路」分支並附 M0 剖面表**。

## 10. 一句話總結給下一個人

**M3 的 15 t/s 不是被「難」擋住，是被「重合」與「沒有儀器」擋住** ——
它的頭條路徑與 D3 的 S2／S3 是同一條，而那一條的 S1 已證明無速度、S3 已被否證；
它剩下唯一在數學上站得住的路（削 `compute`）**缺一個能回答「本錢在哪」的儀器**，
而 §9 的表顯示兩個既有儀器**都拆不到 T=1 的層內**。
**要嘛重新設計 S3，要嘛先建 §9 那個唯一活路（逐節點 GPU 時間）** —— 在那之前，
M3 沒有可執行的實作步驟，而**「沒有判準就不要實作」本身是這個 repo 已經付過學費的結論**
（`CGC_MMV_FUSE`），所以停在這裡是對的，不是進度停滯。

## 11. 續作（同日 17:5x）：per-layer GPU 歸因 —— 儀器已建、已驗，而它把 Cell 1 的結論釘死

### 11.1 建了什麼

`src/llama.cpp/ggml/src/ggml-backend.cpp`（**唯一改動的檔**，+52/−4）：

`cgc_gpu_take()` 本來就逐 segment 回傳 Metal 的 `GPUStartTime/GPUEndTime`，但那些值只被加進
per-step 的 `gt_*` 累加器，**層的身分被丟掉** ⇒ 這個 repo 唯一的 GPU 側讀數只有 per-step。
現在它們按層歸因（`dp_lay_gpu`／`dp_lay_uni`／`dp_lay_gap`／`dp_lay_sg`），並接上既有的
`dp_il`（由 top-k 張量名推層號）與 `CGC-DECPROF` 的印出（step 行加 `gpu_sum/union_sum/gap_sum`；
每層行加 `gpu=/union=/gap=/sg=`）。

**為什麼這一支是唯一 perturbation-free 的歸因**：這些時間戳由 Metal 的 completion handler 提供，
**不給圖增加任何工作**。（`CGC_VERIFY_OP_TIMING` 那種「排程器觀察」會加 sync，成本與觀察點數成正比
⇒ **不能用來算佔比**。）

### 11.2 驗證（兩條，都必要）

1. **inert**：`m123_oracle_gate.py --tag m3_layergpu_20260917` ⇒ **PASS，M1/M2/M3 = 9/9、
   `comparable=True`、`config_diffs=[]`** ⇒ 純量測、位元身分不變。
2. **自洽（內建交叉檢查）**：`Σ per-layer` 必須逐格等於既有的 per-step 累加器。實測（step 384）：

   ```
   gpu_sum=174.61  busy_sum=174.61 | union_sum=118.48  gpu_union=118.48 | gap_sum=21.19  gap=21.19
   ```

   ⇒ 到小數第二位相同。**這一條當場抓到了一個 1000× 的單位錯誤**（`gt_*` 是 ns、`dp_lay_*` 是 µs），
   已修並寫成 lesson `eng-mh-0058`。

### 11.3 判決：**去序列化沒有局部目標**

穩態（step 384、40 層、MODERATE、hit 96.7%）：

| 量 | 值（ms/步） | 佔 wait |
|---|---|---|
| `wait`（逐層相加） | 108.8 | — |
| `Σ GPU union`（實際佔用跨度） | **118.5** | **109%** |
| `Σ GPU gap`（段間閒置） | **21.2** | **19%** |

**逐層分散度**（這是新的、也是關鍵的）：
