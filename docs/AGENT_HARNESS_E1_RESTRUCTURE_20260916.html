3. 搬遷的真正成本：4 個檔案裡的 9 處

642 個檔案是用 git mv 搬的，所以歷史是連續的（git log --follow 走得通）。 但真正的成本不在 642 個搬動，而在 9 處「假設了舊位置」的字串。 它們分三類，其中一類是搬遷才讓它現形的。

3.1 三個路徑錨點（tb_loop/config.env）

config.env 有 4 條路徑不是相對「自己」算的，而是相對「自己所在目錄」的鄰居算的。 搬動之後那些鄰居換了：

原本寫法搬遷前解析到搬遷後若不改
${TB_LOOP_DIR}/../app/cloud/…flashkv-devserver/app/… agent_harness/tb_loop/../app → agent_harness/app（不存在）
${TB_LOOP_DIR}/loopmoe/configs/…agent_harness/loopmoe/… agent_harness/tb_loop/loopmoe/…（不存在）
${TB_LOOP_DIR}/loopmoe_outputagent_harness/loopmoe_output agent_harness/tb_loop/loopmoe_output
${TB_LOOP_DIR}/pd_dataagent_harness/pd_data agent_harness/tb_loop/pd_data

處置：把三個「代表不同事物」的錨點顯式分開，而不是繼續用一個變數加 .. 推：

TB_LOOP_DIR     = agent_harness/tb_loop      # 屬於 tb_loop：harness/ results/ sft_data*/ .venv/
TB_HARNESS_ROOT = agent_harness              # 不隨 tb_loop 移動：loopmoe/ loopmoe_output/ pd_data/
TB_REPO_ROOT    = <repo root>                # 跨過 harness 根：app/cloud/freebuff2api/.env

3.2 三處 PYTHONPATH（三個入口各一）

run_round.sh、gen_sft.sh、finetune/eval_round.sh 都寫 PYTHONPATH="$TB_LOOP_DIR"，而 import 字串是 tb_loop.agents.…。 解譯器要的是套件的父目錄。改法只有一個字串替換，import 字串一行都沒改 （這正是 PLAN R2 推薦 (a) 的理由）： 

- PYTHONPATH="$TB_LOOP_DIR"      # 搬遷前＝ agent_harness/（恰好對）
+ PYTHONPATH="$TB_HARNESS_ROOT"  # 搬遷後＝ tb_loop/ 的父目錄（依定義對）

3.3 兩處 .tb-loop-venv：一個我選的行為變更，明寫在這裡

learning/refine_harness.sh 與 learning/rollback_harmful.sh 用 "$TB_LOOP_DIR/../.tb-loop-venv/Scripts/python" 找 Windows 彩排用的 venv。 這個路徑在搬遷前解析到倉庫根的 .tb-loop-venv，而 tb_loop/README.md 的 Windows 彩排段把 venv 建在 tb_loop/ 裡面—— 腳本與文件的敘述從來就沒有一致過。

我把它改成 "$TB_LOOP_DIR/.tb-loop-venv/Scripts/python"，讓它與文件一致。 這是行為變更（原本找 A 地點，現在找 B 地點），而它在本機無法驗證： venv 從未被創建過，這一支只對 Windows 彩排有意義。 選擇「與文件一致」而不是「維持現狀」，理由是現狀本身沒有依據；把它記在這裡、 記在 commit message 裡，而不是讓它靜默地跟著搬遷漂一格。

=== B) 對照組：錯誤的 PYTHONPATH（指向 tb_loop 自己）—— 必須失敗 ===

=== C) 子模組真正被解析到搬遷後的位置 ===

  tb_loop.agents.codebuff_api_agent      -> .../tb_loop/agents/codebuff_api_agent.py

  tb_loop.learning.attribution           -> .../tb_loop/learning/attribution.py

怎麼讀 A 的最後一列

ModuleNotFoundError: No module named 'terminal_bench' 不是失敗，它是 進度：錯誤訊息裡的模組名從 tb_loop 換成了 terminal_bench， 證明套件解析這一關已經過了，下一個阻塞是環境（沒裝 terminal-bench）。 一個測試的判讀方式是「它報的是不是我正在修的那個名字」。

B 是這個測試成立的原因。沒有 B，「A 通過」可能只是因為當前工作目錄剛好也在 sys.path 上。有了 B，A 通過才有資訊量。

5. 一個我自己犯的測量錯誤（比 §3 的任何一處都值得記）

第一次驗證 config.env 時，我得到一組看起來像重大缺陷的輸出： 

TB_LOOP_DIR    = /Users/alexchuang/Documents/flashkv-devserver        ← 倉庫根！
TB_HARNESS_ROOT= /Users/alexchuang/Documents
LOOPMOE_CONFIG = /Users/alexchuang/Documents/loopmoe/configs/…        ← 完全錯的地方

它看起來像「搬遷把三個錨點全部算錯」。真相是：我的測試跑在 zsh 下，而 BASH_SOURCE 在 zsh 裡是空的——${BASH_SOURCE[0]} 求值成空字串，dirname "" 是 .，於是 cd . && pwd 回報當前工作目錄（倉庫根）。 錯的不是 config.env，是儀器。用 bash -c 重跑之後得到 §4.2 那組正確結果。

這一節為什麼要獨立寫出來

它的形狀與本專案既有的 lesson 家族同源（eng-diag-0013「診斷要先被證明會印」、 eng-gate-0016）——一個壞掉的儀器會產生一個看起來完全合理的缺陷。 這一次它剛好是保守方向的（報錯比實情糟），所以沒有造成損失； 但同一個錯誤若發生在「驗證通過」的方向，就會把一個壞缺陷標成綠燈。 規則：驗證一個「靠 shell 語意求值」的東西時，要確認你用對 shell。 #!/usr/bin/env bash 的腳本要用 bash 跑，不是用你的互動 shell 跑它。

6. 新知識落成 lesson（eng-smoke-0003）

依本 repo 的慣例，新知識要在同一個 commit 進 traces/lessons.jsonl。 這一輪的產物是一條 smoke 類的規訓，它比 eng-smoke-0002 更一般化 （0002 記錄的是「這個缺陷存在」，0003 記錄的是「這類缺陷為什麼無法在移動前被觀測」）： 

rule: 当一个路径变量「恰好」等于另一个时，任何挂在它底下的派生都是定时炸弹：
      它在被移动之前无法被区分（两个名字指向同一个目录，所以两种写法都对），
      移动之后则静默指错。锚点要按「它代表什么」显式命名，不是按「它现在等于什么」；
      而 import 的验证必须带一组对照组，否则「通过」可能只是因为当前工作目录刚好也在
      sys.path 上。

它的 counterexample_observed 記下了同一次搬遷裡最有說明力的一組對照： 用 $(dirname "${BASH_SOURCE[0]}")/.. 這類「自帶錨點」寫法的腳本 （local_rehearsal.py、batch_run.sh、refine_harness.sh 的 TB_LOOP_DIR 推導）在搬遷後一行都不用改；而共享一個變數的腳本全部要改。 同一次搬動，兩種寫法的成本差是 0 比 9。
