一句話。.workbuddy/memory/ 與 ~/.workbuddy/skills/ 的快照 （agent_harness/memory/、agent_harness/skills/）在被憲章記成「三個防線」之後， 過期是完全不可觀測的：兩個既有的 --check 都只驗原檔↔索引、不驗快照， 而跨機器推送器會忠實地把一份過期快照推上去。 本輪給匯入器加了 --check，而它一加進來就紅了兩處 —— 那兩處正好是「防線自己漂了兩天而無人知」的實體。

§1 問題：過期在閘門上不存在

三條各自獨立的實測，合起來構成「不可觀測」：
軸實測後果
有沒有檢查 import_harness_snapshot.py 在 2026-09-18 之前沒有 --check、沒有 argparse （傳 --help 會直接執行匯入） 想知道快照新不新鮮，唯一的辦法是執行匯入——那會改檔，所以問題本身無法在不改變狀態的前提下被回答
有沒有排程 automations 表只有一筆 once 且已過期；launchd／crontab 無相關條目 沒有任何東西會週期性地去跑它
有沒有閘門 build_memory_index.py --check 與 index_assets.py --check 都只驗原檔↔索引（CONVENTIONS.md:940-941 逐字記著這件事） 快照的 bytes 不在任何檢查的管轄範圍內
失效是安靜的。 agent_harness/scripts/auto_git_push.ps1（另一台機器上的定時推送器） 只 git add agent_harness 後 push ⇒ 它會忠實地把一份過期快照推上去， 而沒有任何東西會出聲。這與本 repo 反覆記下的模態同族：綠燈與沒被檢查長得一樣。

1.1 為什麼「過期」在這個設計裡是必然會發生的

權威本體是 host 持續寫入的 .workbuddy/memory/*.md（每日 append-only 日誌， 而且這個 repo 常見多個 session 共寫）。快照是衍生物，因此「它落後」是常態而不是例外； 問題不在落後，而在落後沒有任何觀測面。

這是本輪最有力的證據，因為它否證了「防線存在」這個敘述本身。 一份被設計來防止「安靜的遺漏」的文件，自己用同樣的方式漂了兩天 —— 而既有的每一道閘門都是綠的，因為它們驗的是別的軸。

§3 修法：--check ＋ 三個刻意反直覺的判準

3.1 五種漂移分開，因為處置不同

標記意思處置
[stale]原檔的 source_sha256／source_bytes 與記錄不符正常落後：重跑匯入
[new]探索到原檔但沒有記錄（新的一天／新 skill）重跑匯入
[removed]有記錄但已不是輸入（skill 被刪／改名）重跑匯入
[hand-edited]副本與「用它自己記錄的 snapshot_date 重算」不符 違規：有人手改了副本，而匯入會靜默蓋掉它 ⇒ 先看過再匯入
[readme-table]兩份 README 的成員表與實際集合不符，或表格不存在修表格（見 3.2 第 ① 條）

[hand-edited] 是新增的可觀測面：「不要手改副本」是 D6 三個防線之一在講的事， 而在本輪之前它完全不可觀測 —— 手改的內容會在下一次匯入被蓋掉，而那次匯入看起來完全正常。

3.2 三個反直覺的判準（理由都是同一個：能繞過的閘門不是閘門）

  1. 「拿掉成員表」算失敗，不只印提示。 若「找不到表格」只影響輸出、不影響 exit code，那刪掉表格就是一條靜音的繞道。 （這一條是自測的 F 格逼出來的：第一版寫成「只提示」，那一格於是假失敗 —— 而假失敗正好暴露那個設計是錯的。）
  2. 不接進 pre-commit hook（刻意的）。 .workbuddy/memory/*.md 含多 session 共寫的每日 append-only 日誌 ⇒ 硬閘門會永遠紅。判決沿用 CONVENTIONS.md:927-928： 「每日日誌當天必變，永遠紅的閘門等於沒有閘門」。改走兩條會真的發聲的路： 收尾序列（cgc-commit-gate §6.3）＋ 定時自動化（§4）。
  3. 用「記錄裡的那個 snapshot_date」重算預期內容，不是用今天。 否則每逢跨日，每一份快照都會被誤報成「被手改過」—— 這正是本 repo 反覆踩到的 mtime 假漂移（cgc-commit-gate §3.1 的簽名）。 這一格有自測釘住（D 那一格）。

3.3 自測抓到我自己的一個 bug（守衛放錯了路徑）

B' 那一格（刪掉唯一的 skill）原本 rc=1 卻看不到 [removed]： discover() 的「空清單拒跑」守衛搶先 raise SystemExit。 那個守衛的正當理由是「不要寫出一份空快照」——那是寫入的風險；而 --check 不寫檔， 它應該把那份狀態報出來。 修法：discover(strict=True/False)，守衛只屬於寫入路徑。

3.4 順手修掉的兩個既有危害

  • 匯入器現在有 argparse：--help 真的只印說明 （原本它會直接執行匯入，產生 7 檔 repo churn）。
  • 新增 --dry-run：可以「先看它要做什麼」而不改狀態。

§4 排程：把「有人記得跑」換成「有執行者」

建了一筆每日自動化（automation-1789702849998，FREQ=DAILY;BYHOUR=9;BYMINUTE=10， cwd 指向本 repo）。它的行為是： 
python3 agent_harness/scripts/import_harness_snapshot.py --check
  exit 0  ⇒ 回報一行「快照新鮮，無需動作」，不改任何檔案
  exit≠0  ⇒ 1. 先看 git status（有別人的未提交改動 ⇒ 只回報並停止，不 commit）
            2. 有 [hand-edited] ⇒ 停下回報（刷新會蓋掉它，需要人看過）
            3. 刷新 → 驗 sha 逐檔相符 → 修 README 表 → 重生索引（順序固定）
            4. 再跑 --check 確認轉綠 → 逐檔 stage → RUN_REPLAY_BENCH=0 commit
            5. push 兩個遠端，並用 ls-remote 的真實 SHA 驗三處相同
誠實邊界（重要）：自動化「建好」不構成它「跑過」的證據。 本白皮書寫作時，automation_runtime_state 對這筆新自動化還沒有任何執行紀錄。 ⇒ 本輪只主張「機制已建、且有 14 格自測」；「排程真的在跑」這條義務尚未結清， 驗收是 automation_runs 出現紀錄、而且 --check 在那次執行裡真的被跑過。 這一條已寫進 CONVENTIONS.md D6 的 2026-09-18 修訂（依 §E：不可寫成已完成）。

§6 自測 14 格（含陰性對照）

  PASS  import rc=0 且產生副本
  PASS  副本有 banner（插在 frontmatter 之後）
  PASS  --check 乾淨 ⇒ rc=0
  PASS  --check 不寫任何檔
  PASS  A 原檔變 ⇒ rc=1 且標 stale
  PASS  B 新增原檔 ⇒ rc=1 且標 new
  PASS  B' 刪 skill ⇒ rc=1 且標 removed
  PASS  重跑匯入（含修好 README 表）後回到 rc=0
  PASS  C 手改副本 ⇒ rc=1 且標 hand-edited
  PASS  D 跨日不誤報（用記錄的日期重算）⇒ rc=0
  PASS  E README 宣告不存在的成員 ⇒ rc=1 且標 readme-table
  PASS  F 拿掉成員表 ⇒ rc=1 且明說未檢查（不能靠刪輸入變綠）
  PASS  空 skill 清單 ⇒ 匯入拒跑（rc!=0）
  PASS  空來源 ⇒ --check 不拒跑、而是報 drift（rc=1）

三個陰性對照值得單獨點名，因為它們各自堵掉一種「看起來通過」： 「--check 不寫任何檔」（判準是整棵樹的內容雜湊不變）、 「乾淨狀態必須回 0」（一個永遠回 1 的檢查會讓所有陽性對照通過）、 「跨日不誤報」（防止用今天重算造成永久紅燈）。

§8 誠實邊界（不主張什麼）

  • 不主張排程已經在跑。自動化已建（§4），但沒有執行紀錄 ⇒ 只主張「機制已建、14 格自測」。
  • 不主張 [hand-edited] 的偵測在真實樹上被觸發過。 它只在自測的 C 格被觸發；真實樹上目前 0 筆（見 §5 的 --check 輸出）。
  • 不主張閉環對照已執行。D6 的 2026-09-16 修訂留下的那個義務（改 CONVENTIONS.md 要走一次 PLAN §6.3 的閉環對照）狀態不變、仍未跑； 本輪又改了 CONVENTIONS.md，所以那條欠帳增加了一次改動，並沒有被本輪結清。
  • 不主張成員表涵蓋所有會腐爛的文件。被納入檢查的只有 agent_harness/memory/README.md 與 agent_harness/skills/README.md 這兩張表；本輪在別的地方也看到同一族的腐爛（cgc-commit-gate §5.2 對匯入器的敘述 「沒有 argparse、傳 --help 會直接執行匯入」），那是手動修掉的，不是被檢查抓到的。
  • 不主張 --check 的判準涵蓋「快照該不該存在」。它驗的是 「副本 ↔ 原檔 ↔ 記錄」三者一致；source 路徑本身寫死成絕對路徑 （跨機器時那條路徑不存在，這一點仍是舊有設計，本輪未動）。
