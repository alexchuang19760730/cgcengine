1. 三場景 profile 定義與挑戰

1.1 Profile 矩陣

Profile 輸入長度 輸出長度 核心挑戰 decode 速度目標
qa-zh ~50-200 tokens ~10-80 tokens 短問答, MTP N-gram 易在 prefill 結尾誤觸 stop; draft accept 偏低 (~30-40%) 10-15 t/s (短 prompt overhead 大)
longform-zh ~200-800 tokens ~300-1000 tokens 長文, MTP fast path 命中, 但 prefill 結尾若為結構化 marker 會迴圈 25+ t/s (steady-state)

1.2 三場景共有的關鍵問題

  • 預設模板覆寫: GGUF embedded chat template (Qwen 預設 ChatML) 跟 server 端 disable_think_scaffold / assistant_prefill 邏輯互斥 — 走 generic ChatML 兩個 flag 都失效
  • Nail custom token 兼容性: Nail 的 <|user|> token 是訓練外的 custom token, model 不認, 會重複輸出 <|user|>
  • Pre-fill 結尾邏輯: 不同場景 prefill 結尾差異大 (自然語句 / 反引號 / 換行) — THINK_SEED 注入策略要依場景分支
  • Stop token 衝突: coding 場景 ``` 是必要 fence, 但也被當 stop — 1-token stop 永遠觸發在第一個 code block 結尾

3. Nail-Qwen3.6 Minimal Chat Template 設計

3.1 為什麼需要 Minimal Template

原 Qwen 預設模板的問題:

  • 走 GGUF embedded ChatML, 跳過 server 端的 Nail handler 注入邏輯 (disable_think_scaffold / assistant_prefill 都不生效)
  • model 進入 think loop, 輸出 "Okay, let me think..." 後無限輪轉

解法: 寫一個 Minimal Chat Template, 用 ChatML 風格 (<|im_start|> / <|im_end|>) 但 server 端用 --chat-template-file 強制走 Nail handler。

3.2 Template 源碼 (models/templates/Nail-Qwen3.6-Minimal-Chat.jinja)

3.3 錨點設計: 為什麼 header 註解要含 "Minimal chat template for Nail-Qwen3.6-MTP" + ""

chat.cpp 的 dispatch 邏輯用 字串比對 判斷是否走 specialized Nail handler:

  • 必須含 "Minimal chat template for Nail-Qwen3.6-MTP" — 識別是 Nail 模板
  • 必須含 "" — 識別是支援 think scaffold 的模板
  • 兩者都命中 → 走 Nail handler → 注入 disable_think_scaffold + assistant_prefill 邏輯

這是 dispatch by content sniffing 的脆弱設計, 但因 upstream chat.cpp 不暴露明確 API, 只能靠註解字串錨點。**未來若 upstream 改 dispatch 邏輯, 這錨點要同步更新**。

脆弱點: 若有人誤刪 header 註解 (例如做 lint cleanup), 會靜默回退到 generic ChatML handler, model 進 think loop, 不會有編譯錯誤也不會有明顯 log。 建議: 跑 replay benchmark 跑 qa-zh profile, 觀察是否有 "Okay, let me think..." 開頭的回應。

4. v4 Fix: 改 ChatML + 純 prefill 路徑

4.1 根因 (v3 over-correction)

v3 commit ddde852b0 做了兩個改動:

  1. 把 THINK_SEED 改成空字串 (避免亂碼)
  2. 加 disable_think_scaffold flag

但這 把 THINK_SEED 完全關掉, 連 qa-zh 場景也需要它做開頭引導, 導致 qa-zh 退化 (model 不知道該生成什麼, 開始 think loop)。

4.2 修法 (v4 純 prefill 路徑)

  • 改走 純 prefill 路徑: request 帶 assistant_prefill 讓 model 直接接續生成
  • chat template 改 ChatML 風格 (用 <|im_start|> 不用 Nail <|user|>)
  • 保留 disable_think_scaffold flag 但只在 longform/coding 用, qa-zh 走純 prefill

4.3 結果

qa-zh: 14.88 t/s + 100% MTP accept — 完全沒退化, prefill 路徑乾淨, model 直接接 assistant_prefill 開頭, 不需要 THINK_SEED 引導。

但 v4 不可重現: 14.88 t/s 是特定 prompt 下, 後續重跑會掉到 ~10 t/s。 這是 v5 修復的對象。

5. v5 Fix: wants_think_scaffold_seed + has_assistant_prefill

5.1 v4 不可重現的根因

v4 把 THINK_SEED 邏輯直接跳過 (因為走純 prefill), 但 dispatch 判斷是否注入 THINK_SEED 的函式 wants_think_scaffold_seed 沒考慮 has_assistant_prefill。結果:

  • 若 client 沒帶 assistant_prefill (e.g. /v1/chat/completions 預設), wants_think_scaffold_seed 仍回 true → 注入 THINK_SEED → prefill 污染 → model 進 think loop → 速度掉到 ~10 t/s
  • 若 client 帶 assistant_prefill, 跳過 THINK_SEED → 乾淨 prefill → 14.88 t/s

5.2 修法: 加 has_assistant_prefill 觸發條件

// src/llama.cpp/src/llama.cpp (chat.cpp dispatch)
bool wants_think_scaffold_seed(const std::string & prompt, bool has_assistant_prefill) {
    if (has_assistant_prefill) {
        return false;  // 有 prefill → 不需要 THINK_SEED 引導
    }
    // ...原本的 marker 偵測邏輯
    return prefill_tail_is_structured_marker(prompt);
}

並在 run_server.sh 預設帶 --chat-template-file 走 Nail handler, 讓 v4 純 prefill 路徑在 client 沒帶 assistant_prefill 時也能命中。

5.3 結果

  • qa-zh: 穩定 ~14 t/s (不再依賴 client 帶不帶 prefill)
  • longform-zh: 保持 25+ t/s (THINK_SEED 仍觸發, 沒被誤跳過)
  • coding: 1-token stop 仍存在 (v6/v7 才根治)

6. v6 Fix: THINK_SEED 條件式 Marker 跳過

6.1 問題: longform 迴圈

longform 場景 prefill 結尾若是 結構化 marker (換行、反引號、JSON bracket 等), 注入 THINK_SEED 會讓 model 誤以為「這是 code/JSON 內文, 我該繼續寫」, 結果 迴圈生成。

6.2 修法: 條件式 marker 跳過

// 結尾是結構化 marker (\n / ``` / { / [ 等) → 跳過 THINK_SEED
// 結尾是自然語言 → 正常注入 THINK_SEED 引導 reasoning
if (prefill_tail_is_structured_marker(prefill)) {
    skip THINK_SEED injection;
}

具體 marker 偵測:

  • 結尾是 \n / \r\n / 連續空白
  • 結尾是 ``` (反引號)
  • 結尾是 { / [ / ( (open bracket)
  • 結尾是 " / ' (引號)

6.3 結果

longform-zh: 25+ t/s + 無迴圈 — 結構化 marker prefill 不再被 THINK_SEED 污染。

7. v7 Fix: cgc_patch_coding_stop (coding 1-token stop 根治)

7.1 問題: Qwen3-IQ3-MTP 的已知模型限制

GPT-style stop 集合 (```, <|im_end|>, <|end|>) 是 Qwen3-IQ3-MTP 組合的已知模型限制 — 在無 hint coding prefill 下, 第一個 code block 結尾 (碰到 ```) 立刻觸發 stop, model 只輸出 1 個 token 就結束。

7.2 修法: cgc_patch_coding_stop helper

in tools/server/server-common.cpp:799:

  • 偵測 prompt 結尾是否含 code fence open (```python\n / ```c\n / ```cpp\n / ...)
  • 若含 + 停字串中有 ``` → 把 ``` 替換為 ```\n\n
  • 給 model 機會自然寫完整個 code block 才 stop

7.3 實作關鍵 (從 server-common.cpp 摘)

static void cgc_patch_coding_stop(json & llama_params) {
    // 1. 偵測 code fence open at end of prompt
    bool has_coding_fence = false;
    static const std::vector fence_languages = {
        "python", "py", "c", "cpp", "c++", "java", "javascript", "js",
        "typescript", "ts", "rust", "rs", "go", "ruby", "rb", "php",
        "swift", "kotlin", "scala", "sh", "bash", "sql", "html", "css",
        "json", "yaml", "yml", "xml",
    };
    for (const auto & lang : fence_languages) {
        const std::string marker = "```" + lang + "\n";
        if (prompt.size() >= marker.size() &&
            prompt.compare(prompt.size() - marker.size(), marker.size(), marker) == 0) {
            has_coding_fence = true;
            break;
        }
    }
    // 2. 若有 fence + stop 列表有 ``` → 替換為 ```\n\n
    for (auto & s : llama_params["stop"]) {
        if (s.is_string() && s.get() == "```") {
            s = std::string("```\n\n");
        }
    }
    // 3. escape hatch: cgc_code_strict_stop=1 可強制保留原 stop
    if (k.contains("cgc_code_strict_stop") &&
        k["cgc_code_strict_stop"].get() == "1") {
        return;
    }
}

應用於兩個 endpoint: /completion 跟 /v1/chat/completions。

7.4 設計選擇: 只改 stop 字串, 不刪除 stop

  • 確保非 coding 場景行為 bit-identical (若 prompt 沒 fence, 直接 return)
  • 提供 cgc_code_strict_stop=1 escape hatch 讓 client 強制保留原 stop (debug 用)
  • 不改 model 行為, 純 server 端 patch → 易 rollback

7.5 結果

coding: 27+ t/s + code block 完整生成 — model 寫完 ```python\n ... \n```\n\n 才 stop, 1-token stop 完全消失。

9. 設計哲學: minimal + ChatML + 預設走 Nail handler

9.1 Minimal 設計

Template 只做三件事:

  1. 把 messages 轉成 ChatML 字串
  2. 處理 assistant_prefill 注入
  3. 處理 summary_prefill 注入

不做的事 (留給 server handler):

  • THINK_SEED 注入 (wants_think_scaffold_seed 函式在 server 端判斷)
  • disable_think_scaffold flag 處理 (server 端用 chat_template_kwargs 傳入)
  • Stop 列表 patch (cgc_patch_coding_stop 在 server-common.cpp)

9.2 ChatML 風格 (不用 Nail <|user|>)

原因: b66e0eaf7 驗證 Nail 的 <|user|> token 在 Qwen3.6-35B 訓練集沒出現, model 會重複輸出 <|user|>。 改用標準 ChatML (<|im_start|> / <|im_end|>) 解決。

9.3 預設走 Nail handler (vs GGUF embedded)

server 端啟動時 必須 加 --chat-template-file 走 Nail handler, 否則 dispatch 會走 generic ChatML handler, 跳過 disable_think_scaffold + assistant_prefill 注入 → model 進 think loop。

# run_server.sh 必要參數
--chat-template-file src/llama.cpp/models/templates/Nail-Qwen3.6-Minimal-Chat.jinja
--jinja

10. 後續 Roadmap

10.1 Chat Template 多 profile dispatch

目前所有場景用同一個 template, 透過 server 端 wants_think_scaffold_seed 判斷 是否注入 THINK_SEED。future work:

  • 依 profile 自動選 template (qa-zh 走 minimal prefill, coding 走 coding-aware)
  • 把 cgc_patch_coding_stop 邏輯從 server-common.cpp 移到 template 層

10.2 Nail handler 升級 (upstream 整合)

目前 dispatch 靠 字串比對 判斷走 Nail handler (脆弱設計)。 future work: 跟 upstream chat.cpp 提 patch, 加明確的 is_nail_template flag 取代字串 sniffing。

10.3 Long-form 中文場景品質優化

longform-zh quality 0.333 是 replay benchmark 最低, 主要是 迴圈偵測 + 結構化 marker 混淆。future work:

  • 收集 longform 失敗 case, 訓練停字 (e.g. <|end|> 強化)
  • prefill 結尾 marker 偵測加更多 case (e.g. 半形句號, 中文句號)
