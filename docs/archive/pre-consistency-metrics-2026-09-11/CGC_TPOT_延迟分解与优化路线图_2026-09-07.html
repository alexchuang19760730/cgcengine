2.1 Expert Cache Hook 细项分解（已实测）

CGC_HOOK_PROFILE instrumentation：steady state 平均 100 µs/次，每 token 40 层 = 4.0 ms/token，占总延迟 10%。

Hook 开销中 80% 可 GPU 化（ids 读取 + union 构建 + EMA + remap 写），只有 ensure_batch（文件 IO）必须保留在 CPU。完整 GPU 化可节省 ~3.2 ms/token，对应 +8-9% 速度提升。这是 P1 GPU slot mapping 的核心收益来源。

6.1 P1 GPU Slot Mapping（完整实现）— 预期 +5-10%

最高优先级 · 预期收益最大
基于 CGC_HOOK_PROFILE 实测：hook 开销 4.0 ms/token（占 10%），其中 80% 可 GPU 化。完整 GPU 化可节省 ~3.2 ms/token，对应 +8-9% 速度提升，保守估计 +5-10%。
实现阶段内容预期收益复杂度风险
阶段 1
GPU 端 remap 生成		新增 Metal kernel kernel_moe_remap_generate；slot_table 只读副本上传 GPU（40KB）；graph 中 top-k 后插入 remap kernel；hook 不再写 remap+3-5%中中
阶段 2
完整 GPU slot mapping		ids 读取 + union 构建 + EMA update 全部移到 GPU；只有 ensure_batch（文件 IO）保留 CPU；消除 hook 的 CPU-GPU 同步+5-10%高高

技术细节

// kernel_moe_remap_generate（Metal）
// 输入：ids tensor [n_expert_used, n_tokens]（top-k 输出）
//       slot_table_gpu [n_layer * n_expert]（只读副本，40KB）
//       layer_index（当前层）
// 输出：remap tensor [n_expert_used, n_tokens]（expert id → slot idx）
kernel void kernel_moe_remap_generate(
    device const int32_t * ids,
    device int32_t * remap,
    constant const int32_t * slot_table_gpu,
    constant int32_t & layer_index,
    constant int32_t & n_expert,
    uint32_t tid [[thread_position_in_grid]]) {
    int32_t expert_id = ids[tid];
    int32_t slot = slot_table_gpu[layer_index * n_expert + expert_id];
    remap[tid] = (slot >= 0) ? slot : 0;  // cold → ZERO-slot
}

slot_table 同步策略：steady state 下 slot_table 更新不频繁（大部分是 hit），可在 ensure_batch 后异步全量拷贝到 GPU（40KB，开销极小）。DBUF hook-time refill 的 bg fill 完成后也需要同步。

Metal prefetch 限制

已确认限制
Metal Shading Language 没有标准 prefetch 函数（prefetch(ptr, read_only, keep_in_cache) 会报 "use of undeclared identifier"）。权重预取需要改用其他方法：
(1) 将当前 block 预取到 threadgroup memory（shared memory），但 Apple GPU threadgroup memory 上限 ~32KB，且循环遍历多个 block 复杂；
(2) 依赖 GPU 硬件 cache（当前广播模式已被 cache 优化）；
(3) 调整 threadgroup 大小提高 occupancy，间接提升 cache 命中率。

7.2 内存带宽物理极限

16GB Mac M4 Max 理论天花板内存带宽公式推导 · 70-94 tok/s 原始上限
28-30 t/s
~10% overhead

物理极限说明：M4 Max 16GB 统一内存带宽 ~100-120 GB/s。Qwen3.6-35B-A3B IQ3_XXS 模型 ~13GB，每 token 激活 ~3B 参数（8/256 experts），对应 ~3-4GB 内存读取。理论上限 = 带宽 / 每 token 字节数 ≈ 100GB/s / 3.5GB ≈ 28.5 t/s。考虑 KV cache、系统开销，实际天花板 ~28-30 t/s。当前 25.17 t/s 已达理论上限的 84-90%，剩余优化空间有限但仍可挖掘。

7.3 32GB 升级路径

如果 16GB 达到瓶颈
32GB Mac 可使用更大的 expert pool（12-16GB），捕获 95-99% 的 routing mass（vs 16GB 8GB pool 的 ~76%），从根本上解决 cold expert 问题。预期速度 30-35 t/s，且品质更稳定。同时可启用 async bg prefetch（更大的 pool 减少 race 风险）。
