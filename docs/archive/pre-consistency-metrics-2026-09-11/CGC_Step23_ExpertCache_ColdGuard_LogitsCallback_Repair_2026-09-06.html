CGC Step-2/3 Expert Cache 修復紀錄

日期: 2026-09-06  |  分支: devserver  |  commit: 9100b0230  |  模型: Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X (ngl=99, MTP n_max=3, 4GB expert cache)

1. 背景 — 想解決什麼

ngl=99 + MTP + denseIQ4X 運行時，短 QA（qa-zh）會出兩種壞輸出：

  • Garbage 0000（早期）： นั่นคือ softmax 崩潰成均勻分佈 → top-k 選出 sequential ids [0,1,2,...] → FFN 讀錯 expert 權重 → logits 歸零。
  • Echo / 迴圈（當前）： 例如輸入「hi」輸出「hi<im_end><im_start>」，或「巴黎是哪個國家的首都？」輸出 3× 重複「巴黎是首都的國家是法國」。

目標是同時達到 品質正確（無 0000、無 echo、無重複迴圈）與 速度 25+ t/s（MTP draft accept 高、fast path 히트率高）。

2. Step-2 實作：Weighted Cold Guard

2.1 原本的問題

原本的 Cold Guard 用 count-based 比率：cold_count / union_size > 0.30 就認為「冷 expert 太多」並摧毁整層 fast path，改走 ensure_batch。同一層裡常有 40/64 個 cold expert，但它們的 softmax 權重可能各只有 0.001 — 這種情況 ZERO-slot 攤平完全無害，不該殺 fast path。反之，若 1-2 個 cold expert 承載大部分權重，count 門檻可能不會 trip 但品質會壞。

2.2 修法

改用 加權冷比率：每層在 logits 評估時讀出 gate logits（F32, [n_expert, n_tokens]），對每個 token 算一次 softmax，再把 冷 expert 的 softmax 權重和 除以 全部權重和，得到 0..1 之間的加權冷比率。只有當這個比率 > 0.30 時才 trip guard；否則即使冷 expert 數量多也繼續走 fast path。

當 guard trip 時，只對 union 裡的 cold expert 做 ensure_batch（選填），而非整層重載。

注意：CGC_WARM_NPAST 從 256 降至 64。原本 256 導致 decode 首步 n_past 通常只有 1~7，永遠進不了 fast path — 整個 decode 都在走 ensure_batch。64 的門檻讓 prefill 餵飽 pool 後的 decode 快速進入 fast path。

3. Step-3 實作：Renormalized Routing 預留

原理：若能在 softmax 之前將冷 expert 的 gate logit 設為 -inf，softmax 會自動在剩下的 hot expert 上重新歸一化。這樣 fast path 幾乎不會 trip（因為冷 expert 不再「佔著算席位卻不貢獻權重」），品質退化也會是「少幾個 active expert 的正常行為」，而非 ZERO-slot 汙染導致的 catastrophc failure。

由於 gate logits 是 F32 張量（IQ3_XXS 等量化模型），可在 logits eval callback 讀取該張量並標記冷 expert。目前僅做 env 閘門 CGC_RN_ROUTING + placeholder，實作留待後續。

4. Logits Eval Callback 診斷（關鍵發現）

4.1 目的

在 expert_cache_eval_cb 裡偵測 ffn_moe_logits 節點（非 ask、F32），透過 ggml_backend_tensor_get 將 GPU 上的 gate logits 同步回 CPU buffer，計算加權冷比率並寫入 cache->cgc_weighted_cold_ratio[il]。上限 il≤1 時輸出 CGC-LOGITS il=%d weighted_cold=%.3f%% 日誌。

4.2 觀察結果

CGC-LOGITS 日誌從未輸出過 — callback 中的 logits 分支完全沒有命中。這表示：

  • expert_cache_eval_cb 有在運作（否則連 CGC-COLD-GUARD 和 CGC-CB: name=... 都不會出現）。
  • ffn_moe_logits 節點沒有進入 callback 的「非 ask 冷比率計算」路徑，或該節點名稱/型別不符合條件（strncmp(t->name, "ffn_moe_logits", 14)==0 && t->type==GGML_TYPE_F32）。
  • 或 OA_ASYNC 分段排程（CGC segmented dispatcher）使得該節點的 eval callback 叉斷/延後，導致 gate logits 張量完成時 callback 已結束。

當前效應：weighted cold ratio 永遠是 1e9（unset），因此 cold guard 永遠 fallback 到 count-based 判斷。step-2 的加權冷比率目前 無效，必須先解決 logits callback 卡住的問題。

5. QA-ZH Echo/Looop 修復嘗試

5.1 修了什麼

  • CGC_WARM_NPAST 256 → 64：讓 decode 更早進入 fast path（減少整層 ensure_batch）。
  • cgc_weighted_cold_ratio 初始化為 1e9（unset 哨兵），避免 cold guard 誤用 0.0 當加權比率。
  • log 格式由 weighted_cold=100000000000.00% 改為 cold=13/16 (81% > 30%)，偵錯可讀性大增。
  • llama.cpp 加入 expert_cache_active DEBUG log，印出 n_gpu_layers / ALLOW_NGL / no_gather 狀態。

5.3 根因分析

Log 顯示 layer 0 IDs 正常多樣，layer 1 雖有 guard trip + ensure_batch，但 layer 2~39 全都產生 [0,1,2,...,7] 順序 IDs。這表示問題不在 layer 1 的冷 expert 處理，而是在 层 2+ 的 gate 輸出本身就崩潰成均勻分佈。

可能原因（尚未確認）：

  1. Gate logits 錯誤：layer 2+ 的 gate 輸出本身就是均勻/接近均勻，導致 top-k 選擇 sequential IDs。
  2. Graph reuse 汙染：重複使用圖時，某些 layer 的 gate 權重指標未重置，沿用前一步的 pool re-pointed 指標（但該 pool slot 已被釋放或寫入錯誤資料）。
  3. OA_ASYNC 張量回收：CGC segmented dispatcher 在 pipeline 中提前回收了 top-k IDs 緩衝區，導致 hook 讀到 iota 序列。

6. 下一步建議

  1. [緊急] 確認 logits callback 為何未觸發：在 expert_cache_eval_cb 最前面加 CGC-CBTRACE il=%d name=%.64s ask=%d 日誌（不管是否 ffn_moe 節點），確認 callback 確實收到 logits 節點，且其型別為 F32。
  2. [緊急] 確認 layer 2+ gate logits 是否真的均勻：在 gate logits callback 讀取後，順便輸出 layer 2+ 的 logits 最大值/最小值/entropy，確認是「真均勻」還是「callback 沒读到」。
  3. [質量] 修復 no-think 模板 + stop token 配置：qa-zh 數字迴圈與 pool path 無關，應單独修模板/抽樣/stop token。
  4. [速度] 解決 OA_ASYNC 張量回收問題：若 logits callback 因 OA_ASYNC 沒触发，需為 gate logits 張量加同步保護。
  5. [架構] 評估 graph reuse 第七次修復：確認 layer 2+ 的 weight tensor 指標是否在每步重置。
