1. 整合目標與設計哲學

1.1 為什麼需要「整合」白皮書

Softpool、Expert Cache、L4 skip-load、V1/V2 是四個獨立的子系統,但在 16GB Mac 的 Metal MTP 部署中,它們必須作為一個整體共同工作才能達到 25+ t/s。單獨優化任一子系統都不夠——例如:

  • Softpool 動態可縮,但如果 Expert Cache 仍然寫死 256 expert 對映,池容量變化就會被忽略
  • L4 skip-load gate 預設 OFF,但若 Expert Cache 沒走 Metal fast path,skip-load 也無從談起
  • V1 hash 守護 pool-fill bit-correctness,但若 L4 採用 zero-copy sub-buffer,sub-buffer alias 邊界就需要 V3 介入

本白皮書的目的,就是把這四個子系統的整合邊界(contract)、共同演化路徑(evolution)、預設行為矩陣(defaults)寫死,避免任何單獨改動破壞整體契約。

1.2 設計哲學: 「解耦 + 契約 + 預設 OFF」

整合的三大原則:

  1. 解耦: Softpool 不知道 Expert Cache 存在,Expert Cache 不知道 L4 skip-load 存在,各自獨立可測
  2. 契約: 子系統之間透過 env var + 結構性欄位(不是 function call)耦合,契約寫進 INVARIANTS_v1.md §5 13 條不變量
  3. 預設 OFF: 所有 gate(V1 verify / V2 oracle / V3 alias check / L4 skip-load)預設關閉,不影響原有功能;只在 CI 與 on-demand A/B 測試中打開

2. Softpool 三層架構: L0/L1/L2 動態可縮

2.1 三層定義

Softpool 把傳統的單一「Expert Cache Pool」拆成三層,各層獨立配置:

層級用途預設容量縮放策略對應欄位
L0 (hot) 當前 batch 命中的 expert 8 experts / layer 剛性 — 必須容納 top-8 routing expert_cache_l0_capacity
L1 (warm) 近期 N 個 token 命中的 expert 32 experts / layer LRU 動態 — Soft shrink expert_cache_l1_capacity
L2 (cold) mmap-backed 持久層 全 256 experts 剛性 — GGUF 預讀 + mmap expert_cache_bytes

2.2 為什麼要拆成三層

單層 Expert Cache 的問題是容量剛性:

  • 256 expert × 60 layer × ~10 MB/expert ≈ 14 GB — 在 16GB Mac 上 OOM 風險高
  • 熱點集中: 統計上 top-8 expert 佔 80%+ 訪問,但單層架構仍然全量分配
  • GC 顆粒度大: 一個 expert evict 觸發整層掃描,decode 階段卡頓明顯

Softpool 三層把這些問題分散到不同時間尺度:

graph LR
  A[Token arrive] --> B[Top-k routing]
  B --> C{L0 hit?}
  C -- Yes --> Z[~0 us]
  C -- No --> D{L1 hit?}
  D -- Yes --> E[Promote to L0
~5 us LRU update]
  D -- No --> F[L2 mmap read
~200 us]
  F --> G[Promote to L1
evict cold L1 entry]
  E --> H[Metal FFN read]
  G --> H
  Z --> H

關鍵設計: L0/L1 都是 Metal-resident(共享 GPU pool 容量),L2 是 mmap-backed(按需 pread)。Metal pool 容量是 expert_cache_l0_capacity + expert_cache_l1_capacity 的總和,透過 env var CGC_SOFT_POOL_L0 / CGC_SOFT_POOL_L1 動態調整。

2.3 環境變數

# L0 容量(剛性,必須容納 top-k routing 全部命中)
CGC_SOFT_POOL_L0=8          # 預設 8 experts / layer

# L1 容量(可縮,LRU 動態,範圍 [16, 64])
CGC_SOFT_POOL_L1=32         # 預設 32 experts / layer

# Softpool 整體開關
CGC_SOFT_POOL=1             # 預設 ON,所有 hook 走 Softpool 路徑
CGC_SOFT_POOL=0             # 完全關閉,退回單層 Expert Cache
注意: 設 CGC_SOFT_POOL_L1=0 等同於關閉 L1 層,所有 warm miss 會直接落到 L2 mmap,decode 速度會掉到 14-18 t/s 區間。建議保持 ≥16。

3. Expert Cache 與 Softpool 對接: Hybrid Slot Table

3.1 為什麼 Expert Cache 不能直接寫死 256 expert

dev branch 的 commit b23fb515e 嘗試零拷貝優化,把 expert tensor 直接指向 Expert Cache 池。但這有兩個問題:

  1. Tensor 形狀硬縮: 256 expert 是 GGUF 定義,一旦縮到 32,後續 MUL_MAT_ID kernel 會 OOB
  2. Slot table 互斥: Softpool 的 LRU 動態 slot 跟 256 expert 固定 slot 互相覆蓋,造成混亂

Hybrid Slot Table 的解法是解耦 Tensor 形狀、Pool 容量、Slot table:

  • Tensor 形狀: 仍為 256 expert(來自 GGUF),不可縮
  • Pool 容量: 由 Softpool 動態決定(預設 L0+L1 = 40 experts)
  • Slot table: 256 entry 的稀疏表,entry[i] = {layer, kind, byte_offset, lru_ts} — entry 為 0 表示「不在池中」

3.2 Hybrid Slot Table 資料結構

// src/llama-expert-cache.h
struct llama_expert_slot {
    int32_t  expert_id;     // 0..255, GGUF 內部 ID
    int32_t  layer;         // 0..59
    int32_t  kind;          // 0=ffn_gate, 1=ffn_up, 2=ffn_down
    int64_t  byte_offset;   // 在池中的 byte 位置
    int64_t  lru_ts;        // LRU 時間戳(用於 Softpool L1 淘汰)
    uint32_t hash;          // V1 verify 用的 SHA-256 摘要(8 bytes 截斷)
};

struct llama_expert_cache {
    llama_expert_slot slots[60 * 256];  // 60 layer × 256 expert
    uint8_t * pool;                     // 池本體,L0+L1 大小
    int64_t  pool_bytes;                // 池 byte 容量
    int64_t  used_bytes;                // 已用 byte
    int32_t  l0_capacity;               // L0 experts / layer
    int32_t  l1_capacity;               // L1 experts / layer
};

3.3 對接關鍵: adopt_pool_region

在 L4 Metal fast path 中,Expert Cache 透過 llama_expert_cache_adopt_pool_region 直接採用每個 expert tensor 的 Metal storage 作為該 layer 的 pool region(zero copy)。Metal FFN 從 pool 直接讀,無需先 pread 到 host memory 再 upload 到 GPU。

// src/llama.cpp
if (model->expert_cache_pool_capacity > 0) {
    for (const auto & ref : ml.l4_pool_tensors) {
        if (ref.tensor == nullptr || ref.tensor->data == nullptr) continue;
        llama_expert_cache_adopt_pool_region(model->expert_cache,
            ref.layer, ref.kind, (const uint8_t *) ref.tensor->data,
            (int64_t) model->expert_cache_pool_capacity, ref.expert_bytes);
    }
}

這裡 ref.expert_bytes 對應 Softpool 的 pool capacity,動態可縮。當 Softpool L1 因 LRU 縮小,會觸發 llama_expert_cache_resize_pool,把所有 entry 重新計算 byte_offset(但 Tensor 形狀仍為 256 expert,這是關鍵解耦點)。

4. L4 Skip-Load Gate: Metal Fast Path 的精準切片

4.1 設計動機

16GB Mac 的物理天花板是 16GB Unified Memory。Expert Cache 全量(256 expert × 60 layer × 10MB ≈ 14GB)會 OOM 整個系統,連 model weight + KV cache 都放不下。

L4 skip-load 的策略是: 放棄「先 load 全部 expert 再 cache」,改為「load 預算範圍內的 expert,其他走 mmap」。這需要在 loader 階段就決定哪些 expert 要實際 load tensor,哪些只記下 GGUF offset 留待 mmap。

4.2 Gate 邏輯: llama.cpp line 358-367

// src/llama.cpp (line 358-367)
// CGC: L4 skip-load gate — expert tensors stay on CPU (bounded residency). Same gate as
// expert_cache_active below: -ngl>0 only enables it with the explicit ALLOW_NGL override.
const char * no_gather = getenv("LLAMA_EXPERT_CACHE_NOGATHER");
ml.expert_cache_skip_load = (params.n_gpu_layers <= 0 || getenv("LLAMA_EXPERT_CACHE_ALLOW_NGL")) && !(no_gather && no_gather[0]);
model->expert_cache_skip_load = ml.expert_cache_skip_load;

// CGC expert-cache L4: bounded Metal pool, only on the Metal path (-ngl > 0 + ALLOW_NGL).
ml.expert_cache_l4_skip_layer0 = getenv("LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0") != nullptr;
const bool l4_path = params.n_gpu_layers > 0 && getenv("LLAMA_EXPERT_CACHE_ALLOW_NGL") && !(no_gather && no_gather[0]);
if (l4_path) {
    ml.compute_l4_pool_capacity();
    model->expert_cache_pool_capacity = ml.expert_cache_pool_capacity;
}

四個 env var 控制 L4 path:

Env Var作用預設
LLAMA_EXPERT_CACHE_ALLOW_NGL 允許在 -ngl > 0 時啟用 expert cache(預設只允許 -ngl = 0) OFF
LLAMA_EXPERT_CACHE_NOGATHER 完全關閉 expert cache(包括 hook + gather) OFF
LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0 L4 path 中額外跳過 layer 0 的 expert pool(只用 mmap) OFF
LLAMA_EXPERT_CACHE_PIN_PROFILE 靜態 pin 一個 profile 檔,讓特定 expert 永久 resident OFF

4.3 為什麼預設需要 ALLOW_NGL 顯式打開

在 production(-ngl = 99, 全 GPU)環境下啟用 Expert Cache 是雙刃劍:

  • 好處: 把 expert tensor 從 host 拉到 Metal pool,FFN 計算 zero copy
  • 風險: Metal pool 容量若算錯,會 OOM 整個 process,連 Q4 model weight 都救不回來

預設 OFF + 顯式打開的設計哲學是「讓 production 配置主動承擔風險,而不是默認承擔」。A/B 對照實驗會用 ALLOW_NGL=1 確認效果後,才寫進 production script。

4.4 L4 Skip-Load 與 Softpool 的互動

L4 skip-load 決定哪些 expert tensor 會實際 load 到 memory,Softpool 決定loaded expert 在 Metal pool 中怎麼分層。兩者協同:

  1. L4 skip-load 計算 pool capacity(透過 compute_l4_pool_capacity 掃 GGUF metadata)
  2. Softpool 從 pool capacity 分配 L0(剛性) + L1(LRU 動態)
  3. loader 把預算範圍內的 expert tensor 預讀到 pool,超過範圍的只記 GGUF offset
  4. runtime 訪問超出預算的 expert 時,走 L2 mmap + promote 到 L1
flowchart TB
  A[compute_l4_pool_capacity] --> B[pool_capacity bytes]
  B --> C[Softpool: L0 + L1 = pool_capacity]
  C --> D{Loader 階段}
  D -- expert in budget --> E[pread to Metal pool]
  D -- expert over budget --> F[僅記 GGUF offset]
  E --> G[Expert Cache init: adopt_pool_region]
  F --> H[L2 mmap backed]
  G --> I[Runtime: hit / promote / LRU]
  H --> I

5. V1 Hash + V2 Logits Oracle 整合守護鏈

5.1 V1 vs V2 互補邊界

兩個守護機制覆蓋不同的失效面,不能互相替代:

機制守護邊界能抓到抓不到
V1 hash Pool-fill 階段: expert 進池時 byte 級驗證 loader 寫入錯誤 / GGUF 損壞 / Tensor 排列錯誤 runtime aliasing / Metal buffer 重疊
V2 logits oracle 端到端: 整個 forward pass 的 logits 跟 reference 對 任何引入 logits 偏差的 bug(包含 aliasing) 性能退化 / 邊界 case 不一致
V3 sub-buffer alias(設計階段) Metal subBufferWithOffset:length: 視圖層 V1 漏掉的 runtime aliasing (不適用 — V3 設計在 V1/V2 之間)

5.2 V1 Pool-fill Hash Verify

在 llama-expert-cache.cpp 的 cgc_exact_cache_verify_post_fill 中,每個 expert 進池後立刻算 SHA-256(8 bytes 截斷),存入 slot.hash。對照組是直接從 GGUF 讀取的 expert bytes 算同樣 hash。差異即代表 cache 與 GGUF 不一致。

// src/llama-expert-cache.cpp
void cgc_exact_cache_verify_post_fill(llama_expert_cache * cache, int layer, int expert_id) {
    if (getenv("CGC_EXACT_CACHE_VERIFY") == nullptr) return;  // 預設 OFF
    const uint8_t * gguf_bytes = load_gguf_expert_raw(layer, expert_id);
    const uint8_t * pool_bytes = cache->slots[layer * 256 + expert_id].data;
    uint32_t gguf_hash = sha256_8(gguf_bytes, expert_bytes);
    uint32_t pool_hash = sha256_8(pool_bytes, expert_bytes);
    if (gguf_hash != pool_hash) {
        LLAMA_LOG_ERROR("CGC V1 FAIL: layer=%d expert=%d gguf_hash=%08x pool_hash=%08x\n",
            layer, expert_id, gguf_hash, pool_hash);
    }
}

預設 OFF 是因為 SHA-256 計算在 14GB 全 cache 場景下要 ~200ms,會把 baseline 速度從 25 t/s 拖到 18 t/s。只在 CI / on-demand A/B 中打開。

5.3 V2 Logits Oracle (FNV-1a 64-bit)

V2 透過 cgc_logits_oracle_dump 把 forward pass 的 logits 雜湊成 FNV-1a 64-bit,寫進 JSONL:

// src/llama-context.cpp
void cgc_logits_oracle_dump(llama_context * ctx, int n_tokens) {
    if (getenv("CGC_LOGITS_ORACLE_DUMP") == nullptr) return;  // 預設 OFF
    const float * logits = llama_get_logits(ctx);
    uint64_t h = 0xcbf29ce484222325ULL;  // FNV-1a offset basis
    for (int i = 0; i < n_tokens * n_vocab; i++) {
        h ^= *(uint32_t *)&logits[i];
        h *= 0x100000001b3ULL;  // FNV prime
    }
    FILE * f = fopen(getenv("CGC_LOGITS_ORACLE_DUMP"), "a");
    fprintf(f, "{\"prompt_hash\":\"%s\",\"logits_h\":\"%016llx\",\"n\":%d}\n",
        current_prompt_hash(), h, n_tokens);
    fclose(f);
}

A/B 對照: 同一 prompt,Softpool ON vs OFF,兩份 JSONL 用 cgc_logits_oracle_compare.py 比對,所有 logit hash 都必須相同。

7. 整合驗證: A/B 對照實驗設計

7.1 5 組 A/B 對照

每組都跑 3 profile(qa-zh / longform-zh / coding),每 profile 3 trials,取中位數:

組別A 配置B 配置預期差異守護機制
1. Softpool ON vs OFF CGC_SOFT_POOL=1 L0=8 L1=32 CGC_SOFT_POOL=0(回 256 硬縮) Softpool 應 +5-10% V2 oracle 必須 logit-equal
2. L4 path ON vs OFF ALLOW_NGL=1 ALLOW_NGL=0(預設) L4 應 +30% V1 hash 必須 bit-equal
3. L4_SKIP_LAYER0 ON vs OFF ALLOW_NGL=1 L4_SKIP_LAYER0=1 ALLOW_NGL=1 L4_SKIP_LAYER0=0 影響 memory 但 t/s 接近 V1 hash layer 0 應為 miss(預期)
4. PIN_PROFILE ON vs OFF PIN_PROFILE=./top8.profile PIN_PROFILE=(unset) 影響 warmup latency V1 hash pinned experts 必須 bit-equal
5. V1 hash ON vs OFF CGC_EXACT_CACHE_VERIFY=1 CGC_EXACT_CACHE_VERIFY=0 V1 ON 應 -30% t/s(overhead) V1 必須 PASS(0 fail)

7.2 對照實驗守護鏈

守護鏈: A/B 對照不能只看 t/s 數字,必須搭配 V1/V2 一起跑,確認效能差異不是來自 bit-level 退化。
  1. A 配置: 跑 3 profile × 3 trials,同時打開 V1+V2,記錄 logit hash + slot hash
  2. B 配置: 同樣跑,記錄
  3. 比對:
    • V1: A 的 slot hash 必須 bit-equal B 的 slot hash(說明沒有 bit 變化)
    • V2: A 的 logit hash 必須 bit-equal B 的 logit hash(說明 forward 結果一致)
    • t/s: 差異 = 純效能差,不是 bit drift
  4. 如果 V1/V2 出現不一致,即使 t/s 變好也視為退化(禁止合併)

8. 已知邊界與後續 Roadmap

8.1 已知邊界

  1. V3 sub-buffer alias check 尚未實作: V1 + V2 已上線,V3 處於設計階段(見 CGC_EXPERT_CACHE_SOFTPOOL_WHITE_PAPER §5.4)
  2. 16GB Mac OOM 風險: L4 path 在 32GB+ 設備安全,16GB 設備仍可能 OOM,需透過 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0 + 調小 L0/L1 緩解
  3. 16GB 物理天花板: 即便把所有 gate 開到最優,MTP 接受率 ~27.9% 是物理上限,decode 不可能超過 ~30 t/s
  4. profile dispatch 仍需改進: 目前 longform-zh 的 prefill 結尾 marker 偵測(v6 fix)仍有 ~5% 漏判
