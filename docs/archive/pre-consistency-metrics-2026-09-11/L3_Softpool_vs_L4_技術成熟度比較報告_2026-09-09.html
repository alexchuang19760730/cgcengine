L3 Softpool vs L4 Skip-Load 技術成熟度比較報告

基於 flashkv0516 (dev 分支) 與 flashkv-devserver (demo/sweet-spot-windows-fix 分支) 的源碼、文件、Git 歷史與測試覆蓋分析

報告日期: 2026-09-09 分析範圍: flashkv0516 + flashkv-devserver 分支: dev (83c47b1) / demo/sweet-spot (51c8ac1) 分析者: Emodibrain

1. 執行摘要

核心結論:
  • L3 Softpool（三層動態可縮池）成熟度較高：代碼完整、文件體系完善、有不變量契約、已進入生產預設配置（L0=48/L1=48），並通過 7-profile replay 基線驗證。
  • L4 Skip-Load（Metal Fast Path 精準切片）成熟度中等：核心邏輯已實現（compute_l4_pool_capacity + adopt_pool_region），但預設 OFF、無專屬單元測試、16GB 設備 OOM 風險未解、文件依附於 Softpool 白皮書而非獨立文件。
  • 兩者是上下游協同關係而非競爭：L4 決定「哪些 expert 實際 load 到 memory」，L3 決定「loaded expert 在 Metal pool 中如何分層管理」。L4 是 L3 的前置條件。

2. 技術定位與協同關係

2.1 兩個技術的定義

維度L3 Softpool（三層動態可縮池）L4 Skip-Load（Metal Fast Path 精準切片）
核心問題 已 load 的 expert 權重在 GPU pool 中如何分層、淘汰、動態縮容 哪些 expert tensor 需要實際 load 到 memory，哪些只記 GGUF offset 走 mmap
作用層級 運行時（runtime）— cache 管理層 加載時（loader）— 模型加載層
關鍵數據結構 soft_pool_l0 / soft_pool_l1 / LRU slot table expert_cache_pool_capacity / expert_cache_skip_load / l4_pool_tensors
核心函數 cgc_soft_pool_tier() / LRU evict / promote compute_l4_pool_capacity() / llama_expert_cache_adopt_pool_region()
預設狀態 ON L0=48, L1=48 (devserver 分支) OFF 需 LLAMA_EXPERT_CACHE_ALLOW_NGL=1
性能收益 省 27% 內存，維持 decode 速度；命中率 L0 85%+ / L1 12% Metal zero-copy FFN，理論 +30% t/s；但 16GB OOM 風險

4.2 環境變數與配置

# L4 Skip-Load 配置 (全部預設 OFF)
LLAMA_EXPERT_CACHE_ALLOW_NGL=1     # 允許 ngl>0 啟用 expert cache (核心開關)
LLAMA_EXPERT_CACHE_NOGATHER=1      # 完全關閉 expert cache (debug 用)
LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=1  # L4 中跳過 layer 0 (省 ~250MB)
LLAMA_EXPERT_CACHE_PIN_PROFILE=./top8.profile  # 靜態 pin 特定 expert

# 啟動 L4 path 的必要條件 (全部滿足才啟用):
#   1. params.n_gpu_layers > 0
#   2. LLAMA_EXPERT_CACHE_ALLOW_NGL 已設置
#   3. LLAMA_EXPERT_CACHE_NOGATHER 未設置或為空
為什麼預設 OFF? 在 production (-ngl=99, 全 GPU) 環境啟用 Expert Cache 是雙刃劍：好處是 zero-copy FFN，風險是 Metal pool 容量若算錯會 OOM 整個 process。設計哲學是「讓 production 配置主動承擔風險，而不是默認承擔」。

8. 建議與 Roadmap

8.1 L3 Softpool 後續建議（短期，1-2 週）

  1. 補 L0/L1 分層單元測試: 在 test-expert-cache.cpp 中增加 soft_pool_l0=0 / l1=0 / 邊界值的測試 case，確保 clamp 和退化路徑正確。
  2. V3 sub-buffer alias check 實作: 按照白皮書 §5.4 的設計，在 ggml-metal.metal 的 subBuffer alloc 點插入 trace hook，實作 reverse-lookup SHA-256 驗證。
  3. Softpool 容量自動調優: 根據當前 batch 的 expert 訪問分佈，動態調整 L0/L1 比例，而不是固定 48/48。

8.2 L4 Skip-Load 後續建議（中期，1-2 月）

  1. 補 L4 專屬單元測試: 創建 test-expert-cache-l4.cpp，覆蓋 compute_l4_pool_capacity、adopt_pool_region、L4_SKIP_LAYER0 等邊界。
  2. 納入 Replay 基線: 在 replay benchmark 中增加 L4 path 的 profile (ALLOW_NGL=1)，與 baseline 對比，確保 L4 改動不會 regression。
  3. 16GB OOM 自動檢測: 在 compute_l4_pool_capacity 中增加物理內存檢查，如果 pool_capacity > 可用內存的 70%，自動降級到 L4_SKIP_LAYER0 或關閉 L4。
  4. 撰寫 L4 獨立白皮書: 將 L4 內容從 Softpool 白皮書中抽出，成為獨立文件，涵蓋設計動機、gate 邏輯、zero-copy 機制、OOM 風險、配置矩陣。
  5. L4 CI workflow: 創建 .github/workflows/cgc-l4-metal-test.yml，在 self-hosted macOS runner 上跑 L4 path 的 smoke test。

9. 結論

L3 Softpool: 生產可用級別 (TRL 7-8)

L3 Softpool 已經從實驗階段進入生產預設配置，具備完整的代碼實現、完善的文件體系、不變量契約、雙層 bit-correctness 守護（V1+V2）、pre-commit gate 和 CI 整合。7-profile replay benchmark 驗證了 L0=48/L1=48 的「甜蜜點」配置，品質全 1.0 且速度最優。剩餘工作主要是補單元測試和實作 V3。

L4 Skip-Load: 實驗驗證級別 (TRL 4-5)

L4 Skip-Load 的核心邏輯（compute_l4_pool_capacity + adopt_pool_region zero-copy）已經實現，但仍處於「需顯式開啟」的實驗階段。主要瓶頸是：(1) 16GB 設備 OOM 風險未解；(2) 完全沒有自動化測試；(3) 未納入 replay 基線和 CI；(4) V3 sub-buffer alias check 尚未實作，Metal view 層存在盲點。建議在 32GB+ 設備上先做小範圍生產驗證，同時補齊測試和文件後再考慮預設開啟。

協同建議:

L3 和 L4 是上下游協同關係，L4 是 L3 的前置條件。當前 L3 已經成熟，但 L4 尚未解鎖，導致 L3 的 Metal pool 能力沒有完全發揮（L3 管理的是 CPU mmap 路徑的 cache，而不是 L4 zero-copy 的 Metal pool）。建議優先推進 L4 的測試覆蓋和 OOM 風險控制，一旦 L4 在 32GB+ 設備上穩定，L3+L4 組合可以釋放完整的 Metal fast path 性能潛力（理論 decode 30+ t/s）。
