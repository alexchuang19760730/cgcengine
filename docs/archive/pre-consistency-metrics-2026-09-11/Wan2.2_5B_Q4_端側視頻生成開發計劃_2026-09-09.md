# Wan 2.2 TI2V-5B Q4 端側視頻生成開發計劃

> 版本：v1.1  
> 日期：2026-09-09  
> 目標：在 16GB 端側設備上實現 Wan 2.2 5B Q4 流暢視頻生成體驗，並封裝為消費級爆款產品

---

## 一、項目概述

### 1.1 背景

Wan 2.2 是阿里開源的開放式視頻生成模型，採用 MoE（Mixture of Experts）架構，總參數 27B，每步活躍 14B。其中 TI2V-5B 版本活躍參數僅 5B，適合端側部署。

當前社區已有在 RTX 3060/4060 等消費級 GPU 上成功運行的案例，但在 Mac Apple Silicon 上體驗較差（MPS backend 優化不足），且普遍缺乏針對 MoE 架構的內存優化。

本項目基於 CGC Expert Cache 技術積累，目標是在 16GB 端側設備上實現流暢的 Wan 2.2 5B 視頻生成體驗。

### 1.2 目標

| 指標 | 目標值 | 說明 |
|------|--------|------|
| 模型 | Wan 2.2 TI2V-5B GGUF Q4_K_M | 文本生成視頻 + 圖像生成視頻統一模型 |
| 分辨率 | 480p（832×480 / 480×832） | 兼容橫屏和豎屏 |
| 時長 | 5 秒（81 幀 @16fps） | 標準短視頻長度 |
| 模型加載時間 | ≤ 20 秒 | 從啟動到可接受請求 |
| 生成時間 | 30-60 秒 | 採樣去噪階段 |
| VAE 解碼時間 | ≤ 10 秒 | 潛空間解碼到像素 |
| 總體驗時間 | 1-1.5 分鐘 | 從點擊生成到拿到視頻 |
| 內存佔用 | ≤ 14GB | 留 2GB 給系統和其他程序 |
| 穩定性 | 連續生成 10 次無 OOM | 長時間運行穩定 |

### 1.3 範圍

**包含**：
- Wan 2.2 TI2V-5B GGUF Q4 模型端側部署
- 基於 ComfyUI 的快速落地驗證
- 針對 MoE 架構的內存優化（Expert Cache 遷移）
- Mac Apple Silicon 和 NVIDIA 雙平台支持
- 生成質量和速度基準測試

**不包含**：
- 模型訓練或微調
- 14B 版本支持（後續階段考慮）
- 實時視頻生成（20+ FPS，當前架構不現實）
- 雲端部署和服務化

## 二、產品目標與爆款戰略

### 2.1 產品定位

**核心定位**：本地端側 AI 視頻生成工具——"免費、隱私、離線、無限生成"的消費級產品。

**對比雲端的核心差異化賣點**：

| 賣點 | 端側 Wan 2.2 5B | 雲端（Runway/Pika/可靈） |
|------|-----------------|------------------------|
| **成本** | 幾乎免費（只有電費） | $0.1-0.5 / 5秒視頻，100條 = $10-50 |
| **隱私** | 照片/視頻絕不上傳 | 內容上傳到服務器，有隱私風險 |
| **離線** | 沒網也能用 | 必須聯網 |
| **生成額度** | 無限，想生成多少生成多少 | 有額度限制，超過要付費 |
| **排隊等待** | 不用排隊，本地即點即生成 | 高峰期排隊幾分鐘到幾十分鐘 |
| **可定制** | 本地 LoRA、風格微調、自己訓練 | 只能用官方提供的風格 |

**關鍵洞察**：視頻生成的成本優勢是壓倒性的——雲端生成 100 個視頻要 $10-50，端側只要電費。而 LLM 編碼的雲端成本已經低到可以忽略（$0.001/次），端側沒有成本優勢。這是視頻生成比 LLM 更適合端側的核心原因。

### 2.2 對比端側 LLM 的體驗本質差異

| 維度 | Qwen 3.6 A3B 編碼（16 t/s） | Wan 2.2 5B 視頻生成（1-1.5 分鐘/5秒） |
|------|---------------------------|---------------------------------------|
| **交互模式** | 實時流式輸出，用戶盯著每個 token | 異步批量生成，用戶點完按鈕去做別的事 |
| **等待感知** | 每一秒都在等，16 t/s 寫 100 行代碼要 30+ 秒，全程盯著 | 1.5 分鐘裡用戶可以切去看微信、喝咖啡，回來視頻就好了 |
| **體驗閾值** | LLM 需要 ≥40 t/s 才"流暢"，16 t/s 是明顯的"卡" | 視頻生成的心理預期就是"等幾分鐘"，1.5 分鐘反而比雲端的 30 秒-2 分鐘差不多 |
| **容錯率** | 編碼錯一個 token 可能整個函數邏輯錯了，用戶對延遲和錯誤都敏感 | 視頻有點瑕疵用戶反而覺得"AI 生成的正常"，容錯率高 |

**結論**：16 t/s 的 LLM 是**"實時交互場景下的卡頓"**，而 1.5 分鐘的視頻生成是**"異步任務的合理等待"**。兩者的用戶心理預期完全不同——視頻生成的體驗已經跨過了"可用"門檻，而 16 t/s 的 LLM 還在門檻下面掙扎。

### 2.3 目標用戶畫像

#### 核心目標用戶（P0）

**1. 自媒體創作者**
- 每天要發 5-10 條短視頻，雲端成本高（每月 $100-500）
- 需要快速生成素材草稿，不用排隊等雲端
- 對質量要求：能發朋友圈/小紅書/抖音即可，480p 夠用
- 付費意願：高（已經在付雲端費用，端側免費是強吸引力）

**2. 電商小賣家**
- 商品圖轉視頻，批量生成（幾十上百個 SKU）
- 雲端批量生成成本極高，端側幾乎免費
- 對質量要求：展示商品細節即可，不需要電影級質量
- 付費意願：高（直接降低運營成本）

**3. 隱私敏感用戶**
- 個人照片動起來、家庭視頻生成，絕對不上傳
- 包括：家長（孩子照片）、公眾人物、企業內部內容
- 對質量要求：中等，隱私是第一考慮
- 付費意願：中高（為隱私付費）

#### 次要目標用戶（P1）

**4. 技術愛好者 / 數字藝術家**
- "我在自己電腦上跑大模型"的炫耀需求
- 喜歡折騰 LoRA、風格微調、各種參數
- 對質量要求：高，願意花時間調參
- 付費意願：中（願意為高級功能付費）

**5. 離線場景用戶**
- 飛機上、網絡差的地方、偏遠地區
- 需要離線也能生成內容
- 對質量要求：中等，能生成就行
- 付費意願：中

#### 非目標用戶（不優先考慮）

- 追求極致質量的專業影視製作（用雲端 Sora/Runway，4K/長視頻）
- 一次性嘗鮮用戶（用雲端免費額度就夠了，不會裝本地軟件）
- 手機用戶（端側 PC 軟件，不是 APP）

### 2.4 爆款三要素分析

#### 要素一：體驗超過"可用閾值" ✅ 基本滿足

```
視頻生成的"可用閾值"：
- 5 秒視頻 ≤ 3 分鐘 → 可用
- 質量達到"能發朋友圈/小紅書"水平 → 可用
- 不會經常 OOM/崩潰 → 可用

Wan 2.2 5B Q4 在 16GB 上：
- 1-1.5 分鐘/5秒 → ✅ 遠超閾值
- 480p 質量 → ✅ 社交媒體夠用
- 穩定性 → ⚠️ 需要優化，但可達

對比 LLM 16 t/s：
- 編碼體驗"可用閾值"是 ≥30 t/s
- 16 t/s → ❌ 低於閾值，明顯卡頓
```

#### 要素二：相比雲端有不可替代的差異化價值 ⚠️ 部分滿足

| 差異化維度 | 端側視頻生成 | 端側 LLM 編碼 |
|-----------|------------|-------------|
| **成本** | 5秒視頻雲端 $0.1-0.5，端側幾乎免費 → 差異大 | LLM 雲端 $0.001/次，成本差異小 |
| **隱私** | 個人照片/視頻不上雲 → 強需求 | 代碼/文檔隱私 → 有需求但沒那麼強 |
| **離線** | 網絡差也能用 → 有場景 | 離線寫代碼 → 小眾需求 |
| **速度** | 端側 1.5 分鐘 vs 雲端 30秒-2分鐘 → 差不多 | 端側 16 t/s vs 雲端 100+ t/s → 雲端碾壓 |
| **可定制** | 本地 LoRA、風格微調 → 有價值 | 本地代碼庫索引 → 有價值 |

#### 要素三：有社交傳播性和"哇哦"時刻 ✅ 滿足

```
LLM 編碼的"哇哦"時刻：
- "AI 幫我寫了個函數" → 已經不稀奇了，2023 年就有了
- 傳播性低，大家都見過了

視頻生成的"哇哦"時刻：
- "我輸入一句話，它生成了一段會動的視頻！" → 對普通消費者仍然很新奇
- 生成結果本身就是可分享的內容（視頻比文字更有傳播力）
- "我在自己電腦上跑的，沒花錢" → 額外的炫耀點
```

### 2.5 產品化封裝路線圖

技術可用 ≠ 消費者爆款。當前 ComfyUI 的安裝和使用門檻太高，普通消費者看到就放棄了。產品化封裝是 0 到 1 的關鍵。

#### Phase A：技術驗證階段（對應開發計劃 Phase 1-2）
- 目標：在 16GB 設備上跑通，達到性能指標
- 用戶：技術愛好者、開發者
- 界面：ComfyUI 節點圖（技術用戶能接受）
- 交付：可運行的工作流 + 優化配置

#### Phase B：簡化封裝階段（新增，Phase 2.5）
- 目標：把 ComfyUI 複雜的節點圖封裝成"輸入文字→點擊生成→拿到視頻"的簡單流程
- 用戶：進階用戶、內容創作者
- 界面：簡化的 Web UI（基於 ComfyUI API，隱藏節點圖）
- 關鍵功能：
  - 一鍵安裝程序（自動裝 Python、ComfyUI、依賴、模型）
  - 預設工作流（用戶不用自己連節點）
  - 模型自動下載（檢測硬件，自動選擇合適的量化版本）
  - 進度條 + 預覽（實時顯示生成進度）
  - 歷史記錄（之前生成的視頻方便查看和重用）

#### Phase C：消費級產品階段（新增，Phase 4）
- 目標：做成"剪映級"的消費級產品，普通用戶打開就能用
- 用戶：大眾消費者
- 界面：原生桌面應用（Mac .app / Windows .exe），不是網頁
- 關鍵功能：
  - 極簡界面：一個輸入框 + 一個生成按鈕 + 一個預覽窗口
  - 高質量 Prompt 模板庫（"電影質感"、"卡通風格"、"寫實風格"等，用戶不用自己寫 prompt）
  - 一鍵 Prompt 優化（用戶寫大白話，自動轉成高質量 prompt）
  - 智能硬件檢測（自動檢測內存/GPU，選擇最優配置，不用用戶懂參數）
  - 一鍵分享到社交媒體
  - 自動更新（模型和軟件自動更新，用戶無感知）
  - 付費高級功能：去水印、更高分辨率、更長視頻、專用 LoRA 商店

### 2.6 產品層面成功標準

#### 技術指標（必須達成）

## 三、技術選型

### 3.1 核心框架

| 組件 | 選擇 | 理由 |
|------|------|------|
| 推理框架 | **ComfyUI** | 社區生態成熟，Wan 2.2 支持完善，快速驗證 |
| 模型格式 | **GGUF Q4_K_M** | 體積小（~3.5GB），跨平台一致，llama.cpp 生態支持 |
| GGUF 加載 | **ComfyUI-GGUF 節點** | 原生支持 GGUF 格式的擴散模型 |
| 採樣器 | **Euler / DPM++ 2M Karras** | 速度和質量平衡，20-25 步足夠 |
| VAE | **Wan 2.2 官方 VAE** | 與模型匹配，解碼質量好 |
| Text Encoder | **UMT5-XXL（offload）** | 只在開始用一次，用完卸載到 CPU |

### 3.2 硬件平台

| 平台 | 最低配置 | 推薦配置 | 優先級 |
|------|---------|---------|--------|
| NVIDIA | RTX 4060 8GB | RTX 4060 Ti 16GB | P0（社區成熟） |
| Apple Silicon | M2 16GB | M4 Pro/Max 24GB+ | P0（重點優化） |
| AMD | RX 7600 8GB | RX 7800 XT 16GB | P2（後續考慮） |

### 3.3 自定義優化組件（可選，後續階段）

| 組件 | 說明 | 階段 |
|------|------|------|
| CGC Expert Cache for DiT | 將 LLM Expert Cache 技術遷移到擴散模型 | Phase 3 |
| Metal 優化 Kernel | 針對 Mac MPS 的自定義 Metal kernel | Phase 3 |
| 進度可視化 UI | 實時顯示生成進度和預覽 | Phase 2 |

### 4.3 生成流程

```
用戶點擊生成
    │
    ▼
[1] 模型加載（~20秒）
    ├─ 加載 DiT Q4 模型到 GPU（~5秒）
    ├─ 加載 VAE 到 GPU（~2秒）
    ├─ 預熱 GPU kernel（~3秒）
    └─ 顯示"就緒"狀態
    │
    ▼
[2] 文本編碼（~3秒）
    ├─ Text Encoder 加載到 CPU（~2秒）
    ├─ 編碼 prompt → text embeddings（~1秒）
    └─ 卸載 Text Encoder，釋放內存
    │
    ▼
[3] 潛空間初始化（~1秒）
    ├─ 生成隨機噪聲（81幀 × 4通道 × 空間維度）
    └─ 準備時間步編碼
    │
    ▼
[4] 擴散去噪（~30-60秒，核心階段）
    │
    ├─ 階段 A：早期去噪（步 1-8，~10-20秒）
    │   └─ 用 Expert Group A（構圖專家）
    │
    ├─ 階段 B：中期去噪（步 9-17，~12-24秒）
    │   └─ 用 Expert Group B（細化專家）
    │
    └─ 階段 C：後期去噪（步 18-25，~8-16秒）
        └─ 用 Expert Group C（細節專家）
    │
    ▼
[5] VAE 解碼（~10秒）
    ├─ 潛空間特徵 → 像素空間
    ├─ 分批解碼（避免內存峰值）
    └─ 輸出幀序列
    │
    ▼
[6] 視頻編碼（~2秒）
    ├─ 幀序列 → MP4/H.264
    └─ 保存到本地
    │
    ▼
完成，總計 1-1.5 分鐘
```

**2.1 內存優化細節**：
```
Text Encoder offload：

  - 不保存中間激活值，需要時重新計算

│ DPM++ SDE      │ 測試 │ 測試 │ 測試 │ 測試 │
│ Heun           │ 測試 │ 測試 │ 測試 │ 測試 │

```

| 3.6 Mac Metal 適配 | 針對 Apple Silicon 的 Metal kernel 優化 | 24h | P2 |

#### 關鍵技術挑戰

**Wan 2.2 MoE 與 LLM MoE 的差異**：
```
LLM MoE（如 Qwen）：
  - 每個 token 動態選擇 top-k expert
  - 路由在層間變化大，局部性中等（~60-70%）
  - Expert Cache 命中率受限

Wan 2.2 MoE：
  - 按去噪時間步分組（早期/中期/後期）
  - 同一階段的所有步用同一組 expert
  - 路由在階段內幾乎不變，局部性極高（~95%+）
  - Expert Cache 命中率可以做到接近 100%
```

**Expert Cache 對擴散模型的價值**：
```
無 Expert Cache：
  - 每個階段開始時加載該組 expert（~2-5秒）
  - 3 個階段總共加載 3 次（~6-15秒）
  - 加載開銷分攤到每幀：~0.1-0.3秒/幀

有 Expert Cache：
  - 首次生成時加載所有 expert 到 cache pool
  - 後續所有步零加載（cache hit）
  - 連續生成多個視頻時，第二次起零加載
  - 預計加速：首幀 -30%，連續生成 -50%
```

- [ ] 連續生成第二個視頻的加載時間 ≤ 5 秒
- [ ] 內存佔用不增加（Cache pool 從預留緩衝中分配）

## 六、關鍵技術難點和解決方案

### 6.1 Mac MPS 性能優化

**問題**：Mac 上 MPS backend 對 MoE 擴散模型優化不足，速度比同級 NVIDIA 慢 2-5 倍。

**解決方案**：
1. **短期**：使用 ComfyUI 的 MPS 優化配置，關閉不兼容特性
2. **中期**：針對瓶頸操作編寫自定義 Metal kernel
3. **長期**：考慮使用 llama.cpp 的 Metal 後端（如果支持擴散模型）

**風險**：MPS backend 更新頻繁，可能引入新的兼容性問題。需要跟進 PyTorch 版本更新。

### 6.2 內存碎片管理

**問題**：長時間運行後，GPU 內存碎片導致即使有足夠空間也無法分配大張量。

**解決方案**：
1. 使用內存池（memory pool）管理大張量分配
2. 定期調用 `torch.cuda.empty_cache()` / `torch.mps.empty_cache()`
3. 復用中間緩衝區，避免頻繁分配釋放
4. 生成結束後完整釋放並重新加載模型（如果內存碎片嚴重）

### 6.3 質量與速度的平衡

**問題**：減少去噪步數會加快速度，但可能降低質量。

**解決方案**：
1. 建立質量評估基準（10 個測試 prompt，主觀評分 + 指標評估）
2. 系統測試不同採樣器/步數組合
3. 找到"質量 cliff"（質量急劇下降的步數閾值），在 cliff 之上選擇最快的配置
4. 提供"快速/平衡/高質量"三檔預設，讓用戶選擇

### 6.4 MoE Expert 加載時機

**問題**：Wan 2.2 的 MoE 按時間步分組，何時加載哪組 expert 需要精確控制。

**解決方案**：
1. 分析官方模型的路由機制，確定每個時間步對應的 expert group
2. 在採樣循環中提前 1-2 步預加載下一組 expert（流水線）
3. 使用雙緩衝（double buffering）：當前組計算的同時加載下一組
4. Expert Cache 常駐所有 expert，避免運行時加載

### B. 關鍵配置參數

```yaml
# 基礎配置
model: wan2.2-ti2v-5b-q4_k_m.gguf
resolution: [832, 480]  # [寬, 高]
frames: 81
fps: 16
steps: 20
sampler: dpmpp_2m_karras
cfg_scale: 6.0
seed: -1  # 隨機

# 內存優化
text_encoder_offload: true
vae_tiling: true
vae_tile_size: [27, 32, 32]  # [幀, 高, 寬]
activation_checkpointing: false  # 內存不足時啟用

# Mac MPS 優化
force_mps: true
mps_high_watermark_ratio: 0.8
use_fp16: true
torch_compile: false
```
