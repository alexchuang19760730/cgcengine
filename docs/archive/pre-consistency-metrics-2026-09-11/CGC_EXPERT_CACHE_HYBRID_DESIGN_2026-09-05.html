TL;DR: 把「shrink」從 tensor 形狀層 (ne[2]) 上移到 pool 容量層。三層完全解耦:
  • Tensor 形狀永遠 256 (不可變,保留 mul_mat_id 邏輯形狀)

1. 核心洞察: 把「shrink」從 tensor 形狀層移到 pool 容量層

2.2 三層定義

🟢 L0 GPU Hot Tier

容量 (預設): 32 slot (top-32 hot)
內存: ~2GB resident (Metal pool)
命中率: 85%+
替換策略: 無 (固定 hot)
失誤路徑: → L1

🟡 L1 GPU Warm Tier

容量 (預設): 32 slot (LRU)
內存: ~2GB resident (Metal pool)
命中率: 12%
替換策略: LRU evict → L2
失誤路徑: → L2

🟣 L2 CPU Cold Tier

容量 (預設): 256 expert 完整
內存: ~12.5GB unified mmap
命中率: 100%
替換策略: LRU mmap hint
失誤路徑: → ZERO-slot (最後手段)

2.2.2 實作對應 (2026-09-05 commit 範圍: 階段 1)

本節對應 §4.1 階段 1「Soft Pool Capacity 環境變數」, 記錄實際 commit 的程式碼改動。其他階段 (LRU Eviction / L2 CPU Cold Fallback) 留待後續 commit。

1) 環境變數讀取 (llama-expert-cache.h)

新增 inline 函式 cgc_soft_pool_tier(env_name, fallback):

  • 讀 getenv(env_name), 缺省或空字串 → fallback
  • 解析為 long, 負值 → 0
  • 上限 clamp 256 (避免誤設超大值)
static inline uint32_t cgc_soft_pool_tier(const char * env_name, uint32_t fallback) {
    const char * env = getenv(env_name);
    if (env == nullptr || env[0] == '\0') return fallback;
    long v = atol(env);
    if (v < 0) return 0;
    return (uint32_t) std::min<long>(v, 256);
}

2) Cache 結構體欄位 (llama-expert-cache.h)

llama_expert_cache 新增 2 個 uint32_t 欄位:

  • soft_pool_l0: L0 固定 hot slot 數 (預設 32)
  • soft_pool_l1: L1 LRU warm slot 數 (預設 32)
  • soft_pool_l0 + soft_pool_l1 <= slots_l(layer), 超過則按比例 clamp
  • L0 + L1 = 0 表示未啟用 partition, 走 legacy uniform n_slots 行為 (byte-identical)

3) Init 邏輯 (llama-expert-cache.cpp)

在 slot_table.assign(...) 之後:

  1. 讀 CGC_SOFT_POOL_L0 / CGC_SOFT_POOL_L1 (各 fallback 32)
  2. 若 L0 + L1 > n_slots → 按比例 clamp 並 stderr warning
  3. 若 L0 + L1 = 0 → 走 legacy 行為
  4. 寫入 cache->soft_pool_{l0,l1} 供 runtime introspection
CGC Soft Pool init: L0=<n> L1=<n> (n_slots=<n>, partition <active|disabled>)

4) 當前未實作 (留待後續 commit)

  • ❌ pick_slot L0/L1 分割邏輯 (階段 2 LRU Eviction)
    • 目前 pick_slot 仍走 legacy n_slots 邏輯, L0/L1 欄位僅作 introspection
    • 行為: 若預設 32/32, runtime 跟 legacy 87 slot 略不同 (slot 數變少)
    • 預期影響: pool 容量從 87 縮到 64, cold rate 略升但仍 < 5%
  • ❌ L1 LRU evict 標記 -2 區分 (階段 2)
  • ❌ L2 mmap fallback (階段 3)
  • ❌ L0 hot set 自動學習 (階段 4)

5) 驗證清單 (本 commit 範圍)

  • ✅ CGC_SOFT_POOL_L0=32 CGC_SOFT_POOL_L1=32 (預設) → init log 顯示 partition active
  • ✅ CGC_SOFT_POOL_L0=0 CGC_SOFT_POOL_L1=0 → init log 顯示 partition disabled, 走 legacy 87 slot 邏輯
  • ✅ CGC_SOFT_POOL_L0=9999 (oversize) → clamp 到 256, 不超過 n_slots
  • ✅ CGC_SOFT_POOL_L0=-1 (負值) → fallback 0
  • ✅ 不指定 env → fallback 32/32

2.3 Slot Table 動態演進 (取代固定 ZERO-slot)

graph LR
  subgraph "傳統 devserver slot table"
    A1[hot: st e = 0..n_slots-1]
    A2[cold: st e = -1
固定 ZERO-slot]
  end

  subgraph "Hybrid slot table"
    B1[hot: st e = 0..l0_size-1
L0 固定 hot, 不 evict]
    B2[warm: st e = l0_size..l0_size+l1_size-1
L1 LRU]
    B3[cold: st e = -1
ZERO-slot 仍是 last resort]
    B4[evicted: st e = -2

  end
Slot 值傳統 devserverHybrid 提案差異
0..n_slots-1 hot L0 hot (0..l0_size-1, 永不 evict) 分層
-1 (cold) ZERO-slot 固定 ZERO-slot + L2 mmap hint 新增 L2 fallback
-2 (evicted) 不支援 L2 mmap 仍可 fallback 新增 evict 機制
關鍵差異: L1 用 LRU evict, 不是固定 ZERO-slot。Evicted slot 可從 L2 mmap 重新拉回 (犧牲速度但保正確), 而不是固定讀 ZERO-slot (犧牲正確性)。

4.1 階段 1: Soft Pool Capacity 環境變數 (低風險)

  • 新增 CGC_SOFT_POOL_L0 / CGC_SOFT_POOL_L1 env vars
  • 預設沿用現有 87 slot 邏輯 (L0=87, L1=0)
  • 改 llama_expert_cache_slots_per_layer_l 邏輯支援 L0/L1 split
  • 預期: 行為 0 變化, 只多開關

4.2 階段 2: LRU Eviction 機制 (中風險)

  • slot_owner[il][e] 加 LRU timestamp
  • llama_expert_cache_touch 同時更新 timestamp
  • llama_expert_cache_ensure_batch 滿載時 evict LRU
  • Evicted slot 標記為 -2 (cold 路由可走 L2 fallback)
  • 預期: 內存省 27%, fast path 仍 24+ t/s

4.3 階段 3: L2 CPU Cold Fallback (高風險, 但選用)

  • 新增 llama_expert_cache_fetch_l2(cache, il, e) 從 L2 mmap 拉單個 expert
  • L1 miss 且 slot=-2 時觸發
  • 同步載入 slot + 寫 remap
  • 預期: cold 場景語意 100% 對, 但 fetch 慢 (1-2ms per expert)
  • 可選: 透過 CGC_L2_FALLBACK=0 關閉, 退回 ZERO-slot (速度優先)

4.4 階段 4: L0 Hot Set 自動學習 (進階)

  • 用 LLAMA_EXPERT_CACHE_ROUTE_RECORD=1 收集 route frequency
  • 啟動時跑 calibration (前 10 step) 統計 top-32 hot
  • 寫入 slot_owner[il][e] 為 fixed hot, 永不 evict
  • 預期: warm gate 之後 cold rate 從 65% 降到 ~20%

9.2 驗證 Gates (V1 + V2, 預設全 OFF)

V1 — Pool-fill 雜湊比對 (驗證 §5 Exact Cache 不變量 I1)

位置: llama-expert-cache.cpp::cgc_exact_cache_verify_post_fill

Env var預設Clamp用途
CGC_EXACT_CACHE_VERIFY OFF 設 1 開啟 fill 後 byte-by-byte 對比 fresh-fd 讀到的 GGUF bytes

  • Hook 位置: process_ubatch return res; 之前 (line 1614 附近)
  • 函式內部自己 scan graph 找 logits tensor (F32, ne[0] >= 1024, ne[1] == n_tokens)
  • 零拷貝設計: static FILE * 只在第一次呼叫時 fopen, 後續直接寫入

CI gate (建議) 預設 =1 FIRST_N=10 跑短 prompt 任何 mismatch 立刻 abort

9.4 與其他 CGC env 變數共存

Env var用途與 V1/V2 互動
CGC_NO_PREWARM 停用 hot prewarm 獨立, 不影響 V1/V2
CGC_NO_PREFETCH 停用 bg prefetch 獨立, 不影響 V1/V2
CGC_PREFETCH_SRC prefetch 來源 (step/prev/hist) 獨立, 不影響 V1/V2
CGC_L2_FALLBACK 啟用 L2 CPU fallback 獨立, 不影響 V1/V2
CGC_WARM_NPAST warm gate N past 獨立, 不影響 V1/V2
CGC_TENSOR_DUMP 中間 tensor dump (既有機制) 與 V2 並行, dump 目標不同
CGC_PHASE_TIMING decode 階段計時 與 V2 並行, 開銷獨立
CGC_BYPASS_POOL_FROM 跳過 pool 從某 layer 起 V1 仍驗, V2 仍 dump (但 logits 必偏)
設計守護: 任何新加的 CGC env 都必須遵守「預設 OFF, 不設不影響原行為」。這是 §5 Exact Cache 不變量的延伸 — 觀察手段不污染生產路徑。
