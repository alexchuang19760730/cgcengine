1.1 動態 slot table (256 → 87 對映,無 0000 風險)

核心實作: expert_cache_on_topk (llama-context.cpp:3033-3360)

  • 256 expert 永遠有效: hparams.n_expert = 256 從未被縮
  • slot_table[il][e] 動態記錄每個 expert 對應的 pool slot
    • hot (在 pool 內): 0..n_slots-1
    • cold (不在 pool): -1 → 指向 ZERO-slot (zeroed 過的固定槽)
  • 跟 dev branch 不同: devserver 不修改 ne[2],tensor 仍是 256 expert 完整形狀
關鍵設計: 把「專家是否在池中」這個事實,從 tensor 形狀層(ne[2])移到 slot table 層(sparse lookup)。Tensor 形狀永遠 256,mul_mat_id kernel 邏輯永遠有效。

  • Warm gate (CGC_WARM_NPAST=256): prefill 餵飽 pool 前走 ensure_batch,餵飽後走 fast path
  • Fast path 只 touch + zero slot, 不做 pread, 所以 65% cold 仍能 26+ t/s
  • Cold 走 ZERO-slot (固定 0 權重槽),但 softmax 吸收 < 1/3 cold 不影響 routing

1.4 Layer 0 Identity Remap (L4_SKIP_LAYER0)

核心實作: llama-context.cpp:3158-3169

  • blk.0 是 full-weight CPU skip-load tensor,不走 pool
  • 寫原始 expert ID (identity) → mul_mat_id 讀原始 tensor 完整 256 expert
  • 關閉此 remap 會 OOM Layer 0(全 256 expert 預讀到 Metal pool ≈ 700MB)

2.1 Root cause (522428cdc / 1afedfa68 共同根因)

dev branch 的pool 設計缺陷:

  • Pool 是 zero-copy (adopt from tensor buffer),repointing 是 no-op
  • 載入時把 tensor ne[2] 從 256 縮到 87 (pool capacity)
  • Expert >= 87 直接 OOB 或被當 slot 0 (零權重)
  • 結果: layer 2+ uniform routing [0 1 2 3 4 5 6 7] → 0000 garbage

2.2 Dev branch 修法 (1afedfa68 核心)

llama-context.cpp (line 3659 改前 / 3611 改後):

// 改前 (dev branch 嘗試保留 pool)
if (!pool_active || model.expert_cache_skip_load) {
    identity_remap();  // CPU fallback
}

// 改後 (1afedfa68 修法)
if (model.expert_cache_skip_load) {
    identity_remap();  // 永遠 identity, 不走 pool
}

也就是: 完全不走 pool,所有 expert 從 CPU 原 tensor (ne[2]=256) 讀。語意 100% 對,但速度掉到 5.5 t/s。

2.3 為什麼 dev branch 5.5 t/s (不是 26+)

xychart-beta
  title "decode 速度對比 (t/s)"
  x-axis ["prod-25ts", "devserver (Hybrid)", "dev branch (1afedfa68)"]
  y-axis "t/s" 0 --> 30
  bar [25.29, 26.5, 5.5]
  • 放棄 4GB GPU pool,所有 expert 走 CPU
  • 16GB Mac 上 256 expert 完整大小 = ~12.5GB (over unified memory budget)
  • 強制 unified memory CPU path,沒有 pread 預熱
  • 結果: 5.5 t/s — 是 devserver 的 1/4.7

2.4 為什麼 dev branch 還能正確輸出

  • Identity remap (real expert IDs 0..255) 讓 mul_mat_id 從原始 tensor 找
  • Metal 透過 unified memory 讀 CPU tensor (慢但對)
  • 所有 41 層 256 expert 都能路由,gate logits 不退化
權衡取捨: dev branch 用速度換 100% 語意正確性。我們的策略是相反: 用條件性正確性換 26+ t/s。兩者不可直接合併。

核心矛盾:
  • dev branch 的「正確性 fix」是「放棄 pool 換 100% 對」
  • devserver 的「速度」是「保留 pool 換 26+ t/s,接受條件性 0000 風險」
  • 兩者不可直接合併 —— 一個互斥的 if 條件

4.2 ✅ 1afedfa68 的 n_ubatch bump (llama-context.cpp:436-449) - 可採納 10 min

// [CGC FIX 2026-09-05] when the L4 cap pushes n_batch (and therefore n_ubatch) below
// n_keep_tail=n_rs_seq+1, llama-batch split_equal asserts. Keep n_ubatch at least
// n_keep_tail+1 so the warmup / seq_rm probe / decode steps do not abort.
const uint32_t n_keep_tail = cparams.n_rs_seq > 0 ? cparams.n_rs_seq + 1u : 0u;
if (n_keep_tail > 0 && cparams.n_ubatch <= n_keep_tail) {
    LLAMA_LOG_WARN("%s: n_ubatch=%u bumped to n_keep_tail+1=%u (MTP recurrent)\n",
            __func__, cparams.n_ubatch, n_keep_tail + 1u);
    cparams.n_ubatch = n_keep_tail + 1u;
}
  • 不衝突: 是 llama_context 建構子的獨立 patch,跟 pool / expert cache 路徑無關
  • 防呆: 防止 split_equal assertion crash (MTP 場景下 n_rs_seq 推 n_keep_tail)
  • 採納動作: 手動複製這段到 devserver 的 llama-context.cpp 建構子
