# 品質歸因測試方案 — 量化 vs 我們修改 vs 模型本質

> 日期：2026-09-09
> 背景：48 題裸問官方 ~48/48 vs 本地 IQ3_XXS 17/48，需釐清問題根源

## 核心假設

**IQ3_XXS 單層誤差小，但 MoE 路由對 logits 精度極敏感：**
- Dense 模型：量化誤差逐層平滑衰減，40 層後可控
- MoE 模型：量化誤差影響 top-k 路由決策，選錯 expert = 整層算錯
- 後續層基於 garbage 計算 → 誤差不是線性累積，是跳變放大
- 帶拐杖（prefill/pp/stop）掩蓋了這個效應，裸問才完全暴露

## 關鍵對比與歸因邏輯

```
B 組是分水嶺：
  B ≈ 40+/48  → 量化本身沒問題，問題在我們的修改（看 C/D vs B）
  B ≈ 17/48   → 量化/引擎是主因，我們修改可能是背鍋（看 E vs B）

E vs B（同引擎同代碼，只換量化）：
  E >> B      → 確認 IQ3_XXS 量化誤差累積問題，升 IQ4_XS 可解
  E ≈ B       → 量化不是瓶頸，問題在引擎或我們修改

C vs B（expert cache 加載但全 exact）：
  C << B      → expert cache 加載本身就有問題（即使不用 fast path）
  C ≈ B       → expert cache 加載是乾淨的

D vs C（fast path 的增量影響）：
  D << C      → 我們的 fast path（ZERO-slot/speculative）引入品質問題
  D ≈ C       → fast path 是乾淨的

F vs E（高精度下我們修改是否安全）：
  F ≈ E       → 我們的修改在高精度下安全
  F << E      → 我們的修改本身有問題，與量化無關
```

## 注意事項

1. **每次更換配置必須重啟 server**，不能熱切換
2. **裸問測試不要帶 --warmup**，warmup 會預熱 expert pool 掩蓋冷啟動問題
3. **temp=0 是必須的**，否則採樣隨機性會引入噪聲
4. **每組跑 2-3 次取平均值**，特別是邊界題目可能有波動
5. **關注失敗模式**：空輸出 / echo / fence loop / 重複片語，不同模式指向不同根因
6. **IQ4_XS 模型 17GB，16GB 機器可能需要調整 ngl 或 ctx**

## 失敗模式對照表

| 失敗模式 | 可能根因 |
|---------|---------|
| 空輸出（content=null） | thinking 行為未關閉 / max_tokens 被 thinking 吃光 |
| echo（重複 prompt） | 首 token 採樣偏移 / chat template 問題 |
| fence loop（``` 無限循環） | 量化誤差導致路由漂移 / stop 未生效 |
| 重複片語（≥6字×3次） | logits 邊界問題 / DRY 未生效 |
| 完全亂碼 / 0000 | expert 加載錯誤 / cross-backend garbage |
| 答非所問但語句通順 | 路由選錯 expert，但輸出本身語法正確 |
