2. b23fb515e — feat(expert-cache): L4 zero-copy Metal pool + CGC segmented async dispatch

2026-08-20 · llama.cpp-master/... · 改 6 檔案 +369 lines

核心改動

  • L4 bounded-residency (Metal zero-copy pool):
    • llama-model-loader: compute_l4_pool_capacity 掃 GGUF metadata, shrink expert tensors ne[2] 到 bounded pool capacity (256 → 87),存在 normal Metal buft 上,storage IS the pool region。
    • full expert count 保留給 L1 index,但 Tensor 形狀永久改變。
    • llama.cpp: gate L4 path (-ngl>0 + ALLOW_NGL),adopt 每個 expert tensor 的 Metal storage 作為 per-layer pool region (zero copy)。
    • LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0: blk.0 留 CPU (pool exclusion fix)。
  • CGC segmented async dispatch (ggml-backend):
    • CGC_OA_ASYNC: split Metal graphs at ffn_moe_topk nodes, pipeline 一個 segment ahead (submit seg[i+1] before waiting seg[i])。
    • poll non-blocking completion via ggml_metal_get_cgc_done, fire expert-cache hook on CPU path, GPU never drains。
    • ROUTER_CPU pinning 保持 topk chain 在 CPU split → hook fires there (hit rate 70%+, file_reads=0)。
  • Perf instrumentation (env-gated, zero default change):
    • simple.cpp CGC_STEP_TIMING
    • llama-context.cpp CGC_PHASE_TIMING
    • llama-sampler.cpp CGC_SAMPLER_DBG
    • metal CGC_METAL_DBG / CGC_TAIL_DBG

為什麼跟 devserver 互斥

  1. 違反 Exact Cache 原則: shrink Tensor ne[2] 永久改變模型形狀, 從 pool 讀出來的權重 byte 不等於直接從 GGUF 讀的 byte。
  2. 跟 devserver 動態 slot table 互斥: devserver 假設 expert 數量 (256) 在所有 expert cache 操作期間保持不變,mul_mat_id 邏輯靠 ne[2]=256 來找 topk experts。硬縮後 mul_mat_id 找專家時 index 越界。
  3. 16GB Mac OOM: 256 expert pool 需 12.5GB GPU memory, 16GB Mac 跑了 13GB model 後只剩 3GB → OOM。
  4. 5.5 t/s CPU 瓶頸: 之前 bulk-merge 過此 commit,實際跑出 5.5 t/s (CPU identity remap 走 ggml_metal_get_cgc_done polling 太慢)。

決策

禁制 不單獨 cherry-pick、不 bulk-merge。Hybrid 方案 (180f161df) 走「soft pool env vars + 保留 Tensor 形狀」路線取代此 commit。

3. 522428cdc — fix(expert-cache): identity remap for ngl=99 + embedded GGUF template

2026-09-05 00:41 · Author: alex_chuang

Root cause (0000 bug)

expert cache pool shrink ne[2] from 256 to 87 slots,但 model 仍有 256 experts。 當 gate route 到 expert >= 87,map 到 slot 0 (zero weights) → uniform gate logits → sequential IDs → garbage output。

修法 (resident passthrough §7.3.5)

  • Model loader: 當 expert_cache_skip_load=true 時, expert tensors 留 CPU, ne[2]=256 (不 shrink)。Skip L4 pool capacity computation。
  • Graph build: 當 skip_load=true 時 skip FFN weight repointing 到 pool regions。
  • Eval hook: 強制 identity remap (real expert IDs 0..255),bypass pool path。 所有 41 layers 都得到 diverse gate routing。

Embedded GGUF template fix

  • Remove default Nail-Qwen3.6-Minimal-Chat.jinja template override
  • Remove default --skip-chat-parsing flag
  • Server uses GGUF-embedded ChatML template (<|im_start|>/im_end)
  • Code generation 修好

結果

  • Quality: ZH Q&A ✅, Code ✅, Math ✅ (all expert IDs diverse at all layers)
  • Speed: ~3.4 t/s (CPU bandwidth bound)
  • 16GB Mac: 需要 12.5GB 給 256-expert pool on GPU,OOM 風險

跟 devserver 衝突

這個 commit 假設 skip_load=true 場景 (ngl=99 = 強制走 CPU path), 跟 devserver 預設 ngl=99 + skip_load=0 (走 GPU pool path) 完全不同。 整合到 devserver 會把 26+ t/s 的 GPU path 打成 3-5 t/s 的 CPU path。

5. 83c47b137 — fix(mtp): resolve conflicting -c flags in MTP command line

2026-09-05 04:02 · Author: alex_chuang

Root cause

當 MTP enabled, MTP_ARG 已包含 -c $MTP_CTX (3072)。 CTX_ARG 也傳 -c $CTX (0 from default),造成兩個競爭的 -c flags。雖然第二個 -c 3072 會覆蓋 -c 0, 但這種混亂會在某些 configuration 造成 garbled output。

修法

當 MTP active 時 skip CTX_ARG,因為 MTP_ARG 已經處理 context size。

跟 expert cache 無關

純 CLI flag 處理,沒碰 expert cache / MTP model 邏輯。整合風險低。

驗證

  • MTP + ngl=99 + denseIQ4X: correct output
  • Speed: ~2.7 t/s (CPU resident path on 16GB Mac)
  • Accept rate: 37.5%
  • Hit rate: 92.6%

決策

todo 22b 候選 唯一可單獨整合的 commit。devserver 之前 cherry-pick + 立即 revert (因為同時把 binary dylib 一起帶進來 → hook 衝突 + binary 版本 mismatch)。單純 source-level 整合風險低,但需要驗證 MTP CLI 不再衝突。
