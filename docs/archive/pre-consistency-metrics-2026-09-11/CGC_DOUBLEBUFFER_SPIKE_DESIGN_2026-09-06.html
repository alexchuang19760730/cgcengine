Scheme 1 Double-Buffer Spike — 設計文件（基於已 mapping 的 sync 模型）

日期：2026-09-06 ・ 目標：在 16GB Mac + MTP + denseIQ4X 上把 decode 從 8GB default 的 ~11–22 t/s 推回 25+ t/s 且品質 = baseline（1.0/0.882/1.0）。

1. 已確認的 Sync 模型（spike 的 ground truth）

核心結論：「每層 hook = GPU idle 窗口」已經存在且被 blocking ensure_batch 使用。Swift SpAc 依賴的「跨 command buffer 的 async fill 窗口」在 llama.cpp MTP 路徑不存在 —— 但層間窗口存在。double-buffer 的價值是把「hook 內 blocking 等 pread」改成「fill 提早寫 scratch、hook 只做 µs 級 pointer swap」。

2. 為何現況慢（guard trip = blocking）

  • decode 時每層 hook 檢查 cold：cold → ensure_batch 同步等 slot 資料從 disk (pread) 落地 → GPU idle 等 host → decode t/s 掉。
  • 8GB pool（K≈142）下 cold 少，但「每 token 真正 top-8 全 resident」仍非 100%；重複 token 的冷 expert 一 miss 就 block 整個層。
  • 先前實證：拔 CGC_NO_PREFETCH=1 直接開 bg prefetch → MTP+OA_ASYNC 下 decode 中段崩潰（bg fill 寫 active buffer 撞 GPU 讀）。

3. Spike 設計（最小、gated、單一 pool 驗證）

不一次改 41 層。先用 1–2 層（例如 il=5,6）驗證機制，成功再全開。

3.1 Slot 資料路徑已釐清（spike step 0 完成 — 2026-09-06）

實體模型（已讀碼確認）：L4 zero-copy pool 不是「每 slot 一段 heap buffer」，而是每個 (layer, kind) expert tensor 的 Metal storage 本身就是 pool region（loader 以 ne[2] = capacity 建立，adopt_pool_region 收編；llama-model-loader.cpp:1269-1277）。slot = region 內固定 stride 的一段；graph 的 mul_mat_id 以 remap leaf（每層 hook 寫入的 expert id）索引。Cold expert 的「ensure」= pread 直接寫進該 slot region。

由此得到的 double-buffer 形態（比原估算便宜）：不需要 2× pool（8→16GB 會 OOM）。正確形態是 bounded scratch ring：每層維持 K≈142 active slots + 小型 scratch ring（8–16 slot/層 ≈ +0.5–1GB），fill worker 只寫 scratch；swap 時把「內容已到」的 scratch slot 與該 expert 的舊 active slot 交換（slot_table[e] 翻轉 + remap leaf 重寫），舊 active 變 scratch。swap 點 = 每層 hook（GPU idle、seg i+1 未 submit），天然 race-free。這正是 Swift turbo-fieldfare async diff swap（bounded maxSwaps）的對應物。

崩潰根因對策：上次 bg-prefetch crash = fill 寫入 in-flight seg 正在讀的 active slot。scratch ring 讓 fill 永遠不碰 active；swap 只在層 hook（該層 GPU 已 idle）做 → 兩條件皆消除。

3.2 機制（若為 slot 描述符模型）

  • Scratch set：每 slot 加第二份 storage 描述符（同大小，L4 zero-copy 下為「開窗描述符」非實體複製）。
  • Fill 目標：bg fill worker（現有 8 threads）只寫 scratch 描述符指向的 buffer，永不碰 active。
  • Swap 點：每層 hook（GPU idle）內、submit seg i+1 前，對「該層 scratch 已 ready」的 slot 做 active↔scratch 原子換（host 指標 swap，µs 級），再寫 remap。
  • 誰決定填哪層哪個 expert：MTP draft ctx 的 routing（免費 look-ahead，已 commit 的 SpAc feed 有 draft 來源）+ EMA utility top-K；在 decode step N 的層 hook 時把 step N+1..N+3 的預測 expert 丟給 fill queue。
  • Gate：CGC_DBUF=1（default OFF = 現況 8GB default 品質/speed 完全不動）。

3.3 崩潰風險對策（上次 bg-prefetch crash 的教訓）

  • fill 只寫 scratch（GPU 永不讀 scratch）→ 不可能 race active。
  • swap 只在層 hook 的 GPU-idle 窗口做 → 不可能撞 in-flight command buffer。
  • swap 超時/未 ready → 該 slot 維持現況（fall back 現有 guard 路徑），不 block。

5. 成功判準（spike 驗收）

  1. 1–2 層 spike：decode 不崩、無 0000、telemetry 顯示「swap 成功次數 / miss 次數」。
  2. 單層 cold-step 比例下降（冷 guard trip 從 sync-fill 變成 swap-ready）。
  3. 品質 3-profile = baseline（reference rules, warmup, seed 0）。
  4. decode t/s 上升（若 1–2 層就明顯，代表 fill-window 假設成立，可全開）。

6. 決策點

此 spike 是 16GB 上「25+ 且品質達標」剩餘唯一可行路線（exclusion-renorm 已實證判死）。現有 8GB default baseline 已 commit 且穩定（1.0/0.882/1.0, 11–22 t/s），spike 全程 gated-off，不影響 default。

7. Spike 實作 + 量測結果（2026-09-06 完成）

實作內容（全數 CGC_DBUF=1 gated，default OFF = byte-identical）：

  • Hook-time step-ahead refill（llama-context.cpp fast-path block, verify ctx only）：把本 step 被 ZERO-map 的 cold union members 透過 prefetch_slot 排入 bg fill，讓下一步 resident。安全模型：hook 在 GPU 層間 idle 執行、seg il+1 只讀 union slots、prefetch_slot 的 LRU victim 必為 non-union、slot_table 在 bytes 落地後才 publish。
  • EMA-aware eviction（prefetch_slot, CGC_SPAC=1 時啟用）：victim 改選 spac_util 最低者（tie→LRU），static pins 最後才 yield。修掉 pure-LRU 在長 generation 的 churn（量測：DBUF+LRU 使 longform/coding 退化）。
  • Queue cap（CGC_DBUF_CAP 預設 24）：early-decode cold burst（12/layer × 41 layers ≈ 500）會把 bg queue 塞爆（pread ~1-3ms > step window），late layers 的 fill 永遠 in-flight → 下一步剛好 ZERO-map 正在補的 expert。

Spike 判決

  1. 「層 hook 的 async step-ahead fill」在 MTP+OA_ASYNC 下可行且 crash-free（這是先前 B-section bg-fill 崩潰的結構性修復，也是 25+ 路徑的必要地基）。
  2. 品質仍被 ZERO-fallback 殘餘冷專家綁住：fast path 對「正在補但未 publish 的 expert」與「被 DBUF evict 的 recurring expert」仍會 ZERO-map → 每 token 分佈微扭曲 → IQ3_XXS 下放大成 repetition。8GB default（decode 完全不 evict、冷由 guard→exact 處理）品質最穩。
  3. 要讓 DBUF 過品質閘需要：(a) 機器環境乾淨（無 memory pressure）重測；(b) 或 pool 大到 steady-state cold ≈ 0（10GB+，16GB 邊緣）；(c) 或 ZERO-fallback 對「loading 中且將 resident」的 expert 改為短等而非 ZERO（小改）。

程式碼全部 gated（CGC_DBUF），default 行為 byte-identical；保留作 25+ 路線的 crash-free 地基，環境乾淨後可直接重測。
