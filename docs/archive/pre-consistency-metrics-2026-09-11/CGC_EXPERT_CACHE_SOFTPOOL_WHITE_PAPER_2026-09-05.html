2. 背景: dev branch vs devserver 性能差距分析

2.1 問題根源: Tensor 形狀硬縮 vs 三層解耦

Dev branch 522428cdc / 1afedfa68 採用「靜態 ne[2] 硬縮 256→87」換取 100% 語意正確性, 但代價是:

  • 5.5 t/s: CPU resident bottleneck (identity remap path)
  • 直接放棄 GPU pool: 走 CPU path
  • 跟 devserver 動態 slot table 機制完全互斥: 256→87 對映 + ZERO-slot 路由 + MTP fast path 都被破壞

Devserver 想借鏡的是 dev branch 的內存效率概念, 但不能直接移植它的實作方式 (tensor 形狀硬縮)。 本白皮書提出一個解耦的 hybrid 方案:

  • Tensor 形狀永遠 256 (不動 ne[2], 保留 mul_mat_id 邏輯形狀)
  • Pool 容量動態可縮 (soft shrink, 借鑒 dev branch 內存效率)
  • 動態 slot table 保留 (256→N 對映 + LRU evict, 取代固定 ZERO-slot)
  • Cold 路由可選 ZERO-slot 或 L2 CPU fallback (兼得速度 + 正確性)

2.2 27.6% MTP 接受率 vs 27.9% 的物理上限

27.9% 是無 MTP/Cache 且 IQ2 的基準, 與 IQ3 + MTP 場景不可比; 當前 27.6% 是 IQ3 + MTP 下的實測, 接受率瓶頸在 CPU identity remap path, 修復後應能突破 30%+。

4. Softpool 設計: L0/L1 動態可縮池

4.1 三層定義

層容量 (預設)內存命中率替換策略失誤路徑
L0 GPU Hot32 slot (top-32 hot)~2GB resident85%+無 (固定 hot)→ L1
L1 GPU Warm32 slot (LRU)~2GB resident12%LRU evict → L2→ L2
L2 CPU Cold256 expert 完整~12.5GB unified mmap100%LRU mmap hint→ ZERO-slot (最後手段)

4.2 環境變數配置

# 預設配置: 64 slot (L0=32 + L1=32), 比原 87 省 27% 內存
CGC_SOFT_POOL_L0=32 CGC_SOFT_POOL_L1=32

# 適合長尾: 全 L1 LRU
CGC_SOFT_POOL_L0=0 CGC_SOFT_POOL_L1=64

# 極限: 關閉 soft pool, 走 dev branch 風格 L2 + ZERO-slot
CGC_SOFT_POOL=0
安全閥: 預設值 32+32 是根據 16GB Mac 物理上限 + 12.5GB L2 mmap 共同推導; 任意一項設為 0 表示關閉該層 (走 fallback), 設為負數或超大值會 clamp 到 [0, 256]。

5. Bit-Correctness 守護: V1 (Hash) + V2 (Logits Oracle) + V3 (Sub-buffer Alias)

核心原則: 預設 OFF zero cost on production 只在 CI / debug / bit-flip 排查時開啟。

5.1 V1: Pool-fill Hash Verify

觸發: CGC_EXACT_CACHE_VERIFY=1
實作: src/llama.cpp/src/llama-expert-cache.cpp
機制: Soft Pool / L0 / L1 fill 完成後, 用獨立 fd 重讀 GGUF raw bytes 跟 pool 內 bytes 做 SHA-256 比對, 不一致就 FATAL abort 避免 bit-flip 上線。

捕捉三類 §5 不變量違規:

  • (a) 錯誤的 file_offset 算術 (ensure_batch / pick_slot)
  • (b) 錯誤的 dst 指針 (fill_segments_pool)
  • (c) 跨層 file_offset aliasing

CGC_EXACT_CACHE_VERIFY_FIRST_N (預設 256) 控制每次 fill batch 驗證的 segment 數上限 — 驗證器 是 O(bytes), ngl=99 完整 offload 下會 dominate decode 速度, 所以後續 batch 是 sample-bounded, 第一個 batch 一定全驗證, 確保單一 rogue segment 能快速被抓出來。

5.2 V2: Logits Oracle (FNV-1a 64-bit)

觸發: CGC_LOGITS_ORACLE_DUMP=path/to/oracle.jsonl
實作: src/llama.cpp/src/llama-context.cpp (cgc_logits_oracle_dump)
機制: 每個 decode step 把 logits 做 FNV-1a 64-bit 雜湊 + top-N 記錄成 JSONL。 

// JSONL 每行一個 (step, token_idx) tuple
{
  "step": 42,
  "token_idx": 0,
  "n_vocab": 152064,
  "logits_fnv1a64": "0x9e3b1c4d2a5f8e7b",     // 完整 logits 雜湊
  "row_fnv1a64":    "0x1f8a3b2c5d9e4f7a",     // per-row 雜湊 (for partial match)
  "argmax_token":   12345,
  "sum":            -234.5,
  "top": [12345, 678, 9012, ...]               // top-N token id
}

5.3 工具鏈: cgc_logits_oracle_compare.py

開啟 Soft Pool A/B 比較前, dump 兩份 (control vs treatment) 用 scripts/check/cgc_logits_oracle_compare.py 對齊 (step, token_idx) 比:

  • row_fnv1a64: per-row 雜湊 (per-token 一致性)
  • logits_fnv1a64: 完整 logits 雜湊 (整體 bit-level)
  • argmax_token: 預測 token id (語意正確性)
  • top-N: top-K token 排名 (機率分佈穩定性)

100% 一致才算 bit-correct。

A/B 結果: V1+V2 都開啟 vs 都不開 vs 只 V2, 三條件 × 三 profile (qa-zh / longform-zh / coding) 共 9 組測試, V2 oracle dump 2433/2433 (100%) bit-level 一致, delta < 0.91 t/s (< 4%) 都在 dylib noise floor 內。

5.4 V3: Sub-buffer Aliasing Check (Metal-only, 設計階段)

V1 守護「storage 內部 byte」, V2 守護「最終計算 logits」, 但兩者之間 有一層「view 對映」是盲點 — 也就是 Metal MTLBuffer 透過 subBufferWithOffset:length: 開出來的多個 sub-buffer 視圖, 各自指向 storage 的哪一段 byte。

5.4.1 三層守護邊界對比

層 守護對象 工具 抓得到的 bug 抓不到的 bug
V1 pool storage 內容 SHA-256 pool-fill hash file_offset 算錯 / dst 指錯 / 跨層 aliasing sub-buffer view 指錯位置但 storage 本身正確
V2 decode logits 輸出 FNV-1a 64-bit per-(step,token) JSONL 最終計算結果 bit-level 飄移 / argmax 錯 mild regression (logits 接近但 bit-level 略飄) — 需 §10 contract 定位
V3 sub-buffer view 對映 (MTLBuffer, sub_offset, sub_size) → expert_id 對映表 + reverse SHA-256 offset 算錯 / alias 覆寫 / view 沒 rebase — (定位 view 層 bug 的唯一手段)

5.4.2 核心風險場景

Metal 同一個 MTLBuffer storage 可以開多個 subBufferWithOffset view, Expert Cache 用 sub-buffer 切多個 expert slot。常見的 view 層 bug:

  • offset 算錯: LRU evict 後忘了 rebase base pointer, 或 hot→warm promote 時 slot_owner[] 指向錯的 storage slice → sub-buffer 視圖悄悄指到別的 expert 的權重 byte
  • alias 覆寫: 兩個 sub-buffer view 透過 shared storage alias 互相覆寫 (race condition 後看到 stale data)
  • in-place update 後 view 沒 rebase: storage 內容更新了但 sub-buffer 的 offset/size 沒同步 → 讀到舊 byte
為什麼 V1/V2 抓不到: V1 只驗 storage 內部 byte 跟 GGUF 對齊, 不管 view 怎麼切; V2 驗最終 logits, 但 view 指錯 expert 通常讓 logits 接近 (MoE 路由有冗餘), bit-level 會飄但未必 觸發明顯的語意退化 — 屬於 mild regression, 要靠 §10.3 契約文件才能定位。

5.4.3 Dump 對映表 + Reverse-lookup 設計

V3 做兩件事, env-gated OFF, 預設零成本 (跟 V1/V2 同哲學):

// (1) 觸發: CGC_SUBBUFFER_ALIAS_DUMP=path/to/alias.jsonl
//     在 ggml-metal.metal 的 subBuffer alloc 點插 trace hook
//     每個 sub-buffer 創建時記錄對映表:

{
  "slot_id":     42,
  "expert_id":   87,
  "storage_id":  "0x7f9a3c000",      // MTLBuffer GPU 端 handle
  "sub_offset":  4194304,             // bytes into storage
  "sub_size":    1048576,             // bytes of this view
  "created_step": 1024,
  "tensor_name": "blk.13.ffn_up_exps.weight",
  "view_id":     "0x7f9c10000"       // 該 sub-buffer 的 handle
}

// (2) Reverse-lookup 驗證:
//     從 GGUF 重讀該 expert 的權重 raw bytes (獨立 fd, 不走 cache),
//     跟 (storage + sub_offset)[:sub_size] 算 SHA-256 比對。
//     不一致 → cgc_subbuffer_alias_check 印 FATAL:
//
//     "V3 sub-buffer alias mismatch:
//        slot 42 → expert 87
//        storage 0x7f9a3c000 offset 4194304 size 1048576
//        SHA-256(gguf)  = 0xabc123...
//        SHA-256(view)  = 0xdef456...
//        → likely: offset arithmetic or aliasing bug"

Bug 類型 V1 抓得到? V2 抓得到? V3 抓得到?

5.4.5 Metal-only 範圍

Sub-buffer 是 Metal MTLBuffer 抽象 (透過 subBufferWithOffset:length: 開 view), CPU 路徑走 mmap 沒這個概念, Vulkan 走 vk::BufferView 雖類似但 descriptor set 行為不同 — V3 守護本身無從掛載到非 Metal 後端, 故設計上 僅 Metal 啟用。

5.4.6 實作掛載點 (待後續 commit)

  • Trace hook: ggml-metal.metal 的 ggml_metal_alloc_buffer / ggml_metal_sub_buffer 入口插 env-gated trace
  • 對映表: in-memory hash table sub_buffer_id → (storage_id, offset, size, expert_id), 寫到 JSONL
  • Reverse-lookup 工具: scripts/check/cgc_subbuffer_alias_verify.py, 讀 JSONL + GGUF + 透過 MTLBuffer.contents 讀 GPU storage slice 算 SHA-256
  • 預設 OFF: 跟 V1/V2 一樣 CGC_SUBBUFFER_ALIAS_DUMP 缺省為空 → 零成本

6. Prefill 結尾結構化 Marker Fix (v6 + v7)

6.1 v6 Fix: THINK_SEED 條件式 Marker 跳過

問題: 當 prefill 結尾含結構化符號 (換行、反引號、JSON bracket 等), 注入 THINK_SEED 會 導致 coding 場景的 1-token stop 跟 longform 場景的迴圈問題。

修法: 根據結尾字元條件式跳過 THINK_SEED 注入:

// 結尾是結構化 marker (\n / ``` / { / [ 等) → 跳過 THINK_SEED
// 結尾是自然語言 → 正常注入 THINK_SEED 引導 reasoning
if (prefill_tail_is_structured_marker(prefill)) {
    skip THINK_SEED injection;
}

6.2 v7 Fix: Coding Stop 升級

問題: Qwen3-IQ3-MTP 組合在無 hint coding prefill 下, 第一個 code block 結尾立刻觸發 1-token stop。 GPT-style stop 集合 (```, <|im_end|>, <|end|>) 是已知模型限制。

修法: cgc_patch_coding_stop helper 偵測到 code fence open (e.g. ```python\n) 時, 把 stop 列表中的 ``` 替換為 ```\n\n, 給模型機會自然寫完整個 code block。

設計選擇: 只改 stop 字串, 不刪除 stop, 確保非 coding 場景行為 bit-identical。 若 prompt 中已含 stop ```, client 端可透過 cgc_code_strict_stop=1 kwarg 強制保留原 stop (escape hatch)。

7. Pre-commit Gate 演化: Hook 8/11 強化

7.1 Hook 8: Source ↔ Binary 同步

專案硬性要求: build 產物隨原始碼一起 commit (checkout 免重建可驗證不變量)。 改 llama 原始碼的 commit: (a) build/bin 產物必須一起 staged, (b) binary mtime 不得老於 staged 原始碼。 ALLOW_STALE_BIN=1 可跳過 (b)。

7.1.1 新增例外: ALLOW_ENV_GATED_BIN=1

當 source 改的是 env-gated dead code (例如 V1/V2 在 if (getenv("CGC_...") == nullptr) return; 包裹下), 編譯器會把整段優化掉, dylib 跟 HEAD byte-identical, 不需 stage build/bin。 這時用 ALLOW_ENV_GATED_BIN=1 顯式開啟, hook 會逐個比對 dylib 跟 HEAD 的 bytes, 確認全部相同才放行。

macOS BSD find 限制: BSD find 沒有 -printf '%f\n', 用 ${path##*/} (parameter expansion) 等效 basename。最初用 -printf 導致 0 個 dylib 被比對, hook 默默 fall through 到 fail 分支。 教訓: macOS 腳本不能用 GNU-only 工具。

7.2 Hook 11: Replay Benchmark Regression

三個應用 profile (qa-zh / longform-zh / coding) 跑 12 個指標 (3 profile × 4 aspect: quality / prefill_tps / decode_tps / peak_rss_mb), 跟 .replay_bench_baseline.json 比較:

  • Verdict: 至少 1 個指標改善 + 不超過 1 個指標退化 → PASS
  • 觸發條件: 只對「代碼」commit (src/ / scripts/ / *.cpp / *.h / *.py 等), 純文件不觸發
  • Bootstrap: ALLOW_REPLAY_BENCH_BASELINE=1 + RUN_REPLAY_BENCH=0 第一次進版 baseline

7.2.1 Baseline 來源優先序修正

原本 hook 11 固定從 HEAD:.replay_bench_baseline.json 讀, 問題是: 本次 commit 可能在 baseline 跟 current 兩端都改 .replay_bench_baseline.json (refresh bootstrap 場景), 比較時要拿「這次 commit 預期的 baseline」, 不是「上一次 commit 的 baseline」。修法: 

# 優先用 staged 版本 (`:path` = index 中的版本), 退回 HEAD
if git show ":.replay_bench_baseline.json" > "$BASELINE_OUT" 2>/dev/null; then
    BASELINE_SRC="staged"
elif git show "HEAD:.replay_bench_baseline.json" > "$BASELINE_OUT" 2>/dev/null; then
    BASELINE_SRC="HEAD"
fi

9. 工程經驗教訓: Build Env Drift + macOS 限制

9.1 Build Env Drift (Dylib Swap Noise)

dylib 從 0.0.139 swap 到 0.0.140 時, decode_tps 出現 5-15% 基準偏移, 但 peak_rss_mb 保持穩定。run-to-run noise 也是常態, 需人工解讀是否為系統性退化。 解法: 用同一 dylib 跑 3 次取較好那次作 baseline, 反映當前 noise floor。

Pre-fill Noise ±20-30%: 0.0.140 dylib 物理 noise floor 觀察到 prefill_tps 飄移 ±20-30%, 這是 GPU Metal 排程的內在波動, 不是 cache 改動造成的。所以 baseline 必須用「同 dylib 多次跑取代表值」, 否則會被 noise 誤判為 regression。

9.2 macOS BSD 工具鏈限制

  • find -printf '%f\n' 不支援 → 用 ${path##*/} parameter expansion
  • readlink -f 行為差異 → 用 python3 -c "import os; print(os.path.realpath(...))" fallback
  • 中文全型括號「（」「）」跟 bash set -u 衝突 (10 處都改 ASCII 「(」「)」)

9.3 Env-Gated 守護原則

所有新增的驗證或調試功能必須 預設關閉 (default OFF), 不影響原有功能與效能基準, 且需有完善的環境變數開關文件與預設行為矩陣。 這是 CGC fork 的硬約束之一, 確保 CI / 開發 / 量產環境行為可預測。

9.4 Worktree + Hook 路徑坑

Worktree 的 .git 是 ASCII text 指向 /path/.git/worktrees/xxx, git rev-parse --show-toplevel 會正確解, 但 hook 必須裝在主 repo 的 .git/hooks/ 才能跨 worktree 生效。 在 worktree commit 時, hook 透過 REPO_ROOT=$(git rev-parse --show-toplevel) 拿到 worktree 路徑, 跑 scripts/check_build_tracked.sh --repo "$REPO_ROOT" 才能讀到正確的 scripts。
