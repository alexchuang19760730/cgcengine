CGC Expert-Cache Step-2a / Step-3 Renormalized Routing — A/B 驗證報告

日期：2026-09-06　分支：devserver　模型：Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X（ngl=99 + expert-cache 4GB + MTP）

1. 背景

Step-2/3 的目標是讓 decode 在「expert cache 的 ZERO-slot fast path」下不損失語意品質，最終把速度拉回 25+ t/s：

  • Step-2a（produce）：在每層 top-k hook 前，從被 dispatch 的 topk 節點往上溯源找到該層 ffn_moe_logits* tensor，host 端 softmax 後計算「冷 expert 的加權路由質量 / 總質量」，寫入 cgc_weighted_cold_ratio[il]。
  • Step-2b（consume，先前 commit 5e3d4df9a）：fast-path cold guard 改讀加權冷比率（非 1e9 哨兵時），count-based 只作 fallback。
  • Step-3（renorm）：router softmax 前把冷 expert（slot_table<0）的 logits mask 成 −inf，softmax 重新歸一化到 resident experts，冷 expert 不可能被 top-k 選中 → ZERO-slot 不再污染。

4. 分析（誠實版）

4.1 為什麼「weighted guard 單獨開」會讓 coding 從 1.0 掉到 0.3？

weighted 比率比 count 更「寬鬆」：某層 union 有 20/32 冷 expert（count 62% > 30%，count guard 會擋下 fast path），但若這些冷 expert 只扛 20% 路由質量（weighted ≤ 30%），weighted guard 會放行 fast path → 冷 expert 的 ZERO-slot 貢獻變成 靜默丟失 ~20% 路由質量（softmax 未重新歸一化）。IQ3_XXS 對這種質量的丟失很敏感 → 確定性迴圈。這證明：沒有 renormalization 時，count-based 才是正確的保守選擇；weighted guard 的價值只在搭配 Step-3 時才成立。

4.2 為什麼「weighted + renorm」速度達標（25.5 t/s, 96% accept）但 coding 品質仍壞？

速度證明 mask-leaf 機制與 25+ t/s fast path 相容（無同步 ensure_batch，MTP accept 96%）。但品質壞在 pool 成員與真實 routing 不匹配：

  • 層 0 永遠 warm=0（debug：CGC-RN-FLOOR: il=0 warm=0 < k=8）→ floor 把 mask 全清 0 → 層 0 走 ZERO-slot/guard 路徑。
  • 層 1+ warm 恆為 70/256：這 70 個 = loader 依序 prewarm 的 expert 0..70，而模型真實偏好高 ID expert（如 193/233/249）。renorm 把真熱 expert 全 mask 掉 → 模型被迫在 70 個「錯的」expert 間路由 → 0/1 振盪。

換言之 renorm 讓品質「優雅地」退化成「一個只剩固定 70 expert 的模型」——如果那 70 個不是該 prompt 真正需要的 experts，輸出照樣壞。要讓 renorm 有好品質，pool 成員必須跟著真實 routing 走（decode 驅動的 hot-set prewarm / 每層 ensure 的持續生效 / 或讓熱 expert 在 softmax 前就已 resident）。這是下一里程碑（pool membership 修復）。

6. 最終判定（數據定案）

16GB + ngl=99 + 4GB expert pool（71 slot/層）下，「renorm + 25+ t/s + coding/longform 品質 ≥ baseline」不可兼得。原因是 capacity-bound 而非 membership 選擇：現況 membership 已達 74.8% ≈ 事後完美 top-71 的天花板 76.4%。71 slots 天生只能承載 ~3/4 的 routing mass，renorm 在 softmax 當下無可避免地丟掉 ~24%（mask 在 step 開頭寫入、guard 的 ensure 在層 softmax 之後才補槽，同一 step 補不回來）。

hybrid 原型失敗的機制：mask 在 step 開頭寫死，guard trip 的那一步（本應 exact）softmax 已被 mask 排除真熱 experts → 同一步補不回 → 全 profile 品質崩潰。結論：renorm 的 mask 必須在「該層 softmax 前」membership 就已正確，這要求 resident 集合在 decode 前就貼近該 prompt 的真實 routing —— 而 71 slots 的 mass 天花板只有 ~76%。

7. 可行路徑（供決策）

  1. 加大 pool（唯一能讓 renorm 到 25+ 的路）：K=128 → ~7.3GB、K=192 → ~11GB expert budget（mass 覆蓋 93%/99%），16GB 機在 ngl=99+MTP 下會 OOM → 需要 32GB 硬體再測。
  2. 16GB 上維持現狀：預設 config（baseline 品質 1.0/0.882/1.0，7–14 t/s）；若要更快，可先試「非 renorm」的小步優化（如 reduce guard trip 次數的非同步 prefetch 調校）。
  3. 層 0 warm=0 為設計使然（skip-load full-weight），不需修。

本 commit 的 CGC_MASSCOV 儀表可供日後在 32GB 機上直接量測驗證。

方向：把 turbo-fieldfare 的 MoE-SpAc（EMA utility + 週期性 top-K pool re-target，見 MoESpAcEstimator.swift）移植到 llama.cpp expert cache，讓 pool membership 追蹤 decode 真實 routing，期望在 4GB（71 slot/層）下把 resident mass 從 ~75% 拉高。

8.1 實作（全數 default-OFF，CGC_SPAC=1 才啟用）

8.3 A/B 激活嘗試 → 結構性阻塞（重要發現）

正式 MTP server config（run_server.sh）在 MTP 模式設 CGC_NO_PREFETCH=1（0000 防護：bg thread 在 GPU mid-verify 時填/逐 slot 會覆寫仍在讀的 slot）。因此 B-section 整個 prefetch 區塊（含 SpAc 注入點）在 25+ MTP 路徑被 gate 掉 —— 這是設計使然，不是 bug。

診斷 A/B：手動以同 config 但拔掉 CGC_NO_PREFETCH + CGC_SPAC=1 啟動 —— SpAc 確實活了（feeds 上升、每 refresh ~321 fills、n_prefetch 964），但 server 在 decode 中段崩潰（log: cleaning up before exit）——再次實證「MTP+OA_ASYNC + 背景 pool fill」不相容，正是 CGC_NO_PREFETCH=1 防護的那類毀壞。

結構性結論：25+ MTP 路徑（OA_ASYNC=1 + verify/draft fast path）沒有可用的 async fill 窗口。Swift SpAc 的價值建立在「GPU command buffer 之間用 bg thread 預填 pool」上；llama.cpp 的 MTP 伺服語義為了 0000 安全把這個窗口關了。EMA 只能走同步 mutation 點（pick_slot / ensure_batch），而那類路徑的收益上限就是 §5 的 capacity ceiling（~76%），達不到 renorm 所需的 ~95%。

8.4 結論與建議

  1. 本 commit 交付：完整 gated-off 的 EMA SpAc 基礎（估計器 + feed + prefetch source + config），品質中性（§8.2 三 profile 全數 = baseline），供 32GB 機或未來安全 async 窗口直接啟用。
  2. 16GB + MTP 下不建議再追：async 窗口不存在、同步 re-target 被 capacity ceiling 卡住 —— §6 判定（需 K≈128–192 / 32GB）維持不變。
  3. 若日後要解 0000 防護換 async：需在 verify/draft 之間設計「GPU idle 才 flush」的 barrier，或 double-buffer pool region（2× slot 記憶體），兩者都是新工程。

9. RN 品質歸因 bisect（2026-09-06，8GB pool 上實測）

動機：8GB pool（~142 slot/層，mass 覆蓋 ~95%）+ RN+WCOLD 實測 decode 25.9 t/s / 98.7% accept，但品質仍是 deterministic 0.3（與 4GB/10GB 的 RN 結果相同）。品質失敗對 pool size 不敏感（4→10GB 都不好）→ 歸因必須是「mask 機制」或「exclusion 本身」，不是 capacity。

9.3 結論

  1. qa-zh 崩潰（1.0 → 0.765 echo）100% 由 exclusion 造成：NOOP 拿掉 exclusion 就回到 1.0，mask 機制本身沒有把錯誤值送進 graph。
  2. exclusion 比 mass 損失暗示的更傷：142/256（8GB）甚至 178/256（10GB）「可被選」仍不足 —— top-k 是對整條 softmax 取 8 個，當真 top-8 含有冷 expert（佔總 mass ~5% 卻可能出現在相當比例的 token 的 top-8 尾段），renorm 把那個位置換成低機率 warm expert → 該 token 分佈被扭曲。MTP 下 draft+verify 看到同一個扭曲 → garbage 被 98% accept。
  3. 「mass 覆蓋 ≥95% ⇒ renorm 品質可行」的前提是錯的：品質需要的是「每 token 的 active set 幾乎都在 resident」，不是 mass 覆蓋。coding 在 NOOP 下仍退化（5-run 0.3 vs default 1.0）暗示 RN graph 路徑（額外 output leaf + ADD 改變 Metal split/layout）還有次要擾動 —— 需再查但已非主因。
  4. 定案：exclusion-based renorm 在此模型不可行；25+ 的真正前提仍是「把下一 step 的 active set 提前 resident」（look-ahead fill），而那被 MTP 的 async-window 限制擋住（§8.3）。8GB default（§8/9e046443e 已 commit）是 16GB 上品質安全的實際速度解（11–22 t/s）。

11. EMA-victim 落地（gated-off groundwork，供 async fill 窗口啟用後使用）

pick_slot 的 victim 選擇在 CGC_SPAC=1 時改為「最低 EMA utility 優先、LRU 平手」（llama-expert-cache.cpp）。Default OFF = bit-identical 純 LRU（utility seed 0.5 全等 → tie-break 回到 last_use）。EMA utility（spac_util）已由 df3ee17a6 提供，feed 需 CGC_SPAC=1；此政策是 §8/方案1（safe async fill window）的前置：當 fill 通道打通、pool 能漂移後，victim 選低 utility 讓 resident set 更貼近 EMA hot set。單獨使用在固定容量下受限於 §5 的 hindsight ceiling（~+1.6pt），不預期單獨解決 25+。
