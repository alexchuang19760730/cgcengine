1. 摘要與結論

問題：8GB expert cache 下，IQ3_XXS 仍會在長 generation（尤其 coding）塌進重複迴圈（echo prompt、```python fence loop、計算費氏數列第 n 項 無限重複），品質閘門卻給 1.0。

核心發現（全部為當日量測）：8GB pool 的 mass residency 已經在理論天花板（91.2% ≈ 完美 top-K 的 91.1%），所以漂移不是「pool 不夠大」，而是三因子交乘：

  1. 長尾 count-cold：每步被選中的 top-8 裡，平均 14.9%（各層 12–18%）的 expert 不在 resident set 內（新儀器 selcold 量測）。
  2. ZERO-slot 污染：cold expert 被 ZERO-map 後貢獻 0 logit 但仍佔 softmax 分母 → 每步微小 renormalization error → 200–700 tokens 累積成重複迴圈。
  3. 記憶體壓力：16GB Mac 上 8GB pool + 7.9GB model RSS → 只剩 15–26% free → fills 卡住 → guard 的慢路徑（ensure_batch）失效 → 只能走 ZERO 路徑 → 因子 2 惡化。同一個 binary：安靜機器 25.17 t/s + quality 1.0；記憶體壓力下 14 t/s + 迴圈。

已關閉的路徑：renorm（Step-3）在 4/8/10GB 都測出確定性 0.3——排除 9% 冷 mass 本身就改變 top-8 選擇，IQ3_XXS 對 routing 擾動太敏感。不要再投入。

建議路線：Phase 0 先把量測變誠實（loop 偵測進 gate、selcold 進 commit）→ Phase 1 直接打擊長尾（10GB pool / K=192 的 97.4% mass ceiling 是唯一已驗證可達的槓桿；SpAc K 調大）→ Phase 2 讓 guard 在記憶體壓力下也不 ZERO（修 WCOLD produce side + selective fill + bounded wait）→ Phase 3 記憶體預算工程（需決策）→ Phase 4 模板根因（real special tokens）→ Phase 5 SpAc look-ahead（野心路線）。

3. 根因分析：三因子模型

3.1 因子一：長尾 count-cold（15%）

pool 裝的是 top-143 by mass（91% mass），但每步 top-8 選擇 的長尾（mass 排序 143 名之後的低質量 expert）偶爾進 top-8。8GB 的 mass ceiling 是 91%——這是容量數學，不是 policy 問題。唯一把長尾從 15% 砍到 ~7% 的容量級槓桿是 K=192（10.8GB, 97.4%）。

3.2 因子二：ZERO-slot 污染（品質殺手）

fast path 對 cold expert ZERO-map（讀預留的 zero slot）：該 expert 貢獻 0 logit，但 softmax 分母仍算它 → 每次 renormalization 都偏 → 數百 token 後塌進重複迴圈。這是「品質崩潰」的機制，不是「品質微降」。

3.3 因子三：記憶體壓力（觸發器）

16GB 上 8GB pool + 7.9GB RSS ≈ 0 頭部空間。guard 觸發 → ensure_batch 的 fills（每 expert 1–3ms，多達 24–100 個/步）跟 GPU decode 搶頻寬 → 卡住 → guard 只剩 ZERO 路徑 → 因子二全面發作。安靜機器沒有因子三，所以同 binary 25+ t/s 且 1.0。

結論
三因子缺一不可：沒有長尾（因子一）→ 不會 ZERO；沒有記憶體壓力（因子三）→ fills 來得及 → guard 走 ensure_batch → 沒有污染。修復要同時打因子一（容量/成員）與因子三（記憶體），並在因子二留安全網（guard 寧可慢不可 ZERO）。

5. 解決方案架構（分階段）

Phase 0 — 誠實的量測基建 P0 半天–1 天

沒有可信的尺，後面全部白做。目前 gate 把迴圈判成 1.0。

  • 0.1 片語級 loop 偵測進 replay_server_profile.py 的 evaluate_quality（相同 6+ 字元片語連續重複 ≥3 次即判 loop，分數歸 0）。已要求兩次，從未落地——本次建議書把它列為第一優先
  • 0.2 commit selcold 儀器（本建議書已實作、已 build：MASSCOV dump 加 per-layer selcold=，summary 加 SELECTED count-cold 行）
  • 0.3 session 基準腳本：每 session 自動記錄 memory free %、guard 觸發次數、selcold、loop 偵測結果
驗收
gate 不再給迴圈 1.0；coding 迴圈重測分數 <0.5。

Phase 1 — 直接打擊長尾 count-cold P0 1–2 天

  • 1.1 10GB pool A/B：CGC_EXPERT_CACHE_BYTES=10GiB → K≈192 → mass ceiling 91%→97.4%（min 96%）。10GB pool 已有穩定證據：先前 session 穩定跑 2h22m、RSS 9.64GB。預期 selcold 15%→~6–8%。這是唯一已驗證可達的容量級槓桿。
  • 1.2 SpAc K 調大：CGC_SPAC_K 8→16–32（每次 refresh 多 re-target 一些長尾）；並確認 refresh 真正落在 decode B-section（spac_prefetch call site 已存在，驗證非死碼）。
  • 1.3 驗證 prewarm_hot：確認 prefill route-frequency 有餵（短 prompt 的 prewarm 是 garbage 的已知風險——檢查 LLAMA_EXPERT_CACHE_PREWARM_HOT 狀態）。
驗收
selcold <8%；guard 觸發 <1% steps；coding replay 在 loop 偵測下 >0.5。

Phase 2 — Guard 安全網（讓因子二無害）P1 2–3 天

  • 2.1 修 WCOLD produce side：callback 的 tensor 名稱比對改收 ffn_moe_gate-X（實際收到的名字），讓 weighted cold ratio 真實寫入 cgc_weighted_cold_ratio[il]——低權重冷 expert 的層留在 fast path（不再整層 block）。
  • 2.2 selective fill：guard 決定 fall through 時只填高權重冷 expert（code 已有雛形，驗證 + 開 gate）。
  • 2.3 bounded wait 取代 ZERO：guard 觸發且 fills 在途時，等待 ≤X ms（CGC_FAST_WAIT 已存在但預設 off）——寧可慢，不可 ZERO。這是「品質不退化」的最後防線。
驗收
15% memory 壓力下重跑 coding：迴圈消失（慢但正確），guard 統計顯示 ZERO 路徑使用率 0。

Phase 3 — 記憶體預算工程 P1 1 天 需決策

因子三是今天所有數字被污染的共因。選項：

  • 3a（推薦先試，免費）：測試時清環境（關閉其他 app），CGC_SERVER_MEMORY_MODE=prod auto-degrade（run_server.sh 已留入口）
  • 3b：ctx 8192→4096 釋放 KV ~1.5–2GB（代價：Claude Code 長 prompt 可能塞不下——需量 3,100-token prefill 是否仍 fit）
  • 3c（結構性）：24–32GB 機器。10GB pool（Phase 1）在 16GB 上偏緊，32GB 上無痛
開放決策（請 review 時決定）
16GB 是否為目標硬體？若是，Phase 1 的 10GB pool 與 3b 的 ctx 縮減必須取其一（兩者都要會 OOM）。若可接受 32GB，Phase 1 + 3c 是無痛組合。

Phase 4 — 模板根因修復 P2 1 天

  • 模板改用模型 real special tokens：<|im_start|>（248045）/ <|im_end|>（248046=EOS），讓 scaffold 重發時模型能真正自然終止（現在靠 server 端 marker stops 強切）。
  • 保留 marker stops 作雙保險。

Phase 5 — SpAc L3 look-ahead（野心路線）P2/P3 3–5 天

  • MTP draft 已算 next-3-token 的 router logits 與 top-8（draft_accept 92–98% 證明路由高度一致）——把 draft 階段的 (layer, expert_ids) 直接塞進 prefetch queue，等於零成本精確預取。
  • EMA 每 refresh 重選 top-K 已存在（Phase 1.2 調 K）；look-ahead 是把「歷史頻率」升級成「未來精確」。
  • Swift turbo-fieldfare 已驗證此架構（MoESpAcEstimator + PreadExpertStreamer）。
這是唯一能把 4GB pool 的覆蓋率拉回可用的路線（draft 路由預測覆蓋 85–95%），但工程量最大、風險中高（需在 draft decode 路徑插樁）。建議 Phase 1–2 驗證後再決定。
