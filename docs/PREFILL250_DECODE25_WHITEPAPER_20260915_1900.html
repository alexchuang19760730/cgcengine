一句話結論：decode 步的 91% 是 GPU 在跑，不是 IO、不是 encode、不是 dispatch。 用內建的 M0 剖析器量到 wait=72.56 (91%) / cb=4.54 (6%) / submit=2.98 (4%)。 這推翻了「decode 是 SSD-IO bound」與「decode 是 encode bound」兩個先前假設。

所以你的兩個問題有了同一個答案的兩半：

  • 算子融合（node fusion）：槓桿已用盡——它只能壓 cb，而 cb 只佔 6%（4.5 ms）。實測同向：CGC_MMV_FUSE 今天在這個配置下 變慢且輸出損壞（見 §2）。
  • Metal：還有空間，而且現在知道在哪——那 72 ms 的 wait。 每層單 token 只需搬 ~9 MiB 專家權重，頻寬地板 ~3 ms/token，實測 72 ms → n_tokens=1 的 GEMV 是延遲／並行度受限，不是頻寬打滿。 真正的槓桿是「批次融合」（一層 8 個 expert GEMV 合成一次派發、8× 並行度）， 與已證僞的「節點融合」是兩類不同的東西。

1. 三個決定性測量

1.1 CGC-PHASE：整個 step 都在 compute 裡

為此新增了 fill_wait_us 計數（llama-expert-cache.{h,cpp}）， 語意刻意與 pread_usec 不同：後者是跨 worker 的聚合值（可超過牆鐘）， 前者只由呼叫執行緒累加，所以它是唯一能與單步牆鐘直接相除的計數。 它掛在三個點上：ensure_slot 的 bg_cv.wait、ensure_slot 的 fill_pool_direct、ensure_batch 的 bg_cv.wait。

2.3 但有一類「融合」還沒被試過，而且它打的是對的地方

上面兩個都是節點融合（node fusion）：把幾個 graph node 合併成一次 dispatch， 省的是 cb——已經證明只有 6%。

還沒試過的是批次融合（batching fusion）：把一層的 8 個 expert GEMV 合併成一次派發，讓 GPU 同時有 8× 的權重讀取在飛。它省的不是 encode， 而是提高單次 GEMV 的並行度——也就是直攻那 72 ms 的 wait。

這與路線圖 M3 的工作項 3「batched-union gather（一次收 union、一次 batched matmul）」 是同一條路。它不是已證僞的那條。

3. 問題二：Metal 還有優化空間嗎？

有，而且空間很具體：那 72.6 ms 的 wait。 cb+submit 合計 7.5 ms（9%）——encode 側已經幾乎沒有東西可拿。

3.1 為什麼說 72 ms 是「遠離地板」而不是「已經到頂」

4. 誠實的邊界

  • wait 的實作是 hook_seg() 裡對 cgc_done(split_backend) 的自旋輪詢（ggml-backend.cpp:1883-1886，sched_yield() 迴圈）， 等的是 segment i 的全部 command buffer 完成。所以它是 GPU 完成等待，語意明確。
  • 更關鍵的結構性事實：層與層之間沒有重疊。同一段程式碼的註解說明， 為了修 raciness（top-k hook 必須先寫好 remap leaf，segment i+1 才能消費）， 派發器在 每個 segment 邊界都把管線排空——先等 segment i 整個跑完，才 submit i+1。也就是說「encode → GPU → 等」是序列的，41 段各付一次。 因此每段那 1.77 ms（72.56 / 41）理論上可能混了兩件事： (a) segment 的 GPU 執行時間，(b) 完成回報／啟動爬升的延遲。 兩者在目前儀器下沒有分開。這正是 §6 第 1 項（層內切分）必須先做的原因—— 如果 (b) 佔比高，那槓桿就不是 kernel 而是恢復層間重疊（例如讓 remap 寫入 與 GPU 執行解耦，而非靠排空管線保證順序）。
  • 「20×」依賴 120 GB/s 這個峰值。GPU 實際可持續頻寬低於峰值， 所以真實倍數小於 20；但方向（遠離地板）與量級（不是 1.5×）不受影響。
  • CGC_DECODE_PROFILE 本身有成本（吞吐降 2.4%），且它只覆蓋分段派發迴圈內的時間 （total=80.07 ms vs 未剖析時 compute≈100 ms）→ 約 20 ms 落在迴圈外（tail segment、取樣、HTTP）。這 20 ms 尚未歸因。
  • 本輪所有數字都是 MTP-off 臂。MTP-on 的 CGC-PHASE 顯示 compute=1.12 ms， 那是 MTP draft head 的單 token 前向（因為 n_tokens==1 的過濾把 verify 的多 token 步排除在外）→ MTP-on 的 phase 數字不可與 MTP-off 互比。
  • 16 GB 機器上不存在 cache-free oracle：CGC_SERVER_EXPERT_CACHE_OFF=1 需要 256 experts × 40 層常駐 → Metal OOM，且在載入期就被 P0 的 fail-stop 直接 abort （Insufficient Memory + cgc_wait_cmd_buf → ggml_backend_sched_synchronize）。 這正是 P1（--n-cpu-moe pass-through）存在的理由。

6. 下一步（依槓桿排序）

  1. 把 72 ms 的 wait 在層內再切開，並分離「GPU 執行」與「完成回報」 （attention / routed MoE gate+up GEMV / routed down GEMV / shared expert / dense）。 這是所有後續改動的前提，成本最低、資訊量最大。判別方法：若 wait 隨 segment 數（而非隨權重位元組）成長，那槓桿是恢復層間重疊而非 kernel 效率。
  2. 依切分結果實作批次融合（一層 8 個 expert GEMV 一次派發）。
  3. P0 已完成的 fail-stop 保護維持默認開啟；CGC_MMV_FUSE 在 overlap guard 修好前不要開。
  4. P1：--n-cpu-moe N pass-through，取回 16 GB 機器上缺失的絕對 oracle。
