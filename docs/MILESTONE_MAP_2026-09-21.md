## 3. ★ 今天否證的**不是** S2，但 S2 的上界要砍

這裡最容易誤讀，單獨交代：

- **今天否證的是「async fill / A‑B 段拆分 / 背景預取」** —— 判據是依賴鏈：
  `hook_seg(i)` 等 segment 跑完 → 讀 ids → `ensure_batch()` 阻塞 → 才 `submit_seg(i+1)`，
  而 **segment i+1 的第一個 buffer 立刻要讀剛填好的 slots** ⇒ 中間沒有任何 GPU 工作可拿來墊。
- **S2 是另一件事**：把 slot_table 的發布搬到裝置，讓 `CGC_SUBMIT_AHEAD=1` 從「故意錯的探針」
  變成合法。它拿掉的是 **wait ＋ host 讀 ids ＋ 記帳** 那段，**不是** fill 的 IO。
- ⇒ S2 落地後，**cb 的 IO 時間仍在臨界路徑上**（MoE 在第一個 buffer，權重沒落地就 submit ＝ 已實測的 NaN）。
  所以 M‑S2 的 **22.9（`total → union`）那端不可達**；19.0 那端（只有 submit 能搬）才是它的真上界。
- ⚠ 想再收窄只能靠拆 `gap 54.35` 的分量，而 `gap ⊆ cb + submit` 的交叉檢查以 **10.09 ms 失敗**
  ⇒ **分量相加在這個 regime 不閉合** ⇒ 現階段不給數字，只給結論「上界 ≤ ~5%，且不可引用」。

## 5. 弱點

- **M‑W 的 t/s 幅度不可引用**：單臂噪音 ±27%，A/B 用的是 `dispatch_price_v2` 的 cell
  （t/s 7.6–12.1），與交付的 12.57 **不同口徑** ⇒ 換 cell 後可能歸零。
- **M‑K5 的 (A)/(B) 仍未定**，且手上唯一的反證（prefill 形狀 threads 中位 2048 > 駐留 1024）
  是**不利於 (A)** 的 ⇒ 期望值按 (B) 佔優（＝ 0）看待。
- **M‑S2／M‑CB 屬「推算」且跨線**：線 I 的 cb 天花板是否被今天的結論打折，**本線沒有實測權**；
  表中標「需重述」而不是改數字，就是這個原因。
- **整張表只有一格是量測**（M‑now）。其餘每一格要麼已被撤回，要麼是推算／外推。
- prefill 欄在 09-20 三次未驗證 ⇒ 任何 decode 側改動落地後，**prefill 必須同 commit 重驗**。
