## 3. 目標 3：頻寬能打滿

**先校正這個目標。** 現有的度量是：

- 本機 **實測峰值 108.8 GB/s**（6 緒順序讀；120 是規格值，別當實測）；
- 有效頻寬（1.277 GB/step）：union 口徑 **11.9~15.1 GB/s**、union+gap **7.9~10.7**
  ⇒ **只佔峰值 7~14%**（另一份記載「DRAM 只用了 11%」）。

但**成因不是頻寬不足**：

| 觀察 | 值 |
|---|---|
| expert gather（大塊搬運）本身 | 微基準 **45.3~46.9% 峰值**（另一份引擎估計 50~61%，兩口徑未統一，勿混用） |
| 一個 `RMS_NORM` 節點 | 燒 **57~92 µs** 只搬 **64 KB** ＝ 峰值的 **0.6%**，比 matmul 差近 100 倍 |
| 一個 command buffer 的固定成本 | **~13 µs**（K0，1-node buffer 中位）；另一個 18~19.5 µs（NSM/ K3 邊際，兩獨立儀器互證） |
| 工作節點數 | **2455 個/步**，每一個都付一次幾十 µs 的入場費 |

⇒ **本案是 latency / occupancy-bound，不是 FLOPs 牆也不是 DRAM 牆。**

| # | shape | 狀態 | 證據 |
|---|---|---|---|
| 3.1 | **dense GEMV（佔每步 bytes 81.7%）** | ⛔ **結案**：即使打滿 100% DRAM 峰值，只值 **2.42% < 3% 門檻**；`CGC_MMV_NSG` 1..32 全射程否證 | `DENSE_GEMV_INSTRUMENT`（§EN-434）⇒ **別再往 dense 找錢** |
| 3.2 | **MoE gather 的 tile 旋鈕**（`CGC_MMV_NSG`） | ⛔ **否證**：gate 通道六值跨度 **0.6 pp**（null cell 0.9/3.3%），`nsg≥16` 反而退（32.2%／21.4%） | `MOE_NSG_ADMITTED_WINDOW`（在 admit 窗口上量的，≥Qi 條件具備） |
| 3.3 | **把「佔比」變高（＝消掉空檔）** | ⚪ **唯一還能動的** —— 它就是 **2.4 / 2.5** | 見 §2 |
| 3.4 | 「65~70% 峰值」這個目標本身 | 🟡 是白皮書的主張（row activate／turnaround／refresh ⇒ DRAM 實用天花板 80~85%，目標取 65~70%），**但從未有人證明我們有一天會變成 bandwidth-bound** | `BANDWIDTH_CEILING_100PCT_2026-09-23.html` |

### ⇒ 目標 3 的結論
在今天的瓶頸型態下，**「把單一 kernel 打到 65~70%」的總帳很小**（dense 那 81.7% 的 bytes 只值 2.42%）。
真正能抬高**整步平均有效頻寬**的，是把那 71.3% 之外的時間拿回來 —— **也就是目標 2**。
⇒ **目標 2 與目標 3 是同一件事的兩個名字**，不要各派一條線去做。

## 4. 目標 4：prefill 250+ / decode 25+

### 4.1 prefill 250 —— **曾經做到，今天沒做到**

| 時點 | 讀數 |
|---|---|
| 09-20 定錨（NOMINAL×2） | **281.51 / 281.95** ✅ |
| 壞樣本（同形狀） | 214.30（1.32×）⇒ 風險是**窗口不是引擎** |
| **今天（prod-new, llama-bench）** | ctrl **162.5 ± 6.4**；p0+B **209.5 ± 81.7** ❌ |

已知機制（`MEMORY_PERF` §「prefill 250 的條件式交付」）：
- **熱該不該**必要非充分：COLD-STATE＋發射前 `notifyutil -g com.apple.system.thermalpressurelevel` 讀到 `0`，**仍然只量到 242/227/249**；
- **`swap` 是果不是因**；**直接變數是有效 GPU 時脈**（純階反讀 1470→291、928→227、618→135 MHz）；
- 未排掉的第一候選＝**背景 GPU 客戶端**（agent UI／WindowServer；零 llama 行程時本機地板就是 HEAVY）。

**⇒ 還沒做的**：在乾淨窗口下用 **`prefill250` profile ×（P0 + SPAC_HOT）** 複认缴一次
（今天只用 `prod-new` 跑過，而 P0 對 prefill 是 **+29%**，是目前唯一對 prefill 有效的結果率杆）。

### 4.2 decode 25 —— 現有逐步模型下**不可達**，但今天出現了重開它的東西

不可達的算術（`docs/DECODE25_CEILING_2026-09-20.md`，`S0 = 85.8 ms`）：

```
k=3 即使 accept a = 1.0 → 19.25（需 ml ≥ 5.20 > 硬頂 4 ⇒ 無解）
k → ∞ 且 a = 1.0       → 24.59 < 25          ⇒ 連極限都摸不到
指名槓桿總和            → +5~10%（12.57 → 13.2~13.8）
⇒ 建議目標改寫 14~16
```

剩下的两个——rep sits at the Δ :

| 情境 | step | t/s |
|---|---:|---:|
| 今天環境基底（分段） | 125 ms | 7.8~8.2 |
| 今天的環境對應讀數（錨點） | 247.98 ms | 12.57 |
| **2.4 單段提交（診斷，輸出錯）** | **55 ms（髒）／60 ms（乾淨）** | **17.7~18.08／16.66** |
| 2.4 **+** 2.5 整層重算（不後台化） | 72.8~80 | **12.5~13.7（+1% ~ −8%）** |
| **2.4 + 2.5 且 fill 後台化** | **62~70** | **14.3~16.1（+5~18%）** |
| 2.4 的天花板（miss → 0，即不必補跑） | 55~60 | **16.66~18.08（+23% ~ 2.2×）** |

**⇒ 這是 09-20 之後第一個有資格「重開 25」的東西** —— 因為它動的不是任何單一分量的百分比，
而是 **`cb` + `submit` + 41 段串行整塊消失**（一次提交讓 Metal 自己排層間依賴）。
但它的門檻寫得很死：**錯層必須 < 4 層才划算，實測 ~8 層**。

## 5. 排序建議（本輪的一句話）

1. **先複現 2.4**（零 build：兩個開關今天都在 binary 裡；需共用閘門 + ABBA 協議）
   ⇒ 把「一次提交真實收益」從跨環境的 +23%/2.2× 變成 **同環境配對的可引數**。
2. **然後決定 2.5 走哪一條**：
   - **錯層重算**（工程小，帳上只剩 +5~18%，且要 fill 後台化）；
   - **kernel 級 miss 處理**（對（錯層只重算 miss experts / GPU 查表直連），唯一能碰到 16.66~18 的版本，但工程大）。
3. **別再新開線**：2.1（async fill 藏 cb）、2.2（prebind）、3.1（dense）、3.2（MoE NSG）、
   1.5（第二支行程）、1.7（跨 prompt 靜態放置）**都已判死並有自己的否證文件**。
4. **目標 1 的 1.6（`-np`）先凍結**：它回答的是吞吐而不是單流 decode；除非使用者改目標定義。

## 7. 誠實邊界

- 本輪 **0 GPU、0 build**，全部是源碼與既存文件的核對；所有數字都帶來源，沒有一個是本輪新量的。
- 2.4 的 **2.2× 來自「輸出錯誤」的診斷臂**（routing 佔位），它價格的是**串行的開銷**，
  **不是可交付速度**；任何把它當成交付數字的用法都要先做出 2.5。
- 2.4 的兩輪（髒環境 2.2×、較乾淨環境 +23%）**跨環境**，§7.1 的第一次 ABBA 曾被作廢（env 沒傳）
  ⇒ 引用前務必確認是哪一版修正後的對。
- expert gather 的「%峰值」有兩個未統一的口徑（微基準 45.3~46.9%／另一份引擎估計 50~61%），本輪未裁決。
- **`CGC_SEG_BATCH` 雖在 11:14 的 `libggml-base`，而 `libllama` 是 14:58** ⇒ 兩半不是同一個 build，
  理論可行，但第一次跑要自己看結果是否自洽。
