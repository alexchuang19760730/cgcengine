# M3 的 40% 判準：量到了，且**不成立**（MoE 專家矩陣乘 ≤ 30% of `wait`）

日期：2026-09-18 01:4x–02:0x（+08）
儀器：`CGC_GPU_NODES`（逐 command buffer 的節點範圍→GPU 時間）＋ 兩個新旋鈕
狀態：**未 commit**（動了 `src/`，未跑 D5）

> ⚠️ **2026-09-18 03:0x 更正（原文保留，不回改）**：本文 §4 的表用 `lb` 欄與 `ffn_moe_topk` 的
> 「solo ⇒ 精確」讀數，**那是偽影**。後續在同一批資料上發現：`ggml-metal-ops.cpp:242-252` 把
> `NONE／RESHAPE／VIEW／TRANSPOSE／PERMUTE` 當成顯式 **no-op**（「noop -> next node」），
> 所以一個全 VIEW 的 command buffer **不含任何 GPU 命令**——而它實測卻報 592 µs／節點。
> ⇒ **逐 command buffer 的時長不能被歸屬到節點**，`lb`／`solo` 這條推論線不成立。
>
> **不變的部分**（本文的主結論仍然成立，且理由更強）：`ffn_moe_*`（含 gate/up/down）**遠不及 40%**。
> 上界那條（聯集，≤28.3% of 步 busy）不依賴任何 per-node 歸屬，只依賴「含某家族成員的 buffer 的時長之和」，
> 所以它不受這個偽影影響。細節與更正的完整推導見 `docs/OP_TIMING_CEILING_2026-09-18.md`。

---

## 0. 一句話

`M3_VERDICT §9` 寫的判準是「若逐節點 GPU 時間顯示 `ffn_moe_*` 那群佔 `wait` ≥40% ⇒ Cell 2（MoE
gather 融合）有量」。**現在量到了，而答案是「沒有」**：MoE 專家矩陣乘（`ffn_moe_gate`／`up`／`down`）
對整步的**硬上界**是 **26.5%（中位步）／33.1%（p90）／42.4%（最壞步）的 segment busy**，換成 `wait`
約 **29%／37%／46%**。上界本身還在 40% 以下 ⇒ 真值更低 ⇒ **判準不成立**，走「找不到路」分支。

---

## 1. 先更正上一輪的一個結論：`CGC_VERIFY_OP_TIMING` 不可能回答 M3

上一輪我寫「`CGC_VERIFY_OP_TIMING` 與 `CGC_DECODE_PROFILE` 搶同一個 `callback_eval` 插槽」。
**機制說錯了。** 真因是 `ggml-backend.cpp:1770-1772` 的一行**顯式排除**：

```cpp
} else if (cgc_oa_async_enabled() &&
           getenv("CGC_VERIFY_OP_TIMING") == nullptr &&      // ← 這一行
           strcmp(ggml_backend_name(split_backend), "CPU") != 0) {
```

一開 `CGC_VERIFY_OP_TIMING`，Metal 就退回**上游的 chunked scheduler 路徑**，而那一條在**每個 chunk 之後
都 `ggml_backend_synchronize`**（`ggml-backend.cpp:2600`）。後果是可量的：

| run | env | decode t/s | 熱態 |
|---|---|---|---|
| 生產（分段、OA_ASYNC） | — | **12.0–12.9** | — |
| `en-verify-op` | `CGC_VERIFY_OP_TIMING=1` | **2.65 / 4.17 / 3.91** | HEAVY |

⇒ 那個 regime **慢 3 倍**，每個 chunk 都在等 GPU 排空。它的 `gate`／`up` 數字（44.1／35.2 ms 冷、
32.5／17.9 ms 暖）是「單獨跑那個 op、含 launch 與排空」的成本，**不是生產形狀的佔比**。
再加上它的目標判定含 `node->src[2]->ne[1] > 1`（只在 T>1 生效）——
**結論：`CGC_VERIFY_OP_TIMING` 結構上不適合回答 M3，不該再拿它當判準的儀器。**

（它仍然有用：見 §4 的交叉驗證。）

## 2. 逐節點解析度的天花板是 **Metal**，不是時間戳 API

上一輪我寫「不需要 `MTLCounterSampleBuffer`」。**這個說法要分兩層，而第二層是錯的。**

`ggml-metal-context.m:1304-1315` 讓每個 command buffer 的節點範圍**可以直接導出**，所以
**per-command-buffer** 的 GPU 時間不需要任何取樣 —— 那部分成立（自我檢查 `seg_busy == layer gpu_sum`
逐格相等，`delta=0.00%`）。但要走到 **per-NODE**，就得讓範圍變成 1 個節點，而那需要
`n_cb ≈ n_nodes`，也就是**每個 segment 約 128 個 command buffer**。

**量測結果（2026-09-18 01:48，`CGC_CB_N_MAIN=1` + `CGC_SERVER_N_CB=127`）：伺服器永遠不就緒。**
它不是慢，是**卡住**。`sample 43040 2` 顯示主執行緒 **1716/1716 個樣本**停在：

```
ggml_metal_graph_compute
  -> -[AGXG16GFamilyCommandQueue commandBufferWithUnretainedReferences]
     -> -[_MTLCommandBuffer initWithQueue:...]
        -> _dispatch_semaphore_wait_slow -> semaphore_wait_trap
```

⇒ **Metal 對「在途 command buffer 的建立」有配額**，而建立迴圈卡在 `dispatch_apply` **之前**
（所以沒有任何 worker 編到碼）。症狀層面只看到 `/health` 回 `{"message":"Loading model"}` 與
`server never became ready` —— 與「載入很慢」同形。

| 旋鈕 | 代價 | 可用性 |
|---|---|---|
| `CGC_CB_N_MAIN`（壓 `n_main = MAX(64, 0.1*N)` 的地板） | **零**（cb 數仍是 `n_cb+1`） | ✅ |
| `CGC_SERVER_N_CB`（加寬 worker 切片） | 每個 slice 多一個 MTLCommandBuffer | ⚠️ n_cb ≥ 64 死鎖 |

## 3. 達成的細度與它的代價

`CGC_CB_N_MAIN=1` 讓主執行緒的 cb 只吃 segment 的**第 1 個**節點（那正是 `ffn_moe_topk`），
而不是前 64 個（MoE 的 gate／up／down 原本就埋在那 64 個裡面）。

| 臂 | `n_main` | `n_cb` | 每 segment 的 cb | range 直方圖 | 最大 range |
|---|---|---|---|---|---|
| `en-fine-ctl`（控制） | `MAX(64,·)` | 8 | 9 | `1=36 2=104 3-7=1056 8+=161` | **64** |
| `en-fine-nmain` | 1 | 8 | 9 | `1=36 2=0 3-7=44 8+=1236` | ~13 |
| `en-fine-nmain16` | 1 | 16 | 17 | `1=58 2=80 3-7=2372 8+=0` | **7** |
| `en-fine-matrix` | 1 | 16 | 17 | （由 NSM 的 `b-a` 直接算） | **7** |

**控制臂的自我檢查**：`delta` 全部 `0.00%`、`(other)=0.00 ms`、`seg_busy == layer gpu_sum` 逐格相等。
細版也一樣 ⇒ 細度沒有破壞歸屬。

**細度買到什麼**：`ffn_moe_topk` 變成 **solo buffer** ⇒ `cntw == lb == ub`，是**精確值**
（`en-fine-nmain16`：8.93 ms／10.4%；matrix run：它是 355 個 decode segment 中 54 個的**最貴 buffer**）。

**代價**：t/s 不可引用（`en-fine-nmain16` 13.65、`en-fine-matrix` 9.48、控制 9.67，全部單發、未交錯、
熱態不同）。`en-fine-nmain16` 看起來變快的那個訊號**未經交錯 A/B，不可當結果**，但它值一個正式的
`n_cb` 掃描（見 §5）。

## 4. 結果：家族上界（**聯集**，不是逐 kind 的 ub 相加）

`CGC-GPUNODE` 印的 `ub` 是**逐 kind** 的，所以對「一群總是同住一個 buffer」的家族
（gate／up／down 永遠在一起）它答不出家族的界是 `max(ub)` 還是 `sum(ub)` ——
而那個縫正好是 31.6%–44.2%，**M3 的門檻就落在裡面**。所以改用 `CGC-NSM` 的逐 cb dump 離線算
（`a`／`b` 是節點範圍、`dur_ns`、逐 kind 計數），家族界是**聯集**：

```
fam_ub = Σ (含至少一個家族成員的 buffer 的 dur)      ← 合法上界（單一 buffer 的真實耗時 ≥ 家族在其中的耗時）
fam_lb = Σ (節點全屬家族的 buffer 的 dur)            ← 合法下界
```

**逐段（= 逐層）中位數**（`en-fine-matrix`、355 個 decode segment、每層 GPU busy 中位 3.586 ms）：

| 家族 | **ub（聯集）** | cntw | lb |
|---|---|---|---|
| `ffn_moe_gate`+`up` | **14.6%** | 1.9% | 0% |
| `ffn_moe_gate`+`up`+`down` | **27.1%** | 2.8% | 0% |
| `ffn_moe_topk` | 11.5% | 11.5% | **11.5%（solo，精確）** |
| `ffn_moe_`（見下） | 12.6% | 15.7%… | 0% |

**步層級**（8 個 40 層的步，`gate`+`up`+`down`）：

| 步 | Σ 層 busy | 家族 ub | % of busy | ≈ % of `wait` |
|---|---|---|---|---|
| 0 | 179.7 ms | 59.5 ms | 33.1% | 42.9% |
| 1 | 399.2 ms | 169.1 ms | 42.4% | 121.9% ← 冷池那一步 |
| 2 | 190.2 ms | 62.3 ms | 32.7% | 44.9% |
| 3 | 151.0 ms | 48.7 ms | 32.2% | 35.1% |
| 4 | 152.5 ms | 27.9 ms | 18.3% | 20.1% |
| 5 | 148.5 ms | 37.1 ms | 25.0% | 26.7% |
| 6 | 100.6 ms | 26.7 ms | 26.5% | 19.2% |
| 7 | 96.7 ms | 19.4 ms | 20.0% | 14.0% |

同一個 run 的 `wait` 中位 138.78 ms、`total` 中位 307.83 ms；Σbusy 中位 ≈150 ms ⇒ 換算約 ×0.93。
**中位步 26.5% of busy（≈29% of wait）、p90 33.1%（≈37%）、最壞 42.4%（≈46%，且那一步是冷池步）。**

**⇒ 判準（≥40%）在中位與 p90 都**不成立**，而且這是**上界**。唯一的例外是最壞步／冷池步。**

### 4.1 `ffn_moe_` 是什麼：**不是矩陣乘**

`ffn_moe_` 不是節點名，是**詞彙表**（`ggml-backend.cpp:2100-2109`）的 longest-prefix 兜底桶，
它裝的是沒有更長條目匹配的 `ffn_moe_*` 名稱，實測出現的有：`ffn_moe_swiglu`、`ffn_moe_weights`、
`ffn_moe_weighted`、`ffn_moe_out`（見 `CGC-GPUNODE: hot#` 的原始名）。**這些是逐元素／激活，
不是專家的 GEMV** —— 所以「ALL `ffn_moe_*`」那個讀法（ub 39.2% of busy）**不是 Cell 2 的靶**。

## 5. 交叉驗證：兩個獨立儀器同意

| 儀器 | regime | 家族（gate+up）佔 `wait` |
|---|---|---|
| `CGC_VERIFY_OP_TIMING` | chunked + 每 chunk sync（慢 3×） | **24–38%**（冷 79.34 ms、暖 50.45 ms） |
| `CGC_GPU_NODES` + `CGC-NSM` 聯集上界 | 生產分段路徑 | **≤37%**（p90 步；中位 29%） |

兩條路在**不同的執行形狀**下量到同一個區間 ⇒ 不是形狀相依的產物。

## 6. 誠實邊界

1. **上界寬鬆**：含 gate／up／down 的 buffer 通常還有 `ffn_gate`／`ffn_up`／`ffn_moe_`／`(other)`
   共 5–7 個節點，聯集上界把整個 buffer 算給家族。所以真值 < 上界，方向對判準有利（更不成立）。
2. **步層級的樣本少**：8 個步、單發、未交錯，且第 1 步是冷池步（`total` 399 ms）。結論用的是
   中位與 p90 的**上界**，不依賴任何單一步。
3. **細度有代價**：`n_cb=16` 讓每 segment 的 cb 由 9 變 17；t/s 不可引用，`wait`／busy 的絕對值
   可能被擾動（`delta=0.00%` 的自我檢查只保證歸屬一致，不保證無擾動）。**要引用佔比時要附控制臂。**
4. **`en-fine-nmain16` 的 13.65 t/s 是線索不是結果**（單發、未交錯、熱態與控制臂不同）。

## 7. 下一步（依證據排序）

1. **把上界變成估計（唯一能再縮的）**：在 buffer 內改用以 **FLOPs** 加權的分攤（節點名稱＋
   `op`＋`ne` 在 sched 側都有，不需要動 Metal），並用**已量到的 solo 精確值**（例如 `ffn_moe_topk`
   11.5%）當陽性對照檢驗那個加權模型。這會把 [14.6%, 27.1%] 的區間換成一個帶誤差的值。
2. **正式 `n_cb` 掃描**：`en-fine-nmain16` 的快是單發訊號；做交錯 A/B（`n_cb` 8/12/16/24）就能知道
   它是不是真的（Metal 的在途配額同時限制了它的上限）。
3. **因果替代**：`LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=1` 讓第 0 層的 MoE 走 CPU/BLAS，與生產配置
   **同一層、同一形狀**相減 ⇒ 直接量到一層的 MoE 矩陣乘 GPU 成本（不靠歸屬模型）。成本：兩個臂。
   ⚠️ 要先把該 env 加進 `run_server.sh` 的 allowlist。
4. **不要再做的事**：拿 `CGC_VERIFY_OP_TIMING` 當 M3 的儀器（§1）；把 `n_cb` 開到 ≥64（§2，死鎖）；
   把「ALL `ffn_moe_*`」當成 Cell 2 的靶（§4.1）。
