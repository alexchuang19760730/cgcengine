一句話結論：你問對了，而且問的是閘門的根本性質。 「layer 1 ffn_moe_gate-1 / ffn_moe_up-1 的全零 expert row 沒解決， 怎麼做到 M1/M2/M3 oracle 的正確性？」——答案是：證明不了。 M1/M2/M3 拿 cache-ON 的參考做逐位元對比，而 M1 的定義就是「兩份 dump 相同」； 一個確定性的數值錯誤在兩邊一模一樣，所以它在原理上不可能被自比對抓到。 這個閘門證明的是確定性（determinism）與 M-invariance，不是正確性。

但那一項本身結案了，而且不是引擎的錯。直接回讀 GGUF 量到： 全零 expert row 是模型檔案自己的資料——全模型 35484 個 row（4 KB probe）中 只有 10 個全零（0.028%），全部集中在 layer 0 的 gate/up（experts 25/195/205/252） 與 layer 1 的 gate/up（expert 214），而 ffn_down_exps 一個都沒有。 每一個歷史警報都在 layer 1 / id=214，完全吻合。斷言的前提（「量化 expert 權重的前 4 KB 永不為零」） 對這個 denseIQ4X 混合量化 merge 出來的 GGUF 是不成立的。

真正的壞消息在另一邊：我們現在沒有任何可用的絕對 oracle。 上一輪才接上、並在上一份白皮書被稱為「真正的 cache-free launch」的 CGC_SERVER_EXPERT_CACHE_OFF=1，實測是壞的：探針回傳空字串， dump 的 argmax=59400、top-8 是連續 id 59400..59407 且全部並列 0.125、 sum=−6.83e38（超過 FLT_MAX，典型的未初始化／錯誤張量讀取）。 --load-mode none 與 --load-mode mmap 得到同一個 sum 到全精度， 所以不是「權重沒載入」，是這條路徑本身壞掉。結論：cache-ON 的正確性目前無法由任何獨立來源驗證。

1. 質疑的核心：自比對閘門抓不到確定性錯誤

M1/M2/M3 的三個指標定義是：M1 = row_fnv1a64 逐位元組相同； M2 = argmax_token 相同；M3 = top-N id 集合相同。 閘門把「本次 dump」與「參考 oracle」比對。這個結構有一個必然的盲點：

若錯誤是確定性的（deterministic），則
    參考 dump   = f(正確輸入) + 同一個錯誤
    本次 dump   = f(正確輸入) + 同一個錯誤
    => M1 = 1.0、M2 = 1.0、M3 = 1.0  ->  PASS

PASS 只推論出「兩次運行一致」，無法推論出「與真值一致」。

這不是理論擔憂 —— 它是本專案當時正在追的具體缺陷形態。而我們可以直接檢查 這個盲點有沒有被觸發：如果全零 row 真的落在探針的 forward pass 裡，那參考 dump 本身就已經 是在該 row 為零的狀態下算出來的。

2. 結案：全零 row 是模型檔案的事實

2.1 直接回讀 GGUF

不再從引擎側推論，直接把檔案讀出來。用 gguf.gguf_reader 取得 blk.1.ffn_gate_exps.weight 的 data_offset，再讀 offset + expert × nb02（nb02 = 335872）的前 4096 位元組：

blk.1.ffn_gate_exps.weight1614051 / 4096c0663f66c16e8def

blk.1 的 gate 與 up 在 expert 214 上都是 0 / 4096 個非零位元組， 而其他 expert 都是 4048–4055。注意兩者的 FNV 相同（b43a063055adc383）—— 因為兩者都是零。

2.2 全模型掃描：10 / 35484

對所有 *_exps.weight 逐 expert 做同樣的 4 KB probe 掃描：

total expert rows (4KB probe): 35484   all-zero-in-first-4KB: 10  (0.028%)
by kind: {'ffn_down_exps': '0/14306', 'ffn_gate_exps': '5/10589', 'ffn_up_exps': '5/10589'}

layer kind            n_zero  first ids
    0 ffn_gate_exps        4  [25, 195, 205, 252]
    0 ffn_up_exps          4  [25, 195, 205, 252]
    1 ffn_gate_exps        1  [214]
    1 ffn_up_exps          1  [214]

三個關鍵事實：

  1. 死 expert 只存在於 layer 0 與 layer 1，而 layer 0 在 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0=0 的生產配置下不進 slab 掃描 —— 所以唯一會發出警報的就是 layer 1 的 expert 214，與觀測完全一致。
  2. gate 與 up 的死 expert id 成對相同（layer 0 是 25/195/205/252，layer 1 是 214）， ffn_down_exps 則完全沒有 —— 這是混合量化 merge 的典型痕跡， 不是填充邏輯會產生的樣態（填充是按 row 位址寫入，不會「成對」漏）。
  3. 比例 0.028% 與早期 probe 記錄的「~0.3% of rows zero (4GB: 2/600, 8GB: 6/2048)」同數量級 —— 早期抽樣偏高，因為 sample 恰好落在 layer 0/1。

結論：斷言的前提「量化 expert 權重的前 4 KB 永不為零」對這個 GGUF 不成立。 這個 denseIQ4X merge 出來的模型本來就有死 expert。 引擎側從來看不到檔案，只看到 slab，所以它無法自行區分「模型本身是零」與「填充沒落地」—— 這件事必須由檔案裁決（見 §3）。

3. 裁決工具：mmid_zero_row_triage.py

斷言本身仍然有價值（它是「expert 貢獻被靜默丟棄」唯一的線上探針），問題只出在它無法自我裁決。 新增工具把每個警報的 expert row 直接用 mmid_pool_vs_gguf.py 同一套約定回讀 GGUF：

MODEL-ZERO   檔案該 row 也是零          -> 預期行為，不是缺陷，不要再追
ENGINE-ZERO  檔案該 row 非零但 slab 是零 -> 真正的 dropped-expert 缺陷
UNRESOLVED   id 無法映射到 expert        -> pool 路徑（ne02 < n_expert）缺少 CGC-EXACT-POST 對照表

兩個 id 約定的判別方式與既有工具一致：ne02 >= n_expert 表示 ids 是原始 expert id （M2 whole-layer slab 路徑）；否則表示 ids 是 slot index（pool 路徑），需要把 expert→slot 表反轉。全臂執行結果：

4. 被推翻的兩個假設（都有反證）

在拿到檔案證據之前，我先提出了兩個機制假設，兩個都被實驗推翻 —— 記在這裡是為了避免後人重走：

假設提議的機制反證
A. 雙緩衝丟棄回傳值 cgc_db_worker() 呼叫 llama_expert_cache_fill_layer_slab() 時沒有檢查回傳值 （llama-context.cpp:717），而非 DB 路徑會檢查 filled < 0 並退回（:4487）。失敗時 slab 只有部分被寫，未寫的 row 讀為 0。 用 CGC_M2_DB_DISABLE=1 關掉雙緩衝（改走同步且有檢查的填充路徑）： 全零 row 照樣出現，仍是 il=1 / id=214。
註：這個不對稱本身仍是真缺陷（見 §6），只是不是本項的元凶。
B. 短讀 fill_job() 的 pread 短讀使 ok[i]=0 → fill_segments_concurrent 回 false → 該 expert 目的地位元組未寫入。 LLAMA_EXPERT_CACHE_PREAD_DBG=1（該開關會在 rd != seg->bytes 時印出 offset/want/got/errno/fsize） 全場零輸出 —— 沒有任何短讀。

兩個反證同時也確立了另一件事：n_ids=1656 = 8×207 在 -b 512 與 -b 6144 下完全一樣，所以它與 chunk 寬度無關， 是模型層級的固定事實。

三個判讀：

  • top-8 是連續 id 且全部並列 0.125 —— 真實的 logit 分布不可能長這樣。 這是讀到未初始化／錯位張量的特徵，不是「模型答錯」。
  • sum = −6.83e38 超過 FLT_MAX（3.4e38）—— 若 logits 是 f32 且以 double 累加，單一元素不可能超出這個範圍。
  • 兩種 load-mode 得到同一個 sum 到全精度 —— 排除了「expert 權重沒被載入」 這個最直覺的解釋；壞的是這條路徑本身。

這同時修正了上一份白皮書的一句話。上一輪把 CGC_SERVER_EXPERT_CACHE_OFF=1 描述為「a genuine cache-free launch」—— 它確實能啟動（不帶 -expert-cache），但輸出無效。 「能啟動」不等於「能當 oracle」。在修好之前，任何「絕對正確性已驗證」的敘述都是不成立的。

6. M1/M2/M3 的定位修正（以及它仍然值得留著的理由）

基於 §1，這個閘門的 verdict 應該被讀成 determinism / invariance gate， 而不是 correctness gate。但它並未因此失去價值：

  • 它是唯一能在 16 GB 機器上跑得動的逐位元閘門。絕對 oracle 目前不存在（§5）， 而在它存在之前，M1/M2/M3 是唯一能回答「這次改動有沒有移動數值」的量具。
  • 它抓到的都是真的。最近一輪它抓出 4 個真 bug （M2 slab 的 UNREPOINT、pick_slot 的 SpAc victim 上界、llama-bench harness 的 test_time 型別錯誤、串流 JSON 被中途 OOM 截斷而丟棄已完成 instance）。
  • 它驗證了 M-invariance。本輪的 con_small 臂（ctx 4096 / b512） 對參考（ctx 8192 / b6144）仍是 M1 = 9/9 —— 也就是 CGC_MM_BITIDENT=1 讓 ne11 ≤ 8 全走 mul_mv 所帶來的 M-invariance 是真的、且跨 chunk 寬度成立。這是一個有內容的正面結論。

建議的後續動作（尚未執行）：

  1. 把閘門輸出裡的 VERDICT M1 (numeric identity) 改標為 determinism / invariance，並在結尾自動呼叫 triage 印出 zero_row 的分類摘要。
  2. 修好 cache-OFF 路徑（§5），或另建獨立 oracle —— 見 §7。

7. 正確性要怎麼真的被證明（尚未完成）

既然自比對不夠、而 cache-OFF 壞掉，正確性需要獨立來源。三條可行路徑，依成本排序：

路徑作法狀態
1. 修好 cache-free 路徑 cache-OFF 的輸出是確定性的垃圾（同 sum 到全精度）， 所以它是可除錯的：從 result_output 的張列印往回追， 先確認 src0 是否真的指向專家權重、再確認 n_vocab 與 logits 的 stride。 未開始（本輪只確立它是壞的）
2. 同一 prompt 對照上游 build 用不含 CGC 改動的 versions/llama_roadB/upstream_ref build，在同一 GGUF、 同一 prompt 上取 logits，作為絕對參考。只要 prompt 的 token 序列可對齊即可比對。 未開始
3. 可加性檢查 把某層某 expert 的 slab row 在讀取前人為清零，量測 logits 變化； 再對照「該 expert 在檔案裡的 delta」。若兩者一致，則 slab 路徑對該 expert 的讀取是忠實的。 未開始

在這三條之一完成之前，白皮書的立場是：正確性未驗證（unverified），而非已驗證或已知有錯。
