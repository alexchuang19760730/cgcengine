## 1. 為什麼需要一份事先登記的協定

現況（`Backup/k_abba_2026-09-23/`，5 對 ABBA）：

```
n=5 pairs   mean diff +1.71 t/s (+16.4%)   sd 1.83   SE 0.82   t=2.08  crit=2.78 (df=4)
k3 slower in 4/5 pairs
VERDICT: NOT YET  -- n=5 < planned 7: testing now would be optional stopping
```

我上一輪寫「再 2 對就夠（n=7）」。**那個數字太緊，本文件把它改成 8**：

- n=7 時 `t = 1.71/(1.83/√7) = 2.47`，而 df=6 的臨界是 **2.447** ⇒ 只過 **0.025**。
  而 1.83 這個 sd 本身是 n=5 估出來的，再抽 2 對它一定會動 —— **這是一場 50/50 的賭，不是一個設計。**
- n=8 時 `t = 2.64`，df=7 臨界 **2.365** ⇒ 有餘裕；而且臨界值本身從 2.776 降到 2.365。
- 但 **k=3 是雙峰**（§7.3），新抽的對可能把 sd 撐大 ⇒ 即使 n=8 也可能不過。
  ⇒ 所以第 5 節預先登記好「不過的時候要做什麼」，**而不是繼續加對**。

⚠ **已經偷看過一次**：n=5 的 t=2.08 / p≈0.11 是我算出來的，也就是說這份協定是在看過資料後寫的。
這會讓名目 α 略微失真。可以做的補償是：**把判決做一次、做在 n=8**，且不在中途再看 t。
（無法補償的部分：我已經知道 p≈0.11，所以不會有「n=8 但不顯著 ⇒ 就當沒這回事」的藉口；
不顯著也要照第 5 節走。）

## 4. 順便：把 `pread_usec` 打開 —— **不用 rebuild**

`llama-expert-cache.cpp:418` 的 `rig_snapshot()` 會印
`CGC-RIG-SNAPSHOT … pread_usec=… fill_usec=… fill_wait_us=… reads=… hits=… misses=…`，
**逐 request** 解析（相鄰兩次 snapshot 相減）。它唯一的呼叫點是
`refresh_prefill_protect()`（`:446`），而那個函式在 `CGC_PREFILL_PROTECT_FILE` 未設時**直接 return**。

09-23 全部 log 零命中 ⇒ 就是因為沒設這個 env。

```sh
# flag 檔內容用 "0"：prefill-protect 維持關閉（= 目前預設行為），但 rig 照樣 snapshot
# 後面綴一個序號是為了觸發「內容變更」判定（:458 只在內容變了才印）
printf '0\n%s' "$i" > /tmp/ka/ppflag
# 加到 SERVER_ENV：
CGC_PREFILL_PROTECT_FILE=/tmp/ka/ppflag
```

⚠ **兩個陷阱**
1. **不要用 `CGC_PREFILL_PROTECT` env** —— `cgc_prefill_protect_on()` 用
   `getenv(...) != nullptr`（`:474`），所以 `CGC_PREFILL_PROTECT=0` **也會把功能打開**。
   要維持現狀就用 FILE 寫 `"0"`。
2. `docs/O1_PREFILL_PROTECT_RERUN_2026-09-19.md:87` 寫的 `CGC_RIG_SNAPSHOT=1` **在 src 裡不存在**
   （已 grep 確認）—— 那行是過時/多餘的，別照抄。

這樣同一趟就能同時拿到：① 配對 t/s ② 每次 arm 的真實 `pread_usec`
⇒ 可以直接檢定「k=3 的慢狀態是不是池 IO 服務時間造成的」，不需要多跑 arm。
