1. 問題與前情

250 t/s 一直被當成「達得到、但只有 1/11 的機率」的目標。上一輪（PREFILL250_CERTIFIABILITY_20260916.html） 用 11 次獨立啟動證明：組內離散只有 2–15%，而組間離散 84%，所以差異是「行程之間的狀態」而非量測噪聲； 並把候選機制 free 記憶體（rho −0.70）與 page cache（強制拉高 4.3× 無效）雙雙否證， 結論是「250 是離群值，操作點是 ~170」。那個結論有一半是對的，漏掉的是一個協變量。

漏掉的那一問：那個離群值，是不是「這個 session 的第一次啟動」？ 前兩輪把 286.67 的環境記成「free 3.90 GiB」，卻沒有記「前一次 GPU 負載在幾分鐘前結束」。

2.1 為什麼「286.67 vs 179.09」不是一對可做引擎內部對拆的樣本

下一步原本的構想是把 286.67（wall 45 s）與 179.09（wall 73 s）逐段對拆，理由是 「兩者啟動狀態幾乎相同，差異只可能在引擎內部」。這個前提在資料上不成立—— 而且是在兩個層次上：它只在 free_gib 這一軸上「幾乎相同」，而這一對其實是 兩個不同 session 的第一次啟動，差別正好落在「啟動前間隔多久」這個自變數上。

3.2 逐層歸因：把 CGC-DECPROF 打開之後，答案是「全層等比」

§3 與 §3.1 只證明「GPU 忙著」。§8 第 1 項當初規劃的下一步，是改一行讓 CGC-DECPROF 看見 prefill，然後問一個更細的問題：是某一層變慢，還是全層等比變慢？ 前者指向實作，後者指向時脈／功耗。這一項已經做完，答案是全層等比。

快慢對拆：逐層比值

第一次做這個對拆時，我拿的是「快探針（285.58 t/s）」對「慢跑（122.39 t/s）」，得到 2.32×（CV 6.5%）對吞吐 2.33×。那個數字結論是對的，但證據是壞的， 所以本節改用一組乾淨的配對，並把理由寫下來。

陷阱 A：兩份日誌的層覆蓋不同，配對會偷偷偏向參考跑最貴的層。 快探針那份日誌（2026-09-16 02:58:54）是在 CGC_DECODE_PROFILE_ALL 生效之前抓的， 所以它每個圖只列印 top1..top8 共 80 行；sweep 的日誌（03:01:36 起）每個圖列印 all1..all40 共 400 行（llama_bench_matrix.py 的 mtime 03:00:53 正好落在兩者之間）。 於是「共同層」只剩快跑的 top-8，而那 8 層是由快跑自己的成本排名選出來的——不是隨機抽樣， 而且它們恰好全落在 L28–L38 這段（比值一致地 ~2.3×）。用不同粒度的子集做配對，等於自己挑了樣本。

乾淨的配對必須兩邊都覆蓋全部 40 層。以下用同一輪 sweep 裡的一快一慢：preheat session（198.64 t/s） 對 idle=0 run 1（122.39 t/s），兩個 session 都有 _ALL 生效、都是 4 個 prefill 圖。

答案仍然是「全層等比」，但這次的證據站得住。全部 40 層、跨 4 個 prefill 圖平均之後， 逐層 slow/fast 是 1.60×，層間 CV 8.7%（min 1.25、max 2.06）； 吞吐比值是 1.62×。兩者一致到 1.2% 以內。慢的那一次不是某一層壞掉， 而是整張圖以同一個倍率變慢，且倍率等於吞吐損失 ⇒ 依 §3 與 §6 的判準， 這指向 時脈／功耗上限，不是實作熱點。

三個邊界一起讀：(1) 殘留的 L4–L8 隆起是真的、但很小——L5 的比值 2.06 是中位數 1.59 的 1.30 倍，未達 1.5 倍的標記門檻；L5+L6 合計只佔 wait 缺口 （15585.8 − 9767.6 = 5818 ms）的約 3.5%，其餘 96% 是廣泛的等比放大。 (2) L1 的比值 1.25 是最低者、L0 是 1.27：submit_ahead 之下第 i 層等的是「到第 i 層為止 累積的 GPU 工作量」，所以最前面幾層無論快慢都等得少，這是管線填充而非例外。 (3) 快的那份日誌是同日的一次 preheat session（198.64 t/s），不是 285 t/s 的冷態， 所以這一對量的是「熱 vs 更熱」的 1.62× 差，不是 250 的全距。

陷阱 B：不要把「單一圖的逐層剖面」當成穩態剖面。 同一份資料，只讀第一個 prefill 圖時，比值是 mean=1.64×、CV=30.1%、 L5 高達 3.50×，判定會翻成 NOT UNIFORM：去找某一層； 改成跨 4 個圖平均後，同一份資料是 1.60×、CV 8.7%。差別全部來自每個行程一次的 載入／首次觸碰暫態，而那個暫態落在哪幾層是取決於時序、不是取決於那幾層的實作。 所以「層間 CV」本身就是一個會被儀器讀法左右的量：讀一個圖會把它放大約 3 倍。 驗證方法很便宜——把每個圖的 worst layer 印出來（上面的診斷區塊）：它如果在圖之間漂移， 那就是暫態，不是層的性質。

陷阱 C：不要用 peak/mean 判斷「均勻還是局部」。 慢跑的 peak/mean = 1.75，用「> 1.5 就是單層問題」的門檻會判成 LOCALISED—— 但那個峰值屬於管線爬升段，而 L0–L4 全部低於平台。把最大值除以平均值，等於讓一個結構性的暫態 去支配判準。改用 中位數 + IQR/中位數 + 落在中位數 ±25% 內的層比例， 同一份資料立刻變成 UNIFORM。這個修正在 scripts/check/prefill_certifiability.py 的 harvester 裡（欄位 dpq1_lay_w_median_ms、dpq1_lay_w_iqr_over_median、 dpq1_lay_w_frac_within_25pct）。

附帶一個可用的副產品：cb（top-k hook，含阻塞式填充）在快取冷時明顯偏高—— 探針第一次 prefill 的 cb=982 ms、第二次 184 ms； 慢跑是 383.68 ms 對 121.38 ms。這證明「每個行程的第一個 prefill 圖要付 一次冷填充成本」是可量測的，也解釋了 step=1 為何系統性貴於 step=2。 但它的量級（~0.1–0.4 s）遠小於 wait（6.2–14.4 s），所以不是快慢之別的主因。

7. 可操作規則

  1. 報 prefill 數字時必附三件事：本 session 第幾次啟動、距上次啟動結束的間隔秒數、 gpu_union/wait。只看「第幾次」會把熱暫態誤讀成抽獎。 間隔必須是導出值或儀器值，不是估計值——本報告初版就是在這一欄放了沒有來源的數字 （§2.2）。
  2. 要 250，就讓它是間隔後第一次，而且間隔 ≥ 150 秒（§3.3 直接量到 120 s < τ ≤ 150 s；舊文的「≥ 247 s 已足夠、67 s 不足」方向對但太寬）。 這是配置層面的操作規則，不是程式碼修復。
  3. 把 165 當成「間歇負載」的規格，但要知道熱態會繼續下探：連續熱跑（中間隔 0–120 s） 本輪觀察到低到 122 t/s（§3.3）。冷啟動可達 250–308。 三個數字都是真的，差別在操作點；單獨引用任一個都是錯的。

  • pick_slot 的淘汰會清掉被犧牲者的 slot 表條目 （slot_table[layer*n_expert + evicted] = -1，llama-expert-cache.cpp:~555）⇒ 淘汰對同一個 batch 的其餘成員是可見的，一次 eviction 會把一個 resident 成員變成 miss。
  • ensure_batch 的 batch_owned（註解自稱「本 batch 讀的 slot，批次中永不淘汰」） 是和 miss 指派同一個迴圈裡增量填入的 ⇒ 只有已經走過的成員被保護， 還沒走到的仍然可被淘汰。

於是 ids=[0..7] 對上一個滿池：expert 0 冷 ⇒ miss ⇒ 淘汰掉下一個成員的 slot ⇒ 那個成員變冷 ⇒ miss ⇒ 再淘汰下一個 ⇒ 連鎖。每個成員拿到的是後面那個的 slot， 這正是日誌裡的 st[e] = e+1。（第一個犧牲者為何是 slot 1 而不是 slot 0： 那一刻 slot 0 不是候選（busy 或 pinned），日誌單獨看不出是哪條 skip 規則生效；但連鎖不依賴它—— 任何 index k 的第一個犧牲者，都給 k 之後的所有成員同樣的 +1 位移。） il=2 的 NaN 是下游簽名、不是因：映射位移一格 ⇒ 每個 expert 讀到別人的權重， 而位移會把池的 residency 上緣推過最後一個可用 slot ⇒ 池區 OOB 讀，這是會產生 NaN 而不只是「算錯」的那一類。

修法（已實作）：ensure_batch 改兩趟指派。 pass 1 先認領每個 resident 成員的 slot，pass 2 才配 miss ⇒ pass 2 挑的犧牲者 不可能是本 batch 要讀的格。pass 1 另外收養 in-flight fill： slot_owner[s] = e 且 slot_queued/loading 已設、但 slot_table[e] 尚未發布時，舊的 hit 判定只看 slot_table[e] ⇒ 會把它判成冷的 ⇒ pass 2 會給它第二個 slot（一個 expert 兩個 slot）。新增計數器 n_hit_adopted_queued 讓這條路徑可見而不是靜默。 另加閘門 LLAMA_EXPERT_CACHE_BATCH_INVARIANT=1（並接進 run_server.sh 的 SERVER_ENV 白名單，否則生產入口設不到它），在每個分層 batch 上重驗 「slot 互異 / slot_table[e] 讀得回來 / slot_owner 相符」—— 原本的失敗是靜默的（每個被選中的 expert 都有一個 slot，只是錯的），所以這裡是驗證、不是假設。

9.1 「被一個設計不變量擋住」是什麼意思，以及為什麼那不等於「沒辦法」

先釘「解在出貨碼上」這句話的位置。blocker B 的修法在 2b284667f， 它就是 demo/sweet-spot-windows-fix 的尖端（不是側分支）， 改的是 src/llama.cpp/src/llama-expert-cache.cpp——出貨路徑，不是實驗分支， 且與 libllama.0.0.239.dylib 同一個 commit（檢查 8）。兩個保守的補充： (a) 它還沒有推到任何遠端——最新的遠端副本 cgcengine0907/demo/sweet-spot-windows-fix 是它的祖先，落後 7 個 commit；(b) 「在出貨碼上」不等於「在出貨配置上生效」， 對預設（非 split）配置它是量到的 no-op，見本節下方的界線。

上面那句話值得展開，因為它很容易被讀成一句安慰。它不是——它是一個可查核的述句， 而且它改變的是下一件工作的種類。先把兩個詞釘在原始碼上。

「wide 路徑」是什麼。CGC_POOL_SPLIT=1（預設 OFF，開啟時會大聲警告） 做的是三件事同時發生：載入器不再把 expert 張量的 ne[2] 縮到池容量、 池自有一塊 buffer、以及解除 n_batch 的夾制。 解除夾制之後，一個 16 成員的 batch 就會以 ntok=16 mode=wide ne2=256 出發——也就是 Metal 要隔著「模型的權重 buffer」 去讀一個 256-expert 的張量。原碼明寫這就是載入器縮張量存在的原因：

llama-context.cpp:268  [CGC M1 work item 1 CGC_POOL_SPLIT, 2026-09-14] The clamp is NOT lifted for an owned pool.
                       ... lifting it produced a `ntok=16 mode=wide ne2=256` build whose Metal encoder faulted,
                       and the hook at il=2 then reported router ids that are the bit pattern of a NaN.
                       The wide path means Metal reading a 256-expert tensor through the model's weight buffer,
                       which is the exact configuration this engine's loader shrink exists to avoid.

它為什麼是「不變量」而不是「難度」——機制在另一份文件裡，而且它不是數值問題。 M1_POOL_GRAPH_DECOUPLE_PLAN_2026-09-14.md §2 把機制寫成一句： gather 路徑把一個住在 Metal buffer 裡的 expert 張量重新指向一個 Metal 從未被通知過的 host 指標。於是 Metal 找不到那塊 buffer、什麼都不讀：

ggml-metal-device.m:2026: error: tensor '%s' buffer is nil

而在 2 GiB／n_slots=35 的實測裡，這件事的形狀是整份文件最該記住的一行：

0 次 abort。這是不變量與 bug 的分界線。它不報錯，它靜默地算錯—— 而那比 abort 嚴格更糟：abort 會被看見，錯的值會一路流下去（這正是本專案 §6 那條 「印四條空序列與量到零同形」的同一個家族）。計畫文件對它的判語是 「the union>slots region is broken by construction: there is no legal place to put the weights」 ——沒有合法的位置放權重，而這是幾何問題，不是找 bug 能解決的問題。

所以「設計不變量」的準確意思是：三個部件互相扣住，而拆掉任一個不會得到部分進展。

這就是「被難度擋住」與「被不變量擋住」的差別。被難度擋住時，投入更多努力（更多搜尋、更多假設） 會被回報，因為某處有一個 bug；被不變量擋住時，努力施加在單一部件上會讓狀態變壞 （從報錯變成靜默算錯），而出口是可以列舉的——這裡恰好兩條，而且兩條都是明示的：

  1. 讓 Metal 正確地讀 wide 張量：後端問題，動的是 Metal kernel 與 buffer 綁定。
  2. 讓 wide 路徑不需要存在：給常駐的 wide 區域一塊真的記憶體， 而不是把 Metal 已知的 buffer 重指向一個未知的 host 指標。

而第 2 條不是願望——它已經實作過一次，而且正在跑。 CGC_PREFILL_STREAM=1（M2 prefill streaming）服務 6144-token chunk 的方法， 就是把 expert 權重從 GGUF 直接讀進一塊暫時的 Metal slab，ne[2] = n_expert、 remap id 用原始 expert id。那就是 wide 幾何，而它能正確讀—— §3.3／§10 那些 276–308 t/s 的數字全部跑在這條路上；計畫文件也已經把它寫成下一步： 「that is exactly why the region needs a real slab」，且早先的測試 3 證明 Metal 可以配置 280 MB+ 的連續 buffer 並整層 batch-matmul 一個 768 MB 的 layer。

那為什麼還要說「verdict 不變」——兩條誠實界線。 第一，修好 wide 路徑是 M1/W3 的前提，不是吞吐結果： blocker B 的修法在出貨預設（非 split）配置下量到是 no-op（逐位元相同）， wide 路徑同理——就算通了，那也只是一句「現在可以量了」，數字仍要另一次量測才會出現。 第二，唯一能證明「下一步真的是 wide 路徑」的那個實驗（split 配置的真機 served request） 做不了：10 GiB 與 4 GiB 兩種池預算都在 warmup 掛 CGC-METAL-FAIL ... status 5 (Insufficient Memory)。所以「下一步是 wide 路徑」 這句話的依據是排除法 + 原始碼（槽位配置已被證明可以在單元層修好並回歸， 而 wide 路徑有明示的結構障礙），不是一次端到端的成功。

那件事後來做掉了（0a4bfd73c）——而且它比「一行註解」大。 原本這裡記著：llama.cpp:420-423 的警告註解仍記載著已被取代的診斷 （"degenerate routing at il=1 (the remap maps two experts to one slot)"）， 而日誌寫的是 st[1]=2、擷取裡沒有任何一行顯示兩個 expert 共用一個 slot。 當時刻意沒動它，理由是檢查 8 要求 src/ 改動要一起 stage dylib， 為一行註解重建整個庫不該塞進「頻率／散熱」那個 commit。

實際動手時才發現的第二個問題：不只那行註解該更正。 同一段落的 LLAMA_LOG_WARN 把同一個被推翻的診斷當成出貨字串在印 （"EXPERIMENTAL, KNOWN-BROKEN configuration (degenerate routing + SIGSEGV)"）。 所以 2b284667f 之後的那棵樹裡，文件說「那不是原因」、binary 說「那是原因」—— 而且讀者不同：文件是維護者讀的，這個 WARN 是操作者讀的。 更正後的新字串已用 strings -a … | grep -F 確認進了二進位，而舊字串消失 （「消失」那一半比「出現」那一半重要：改了註解卻把舊字串留在 string table 裡， 是同一個缺陷往下一層）。

順帶更正了那段註解的兩個事實錯誤：它宣稱的原因是 blocker A（wide 張量／ Metal buffer is nil），而 blocker A 是靜默失敗 （0 次 abort、234 次 buffer-is-nil、M1 2/42）——這正是警告必須留在大聲的原因。 D5：RUN, PASS（M1/M2/M3 各 9/9、fnv1a64 9/9、cross-tab 9/0/0/0）。 見 lesson eng-gate-0028。

10. 追加（2026-09-16 上午）：§3／§5 的開放問題有答案了 —— 是時脈，而且是熱壓選的

10.6 對 prefill 250 的意義

250 之所以是「冷態的數字」，不是因為冷態有什麼魔法，是因為冷態坐在最高檔上。 這台機器的 GPU 最高 DVFS 檔位是 1470 MHz，而冷態有 71% 的活躍時間就坐在那一階。 熱態把整個操作點移下去（928 → 618 MHz），於是吞吐跟著掉到 151 t/s。 「250」與「151」因此在同一個座標軸上：它們是同一份工作的兩個操作點，差別是散熱器讓 GPU 能跑哪一階， 不是引擎換了路徑。

而且障礙已經被量化：最高檔 → 穩定檔是 1470 → 618 MHz，掉 58%； 吞吐是 276.25 → 151.28 t/s，掉 45%。兩者不是 1:1。

邊界：R² 0.9987 是三個點配兩個參數，只剩 1 個自由度。 它證明「這個形式能容納資料」，不證明那個 0.558 ms 是精確值——樣本數只有 3。 可被引用的是方向性的兩個述句：(1) 純 1/f 縮放與資料不符（上面那兩個差值）， 這不需要任何擬合就成立；(2) 因此存在一個不隨時脈縮放的成分。它的量級需要更多時脈台階才敢定。

另外一個可以立刻使用的結論：散熱狀態的操作點是階梯，不是連續值。 本輪量到兩個清楚的平台（928 與 618 MHz），各自由 governor 選定後鎖住數十秒不動。 這對「要 250 就等 150 秒」（§7 第 2 條）是同一個機制的另一面： 冷的判準是「回到最高檔」，而不是「降了幾度」。

10.7 這一節不說

  • 不改變 decode。本節從頭到尾是 n_gen=0 的 prefill 擷取。 decode 對熱狀態不敏感這件事（§5 第 1 條）完全未動——25 tok/s 那條路仍與本節無關。
  • 不指認「哪個感測器」或「幾度」。熱壓等級是 macOS 的綜合分級， 本節證明它與時脈同步、且領先時脈，但沒有拿到溫度讀數，也沒有做熱模型。 「Nominal→Heavy」到此為止是一個因果相鄰的觀測，不是完整的熱力學解釋。
  • 不宣稱 151 t/s 是熱態下限。§3.3 在同一台機器上量過 122.39 t/s； 本輪最深只到 151.28，所以這道階梯下面還有階。
  • 不宣稱 250 是硬體極限。250 只是最高檔給出的值。真正未被回答的是 「那些不隨時脈縮放的 15.4% 是什麼」——那是下一個可動的目標。
  • 樣本仍小。一個 session、三次啟動、一份擷取。 但熱壓翻轉與時脈下降的逐樣本鎖定（§10.4）不是統計推論，是那 10 行的原文。

10.10 把兩半接起來：頻率／散熱 → prefill 的因果鏈，以及「250 的設定」是什麼

10.10.1 因果鏈：五個環，每一環都有獨立儀器

這條鏈的重點不是「頻率會影響速度」——那是廢話。重點是③ 這一環不屬於引擎： ①②之間沒有可調的設定，②→③ 是 thermal governor 的決定， 而 ③ 一旦被選定就會鎖住數十秒（§10.6：量到 928 與 618 兩個平台各維持數十秒不動）。 所以引擎的旗標能不能到 250，取決於它跑的時候 governor 把它放在哪一階。

10.10.5 這一節不說 —— 一個未解的觀察者差異

一句話：要 250，就是 CGC_SERVER_PROFILE=prefill250 加上機器安靜 150 秒以上，加上只採信每個 session 的第一筆。 三層裡有兩層不在程式裡。
而 250 不是這台機器的上限：最高階 1470 MHz 的純階預測是 291.3 t/s， §3.3 也真的量到 294–308。250 只是那一階之上的一道檻；真正的天花板是 §10.6 那個不隨時脈縮放的 0.558 ms／token 地板（冷態佔 15.4%）。

11.12.1 item 2｜mmap × expert cache：修在張量落點，不是修在 expert cache

原缺陷（12:02 量測）不是「pool 不能是唯讀映射」這種模糊描述，而是一條寫死的假設： expert cache 的 L4 pool 是 regions adopted from expert tensors（log 原句）， 它直接寫進模型張量的儲存。而 src/llama-expert-cache.cpp:693-710 的 fill_pool_direct 有一條復原路徑「短讀取 → memset 清零」， 這條路徑預設了 dst 可寫。--load-mode none 時那是可寫的堆積，所以假設成立； mmap 時那是唯讀的 file-backed 映射，於是 __bzero 觸發 KERN_PROTECTION_FAILURE。log 第 17 行那句「short read … zeroing slot」是誤導： pread 成功，fault 的是那個 memset。

修法是換張量的身分，不是換它的家。關鍵在 src/llama-model.cpp:1595：mmap fast path 只在 is_default_buft（buft == ggml_backend_dev_buffer_type(dev)）時成立。 於是新增一個與 shared buft 逐項相同、但物件身分不同的 buft： Metal 後端廣告 MTL<i>_Pool（ggml-metal.cpp， get_alloc_size 也照抄，因為 GGML_OP_MUL_MAT_ID 的 extra_tpe/extra_ids 不可省），loader 在 use_mmap 時為 L4 pool tensor 選它（llama-model-loader.cpp:select_pool_buft，名字是唯一契約）。 其餘權重照樣走 zero-copy 檔案映射 —— 這正是修復的價值：模型頁仍然可回收。 條件式選取 ⇒ load_mode=none 的 buft 選擇與以前逐位元相同。

11.12.4 item 5｜cmd_buf_last：從借用改成持有

cmd_buf_last 是「這個 context 佇列的最後一個 buffer」，讓 synchronize 不必知道它落在 cmd_bufs[] 還是 cmd_bufs_ext。 它原本是借用指標：每個賦值站都存一個自己不擁有的指標，而所有者在其腳下釋放它 （cmd_bufs[cb_idx].obj 每次 graph_compute 都 release+replace； cmd_bufs_ext 會被 removeAllObjects 清空）， 於是存在一個窗口：指標指向已解構的物件，而三個讀者 （synchronize、capture 路徑、drain hook）會對它發訊息。

改成持有：cgc_set_cmd_buf_last（相同物件則 no-op，否則 release 舊的、retain 新的） 與 cgc_clear_cmd_buf_last。7 個賦值站全部改走前者 （set_tensor_async、get_tensor_async、cpy_tensor_async、 graph_compute 的主 buffer 與其餘 buffer、event_record、event_wait）， 2 個清除站（synchronize 的 wait 之後、capture 路徑）與 ggml_metal_free 各改走後者。

並且我把「夠不夠」查了，而不是假設。 cmd_buf_last 的每一個讀者都在那條變更它的執行緒上（drain hook 在 graph_compute 之內，不是 watchdog queue）； watchdog queue 是唯一另一個能碰到這個 struct 的執行緒，而它從不讀這個欄位 （只碰 cgc_watchdog_* 與 per-cb 時間戳）。所以持有參照在這裡是充分的； 跨執行緒的讀者會額外需要自己的 retain —— 這一點寫進註解，因為未來的人加一個讀者時就會踩到。

11.12.5 item 4｜最快的證據路徑上有三個缺陷，不是一個

(a) newest_ips（原本要修的那個）。 舊寫法是 ls -t … | head -1 再與 before 值比較：看起來是 difference test， 實際是 ordering test，分不出「這一臂當了」與「磁碟上最新那個檔換了」。 實測失敗（12:05）：6144 對照臂把 29 分鐘前別的臂寫的 llama-server-2026-09-16-113649.ips 報成自己的。改成 「臂前快照集合 + 差集 + mtime ≥ 臂起始時間（第二張網，因為 ReportCrash 會在行程死後才發布）」。修後的真陽性驗證：12:46 那臂正確列出自己的 llama-server-2026-09-16-124700.ips；13:23–13:26 四個會當的臂各列出自己的那一個。

(b) newest_server_log（修 (a) 的路上發現的）。 它 glob 的是 $PWD/$OUTDIR，但 server log 住在 $ROOT/Backup/cgc_logs（run_server.sh:466-467 是硬編目錄）。 於是每一個自訂 OUTDIR 的臂都空轉完整的 240 秒， 然後在報告裡寫 log=<none> —— 那讀起來像「server 沒有產生 log」， 而不是「這隻腳本看錯目錄」。修後單臂時間 5m15s → 1m33s， 而且 log= 欄現在指向真正的檔案。

(c) OUTDIR 從來沒有被建立（在 (b) 修完之後才暴露）。 env … run_server.sh > "$OUTDIR/<x>.driver.log" 2>&1 & 在目錄不存在時 失敗在重導向、因此根本沒有執行 run_server.sh：沒有 server、沒有 server log， 而報告印出 ready=no last_request=0 survived=n/a —— 與「server 起來然後死了」 完全同形。實測：13:39:34 的驗收臂就是這樣（OUTDIR=Backup/cgc_logs/prod_accept 不存在）， 連它自己的報告都寫不出來（tee: … No such file or directory）。 修法：開頭 mkdir -p "$OUTDIR" || exit 2。

(d) 同一次暴露出來的第四件事：沒有 before-set 時，它宣稱了 8 個不屬於它的報告。 因為 new_ips 在快照檔不存在時把 before 當成空集合 ⇒ 磁碟上每一個報告都變成「新的」。 13:39:34 那一跑因此把 12:47 到 13:35 之間別的臂寫的 8 份報告列成自己的。 修法：快照檔不存在時拒絕歸因（明印 crash-report attribution: UNAVAILABLE），因為「不能分辨」與「沒有」是不同的斷言。 驅動腳本的 parser 也跟著把這種臂的 crashes 記成 ?，不是 0。

另外補了一個真正的競態：ReportCrash 的發布延遲。12:46 那臂約在 12:46:56 死，它的 .ips mtime 是 12:47:00 —— 約 4 秒，而腳本只 sleep 3。 那個臂之所以還是列對了，部分是因為當時還有一個 240 秒的空轉墊在後面（即 (b)）。 移除 (b) 之後這條競態就露出來了，所以改成「只在臂看起來當掉時」有界地輪詢（最多 60 秒， 一有報告就停），健康的臂仍然只付 3 秒。目前還沒有觀察到漏抓（移除空轉後 4/4 個會當的臂都歸因正確） —— 這是預防，不是修一個已觀察到的失敗。

11.12.6 item 3｜build_fork_llama.sh：政策漂移改成可驗的契約

原本的問題不是「腳本與 live build dir 不一致」而已 —— 是那些差異是刻意的，而且無法事後歸屬。 改動前的 6 列漂移裡，4 個 GGML_* 是真正的政策漂移， LLAMA_BUILD_SERVER/LLAMA_BUILD_TESTS 則是 devserver 為了要 server target 刻意要的。 所以修法不是「讓它們一致」，而是讓選擇顯式且可檢查：

  • CGC_BUILD_PROFILE=prod|devserver（prod＝SERVER/TESTS=OFF、 devserver＝ON；未知值 exit 2）。
  • 移除 LLAMA_CURL：llama_option_depr(WARNING LLAMA_CURL) （CMakeLists.txt:186）只在傳 ON 時才建立 cache 條目， 所以傳 OFF 是死旗標，只會讓腳本的旗標集與 live dir永遠差一列。
  • --check 一命令給裁決：devserver 10/10 PASS； prod 4 列 FAIL（1 列 profile ＋ 3 列刻意的 SERVER/APP/TESTS）。
  • build dir stamp build/CGC_BUILD_PROFILE.txt：profile、built_at、git_head、 dirty 檔數、各旗標、MTP_SUPPORT ⇒ 哪個 profile 產生這個 binary 事後可答。

  • 順手修 --check 的預設：裸跑時改成對這個目錄自己的 stamp 檢查 （沒有要求 profile 就沒有理由用 prod 去比），否則每一次裸跑都會印 4 列差異， 訓練讀者忽略整份報告。

重建後的產物副作用要一起記：SONAME 由 0.0.277 走到 0.0.279， 新的 libllama-common/libllama/libmtmd 三個 .0.0.279.dylib 必須與 symlink 重指同一個 commit（check_build_tracked.sh 會把六個 symlink 目標逐列印成 tracked）。

11.12.8 這一節能說與不能說

能說：(1) mmap × expert cache 的缺陷本體已修，修在張量落點 （一個非 device-default 的 _Pool buft），而且沒有動 expert cache 一行； 載入階段的 SIGBUS 消失，閘門五面對照全部逐字符合預期。 (2) OOM 的邊界是 (pool + compute) 的和，兩個方向都量到了（ub↓ 或 池↓ 都能救）， 這讓它從形容詞變成一個可以用旋鈕移動的邊界。 (3) cmd_buf_last 已改成持有，而且「所有讀者都在變更的那條執行緒上」是查過的。 (4) 那一隻證據腳本裡三個同型缺陷（ordering test、看錯目錄、沒建 OUTDIR）都已修， 單臂時間 5m15s → 1m33s。 (5) build profile 契約與 stamp 落地，--check 可裁決。 (6) 出廠預設從 0/5 死的 6144 改成 4/4 活的 5632，並在出廠預設上量到 256–274 t/s prefill。

不能說：(1) 不能說 mmap 的缺陷只是被擋住、修它要動 expert cache —— 已被本節推翻。(2) 不能說 ≤6144 的繞道要付 −22% —— 那個數字來自別的 binary。 (3) 不能說 OOM 被修好了 —— 它只是被一個旋鈕移開；真正的解要讓 resident footprint 低於實體記憶體，那要動模型側。 (4) 不能說 mmap 可用 —— 它在任何量過的寬度都 0/5，而且會把 Metal 工作集撐大。 (5) 不能說 prefill 250 是隨時可重現的 —— 它是這個設定在有餘裕的機器狀態下的表現， 同指紋可以差到 2 倍。 (6) 不能說 _Pool 這件事有 log 行可引用 —— 沒有，證據是行為的。 (7) 不能說 5632 是邊界值 —— 它是量到的最高存活樣本， 邊界落在 (5632, 6144]；5888 沒量過。

11.14.7 為什麼閘門只能「分類」而不能「強制」

pmset -g therm 在本機只回 Note: No thermal warning level has been recorded（非 root 讀不到等級）； 讀 DVFS 駐留與有效時脈需要 root 的 powermetrics（§3.5、§10.1）。 所以沒有任何非 root 的即時儀器可以回答「governor 現在選了哪一階」。 閘門因此不能「強制」條件，只能分類這一臂的宣稱——見 §11.14.8。 這個區別不是措辭：一個會宣稱「已滿足前提」而其實讀不到的閘門，比沒有閘門更糟。

11.14.8 儀器改動：把「這一臂是什麼」變成機器判定

Backup/run_req2_retest.sh（gitignored）新增三態標籤：

標籤條件對應的宣稱權
COLD-STATE距上一臂結束 ≥ COLD_QUIET（預設 1800 s） 交付級：它的 prefill t/s 可以被引用
HOT-STATE距上一臂結束 < COLD_QUIET 只能當熱態觀察；報告就地印出「不要當成出貨數字」並附冷／熱對照
UNKNOWN-STATE狀態檔 $OUTDIR/.last_arm_end 不存在 兩邊都不宣稱（新增態：先前版本在無狀態時會靜默當成 0，那是沒有證據的斷言）

狀態檔在每臂結束時寫入 epoch。誤標的代價本節已經量到兩次： 把熱態臂當交付數字，會得到「250 是抽獎」；把冷態臂當常態，會得到「已經交付」。 兩者都是同一個錯誤：讓機器狀態冒充產物性質。

11.14.9 能說與不能說

(1) 能說 條件式交付成立，且已在最終產物上量到 254.29 / 282.38 / 265.27 t/s （req1–req3 全部 ≥ 250、全程存活、0 crash report）。

(2) 能說 條件不是「啟動前靜置 N 秒」——安靜最長（34 s）的那一臂最慢（166.95）， 安靜最短（18 s）的那一臂最快（265.27）。

(3) 能說 swap 被排除，且它是果不是因（32 分鐘安靜中它自己從 5066.06M 回到 2743.00M）。

(4) 能說 熱態平台的高度在兩個序列不同（≈130 vs ≈185，差 55 t/s）， 而本輪沒有歸因它。

(5) 不能說條件可由非 root 儀器觀測（§11.14.7）。

(6) 不能說 req2/req3 一定也 ≥ 250：第 2 臂的 req3 是 233.51。 安全的述句是「req1 ≥ 250 且該臂全程存活」。

(7) 不能說本節的五臂是單變數實驗。它們共享同一份產物與同一組設定， 但機器狀態（累積熱、swap、背景 load）逐臂不同，而這正是本節要量的東西。
