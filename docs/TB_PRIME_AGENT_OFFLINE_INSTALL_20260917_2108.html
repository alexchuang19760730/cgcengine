prime-agent 的容器內離線安裝

flashkv-devserver ／ 2026-09-17 21:08 ／ D5 白皮書附件（隨本輪 tb_loop 安裝路徑修復一起提交）

一句話 容器對外網只有 164 KB/s（host 對同一個 URL 是 12.7 MB/s，差 80 倍），而官方安裝器把 --max-time 300 寫死 ⇒ 59.6 MB 的 release 永遠抓不完，安裝 421.89 s 後逾時， agent 從未被啟動、total_input_tokens = 0。修法是在 host 先把 release 抓成鏡像、 用 copy_to_container 送進容器，再讓官方安裝器從容器自己的 loopback 取檔 （上游明文支援的 feed）—— 安裝 421.89 s → 43.26 s。過程中另外量到兩個獨立缺陷與一次 被實驗推翻的自己的判斷。

1. 問題：慢的不是上游，是容器的網路

前一份白皮書（TB_SMOKE_ENTRYPOINT_HARD_CONSTRAINTS_20260917_2035.html）查出安裝失敗在 curl: (28) … 49090240 out of 59607437 bytes received。本輪把責任分開：同一個 URL 各量一次。

量測位置下載量時間速率
host（本機 curl）59,607,437 B（整檔）4.71 s12,667,579 B/s ≈ 12.7 MB/s
容器內（tb 任務容器）49,090,240 B（82% 後逾時中斷）300 s≈ 164 KB/s

⇒ 差 80 倍，瓶頸是 colima 的 NAT。按容器速率，59.6 MB 需約 364 s， 而官方安裝器的 --max-time 300 是寫死的 （prime_agent_curl_download -fsSL --connect-timeout 10 --max-time 300 …， 全檔沒有可調該值的環境變數）⇒ 重試也一定失敗，不是偶發。

這一條判準可以搬去別的地方用 「同一個 URL 在 host 與在容器內各量一次」是分辨「上游慢」與「容器網路慢」最便宜的辦法 —— host 端 20 秒的樣本就夠：curl -s -o /dev/null --max-time 20 -w "%{size_download} %{speed_download}\n" <url>； 容器端連另外量都不必，curl 的 (28) 訊息自帶已收位元組數與毫秒數。

2. 修法：host 預抓 → 注入 → 容器內 loopback 供檔

2.1 為什麼是 loopback，而不是讓容器連 host 的 http server

這是上游明文支援的路徑，不是 hack。官方 install.sh 的 prime_agent_validate_download_base_url： 

case "$prime_agent_base_url" in
    https://*) prime_agent_allow_insecure_http=0 ;;
    http://*)
        if [ "${PRIME_AGENT_ALLOW_INSECURE_HTTP_FOR_TESTS:-0}" = 1 ] &&
            prime_agent_is_loopback_test_base_url "$prime_agent_base_url"; then
            prime_agent_allow_insecure_http=1
            return
        fi
        printf 'error: Prime Agent downloads require an HTTPS base URL.\n' >&2
        printf 'Local loopback test feeds require PRIME_AGENT_ALLOW_INSECURE_HTTP_FOR_TESTS=1.\n' >&2
        exit 1 ;;

prime_agent_is_loopback_test_base_url 只接受 http://127.0.0.1:<數字埠>。 ⇒ 這條路既避開 HTTPS 要求、又完全不走容器外網。而走 loopback 還有一個附帶好處： 不需要在 host 上開服務、不需要 host.docker.internal、不需要猜埠會不會被佔。

2.2 改動的三個檔案

檔案角色
agent_harness/tb_loop/scripts/fetch-prime-agent-mirror.sh（新） host 端抓一次並快取在 ~/.cache/prime-agent-mirror{,.tar.gz}（112 MB / 113 MB）。冪等（已快取且 sha256 相符就跳過）、--refresh 強制重抓、逐檔驗 sha256。

一個會踩的細節：鏡像的目錄／檔名佈局不對稱 <base>/<channel>（內容如 v0.9.5）、 <base>/releases/v<ver>/SHA256SUMS、 <base>/releases/v<ver>/prime-agent-<ver>-linux-arm64.tar.gz —— 目錄帶 v、檔名不帶。我第一版兩個都帶 v，拿到 404。

4. 順帶修掉一個會讓每次模型呼叫都 400 的缺陷

在重現 agent 那一步時，命令列上的 model 字串是 local-gemma4/openai/deepseek/deepseek-flash —— 多了一層 openai/。 單變數對照（同一顆容器、只改這一個字串）：

案例命令結果
A tb 實際送的 --model local-gemma4/openai/deepseek/deepseek-flash 400 The model or service ID openai/deepseek/deepseek-flash does not exist…
B adapter 想送的 --model local-gemma4/deepseek/deepseek-flash rc=0，輸出 pong ← 本線第一次真的成功的模型呼叫

4.1 機制（讀原始碼，不是推論）

# terminal_bench/cli/tb/runs.py:60  _process_agent_kwargs
for kwarg in agent_kwargs:
    key, value = kwarg.split("=")
    processed_kwargs[key] = _infer_type(value)

if model_name is not None:
    processed_kwargs["model_name"] = model_name        # ← 後套用 ⇒ -m 覆蓋 -k model_name=

⇒ -m 的值會蓋掉 -k model_name=，而且會一路變成送給端點的 model id。 這同時推翻了本專案 skill 裡一句舊話（「-m 只是 terminal-bench 的標籤， 真正送給端點的是 -k model_name=」）—— 已在 cgc-tb-smoke 就地更正。

修法兩道：

  • run_model_smoke.sh：-m "${TB_GEMMA4_MODEL}"（拿掉 openai/ 前綴），並在旁邊寫明出處行號。
  • prime_agent_adapter.py：__init__ 裡剝掉一層 openai/，讓 adapter 對 tb 的兩種寫法都成立。單元實測：兩種輸入都得到 local-gemma4/deepseek/deepseek-flash。

5. 一次被實驗推翻的自己的判斷（Python kernel）

為了省時間，我一度在安裝腳本裡加了 PRIME_AGENT_BOOTSTRAP_KERNEL_ON_INSTALL=0 （跳過「安裝時順便準備 Python kernel」那段，它實測 >418 s —— 900 s 上限下跑到 6 分 58 秒 仍未完成，只裝完 uv 0.12.15）。這個判斷是錯的，被同一顆容器的實驗推翻。 

prime-agent -p --offline --model local-gemma4/deepseek/deepseek-flash \
  --autonomous --autonomous-max-turns 3 --autonomous-timeout-ms 60000 'reply with the single word: pong'

Autonomous run stopped before terminal evidence; maxTurns reached (4/3)
Status: blocked — no executable tool is available.
Evidence (host-observable, repeated 3 times):
- Every `ipython` call returns: `Failed to set up the Python kernel runtime. uv is required to set up the Python kernel.`
- `bash()` is exposed only through the Python REPL, so the broken kernel also removes shell access.

⇒ --autonomous 的 bash() 是透過 Python REPL 暴露的， 沒有 kernel 就等於沒有任何工具。所以 kernel 是必需品，只是它也需要和 release 一樣的 「鏡像／預熱」待遇。那個 export 已撤回，並在原處留了註解說明為什麼不要再用它換速度 —— 否則下一個人會用同一個「划算」的動作製造出一個靜默的工具全失。

這條的形狀值得單獨記 我當初的推理是「prime-agent -p --offline "…" 在 1 秒內就走到 provider 層報 No API key found，全程沒提到 kernel ⇒ kernel 對模型路徑不是必需品」。 那句話本身是對的，但它回答的是錯的問題：模型路徑不需要 kernel， 而 agent 路徑需要（工具是透過它暴露的）。⇒ 在 --autonomous 這一格上， 「能呼叫模型」與「能做事」是兩件事。

7. 誠實邊界：本文件不主張什麼

  • 不主張 smoke 現在會成功。修復後的那一輪（model_smoke_20260917_210215） 仍然是 is_resolved: false、total_input_tokens = 0， 而且 failure_mode 是 unset（不是 agent_timeout）； agent 階段只持續 44 秒 （agent_started_at 13:02:22.7 → agent_ended_at 13:03:06.7）。 以本文 §5 的證據判斷，下一個 blocker 是 Python kernel 起不來 ⇒ agent 沒有工具。
  • 不主張 deepseek/deepseek-flash 能不能解 raman-fitting.easy。模型路徑只證明到 「能正常回覆一句話」（案例 B）。整題跑通還沒被觀察到。
  • openai/ 的剝除只剝一層；沒有處理 anthropic/ 等其他前綴 （本線用不到，但不主張它普遍正確）。
  • 未跑--n-tasks 以外的情境，也未測續跑守衛的 (c) 分支 （非空、無 lock 的 abort）。

7.1 為什麼沒有重跑一次 smoke 來「驗證修復」

因為以現在的狀態，重跑結構上不可能產生新的判決：kernel 那個 blocker 會讓 agent 在沒有工具的 狀態下耗完回合 —— 那正是本文 §5 案例 C 已經量到的結果（同一顆容器、同一個失敗訊息）。 重跑一次要 ~10 分鐘，換到的是一個已知的形狀。這是取捨，不是省時間： 兩個修復各自都有單變數證據（安裝：421.89 s → 43.26 s，同一條 pipeline；model 字串：A 400 / B rc=0， 同一顆容器），而 kernel 那條 blocker 尚未修 ⇒ 重跑不會改變任何結論。
