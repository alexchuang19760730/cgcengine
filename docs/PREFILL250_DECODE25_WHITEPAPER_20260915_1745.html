2. 生產級量測口徑：llama-bench 的 pp/tg × depth

本輪依使用者指示，把 prefill / decode 的驗收口徑改為 llama-bench 的多上下文標準。 口徑的定義是：-p n_prompt（pp）× -n n_gen（tg）× -d n_depth， 其中 --n-depth 是「量測開始前 context 裡已經裝了多少 token」； n_ctx = n_depth + n_prompt + n_gen，而且 llama-bench 對每一個 (p, n, d) 組合都會 新建並釋放一個 llama_context —— 它天生就是一個多 context harness。 這正是 streaming-expert 引擎該被檢驗的軸：整個設計關心的就是工作集隨 context 變長會發生什麼事。

2.1 為什麼 llama-bench 跑我們的模型會 OOM（已修）

根因不是記憶體不足，是沒帶 -expert-cache。 llama-bench 確實接受 -expert-cache <bytes>（--help 已確認）， 不帶的話模型會以「40 個 MoE layer × 256 experts 全部常駐」載入 = 13.66 GiB， 對上這台 M4/16GB 的 recommendedMaxWorkingSetSize = 11.45 GiB， 第一個 batch 就 test_prompt: failed to decode prompt batch, res = -3。 解法是讓 bench 走 run_server.sh 解析出的 profile（-expert-cache 8589934592）， loader 就會改用 143 slots/layer 的 L4 pool。

2.2 為什麼修完 OOM 之後又踩斷言（已修）

pool 一起用，llama-context.cpp:285 就會把 cparams.n_batch 夾到 cgc_pool_max_tokens()（預設 8），因為更寬的 batch 會把縮小後的 per-layer expert tensor 讀出界。於是 -p 512 直接 GGML_ASSERT(n_tokens_all <= cparams.n_batch) 中止。 llama-bench 無法從外部設 n_batch，所以 harness 必須自己決定： stream 臂用 CGC_PREFILL_STREAM=1 + CGC_GATHER_SLAB_CAP=256（夾制被解除， 寬 chunk 走 whole-layer slab），pool 臂用 -b 8 -ub 8 （這不是 workaround，這正是 server 自己在該配置下每個 prefill chunk 的做法）。

2.3 一個真相來源

bench 的 env 不是在 harness 裡另寫一份清單，而是呼叫 run_server.sh CGC_DUMP_ENV=1 取得「所有 profile 預設與覆寫都已套用、就在 exec 之前」 的那份 CGCENV/ENV/ARG。理由：25.17 → 5 t/s 那次回歸本身就是 配置漂移（CGC_OA_ASYNC 1→0、CGC_SPAC on→off、 CGC_MM_BITIDENT 掉出 allowlist、兩個 bit-identical 支柱 1→0）， 所以第二份手寫的 env 副本正是要避免的失敗模式。

3. 兩個真 bug：讓多 context 口徑跑不完的元凶

llama-bench 每個 instance 都建/釋放一個 context。這個行為把兩個過去被單 context 使用模式遮住的 bug 曝露出來。兩者都不是「量測問題」，是真的會讓行程死掉。

3.1 SIGSEGV（rc=-11）：teardown 釋放 slab 前沒有把 tensor 還原

M2 whole-layer slab 路徑的做法是就地改寫模型自己的 FFN expert tensor： 把 wt->data / wt->buffer / wt->ne[2] 指向 slab， 原值存在 cache_orig / cache_gather_orig_buf / cache_gather_ne2， 還原時機是下一層的 per-layer hook。最後一層沒有「下一層」，所以它的重指向 永久懸空；~llama_context 把 slab 釋放掉之後，第二個從同一個 model 建出來的 context 就會透過懸空的 wt->buffer 去認領 L4 pool。

症狀：prod25-stream 的 pp512 跑出 115.84 t/s 之後崩掉； prod25-stream-nodb 仍崩（排除 double-buffer 執行緒）； 只有不含 slab 的 prod25（pool-only）不崩 —— 定位收斂到 slab。 修法是在釋放 slab 迴圈之前插入 UNREPOINT 還原迴圈，並印出還原了幾個 tensor。 修完之後 4 個 llama-bench instance 連續跑完不崩；另外第一節的四次獨立啟動逐位元相同 也只有在這個修法之後才成立。

3.2 SIGABRT（rc=-6）：pick_slot 的 SpAc victim 上界假設錯誤

中止訊息是 ensure_slot layer=1: no usable slot and no fill in flight， 而 instrumentation 顯示該層 owned=142/142 usable slots、loading=0、 queued=0、pinned=0 —— 一次「應該會成功的驅逐」卻回傳了 -1。

pick_slot 的三段 pass 裡，pick_slot 唯一會「三 pass 全數拒絕所有已擁有 slot」的分支就是 SpAc victim：util < best_util || util == best_util。 舊碼把上界寫成：

double best_util = 2.0;  // > max possible (1.0), so any real utility wins

這個「max possible = 1.0」不是 spac_util 的性質。 spac_update 對 routed union 裡每一次出現都加一次 bump （u[e] *= alpha; u[experts[i]] += bump），所以一個在單步內被選中 k 次的 expert 其固定點是 k（實測 layer 1 slot 0 的擁有者 = 4.375）。 一旦有任何 slot 的 utility 超過 2.0，util < best_util 就對所有候選皆為假， 三 pass 全部回 best_slot == -1，呼叫端直接 abort。 它只在 CGC_SPAC=1 且 EMA 累積超過 2.0 之後可達 —— 這正是它躲過 09-14 / 09-15 兩輪 SPAC 掃描的原因。

修法三件（可證明不改變任何「本來會成功」的決策）：把上界改成 std::numeric_limits<double>::infinity()；把 spac_util[layer] 可能是空 vector 的情況補上 !empty() 守衛；另立一個 flag-filtered 的 LRU 候選， 只在 SpAc 分支什麼都沒選到時才被採用 —— 把「所有 utility 都是 inf/NaN」的 abort 轉成呼叫端契約本來就假設的 LRU 驅逐（pick_slot 回 -1 只允許發生在「有 fill 在飛」）。 另補兩個計數器 n_spac_nonfinite / n_spac_lru_fallback， 讓腐敗的 utility row 是可見的而不是靜默停用 SpAc。

4. M1/M2/M3 閘門：那個 FAIL 是「類別錯誤」，不是回歸

前一份白皮書寫「M1/M2/M3 尚未解決」。本輪把它查到底，結論是：當時報的 FAIL 不是引擎的缺陷，而是拿一個「在另一種配置下、由另一份程式碼」產生的參考，去做 bit-identity 比對。 三條獨立證據如下。

4.3 決定性證據：引擎本身是確定的

四次獨立啟動（detA/detB/detC/detD），同一份生產配置，互相逐位元比對： common = 9 keys、only_A = 0、only_B = 0、row mismatch = 0。

這直接證明「舊參考過期」而不是「引擎壞了」：現役配置不但可重現，而且已經達成 run-to-run bit-identity —— 也就是說 M1 指標的前提是成立的。

4.4 閘門升級：把「參考是否可比」變成前置條件

舊閘門的缺陷不是判錯數字，是沒有能力發現自己在做跨配置比對。已在 scripts/check/m123_oracle_gate.py 補上：

  • 兩側都用同一條路徑解析配置：run_server.sh CGC_DUMP_ENV=1， 在「所有 profile 預設／覆寫都套用完、就在 exec 之前」印出 CGCENV/ENV/ARG 後 exit 0。 純讀取、無副作用，且不可能與 server 實際收到的東西漂移。
  • 比對「決定數值的子集」：排除純診斷鍵（CGC_LOGITS_ORACLE_*、 *_DBG、log/port 路徑），其餘逐鍵 diff。
  • 跨配置 → INVALID COMPARISON（exit 2），不是 FAIL， 並列出差異與一行的重新基準化指令。也支援 --allow-incomparable 只讀差異。
  • --write-ref PATH：把剛跑完的 dump 複製成新參考並寫下 PATH.cap（含完整解析後配置、profile、模型 digest、note）。 每次跑閘門也會留下自己的 Backup/m123_oracle_gate/cap_<tag>.json， 讓下一次的「可比性」有東西可比。

本輪結果：舊參考已按倉庫既有的 _STALE_ 慣例退役為 ref_iq3_pool8gb_M2_6144_STALE_pre-mmbitident.jsonl，其 .cap 記下退役理由、 二分證據與 superseding 檔名。新基準為 Backup/knifeedge_matrix/ref_iq3_pool8gb_M2_6144_bitident.jsonl（profile prefill250，三支柱全部 = 1，ctx 8192 / batch 6144 / budget 8 GiB）。

5. 已知限制 / 下一步

  1. 把 250 變成規格的前提是「記憶體閉合」，不是「再調一個旋鈕」。 目前 prefill250 是超訂的（13.6 GB 模型 + 8 GiB pool + 6144 寬 compute buffer 塞 16 GB unified），所以 pp2048 會在 122.68–276.59 之間抽獎，而 OOM 天花板 在 p3072/p4096 之間游移。可驗收的下一步是把「載入後」的 free% 也納入 guard （現在 preflight 只在啟動前檢查一次），或把 ubatch 降到能穩定不 OOM 的值， 然後在固定 shape 上重複 5 次確認離散 <5%。在此之前，認證數字是窄 chunk 的 111.86–120.56。
  2. M1/M2/M3 閘門只證明「相對不變性」。cache-ON 的參考永遠不能被當成真值 （knifeedge_matrix.py --oracle-abs 對這點是拒絕的），因為 pool 的成員決定 logits。絕對正確性需要 CGC_SERVER_EXPERT_CACHE_OFF=1 的控制組 dump； 在 16 GB 機器上它只裝得下很小的 prompt。這一格仍然是空的。
  3. layer 1 的 gate/up expert row 全零（fill-vs-read 時序）尚未解。 b75c1a3de 的常開斷言抓到 8 次全零 row，全部在 ffn_moe_gate-1 / ffn_moe_up-1（同 slot 的 down 非零， pool 與 slab 兩條路徑都中）。全零 row 代表該 expert 的貢獻被靜默丟掉 —— 這是絕對正確性的缺口。下一步：CGC_MMID_ASSERT_FATAL=1 讓它停在第一次違規，再對照 ensure_batch / double-buffer publish 的時序。
  4. decode 25 的兩個新槓桿（尚未實測）：
