TL;DR。新增第三條 capture stream（path=POOL）：在 mul_mat_id 的內核跑完之後、 同一個 encoder 內，從裝置讀 ids 運算元與它選中的 pool row，逐 row 寫下 (id, sum, xor, wsum, nbytes)。

它回答的問題只有一句：兩臂在「消費者讀取的那一刻」，對同一個 slot 索引是否讀到同一批位元組。 這是 S1 分歧定位唯一還沒被排除的敘述，也是為什麼它必須是內核而不是主機側探針（§1）。

它不產生修復，只產生決策：四個分支各有不同的下一步（§4）。把 SAME 讀成「兩個 pool 一樣」或把 DIFF 讀成「引擎壞了」都是過度解讀。

本次沒有建置、沒有跑任何量測（04:00–06:10 的機器歸 prefill 的 SPAC COLD 交錯 A/B）， 而且 .metal 在這台機器上無法離線編譯（§7）。

↑ 這一段是 03:55 的實況，保留作為當下狀態的記錄。09:06 已建置、09:07 已跑第一次： 結果在 §6.1–§6.2。

1. 為什麼這件事非得在內核裡做

倉庫裡早就有這支儀器：CGC_MMID_MV_DBG（ggml-metal-ops.cpp:4020 起）會對每個 MoE 節點印出「ids 所選的前 4 列、各前 ≤4096 bytes 的 FNV-1a 指紋」，它自己的註解就寫明了判準： 「ids 相同而指紋不同 ⇒ 池內容是載體。」——正是我們要的那一格。

問題是它在 S1 臂上量不到東西，而且是可證的量不到：它在圖編碼期讀 op->src[2]->data，而 S1 臂的 ids 是一個 graph 算出來的節點（get_rows(slot_table, selected_experts)）， 那一刻 GPU 還沒寫它。實測結果寫在 Backup/run_ids_dst_capture.sh 的 MMID 段與 docs/S1_SRC2_INSTRUMENT_BLIND_20260917.html：

id_oob_vs_ne02 = 16/16          ← 16 個「ids」全部越界
值是 float 位元模式              ← 讀到的是那個 buffer 的前一個佔用者，不是 ids
錨臂（host leaf）: id_oob = 0，指紋完整

這是 eng-mh-0008 的又一次發作：主機側在編碼期讀一個「中間運算元」，量到的是 誰寫了那個 buffer，不是消費者收到什麼。同一個檔案裡 kernel_cgc_ids_capture 的註解已經把這件事寫過一次（09-15），但當時只修了 ids 側。

2. 機制

2.1 每個 slot 的字（CGC_POOL_STRIDE = 64）

word內容為什麼是它
out[0]實際寫出的 group 數0 與「寫了但全 0」必須分得開
1+5r+0消費者用的第 r 個 id與 digest 同列 ⇒ 一行就能分辨「索引不同」與「索引同但位元組不同」，不必再開一支儀器
1+5r+1該列 probe bytes 的 sumbyte 級，不是 word 級：運算元是量化格式（IQ3_XXS/IQ4_XS），按 word 化簡等於把 block 的 metadata 一起算進去
1+5r+2同上 xor
1+5r+3加權和，權重 = (byte index + 1)
1+5r+4位元組數（0 = 這一列沒讀）比較器唯一可靠的「有沒有讀」欄位；只改成 sum/xor 會被 0 與哨兵混淆

加權和的理由與 CGC_TENSOR_CAPTURE_HASH 相同：純 sum 看不見置換，而「gather 順序不同」 正是這個 fork 被懷疑的東西之一。

2.2 邊界檢查寫在內核裡

池路徑上 id 越界的後果不是崩潰，而是讀到隔壁專家的儲存——印出一組看起來很合理的數字。 所以 id 不在 [0, row_limit) 時不 dereference：記成 id 加 nbytes = 0； 運算元裡根本沒有第 r 個 id 時記成 id = -1。兩者都不會與「真的讀到」混淆。

5. 兩個會說謊的失敗模式與對應護欄

5.1 全哨兵（已發生過一次）

沒被寫到的 slot 是 0x7fffffff，而哨兵等於哨兵。2026-09-17 00:30 就是這樣把一輪讀在 205 列裡 188 列純哨兵的表上。因此 Backup/compare_pool_row.py 以 nbytes == 0 為判準，兩側都沒讀到就報 NOT-READ， 永不報 SAME；且當所有共享列都是 NOT-READ 時，整體判決撤銷而不是印「找不到差異」。

5.2 沒有可比對的列

若兩份日誌沒有共同的 (graph, name)（節點名少打一個字、兩臂抓不同層）， 「沒有差異」是空洞的。比較器報 NO-OVERLAP 並拒判。

5.3 同臂控制（必跑）

這個 copy 讀的是別的內核可能還在寫的 buffer：少了 memory barrier，同臂自比就會失敗， 而跨臂的讀數會變成一個「有自信的假陽性」——09-16 的 DST 輪正是這樣（無 barrier 時 205/205 不一致， 加上後乾淨）。所以

# 同一個臂跑兩次、兩份 POOL 流互比。任何一列不是 SAME ⇒ 讀數本身就是發現，不是引擎。
python3 Backup/compare_pool_row.py run1-<arm>.log run2-<arm>.log

5.4 不讓排除變成靜默

path=POOL 不是 Backup/analyze_capture_nodes.py 的比較單位（那是一份已發表的定位結果）， 所以該檔顯式排除 POOL 列，並在 main() 印出排除幾列。 靜默改變一個比較器看到什麼，是這個倉庫反覆學到的那個缺陷（256 byte 濾網、--upto 盲點）。

交叉核對（這條支持「同一時刻」的主張）：POOL 列裡那 8 個 id （2,105,7,9,5,106,1,84）與同一輪 MV 列印出的 ids 逐項相同；兩個 dispatch 之間只隔 數微秒（slot=3 與 slot=0 的 seq 相鄰）。所以 pool 摘要讀的確實是那個 kernel 消費的那些列。

整輪 n_predict=4 共 99 列 POOL（gate／up／down 各 33）， nsel 由 16 走到 64（＝8×T，T 由 2 走到 8）——與既有的 chunk 序列一致。 這一輪不是量測：單臂、n_predict=4，它只驗「管子通不通」。decode 10.06 t/s 這種數字在這種樣本數下不可引用。

一個真實的退化案例，正好示範守衛為什麼要 key 在 nbytes：同一輪裡 id=14 那一組是 sum=0 xor=0 wsum=0 nbytes=4096 —— 那個 4096-byte 前綴真的全是 0。 這是模型自己的資料（同一個 log 有 layer=0 zero-prefix=2 of 143 resident slots）， 被讀到了，只是內容為零。若守衛寫成「sum==0 就算沒讀」，這一列就會被誤判成 NOT-READ； 若寫成「全零等於相同」，它又會與沒被寫到的哨兵混淆。只有 nbytes 分得開這兩件事。

結論（這支儀器唯一的產物）：「同一組 ids、同一池佈局、gather 讀到的位元組不同」——被否證。

在兩臂選到同一組 slot 的每一個 graph 上（共 30 個，含第一個 T=1 步），那些 slot 指向的 整列位元組逐位元組相同；等到兩臂的列不一樣時，原因是ids 本身不同（不同的專家被選中）， 而不是同一個索引裝了不同的東西。

⇒ 池內容（residency）不是 S1 分歧的載體。要查的方向因此離開 gather 的輸入側： 第一個 T=1 步（g30）的 attn_norm-0.dst 已經 DIFF，而同一時刻 layer 1 的 ids 仍然相同 ——分歧在層 0 的活化鏈上就已經存在（那一步的 router 還沒翻），再一步（g31）路由才跟著翻。 所以下一步該看的是層 0 的 delta-net 路徑與它帶進下一步的遞迴狀態，不是池。

誠實邊界：SAME 是強證據不是證明——(sum, xor, 加權和) 三字摘要理論上 可以被一組補償性的 multiset 變化碰撞。但這已經是這支儀器能給的最強語句，而且是 「整列的」而不是「窗口的」。同時它只涵蓋層 1 的三個節點、每個節點被選中的前 8 列—— 不是全模型、不是全部 8×T 列。

7. 誠實邊界：這份文件不主張什麼

  • 不主張任何速度或正確性數字。本次沒有做任何可引用的量測；mul_mat_id 的數值路徑 一行未改（三條 capture 流預設全部關閉，要 env 才動）。09:07 的單臂短跑 （n_predict=4）只證明管子通，它的 decode 數字不構成結果。
  • 不主張內核語法正確。.metal 在這台機器上無法離線編譯： xcode-select -p 是 /Library/Developer/CommandLineTools、沒有 Xcode， xcrun metal 回 unable to find utility "metal"。 而 GGML_METAL_EMBED_LIBRARY 是把 shader 原始碼嵌進 binary、執行期才編譯， 所以語法錯誤只會在第一次跑到它時以「整個 library 編譯失敗」的形式出現。 已經做過的替代驗證：在 /tmp 抽出結構與內核單獨嘗試編譯（工具不存在，未成功）、 逐項核對型別用法在同檔皆有先例（uchar、uint64_t、threadgroup uint32_t、 靜態 threadgroup 記憶體、threadgroup_barrier）。 第一次跑的臂請用小 POOLNODES 與短 n_predict。 09:07 第一次跑（單臂、n_predict=4）已通過執行期編譯並產出 99 列 POOL ⇒ 語法已被實跑證明；但離線編譯仍然不可用，所以未來任何 .metal 改動都還是只能靠實跑驗證。

  • 不主張「同臂控制會過」。barrier 依 DST 輪的理由放進去了，但它的必要性只能由量測確認。
