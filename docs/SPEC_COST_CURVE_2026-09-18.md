## 0. 一句話

**攤薄係數實測 `m ≈ 0.47`（三輪配對中位）／`m ≈ 0.69`（唯一全程 NOMINAL 的那一點），
而計畫書要的 2× 需要 `m ≤ 0.214`、3× 需要 `m ≤ 0.059`。**
也就是說：在這個受試對象上，**把 accept rate 練上去本身到不了 2×，天花板上界約 1.5×**；
而且今天開啟 MTP 是**淨虧**（每個 k 的加速比都 < 1）。錢該花在壓 `m`，不是花在練 head。

## 1. 為什麼這一次不用「擬合兩個未知數」

可行性文件裡的 `m ≈ 0.21` 是從**單一個 k** 反推出來的 —— 一個點無法把 `E`（每步接受幾個
token）和 `cost` 分開，那是同一個方程裡的兩個未知數。這一次把兩個量都變成**直接讀數**：

| 量 | 怎麼量 | 依據 |
|---|---|---|
| `E`（每輪幾個 token） | `LLAMA_BENCH_SPEC_DBG=1` 每輪印一行 `SPECDBG round: n_done=.. draft=..`，數行數 ⇒ `E = n_gen / rounds` | `llama-bench.cpp:2631` |
| 有效 draft 深度 | 同一行的 `draft=` 取平均（**不是** `--spec-draft-n-max`，MTP 模組會自己截斷） | 同上 |
| verify 專家並集 | 快取在 teardown 無條件印 `verify: calls=.. union=..` ⇒ `union/calls` | `llama-expert-cache.cpp:2529` |

`E` 之所以能乾淨地數，是因為 warmup 的 generation 走的是**非 spec** 的
`test_gen(ctx, 1, ..)`（`llama-bench.cpp:2926`），不會混進計時輪次。

有了 `E` 和 `S = tps(k)/tps(k=0)`，就不需要擬合：

```
cost(k) = E(k) / S(k)          m = (cost(k) - 1) / k_effective
```

`m` 才是用最小二乘（過原點）擬合出來的，擬合的是 `cost-1 = m · k_eff`。

**配對設計**：llama-bench 一次呼叫只能有一個 `--spec-draft-n-max`，所以 k 曲線得分次呼叫；
每輪內 6 個 k 依 ABBA 交錯（奇數輪正序、偶數輪逆序），**每個比值都用同一輪自己的 k=0 基準**，
最後取三輪中位。這樣做的是「抵銷慢漂」而不是「解釋慢漂」—— 本專案已記錄的單臂噪音
（±1.9 t/s）比多數待測效應還大，且沒有任何已記錄變數排得出順序。

## 4. 成本長在哪：verify 的專家並集

```
union/call(k_eff) = 9.36 + 3.12 · k_eff      （單 token 一步 = 8）
```

**每多一個 draft token，verify 那一批就要多抓約 3.1 個專家／層。**
k=7 時並集 22.9 ≈ 單 token 的 2.9 倍，而它只換到 `E = 1.66`。這就是 `m ≈ 0.47` 的來源。

這也順手回答了待辦 **(ii)**：`union/call` 是 12.2–22.9 而**不是 8.00**，加上
`verify-strict: refused=3 zero_mapped_selected=0` ⇒ **union remap 在 bench 側是真的有做**，
09-17 那條「bench 其實量到的是 exact-path fallback（union/calls = 8.00）」的懷疑**已被排除**。
所以服務路徑與 bench 的落差不是那個 bug。

## 5. 上界：accept 拉滿也買不到 2×

把實測 `m = 0.474` 代進 `S = E(a,k)/(1 + m·k)`：

| a \ k_eff | 1.00 | 1.72 | 2.46 | 3.99 | 4.68 |
|---|---|---|---|---|---|
| 0.43（今天 k=3 的實測） | 0.97 | 0.87 | 0.77 | 0.60 | 0.54 |
| 0.58（服務路徑 09-17 的水準） | 1.07 | 1.01 | 0.93 | 0.77 | 0.71 |
| 0.70 | 1.15 | 1.14 | 1.09 | 0.96 | 0.90 |
| 0.85（計畫書的低標） | 1.26 | 1.31 | 1.32 | 1.28 | 1.25 |
| 0.92（計畫書的高標） | 1.30 | 1.40 | 1.45 | **1.47** | **1.47** |
| 1.00（不可能的上界） | 1.36 | 1.50 | 1.60 | 1.73 | 1.77 |

反過來解「要多少 `m`」：

- **2× 需要 `m ≤ 0.214`**（實測 0.474；NOMINAL 那一點是 0.689）
- **3× 需要 `m ≤ 0.059`**

而 `a = 1` 是硬上界：`S ≤ (k+1)/(1+mk)`，在 `m = 0.474` 時即使 k→∞ 也就趨近 `1/m = 2.11`，
但那需要**完美接受率 + 無限深 draft**；現實區間（a ≤ 0.92、k ≤ 5）的上界是 **≈1.5×**。
若用 NOMINAL 那一點的 `m = 0.689`，連 `a = 0.92` 都只剩 **≈1.03×**。

## 6. 對計畫書的裁決

| 計畫書的主張 | 本次實測 | 裁決 |
|---|---|---|
| 「2-3× 靠 accept 48-65% → 85-92%」 | accept 拉到 0.92 只給 1.47×（m=0.474）／1.03×（m=0.689） | **不成立**：accept 不是那個瓶頸 |
| 訓練 draft head（Phase 2-3，12-18 天） | 同樣的成本，收益被 `m` 鎖在 ~1.5× 以內 | **先別做**；先壓 `m` |
| 「流式 MoE 上 draft 邊際成本不為零」 | union 隨 k 每個 +3.12 專家/層 | **證實**，且量化了 |

**RSL-MTP（Resident-Set-Locked）的量化理由**：若 draft 的 top-8 被鎖在本步已付費的並集內
（並集恆為 8/層 ⇒ `cost → 1`），則**同一批實測的 `E`** 會直接變成加速比：

| k | 實測 E | 實測 S | RSL 假想 S（cost=1） |
|---|---|---|---|
| 1 | 1.306 | 0.743 | 1.31× |
| 2 | 1.362 | 0.721 | 1.36× |
| 3 | 1.662 | 0.637 | 1.66× |
| 5 | 1.882 | 0.691 | 1.88× |
| 7 | 1.662 | 0.548 | 1.66× |

⚠ 這是**從假設投影出來的，不是量到的**。`union(k)` 的斜率支持「成本主要由並集大小決定」，
但並沒有證明它（r² = 0.72，且樣本受熱態污染）。**先量 `p_route`（待辦 iii）再決定要不要做。**
