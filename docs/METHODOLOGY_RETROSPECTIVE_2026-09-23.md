# 方法論復盤：為什麼我們花了這麼多時間，估計卻一直失準

**日期**：2026-09-23
**性質**：方法論檢討，不是技術報告
**對象**：flashkv-devserver 效能最佳化專案

---

## 0. 一句話

**我們一直在「估計收益」，卻從來沒有先搞清楚「這件事到底可不可能」。**

看到個 flag 就估計它能帶來 +20%，看到個變數就假設它是有數據的，看到個機制就假設它是實作好的。
結果每一個估計都不準，每一個方向都踩雷。

---

## 1. 我們做了什麼（時間線）

| 時間 | 方向 | 我們估計的收益 | 實際結果 |
|------|------|--------------|---------|
| 9/20 | P2 kernel bit-exact | +3-5% | 改到了錯的 kernel 變體（IQ3_XXS vs IQ2_S），零覆蓋 |
| 9/21 | Dense kernel tile 最佳化 | +5-10% | K0 證實輸出軸已切滿，沒有空間 |

| 9/23 下午 | CGC-RIG-SNAPSHOT / pread_usec | ??? | 讀完代碼才發現它只是個日誌函數 |

**規律：每一個方向，我們都是先估計收益，再去量測，然後發現根本不是那麼回事。**

---

## 2. 為什麼估計會失準？

### 2.1 我們跳過了「第一性原理」這一步

```
正確的思考順序應該是：

  1. 第一性原理：這件事可能嗎？
     → 從架構、硬體限制去推
     → 不需要量測

  2. 機制理解：為什麼？怎麼做？
     → 讀代碼，理解機制
     → 不需要量測

  3. 收益估計：多少？
     → 到這一步才需要量測

我們的實際順序：

  1. 看到個 flag / 變數 / 機制
  2. 直接跳到「能帶來多少收益？」
  3. 然後去量
  4. 結果發現根本不是那麼回事

⇒ 我們跳過了前兩步，直接跳到第三步
⇒ 所以估計完全不準
```

### 2.2 我們把「假設」說成了「事實」

```
具體的例子：

  → 看到樹上有個 draft_prefetch_ids
  → 就假設它是有數據的
  → 就開始算「如果接回來會有多少收益」
  → 結果量出來才發現那個 buffer 是空的

  → 看到有個 CGC-RIG-SNAPSHOT
  → 就說「這是 FAIL 之後的備案」
  → 就要走這個方向
  → 結果讀完代碼才發現它只是個日誌函數

⇒ 我們把「我以為」說成了「就是這樣」
⇒ 把「可能」說成了「事實」
⇒ 這跟之前誇大成果是同一個毛病
```

### 2.3 我們在「猜」，而不是在「推」

```
我們做了什麼：
  → 猜 U 是多少 → 猜錯了（15.5 vs 19.4）
  → 猜預測源有數據 → 猜錯了（buffer 是空的）
  → 猜頻寬利用率是多少 → 猜錯了（以為 47.6 是屋頂）
  → 猜 kernel 瓶頸在哪 → 猜錯了

⇒ 每一個環節都在猜
⇒ 多層猜測疊起來，就完全失真了

正確的做法：
  → 從第一性原理出發，推導出可能的方向
  → 排除不可能的
  → 再去量剩下的
```

## 3. 第一性原理能告訴我們什麼？

### 3.1 不需要量測就可以知道的事

```
1. Transformer 層是串列的
   → Layer 1 必須等 Layer 0 跑完
   → 這是架構決定的，改不了
   → 不需要量就知道

2. GPU 時間 > CPU 時間
   → GPU 忙 113ms，CPU 只需要 35ms
   → 理論上 CPU 應該可以在 GPU 跑的時候把事情做完
   → 不需要量就知道有重疊空間

3. 頻寬峰值是 108.8 GB/s
   → 現在只用了一半
   → 理論上有 2 倍空間
   → 不需要量就知道

4. Expert 是分散的
   → 8 個 expert 分散在記憶體各處
   → 跳來跳去，頻寬利用率低
   → 不需要量就知道這是問題
```

### 3.2 為什麼我們沒有先做這一步？

```
因為我們想快速給答案

  → 用戶問「這個方向可行嗎？」
  → 我們想快速回答「可行，能帶來 +20%」
  → 而不是說「等一下，我先搞清楚這是什麼」

⇒ 我們太急著給答案
⇒ 就跳過了思考的過程
⇒ 結果答案都是錯的
```

## 4. 以後的做法

### 4.1 三步法

```
第一步：第一性原理（用頭腦，不用儀器）
  → 這件事可能嗎？
  → 從架構、硬體限制去推
  → 排除不可能的方向

第二步：機制理解（讀代碼，不用儀器）
  → 為什麼？怎麼做？
  → 讀代碼，理解機制
  → 確認東西真的存在

第三步：收益量測（這一步才用儀器）
  → 多少？
  → 到這一步才需要量測
  → 用數據說話
```

### 4.2 檢查清單

```
在說「這個方向能帶來 X% 收益」之前，先問自己：

  [ ] 我理解這個機制是怎麼運作的嗎？
  [ ] 我確認這個東西真的存在嗎？
  [ ] 我是從第一性原理推導出來的，還是憑感覺估的？
  [ ] 我有沒有把「假設」說成了「事實」？

如果有任何一題答「沒有」，就不要說收益數字。
```

---

## 5. 教訓

```
1. 不要看到個 flag 就假設它是有數據的
   → 先確認它真的被填過

2. 不要看到個變數就假設它是有用的
   → 先確認它真的被用到

3. 不要看到個機制就假設它是實作好的
   → 先讀代碼，確認它真的存在

4. 不要急著給收益數字
   → 先搞清楚機制，再談收益

5. 不要什麼都從零開始量
   → 先用第一性原理縮小範圍
   → 再用量測確認數字
```

---

## 6. 結語

```
這一週我們學到的最重要的教訓：

  → 不是哪個 kernel 最佳化的技術細節
  → 而是「怎麼思考」的方法論

  → 先想清楚，再動手
  → 先理解機制，再估計收益
  → 先用第一性原理，再用量測

⇒ 方法對了，效率才會高
⇒ 方法錯了，再努力也是白費
```
