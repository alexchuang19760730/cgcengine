§1 第 2 件：L0 定案（否定）

§1.1 判準事先寫定，寫在腳本裡

量測之前先把判準寫進 scripts/check/decode_sweep.py 的臂 docstring， 避免事後挑一個好看的讀法：

#   ratio = L0 gpu / median(other 39 layers' gpu), per arm, median over steady steps
#     ratio >= 3 in ntok=1 only      -> layout-dependent (candidate: segment 0's extra work)
#     ratio >= 3 in BOTH             -> layer-independent (candidate: head-of-step ramp)
#     ratio <  2 in both             -> no reproducible anomaly; the 7.2x was that run's artifact

統計量刻意取 run 內比值而不是跨臂水準：臂的位置本身就值 +12.5% （lesson eng-mh-0061），跨臂比會量到位置而不是形狀。

判準第三條成立（後兩臂都 < 2×）。兩個獨立的觀察把「L0 這一層有問題」排除掉：

  • 純 decode 裡 L0 比中位還快（0.46×）。它是最先被排程的那一層，池預熱之後沒有任何額外工作。
  • 投機臂裡 L0 的 gpu 排第一但只有 1.6×，而它的 union 反而低於中位 （0.62×）⇒ 抬升來自 busy（多個 command buffer 重疊），不是跨度。
  • 兩臂的 cb 前四名都是 L2／L1／L0／L3 ⇒ 那是池填充由最前面幾層付錢的既有模式， 不是 L0 這一層的性質。

§1.3 那個 7.2× 屬於哪個 regime，以及兩個剩下的候選

7.2× 出現在 llama-bench -d 512 的形狀裡，而那個形狀有兩個特徵同時成立： 它先做 512 token 的 depth prefill，而且它是 MTP env 全開但沒有真的投機 （llama_bench_matrix.forward_argv() 不轉發 --spec-type， 所以 decode step 的 ntok 恆為 1）。那不是出貨形狀。 ⇒ 第 2 件的 9.46 ms 從「可引用的 L0 成本」降級為「某個非生產形狀的讀數」。

只在該 regime 裡還需要解釋的兩個候選（都沒有被進一步分離）：

  • (a) segment 0 真的扛了額外工作。 GGML_SCHED_DEBUG=2 顯示一個 segment 圖只有 10 個節點（2 個 split：一個空的 CPU ＋ 一個 MTL0），而 segment 0 把 model.input_embed、2 個 view 與 layer 0 的 leaf／attn_inp_* 群併在一起。 但一個 ntok=1 的 get_rows 只有 8 KB ⇒ 這條仍缺一個環節。
  • (b) segment 0 付的是每步開頭的啟動坡（分段的 dispatcher 在每個 segment 邊界等 cgc_done ⇒ 每一步都從「GPU 已排空」開始）。但這條被上表第三列否掉： 投機臂同樣每步開頭排空，L0 的 union 卻是低於中位的。

§2 第 3 件：為什麼不需要 MTLCounterSampleBuffer

docs/M3_VERDICT_2026-09-17.md 的結論是：要裁決 M3 就需要「逐節點 GPU 時間」， 而且「唯一活路」是 Metal 的 counter sample buffer，成本最高。活路對，成本判斷錯。 關鍵是 ggml-metal-context.m 的編碼回呼早就把圖切成固定範圍了：

// ggml-metal-context.m:1304-1315（既有程式碼，逐字）
const int n_nodes_0 = ctx->n_nodes_0;
const int n_nodes_1 = ctx->n_nodes_1;
const int n_nodes_per_cb = ctx->n_nodes_per_cb;
int idx_start = 0;
int idx_end   = n_nodes_0;
if (cb_idx < n_cb_l) {
    idx_start = n_nodes_0 + (                                         (cb_idx + 0) * n_nodes_per_cb);
    idx_end   = n_nodes_0 + (MIN((cb_idx == n_cb_l - 1) ? n_nodes_1 : (cb_idx + 1) * n_nodes_per_cb, n_nodes_1));
}

⇒ 主執行緒的 slot（cb_idx == n_cb）編的是 [0, n_nodes_0)； worker cb_idx < n_cb 編的是 [n_nodes_0 + cb_idx·p, …)。 而 n_cb / n_nodes_0 / n_nodes_per_cb 在 sched 側讀取時都還在 （同一個 ctx，同一次 graph_compute 的產物）⇒ 範圍可以直接導出。

把這件事與既有的 CGC_GPU_TIMING 接起來就完成了：那個儀器已經逐 command buffer 讀 [cb GPUStartTime]／[cb GPUEndTime]， 只是把它們聚合成了一個 segment 跨度（union = max(end) − min(start)， 見 ggml-metal-context.m:497 的定義）。節點身分是在聚合那一步被丟掉的， 不是在取樣那一步。

圖 1：一個 segment 切成 n_cb+1 個 command buffer，各自覆蓋一段連續節點。

§4 三個坑（兩個是我的錯）

§4.1 ctx->gf 是懸空指標 ⇒ 載入期 SIGSEGV 11

症狀：run_server.sh 印 Segmentation fault: 11， decode_sweep 報 server never became ready， 而伺服器日誌在 CGC-POST 之後就斷了。

真因：ctx->gf 存的是呼叫者的 cgraph，而分段 dispatcher 把它建在 區域變數上（ggml-backend.cpp 的 submit_seg： struct ggml_cgraph gv = seg_view(s); 然後 ggml_backend_graph_compute_async(split_backend, &gv)） ⇒ 那個呼叫一返回 ctx->gf 就懸空，而 sched 側的 hook 在其後才讀。

而我這支是全檔唯一在「呼叫之後」讀 ctx->gf 的讀者 （既有的讀者都在 graph_compute 之內）⇒ 既有測試面全過，缺陷只在新功能下出現。

修法：在 ggml_metal_graph_compute 內（gf 還活著、thread pool 還沒啟動時）把節點名指標快照到 ctx->cgc_nm[]。 ggml_tensor 本身活在模型的 context 裡 ⇒ 只快照指標就夠，只死掉的是 cgraph 的節點陣列。

⇒ 已登錄為 lesson eng-diag-0034（class diagnosis）。它的推廣述句是： 跨模組的存取器不可以讀「呼叫者擁有的指標」；判別式是「這個欄位在呼叫返回之後還有誰在讀」—— 若只有新加入的讀者會讀它，症狀就會是「新功能一開就 SIGSEGV，而既有路徑完全正常」。

§4.2 自我檢查第一版是空轉

第一次跑 en-nodes 時 delta 印 0.00%， 但同一行是 layer gpu_sum=0.00 ms —— 分母是 0，所以那個 0 沒有意義。 原因：dp_lay_gpu[] 只在 CGC_GPU_TIMING 開著時才被填， 而那一版臂沒有帶它。修法：en-nodes 臂加上 CGC_GPU_TIMING=1， 並把「為什麼需要它」寫進臂的註解。

§4.3 詞彙表第一版把 67% 的時間丟進 (other)

第一版的種類鍵是「去掉節點名尾端的 -<層號>」。那在有 40 層的模型上 仍有約 600 個不同的名字，於是 48 個格子被 warmup 期的罕見種類佔滿 （conv_states_reshaped、alpha、beta…）， 大的種類反而進不了表。修法：改成固定的前綴字彙表（40 個前綴、最長匹配） ⇒ nkind=22、(other)=0.00 ms。

⇒ 第 3 件交付的是可用的儀器（有精確的自我檢查），不是已調校的詞彙表。

§7 誠實邊界（本文件不主張什麼）

  • 不主張「L0 已被解釋」。 這一份主張的是「L0 沒有可重現的異常」， 以及 7.2× 屬於哪個 regime。§1.3 的兩個候選都沒有被分離。
  • 不主張這張種類表可以下 M3 的判決。 §5 的兩個限制未解之前， 「ffn_moe_* 佔多少」這個問題還不能問。
  • 不主張逐節點。 這支儀器的解析度是「一個 command buffer 覆蓋的連續節點範圍」， 範圍內的節點沒有被時鐘分開。真正的逐節點需要 sample point 或改派送。
  • 沒有量 t/s。 這一輪的所有讀數都是 GPU 時鐘與計數器，沒有吞吐數字被引用； 三組量測的熱態各不相同（一組 MODERATE/NOMINAL、兩組 HEAVY）， 所以它們只被當成比值的來源，不被當成水準。
  • 沒有跑 check_build_tracked.sh 的 replay bench（依 D2， RUN_REPLAY_BENCH=0，理由是 .replay_bench_baseline.json 已 stale）。
  • 沒有 push。
  • 本輪的 build 把另一條線未提交的 ggml-metal-ops.cpp 一起編進去了 ——同一個 binary 無法分離，所以由這個 commit 收錄並在此揭露。 兩個版控內的 dylib 因此被改寫（libggml-metal 037c931e → 2f2f85e7、libggml-base 23f533ad → 4323e8eb）。
