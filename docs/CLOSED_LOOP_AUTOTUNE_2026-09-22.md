# 闭环 autotuner：把「精准测量工具」补上那 20%（2026-09-22）

回答一个问题：`shape_knob_search.py` 已经是一把很准的尺，为什么还不是 autotuner。

## 一、缺的三件事，各自的判别方式

要让「闭环」「会学习」「真正的 autotuner」不是形容词，它们必须各自能被证伪。我把它拆成三条，每条配一个**突变开关**，突变必须让配套测试变红：

| 声明 | 具体含义 | 突变（必须变红） | 实测代价 |
|---|---|---|---|
| **1 闭环** | 下一个测谁由后验决定，不是由事先打好的清单决定 | `--broken policy`：改成均匀分配，完全无视观测 | 后验收敛到真最佳的质量掉 **3.1 个百分点** |
| **2 学习** | 观测噪声 σ 由重复观测估计，不是假设一个值 | `--broken sigma`：固定 σ=0.06（比实际安静 4 倍） | 全噪声场景的假发现率 **6.0% → 54.0%** |
| **3 诚实** | 带 P(best) 给推荐，达不到就 `NO_EVIDENCE`；低于 3% 门槛不发声 | `--broken noev`：永远宣布领先者胜出 | 假发现率 **6.0% → 93.0%** |

三条都**在进程内自己跟自己的消融对照**，没有写死任何「应该通过」的布尔值 —— 也就是某个突变哪天不再有代价，整套会自己变红，而不是默默同意自己。

## 二、它到底是怎么办事的

```
先验: theta_g ~ N(0, 0.5^2)   // log 空间；mu=0 = 「旋钮没用」，这行的先验立场来自这个 repo 的历史
每次观测: y = log(cell_ts / ref_ts)   // ref 用 crossover_estimate.ref_at 在 cell 自己的时刻做 log 插值
更新:     共轭正态，观测噪声 sigma 由重复观测 pooled 估计
选下一个: Top-Two Thompson Sampling（TTTS）——每次抽两组后验样本，J1 与「除 J1 外的胜者」J2，掷币决定。
         用 Top-Two 而不是普通 Thompson，是因为只有**亚军**能推翻领先者。
停止:     P(best) >= 0.95 且 |effect| >= 3%（repo 门槛）
```

**为什么所有东西都在对数空间**：机器对吞吐是**乘法**作用的，而 cell/ref 是个比值，只有取 log 之后才变成加法。这条和 `crossover_estimate.py` 是同一个理由。

**为什么一个 block 共用一对 reference**：逐个 cell 夹测（head ref + cell + tail ref）会让 reference 吃掉三分之二预算，而一次 reference 和一次 cell 一样贵。block 把 `ref_head + K 个 cell + ref_tail` 排在一起，成本从 `K + (K+1)` 降到 `K + 2`。代价是 block 内部假定漂移在 log 空间线性 —— 这正是夹测本来就在做的事，没有引入新假设。

## 三、能依赖的部分 vs 不能的部分

selftest（`scripts/check/closed_loop_autotune.py --selftest`，17 项全绿，100 seeds）：

```
CLAIM 1 [loud  σ=0.16] 后验集中在真最佳上 30.4% vs 均匀分配 28.3%（4 臂先验是 25%）
CLAIM 1 [quiet σ=0.06] 31.7% vs 28.6%
CLAIM 1 突变：忽视后验 → 掉 3.1 个百分点
CLAIM 3 平坦场景（四臂完全相同）保持沉默：假发现 6.0%
CLAIM 3 突变：拿掉证据闸门 → 93.0% 凭空宣布胜者
```

### 三件不好看但必须写下来的事

1. **regret 不是它赢的地方。** 我原本断言「学习策略部署得离真相更近」，实测在 14 次 launch 的预算下**并非如此**：
   `quiet 1.92%（均匀 1.75%）`、`loud 3.21%（均匀 2.94%）` —— 学习策略偶尔偏小 regret，比均匀略差。原因不神秘：集中采样买更少的臂，一旦自信地排错，regret 就付出代价。所以**这项从「判定项」降级为「如实打印的观察」**，只有真的会动的两项留在断言里。（这正是上次 `crossover_estimate.py` 里 cherry-pick 的教训：不能挑一个几何来证明自己。）

2. **观测到的假发现率高于标称值。** 标称是 `1 - 0.95 = 5%`，实测 6.0%。因为同一 block 内的 cell 共享那两次 reference launch，**它们的观测误差是相关的**，于是 n 高估了实际证据量。这条我没有靠调 σ 把它抹掉，而是印出来。

3. **高噪声下报价会偏高 1~2 个百分点。** σ=0.16 时 +7% 的真实效果平均读成 +8.9%。这是 `exp()` 是凸函数造成的（Jensen），不是修正管道有偏 —— 用 σ=0.02 验证过，偏差只有 ≤0.2 个百分点。**这正是决策依赖 P(best) 而不是依赖报价数字的原因**：P(best) 数的是 argmax，对单调变换免疫。

## 四、最有用的一张表：什么样的效果才值得去 sweep

这是这个文件算出来最值得记住的东西。给定一份预算和一个噪声水平，**多大的真实差距才能被认证**：

| σ（单次对数观测噪声） | 两臂解析下界（乐观） | 仿真标定的真实门槛 |
|---|---|---|
| 0.16（这台机器的水平） | 23.5% | **~68%** |
| 0.06（安静／多次平均后） | 8.4% | **~52%** |

两臂代数式是乐观的，而且错在两个都往同一方向推的方向：要打败的对手不止一个；且每次观测量 `log(cell / 插值ref)` 叠了两段 reference 的噪声，有效 σ 比 launch-to-launch σ 大。所以门槛用**仿真标定**（`calibrate_boundary()`，二分搜到 50% 认证率），不用我的代数。

**这张表怎么用**：如果你的旋钮预期只能带来 3~5%，**别做这个 sweep** —— 14 次 launch 的预算在数学上不可能把它和噪音分开，无论加多少旋钮都一样。这不是悲观，是算出来的。而这也解释了为什么这个项目一路剥下来每一层都「低于门槛」。

## 五、落地的东西

- `scripts/check/closed_loop_autotune.py`：政策层 + 预算 + 停止规则 + 自我证伪
  - `--selftest`（17 项）／`--exec`（真跑）／`--dry-run`（只印计划）／`--grid`／`--block`／`--max-launch`／`--confidence`
  - ⚠ `--broken` 一旦上了值，`--exec` 会拒绝启动 —— 突变是用来在进程内用植入的真值验证逻辑的，不该花真实GPU时间去量一个已知会错的算法。
- `scripts/check/shape_knob_search.py`：budget 轴从 `{4, 8} GiB` 扩成 `{3, 4, 6, 8} GiB` 阶梯，给闭环一个真正的搜索空间（4 臂）。

## 六、今晚用它跑了什么：budget 轴

动机来自 §EN-437 那个反直觉的读数：**capacity miss 只占 miss 的 6~7%**，143 个 slot 并不是容量饥饿
⇒ 处方应该是**缩池**，把 RAM 还给 §EN-434 已量到占 81.7% 的非 MoE dense 部分。搜索空间
`LLAMA_ARG_EXPERT_CACHE = {3, 4, 6, 8} GiB`（16 GB 里 dense 与 pool 的分法），`--block 2 --max-launch 16`。

结果（`Backup/shape_search/prod25-stream_-loop_budget/autotune.json`）：

```
best=LLAMA_ARG_EXPERT_CACHE6442450944 +3.40%   P(best)=0.44   launches=16   sigma=0.281
STATE: NO_EVIDENCE   P(best)=0.44 < 0.95: budget spent, arms not separated

   6 GiB  n=3   +3.40%  sd=0.127   ys=[+0.066, +0.013, -0.037]
   3 GiB  n=2   -3.89%  sd=0.139
   4 GiB  n=2   -6.78%  sd=0.200
   8 GiB  n=3  -11.21%  sd=0.144   ys=[-0.234, +0.006, +0.195]
reference series: 9.43  10.47  10.08  10.20  9.78  11.44
```

**读法，按重要性排序：**

1. **窗口是干净的，这次赖不了。** reference 序列全程 NOMINAL、散度只有 ±10%（对比昨晚 M 扫描那个
   11.72 → 5.22 的崩塌）。所以「没分开」不是机器漂移的锅。
2. **在线学到的 σ = 0.281**（28%，已含漂移修正后剩下的每次观测噪声）── 比我 selftest 里假设的
   0.16 还糟近一倍。这才是这条轴测不出来的原因。
3. **排序本身是诱人的**（6 GiB 最好、默认 8 GiB 最差，方向正好符合「缩池把 RAM 还给 dense」的假设），
   但 **P(best) 只有 0.44**（四臂的先验是 0.25）。这个数可以写成「值得再追」，**不能写成结论**。
4. **要把它做成结论需要多少预算**（用学到的 σ=0.281 算，且这是乐观的两臂下界）：

   | 想认证的效果 | 每个 arm 需要的观测数 | 大约 launch 数 | 墙钟时间（~2 min/launch） |
   |---|---|---|---|
   | 43% | 3 | 16 | ~35 min（今晚做的就是这格） |
   | 10% | ~50 | ~200 | ~7 小时 |
   | **5%** | **~170** | **~680** | **~23 小时** |
   | **3.4%（今晚看到的差）** | **~250** | **~1000** | **~33 小时** |

   ⇒ 在 σ=0.28 下，**靠加预算来验证这条轴是不划算的**。真正的杠杆不是预算，是 σ 本身：
   把每次测量的方差降下来（更长的 generation、更多 reps、每侧多跑一次 reference 以压掉插值噪声），
   让 σ 从 0.28 掉到 ~0.10，同一套问题就回到可解范围。**这也是这份机器给出的最实际的一条建议。**
