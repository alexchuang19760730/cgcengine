# 在 16 GB 上碰 1M：不靠 KV 技術，靠「別把 1M 放進 context」

日期：2026-10-02 · 作者：線 A · 狀態：**原型（新軸）**，未進任何看板格、未進任何閘門

## 0. 這份文件回答什麼

上一篇（DA 評估，見 `.workbuddy/memory/2026-10-02.md` 21:1x 節）的結論是：1M 上下文在
這台盒子上**裝不下也跑不動**，而 DA 是速度槓桿不是容量槓桿。那剩下的問題是：

> 如果一定要在 16 GB 上處理 1M token 的語料，具體怎麼做？

答案：**不要把它放進 context**。這份文件給出可執行的分層方案與預算。

## 1. 先記住這三個數字（都是已認證的，不是估的）

| 量 | 值 | 來源 |
|---|---:|---|
| KV 成本 | **10.5 KiB/token** | GGUF 實讀：41 層、`head_count_kv=2`、`key/value_length=256`、q8_0、`full_attention_interval=4` ⇒ 只有 10 層帶 K/V；8192 ctx 實測 85 MiB 對得上 |
| prefill | **≥250 t/s**（9 次 launch，最高 296.24；認證臂實測 291.36） | 看板 `m-prefill250`（C1） |
| decode | **15.210976 t/s**（C13，⚠ `both`＝降級窗）／乾淨窗 13.867（C12） | `decode_board_2026-09-29.yaml` |

## 2. 真正的約束不是記憶體，是 prefill

| 做法 | KV 記憶體 | prefill 時間（@250 t/s） | 可行性 |
|---|---:|---:|---|
| 1M 直接塞 | **10.8 GiB** | **4,000 s ≈ 67 分鐘** | ❌ 裝不下（＋pool 8 GiB ＝ 18.8 GiB > 16 GB），也慢到不能用 |
| 檢索後塞 8K | 86 MB | 32 s | ✅ |
| 檢索後塞 4K | 43 MB | 16 s | ✅ 建議起點 |

**關鍵認知**：就算記憶體奇蹟地夠，1M 光 prefill 就要一小時。所以 RAG 的價值在這裡
是**把 67 分鐘變成 16 秒**，省記憶體只是附帶好處。

⇒ **預算寫死：每次 query 只塞 4K–8K token。** 這同時也讓 KV 小到完全不是問題
（43–86 MB，對比 1M 的 10.8 GiB）。

## 3. 分層方案

### Tier 0 — BM25 詞彙檢索（**零模型、零額外記憶體**，從這裡開始）

- 索引是 sqlite FTS5，放磁碟、mmap 讀取 ⇒ query 時常駐 RAM 幾乎為 0。
- **不需要第二個模型** —— 這是本方案的核心設計約束。理由：一個專用 embedding 模型
  必須與 35B ＋ 8 GiB pool 同時常駐，而這台盒子現在 swap 就用了 3.8–9.5 GB（總量 10.24 GB）。
- 工具：`scripts/rag_bm25.py`（stdlib only，無依賴）。
- 中文處理：FTS5 的 unicode61 tokenizer 對沒有空白的中文會切成**一個 token**，
  所以索引時把 CJK 展開成重疊 bigram（「機器學習」→ `機器 器學 學習`）。
- ⚠ FTS5 的 `MATCH` 預設是 **AND** 語義；bigram 不可能全部共現 ⇒ 查詢必須用 **OR**
  交給 `bm25()` 排序，否則中文會 0 命中。

### Tier 1 — 語義召回（選配，離線建索引）

- build 裡**已經有 `llama-embedding` 和 `llama-retrieval`**（`src/llama.cpp/build/bin/`）。
- 做法：在 **35B server 沒跑的時候**，用小模型（例：0.6B Q8 ≈ 600 MB）跑一次
  `llama-embedding` 把 chunk 向量化，存進 sqlite。
- ⚠ query 時要嵌入問題 ⇒ 又要載一次那 600 MB。這台盒子風險高，建議先做
  「BM25 取 50 候選 → 小模型重排」而不是純向量召回。

### Tier 2 — context compression（選配）

- LLMLingua 那類方法**需要一個小模型打分**，同樣有共存問題。
- 零模型替代：對檢索回來的 chunk 做「句子級去重 ＋ query 詞覆蓋度過濾」，
  把 4K 壓到 2K ⇒ prefill 再省一半。
- 另一條（離線）：用主模型自己對 chunk 做 map-reduce 摘要，建一份壓縮過的索引。

## 4. 具體怎麼跑

```bash
# 1) 建索引（每個語料跑一次；選盒子沒在量測的時候）
/opt/homebrew/bin/python3 scripts/rag_bm25.py index \
    --db /tmp/rag.db --input ./corpus \
    --chunk-tokens 500 --overlap-tokens 50

# 2) 只看法：印出組好的 prompt
/opt/homebrew/bin/python3 scripts/rag_bm25.py query \
    --db /tmp/rag.db --q "你的問題" --k 8 --budget-tokens 4000

# 3) 真的丟給 :8080 的 server（OpenAI-compat）
/opt/homebrew/bin/python3 scripts/rag_bm25.py query \
    --db /tmp/rag.db --q "你的問題" --server http://127.0.0.1:8080
```

分塊建議：500 token／塊、50 token 重疊 ⇒ 1M token ≈ 2,000 個 chunk。
`--chars-per-token` 預設 3.0（英文散文約 4.0、中文約 1.5–2.0），語料偏向哪一邊就調它。

## 4.1 實測（1M token 合成語料，24 檔）

| 項目 | 實測值 |
|---|---:|
| 語料 | 3,000,518 chars ≈ **1,000,173 tokens** @ cpt=3.0 |
| 建索引（24 檔／2,208 chunk） | **1.7 s**，索引檔 **23 MB** |
| 查詢延遲（12 題，含 Python 啟動） | min 100 ms／**p50 110 ms**／max 152 ms |

⇒ 檢索本身不是瓶頸：它佔一次查詢的 **0.4%**。真正的時間在 prefill（16 s）與 decode（13 s）。

**端到端延遲對照**（一次查詢，語料 1M token）：

| 做法 | KV | prefill @250 t/s | decode 200 tok | 總計 |
|---|---:|---:|---:|---:|
| 1M 直接塞 | 10.89 GiB ❌ 裝不下 | 4,000 s | 13 s | **4,013 s ≈ 67 min** |
| 256K 直接塞（盒子極限） | 2.81 GiB ⚠ 貼爆點 | 1,024 s | 13 s | **1,037 s ≈ 17 min** |
| **RAG 只取 4K** | **43 MB** | **16 s** | 13 s | **29 s** |

⇒ 對「能跑的」基準（256K）是 **約 36×**；對 1M 是約 138×，但 1M 本來就跑不起來。

⚠ 上表 prefill／decode 是用**已認證讀數外推**（prefill ≥250 t/s、decode C13 15.210976），
不是本工具量出來的；RAG 那一列的「43 MB」是 KV 幾何（10.5 KiB/token）算出來的。
⚠ 這是 **CPU／磁碟量測 ＋ 外推**，不是 GPU decode 實測 ⇒ 不在認證管道內、不進看板格，
也**不能用來推論新的 t/s**；要引用 t/s 仍須過 `caliber_gate.py` ＋ `quote_gate.py`。

## 5. 已知限制（寫在前面，別踩）

- ⛔ **本工具不在認證管道內**：它不餵任何看板格、不過任何閘門。用它量到的 t/s
  必須先過 `scripts/check/caliber_gate.py` 與 `scripts/check/quote_gate.py` 才可引用。
- ⚠ chunk 邊界的重疊是用「末尾 N 個字元」切的 ⇒ 偶爾會從半個詞開始（例如 `TP 關閉`）。
  原型階段可接受；要乾淨就改成按句邊界回退。
- ⚠ BM25 是詞彙匹配，抓不到同義改寫。這是 Tier 1 存在的理由。
- ⚠ 建索引是 CPU／IO 活，不要在量測窗內跑。

## 6. 與主線（20+）的關係

**沒有關係，也不該有。** 本線主線是消非 compute 時間（gap/wait/cb/fill）且維持
M1/M2/M3 bit-identical，交付 cell 是短上下文（`-p 2048 -d 512`）。RAG 是「長語料」
這條新軸的入口，不改變 decode 步預算，也不該被讀成 20+ 的進展。
