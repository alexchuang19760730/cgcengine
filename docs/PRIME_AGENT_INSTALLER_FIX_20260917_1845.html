1. 怎麼被發現的：三次執行、兩次 hang

2. 缺陷一：被 source 的腳本不能用 exit

tb 執行安裝腳本的方式（run.log:18 原文）：

Sending keys: ["source /installed-agent/install-agent.sh || echo 'INSTALL_FAIL_STATUS'", '; tmux wait -S done', 'Enter'] min_timeout_sec: 0.0 max_timeout_sec: inf

是 source。而原版只開了 set -e、沒有 set -o pipefail，所以 curl … | sh 的管線狀態取右側 sh 的（空 stdin → 0）； 真正的錯因只剩 stderr 那一行。接著腳本走到驗證段，印 prime-agent install failed，然後 exit 1 —— 在被 source 的腳本裡，exit 會連 tmux shell 一起結束， 於是同一行後面的 tmux wait -S done 永遠不執行，tb 就停在 max_timeout_sec: inf 上。

最刺眼的一點：失敗訊息一次都沒印出來。 INSTALL_FAIL_STATUS 在 pane 與 run.log 裡各出現 1 次 —— 但 grep -n 指出那兩次都在「被印出來的那行命令」裡，不是輸出。 所以「|| 有沒有生效」這件事，光看「字串在不在」會得到相反的結論。

2.1 在隔離環境重現（不需要容器）

$ printf '#!/usr/bin/env bash\nexit 1\n' > /tmp/a.sh
$ bash -c 'source /tmp/a.sh || echo FELL_THROUGH; echo "shell 還活著"'
  rc=1                     ← FELL_THROUGH 沒印、shell 還活著 也沒印

$ printf '#!/usr/bin/env bash\nreturn 1 2>/dev/null || exit 1\n' > /tmp/b.sh
$ bash -c 'source /tmp/b.sh || echo FELL_THROUGH; echo "shell 還活著"'
FELL_THROUGH
shell 還活著                 ← 契約達成
$ bash /tmp/b.sh; echo rc=$?  ← 獨立執行時仍然正確
rc=1

這一組對照同時證明了修法的兩個方向都對：被 source 時 || 收到非零且 shell 存活； 被當獨立程式跑時回傳 1。

3. 缺陷二：沒有 curl，而沒有 pipefail 把錯因藏起來

任務映像 ubuntu-24-04 是精簡版。在容器裡逐項確認：

工具在容器裡備註
curl沒有prime-agent 官方安裝腳本需要它
wget沒有——
nc沒有——
python3有所以我用它做過連通性探測
setsid有（/usr/bin/setsid）缺陷三的解法靠它

apt-get install -y curl 在該映像裡成功 —— 也就是說容器有對外網路， 缺的只是「沒人先裝它」。修法就是在安裝之前補上這一步。

4. 缺陷三：5 個提示只有 1 個認開關

官方安裝器（app.primeintellect.ai/prime-agent/install.sh，2357 行）一共問 5 次 yes/no：

行號問題認 PRIME_AGENT_INSTALLER_NONINTERACTIVE？
:2233Install Prime Agent v<ver>?認（:2232 那個守衛就在它上面）
:1078Install Node.js and npm with <method>?不認
:1485Add standalone Node.js to your PATH?不認
:1607Install Prime Agent v<ver> globally with npm?不認
:1642Prepare Python runtime now?不認

而提示的輸入來源是 prime_agent_prompt_yes_no()（:883）：

if ( : <>/dev/tty ) 2>/dev/null; then
    prompt_input=tty
    exec 3<>/dev/tty          ← 優先開 /dev/tty
elif [ -t 0 ]; then
    prompt_input=stdin
else
    return 2                 ← 兩者都沒有 ⇒ 「不問」，呼叫者視為繼續
fi

tmux 裡 /dev/tty 是可開的，所以它會走第一支，等一個永遠不來的 Enter。 實測：只加 NONINTERACTIVE=1 之後仍然卡住，而症狀極具誤導 —— 行程只剩一個 sh 在等、~/.local/bin 是空的、/tmp/node-compile-cache 存在 （看起來像「正在裝」，其實是「正在等輸入」）。

解法：不給它控制終端。 curl … | setsid sh ⇒ /dev/tty 打不開、stdin 也不是 tty ⇒ 五個提示全部走 return 2（＝繼續）。 在同一個「有 tty」的容器裡做的對照：

$ docker run --rm -t ghcr.io/laude-institute/t-bench/ubuntu-24-04:latest sh -c '
    export PATH="$HOME/.local/bin:$PATH"
    apt-get update -qq >/dev/null 2>&1; apt-get install -y -qq curl >/dev/null 2>&1
    curl -fsSL https://app.primeintellect.ai/prime-agent/install.sh | setsid sh'
downloading uv 0.12.15 aarch64-unknown-linux-gnu
everything's installed!
✓ ready
kernel python: /root/.prime/agent/kernel-venv/bin/python
Installed Prime Agent 0.9.5 at /root/.local/share/prime-agent/bin/prime-agent
/root/.local/bin/prime-agent
0.9.5

我在這個修法裡自己先寫錯一次，值得記下來：第一版寫成 PRIME_AGENT_INSTALLER_NONINTERACTIVE=1 curl … | sh —— 那個賦值只作用於 curl，而安裝器是在管線右側的 sh 裡跑的， 它看不到那些變數。症狀與「這個開關根本沒用」一模一樣。必須用 export。

6. 「停在模型端點」的直接證據

tb 的 pane 捕捉不含 agent 自己的 stderr，而容器在收尾時被刪掉了 （datasets/…/play-zork 的 compose 專案已經 down）。所以我在 host 上補了這一塊： 把 harness/ 複製到 /tmp（避免污染 repo），用同一組 TB_GEMMA4_* 變數跑一次 prime-agent，然後讀它自己的日誌：

{"provider":"local-gemma4","model":"openai/hy3","api":"openai-completions","kind":"auth",
 "providerErrorType":"authentication_error","status":401,
 "message":"401 The API Key does not exist or signature verification failed. Please check
            whether the API Key is correct. See: https://console.cloud.tencent.com/tokenhub/apikey"}

也就是說：整條鏈路是通的（容器 → 網路 → OpenAI 相容端點 → 認證）， 而在 agent 安裝修好之後，剩下的一關就是一把有效的 API key。

關於「WorkBuddy 有沒有提供這種端點」（同一輪被問到的）：

  • WorkBuddy 自己的開放 API（workbuddy.cn/apiDocs，Base https://api.copilot.tencent.com/api/v1）是企業管理 API： 12 個域（成員／License／用量／模型管理／技能／專家／日誌／可觀測／資源）， 沒有 /v1/chat/completions，且明文「不支持个人 API Key 调用」（個人 Key 一律 401）。
  • WorkBuddy CLI 的本地 REST（codebuddy --serve --port 8080）是它自己的形狀， 而且預設也用 8080，會跟本 repo 的 llama-server 撞埠。
  • 但 OpenAI 相容的端點有，來源是騰訊雲 TokenHub —— WorkBuddy 自己就是用它當「自訂模型」： 端點 https://tokenhub.tencentmaas.com/v1/chat/completions，Key 在 console.cloud.tencent.com/tokenhub/apikey 建立（要確認 Key 的可訪問範圍有勾到模型）， 文件範例模型 hy3。上表那個 401 就是它回的。

7. 兩個順帶發現（不屬於本 commit）

7.1 tb_loop/README.md 的範例沒有可用的 cwd（未修）

README 寫的是：

PYTHONPATH=agent_harness .venv/bin/tb run … -k harness_dir=tb_loop/harness

但這三個相對路徑沒有任何一個 cwd 能同時滿足：.venv/bin/tb 要 cwd 是 agent_harness/tb_loop；PYTHONPATH=agent_harness 要 cwd 是 repo 根； 而 agent_harness/tb_loop/tb_loop/ 不存在（所以 harness_dir 也對不上）。 本輪用的是「cwd＝repo 根 ＋ harness_dir 給絕對路徑」，實跑通過。

本 commit 刻意不改它：agent_harness/tb_loop/README.md 在 MANIFEST.jsonl 裡，改它會多一筆索引漂移；而此刻另一條線正在寫 scripts/run_server.sh 與 phase_split_ab.py（見 §8）， 重生索引會把他們尚未完成的位元組寫進我的 commit。 所以只記錄、不動手，等對方停手再一起改。

7.2 安裝器的 5 個提示這件事值得回報上游

PRIME_AGENT_INSTALLER_NONINTERACTIVE 只蓋住 1/5 個提示，對「在容器／CI 裡裝」是一個真問題 （而且在 tmux 這種有 /dev/tty 的環境才現形，在沒有 tty 的 CI 裡反而不會遇到 —— 這也是它不容易被發現的原因）。 本輪用 setsid 繞過，但那應該由安裝器自己提供「全部提示都可關」的開關。

9. 誠實邊界

這份文件不主張：

  • 不主張那條模型 smoke 會通過。它仍然 Unresolved（0/1）—— 缺的是一把有效的 API key；本輪用的 api_key=sk-local 是佔位符。
  • 不主張缺陷三是「唯一的」第三個。本輪只跑到「安裝成功 ＋ 第一個模型呼叫」為止； 提示 :1485（加 PATH）與 :1642（Python runtime）在這次路徑上被 setsid 一併自動回答了， 但各分支是否都被走過，我沒有逐一證明。
  • 不主張 setsid 在所有任務映像裡都存在。它在 ubuntu-24-04 映像是 /usr/bin/setsid（util-linux）；腳本保留了沒它時退回 | sh 的分支，而那條分支沒有被驗證過（會回到缺陷三的症狀）。
  • 不主張 §6 那個 401 是「容器內」發出來的。它是 host 上跑 prime-agent、 指向同一個端點、用同一組 TB_GEMMA4_* 得到的；容器內的 401 我在更早一輪 用 curl 直接量過（同一組假 key、同樣的 authentication_error）， 但那一次用的是 curl，不是 prime-agent。
  • 不主張 --offline 是什麼意思。那是 adapter 既有寫法 （prime-agent -p --offline …），本輪照用，沒有查它的語意。
  • 不主張 3m21s 是這個任務的正常時間。agent 在第一個模型呼叫就失敗了， 所以那個數字只反映「安裝 ＋ 失敗」，不反映任務本身的長度。
