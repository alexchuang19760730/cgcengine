1. 為什麼問得出來

S2（把 slot_table 的發布從 host 搬到裝置）必須重現 pick_slot （llama-expert-cache.cpp:478）的答案 —— 因為 host 的 fill 落在 host 選的槽裡， 兩邊不一致 ⇒ gather 讀到錯的槽。而 pick_slot 需要的狀態有七項（見 §3）。

但 pick_slot 已經獨立追蹤一個純 LRU 候選：lru_slot （:531-556，2026-09-15 作為 abort 修復加入，只在 SpAc 分支選不出東西時當 fallback 被使用，卻每一趟 pass 都在算）。⇒ 「EMA 有沒有改變答案」＝ lru_slot != best_slot 一次比較 —— 不需要新狀態、不需要模擬、不需要第二套策略。

在此之前這個問題在 log 上同形。三個計數器存在於樹上卻從未在任何地方被讀： n_spac_lru_fallback、n_spac_nonfinite，以及本探針新增的 LRU 失配配對。 同型的既有註解就在 :2391-2401（n_hit_adopted_queued「written and never read anywhere in the tree」）—— 本探針照那個樣式補齊。

3. 裝置狀態清單（本節真正的產出）

計畫書 docs/S2_IMPLEMENTATION_PLAN_2026-09-20.md §4 第 1 項寫的是 「現行的 expert_cache_on_topk 要在裝置上有一個等價物，或改成表由裝置增量維護」 —— 這一節把那句「要有個等價物」變成一份逐項可查的清單。

狀態要不要搬到裝置依據
slot_owner[]要決定「這個槽是誰的」
slot_last_use[]（uint64 tick）要純 LRU 的依據；也是 EMA 的 tie-break
spac_util[layer][expert]（FP EMA）要 57.42% 的受害者由它決定
batch_mask要這一批已擁有的槽不可選
slot_loading / slot_queued要（介面問題） 在飛的 fill 不可選，但 fill 本身是 host 的行為
tick要（一個純量）LRU 的單調來源
slot_pinned / slot_pinned_static / slot_decode_reserved 可以丟三者 engagement 全為 0

⇒ 常駐狀態＝ 3 個陣列（owner / last_use / spac_util）＋ 1 張 bitmap（batch_mask）＋ 1 個純量（tick）。 難點不是資料量：spac_util 由 spac_update 以 u[e] += bump 的 EMA 維護，要被逐位元重現，否則 placement 分歧 —— 而 57.42% 的受害者由它決定。

4. 它改變了什麼

  • 對 S2 的量級：計畫書 §4 的評估成立（S2 維持大工程）—— 但「工程主體」現在有一份可逐項勾的清單，而不是一句「要有個等價物」。
  • 對「簡化」的誘惑：本輪稍早我一度想用「池子不滿 ⇒ 裝置只做空槽分配就好」來縮小 S2。 那條被兩個獨立讀數擋掉：長 run 的 79.9% capacity（§EN-323） ＋ 本節的 99.2% 需要挑受害者。
  • 對交接單的階梯 ②（owner ＝ 線A (ace)）：這一步沒有移動任何被量測的指標， 它把「S2 要搬多少狀態」從未知變成已知。

6. 誠實邊界

  • 單一 regime：prod25、pool 8 GiB、MTP on、HTTP door。 「三個 pin 類 engagement ＝ 0」是這個配置的性質，不是普遍事實 （換 pool 大小或開 routing-aware placement 就會變；n_pin_marked 有印，本輪未開）。
  • 失配 ≠ 觀測到的分歧：受害者不同 ⇒ 表不同，但被消費的條目是否不同， 取決於那位專家後來有沒有被要。長 run 的 79.9% capacity 強烈暗示會被要， 但這需要第二支探針（在被消費集合上比對）才能定量。 本節只主張「EMA 決定了 victim」，不主張「表在數值上分歧」。
  • free=112 幾乎全發生在預熱期，所以那 0.8% 不是穩態的代表。
  • 沒有動任何數值路徑：探針只在 pick_slot 的兩條 return 上加計數， 不改 dispatch、不改 hook 順序、不改 slot_table 的內容。
