1. 為什麼一個症狀底下有三個根因

這次從頭到尾只有一個症狀：total_input_tokens = 0。但 failure_mode 會在 agent_timeout / unset / test_timeout / parse_error 之間跳 —— 因為它報的是第一個撞到的失敗點，而失敗點會隨著前一個被修好而往後移。底下是三件互不相干的事， 修好任一件不會讓另兩件變好。
判準（本輪最有用的那一條）：不要看 failure_mode，看「agent 那一步實際花了多少秒」 —— run.log 的 Blocking command completed in <N>s。 10 秒 = agent 根本沒被等待；53／163 秒 = 真的跑了。

2. 三個缺陷

#缺陷實測症狀修法與出處
1 安裝腳本裡的 Node.js 兜底（curl https://deb.nodesource.com/setup_22.x | bash - ＋ apt-get install -y nodejs）是安裝階段唯一剩下的外網依賴 smoke5 裝成了（整段 43.26s）；smoke6 卡死 >10 分鐘，pane 停在 deb.nodesource.com 那一行。
量到的原因：Fetched 24.1 kB in 2s (10.7 kB/s)，而 nodejs 的 deb 約 25 MB ⇒ 約 40 分鐘，超過 360s 預算。		 整段刪掉，並把安裝方法釘死成 native。
官方安裝器不需要 node：install.sh:76-88 在 PRIME_AGENT_INSTALL_METHOD=auto 且 prime_agent_native_platform 成功時， 直接 prime_agent_install_native 並 return ⇒ :1078 的 Install Node.js and npm with …? 提示 一行都不會執行。
另加 export PRIME_AGENT_INSTALL_METHOD=binary：平台偵測萬一失敗就 當場報錯，而不是靜默回退到那條會掛 40 分鐘的路。
2 tb 的 agent 命令預設 block=False ⇒ send_command 送完就返回 agent 階段只有 10 秒、total_input_tokens = 0； run.log 裡 agent 那條命令之後沒有 Blocking command completed。 TerminalCommand(..., block=True, max_timeout_sec=float("inf"))。
出處（皆為原始碼）：terminal/models.py:13（預設 False）→ tmux_session.py:296-307（send_keys(block=command.block)）→ abstract_installed_agent.py:173-179（送完即 return AgentResult(total_input_tokens=0, total_output_tokens=0)）。
上游既有寫法一律 block=True：claude_code_agent.py:64、codex_agent.py:46。
改後實測：agent 階段 10s → 53s → 163s，且真的出現了模型輸出。
3 agent 的時間預算把「安裝 agent」也算進去 預算被安裝吃掉 ⇒ 剩下的時間不夠 agent 做事 ⇒ 結果被讀成「模型解不出來」。 時限來源是任務自己訂的：harness.py:639-643 取 trial_handler.task.max_agent_timeout_sec，而 raman 的 task.yaml:35 是 360.0。tb 把安裝與 agent 送進同一個 tmux session （run.log 的順序：Sending keys: [source …/install-agent.sh …] → Agent timed out after 360.0s）⇒ 安裝花的每一秒都從 agent 預算裡扣。
加 --global-agent-timeout-sec（預設 900，TB_AGENT_TIMEOUT_SEC 可覆寫）。
★ 代價寫清楚：官方榜單的數字是 360s 下產生的，放寬後不可直接與之比較。

2.1 第 2 條為什麼最值得記

它讓前面所有「模型不行」的推論全部失效：agent 從來沒有被等待過。 而它的現場與「安裝太慢」長得幾乎一樣（都是 0 token ＋ 一個 timeout），所以修好第 1 條之後， 直覺會以為「現在應該會動了」—— 實際上不會。兩個缺陷必須分別量、分別修。

3. Python kernel：接受判準在執行檔裡，不在文件裡

3.1 官方文件給的解析順序

release tarball 內的 rlm-runtime.md（在它的 docs/ 目錄下，Kernel Lifecycle 章節）原文：

Python resolution is:
1. PRIME_AGENT_KERNEL_PYTHON, when it has a current prime-agent-runtime;
2. ~/.prime/agent/kernel-venv/bin/python, bootstrapped with uv; or
3. the XDG data location when ~/.prime is not writable.

The managed environment includes Python 3.11, prime-agent-runtime, dill, and the default Python packages.
A bootstrap marker detects stale environments.

3.2 路徑②走不通：缺一個文件沒說名字的標記

那句話說有「A bootstrap marker」，但沒說它叫什麼。改成掃執行檔字串就有了 —— 在 prime-agent（約 160 MB）裡： 
var bPn = 9, pPn = "3.11", SPn = "prime-agent-runtime", R7e = "dill",
    x7e = "curl -LsSf https://astral.sh/uv/install.sh | sh",
    xPn = ".bootstrap-version",
    E$s = ".bootstrap.lock";
⇒ 路徑②的 ~/.prime/agent/kernel-venv 需要一個 ~/.prime/agent/.bootstrap-version（常數 9）才算 current。 我們離線自己建出來的 venv 沒有那個標記 ⇒ 必被判 stale ⇒ 走 bootstrap ⇒ uv python install 3.11 因無網而失敗。實測（smoke8）agent 拿到的原文： 
Failed to set up the Python kernel runtime.
/root/.local/bin/uv python install 3.11 failed with exit code 1
First-time setup needs internet to install uv, Python, prime-agent-runtime, and default Python packages;
once set up, prime-agent runs offline. An interrupted runtime upgrade needs network once more,
so re-run this while online.
Set PRIME_AGENT_KERNEL_PYTHON to a Python with a current prime-agent-runtime and default Python packages
installed to skip auto-bootstrap.
⇒ 必須走路徑①（在 agent 命令裡 export PRIME_AGENT_KERNEL_PYTHON=…）。

3.3 路徑①有一道硬檢查（不是警告）

改成路徑①之後（smoke9），agent 拿到的原文換成： 
PRIME_AGENT_KERNEL_PYTHON points to a Python missing default Python packages
(requests, httpx, yaml, tomli, dotenv, pandas, numpy, scipy, bs4, lxml, pydantic, tyro):
/root/.prime/agent/kernel-venv/bin/python
那份清單裡 numpy / scipy / pandas / lxml / pydantic-core 都是原生擴充 ⇒ native wheel 綁 ABI ⇒ 先前那版「用映像自己的 python ＋ 只裝 pure-python wheel」的 19 MB bundle 在這道要求下根本不可能成立（我為此白做了一版）。 可行解：bundle 自帶 linux-aarch64 的 standalone CPython 3.11.15（wheel 全 cp311 ⇒ 與任務映像的 Python 版本無關；3.11 也正好是執行檔裡 pPn = "3.11" 期望的版本） ＋ 那 12 個包 ＋ dill/hatchling 的 cp311 wheelhouse。
量測值
bundle 大小128 MB（解開 199 MB）：uv 41 MB ＋ CPython ＋ 35 個 wheel／67 MB
容器內離線建 venv ＋ 裝完 30 個包1 秒
15 個關鍵 import（rlm／rlm.mcp／dill／numpy／scipy／pandas／pydantic／tyro…）全部 OK

3.4 mcp 仍然不裝 —— 而且這件事是關鍵

kernel shim 把四個 import 放在同一個 try 裡（執行檔內的 shim 原始碼）： 
try:
    import rlm as _prime_agent_rlm_module
    rlm  = _prime_agent_rlm_module.rlm
    bash = _prime_agent_rlm_module.bash
    import rlm.mcp as mcp
except Exception as _prime_agent_rlm_error:
    _PRIME_AGENT_RLM_IMPORT_ERROR = str(_prime_agent_rlm_error)
    class _PrimeAgentMissingRlm:
        def _raise_missing(self): ...
    rlm = _PrimeAgentMissingRlm()
    def bash(command):
        rlm._raise_missing()
⇒ import rlm.mcp 失敗會連 bash() 一起廢掉。 而實測：import rlm.mcp 在沒有 mcp 套件的情況下 OK —— rlm/mcp.py 是 MCP client registry，只 import 標準庫與 .mcp_base， 而 mcp_base.py:101,207 對 mcp SDK 的 import 全在函式內部（惰性）。 裝了反而壞：mcp → pyjwt[crypto] → cryptography， 其原生擴充在這台 VM 會 SIGILL（import 'cryptography.hazmat.bindings' → Illegal instruction）。 ⇒ 用 --no-deps 裝 runtime，把 mcp／cryptography 擋在外面。

7. 誠實邊界（本 commit 不主張什麼）

  • 不主張 smoke 端到端通過。最後一輪是 402（額度），程式側的修法各有實測，但沒有一次 「安裝 → kernel 被接受 → agent 用工具解題 → 測試通過」的完整證據鏈。
  • 不主張 deepseek/deepseek-flash 能解 raman-fitting.easy。 模型路徑證明到「能產生完整的擬合程式碼與解釋」（smoke8），但那時 agent 沒有工具可用。
  • 不主張這個 smoke 的數字可與官方榜單比較。本輪把 agent 預算從任務的 360s 放寬到 900s （理由見 2.3）；官方數字是 360s 下產生的。
  • 不主張 kernel 與官方 managed 環境等價。我們裝了那道硬檢查要求的 12 個包，但 prime-agent 自己 bootstrap 時還可能裝別的東西；另外刻意不裝 mcp ⇒ MCP 工具伺服器在本流程不可用（本線跑 tb 任務不需要）。
  • 不主張測試階段（max_test_timeout_sec: 60.0）不會再卡。 raman 的 run-tests.sh 自己會 uv sync（走同一條慢 PyPI 通道）， 實測在 60s 內沒跑完。這是下一個未知，本輪沒有處理。
