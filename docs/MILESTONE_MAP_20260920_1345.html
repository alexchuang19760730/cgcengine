5. 為什麼不能相加

兩條階梯的天花板不能相加 —— 而這不是保守，是有實測的：

  • gap ⊆ cb+submit 的原始碼內建交叉檢查實測以 10.09 ms 失敗 （應 ≤24.78，實測 gap=34.87）；
  • 交付 regime 的 union+gap = 1.14 × total 是 UNEXPLAINED （docs/G1_ACHIEVABLE_CEILING_2026-09-20.md §7）。

⇒ 在它被解釋之前，total → union 這個換算在交付 regime 裡不能假設， 「S2 完美 ⇒ 步＝ union」也就不能當成交付承諾。

每一格都要帶 regime 標籤（這是兩份 ceiling 互相否證的成因）

量帶了什麼值
cb高 swap（10.1/11.2 GB）＋ CGC_HOOK_SPLIT ＋ mean_len 3.715 60.22 / 74.18 ms
E2b 暖 ＋ mean_len 2.4021.23 ms

⇒ 差 3 倍，而兩個都可能對。他們的文件已自己標了「絕對值不可與未帶儀器的交付讀數並排」 —— 請把那句當成引用規則，不是免責聲明。

6. 按表操課的紀律

  1. 引用任何 t/s 之前，先指名 (a) 儀器、(b) cell、(c) regime 標籤。 交付 decode 一律用 scripts/check/prod_profile.py 的 decode-delivery cell（--batch 512 --ctx-size 4096 --warm-skip 64 --spec-type draft-mtp）。
  2. 單臂噪音底 ≈ ±27%（同一個命令、同一次 session 讀 9.90 與 12.57，更低的那次 worst=MODERATE） ⇒ 小於 ~27% 的效應，單臂前後對比證明不出來，只能用配對交錯 A/B（第一步 --null）。
  3. 動了 decode 的槓桿，prefill 必須用同一個 commit 重量 —— CGC_SPAC 的 EMA 更新與 spac_prefetch 都在 prefill 的熱路徑上 （run_server.sh 的 prefill250 區塊自己寫了這件事）。
  4. 任何 commit 都要指名它移動 G1 的哪一個 restatement （cb_sum/total 還是段數）—— G1.to 自己寫了這條要求。
  5. 改動前先查窗口：cmake --build 會蓋掉別的 session 正在 map 的 .dylib， 而這個 repo 的所有比較都建立在「同一個 build」上。

7. 誠實邊界

  • 本頁不是新的量測。每一格都指回既有出處；本頁的工作是把散在四份文件裡的東西 放進同一張表並標明性質。
  • M-now 的 prefill 是 09-18 的數：09-20 三次嘗試（188.12／212.59／222.40） 全部 worst ≥ MODERATE ⇒ 不可引用，所以「prefill 現況」這一格 嚴格說是未驗證。
  • 兩條階梯的推算格沒有一個是量測，而且其中一條（線 I）的預取那一半 今天已被自己的 L1 關門 ⇒ 它的 25.8 是收不到的舊天花板。
  • 「總和天花板」不是一個數字。可給的是三個帶標籤的上界： 48.5（已觀測最好單層的外推）、173（權重地板，不可達）、 ~205（前者再加 mean_len→4）。而 25 落在「過線」附近， 不是終點 —— 但沒有任何一格是量測達到的。
