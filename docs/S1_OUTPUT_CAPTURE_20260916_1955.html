§9.18.6 輸出擷取：儀器先用對照證明自己，然後推翻了 §9.18.4

三句話： (1) §9.18.6 要的儀器做好了——而且它只是把既有那個通用拷貝內核指向另一個 buffer，.metal 一行未改。 (2) 第一版沒有記憶體屏障，同臂對照顯示它的讀數不可重現，而跨臂跑出來的结果看起來正好證實 正在測的假說 ⇒ 一個自信的假陽性。加上屏障後對照全綠。 (3) 有了可用的讀數：layer 1 的 MoE 輸出在兩臂之間逐位元相同，而 layer 0/1 的 ids 相同、layers 2–39 不同 ⇒ §9.18.4「缺陷在 ids 指向的權重內容（池／slot 內容）」被直接量測推翻， 分歧在 layer 1 的 MoE 輸出之後、layer 2 的 router 之前。

1. §9.18.6 問的是什麼

§9.18.3 用內核側 ids 讀數建立了兩件事：ids 在兩臂之間逐位元相同（39 層 × 117 node × 連續 3 個 graph）， 以及第一個分歧節點是 ffn_moe_gate-2（layer 2 的 router）。§9.18.4 接著做了一個排除法論證：

layer 1 的 gate/up/down ids 相同    （量到的）
layer 2 的 router ids 不同          （量到的）
⇒ layer 1 的 MoE 輸出不同           （推理）
⇒ 「輸入相同 + ids 相同 ⇒ 輸出不同」＝ ids 指向的權重內容不同
⇒ 載體是池／slot 的內容本身        （§9.18.7 因此主張「要修的是 residency」）

整個結論掛在第三步上，而第三步從來沒被量過。§9.18.6 就是把它量出來： 擷取 ffn_moe_down-1（layer 1 的 down projection）的輸出張量，兩臂比對。

2. 儀器：重用通用內核，不是第二套實作

讀 kernel_cgc_ids_capture 的原始碼會發現它與 ids 無關——它就是一個 「把 stride 個 int32 從 buffer 1 抄進 buffer 2 的第 N 個 slot」的內核：

kernel void kernel_cgc_ids_capture(
        constant ggml_metal_kargs_cgc_ids_capture & args,
        device const char * ids,      // buffer 1：來源
        device       char * dbg,      // buffer 2：目的地
        uint tgpig [[threadgroup_position_in_grid]]) {
    if (tgpig != 0 || args.slot < 0) { return; }
    device int32_t * out = (device int32_t *) (dbg + (size_t) args.slot * (size_t) args.stride * sizeof(int32_t));
    device const int32_t * in = (const device int32_t *) ids;
    for (int32_t i = 0; i < args.stride; ++i) {
        const int32_t j = args.n_skip + i;
        out[i] = (j < args.n_ids) ? in[j] : 0x7fffffff;   // sentinel
    }
}

所以「指向另一個 buffer」不需要新內核、新 kargs、新 pipeline。實際改動：

新增的 env
CGC_TENSOR_CAPTURE=<精確節點名>、CGC_TENSOR_CAPTURE_WORDS=N（預設 32，上限 32）
改到的檔案
ggml-metal-ops.cpp（cgc_submit() 共用提交體、cgc_dst_capture()、init 擴充、seq 合併）、ggml-metal-ops.h（註解）、scripts/run_server.sh（allowlist 三行）
沒改到的
ggml-metal.metal、ggml-metal-impl.h、ggml-metal-device.{h,cpp,m}、ggml-metal-context.m
比較器
scripts/check/ids_capture_diff.py 原封不動可用（列格式相同，path=DST）

三個設計要點（都寫在原始碼註解裡）：

  1. 精確名稱比對，不是 substring：ffn_moe_down-1 是 ffn_moe_down-10..-19 的子字串，substring 會一次擷取十層，而比較器按名字配對並保留第一個出現⇒ 會變成一個安靜的錯誤比較。
  2. 獨立的 slot 空間與 buffer：ids 那條已經正好在 4096 上限（36 graphs × 117 nodes），共用 cursor 會 悄悄吃掉「比較器用來切 graph 的那條流」。寬度也不同：ids 運算元 8 words，MoE 輸出一列 2048（此模型）。
  3. 兩條流按提交序合併印出：ids_capture_diff.py 在 ffn_moe_gate-1（一個 ids 列）切 graph。 若把 dst 列全部接在 ids 列之後，它們會落進最後一個偽 graph、跟什麼都比不到、被報成 IDENTICAL——一個假陰性。

3.1 機制：不對稱就是簽名

為什麼 ids 可重現而 dst 不可？

ids 運算元
生產者在 mul_mat_id 很多節點之前（router／add），早已沉降 ⇒ 讀它安全
dst 輸出
生產者是緊鄰的前一個 kernel，而這個 fork 支援內核併發（見 ggml_metal_op_concurrency_reset → ggml_metal_encoder_memory_barrier）⇒ copy 可能讀到該 buffer 的前一位佔用者

修法是在診斷路徑上插一個屏障：

// ggml-metal-ops.cpp, cgc_dst_capture()
// ★ THE BARRIER IS NOT OPTIONAL, and it is the one place this instrument does NOT get to be a
//   pure observer. ... An ids operand is produced many nodes upstream ... the dst is produced by
//   the IMMEDIATELY PRECEDING kernel ...
ggml_metal_encoder_memory_barrier(ctx->enc);

屏障不改變任何數值，只把診斷 copy 排在生產者之後；它同時是這支儀器唯一偏離 「不動 graph／allocator／dispatch 順序」這條原則的地方，所以在原始碼裡明寫出來。

可移植的規則：任何新儀器在跨臂 diff 之前，必須先做「同臂兩跑、互比」的對照。 一個不可重現的讀數不會表現成雜訊——它會表現成一個看起來很確定、而且方向迎合假說的答案。

SAME = [ ffn_moe_down-0, ffn_moe_down-1, ffn_moe_gate-0, ffn_moe_gate-1, ffn_moe_up-0, ffn_moe_up-1 ]
DIFF = layers 2..39（114 個節點）
ffn_moe_gate-0: SAME     ← layer 0 的 router 看的是輸入 token 的 embedding
ffn_moe_down-1.dst: SAME ← layer 1 的 MoE 輸出

4.1 兩個必須一起讀的推論

  • layer 0 的 router ids 相同 ⇒ 兩臂處理的是同一個 token。這排除了「只是 token 流分歧」這個 平凡解釋——否則 layers 2–39 的分歧就不需要任何缺陷來解釋。
  • layer 1 的 ids 與它的 MoE 輸出都相同。而 layer 1 的 MoE 輸出逐位元相同也意味著 layer 1 的 attention 輸出相同（出入不同的 attention 不會產生逐位元相同的 MoE 輸出）。

5. 推翻了什麼、重新定位到哪裡

§9.18.4 被推翻。它的前提是錯的。它推理「輸入相同 + ids 相同 ⇒ layer 1 的 MoE 輸出不同」， 而直接量測說它相同。連帶 §9.18.7 的「要修的是 residency」失去唯一的直接證據， 應降級為「未受支持」（它整條建立在 §9.18.4 上）。

新的定位：分歧出現在 layer 1 的 MoE 輸出之後、layer 2 的 router 之前。 由 4.1 的兩點，候選收斂到：

  1. layer 2 的 attention 路徑（q/k/v 投影、rope、KV 讀取）；
  2. layer 1 → layer 2 之間的 norm／殘差。

而專家池的權重內容不再是候選——至少 layer 1 讀池讀到的東西是對的。

不要過度延伸。這只否證了「載體是 layer 1 的 MoE 權重內容」。它沒有說池在別的層沒問題， 也沒有說 S1 是安全的——只說 §9.18.4 用來指控池的那一步推理不成立。

6. 儀器的已知限制（不假裝沒有）

限制後果
cgc_dst_capture() 只掛在 ggml_metal_op_mul_mat_id 裡 只能擷取 mul_mat_id 節點的輸出（gate／up／down）。要擷取 attention 的輸出， 需要掛在別的 dispatcher 上——那正是 §5 指出的方向，也是下一個 probe 的前提。
固定 CGC_DST_STRIDE=32 words（128 B）輸出張量的一列是 2048 words ⇒ 只看到前 32 個。 「前 32 個相同」不等於「整列相同」；要更寬得改 stride（連帶改 buffer 大小）。
需要 ggml_metal_encoder_memory_barrier這是唯一偏離「純觀察者」的地方（見 §3.1）。
ids 那條仍是 4096 slots 上限跑長一點的 run 會截斷 ids 流 ⇒ 比較器切不出後面的 graph。本次用 --rounds 1 --warmup 0 --n-predict 24（36 graphs）。

8. 誠實邊界

  • 不主張 S1 是安全的。只主張 §9.18.4 的指控（池的內容）沒有證據。
  • 不主張「layer 2 的 attention 就是缺陷所在」——那是候選集合，不是結論。要裁決它得把擷取點 移到 attention 的輸出（見 §6 的第一條限制）。
  • graph 31+ 的 dst DIFF 不能當證據：那裡 ids 也已經 DIFF，輸出不同已被上游解釋。
  • 「同臂對照 SAME」是在這台機器、這份 build、這個 prompt 上量到的。 換 build 或換 run 形狀要重量——對照很便宜（~3 分鐘），沒有理由省。
  • 第 3 節那段「看起來像證實」的輸出保留在紀錄裡（Backup/cgc_logs/ids_dst_capture/ 的無屏障那批），因為它正是這條教訓的證據。不要引用它當結果。
