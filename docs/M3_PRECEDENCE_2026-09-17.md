# M3 剖面前置：M1 落地後「該動哪一格」的判準（2026-09-17）

**里程碑**：M3 — decode 的 compute 削減（W2）· roadmap 標記 **★ 最可能失敗**
**目標**：`100 ms/token → 40 ms/token` 的那個 **2.4×**
**離開條件（原文）**：成功 ⇒ decode（**MTP off**）**≥ 15 t/s** 且 M1/M2 = 100%；
失敗 ⇒ 寫一份「找不到路」的結論，**附上 M0 的剖面表當證據**。
**本文件的角色**：**前置**。它不實作任何東西（`src/` 零改動），它做的是讓 M1 一落地就能動手 ——
把三個工作項各自變成「**剖面必須顯示什麼、用哪個儀器、門檻是多少、什麼會否證它**」。

## 0. 先講清楚一件事：M3 的判準是 **MTP off**

離開條件的字面是「decode（**MTP off**）≥ 15 t/s」。這與「只認 `llama-bench`」的裁定**剛好相容**，
因為 `llama-bench` 對投機是瞎的（`sampler|speculat|draft|MTP` 在它的原始碼零命中）
⇒ 它量到的**天然就是 MTP off 的 decode**。所以 M3 的頭條儀器與裁判儀器可以是同一支，
不必再引入第三套口徑。**M4（MTP）與 M3 分開，不要混談。**

**一條指令**（`src/` 零改動；env 走 `run_server.sh CGC_DUMP_ENV=1`）：


**產物指紋**：`-m …Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf`、`-b 512 -ub 512 -p 0 -n 128 -d 512 -r 3`、
`thermal: launch NOMINAL@16:48:52 worst NOMINAL hist {'NOMINAL': 104} n=104`、
`cache: hit 96.5% misses 4511 reads 27342 us/job 15630 cap% 13.7`。

**t/s（照標準規則報「平台值」）**：`samples_ts = [8.66, 10.59, 10.97]`

```
avg_ts  = 10.07 ± 1.24      ← rep 1 是冷的（8.66），不要把這個當結論
platform = (10.59 + 10.97) / 2 = 10.78 t/s   ← 該引用的那一個
```

**⇒ 平台值 `10.78` 與既有的基準 `10.78 / 10.91`（2026-09-16）逐字吻合。**
這同時是兩件事的驗證：(a) 今天的機器狀態與當時同級；(b) **「丟掉 rep 1」這條規則真的在起作用**
（不丟就是 10.07，差 7%）。**下面的步級數字都是穩態讀數，對應的是平台條件（暖），
所以本文件的換算一律用 `10.78 t/s` ⇒ 92.8 ms/token，不是 10.07 的 99.3 ms。**

### 1.1 步級拆解（穩態，`CGC-DECPROF` step 376／384）

| step | total | **wait** | cb | submit | segs / layers |
|---|---|---|---|---|---|
| 376 | 74.51 ms | **64.07 (86%)** | 7.29 (10%) | 3.15 (4%) | 41 / 40 |
| 384 | 81.79 ms | **71.64 (88%)** | 6.93 (8%) | 3.21 (4%) | 41 / 40 |

### 1.2 GPU 自己的時鐘（`CGC-GPUTIME`，末 20 步中位數）

```
wait=65.7  gpu_busy_sum=101.7  gpu_union=68.0  gap=15.8 ms
gap/wait=24%   busy_sum/union=1.50   union/wait=104%
```

**這四個數各自能說什麼、不能說什麼**（照 `cgc-decode-attribution` 的已校準判準）：

- **`gap = 15.8 ms ＝ wait 的 24%` → 這是唯一乾淨的證據。** 已校準的讀法是
  「`gap` 佔 `wait` 的 20–35% ⇒ 有**可證的閒置**」。今天落在 24%，**與 2026-09-15 的 12–22 ms／17–35% 同帶**。
- **`union/wait = 104%` 不是證據**（陷阱 2：`gpu_union ≈ wait` 是結構性的，
  同一條 queue 上 `[min start, max end]` 本來就橫跨整個佔用窗口）。**不要用佔用率反推病因。**
- **`busy_sum/union = 1.50` 是新的、而且有用**：它說同一個段裡的 `n_cb+1` 顆 buffer **確實在重疊**
  （若 ≈1 才是幾乎序列）。⇒ **`n_cb` 掃描那條路（1→16）本來就沒有東西可掃**，這與歷史結論一致。
- **`gpu_union = 68.0 ms`，而 `gpu_busy_sum = 101.7 ms`。** 對上 **92.8 ms/token**（平台值 10.78）：
  **GPU 的佔用跨度是 73%（`union`）**，但**段內 buffer 有 1.5× 的重疊**（`busy_sum/union`）
  ⇒ **真實的 GPU 忙碌介於 68.0 與 101.7 ms 之間**，不能只挑一個講。
  未被 `union` 覆蓋的 ~24.8 ms 是 `cb+submit`（CPU 側 ≈10 ms）＋ `gap`（15.8 ms）＋ 未歸因的殘差。

### 1.3 逐層歸因（`CGC-DECPROF topN`，50 步 × top8）

- 每個位置的中位 wait：`top1..top5 = 3.23 / 3.24 / 3.19 / 3.15 / 2.25 ms` ⇒ **8 層各約 3 ms**。
- 出現在 top1 的層是**分散的**：`L0 (7 次)、L1 (6)、L20 (5)、L26 (3)、L21 (3)、L2 (3)、L18 (3)…`
  ⇒ **沒有單一熱點層。**
- ⇒ **wait 的形態是「很多層各付一小段」**，而不是「某一層壞了」。這正是「**per-layer 同步**」
  這個工作項的簽名（每層一個段邊界，`segs=41 ≈ layers=40 + 1`）。

## 2. 三個工作項：各自的前置條件、儀器、門檻、否證者

順序＝**本輪依剖面重排後**的建議順序（roadmap 原本的順序來自 r33 修正**之前**的剖面，
而 r33 把 hit 由 57.1% 抬到 72.0%，基準已經移動 ⇒ 必須重排，見 §3）。

### Cell 1 — 消除 per-layer `eval()` 同步

| | |
|---|---|
| **剖面必須先顯示** | `gap / wait ≥ 20%`（**今天 24% ✓**）且 `segs ≈ layers`（**41 / 40 ✓**）⇒ 段邊界是**每層**的，不是偶發 |
| **儀器** | `CGC_GPU_TIMING=1`（`gap` 只有它會印）。**不是** `CGC_DECODE_PROFILE` —— 後者是 CPU 側牆鐘，分不出「GPU 在算」與「在等啟動」 |
| **門檻** | `gap/wait` 由 24% 降到 **≤5%**，**且** 同一個 cell 的 t/s 上升 **≥10%**（兩者要同時成立；單看 t/s 會被熱漂移騙） |
| **否證者** | `gap` 掉到 ≈0 而 t/s **不動** ⇒ 那 15.8 ms 不是關鍵路徑（被其他窗口吸收了）⇒ 這個 cell 的期望值應下修，資源轉 Cell 3 |
| **前置（M1 的哪一部分）** | 無硬依賴；但它與 M1 工作項 2（phase split）**共用同一批 `llama-graph` 節點** ⇒ 兩者一起動可以省一次閘門 |
| **成本／風險** | 中（動 eval 點會影響所有路徑）；**輸出必須逐位元不變**（它不該改數值）⇒ D5 是硬閘門 |

### Cell 2 — MoE gather 的融合

| | |
|---|---|
| **剖面必須先顯示** | **目前做不到**：這條需要「GPU 時間按節點型別拆」的讀數，而**引擎沒有那個儀器**（`segs`／`union` 都只到層級）。⇒ **這一格的判準本身要先做** |
| **要補的儀器** | 兩個候選：**(a)** 對 `ffn_moe_*` 這幾個節點名開 `CGC_TENSOR_CAPTURE`（它在 `mul_mat_id` 上有掛鉤）——但那是**擾動型**儀器（釘張量會改排程器配置，見陷阱 15 的 fail-stop 邊界），**不能當 gate 臂**；**(b)** 在 `CGC-DECPROF` 的層級拆解上加一欄（**這是 `src/` 改動，歸引擎層**） |
| **門檻（一旦有讀數）** | 被融合的節點群佔 `union` 的比例 ≥ 20% ⇒ 值得動；< 10% ⇒ 不值得 |
| **否證者** | 節點層讀數顯示 MoE 只佔 `union` 的一小塊 ⇒ 融合不會動到關鍵路徑（**這一格可能是「沒有 2.4×」的答案所在**） |
| **排序理由** | **排第二，因為它的判準還沒建立**。先動它＝用沒拆開的數字做決策，那正是 roadmap 明令禁止的 |

### Cell 3 — batched-union gather

| | |
|---|---|
| **剖面必須先顯示** | `CGC-PHASE-SPLIT` 今天印的是 `cap=8 routable=142 slots / top_k=8 -> decode graph width=8 tokens (bound=8, T_prefill=512, non-binding)` ⇒ **decode 的圖寬是 8，而池路徑把 `n_batch` 夾在 8**。⇒ 「一次收 union」的**寬度上限就是 8**（`llama-graph.h` 的 `CGC_POOL_MAX_TOKENS`，預設 8、可調 [2,64]） |
| **真正的問題** | 這一格**住在 M1 的世界**：要用 whole-layer slab（`ne[2]=n_expert`，裝得下 256 個）才可能把 union 一次收完。而**只有 `CGC_PREFILL_STREAM` 的臂有 slab** ⇒ 它就是我們統一後的 `prefill250` |
| **儀器** | 同 Cell 1（`gap`＋`segs`）＋ **`segs` 的下降**是這一格的直接指紋（把 T 次 gather 合成一次 ⇒ 段數／步數下降） |
| **門檻** | `segs` 由 41 下降 ≥20%，且 `union` 不上升（不可以用更多 GPU 時間換更少段數） |
| **否證者** | `segs` 降了而 t/s 不動 ⇒ 段邊界不是成本（與 Cell 1 的否證者**互為交叉驗證**） |
| **前置** | **M1 工作項 4（canonical gather order）** ——另一條線已在做（`CGC_CANON_ORDER`），而且它的規格已寫明「置換須對 (貢獻,權重) 成對施加」 |
| **成本／風險** | 高（會改數值 ⇒ 必須走控制臂 ＋ 重新基線，見 skill `cgc-commit-gate` §2.5） |

## 3. 排序的重排理由（為什麼不是照 roadmap 的順序）

roadmap 寫「工作項按 M0 剖面的結果排序，最貴的先動」，而它的順序是
`1. eval() 同步 → 2. MoE gather 融合 → 3. batched-union`。**本輪重排成同樣的順序，但理由換了**：

| roadmap 的理由 | 本輪實測的狀態 | 處置 |
|---|---|---|
| 「pool 143→179 slots 讓 I/O 少 3.7×，decode 只 +9% ⇒ I/O 不是瓶頸」 | 仍然成立，且今天 `hit 96.5%`／`cap% 13.7` 更強化它 | 保留 |
| 「MTP-on：draft head 只佔多出來的 16%，84% 是 verify 拿不到批量紅利」 | **已作廢** —— 那組數字（T=1 92 ms、T=2.6 104 ms）來自 r33 修正**之前**，而修正把路由改了（hit 57.1→72.0%） | 改以 §1 的 MTP-off 剖面為準 |
| 「那筆 run 的 pool hit 87.3%，`pread` 只用 8 條 worker 裡的 1 條 ⇒ 加預取沒用」 | 今天 hit 96.5% ⇒ 預取更沒用 | 保留（否定） |

**⇒ 重排後的前置結論：Cell 1 有可證的目標（gap 15.8 ms）；Cell 3 有明確的前置（M1 工作項 4，已在做）；
Cell 2 連判準都還沒有。所以 M1 一落地的第一件事是 Cell 1，而 Cell 2 的**儀器**可以平行準備。**

## 4. 裁決儀器的白名單／黑名單（這一節是為了防止下一個人用錯儀器）

| 儀器 | 能不能當**裁決** | 理由 |
|---|---|---|
| `CGC_GPU_TIMING=1` | **可以** | GPU 自己的時鐘；`gap` 是唯一乾淨的閒置證據 |
| `CGC_DECODE_PROFILE=1` | **可以（拆解）** | 步級 `wait/cb/submit`；但它是 CPU 側牆鐘，**不能**用它區分「GPU 在算」與「啟動延遲」 |
| `CGC_DECODE_PROFILE_ALL=1` | 可以但貴 | 逐層全印 |
| `CGC_PHASE_TIMING=1` | 可以（相位） | `build/alloc/inputs/compute/fill_wait/gpu` 每 32 步一行 |
| `CGC_SUBMIT_AHEAD=1` | **❌ 不可（只能當上界探針）** | 它**故意錯**（移除窗口但語意錯）⇒ 輸出必然損壞、md5 必須變。它的地位是「**天花板**」，已認證值 **×1.711**（配對中位，區間 1.327–1.924） |
| `CGC_MMV_FUSE=1` | **❌ 不可** | 現配置下**輸出損壞且更慢** |
| `CGC_TENSOR_CAPTURE` / `CGC_S1_OUT_CAP` | **❌ 不可當 gate** | 擾動型（釘張量改排程器配置；全 graph × 40 層 = 載入期就 OOM abort）。只能當**診斷** |
| `llama-bench` | 可以（頭條） | 唯一 instrument of record；天然 MTP off ⇒ 與 M3 的離開條件相容 |

## 5. 混淆項（本剖面已排除的與未排除的）

- **✅ 排除：熱。** `thermal: launch NOMINAL@16:48:52 worst NOMINAL hist {'NOMINAL': 104} n=104 @0.5s`
  —— 全程 104 個樣本都是 NOMINAL。**這個剖面的形狀（wait 86–88%、gap 24%）不是熱造成的。**
  而它的平台值 **10.78** 與 09-16 的 **10.78／10.91** 逐位吻合 ⇒ **今天沒有「順手拿到一個更好的機器」。**
- **✅ 排除：模型檔。** `cmd` 行逐字顯示 `-m …denseIQ4X.gguf`，而且 `-b 512` 的來源是 `[cli]`
  （不是 profile 的 5632，也不是池路徑的 8）。**這一條要特別寫，見下。**
- **★ 新發現（本輪）：既有的兩個歸因臂跑的不是生產模型。**
  `decode_sweep.py` 的 `p25-gputime` 與 `p25-decprof` 兩臂都**顯式帶 `CGC_SERVER_MTP=0`**
  ⇒ 依 lesson `eng-mh-0055`，那會把模型換成 `Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf`（非 Nail）。
  **所以歷史上所有「decode 歸因」的數字都是在非 Nail 檔上量的**，而 M3 的目標是生產配置。
  本輪用 `prefill250:CGC_GPU_TIMING=1;CGC_DECODE_PROFILE=1` 的 `PROFILE:ENV=VAL` 形式避開了這件事
  —— **那個形式是 `llama_bench_matrix.py` 支援的，`decode_sweep.py` 不支援**（它沒有 `--env`）。
- **⚠ 未排除：`wait` 的內部結構。** `wait=65.7 ms` 裡只有 `gap=15.8 ms` 有 GPU 時鐘的證據；
  剩下 ~50 ms 是「GPU 在忙但 CPU 在等」還是「CPU 在忙」，**這份剖面分不出來**。
  要分就得上 `CGC_PHASE_TIMING`（相位）或逐節點 GPU 時間（＝Cell 2 缺的那個儀器）。

## 6. 誠實邊界

- **本文件沒有實作任何東西**，也**沒有跑任何 A/B**。它跑了一次剖面（§1），其餘全部是
  既有儀器與已校準判準的整理。
- **M3 可能真的沒有 2.4×**，roadmap 自己就這樣標（★ 最可能失敗），並且**允許以否定結果結束**。
  本文件的價值在於：**若它失敗，失敗會是可稽核的**（每一格都有判準與否證者），
  而不是「用沒拆開的數字下去做決策」。
- **`gap` 那 15.8 ms 是最明確的、可拿到的量。** 換算：`92.8 ms → 77.0 ms` ⇒ 約 **1.21×**。
  **這遠小於 SUBMIT_AHEAD 認證的 ×1.711 天花板**，因為那條路移除的是**整個 wait 窗口**，
  而 gap 只是其中的空窗。**兩個數字不能互換使用**：1.21× 是「Cell 1 若成功」的下界，
  1.711× 是「所有序列化都消失」的上界，而 2.4× 比上界還大 ⇒ **M3 需要的不只是去序列化。**
- **所有引用都必須附今天的日期與指紋**，因為這個 repo 的基準在 2026-09-17 被 r33 移動過
  （hit 57.1% → 72.0%），任何跨日的 decode 比較都要先確認基準。

## 7. M1 落地後的前三件事

1. **Cell 1**：動 eval 同步之前先量同一個 cell 的 t/s 基準（今天的 10.07 ±1.24 可以直接當基準，
   但要用**同一支 binary** 的重量測補一次，因為 M1 會改 binary）。
2. **Cell 2 的儀器**：沒有它，這一格永遠只能猜。它可以在 M1 進行中平行準備
   （若走 `src/` 路線，那是引擎層的活；若走 `CGC_TENSOR_CAPTURE` 路線，記得它是**診斷**不是 gate）。
3. **Cell 3 的閘門**：它會改數值 ⇒ 先做控制臂、再重新基線（`--write-ref` + 改 `DEFAULT_REF`），
   證據標準是**jsonl md5 相同**，不是「M1 9/9」。
