核心結論：
① 異步模式下，瓶頸是 CPU Metal encoding（~13.6ms，佔 85%），GPU compute 被完全隱藏在後面。
② GPU 內部，實際計算只佔 ~11%，剩下 ~89% 是 ~2000 顆小 kernel 的 dispatch/launch overhead。
③ 同步模式下，GPU dispatch 是最大頭（~38.8ms，佔 66%），但這個模式不用於生產。
④ 要突破 250 t/s，必須同時攻兩個方向：減少 CPU encoding 時間（graph build 緩存、kernel fusion）+ 減少 GPU dispatch overhead（大 kernel、減少 op 數量）。

與 TPOT 報告（decode）對照：Decode 的 dispatch overhead 分解為 CPU MTL encoding 60ms + GPU compute 35ms（重疊）+ EOG sync 4.24ms + dispatch bubble 38ms。Prefill 的結構類似，但 batch 更大，GPU compute 更容易被 CPU encoding 掩蓋。兩者的共同結論：llama.cpp 的 per-op dispatch 模型是結構性瓶頸，不是參數調優能解決的。

優先順序建議：
1. Gather matmul 專用 kernel（中風險、高收益、可獨立驗證）—— 先做這個，因為 FFN 雖然只佔 0.8%，但 mul_mat_id 的 dispatch 模式可能是整個 overhead 的源頭
2. Graph build 緩存（中風險、高收益）—— 重用 dispatch plan，直接攻 90% 的 overhead
3. Metal kernel fusion（高風險、最高收益）—— 最終手段，需要深度改動 ggml-metal
