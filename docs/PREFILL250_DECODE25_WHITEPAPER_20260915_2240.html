一句話結論：S1 的 ids 是逐位元相同的，缺陷在它們指向的東西。 本輪把「S1 過不了 bit-identical 閘門」這個問題，從「不知道哪一半錯了」收斂到單一命題： 池／slot 的內容不一致。做法是把 mul_mat_id 的 Metal kernel 實際解碼出的 ids 寫進 pinned debug buffer、sync 後讀回——這是唯一同時切開 「時序」與「allocator 別名」的讀數，不依賴任何主機端推論。

而閘門自己有三個更嚴重的病，本輪全部修好：

  • 指紋漏檔——建置指紋只雜湊 3 個檔案，而閘門修正所在的 ggml-backend.cpp 編進 libggml-base，不在那 3 檔裡 ⇒ 修前修後兩跑被標成可比。
  • profile 漂移——閘門由「測存在」改成「測值」之後， off / prefill250 / qa-zh / longform-zh 四個 profile 被靜默改道； 只有 prod25 不受影響，因為它是唯一顯式寫死該旋鈕的 profile。
  • 可比性檢查全盲——舊 oracle 的 cap 是在「值不生效」的年代寫的， 它記錄的是意圖不是行為 ⇒ 每一跑都判 INVALID COMPARISON。 本輪修好後閘門回到 PASS。

1. 內核側 ids 讀數（本輪核心儀器）

1.1 為什麼非做這個讀數不可

在此之前有兩個探針，讀同一個欄位，給出相反的答案。差別不在數值，在時刻：

探針在哪裡讀時機它量到什麼
CGC-MMID-ASSERT主機端（encode 期）在 command buffer 執行之前 前一位佔用者的殘留
CGC-IDS-CAP（本輪新增）Metal kernel（消費後）同一 command buffer 之內 kernel 真正解碼出的值

主機探針看到 id_oob=16/16 first=1063585220，而 1063585220 = 0x3F65BD44 是一個 F32 約 0.895 的路由器機率——不是 id。 內核探針對同一層看到 [2,105,7,9,5,106,1,84]，全部落在 [0,143)。 兩者都「對」，因為它們量的是不同時刻的同一個 buffer。

1.2 儀器的設計約束

三個約束決定了實作形狀，值得記下來（換一個專案也會踩）：

  • 不改主 kernel：在消費 kernel 之後、同一 encoder 內追加一個 tiny kernel kernel_cgc_ids_capture，綁同一個 ids buffer。同一 command buffer ⇒ 執行順序天然在後，不需要 fence。
  • 不改 graph：觀察者不得擾動 allocator 佈局。這條是有代價換來的——當天稍早的 p25-buildleaf 就是因為多建一個節點而整個跑不起來。
  • destination 不受 allocator 管理：用 ggml_metal_buffer_init(dev, size, shared=true) ⇒ n_buffers=1、 主機可讀、不經 graph allocator。這同時就是 D3 對 slot_table buffer 的壽命要求（見 §5），已有可運行先例。

2. 閘門的三個真實缺陷（本輪修好）

2.1 建置指紋漏了 libggml-base

build_fingerprint() 只雜湊 llama-server + libggml-metal + libllama 三檔，而閘門修正所在的 ggml-backend.cpp 編進 libggml-base。後果不是「不準」，是反向的： 修前修後兩跑被判定可比，於是「閘門修好」這件事在指紋層面不可見。 修法：glob 所有 libggml* / libllama* + server binary（8 鍵）。 固化為 eng-mh-0007。

2.2 「讓閘門讀值」是一次行為變更，不只是修 bug

舊閘門是 getenv("CGC_OA_ASYNC") != nullptr（測存在），而 run_server.sh 無條件把該變數塞進 SERVER_ENV ⇒ 那個 0 從來沒有生效過，每個 profile 都跑分段。 改成 value-aware 之後，0 第一次真的生效，四個 profile 被靜默改道到 非分段路徑（同一 build 實測 6.95 → 0.72 t/s，約 10×）。

而「錨 digest 不變」不能證明行為不變。 prod25 是唯一顯式把該變數設成 1 的 profile ⇒ 它正是 value-aware 修正不可能移動的那一格 ⇒ 它是最差的證人。 固化為 eng-gate-0006。

2.3 舊 oracle 的 cap 記錄的是「意圖」，不是「行為」

本輪跑閘門得到一個看似矛盾的結果：M1/M2/M3 全 9/9，判決卻是 INVALID COMPARISON。 唯一差異是 ENV.CGC_OA_ASYNC: ref='0' now='1'。

追下去：v2 oracle（ref_iq3_pool8gb_M2_6144_bitident.jsonl）dump 於 17:21，比 21:36 的 value-aware 修正早四小時。也就是說它的 cap 是在 「值不生效」的年代寫的：它記錄的是啟動器的意圖， 不是那次真正跑的分支。

兩問被混為一問。 cap 問「配置相同嗎」；logits 問「數字相同嗎」。它們不一致時，直覺會信 cap，因為 cap 是閘門 自己的機械。但 cap 只跟寫它的那個閘門一樣有行為意義。

判別器：兩條 dispatcher 是實測 10× 的分支、digest 不同 （非分段落在 ff68c5a2，錨是 dc055e63）。 若今天跑的是非分段，就不可能對分段的 v2 量到 9/9 bit-identical。

處置：把 profile 一直是的那一格寫死（prefill250 顯式 pin CGC_SERVER_OA_ASYNC=1），並重錄 ref 讓 cap 記錄行為。 重錄之所以不是「移動球門」，是因為新 dump 與舊 dump 逐位元相同： md5 d2f0b9a01fc5404ebb04dcf3583e133f（v2 與 v3 一致）。

明確拒絕 --allow-incomparable：那是對一個邊界已知的 一次性 stale metadata 問題給永久特赦，會讓未來真正的跨配置回歸以 PASS 的形式到來。 固化為 eng-gate-0008、dec-20260915-2233。

這 9/9 證明了什麼、沒證明什麼：它是 cache-ON 的相對不變量檢查 （兩個 dump 是否一致），不是絕對正確性。M1 的定義就是「兩個 dump 相同」， 所以一個確定性的錯誤在兩側完全相同、依構造不可見。絕對 ground truth 在 16 GB 機器上仍不可得 （cache-free oracle 需要 256 experts × 40 層常駐 → Metal OOM）。

5. D3：把 expert→slot 查表搬到 GPU

目前 remap 是主機每步手寫的 input leaf （llama-graph.cpp:2122-2126），消費點在 :2144。 這正是「每個 segment 邊界必須排空管線」的唯一理由：segment i+1 不得在 hook 寫完 leaf 之前提交。

D3 把它改成 graph 算出來的 slot_lookup(selected_experts, slot_table)， table 由主機維護並發布。圖裡不再有 host 寫入 ⇒ 段邊界失去存在理由， n_segs 由 40 收到 ~1，那 44% 才吃得到。

階段內容閘門
S1table 化、段數不變先過 bit-identical
S3收段（~1 split）吞吐 + bit-identical
S2去掉等待（保留分段）建議作 fallback——段邊界失去理由後，正確動作是「不要分段」

submit-ahead 不是被廢棄的方案——它一天都不曾是方案。 CGC_SUBMIT_AHEAD=1 是故意錯的 ceiling probe（在 segment i 的 top-k hook 寫 remap leaf 之前提交 segment i+1），它只是量具。D3 之下它的角色由「S2 天花板」 變成「段邊界的總價值 = S3 天花板」，其數字成為 D3 的驗收參考。 D3 明確優於它：D3 沒有 race。

唯一的前提風險：slot_lookup 的 table 仍是主機寫的 （publish_slot_table）。所以「圖裡不再有 host 寫入」成立的條件是 publish_slot_table 不在熱路徑。這是待測且最便宜的一項。 注意 CGC-SLOT-TABLE 的 clamp 計數全天 0 行不能回答這個問題 （它只在 clamp 觸發時計數）。

數字陷阱：CGC_OA_ASYNC=0 的 0.72 t/s 不能推論 「D3 收段會慢 ~20×」——那是 40 splits + 序列化調度；D3 是 ~1 split。 CGC_OA_ASYNC 動的是調度策略，D3 動的是 split 數。

6. 誠實的邊界

  • S1 的 bit-identical 閘門仍未通過。命題已收斂為「ids 正確，缺陷在池／slot 內容」， 但尚未證明。下一個唯一決定性的測量是 capture ffn_moe_down-1 的輸出 （兩臂、graph 3）：若輸入與 ids 相同而輸出不同，池內容就被證明是載體。
  • 本輪的 llama-bench 未做交錯 A/B（見 §3），所以 §3 的差異不構成 regression 主張。
  • publish_slot_table 的呼叫次數尚未測——它決定 S2 是否存在， 必須排在任何 S1 實作之前。
  • 內核儀器的 stride 限制：n_ids=64 時只看得到 token 0。
  • S1 的臨時診斷（CGC_S1_DBG 等）保留為 opt-in，尚未清理。
  • 本輪沒有動 E1（git mv 進 tb_loop/）與 E2/E3/E4 的任何檔案。
