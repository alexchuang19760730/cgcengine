## 1. 背景與目標

### 1.1 問題
當前 L4 Expert Cache 架構：
- expert tensor 被縮小（ne[2] 從 256 → n_slots，如 143）
- 用 `--no-mmap` 加載，expert 數據通過 pread 複製到縮小後的 Metal buffer
- 8GB Metal pool 全量常駐，16GB 機器上 free 僅 14%
- 記憶體懸崖導成品質崩壞

### 1.2 目標（白皮書 P1 驗證標準）
- 峰值記憶體 ≤5GB（短 ctx 1.5-2GB，中 ctx 2.5-3.5GB）
- 48 題與 P0 同分（無損，byte-identical）
- decode ≥8 tok/s
- 不訓練、不改變數學（BigMoeOnEdge 風格的工程層改造）

### 1.3 核心洞察（白皮書 §4）
Apple Silicon 統一記憶體 zero-copy：
- llama.cpp Metal backend 已用 `newBufferWithBytesNoCopy` + `MTLResourceStorageModeShared`
- `ggml_metal_buffer_map()`（ggml-metal-device.m:1698）支援把外部指針（含 mmap）包成 Metal buffer
- 當前用 `--no-mmap` + 8GB pool 反而放棄了這個免費機制
- **改造 = 把 expert 權重放回 mmap + noCopy Metal buffer + 有界 LRU**

## 2. 當前架構分析

### 2.1 L4 全量常駐流程
```
compute_l4_pool_capacity() → n_slots = budget/(layers*per_slot)
create_tensor() → expert tensor ne[2] 從 256 縮小到 n_slots
--no-mmap 加載 → pread 讀 expert 數據到縮小後的 Metal buffer
adopt_pool_region() → Metal buffer 指針交給 expert cache
prepopulate() → 標記前 n_slots 個 expert 為 resident
ffn_moe_topk_remap → expert id 映射到 slot index
Metal FFN → 從 pool buffer 讀取對應 slot
```

### 2.2 關鍵文件
- `src/llama.cpp/src/llama-model-loader.cpp`：expert tensor 縮小 + 加載
- `src/llama.cpp/src/llama-expert-cache.cpp/h`：L2/L3/L4 cache 管理
- `src/llama.cpp/ggml/src/ggml-metal/ggml-metal-device.m`：Metal noCopy buffer（ggml_metal_buffer_map）
- `src/llama.cpp/src/llama.cpp`：adopt_pool_region 調用點（第418行）

## 3. P1 目標架構：mmap-native streaming

### 3.1 核心思路
expert tensor 不縮小（保持 ne[2]=256），走 mmap 路徑，Metal noCopy 直接讀。Expert Cache 只負責「頁面預取 + LRU 釋放」，不做數據複製。

### 3.2 目標流程
```
LLAMA_EXPERT_CACHE_MMAP_STREAM=1
  → 不縮小 expert tensor（ne[2]=256）
  → 不設置 expert_cache_pool_capacity
  → mmap 加載，expert tensor data 直接指向 mmap 區域
  → Metal backend 用 ggml_metal_buffer_map 包成 noCopy buffer
  → Expert Cache 進入 mmap_stream 模式：
      - 不創建 pool，不做 pread
      - expert_cache_on_topk hook → madvise(MADV_WILLNEED) 預取
      - 後台 LRU 線程 → madvise(MADV_FREE) 釋放冷頁面
      - slot_table = identity（expert id = slot index）
  → ffn_moe_topk_remap = identity
  → Metal FFN 直接從完整 expert tensor 讀取
```

### 3.3 記憶體模型
| 組件 | 當前（L4 全量常駐） | P1（mmap streaming） |
|------|---------------------|---------------------|
| Expert 權重 | 8GB Metal pool 全量常駐 | mmap 映射，OS page cache 管理（~1-2GB 熱頁） |
| Dense 權重 | ~3GB（mlock） | ~3GB（mlock，不變） |
| KV cache | 8GB | 2-4GB（可調） |
| 峰值總計 | ~13-14GB | ~5-7GB（短 ctx 可到 3-4GB） |

## 4. 具體改造點

### 4.1 Loader 改造（llama-model-loader.cpp）

**新增環境變量**：`LLAMA_EXPERT_CACHE_MMAP_STREAM=1`

**改造點**：
1. `compute_l4_pool_capacity()`：當 MMAP_STREAM 啟用時，直接 return（不設置 expert_cache_pool_capacity）
2. `create_tensor()`：當 MMAP_STREAM 啟用時，不縮小 expert tensor（跳過 ne[2] shrink）
3. `init_mappings()`：dense 部分 mlock，expert 部分不 mlock
4. 新增 `expert_cache_mmap_stream` 標誌位

**偽代碼**：
```cpp
// llama-model-loader.h
bool expert_cache_mmap_stream = false; // 新增

// compute_l4_pool_capacity()
if (getenv("LLAMA_EXPERT_CACHE_MMAP_STREAM")) {
    expert_cache_mmap_stream = true;
    return; // 不計算 pool capacity，不縮小 tensor
}

// create_tensor() 中的 shrink 邏輯
if (expert_cache_pool_capacity > 0 && !expert_cache_mmap_stream) {
    // 原有 shrink 邏輯
}
```

### 4.2 Expert Cache 改造（llama-expert-cache.cpp/h）

**新增 mmap_stream 模式**：
1. 新增 `bool mmap_stream = false` 字段
2. `llama_expert_cache_init()`：當 MMAP_STREAM 啟用時，pool_active = false，不創建 pool
3. 新增 `llama_expert_cache_madvise_willneed()`：對選中的 expert 做預取
4. 新增 `llama_expert_cache_madvise_free()`：對冷 expert 做釋放
5. `expert_cache_on_topk` hook：mmap_stream 模式下調用 madvise_willneed
6. 後台 LRU 線程：定期調用 madvise_free

**關鍵：slot_table = identity**
- mmap_stream 模式下，slot_table[layer * n_expert + expert] = expert（恆等映射）
- 不需要 pread，不需要 ensure_slot
- Metal FFN 直接用 expert id 索引完整 tensor

### 4.3 FFN remap 改造（llama-context.cpp）

**mmap_stream 模式下**：
- `ffn_moe_topk_remap` 改為 identity（直接寫 expert id）
- 或者跳過 remap，Metal kernel 直接用 expert id

### 4.4 啟動參數

| 參數 | 說明 | 預設 |
|------|------|------|
| `--moe-stream` | 啟用 mmap 流式模式（設置 LLAMA_EXPERT_CACHE_MMAP_STREAM=1） | OFF |
| `--cache-mb N` | 常駐 expert 頁面上限（MB） | 1024 |
| `--release-mmap` | 加載完成後釋放非必要 mmap 映射 | OFF |

## 7. 風險與緩解

| 風險 | 影響 | 緩解 |
|------|------|------|
| Metal noCopy buffer 對 mmap 頁的支援 | 高 | 已確認 ggml_metal_buffer_map 支援；先小模型驗證 |
| madvise 在 macOS 上行為 | 中 | macOS 支援 MADV_FREE（10.14+）；先用 mincore 驗證頁面常駐 |
| expert tensor 不縮小後 Metal buffer 過大 | 中 | noCopy buffer 不佔用 GPU 內存，只有被訪問的頁面才常駐物理內存 |
| FFN remap identity 後 Metal kernel 行為 | 中 | 逐步驗證：先關 MTP，再開 MTP |
| OS page cache 與進程爭奪內存 | 中 | 用 --cache-mb 限制常駐上限；madvise(FREE) 主動釋放 |

## 8. 關鍵技術細節

### 8.1 Metal noCopy buffer 機制
- `ggml_metal_buffer_map(dev, ptr, size, max_tensor_size)`（ggml-metal-device.m:1698）
- 使用 `newBufferWithBytesNoCopy:ptr length:size options:MTLResourceStorageModeShared deallocator:nil`
- `res->owned = false`（不擁有內存，由 mmap 管理）
- 超過 max_buffer_size 時自動分片

### 8.2 mmap 加載路徑
- `init_mappings()`：對每個文件創建 llama_mmap
- `load_all_data()` 中：`data = mapping->addr() + weight->offs`
- `ggml_backend_tensor_alloc(buf_mmap, cur, data)`：把 mmap 指針分配給 tensor
- Metal backend 最終調用 ggml_metal_buffer_map

### 8.3 madvise 頁面控制
- `madvise(addr, len, MADV_WILLNEED)`：預取頁面（非阻塞，內核後台讀取）
- `madvise(addr, len, MADV_FREE)`：釋放頁面（macOS 10.14+，頁面可被回收）
- `mincore(addr, len, vec)`：查詢頁面是否常駐（用於 LRU 統計）
