8. 算術：駐留這一半最多值多少

F1 的擬合（r² = 0.862）：cb_layer = 0.46 ms + 0.695 ms × m。交付暖態 cb = 21.23 ms/step、L = 29：

barrier  = 29 × 0.46 = 13.34 ms
per-miss = 21.23 - 13.34 = 7.89 ms      ⇒ m ≈ 11.4 misses/step
capacity 佔 miss 的 26.0%  ⇒ 0.26 × 7.89 = 2.05 ms/step = 139.46 ms 的 1.5%
就算 capacity 佔到 50%      ⇒ 3.9 ms = 2.8%

而 first-touch（74.0%）不可能拿掉 —— 池子再大也得為第一次被選中的專家付一次讀取。 ⇒ 駐留這一半的全部價值 ≈ 1.5–2.8%，低於單臂噪音底（±27%）， 所以它的 t/s 效應在單臂前後對比下測不出來；只能像本文件這樣從機制 （capacity=、evictions=）去證明。

9. ★★ drain：為什麼不可能只靠主機側完成

S1 之後，index vector 由裝置產生（selected_experts 的 CONT， llama-graph.cpp:2290-2345），所以主機不再需要為 gather 寫東西。 但 dispatch 迴圈（ggml-backend.cpp:2612-2630）仍然是：

for i in 0..n_segs-1:
    hook_seg(i)                  # 先等 segment i 跑完（:2119 的 sched_yield 輪詢），再跑 top-k hook
    if i+1 < n_segs: submit_seg(i+1)

hook_seg(i) 做三件事，全部依賴 segment i 的輸出： ① 讀出該層的 expert ids；② 用 ids 跑 ensure_batch 把不在池裡的專家填進去 （這就是 miss 成本）；③ 把結果寫進 slot_table[layer]。

而 segment i+1 恰好從該層的 mul_mat_id 那一段開始： seg_view(s) 的邊界是 a = as_idx[s-1]+1、b = as_idx[s] （ggml-backend.cpp:2057-2060）⇒ 邊界節點 as_idx[i] 是 segment i 的最後一個節點，而它的下一個（as_idx[i]+1）就是 segment i+1 的起點； 該層的 mul_mat_id 就在其中，透過 get_rows(slot_table, …) 讀這張表 ⇒ 第 ③ 步的產物是 segment i+1 的直接輸入 ⇒ 它的 commit 必須在 hook 之後。 CGC_SUBMIT_AHEAD=1（把那兩行對調）刪掉的正是這個順序， 所以它必然錯；它量到的 ×1.78 只是這個家族的上界。

繞法為什麼不行
表延後一步發布「第一次被選中」的專家在延後的表裡沒有槽 ⇒ zero-map ⇒ G2.zero_mapping_invariant 否決（本 run 實測 zero_mapped_selected=0）
表雙緩衝 ＋ 世代選擇器世代必須在 encode 時確定，而世代由 hook 決定 ⇒ 同一個雞生蛋
讓「這一步不會改表」在主機側可證唯一可行方向，但條件是 cap == 256 且 256 個專家全部常駐 ⇒ 41 × 256 × ~1.13 MB ≈ 11.9 GB，16 GB 放不下（模型本身還要 ~10 GB）

⇒ 只要「本步的映射依賴本步的 ids」成立，drain 就是必要的。拿掉它只有兩條路： (i) 把駐留判定搬上裝置（裝置側表 ＋ 一個「有沒有被選中的專家不在池裡」的裝置側判定 ＋ 在那條時間線上排隊的填寫）—— 這是 kernel 工程，不是配置或幾行程式； (ii) 打破「映射依賴本步 ids」（= 接受錯誤），已被 G2 否決。

10. 誠實邊界

  1. §3 的 distinct 是 512 token 的讀數；更長的 run 會更大（另一批長 run 的 worst=layer 0/1/2 distinct=242–255 就是這個方向）⇒ 「4 層」是下界估計， 而那些長 run 是 MTP=0（沒有 40-40:256、且有 draft 路徑）， 兩個 regime 不可直接比。
  2. §8 的 cb 拆解用的是 09-19 的 F1 擬合，不是本 run 重測的。 它與本 run 的總量自洽（0.46×29 + 0.695×11.4 = 21.3 vs 記錄的 21.23）， 但沒有在同一 run 內同時量過。
  3. 本輪沒有跑 t/s 對比：+0.48 GiB 的配置改動換 1.5% 的效應，而交付 cell 的單臂噪音 ±27% ⇒ 那個對比在設計上就不可能給出答案，不做比做一個誤導性的數字好。
  4. caps 的 bit-identity「未被驗證」（§6）：處理臂死在 OOM 上、沒有 M1/M2/M3。 對照臂（不含 caps）在同一棵樹上 PASS ⇒ 基準仍有效，而失敗方向是單向的。
  5. §7 的歸因是「2/3 可重現 ＋ 對照臂通過」，不是「3/3 必然」—— ..._141049 那次帶 caps 跑通，所以嚴格說法是「使…很可能發生」。
