# 在水位受控條件下重讀 `cb` —— 負結果（2026-09-20）

## 要回答的問題

> 「下一個真正值得做的是在水位受控的條件下重讀 `cb`（把 `usable%`／swap 當強制進入條件，像
> `--min-headroom-mb` 那樣），否則 victim rule 的優先級排序建立在一個會漂移 6 倍的数上。」

工具：`scripts/check/cb_headroom_probe.py`（本輪新增，自檢 15/15）。
它把「水位」當**強制進入條件**（不在帶內就等，等到超時就 abort），並同時記錄
進入水位、`run` 期間的水位軌跡、以及 `cb` 的**分段統計**（all / first_half / last_half / thirds）。

**結論：這個條件建不出來，而且就算記錄了水位，它也不是 `cb` 的主導變數。三條獨立的否證。**

---

## 否證 1：壓力帶**進不去** —— 壓力態是 run 自己造出來的

```
$ ... --carrier joint --max-usable-pct 15 --max-free-pct 25 --band-timeout 60
REFUSED: band not enterable in 60.0s: usable_pct 52.85 > 15 ; free_pct 81 > 25
```

壓力態只存在於**一支 run 正在跑的時候**（`traj` 裡 `usable_pct` 中位 5.9–6.4、`swap` 中位
4789–5708 MiB），而 run 一結束，盒子在 **~2 分鐘內自己回到 `usable 56–64%` / `free 72–82%`**。
⇒ 「進入壓力帶」在物理上不可行：你沒辦法在 run 開始前站在那個狀態裡，因為那個狀態是 run 的產物。

## 否證 2：水位**讀數本身**不穩 —— 拿它當閘門會不可重複

空盒子（無 llama 行程）上連續採樣：

```
free 5.62 GiB  →  0.06 GiB   （30 s 內）
```

同一條命令會時而通過時而 abort，取決於你在 30 秒窗口的哪個瞬間敲下去。
一個閘門如果對「何時敲」敏感，它就不是受控條件。

## 否證 3：水位**更好**的那次，`cb` **更高**（直接反例）

同載體 `prod25`、連發三次（`--runs 3`），run 2 的進入水位在**每一個軸上都比 run 1 好**：

| 進入水位 | b2b_r1 | b2b_r2 | 方向 |
|---|---|---|---|
| `usable_pct` | 51.02 | **63.77** | r2 較好 |
| `free_gib` | 4.18 | **9.04** | r2 較好 |
| `headroom_mb` | 8360 | **10447** | r2 較好 |
| `cached_gib` | 2.37 | 0.95 | r2 較差 |
| **→ `cb`** | 23.89 ms | **33.87 ms** | **r2 差 +42%** |
| **→ 步時 total** | 139.15 ms | **238.31 ms** | **r2 差 +71%** |

「低水位把 `cb` 抬上去」的單調故事被這一支直接駁倒。唯一同向的是 `cached_gib`（頁快取被前一
支 run 擠掉 ⇒ `pread` 得真的打到 NVMe），但它是**與 run 順序共線**的，無法與 run 序號分離。

## 五次讀數的全表（`cb_ms` 皆為同一函式、同一過濾口徑）

| tag | carrier | 進入 cached | 進入 usable% | 進入 swap | cb all | cb 前半 | cb 後半 | 步時 |
|---|---|---|---|---|---|---|---|---|
| cold1 | joint | 2.93 | 52.5 | 3267 | 17.01 | 23.35 | 12.82 | 130.00 |
| prod25_cold | prod25 | 2.08 | 50.6 | 3442 | 25.60 | 34.92 | 19.84 | 142.05 |
| b2b_r1 | prod25 | 2.37 | 51.0 | 3857 | 23.89 | 34.03 | 19.43 | 139.15 |
| b2b_r2 | prod25 | 0.95 | 63.8 | 5061 | 33.87 | 48.72 | 27.10 | 238.31 |
| b2b_r3 | prod25 | 0.88 | 59.7 | 5190 | 28.34 | 38.14 | 23.43 | 160.00 |

**同載體（prod25, n=4）的相關係數——全部未達顯著（n=4 的 |r| 臨界：p=.05 → 0.950）**

```
r(cb, usable%  ) = +0.940     ← 符號與「壓力抬 cb」相反
r(cb, headroom ) = +0.939     ← 同上
r(cb, cached   ) = -0.836     ← 符號合理（頁快取少 → cb 高），但與 run 序號共線
r(cb, swap     ) = +0.761
```

四個軸的 `|r|` 全在 0.76–0.94，**沒有一個過 0.950**。而且 `usable%`／`headroom` 的符號是正的
（記憶體越寬鬆 `cb` 越高）——與原假設相反。這組資料**沒有能力**指認任何一個進入水位變數。
（這正是 `.workbuddy/memory/MEMORY.md` 量測衛生節記過的陷阱：n=4 的後設相關要嘛過不了臨界、
要嘛是順序的代理。）

## 那真正跟 `cb` 動的是什麼：**run 內位置**

五次 run **全部**單調衰減，倍率 1.63–1.82×：

```
cold1        23.35 → 12.82 (1.82x)     cold1       cb_max 413.9 → 38.2 ms
prod25_cold  34.92 → 19.84 (1.76x)     prod25_cold cb_max 4043.8 → 197.2 ms
b2b_r1       34.03 → 19.43 (1.75x)
b2b_r2       48.72 → 27.10 (1.80x)
b2b_r3       38.14 → 23.43 (1.63x)
```

`cb` 的**單臂離散是 1.42×（23.89–33.87）**，而**單支 run 內部的衰減是 1.63–1.82×**。
⇒ 最大的單一成分不是水位、不是載體，是**池在 run 內被填熱**（`cb_max` 從 4 s 掉到 0.2 s
就是冷填充的那幾步）。這解釋了為什麼「74.18 vs 11.26」這種 6.6 倍的差距裡，有相當一部分
其實是**取樣落在 run 的哪一段**，而不是盒子的水位。

## 判定與建議

1. **不要把 `usable%`／swap 做成強制進入條件。** 它進不去（否證 1）、讀數不穩（否證 2）、
   而且方向被反例駁倒（否證 3）。工具保留 `--min-*`/`--max-*` 但定位改為**記錄與篩選**，
   不是閘門。
2. **要重讀 `cb`，受控的是「載體 + run 內位置」。** 固定丟棄前半（或明確並列前／後半兩個數），
   並且**只在同載體下互比**。本輪起 `cb_headroom_probe.py` 一次同時給 all/first_half/last_half/
   thirds，就是為了讓「誰引用了哪一段」變成顯式口徑。
3. **victim rule 的優先級不要建立在 `cb` 絕對值上。** 應該建立在**同載體配對的 Δcb**
   （`paired_ab.py` 那套 AB/BA）。線 I 的 74.18 與本線的 11–34 若要對帳，
   要對的是**載體（`profile`/`--batch`/`--ctx-size`/MTP）+ run 內位置 + 頁快取狀態**，
   不是水位。
4. **順帶（未證實，n=1）**：`b2b_r2` 的步時 238 ms 是同載體下 139 ms 的 **1.71×**，
   而它是進入 `cached` 最低（0.95 GiB）的那次。「GGUF 頁快取被擠掉 ⇒ 專家權重真的走 NVMe ⇒
   步時暴漲」是一個機制上說得通的假說，值得用 `--min-cached-gib` 做**配對**（不是單臂）去試，
   但目前只有一個樣本，不能引用。

## 可引用 / 不可引用

- **可引用**：三條否證、五次讀數的表、`cb` 前半→後半 1.63–1.82× 的衰減、相關係數未過臨界。
- **不可引用**：任何「水位 → cb」的因果或單調關係；`b2b_r2` 步時 238 ms 當作水位效應。
- ⚠ 全部走 HTTP 路徑（非交付口徑）⇒ 只引用**比值與閉合關係**，不引用絕對步時。
