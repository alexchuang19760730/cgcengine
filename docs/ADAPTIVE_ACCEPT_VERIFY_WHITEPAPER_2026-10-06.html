1. 為什麼是「形狀」：k_eff 這條軸為什麼先死

投機解碼有兩個性質不同的旋鈕：走多深（draft 鏈的長度 k）與走多寬（一輪驗幾條候選列）。 本線原本壓在 k 上，但 k 在「有 alt-seed」的配置裡被引擎自己擋住——而且理由不是原先以為的 M-RoPE 牆。

1.2 那顆多餘的 token 從哪來：seq 1 在同一步被加兩顆

1.3 BRESET：殘留假說已死（為什麼它不在這顆 commit）

bench 側還試過一條便宜的假說：當 B 被關著（W_eff == 1）時，seq 1 的 cell 一個都不收， 它停在最後一次 B-on 的位置，B 再開時可能落在殘留之後。處置碼就是 BRESET（預設關）。 A/B 判詞（跑前註冊）是 FAIL：把 seq 1 補刪之後，oracle 逐輪 281 行、ACCEPT 5 行、 SPEC-TREE 10 行三條頻道逐位元相同；而「B 恆開」的否證控制如設計一字不動。 ⇒ B-on 段接受量的落差不是 seq-1 draft cell 殘留造成的，殘留無法解釋它。

誠實邊界：逐位元相同允許兩種讀法（(a) 那些位置本來就沒殘留；(b) 有殘留但不在遮罩作用範圍）， 兩者都讓殘留無法解釋落差，所以否證成立；但「BRESET 真的刪掉了 cell」這件事沒有正控 （llama_memory_seq_rm 的回傳值沒被記）。因此 BRESET 程式碼留在工作樹、不進這顆 commit。

2. 方法：把驗證形狀變成可決策的變數

2.1 參數化：狀態用「尾長 d」，不是列數

一輪的驗證列數是 rows = W_eff × (1 + d)。控制器把狀態記成 尾長 d 而不是列數， 因為 W_eff 會逐輪變（B 開／關），列數不是形狀唯一不變的自變數；d 才是。 列數則由 d 與當輪的 W_eff 推得。

  • 起手 d = 1，不是 0：d = 0 的尾巴是空的、m 恆為 0，量不到接受率 ⇒ 控制器沒有方向。
  • 靜態旋鈕 CGC_SPEC_TREE_ROWS=<n> 走另一條式子（d 由需要的列數反推）， 讓「靜態」與「自適應」共用同一套見證。
  • 解耦 CGC_SPEC_TREE_ALTBIND：把「alt draft 綁進 tree batch」與「alt 分支探索」 拆成兩個旗標（.alt 與 .alt_branch）。沒有這個解耦，k_full 在有 alt-seed 的輪 斷在第二步（§1.2），自適應根本換不動形狀——形狀的量測會被引擎的拒絕蓋掉。

2.2 觀測量：本輪「實際」接受了什麼

  • m：本輪真的被接受的 draft 數。root不計——它每輪都會被接受，是常數。
  • tail_len[win_br]：勝出分支實際進 verify 的尾長，不是目標列數。 用實際尾長做分母，被 draft 深度或 cap 砍過的輪才不會讓接受率失真。
  • rows_actual：實際列數，同樣不是目標列數（被 cap 過的輪不該被記成便宜）。

2.3 兩把尺：rate 與 net

目標式子回答的問題
rate（_OBJ=rate，預設） rate_t = m / tail_len[win_br]，與 _THR 比 「最近接受率夠高嗎」
net（_OBJ=net） payoff_t = m；cost_t = rows_actual × COST/100；net_t = payoff − cost 「這一輪多送的列值不值得」

接受率高不等於划算：列數是逐輪都要付的成本，而門檻版的回饋迴路只看比率， 看不到「多送的列值不值得」。這是換目標的動機。_COST 的單位是 百分之一 token／列（100 ＝ 每列 1.0 個被接受 token 的成本）。

2.4 探索—利用政策（兩版共用，差別只在目標）

rate：mean = 最近 _WIN 輪 rate 的算術平均（不是 EWMA）
      mean > thr ⇒ d+1 ；mean < thr ⇒ d−1 ；相等不動      （邊界夾在 [1, dmax]）

net ：每 dmax 輪插一輪「探測」（round-robin 走過每個 d）
      其餘輪「利用」：d = argmax_d mean(net)，同分取較小的 d

探測為什麼要穿插、而不是全排在最前面：這個 cell 的頭幾輪 MTP 接受率還沒起來（實測 m 連續為 0）， 把探測全塞在暖機段會讓每個 d 都量到 0 分 ⇒ argmax 退化成「列數最少的那個」—— 探測自己把答案汙染掉。

2.5 前置條件：「臂的責任」，本格不代打

控制器只能從它量到的東西學習。若臂沒有把條件擺好——draft 深度 ≥ dmax、 CGC_SPEC_TREE_RS ≥ K、DRAFT_N_MAX 足夠——量到的就是被 cap 過的形狀， 此時控制器是「決策動、形狀跟不上」。這個失敗形狀看得見：rows_unmet > 0 （目標列數沒被滿足的輪數）與直方圖會一起露出來，見 §4 的 _nk 格。

3.3 三條紀律

  1. 負控制先跑：控制器關／靜態列數的格必須顯示 rows_kinds=1、rows_switch=0。 沒有負控制，「自適應看起來在動」可能只是雜訊。
  2. 判準跑前註冊：每一格的預期寫進 harness 的 docstring，事後對不上要如實記為錯 （§7 有一條錯的，且它是本方法最重要的限制之一）。
  3. 位元不變的 A/B：改動前後各建一次 binary，跑預設路徑與 rate 路徑， 四條見證頻道（ACCEPT／SPEC-TREE／ORACLE／SPEC-DUMP）剝掉新增尾端欄位後必須逐字元相同。 這條保證「新旋鈕沒有偷偷改變舊行為」。

本節最有價值的一個數：交叉點。 net(d) = mean_m(d) − c × 2(1+d) 的交叉點約在 c ≈ 0.11–0.14（COST ≈ 11–14）： 列的成本只要高於約 0.12 個被接受的 token，最淺的形狀就贏。這解釋了 COST=100 的 net_pick=1，也說明了「6 列的預設形狀」在這個目標下不是最優—— 已測的 COST（0／20／40／100）都選 4 列或 8 列，中間的 6 列從未成為 argmax。 （更細的 COST 掃描沒跑；煙霧 cell 上的交叉點另有不同值。）

7. 判詞，與那個錯的預測

我的預測錯了一格，而這個錯是本方法的核心限制。 我註冊「COST=20 ⇒ d=2」，實測是 d=3。原因是：我的預測用了門檻版軌跡在 d3 上的均值 （約 1.6），而 net 版在同一個 d 上量到 2.333。 也就是說：一個形狀的「收益」估計不是政策無關的——誰去拜訪它、帶著什麼 carryover 去拜訪， 會改變它被接受的長度。這是一個真實的混淆，不是算錯。
判內容
機制 PASS 控制器可掃、可讀（見證欄位說得出每一輪用了幾列）、逐輪跟訊號走（門檻 20／40／70 給出三條不同軌跡、方向性對）、且不退化成靜態（kinds=3、switch>0，端到端亦然）。
目標函數可替換 PASS 同一個開關換目標，得到不同的、可解釋的形狀軌跡（深 vs 淺），且離線重算與見證一致（4/4）。
未轉正 MTP-on 未達 t/s 目標；且本線不引用任何小數 t/s 讀數（噪音底 15–43% ≫ 門檻 9%）。「機制動了」不等於「指標動了」。
已知混淆 (1) 形狀收益非政策無關（上面那格）；(2) 探索是貪婪的（見 §8）；(3) k 的上界仍被引擎的 seq-1 雙加壓著（§1.2 未套用修補）⇒ 本方法的上限還沒被量到。

8. 讀數陷阱（會咬人的四條）

  1. rows_switch 在 net 版不能當「非退化」的證據：探測是每 dmax 輪強制的， 所以 switch 數大部分來自探測（rows_adapt_net 的 28 次裡約 21 次）。 要看的是利用輪的分布：exploit 的 pick 在非探測輪始終是 1，且直方圖 4:50/64。 判準必須跟著目標換——門檻版能用的證據，net 版不能用。
  2. net_tab 是「最後一個 rep」的窗，不是整臂：要整臂的原料必須把 CGC-ROWS-ROUND 併起來（§6.1 的表就是這樣做的）。
  3. 貪婪凍結：沒被選中的 d 只在探測輪更新樣本，兩次探測之間的估計是凍結的。 這是教科書級的 explore／exploit 弱點，本輪沒有處理（_WIN 只保證被拜訪的 d 有新鮮樣本）。
  4. 單一 rep 的 emit_per_round 不可引用（噪音底 15–43%）；§6 只用它做形狀的旁證， 不拿它做判詞。

10.3 檢查 11（replay benchmark）為什麼從來不可能 pass，以及怎麼修好的

2026-10-06 第一次在空的 GPU 上把檢查 11 真的跑完（--mtp --dense-iq4x、10 GiB expert pool、 --all-profiles --runs 3 --seed 0）。verdict 是 FAIL， reason = quality regression (hard gate): 1 profile(s) degraded。逐項拆開後， 兩個成因都與被測 commit 無關：

  • 成因一（ruler 與輪詢不一致 ⇒ 恆 FAIL）：--runs 3 會依序輪詢 profile 的 3 個 prompt （2026-09-08 4715610df 加入），但 qa-zh 的 required_any 只列 [巴黎, 法國]。「太陽系有幾個行星」與「15 + 27」兩題的正確答案永遠不含這兩個詞， 於是 3 次分數固定為 [1.0, 0.765, 0.765]、median 0.765， quality 硬閘門（絕對差 0.1）對任何 commit 都 FAIL —— 包括一個空 commit。 修法：把這兩題的答案鍵（行星名／八顆／42／四十二）併進 required_any，並在 _doc 寫下「required_any 必須覆蓋該 profile 會被輪詢到的每一個 prompt」。 修後 qa-zh 為 [1.0, 1.0, 1.0]。
  • 成因二（baseline 早於既定決定 ⇒ 記憶體恆退化）：舊 baseline 記的是 commit=WORKTREE（2026-09-06），早於 expert pool 的兩次故意放大 （4→8 GiB 於 2026-09-06、8→10 GiB 於 2026-09-13）。同一個 server 在這兩代之間 RSS 差約 4.3 GB， 三個 profile 一律越過 25% 門檻。這不是退化，是舊 baseline 不知道預算已經被改過。

處置：修 ruler，並在 dbe5f8eb1 重新量測 baseline（去掉 _stale， 同時解除 agent_harness/shared/stale_registry.json 的 stale 登記與 .gitignore 的對應註解）。 驗證方式是用同一 session 狀態下的兩次獨立量測互比： verdict PASS、improvements=2 regressions=0 neutral=10、離開碼 0。

仍未解的限制：這台 16 GB 機器跑滿載時會把 swap 用到見底（實測 13.7/14.3 GB）， 速度因此隨「開跑多久」漂移 —— 兩次連續量測的 qa-zh decode 曾差到 2.1 倍，而現行的 unstable 規則（run 內 CV > 30%）抓不到這種跨 session 漂移。 baseline 取兩次之中較慢的那次，以免未來的 run 誤觸；但「同一 commit 兩次量測可以差 2 倍」 本身仍是這個閘門沒解決的問題。另：扁平 required_any 對「回顯題目」仍可能誤判為通過， 逐題防回顯的那把尺是 scripts/check/bare_48.py 的 strict 尺。

11. 交叉補充（線A）：Fix A 的否證，與病灶收窄到 seq-1

11.1 被否證的假說：「draft 只寫了 1 個位置槽」

先前 scoping（Backup/spec_tree/rs3_mrope_draft_pos_scoping_2026-10-06.md §1.1）主張： llama_batch.pos 是 n_tokens × n_pos_per_embd(=3) 寬、每 token 佔 3 槽（t/h/w）， 而 draft 建批時只寫了 dim 0 ⇒ draft KV 的 RoPE 用 (pos,0,0) 而非文字該有的 (pos,pos,pos) ⇒ 隱藏態偏掉 ⇒ accept 塌陷。這條假說不成立。

#事實位置

2allocr 輸入按 1D 讀：seq_pos[s1].insert(batch.pos[i]) —— X<Y 檢查的 Y 正是這組值llama-batch.cpp:170

若照這條假說實作，兩種結果都不會改善 accept。 batch.pos 只有 n_tokens 寬，往 pos[k*nppe+1..] 寫：
  • 踩到別的 token 的位置槽 —— multi-seq draft 一輪會多次 common_batch_add，索引是連續被占用的；
  • 就算落在未用區，文字模式下 ubatch_add 只讀 pos[idxs[i]]， 這些額外寫入完全不進廣播 ⇒ 零影響。
沒有好結果；第一種還會污染位置。這是本輪第二個「差點寫下去的錯」。

11.2 那 3D 位置究竟是誰給的

不是 common_batch_add，是 allocr。選擇器在 src/llama.cpp/src/llama-graph.cpp:3033： ggml_build_forward_select(gf, inps.data(), inps.size(), ubatch.token ? 0 : 1) —— token 非空 ⇒ 走 token embedding 那條，ubatch.embd 被整條丟掉。 而 llm_graph_input_embd_h::set_input（llama-graph.cpp:155-159） 又把 embd 餵給 h —— 兩個通道各司其職。

本案模型（qwen35moe）不走那個通用 builder，而用 llm_graph_input_embd_h（models/qwen35moe.cpp:652）， 一次收 tokens ＋ embd ＋ h 三個輸入。配對合約由此定為：

位置 Q 的輸入 = ( x_Q , h_{Q-1} )
  x_Q      走 inp->tokens   → embed_tokens
  h_{Q-1}  走 ubatch->embd  → inp->h      (llama-graph.cpp:155-159)
  → concat[enorm(x); hnorm(h)] → eh_proj → attention → 預測 x_{Q+1}

⇒ 「token 與 embd 兩個都有」是必需且正確的： speculative.cpp:1794 寫 token、:1795 把 pending_h 寫進 embd。 這不是 bug，是 MTP 頭的輸入格式。

邊界（這條要留著）。 ubatch.token ? 0 : 1 同時顯示：純 embedding 批次（token == nullptr） 確實要求入口就是 nppe 寬（tools/mtmd/mtmd-helper-common.h:85 的 pos.resize(n_tokens*n_pos_per_embd) 即此類）。當前 MTP draft 有 token ⇒ 不適用。 但若將來把 draft 改成不填 token 的純 embd 批次，那時才需要 nppe 寬佈局—— 那是另一筆帳，不是 Fix A。

11.3 i_h 對齊證明：chain 路徑是乾淨的

四步求證，每步都有行號：

  1. verify batch 布局：[id_last @ P, d0 @ P+1, …, d_{k-1} @ P+k] （llama-bench.cpp:3535-3537；注意 n_past++ 的 post-inc 順序）。
  2. nextn_ith(j) ＝ index j 的輸出隱藏態，按 token 位置密集排列 （llama-context.cpp:1525 註釋明寫；填充見 :2888-2891，語意見 :2467）。
  3. 全接受時 ids = [d0..d_{k-1}, bonus]、ids.size()-1 = k ＝ accepted drafts （llama-bench.cpp:3712 的註釋 // accepted drafts，配合 :3625-3670 的 tree walk 推出 k+1 次取樣）。
  4. 新 root ＝ bonus @ P+k+1（:3916 id_last = ids.back()）。

⇒ 次輪需要配對 h_{P+k}；而 accept_seed（common/speculative.cpp:2086-2088）取 i_h = min(n_accepted, n_rows-1) = min(k, k) = k ⇒ pending_h = verify_h[k] = nextn_ith(index k) = h_{P+k} —— 與所需完全一致，chain 路徑沒有 off-by-one。

推導中踩到的陷阱。 一度以為「ids 不含 bonus token」（新 root 落在 P+k），那樣算起來會差一站、 看起來就像 off-by-one。含不含 bonus 會讓整個結論翻面，必須讀到 llama-bench.cpp:3712 才能定案——只憑 :3535 推會導錯。
