1. 入口 A：harness.py —— 為什麼要有前門

它存在的原因不是潔癖，是一組實測到的散佈

四支工具各自實作了一次「等到盒子空了再跑」：decode_window_harness.py（定義探針的那支）、m123_gate_window.py、plain_match_window.py、server_window.py cmd_wait。它們彼此不一致，而不一致不是外觀問題：同一份設定的實測散佈是 17%，壞日子 2.5×——而這種失敗在它產生的數字裡看不出來，所以只有在啟動前攔下來才有用。攔不攔得到，取決於你剛好挑了哪一個 wrapper。

harness.py 不取代那四個 wrapper，它是前門：一個知道四件事的地方。

#它知道的事實作
1哪一支工具需要安靜的窗口REGISTRY（28 支）＋ server_window.audit() 併入的 launches，所以新啟動器不必有人記得改表就會出現
2盒子現在怎麼說server_window.decision() —— 一次提問、兩個定義並排
3那個判定在物理上可不可以信--certify：先量 window_sentinel 的吞吐量當哨兵（thermal NOMINAL 曾在 2026-09-20 簽過一台慢 ~5 倍的機器）
4證據去了哪裡Backup/phase_decomp/harness_runs.jsonl，每跑一次 append 一行（目前 5 行）

三種立場，而「未知」不是 False

needs_window=True   盒子忙會汙染這支工具的輸出（要等窗口）
needs_window=False  它只解析檔案 / 做算術，鄰居的 server 不改變答案（只改變速度）
needs_window=None   還沒標記 —— show 會把它報成缺口，而不是靜靜當成 False

未登記的工具一律 needs_window_for() == True：不安全是不對稱的。
把「需要安靜」誤判成「不需要」會產生一個看起來正常、描述的是鄰居的數字；
反過來只會讓人多等。

CLI

2. 前門上面那個洞：sw.decision() 不存在（已修）

症狀。python3 scripts/check/harness.py show（也就是這個檔案自己的預設指令、docstring 叫人「先跑這個」的那一條）當場崩潰：

File "scripts/check/harness.py", line 207, in cmd_show
    box = box_view(sw, args.port, args.need_mb)
File "scripts/check/harness.py", line 171, in box_view
    d = sw.decision(port, need_mb)
AttributeError: module 'sw' has no attribute 'decision'

範圍。sw.decision( 的呼叫者：harness.py（三個 worktree 各一份）、box_probe_compare.py、Backup/phase_decomp/gap_split_swap.py。全樹沒有任何檔案定義它——五個 worktree 都沒有。

為什麼 selftest 一直是綠的。舊的 selftest 把 decision 的 dict 當 fixture 造出來（base = {"decision": {...}}）再斷言——它驗的是 _verdict() 這個純函式對一份自己造的輸入的反應。沒有任何一項檢查去問「這個 dict 的生產者存在嗎」，所以一個不存在的函式可以讓 22 項自測全過，而預設指令是壞的。

修法（三個檔案，各一處）

檔案改動為什麼是這樣改
server_window.py 新增 decision() 與 launcher_guard()（44 項自測） harness 側沿用既有的 quiet() 探針；launcher 側去問 launcher 本人，不在 Python 端重算它的門檻
run_server.sh [guard] 那行多發布 req_phys / req_free / req_other / admits=yes|no 門檻只住在 cgc_memory_guard_req。由 Python 從 free% 回推「launcher 會不會放行」＝在世界裡多一個 launcher 門檻定義，而那正是「兩個 free memory 定義」已經付過一次代價的病
harness.py 看板對缺席值印 - 而不是 0；selftest 改為斷言生產者（9 個 key） 0 會被讀成「launcher 什麼都會拒絕」；而 0 與「沒有發布」是兩句不同的話（absence-as-a-value）

launcher 的自我判定是它自己印的，成本 0.25 秒（CGC_DUMP_ENV=1 bash scripts/run_server.sh，印完就結束、不啟動）：

[guard] memory_mode=dev class=full-mtp phys=16GB free=72% other_llama_servers=0 \
        req_phys=0GB req_free=40% req_other=0 admits=yes

而 decision() 回傳的就是兩個定義並排的那一份：

{
 "reclaimable_mb": 5607.234375, "need_mb": 8000.0,
 "foreign_llama": [], "port_held": [],
 "harness_admits": false, "harness_terms": {"memory": false, "foreign": true, "port": true},
 "launcher_class": "full-mtp", "launcher_free_pct": 72, "launcher_req_pct": 40,
 "launcher_terms": {"phys": true, "free": true, "other": true}, "launcher_admits": true,
 "agree": false, "binding": "harness", "admits": false, "refused_by": ["harness:memory"]
}

修完的當場價值：兩個定義現在真的不一致，而它變成一條指令就能讀到的事實。harness 說 5607 < 8000 拒絕；launcher 說 72% ≥ 40% 放行。agree=false、binding=harness——這正是 2026-09-20 那次（harness 在 6636 MB 拒絕、launcher 讀到 84%）的形狀，只是現在不必靠回憶。

自測補上的三件事（這些是原本抓不到的）

  • decision() 必須真的存在，且帶齊 admits / harness_admits / launcher_admits / agree / binding / reclaimable_mb / port_held / foreign_llama / launcher_class。
  • agree 只有在 launcher 有發布判定時才可能是 True。
  • [guard] 舊格式（沒有 req/admits 欄位）仍要能解析，而且發布「沒有判定」而不是暗示的 yes——其他 worktree 的 run_server.sh 還沒更新時，這條才是誠實的。

3. 入口 B：check_build_tracked.sh —— pre-commit 的 12 道檢查

hook 的落點，以及三個很容易裝錯的地方

安裝：scripts/check_build_tracked.sh --install-hook。它寫的是 git 真正會讀的 hooks 目錄（git rev-parse --git-path hooks，也就是 common dir 的 hooks）——這個 repo 有多個 worktree，所以同一顆 hook 服務全部 worktree。
#!/bin/bash
# generated by check_build_tracked.sh --install-hook
set -euo pipefail
export BIN_DIR='src/llama.cpp/build/bin'
REPO_ROOT="$(git rev-parse --show-toplevel 2>/dev/null)"
exec "$REPO_ROOT/scripts/check_build_tracked.sh" --repo "$REPO_ROOT"
  • REPO_ROOT 在執行時解析、不寫死。寫死安裝當下那一個，從別的 worktree commit 時會去驗錯的 repo（偽 PASS）——這個檔案以前就是落到死路徑。
  • hook 的 set -e 會傳進本 script。set -uo pipefail 不會把 -e 關掉，所以新增的檢查必須把非零離開碼接在 if 條件裡，否則整個 script 會被中止（檢查 12 的註解就是記這件事）。
  • SKIP 要計數（B7：可被跳過的閘門不是閘門）。本 script 會在總結說「本次有 N 個區段被 SKIP」，因為「OK」在 11 個區段全被跳過時也照樣印得出來。

4. 入口 C：產物出處契約本身

「window class」是四個值，而不是一個布林

server_window.provenance() 在行程內取樣，不在事後補蓋——寫檔當下的盒況不是量測當時的盒況，事後蓋章是偽造的出處，與這條線產生過的每個錯數字同一形狀。

class意思
clean每一個樣本都安靜，而且 gated 的那次啟動看到的是安靜的盒子
busy-then-cleared稍早忙過，但 gated 的啟動是安靜的（等待型守衛的正常結果）
busy-overridden在忙的盒子上照跑（CGC_WINDOW_OVERRIDE=1）：這筆可能描述的是鄰居
unknown這個行程從沒問過共用探針——明講，不是留白

「measured object」的判定是 11 個 key：mean_len, accept, m1_numeric_identity, m2_decision_agreement, tps, arms, cuts, rows, requests, results, onoff_separated。rows／arms／requests 本身是容器，所以帶著它們的容器也要有 window——這個陷阱吃過兩次（一份記錄了盒況的產物，仍有一半的 object 答不出來）。

報告與它的 sidecar：為什麼是登記制，而不是「所有 docs/*.html」

docs/ 裡有 77 個 *.html，幾乎都是手寫的白皮書。對所有 HTML 要求 sidecar，就是一個會被 --no-verify 掉的規則。所以這裡反向定義：一份產物被判，是因為有一個工具被登記為它的生產者。

REPORT_PRODUCERS = (
  target25_report.py         docs/TARGET25_REPORT_*.html   sidecar=<stem>.json
    evidence: writes the sidecar in the same run (target25_report.py:636)
  decode_window_harness.py   docs/DECODE_WINDOW_????-??-??.html   sidecar=<stem>.json
    evidence: sidecar written in the same call as the HTML (write_report / autoreport)
)

第二條的 glob 是那支工具自己的命名規則，不是 DECODE_WINDOW_*.html。寬的版本會去判 docs/DECODE_WINDOW_HARNESS_20260919_1745.html——那是一份手寫的、關於這支 harness 的分析（它自己的內文就這麼說），因此依定義不會有 sidecar。把比對寬度放大在這裡不是保守：它等於向一份從未被量測的產物索取證據，跟向 docs/ 那 77 份手寫白皮書索取 sidecar 是同一種病。已知盲點：用 --out 寫到別的名字的報告會逃出這條規則。

登記制最危險的方向是過期：一個新 producer 沒人登記，它寫的產物就沒人判。所以登記表自己的完整性也要被查——producers_writing_html_docs() 掃 scripts/**/*.py，找出所有「組出一條指向 docs/ 的 .html 路徑」的行，每一支都必須在登記表裡或有具名理由的例外。

那個掃描規則是量出來的，不是猜的。粗糙版（同一行同時出現 docs 與 .html）在這棵樹上命中 14 行，其中 12 行是 docstring／help 文字（例如 knifeedge/feasibility.py:209 是一句 stderr 提示的 f-string）。加上兩個排除條件（註解行、stderr／print( 行）＋「必須是路徑建構」之後，剩下的恰好就是兩支真的 producer。

唯一的例外是這個閘門自己：它的 selftest fixture 會把 docs/TARGET25_REPORT_t.html 寫進一顆臨時 repo，所以 REPORT_EXEMPT 收錄它並記錄理由——而 selftest 會在例外過期時轉紅（被例外的檔案若不再命中，就是一條没人管的 allow-list）。

  • 「不解析的 7 個」不算違規。實測：其中 6 個是 vendored 的 JSONC 設定（pyrightconfig.json、三個 llama.cpp 樹裡的 tools/ui/tsconfig.json），加上一個 12 bytes 的 No results。把基準灌這些進去，就是訓練人忽略這個閘門。但它們仍被記名，所以新的不解析檔案會變成 WARNING，不會靜靜通過。
  • 基準只降不升，而 update 是獨立指令。重新基準不可能在 commit 裡意外發生。
  • 自測通過，而且分母是算出來的、不是打上去的。本文件刻意不寫那個 N：這個「N/N」在本線已經過期三次（含寫完這份文件之後又被改了兩次），而一個手動維護分母的自測無法被信任來報告自己的覆蓋率。要讀那個數字，跑 selftest：它會把分母自己算出來並印成最後一行。

  • commit 閘自己跑了一次真的把關：第一次 commit 被 hook 擋下（FAIL 檢查 11：replay benchmark 需要活著的 llama-server），最後以 RUN_REPLAY_BENCH=0 過關。這是逃生閥、不是靜默略過——script 自己的總結會把 SKIP 列出來（那次是 4 個區段），而檢查 12 在同一次執行裡是 PASS。
  • 本線還留在工作區的一份獨立工作（25 t/s 量測鏈：target25_grid.py、verify_marginal.py、gap_vs_miss.py、draft_budget.py、shape_roofline.py、mtp_k_sweep.py 與 TOOLCHAIN_25TPS／VERIFY_MARGINAL／TARGET25_* 幾份文件）尚未 commit——它是一個獨立的主題，所以沒有搭這顆便車。
  • 成對規則只看已登記的 producer，也只看 docs/。寫到 Backup/ 或 /tmp 的報告不在這條規則的可見範圍內（/tmp 那個正是原先 2 unpaired 的成因）；而沒登記的 producer 會被規則 3 擋在 commit 之前——這是兩條不同的防線，只有其中一條能擋未來。
  • backfill 出來的 sidecar 不是「已驗證的證據」。它證明的是「這份報告的 digest 與讀數與它自己一致」，不是「那次量測乾淨」。window class 所以是 unknown 而不是 clean——把 backfill 讀成後者是這條線最熟悉的那種錯（把缺席當成一個值）。
  • 報告與 sidecar 必須進同一顆 commit，所以「HTML 逐位元不變、只有 sidecar 重跑」也會被擋。那是「成對移動」的嚴格讀法，也是刻意的：拆開的半對就是沒人查得了的半對（git add docs/X.* 會一起 stage）。
  • 一個沒有動到報告的 commit 裡刪掉 sidecar，不會被看到。--diff-filter=ACMR 把刪除排除在 staged 集合之外；要涵蓋就得把 D 也拿進來，而那會讓「刪一份舊報告」的 commit 多一道判定。
  • key 比對會有偽陽性。把同樣的證據記在別的欄位名下的產物，會被算成缺。一次偽陽性的成本是一行修正；一次偽陰性的成本是幾週，所以閘門偏向指名檔案。
  • 重新命名（rename）會被當成新增。把一份歷史違規搬路徑會進到新路徑 ⇒ 被擋。這是規則 1 的字面讀法，不是特例：帶上證據，或不要把那個檔案放進這次 commit。
  • 前門的紀錄是「子行程周圍的盒子」。harness_runs.jsonl 記的是這個行程在啟動前與返回後看到的盒況；子行程有自己的位址空間。若子行程本身是受閘工具，它會自己問同一個探針並帶上自己的證據（child_gated 就是標這件事），否則那筆紀錄只描述盒子，不描述子行程內部。
  • 5 支啟動器仍未受閘（decode_step_profile.py、decode_sweep.py、http_duo.py、m123_oracle_gate.py、mtp_accept_ab.py）。window_gate 的規則是不只不能增加，只能下降——要降就得把它們接上 require_first()。
  • --certify 需要 window_sentinel_ref.json；沒有參考值時它會拒絕背書（rc=4），而不是用 0 當門檻。
  • 看板的 REFUSED 是 harness 的門檻（8000 MB），不是 launcher 的。要改用 launcher 的門檻跑就得刻意傳較低的 --need-mb——紀錄會寫明用了哪一條。這一格以前只會給出「the box is busy」的錯覺，現在它會指明 binding。
