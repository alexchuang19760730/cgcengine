# M-W 在交付 cell 上的判决：`CGC_SERVER_WORKERS=8 → 2` 到底值几个百分点

日期：2026-09-21（21:06–21:56）　方法：llama-bench 交付 cell、0 重建、10 臂（5 有效配对）
结论一句话：**机制是真的（fill −9.8%，5/5 配对同向，p=0.031），但端到端只值 ≈ +1.7%，
低于 3% 可见门槛 ⇒ 不是「可交付的加速」，只是「零风险、可顺手改」的 env。**

---

## 0. 旋钮只影响一件事（归因干净）

`scripts/run_server.sh:1353` 是 `CGC_SERVER_WORKERS` 的**唯一**去处：

```sh
LLAMA_EXPERT_CACHE_WORKERS="${CGC_SERVER_WORKERS:-8}"
```

⇒ 它只改 IO 填池的 worker 数，不碰 HTTP 线程、不碰 GPU。所以 A/B 的差值可以干净地归因到 fill。
（⚠️ 反过来：**直接设 `LLAMA_EXPERT_CACHE_WORKERS` 无效** —— 走 `llama_bench_matrix` 的
`PROFILE:ENV=VAL` 会被 `run_server.sh` 静默覆盖回 8，已用 0-GPU resolve 验证。）

---

## 1. 这一轮和之前那轮（6v4、非交付 cell）有什么不同

| | 之前（K3 cell） | **本轮（交付 cell）** |
|---|---|---|
| cell | `dispatch_price_v2` 自建 | `prod_profile.DECODE_SHAPE`（与 12.57 同一条命令） |
| 臂数 | 6v4 | **5 配对（10 臂）** |
| thermal | 末臂进 MODERATE | **10 臂全部 NOMINAL（107–117/117 采样）** |
| 顺序 | AB 交替 | **ABBA（round 奇偶反转）** |
| 臂间冷却 | 无 | **150 s + 轮询等 NOMINAL** |

**为什么冷却是必需的（本轮最贵的方法论教训）**：第一次尝试（无冷却）里，
第 1 臂 w=8 的 120 个采样**全部 NOMINAL**，紧接的第 2 臂 w=2 有 **81/120 在 HEAVY**。
热是臂**内部**升上去的、且单向 ⇒ 「发射时 NOMINAL」的闸门完全挡不住，
而单向漂移**不能靠 AB 交替抵销**，只能靠冷却 + ABBA + HEAVY 臂作废。
加了 150 s 冷却后无任何一臂进 HEAVY。

**主指标 `pool_wait_us / misses`（run 级累加量，越低越快）**

- 中位比值 **0.902（−9.8%）**
- 全部 5 个比值：0.875 / 0.891 / 0.902 / 0.909 / 0.959
- **5/5 配对同向**（硬币零假设 p = 2⁻⁵ = **0.031**）
- 臂内离散：w=8 的 CV ≈ 0.7%（667.1 / 670.7 / 660.9 / 644.2 / 643.3），w=2 的 CV ≈ 4.6%

**副指标 t/s（单臂噪音 ±27%）**

- 中位比值 1.060（+6.0%），但**只有 3/5 同向**，比值散布 0.826–1.119
- ⇒ **幅度不可引用**，只能说「方向为正」

## 3. 为什么机制显著而端到端不显著：pool_wait 只占步时约 17%

用同一批 run 自己的数字换算（不跨 run 相乘）：

```
misses(中位)      = 9779        pool_wait = 661 µs/miss × 9779 = 6.46 s
decode 步数       = gen 128 × reps 3 = 384
⇒ pool_wait / 步  = 6.46 s / 384 = 16.8 ms
   总步时          = 1000 / 9.938 t/s = 100.6 ms
⇒ pool_wait 占步时 ≈ 16.7%
```

⇒ 端到端期望：`−9.8% × 16.7% ≈ −1.6% 步时` ⇒ **t/s +1.7%**。

这解释了 t/s 只有 3/5 同向：**信号 ~+1.7%，噪音 ±27%（配对后仍 ~±12%）**，
测到一个 +6% 的中位只是运气。⚠️ `misses` 里含少量 prefill 贡献（量级 <5%），
所以 16.7% 是量级而非精确值 —— 但即使高估一倍，端到端仍 ≤ 3.4%。

## 4. 判决

| 问题 | 答案 |
|---|---|
| fill 真的变快了吗？ | **是**。−9.8%，5/5 配对同向，p=0.031 |
| 端到端值几个百分点？ | **≈ +1.7%**（12.57 → 12.78）；实测中位 +6.0% **不可引用** |
| 过 3% 门槛吗？ | **不过** |
| 有风险吗？ | 零（单一用途 env，不改语义、不需要重建） |
| 要写进交付默认值吗？ | **可改，但不要对外宣称收益**。它是「顺手改」不是「优化项」 |

**不要把 M-W 记为「+6% 的杠杆**」——那是噪音。它在里程碑表里应该标成
**「机制确证 / 端到端 ≈ +1.7% / 低于门槛」**。

## 5. 附：第 2 格（M-K5）的重建规格已经确定

今天顺手做了 M-K5 的 0 重建前置，结论是**它必须重建，且现有 dump 不够**：

- `CGC_GRPH_DBG`（`ggml-backend.cpp:2091`）是 **`static int cgc_grph_dbg_n < 6`** ⇒
  整个进程只打 6 次。历史 raw（`Backup/cgc_logs/llama_server_20260921_173218.log`）证实：
  前 5 次全是 `n_nodes=4116`（**prefill**），只有第 6 次是 91 节点 ⇒ **decode 形状一次都没拿到**。
- 而且它只打 `ne=[%lld,%lld]`（**只有 ne[0], ne[1] 两维**），没有 ne[2]/ne[3]，
  也没有 `op_params` ⇒ **即使让它 fire 在 decode，也判不出 (A)「grid 太小」**。
- ⇒ 重建要改两处：① 触发条件改成「只在 decode 图形状触发 / 把上限提到 ≥ 40」；
  ② 打印补全 `ne[0..3]`。改完才能给 (A)/(B) 下定论。
