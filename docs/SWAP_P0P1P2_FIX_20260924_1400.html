一句話結論：真正的病不是 swap，是結構性超訂 4838 MiB—— expert 權重在 CPU 副本（read_raw 讀成的匿名頁）與 pool 各住一份， 靜態需求 21222 MiB 塞進 16384 MiB。P0 讓 skip-load 的 expert 不再 read_raw， 單趟 run 的 swap 增量從 +5678.88 MiB 降到 +448.56 MiB（−92.1%）， 證明「這份 CPU 副本佔位、卻從未被算過」的機制是真的。

但修正的代價也是真的：decode 從 10.20 掉到 7.60 t/s（−25.5%）—— 權重不再預先駐留，每次 miss 都得付一次真正的磁碟 IO。

判決的精確措辭（不要被上面那句話誤導）：三條驗收判據中， 第 1 條（dswap ≈ 0 且不累積）沒有通過——三趟跑完累積仍 +6876.94 MiB； 第 2、3 條以代理儀器通過，但不是原設計的輸入（CGC-SHAPE／ final stats 這批 stderr 欄位在本輪 log 裡完全沒有被 capture 到）。 所以本文件的主張是「P0 的機制正確且效應巨大」， 不是「swap 問題已修好」。詳見 §7 與 §8。

§2　病根：21222 MiB 塞進 16384 MiB

這台機器上的超訂是靜態的——它不取決於 run 多長、prompt 是什麼， 只要模型和 pool 的大小定了，它就存在：

項目大小說明
模型檔13030 MiB 其中 expert = 256 × 40 × 1.0703 MiB = 10960 MiB，dense／其他 2070 MiB
expert pool8192 MiB--expert-cache 8589934592
靜態需求21222 MiB對上實測 resident 21222 MiB
實體記憶體16384 MiBMac16,12 unified
超訂4838 MiB run_server.sh:1056-1057 自己會印這行並標 OVERSUBSCRIBED

2.1 這個前提要拆成兩條通道（關鍵的方法論）

原始的問題是「swap 大 ⇒ miss 也高」。它其實是兩個不同的主張，而且答案相反：

通道問的是答案
cost 通道一次 miss／hit 要付多少時間 成立，且是主效應。匿名頁 reclaim 要先寫後讀（2× IO）； file-backed clean 頁是直接丟掉重讀（1× IO）。
count 通道miss 的次數有沒有變多 大概率不成立。既有的 miss 歸因是 compulsory 91.4% / capacity 8.6%——91% 的 miss 是「這個 (layer, expert) 第一次被摸到」，與剔除、水位、swap 都無關。

推論：「swap ⇒ miss」是混淆不是因果。macOS 的 swap 在本機單調累積、 永不回收（MEMORY_HYGIENE.md:44 實測 purge 不減 swap_used）， 所以任何隨時間惡化的東西（熱／DVFS 降階、背景 GPU 客戶端、累積負載）都會跟它同向。

有一條反向實測可以直接否掉 count 通道的因果：pool 8G／6G／5G／4G 的 hit 分別是 96.0 / 93.3 / 91.4 / 87.6%——pool 越大（記憶體壓力越大、swap 越大），hit 反而越高。 真正控制 miss 的是槽數，swap 是它的下游結果。

§3　機制：為什麼 expert 有兩份潛在駐留

下面這條事實鏈每一環都有代碼位置，是本輪 P0 的直接依據。

#事實位置
1 pool fill 直接 pread/preadv 讀檔案，不走 mmap、不走 CPU 副本 llama-expert-cache.cpp:35、:149
2 compute 時 GPU FFN 讀的是 pool（pread 直接寫 pool buffer） llama-expert-cache.cpp:35/149、adopt_pool_region :1881
3 skip-load 的 expert tensor 卻仍被 read_raw 全量讀進 CPU RAM （匿名堆，非 file-backed） llama-model-loader.cpp:1844-1850
4 ⇒ expert 的 CPU 副本是純佔位：佔掉 ~10.9 GB 匿名記憶體，卻從沒被算過 由 1＋2＋3 推得

3.1 為什麼佔位也要付出代價（2× IO 不對稱）

--load-mode none 是 run_server.sh:507 的預設。在這個模式下， 那 10960 MiB 被 read_raw 讀成匿名頁 （run_server.sh:1014-1017：_MODEL_KIND="匿名頁、不可回收"）。 匿名頁在記憶體壓力下的命運與 file-backed clean 頁完全不同：

  • file-backed clean 頁：核心直接丟掉，下次用到重讀一次 ⇒ 1 次 IO。
  • 匿名頁：必須先寫到 swap，用到的時候再讀回來 ⇒ 2 次 IO。

而且它在快取中繼資料上仍然是 hit（不計入 miss）。這就解釋了那個看似矛盾的觀測： 你看到 t/s 崩、hit% 卻紋風不動。損失發生在 latency 上，不在計數器上。

§4　P0／P1／P2 各做什麼

編號開關做什麼效果
P0 CGC_EXPERT_SKIP_READRAW=1 skip-load 的 expert tensor 不 read_raw。CPU buffer 保持佔位， 位元組由 pool fill 的 pread 供給。 砍掉 10960 MiB 匿名駐留（雙駐留的那一半）
P1 CGC_POOL_MADVISE=1 fill 之前對目標 slot 的頁 madvise(MADV_DONTNEED)： 那塊馬上要被 pread 整塊覆寫，核心卻得先把它物化 （若在 swap 上就是一次 swap-in 讀，讀進來下一刻就丟）。 砍掉「覆寫前的 swap-in 讀」
P2 CGC_POOL_MADVISE=2 evict 時對該 slot 做同樣的事：內容本來就作廢，不該被寫出去。 砍掉 garbage 的 swap 寫

三者都不動槽數——這是刻意的。SWAP_MISS_LINK §4.1 已經算過： 另一帖藥「縮 pool 降 swap」要壓到 3072 MiB 才不超訂，那時每層只剩約 53 槽（今天 143 槽）， 而 8G→4G 只把超訂從 4838 砍到 742，卻先付掉 8.4pp 的 hit。 拿 miss 換 swap，方向反了。

4.1 為什麼設計成「預設關閉」

三個開關全部預設關，不設 env 時行為與舊路徑逐位元組相同。這不是保守， 是這個 repo 的併行工作需求：llama-expert-cache.cpp 同時有另一條線 （線 I，cb／快取命中儀器）的 218 insertions 未提交， 統一 diff 對這種會漂移的檔沒有用，而「降落即生效」會動到別人正在跑的量測。

§6　邊界與陷阱（寫錯就是靜默毀損）

這一節是整份文件最硬的部分。P0/P1/P2 的錯誤模式共同點是： 它們都不會報錯——要麼毀掉隔壁 slot，要麼讓整網輸出垃圾。

6.1 P0 的三個 guard

#guard漏掉的後果
1 只對 loader 自己放上 skip-load 路徑的 tensor 生效 （skip_no_read 表，在前項確保含 !buft 前提）。 重寫一次 strstr(name,"_exps") 是錯的： 會跳過從來沒打算被跳過的 tensor（例如經 tensor_buft_overrides 送上 CPU 的 expert），其資料沒人供給。
2 L4_SKIP_LAYER0 的 blk.0 必須排除。 它被故意降回普通 CPU tensor（l4_kind = -1）， 它的 FFN 真的從這個 CPU buffer 讀（llama-context.cpp:6437）。 layer-0 吃到 zeros ⇒ 整網輸出垃圾，而且完全不報錯。 這是 P0 唯一的靜默毀損模式。
3 連 ggml_validate_row_data 一起跳。 buffer 未初始化，--check-tensors 會 throw invalid data。 帶 --check-tensors 的 run 直接崩在載入階段。

guard 2 的觸發條件是 CGC_SERVER_SKIP0 （run_server.sh:1445，預設 0）⇒ 目前的交付配置是安全的。 但 cgs_skip_readraw 必須寫成「skip_no_read 命中 且 非（SKIP0 開啟且是 blk.0）」，不能只判 skip-load。

6.2 P0.g：存在判定 vs 取值判定

第一版寫的是 getenv("CGC_EXPERT_SKIP_READRAW") != nullptr—— 任何值都把 P0 打開，包括 =0。這很危險，因為把「顯式預設 0」 寫進 launcher profile 是最自然的做法，那會讓 prod-new 靜默開著 P0 跑。已改成取值判定（0／空 = 關）：

static const bool on = []() -> bool {
    const char * v = getenv("CGC_EXPERT_SKIP_READRAW");
    return v != nullptr && v[0] != '\0' && v[0] != '0';
}();

6.3 P1/P2：頁對齊與 68.5 頁的 stride

兩個 helper 存在的理由完全相同，而且都指向靜默毀掉隔壁 slot：

  1. madvise() 要求頁對齊的位址，否則 EINVAL。
  2. expert stride = 1.0703 MiB = 68.5 個 16 KiB 頁，不是頁的整數倍 ⇒ 範圍若往外取整，madvise 會清掉前一個 slot 的尾頁與下一個 slot 的頭頁， 而且不報錯。

所以正確做法是：start 往上取整、end 往下取整，只丟完整落在範圍內的頁 （範圍內無整頁就什麼都不丟）。自檢第 2 項實測：6 個連續 slot 全部零越界， 每個 slot 丟到 67 頁（68.5 向下取整並扣除兩端不完整的部分）。

6.4 Metal 的 pool_ext 永遠不碰

pool 的兩種記憶體來源不同：pool 是 malloc 的匿名記憶體， pool_ext 是 Metal 分配（pool_region()， llama-expert-cache.cpp:715-730）。對後者做 madvise 等於從 GPU 腳下把位元組抽走。cgc_in_malloc_pool 會先把非 malloc 的 dst 擋掉。

6.5 落地時踩到的前向宣告

cgc_pool_madvise_mode() 在 pick_slot（約 :700）被呼叫， 但定義在 pool_region 之後（約 :800，因為要用 slots_l）。 少一個前向宣告就是編譯錯誤——而這個檔的編譯錯誤會擋掉所有人的 build。已補兩個前向宣告。

§7　A/B 實測與三條判據

7.1 環境與設計

  • profile：prod-new ＋ CGC_SERVER_MTP=1。 必須疊 MTP=1：prod-new 的 MTP=0 分支 會把 MODEL 換成沒有 nextn head 的另一個 checkpoint （run_server.sh:153-161）⇒ 那不是交付模型，三臂都換模型的話完全不能比。
  • binary：三臂同為 build 1ca685490。對照臂不是另一個 build， 而是同一個 binary 不設 env。
  • thermal：三臂 launch／worst 皆 NOMINAL， histogram 全程 NOMINAL。
  • cell：decode，--reps 3，--no-ref。
  • reps／輪數：單趟（rounds=1），沒有 ABBA。

7.3 三條判據逐條評

miss_attr_gate.py 定義的三大條來說，說明現有數據能夠判到哪裡。

判據設計輸入本輪結果
1　dswap ≈ 0 且多趟不累積 sysctl vm.swapusage（有） FAIL。單趟最大 |dswap| = 5678.88 MiB（門檻 64）； 三趟累積 drift = +6876.94 MiB。
2　hit_pct 不降 原設計用 CGC-SHAPE／final stats 的 hit_pct= ——本輪 log 完全沒有被 capture 到 代理通過，但不是原設計輸入。改用 prod_profile.py 的 cache: 摘要：ctrl 57.7 → p0 57.2（−0.5pp，恰在容許邊界） → p012 59.1（+1.4pp）。
3　capacity 不升 ＋ pread 降 同上（未 capture） 代理部分通過。cap%：35.6 → 38.1 → 35.5 （p0 略升、p012 持平）；us/job：14569 → 11683（−19.8%）→ 12441（−14.6%） ⇒ 每次 IO job 的成本確實下降。

為什麼判據 2/3 不算「驗過」：miss_attr_gate.py 的輸入是 引擎 destructor 在乾淨關機時印的 stderr 行（CGC-SHAPE v=1 phase=final、 final stats:、miss attribution:）。本輪的三份 log （runner.out/decode-delivery.out）裡這三批行一行都沒有—— 與 miss_attr_gate.py docstring 自己註記的 「SIGINT 時 destructor 可能跑不到」（llama-expert-cache.cpp:515-518）吻合。

所以上面第二、三條的 hit%／cap%／us-job 是另一支儀器（prod_profile.py 從 llama-bench 摘要出來的 cache: 行）的數字，欄位口徑不同。 拿它們填進 miss_attr_gate.py 會得到「PASS」的錯覺。 嚴格說這兩條是「未驗」，本文件只是在旁邊放了代理數字供參考。

7.4 −25.5% 的代價怎麼讀

三個數字要一起看，但它們不是同一個分母，不能互相對沖：

  • t/s：10.20 → 7.60（−25.5%）——端到端吞吐。
  • us/job：14569 → 11683（−19.8%）——單次 IO job 的成本， 下降了（不再有 swap 的 2× IO 摻在裡面）。
  • reads：43857 → 44589（p0 略增）—— IO 次數。

合理的機制解釋：P0 之前，expert 在載入時就被讀成匿名頁 ⇒ 之後的 miss 有很大一部分 只是在記憶體裡（或 swap 裡）搬動。P0 之後每次 miss 都要付一次真正的 SSD 讀。 單次 job 更有效率（us/job 降），但要真正跑 SSD 的次數再也躲不掉了。 這一台的超訂配置本身就不適合「不預讀權重」的策略。

⚠ 另一個不能忽略的混淆：三趟是順序跑的，起點水位不同 （0 → 5678.88 → 6127.44 MiB）。ctrl 在乾淨機器上跑，p0/p012 則承擔了 前一趟留下的 swap。沒有 ABBA（正反序）就無法分離「P0 的效應」與「累積的效應」。 要分離兩者就必須跑 --rounds 2 的 ABBA（正反序各一趟）。

§8　誠實邊界：不主張什麼

本文件不主張下列任何一件事：

  1. 不主張「swap 問題已修好」。三條判據中第 1 條 FAIL，且三趟累積仍在 +6876.94 MiB。P0 把增量降了 92%，但沒有讓它歸零。
  2. 不主張 P1/P2 有效或無效。本輪 p012 的 Δswap（+749.50）高於 p0（+448.56），但這是 n=1 且起點不同。要判 P1/P2 必須跑 ABBA。
  3. 不主張 7.60 t/s 是可交付數字。它比 ctrl 慢 25.5%， 而且這三者都是在超訂配置上跑的（見 §9 註）。
  4. 不主張第 2/3 條判據已通過。原設計的 CGC-SHAPE／final stats 欄位未被 capture；§7.3 的代理數字來自另一支儀器。
  5. 不主張這組數字可以對上 12.57 或任何交付錨點。binary 含線 I 未提交的 294+ 行。
  6. 不做目的 clipping。沒有加重排除任何 record；ctrl 那一趟就是從乾淨的 0 MiB 起算。

8.1 下一步（成本由低到高）

  1. 修 log capture（零 GPU）：讓 CGC-SHAPE／final stats 被 tee 到 .out，然後重新用原設計輸入跑 miss_attr_gate.py。 這是判據 2/3 從「未驗」變成「驗過」的唯一路徑。
  2. 跑 --rounds 2 ABBA（~40 分鐘）：分離 P0 效應與累積效應、 並給 P1/P2 一個能看的 window。
  3. 正的架槓是 L1（pool 甜點）還是 P0？ SWAP_STRUCTURAL_FIX §7.5 已確認 L4 adopt/shrunk 早就生效 （footprint MALLOC 僅 474 MB，expert 沒有 ~10GB CPU 副本）—— 與本輪 P0 看到的 −92% swap 增量表面上看起來對不太上。 這是本輪留下來的開放問題，下一步要 reconcile 「server load probe 的 adopt 結論」與「A/B 看到的 5678 MiB 差額」。
