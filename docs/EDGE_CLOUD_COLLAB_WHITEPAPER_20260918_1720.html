這份文件的定位：新主題 ⇒ 另開新檔，不是追加。 FLEET_PORTAL_DELIVERY 描述的是 「入口」那一條線（機隊上報、網站、匯出、自動化），本檔描述的是 「端到雲的協同開發」這一張全域圖：有哪幾個平面、每個平面的權威在哪、資料怎麼流、 協議怎麼表達「誰是哪一類 agent」、以及哪些事還沒做。 兩份不互相取代；本檔凡是引用那一份已經寫過的細節，都會指名節號而不重抄。
一頁速覽（先記這五句，後面每一節都是它們的展開）
  1. 四個端點、一個雲：mac-local（本機，reaches=self）、 cloud-host2（雲主機，reaches=network）、 windows-rtx4090 與 harmonyos-matebook14（reaches=offline）。
  2. 端上只需要裝一個東西：edge_server.py。它同時是 OpenAI 相容推理入口、 狀態上報來源、以及 store-and-forward 的 dump 產生器。
  3. 「怎麼到達一個端點」只有一份真相：agent_harness/portal/fleet.json 的 reaches 與 channels。別的檔案只准引用它。
  4. agent 的分類寫在協議上：A2A 卡片帶 x-agent-class 與 x-macro-scope，而且路由會因為類別不匹配而拒絕 —— 分類不是標籤。
  5. 離線不是失敗：連不上、沒上報、通道沒開，一律是 unknown／absent。 一個會因為連不上而變紅的入口，會在每一個離線的早晨說謊。

§1 全域拓撲：三端一雲，與五層

先把圖看一遍。這張圖的每一格都在後面有專節，而且都指得到檔案。 圖裡刻意把「誰是權威」畫在方框內、把「誰只是派生」畫在箭頭上。

※ 圖上的箭頭不代表「有實作」：每一條箭頭都對應 fleet.json 裡的一條 relay.how 或 heartbeat，而每一條都帶 evidence（指到既有腳本）。 沒有 evidence 的箭頭不畫 —— 畫上去就會變成「看起來已經通了」。

§2 先把五個平面分開，否則後面每一句都會歧義

「端雲協同」最容易出事的地方不是技術，是同一個詞在兩個平面裡指不同東西。 例如「狀態」：控制面的狀態是帳號與模型清單，端側的狀態是服務與硬體， 取證面的狀態是「這份上報有多舊」。三者混在一張表裡，就再也答不出「哪一個是權威」。

推理面 模型在哪跑、KV 怎麼搬、prefill/decode 怎麼分 pd/pd_service.proto（14 個 rpc）＋ edge_server.py A2A 的 pd-inference 只是它的身分，不是全部能力 把「身分」當「全部 rpc」⇒ 會宣稱整合完成（假的）

到達面 我們怎麼碰到某個端點 portal/fleet.json（reaches ＋ channels） fleet_auto.py 讀它決定來源；portal 頁面照它畫 有人在別處再寫一份「端點清單」⇒ 兩份真相，分歧時靜默
紅線（fleet.json 的 rules.no_second_truth）： 端點清單只在 fleet.json；來源清單只在 trend_sources.json。 所以 fleet_auto.py 不自己維護一份端點清單 —— 它讀 fleet.json。 這也是為什麼 §7 的三步裡，第一步的輸入是 fleet.json 而不是任何設定檔。

§3 端側：edge_server.py —— 端上唯一要裝的東西

端側的設計目標是「一條一定跑得完的指令」。這件事有一個很硬的判準： 如果那條指令需要模型檔、需要 llama-server、需要開埠， 那它在目標機器上就跑不動 —— 而跑不動的指令等於沒有這條路。

§3.2 store-and-forward 的入口：--dump-status

離線端（Windows／鴻蒙）不在我們的網路上，所以我們碰不到它的 /v1/edge/status。但它能寫一份檔。而下游那一支 （report_endpoint_status.py）吃檔案與吃 URL 是同一條路 —— 所以「端點 dump → 既有通道帶回 → harness 映射」成立。

# 在端點上跑（不起服務、不開埠、不需要模型、不需要 llama-server）
python3 installer/edge_server.py --dump-status status.json --endpoint-id windows-rtx4090
# 或直接寫 stdout
python3 installer/edge_server.py --dump-status - --endpoint-id windows-rtx4090
schema 完全相同，只多一格 dump。 uptime_s 與 served 是這個 dump 行程自己的讀數（幾乎一定是 0）， 不是一個長期服務的統計。不標這一格，下游會把「剛 dump 所以 uptime≈0」 讀成「服務剛重啟」。實測輸出：uptime_s: 0.0 —— 這是對的，而且是需要被說出來的對。

沒給 --endpoint-id 會出聲：那時這份 dump 不知道屬於誰， harness 側會拒收 —— 一份「不知道屬於誰」的狀態上報，比沒有上報更糟。

§3.3 上報檔的契約（endpoints/<id>.json）

契約正本在 fleet.json 的 contract。必填 7 欄：

"required": ["endpoint_id", "reported_at", "platform", "arch",
             "what_ran", "capabilities", "not_measured"]

兩個語意上的要點（都在 endpoints/README.md 有完整說明，這裡只留最容易錯的）：

  • reported_at 是「觀測時刻」，不是「映射時刻」。 端點離線三天、dump 今天才被帶回，入口必須顯示三天前。 手動跑時人會看時間；定期跑每小時把它抹平一次，就永遠看起來是新的。 所以另有一格 mapped_at 記處理時刻 —— 兩件事分成兩格。
  • not_measured 是必填，不是選填。沒有這一欄， 「我沒量」與「我量了沒事」會長得一樣。

§4 協議面：A2A 閘道 —— 把分類寫進協議

這一節是整份文件最「有主張」的部分。需求原話是 「pd 服務提供 A2A protocol 能力」與「能夠區分 agent 屬於哪一類」， 而且宏觀決策與微觀能力的分類要放在 A2A 協議裡。

三個決策（使用者拍板）： ① 落點在 harness 側新增閘道（不動 pd 的 gRPC）； ② 範圍做完整規格（send / stream / tasks / pushNotificationConfig）； ③ 形狀用 標準 skills[] ＋ 擴展欄位。

§4.1 四個檔案，三層編譯

檔案角色為什麼要獨立存在
a2a/taxonomy.py分類的正本：三類 × （宏觀域 ＋ 微觀能力） 分類是一個維度，能力是另一個。塞進同一層，下一個人就會以為「能執行」＝「有權決定」。可 python3 taxonomy.py 自我檢查。
a2a/registry.json實例清單：有哪些 agent、跑在哪、不做什麼 「這台機器上有什麼」（fleet.json）與「誰在跑」（registry）是兩個正交的軸。併成一張表就再也答不出「這台機器上有誰」。
a2a/agent_card.py編譯器：taxonomy ＋ registry → A2A Agent Card 卡片是派生。手寫卡片必然與 taxonomy 漂移，而漂移是靜默的。
a2a/a2a_server.py閘道：stdlib HTTP ＋ JSON-RPC ＋ SSE ＋ push 不引入框架（見 §12 的邊界說明）。
a2a/identity.py身分 → 類別 → 四維（§5） 「我屬於哪一類」與「那一類要整理什麼」是同一支工具的兩個出口。

§4.3 分類的實際作用：路由會因為它拒絕

只寫在卡片上的是標籤。真正讓分類成為分類的是這條：

把 explorer 的 skill 送給 developer agent
⇒ code = -32005
   message = skill 'register-decision' 不屬於 developer 這一類（它是 探索 agent）
   data = {"agentClass":"developer","skillOwnerClass":"explorer","availableSkills":[...]}

同理，沒指名 skill 也拒收（-32602）—— 猜一個預設 skill 會讓打錯字的請求看起來像成功。

而且卡片上帶了 x-taxonomy.skill_owner（每個 skill 屬於哪一類的正本）， 對端可以自己核對，不必相信我們。

§4.5 每個 agent 都要寫「不做什麼」

registry.json 的 not_capable 是必填：只寫「能做什麼」的卡片， 會讓對端把「沒寫」讀成「可以做」。四張卡片的實例：

agent類別它明說不做什麼（首條）
cgc-dev-portingdeveloper無權決定要不要放棄某個移植目標 —— 那是 explorer 的 macro
fleet-operatoroperator無權改動引擎原始碼或決定移植策略 —— 那是 developer 的 macro
pd-inferenceoperator它的後端是 gRPC 的 pd_server，閘道只做 A2A 到 gRPC 的映射 —— 沒有把每個 rpc 都翻譯過來
cgc-explorerexplorer無權直接部署或改動生產服務 —— 決定了之後由 operator 執行
這四條不是禮貌用語，是權限邊界。它們把「誰能決定什麼」寫成機器可讀的資料， 於是「越權」這件事有機會在呼叫之前被拒絕，而不是在事後被發現。

§5 身分錨：session 屬於哪一類，以及那一類的四維

「我屬於哪一類」如果靠 session 自己宣稱或靠標題，它就是一個不可機檢的宣稱。 最不會漂移的判準是它用哪一個帳號登入雲側。

§5.1 判準是帳號，不是自稱，也不是 role

類別帳號雲側 role（實況）UUID

三個帳號都是 super_admin（2026-09-18 實測）。 所以 role 不承擔「區分類別」的職責，區分只在 email 上 —— 如果有人以為「role 低的那個是開發者」，他會做錯判斷。 identity.py --check 拿實況比對：角色不符報「不一致」、帳號不存在報「absent」， 兩件事分開講（處置完全不同）。

只做精確比對：nobody@powerauto.ai（同網域但不在錨上）⇒ 拒答。 判不出來就拒答，不猜一個預設類別 —— 猜的代價是：一個打錯帳號的 session 拿到「運營者」的四維， 而在它自己看起來完全正常。

§5.3 出處（不是身分）：為什麼不做 session 註冊

決定：身分只到「帳號」這一層，不做 session 級註冊。 同一帳號同時開兩個 session（一個做移植、一個做運營）會拿到同一類的四維 —— 這是有意接受的，不是漏掉的功能。

理由是：能區分兩者的東西（本機檔案、git 操作）本來就擺在那裡， 而且兩個 session 看到的是同一份。再加一層註冊表只會多一份會漂移的真相 （這個 repo 已經為「兩份真相」付過學費）。

所以四維帶上出處，並把「不區分 session」寫成輸出裡的一格：

$ python3 agent_harness/a2a/identity.py --here
出處（★ 這不是身分，是歸因）：
    repo    /Users/alexchuang/Documents/flashkv-devserver
    cwd     /Users/alexchuang/Documents/flashkv-devserver
    HEAD    demo/sweet-spot-windows-fix 22e7cb9919d3
    最近提交 feat(a2a): 身分錨 -- session 屬於哪一類，以及那一類的資產／能力／進度／復盤
    未提交  8 筆（分不出是誰改的：多 session 共用一棵樹）
    錨文件  7 個讀得到、0 個讀不到
    讀數時刻 2026-09-18 17:07:56
    ★ 同一帳號的多個 session 會判到**同一類**（level=none, byDesign=True）

sessionDiscrimination.level 固定是 "none"， 而自測有一格釘住它 —— 免得之後有人偷偷加回一個註冊表、卻忘了改這個宣告。 「分不出是誰改的」那半句也是刻意的：它把 repo 的既有事實（多 session 共寫一棵樹） 放在讀者眼前，而不是讓那個 dirty 清單看起來像「我改的」。

錨文件是四維的來源清單（taxonomy.py／fleet.json／ decisions.jsonl／fleet_export.json／端側的 edge_server.py…）。 缺檔也留在清單裡（標 exists:false）—— 從清單消失會讓 「還沒匯出」與「我忘了檢查」長得一樣。

§5.4 憑證怎麼放

identity.py 的原始碼裡沒有任何 key（它連自己都測這一格）。 憑證只從環境變數或 ~/.config/powerauto/supabase.env（repo 外、chmod 600）讀。 而且它刻意只用 anon key ＋ 各類帳號自己的 JWT，不用 Service Role Key —— 這樣讀到的就是那條路徑真的讀得到的東西，RLS 在雲側那一頭生效。

POWERAUTO_PASSWORD=...                    # 三個帳號共用同一把
POWERAUTO_EMAIL_OPERATOR=alexchuang@powerauto.ai
POWERAUTO_EMAIL_DEVELOPER=developer@powerauto.ai

§6 通道：fleet.json 是「怎麼到達」的唯一真相

§6.3 「拿不到」是最常見的結果，而它不是失敗

fleet.json 的 rules.unknown_not_red 寫得很直白：

§7 自動化：fleet_auto.py —— 三步、三態、一份留痕

需求原話：「要讓這個 pd + agent harness 自動跑」。但自動化有兩個很容易搞錯的前提， 所以這一節先講邊界，再講實作。

§7.1 它做三步，每一步都呼叫既有工具

步做什麼呼叫誰
1. 採集讀 fleet.json 決定來源；對每個端點先試 edge_status.url，失敗再讀 dumpHTTP（--noproxy）／檔案
2. 映射把端點狀態轉成合契約的上報檔report_endpoint_status.py --from-edge-status（同一支，不重寫）
3. 匯出產生給網站吃的資料build_fleet_portal.py --export
為什麼第 2 步一定要呼叫同一支工具：再寫一份映射實作必然漂移， 而漂移是靜默的 —— 這個 repo 已經為此付過學費。 一個第二份實作，等於一個不會報錯的分歧。

§7.2 看門狗：三態，而且「從未啟用」不是紅

$ python3 agent_harness/portal/fleet_auto.py --check       # 看門狗
  健康      ⇒ rc=0
  裝了卻沒跑 / 停擺 ⇒ rc=1（有排程但留痕不新鮮）
  從未啟用  ⇒ rc=0（unknown，不是紅）

第三態是刻意的：「沒裝」與「裝了但壞了」的處置完全不同， 把前者也畫成紅燈，會讓紅燈失去意義。

§7.3 排程，以及「怎麼知道排程真的被觸發過」

§7.4 兩個「自動化會放大」的缺陷（都已修）

① reported_at 原本取「映射時刻」而不是「觀測時刻」。 端點離線三天、dump 今天才被帶回，入口會顯示「它剛剛上報」。 手動跑時人會看時間；定期跑每小時把它抹平一次，就永遠看起來是新的。 現在觀測時刻與處理時刻分成兩格（reported_at / mapped_at）。
② 覆蓋會洗掉人寫的東西（實測踩到）。 第一次端到端跑，一台剛 --no-worker 起來的 edge_server 讓 mac-local 從「3 條能力 ＋ 3 個實測 metrics ＋ 3 條未量測 ＋ GPU 型號」 變成「uptime 2.6s、服務 0 次」—— 用零換掉實質。 現在覆蓋前用 edge_derived 這條界線把人工欄位接過來 （實測已復原：capabilities 2→5、not_measured 3→6、metrics 與 gpu 都在）。

§7.5 它只寫檔，不 commit

這個 repo 多 session 共用一棵樹，自動 commit 會把別人正在改的檔一起推上去。 所以 fleet_auto 的職責邊界是「寫檔 ＋ 留痕」， 而「要不要 commit」留給人。

留痕與日誌也刻意放在版控之外：auto_runs.jsonl 進 .gitignore， 日誌在 ~/Library/Logs/powerauto/（repo 外）—— 否則 git status 的雜訊會掩蓋真正的變更。

§8 pd 子系統：gRPC 的推理面，以及它與 A2A 的關係

agent_harness/pd/ 是 prefill/decode 分離的推論子系統。 它住在 agent_harness/ 底下是歷史原因（整併時一起進來的），不是設計。

§8.1 PDService 的 14 個 rpc

分組rpc管什麼
KV 管理AllocateBlocks · StorePrefixKV · GetPrefixKV · InvalidatePrefixKV 區塊配置與前綴快取的存／取／失效
DOPD handoffPrepareHandoff · CommitHandoff · ResumeDecode · AbortHandoffdecode 從一個節點交接到另一個節點的四階段
引擎命令ExecuteCGCCommand · ExecuteKDAForward · UpdateKDABasisCGC／KDA 的指令與前向
狀態QuerySessionState · HealthCheck會話查詢與健康

§8.2 整合方式：不改它

決策：A2A 閘道不動 pd 的 gRPC。pd 在協議上只是 pd-inference 這個 agent 的身分，閘道做的是 「A2A → gRPC」的映射。

這樣做的理由是職責邊界：pd 是引擎側元件， 把 agent 語意（類別、macro、卡片）混進推理服務，會讓兩邊的變更節奏綁在一起。

而 registry.json 的 not_capable 也誠實地寫出了目前的缺口：

「它的後端是 gRPC 的 pd_server，本閘道只做 A2A 到 gRPC 的映射 —— 沒有把 PDService 的每個 rpc 都翻譯過來。」 ⇒ 目前 pd-inference 的能力是它的身分，不是它的全部 rpc。 說「整合完成」會是假的。

§8.3 共用的一支：pd/compute_sharing.py

fleet.json 的 heartbeat 指的就是它 （--role node --port 9100 開 /v1/compute/status）。 它是「這台機器有多少算力」的活著探測，與 /v1/edge/status （「這台機器現在是什麼狀態」）是兩件事，兩個埠，兩條路。
