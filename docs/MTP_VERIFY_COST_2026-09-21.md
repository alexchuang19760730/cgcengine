# MTP verify 的成本：機制量化與 k 掃描

日期：2026-09-21　承 `docs/S0_MTP_ONOFF_AB_2026-09-21.md`（§EN-367）
工具：`Backup/phase_decomp/k_sweep_ab.py`（新寫）　原始資料：`Backup/phase_decomp/spec_onoff/k_sweep.json`

---

## 0. 結論先講

1. **「verify 是好幾倍」是單位混用**：一輪 verify 的**牆鐘**是一步普通 decode 的 **3.44×**，
   但一輪吐 **3.197 個 token** ⇒ **每 token 只貴 8%**（99.3 vs 92.2 ms）。
2. **機制確認**：每步的專家 union 從 **8.19 長到 18.09**（**2.21×**），池裝不下 ⇒
   命中率 **96.5% → 57.5%**、bytes/token **×2.12**。這就是成本來源。
3. **但把它修掉沒有用**：k 掃描（k=0/1/2/3，12 臂配對）**沒有任何 k 贏過 MTP off**
   （`best_k = 0`）。⇒ 「降 k 換速度」**REFUTED**。
4. **draft head 不是兇手**：24.7 ms/輪 = 該輪的 **7.5%**。
5. 整個 MTP 軸可優化的量 ≈ **7%**，天花板 **10.8 t/s**。**不是通往 25 的路。**

## 1. 先把「幾倍」拆成兩個單位

`--temp 0`（prod25 的 MTP 臂會帶）⇒ 接受率很高，一輪吐 **3.197 / 最多 4** 個 token。

| 量 | 普通 decode（一步） | MTP verify（一輪，k=3） | 比值 |
|---|---|---|---|
| 牆鐘 | 92.2 ms | **317.4 ms** | **3.44×** |
| 產出 token | 1.000 | 3.197 | 3.20× |
| **每 token** | **92.2 ms** | **99.3 ms** | **1.08×** |

⇒ 拿「一步」比「一輪」會得到 3.44 倍；拿「每 token」比只有 **1.08 倍**。
兩個數字都對，問題在分母。

---

## 2. k 掃描（唯一隔離 `--spec-draft-n-max` 的實驗）

設計：prod25 / llama-bench / `-d 512` / `--reps 3` / **3 對配對、旋轉順序、12 臂**。
四臂只差 `--spec-type draft-mtp --spec-draft-n-max k`（`--dry-run` 驗證過）。
開啟 `CGC_MTP_PERF=1` 以取得引擎自己的 union 計數與 draft head 計時。

| k | union/(層,輪) | draft head ms/輪 | emit/輪 | t/s（中位，3 樣本） | step ms | **ms/token** |
|---|---|---|---|---|---|---|
| 0 | 8.19\* | – | 1.000 | **10.845**（10.707 / 10.845 / 11.035） | 92.2 | **92.2** |
| 1 | 12.94 | 10.9 | 2.000 | 10.320（9.244 / 10.320 / 11.305） | 193.8 | **96.9** |
| 2 | 15.86 | 18.1 | 2.725 | 10.809（10.688 / 10.809 / 11.335） | 252.1 | **92.5** |
| 3 | 18.09 | 24.7 | 3.197 | 10.072（7.152 / 10.072 / 12.521） | 317.4 | **99.3** |

\* k=0 沒有 MTP fast path 計數器，8.19 取自 OFF 臂 `requests/(384 token × 41 層)`。

**讀法**：union 隨 k 單調成長（機制成立），但 **ms/token 全場平坦在 92–99（±8%）**
⇒ **MTP 在這個形狀下每 token 一個都沒省**。

熱標：k=3 第三對是 HEAVY/HEAVY（7.152），兩對 NOMINAL。中位數已吸收。

## 3. 機制的硬證據（引擎自己的計數器，ON/OFF 同一輪）

| | OFF（k=0） | ON（k=3） | |
|---|---|---|---|
| union/(層,輪) | 8.19 | **18.09** | **2.21×** |
| 池命中率 | **96.5%** | **57.5%** | −39 pp |
| capacity miss 佔比 | 12.1% | **26.1%** | ×2.2 |
| **超過容量的層數** | **6** | **28** | ×4.7 |
| 最壞層 distinct / slots | 201 / 143 | **245 / 143** | 需 1.71× |
| file reads（jobs） | 27,240 | 40,908 | ×1.50 |
| bytes/token | 12.4 MB | **26.3 MB** | **2.12×** |

⇒ MTP 把每層的工作集推過池容量 ⇒ **capacity thrash**。
要救回 96.5% 需要 **245/143 = 1.71× 的池 ≈ 13.6 GB** ⇒ **16 GB 上做不到（硬牆，已量化）**。

### 3.1 ZERO-slot 從沒啟動

```
MTP fast path: calls=7913 union=140086 cold(ZERO)=0 (0.0%)
               verify: calls=7553 union=137206 cold=0 (0.0%)
verify-strict: refused=0  zero_mapped_selected=0
```

- 好消息：**沒有品質損耗**（沒有專家被讀成零）。
- 壞消息：代表 **cold guard（`CGC_FAST_COLD_MAX` 預設 0.30）一值把 verify 打回 blocking
  `ensure_batch`**（cold ≈ 42% > 0.30）⇒ **verify fast path 在 MTP 下實質上沒在跑**。
- 調高 `CGC_FAST_COLD_MAX` 可留 fast path，但 cold 專家會被 ZERO-map ⇒ 有損，不做。

## 4. 預註冊判準的結果（誠實記錄）

判準在跑之前寫在 `k_sweep_ab.py` 檔頭：

| # | 判準 | 結果 |
|---|---|---|
| 1 | 機制：成本 ∝ union 寬度 | **CONFIRMED**（union 8.19→18.09 單調；k=3 處 2.21× vs §EN-367 的 marginal 2.23×，吻合 0.5%） |
| 2 | 槓桿：縮小 k 買得到速度 | **REFUTED**（`best_k = 0`，沒有 k 贏過 MTP off） |

⚠️ **判準 1 的公式本身寫錯了**：我用 `(step(k) − step_off)/k` 當 marginal，誤差 0.24 / 0.50 / 1.33。
原因：它把 **draft head**（10.9–24.7 ms）與 **`emit/round ≠ 1+a·k`**（本輪 `--temp 0` 實測
3.197，MTP 模型用的是 2.611）混進同一個平均。**正確讀法是增量**：

```
verify(k) = step(k) − draft(k)   →  182.9 / 234.0 / 292.7 ms（k=1/2/3）
增量 per 新增位置                 →  90.7 / 51.1 / 58.7 ms
plain batched 增量（§EN-363）     →  27.3 ms
```

⇒ 每多一個位置，MTP verify 付 **51–91 ms**，plain batching 只付 **27.3 ms** ⇒ **1.9–3.3×**。

## 5. 能不能優化？

| 手段 | 可得 | 可行性 |
|---|---|---|
| 降 k（縮 union） | 0（實測 `best_k=0`） | ✅ 已測，無效 |
| 消滅 draft head | +7.5% | ✅ 已測，只佔 7.5% |
| 池加大到 1.71×（13.6 GB） | 未知上界 ~7% | ❌ 16 GB 做不到 |
| 調高 `CGC_FAST_COLD_MAX` 留 fast path | 未知 | ❌ 有損（ZERO-map ⇒ 0000 garbage 機制） |
| prefetch | — | ❌ 本輪 `prefetch=390/79`，OFF 只 `79/0`，近乎失效 |

⇒ **這個軸全部加起來 ≈ 7%，天花板 10.8 t/s，離 25 差 2.3×。**

## 6. 唯一的新線索（未驗證，下一步）

既有標定點（§EN-363）：**同一條序列的 B=4 ubatch = 167.81 ms ⇒ 42 ms/token**。
本輪：**MTP verify 4 個位置 = 317.4 ms ⇒ 99.3 ms/token**。

**同樣 4 個位置、同一個模型：一個攤得動（42 ms/token），一個攤不動（99.3 ms/token）——差 2.4×。**
這 2.4× 目前**沒有任何儀器指到它**。

最便宜的下一步（單臂，~2 分鐘）：在**現行 build** 重測一次 plain B=4 ubatch。

- 仍是 42 ms/token ⇒ 那 2.4× 是 **MTP verify 路徑本身的缺陷**，是真正的槓桿；
- 也退化到 ~99 ⇒ §EN-363 的 167.81 是另一個 regime，沒有缺口，**MTP 軸就此結案**。

⚠️ 既有 167.81 是舊 build 的標定點，本輪未重測 ⇒ **不要直接相減引用**。

## 7. 對 decode 25 的判決

不變，但更硬：MTP verify 的代價**完全歸因**（union 變寬 ⇒ 池 thrash），
而**歸因之後發現修不好也救不了** —— 因為關掉 MTP 也只有 10.8 t/s。

**8.8× 的開銷在 `S0 = 92 ms/token` 本身**，MTP 從頭到尾沒動過它（92–99 ms/token 平坦）。
