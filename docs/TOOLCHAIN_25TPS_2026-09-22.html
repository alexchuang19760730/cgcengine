這些工具解決的是同一個病：把「非結論」講成結論。這個 repo 反覆吃過四種： 手打的表格（有一次出貨時重複了一個 key、漏了另一個）、缺席被當成 0（「沒有 miss 軸」被讀成「沒有相關性」）、 跨 regime／跨 harness 的數字並排、以及啟動順序與 swap 漂移被當成效果。 六支工具各自的 拒算規則就是針對這四種寫的，而那比它們印出來的表更重要。

1. gap_vs_miss.py —— 共用的逐層解析器 445 行 · 11/11 自測

一層的 decode 空窗，是它的 miss 數買來的，還是固定的每層成本？

它是整條鏈的地基：把一份 server log 變成三條逐層序列，供上面所有工具匯入使用。

序列來源行語意
idle_hostCGC-GAPSPLIT-L每層每圖的 CPU 空窗（hook + tail + submit）
cb / wait / submitCGC-DECPROF alltop-k hook（gather）／eval-sync／派送
missesBATCHDBG每個 ensure_batch 的 miss 數（misses=N）

三個總量規則，全部是量出來的而不是假設的：

  • 相位邊界＝最後一條 CGC-POST:。在 223046 那份 log 上，這條線把 2331 次 fill 中的 1334 次（與 59% 的 miss）移出 decode 母體 —— 跨相位擬合基本上就是在做 prefill 迴歸。
  • 圖身分：log 裡有 segs=41（41 層圖）與 segs=2（MTP draft 圖，單層）兩族。非 41 段的列被排除並計數，prefill 區的列也是。兩種排除都會印出來。
  • 中位數而非平均：同一層的列跨 0.02–194 ms，平均數是「這輪最慢那張圖」的陳述。因此它也另外保留 *_mean 變體，讓「邊際成本」可以用平均（邊際成本不會出現在中位數上）。

拒算：缺 BATCHDBG ⇒ INVALID（不是「無相關」）；缺 CGC-POST 邊界 ⇒ INVALID（相位未知）；完全沒有列 ⇒ INVALID 並附理由。三條都有自測，其中一條刻意檢查「即使另外兩條序列擬合得很漂亮也必須 INVALID」。

python3 scripts/check/gap_vs_miss.py --log Backup/cgc_logs/llama_server_YYYYMMDD_HHMMSS.log
python3 scripts/check/gap_vs_miss.py --selftest        # 11/11

模組介面：parse(path) -> (series, meta)。

2. mtp_k_sweep.py —— 在一個窗口內量完整條成本曲線 594 行 · 33 項自測

多一個 verify token 要多少 ms —— 而這件事能不能在同一個 harness、同一個窗口內量到？

起因是 draft_budget.py 的擬合只有兩個點、且來自兩個不同 harness（llama-bench 的 OFF 臂 vs server 的 k=3）： 兩點兩參數、零自由度，它描述資料但不能檢驗資料。這支驅動去補那些缺的點，而且是一次補四個。

旋鈕：CGC_SERVER_MTP_N_MAX（run_server.sh 轉成 --spec-draft-n-max），已用 CGC_DUMP_ENV=1 驗證它真的落到 bench 行程的 ARG 行。

instrument：引擎自己就印 CGC-MTP-PERF（common/speculative.cpp:3012，由 CGC_MTP_PERF 打開）：

CGC-MTP-PERF type=draft-mtp calls_begin=... calls_draft=... gen_tokens=... acc_tokens=...
             t_begin_ms=... t_draft_ms=... t_accept_ms=... acc_rate=...
             gen_tok_per_round=... acc_tok_per_round=... emit_tok_per_round=... ms_per_round=...

計數器是累積的 ⇒ 一次 run 的最後一行就是該 run 的總計（原始碼自己這樣寫）。有這行就不必再跑 n-gram 消融去做初步歸屬 —— 消融因此降級成「交叉檢查同一個計數器」，不再是發現步驟。

協議：每 rep 輪替臂序（rep1: k1,k2,k3,off；rep2: k2,k3,off,k1…），因為這個專案已多次證明「啟動順序主宰」。 每臂記錄 engine digest、窗口樣本、池統計，以及完整的 stderr（<stem>.stderr.log，CGC-MTP-PERF 就在那裡）。

拒算：盒況不足（--min-usable-pct，預設 30%）不開跑；跑到一半被搶走會落下紀錄； 而一條 INVALID 的紀錄不算「這臂做完了」（否則重跑會跳過失敗的臂 —— 這是實際修過的 bug）。

python3 scripts/check/mtp_k_sweep.py --reps 3 --logdir /tmp/mtp_k_sweep
python3 scripts/check/mtp_k_sweep.py --report-only --logdir /tmp/mtp_k_sweep   # 只重算報告，不重跑
python3 scripts/check/mtp_k_sweep.py --extra-env CGC_MTP_PERF=1,CGC_DECODE_PROFILE=1
python3 scripts/check/mtp_k_sweep.py --selftest

報表用「同 rep 內配對」，不用池化。修好之前的 bug 之一：run["rows"] 在 --json 路徑永遠是空的， 於是有個臂明明量到 11.13 t/s 卻被報成「0 samples」。守門拒絕是對的（寧可 INVALID 也不要假 0），來源是錯的。

3. verify_marginal.py —— 邊際 verify token 的三路拆分 553 行 · 30 項自測

那 61 ms/token 的黑盒子（「target verify + host」）裡，是 miss、是 matmul、還是主機路徑？

三個機制先驗可分辨，且指向三種不同的工作：miss-driven（槓桿＝覆蓋率／路由局部性）、 compute-driven（槓桿＝verify 的 op 路徑）、host-driven（槓桿＝批次化主機路徑）。

設計：兩臂唯一差別是 verify 寬度（k=1/T=2 vs k=3/T=4），三條軸各自量，全部換算成「每回合」再差分除以 ΔT。

marginal_total   = (round_ms(T=4) - round_ms(T=2)) / dT        CGC-MTP-PERF
marginal_miss    = (miss/round(T=4) - miss/round(T=2)) * PER_MISS_MS / dT   BATCHDBG
marginal_compute = (vop_us/round(T=4) - vop_us/round(T=2)) / dT / 1000      CGC-VERIFY-OP

PER_MISS_MS = 0.695 是借來的外部常數（F1 的定律，範圍 0.59–0.85 一併標註），工具會把它印在表頭。

它印出來的東西：三路拆分表、MEDIAN shares 與一條 RULE -> 判定、 逐層 miss 的集中度（前 8 層佔 |miss delta| 的多少）、逐層 marginal（三軸 + miss + 殘差）、 以及 rep 1 的 round budget 收斂表與每一個可用 rep 的收斂表。

拒算（全部命名的拒絕，不是空表）：缺相位邊界、缺 miss 軸、目錄為空、兩臂回合數相同、 該臂完全沒有逐層列 ⇒ exit 1 並說出原因。自測裡就有一條「該臂沒有 DECPROF 時必須具名拒絕，而不是靜默回傳空表」。

python3 scripts/check/verify_marginal.py --logdir /tmp/verify_layers
python3 scripts/check/verify_marginal.py --logdir /tmp/verify_marginal --per-miss-ms 0.695
python3 scripts/check/verify_marginal.py --selftest

必須跟著這些數字一起讀的儀器陷阱：CGC_VERIFY_OP_TIMING=1 與 DECPROF／GAPSPLIT 家族 互斥。前者讓 expert-cache 的 callback 在 verify 的 MUL_MAT_ID 節點上答 ask=true， 於是那些節點走逐節點的 exact 路徑，分段式 async 派送器整條不跑 （同一 run 內：CGC-VERIFY-OP 4096 列 + BATCHDBG 5647 列，而 CGC-SEG / CGC-DECPROF / CGC-GAPSPLIT-L / CGC-GPUTIME 全為 0）。總量上也看得出來：那一對的回合是 396/684 ms， 而未上儀器的那對是 273/352。⇒ 三路拆分的佔比是定性的，逐層那組來自另一對。一次 run 不可能兩者兼得。

4. target25_grid.py —— 必要條件階梯（兩個模式） 267 行 · 14/14 自測

25 t/s 到底需要什麼？而「需要」有一個逐階可查的答案嗎？

兩個模式是刻意的，因為兩個 regime 的 step 分解不同，混用就是這條線一直在付的代價：

模式輸入step 軸誰會用
--log PATH（預設）一份 server-regime log 遮掉多少主機端 gap（cb hidden → union floor） 沒有 MTP 配對時的舊軸
--from-pair DIRk 掃描的 arms.jsonl（需 k1 + k3 兩臂） 實測的 round 預算：每往下一階＝移除一個實測項 MTP 開啟時唯一有意義的軸

表怎麼算：needs mean_len = 25 × step/1000；needs alpha 是讓幾何 E = 1+a+a²+a³ 達到該 mean_len 的每-draft 接受率（二分法解）。impossible ＝ 連 α=1 都不夠 —— 那個 None 正是這張表的重點：它是任何接受率都到不了的格。

alpha=1 的邊界說明寫在自測裡：alpha=1 正好吐 k+1 個 token、alpha=0 正好吐 1 個、 alpha=0.5, k=3 吐 1.875 —— 而 required_alpha 對 want 必須單調。

自測裡最有價值的四條：「地板以上每一階都需要超過上限的 mean_len」、 「上限以上不存在任何 α」、「階梯的最後一階就是 eval-sync 鏈」、以及「配對不齊 ⇒ INVALID，不是一張空表」。 另有一條把 gpu_busy_sum 與 union_sum 分開（前者「重疊算兩次」不是地板 —— 這條曾經出錯過一次並被撤回）。

python3 scripts/check/target25_grid.py --selftest
python3 scripts/check/target25_grid.py --from-pair /tmp/verify_layers          # round 預算階梯
python3 scripts/check/target25_grid.py --log Backup/cgc_logs/llama_server_20260920_023021.log
python3 scripts/check/target25_grid.py --from-pair /tmp/verify_layers --k 4    # 換寬臂

5. draft_budget.py —— accept 軸值多少 215 行 · 7/7 自測

一旦確認批次不會攤薄，最佳 verify 寬度 k 是多少？而 accept 單獨的天花板在哪？

舊模型是 S = E / (1 + m·k_eff)，把 m 當一個不透明的數，並假設批次有些攤薄。 shape_roofline.py 在 kernel 層量到相反的事實：n=1..4 在我們確切的 MoE 形狀上，每-token 成本是平的 （iq2_s 60.22 → 57.48 µs/token、+4.6%；iq3_s 98.86 → 102.56、−3.7%）。 每個 token 帶自己的 top-k ids ⇒ 每個 token 都要重讀自己的 experts；批次只買到列數，沒買到頻寬。

於是成本律對 token 數 T 是嚴格仿射的：

cost(T) = C_fixed + c_tok * T
  T=1（MTP off）：S0 = 93.3 ms        docs/S0_MTP_ONOFF_AB_2026-09-21.md
  T=4（MTP on k=3）：247.98 ms        docs/TARGET25_TWO_AXIS_2026-09-20.md
  ⇒ C_fixed 41.74 ms + c_tok 51.56 ms * T   （kernel 8.36 = 16.2%，其餘 43.20 = 83.8%）

七項自測裡有兩條專門守住這個擬合的誠實性：k=0 必須精確回推 S0； 以及 alpha=1 的天花板是 per-token 項而不是固定項（19.39 t/s）。

它回答的三個問題：① 每一個 k 要打平需要多少 accept（k=1:0.553 → k=7:0.851，單調上升）； ② 給定 α 哪個 k 最好（α ≤ 0.8 時是 k=1，只有 α ≥ 0.9 才輪到 k=3）； ③ accept 軸自己的天花板與 kernel 的必要性。

python3 scripts/check/draft_budget.py --selftest
python3 scripts/check/draft_budget.py --ratio 0.889 --ratio-k 3      # 同 harness 比值反解 alpha
python3 scripts/check/draft_budget.py --s0 93.3 --step-t4 247.98

「同 harness 比值反解」是這支工具的關鍵設計：ON/OFF 來自同 harness、同 shape、只差 --spec-type， 所以比值不帶跨 harness 誤差。把 0.889 反解 ⇒ α = 0.654， 低於 k=3 的損益平衡 0.731 ⇒ 今天 k=3 是淨虧，而最佳 k 是 1（11.42 t/s = 1.066×）。 兩個點來自不同 harness 這件事則必須標在臉上：# 2-point fit: describes, does not test。

四、共同紀律（六支工具共用的六條規則）

規則在哪裡被強制它防的是哪種錯
缺席不是 0 gap_vs_miss 對缺 BATCHDBG 給 INVALID；mtp_k_sweep 的 pool_stats 對「不存在」回空而非零 「沒有 miss 軸」被讀成「沒有相關性」；「讀錯 key」被讀成「0 samples」
只有一個解析器 target25_grid → verify_marginal → gap_vs_miss 單向依賴 兩份 regex 對同一份 log 給出兩個答案（這個 repo 已有「兩個可用記憶體定義」的前例）
同 rep 內配對 mtp_k_sweep 的 --report-only 報表；verify_marginal 逐 rep 差分 1.5× 的 rep 漂移被當成效果；啟動順序被當成自變數
regime 不混 target25_grid 的兩個模式互斥；verify_marginal 的相位邊界 把 prefill 的 miss 混進 decode 母體；把 llama-bench 的數字與 server 的並排
拒算優於猜測 shape_roofline 的未知型別／缺形狀；target25_grid 的配對不齊；verify_marginal 的五種具名拒絕 靜默代換後的表格比沒有表更糟
產物帶身分 mtp_k_sweep 逐臂記錄 engine digest + 窗口 + 池統計 + 完整 stderr 「這個數字是不是另一顆 binary／在超訂的盒況下量的」無法從產物回答

六、邊界

  • 絕對值綁窗口。已量到的配對是在 swap 4.5–6.8 GB、usable 39.9–63.9%、部分臂 thermal HEAVY 下取得的。 比值與表形狀耐受漂移；t/s 絕對值不可與乾淨的 12.57 家族並排。
  • 兩點兩參數的擬合只描述、不檢驗。draft_budget 的 cost law 自由度是 0； 支持「仿射形式」的不是它的算術，而是獨立的 kernel 量測（n=1..4 線性、截距≈0）與 k=0 能精確回推 S0。 檢驗方法補了第三、第四、第五個點（mtp_k_sweep）。
  • remainder 是相減出來的，所以它的大小只跟同一臂的 per-layer 均值一樣好； 它的內部切分（lm_head／sampler-argmax／accept 路徑／圖與圖之間的宿主簿記）仍未量測。 可否證的預測已寫下：那段區間應該量到 T=4 ≥ 100 ms/round、T=2 ≤ 10 ms/round。
  • M1/M2/M3 閘門不在這條鏈裡。這些工具全部只讀既有日誌或只改環境變數 ⇒ 不重建引擎。 engine digest 逐臂記錄，但「逐位元一致」的宣稱要另外跑那套閘門才成立。
  • test-backend-ops 的 perf 模式有自己獨立的一份 case 清單（make_test_cases_perf）； 測資要加在那一份。eval 清單裡有一份被 #if 0 關掉的複製品，會誤導人。
