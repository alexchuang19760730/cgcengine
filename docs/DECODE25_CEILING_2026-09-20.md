# decode 25 t/s 的天花板（2026-09-20 定案）

問題：「25 到底有沒有機會」。答案分兩層：**k=3 交付形狀下沒有機會；放寬 k 之後仍差
約 1.7% 到不了**。下面全部用同一輪、同臂、哨兵認可窗口的讀數，不再跨 run 組合商數。

## 1. 這一輪的讀數（23:09，gate OK，sentinel HEALTHY 265.90 / floor 239.28，thermal NOMINAL）

| 量 | 值 |
|---|---:|
| `union_sum` | **106.91 ms** |
| `step_decprof`（DECPROF work-row median） | 167.81 ms |
| `step_round`（實付週期 = mean_len / tps） | **207.8 ms** |
| mean_len（measured 段） | **2.025** |
| bench t/s（此盒此輪） | 9.7448 |
| `n_gen` / `avg_ns` | 64 / 6.574 s（warm-skip 64 ⇒ 只計後 64 token） |

`union_sum 106.91` 落在分支 B 帶（98–110）的邊緣，但 `step_round 207.8` 遠高於分支 B 假設的
122 —— 也就是**分量的讀數支持分支 B，而週期的讀數不支持**。這個不一致本身就是結論的一部分
（見 §4）。

## 2. mean_len 的雙 regime（本線第三次踩到，這次被量化）

工具直算 `384 tok / 284 verify row = 1.352`。但用 `step_round` 反推只有兩個可能：

- 用 1.352 ⇒ `step_round = 138.7 ms` < `step_decprof = 167.81 ms`。**物理矛盾**（一個週期不可能
  比它自己的 graph_compute 窗口還短）⇒ 1.352 是壞商數。
- 用 2.025 ⇒ `step_round = 207.8 ms` > 167.81 ✓ 自洽。

分離後完全對上：measured 段 64 tok/rep 用 31.6 round/rep ⇒ **ml = 2.025**；
warmup 段 64 tok/rep 用 63.1 round/rep ⇒ **ml ≈ 1.015**，即 **MTP 在 warmup 段幾乎完全失效**
（每輪只接受 1 個 token）。整體 1.352 是這兩個 regime 的加權平均。

⇒ **`--warm-skip` 不只是「跳過計時」，它跳過的是一個接受率完全不同的母體。**
任何把 warm-skip 0 與 warm-skip 64 的數字混用的推導都無效（這正是先前「分支 B 邊緣可達」
那個結論的來源）。

## 3. 天花板（S0 與 m 由本輪同 run 反推）

`step_round(3) = 207.8 ms`，`C = 1 + m·k`，`m = 0.474`（bench 實測）⇒
**`S0 = 207.8 / 2.422 = 85.8 ms`**（k=0，即無 MTP 單 token 的成本 = 11.66 t/s）。

`t/s(k) = 1000 · mean_len(k) / (S0 · (1 + m·k))`，且 `mean_len(k) ≤ k+1`（硬上界）。

| k | 現況 a=0.537 | 完美接受上界 a=1.0 |
|---:|---:|---:|
| 1 | 12.16 | 15.81 |
| **3（交付形狀）** | **12.57** | **19.25** |
| 5 | 12.75 | 20.75 |
| 8 | 12.89 | 21.89 |
| 16 | 13.03 | 23.08 |
| 32 | 13.12 | 23.79 |
| 64 | 13.16 | 24.18 |
| ∞ | — | **24.59** |

三條判死線：

1. **k=3 判死**：即使 `a=1.0`（每輪全接受，`mean_len` 達到硬上界 4）也只有 **19.25 t/s**。
   要 25 需要 `mean_len ≥ 207.8/40 = 5.20`，而 k=3 的上界是 4 ⇒ 無解。
2. **加深 k 判死**：`a=0.537 < m=0.474`… 實為 `a` 與 `m` 同階 ⇒ 曲線從 k=1 到 64 只從
   12.16 走到 13.16（**+8%**）。MTP 加深不是這條路的槓桿。
3. **極限判死**：`k→∞` 且 `a=1.0` 的極限是 `1000/(S0·m) = 24.59 t/s < 25`。
   兩個條件各自都不現實，一起成立仍差 **1.7%**。

## 4. 要真的過 25，只有兩條路（都要動到「每 draft token 的固定代價」）

| 路 | 需要 | 現況 | 幅度 |
|---|---|---|---|
| 降 `m`（每 draft token 的攤薄係數） | k=3 需 `m ≤ 0.073`；k=8 需 `m ≤ 0.184` | 0.474 | **降 61–85%** |
| 降 `S0`（無 MTP 單 token 成本） | `S0 ≤ 43.1 ms`（= 無 MTP 也要 23.18 t/s） | 85.8 ms | **×0.50** |

`m` 的機械解釋已知：每多一個 draft token 約 46–59 ms 的固定代價（`k_eff` R²=0.842，
pool budget 的主項）。也就是說，**25 的門票不在 dispatcher、也不在 k，而在 expert cache pool
的每 token 成本**。這與 §EN-350 的 `cb` 分量、與線 I 的快取命中儀器是同一個靶。

## 5. 結論與建議

- **25 t/s 在 k=3 交付形狀下數學上不可達**（天花板 19.25，差 1.30×）。不是工程餘裕問題。
- **放寬 k 也救不了**（極限 24.59）。
- prefill 250 已達成（281.51 NOMINAL），不受本結論影響。
- **建議改寫目標**：
  - 保守且可交付：**16 t/s**（指名槓桿總和 +5~10% ⇒ 12.57 → 13.2–13.8；再往上要靠 `m`）。
  - 或改配方：把 `m` 降 61% 以上（k=8）才能談 25；在 `m` 沒動之前，任何「把 k 加大」
    或「融合 kernel 省 dispatch」的工作都不會讓 25 成立（G4 已證實單次 dispatch 只 0.0736%）。
- **別再做**：跨 warm-skip regime 混用數字；用 `union_sum` 單一分量推導可達性
  （本輪 `union=106.91` 支持分支 B，但 `step_round=207.8` 否證它）。

## 6. caveats

- binary 是 22:16 建置，樹上有別條線未提交的 `process_ubatch` / `expert_cache_on_topk` 改動
  （+191 / +380 行，熱路徑）。本輪量的是**建置產物**，不是工作樹。
- `S0` 與 `m` 是同 run 反推，非直接量測；`m=0.474` 取自先前 bench 的 cost 曲線（不同 run）。
  若 `m` 實際較小，`S0` 會較大、極限會更低；若 `m` 較大，則結論更悲觀。方向不變。
- 此盒此輪 `usable 59.2% / free 6.37 GiB`，不是最乾淨的狀態；交付記錄 12.57 是在更好的窗口。
  用 12.57 反推會得到 `step_round ≈ 161 ms`，k=3 天花板變成 24.8 —— 仍 <25，但擦邊。
  ⇒ **若要推翻本判決，唯一的方法是量到「同一 run 內 t/s ≥ 12.57 且 step_round ≤ 160 ms」**。

## 7. ★ 物理頻寬帳（23:2x 追加）——上面那個「天花板」是條件性的，不是物理定律

§3 的天花板全部建立在「`m` 與 `S0` 不變」之上。把它們視為可變，就要先問：
**85.8 ms 裡面有多少是物理下限？** 答案是：很少。

機型 `Mac16,12`（MacBook Air M4，統一記憶體頻寬取規格值 120 GB/s）；
模型 `Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS`，檔 13,663,116,512 B = **12.72 GiB**，
35B 總參數 ⇒ **3.12 bpw**；A3B ⇒ 每 token 激活 3B ⇒ **每 token 必讀 1.171 GB（1117 MiB）**。

| 情境 | ms/token | t/s |
|---|---:|---:|
| 100% 命中 RAM（**帶寬物理上限**） | **9.76** | **102.5** |
| 100% 走 SSD（Air NVMe ~3 GB/s） | 390 | 2.56 |
| **實測 `S0`** | **85.8** | **11.66** |

⇒ **峰值頻寬效率只有 11.4%，離物理上限還有 8.8×。** 25 t/s 只需要 40 ms/token，
也就是 29 GB/s 的有效頻寬 = 峰值的 24%。**所以 25 不是被物理頻寬擋住的。**

### 那 85.8 ms 是什麼？

用 `t = bpt·[(1−f)/BW_ram + f/BW_ssd]` 反推（`f` = 每 token 讀取量落到 SSD 的比例）：

- `f = 20.0%` ⇒ **85.9 ms / 11.64 t/s**，與實測 `85.8 ms / 11.66 t/s` **吻合到小數點後一位**。
- 25 t/s（40 ms）⇒ **`f ≤ 7.9%`**；16 t/s ⇒ `f ≤ 13.9%`。

⚠️ `f` 是**等效** miss 率：它把全部非理想開銷（SSD miss、dequant、GPU kernel 效率、dispatch）
都折算成「等效慢速流量」，所以 **20% 是上界解釋** —— 真實的 SSD miss 率可能更低，
剩下的算在 dequant／kernel 效率上。但結論的方向不受影響：**25 的門票是把「每 token 等效慢速
位元組」從 20% 降到 8%。**

### 為什麼會 miss —— 16 GB 這台機器的牆

模型 **12.72 GiB** vs `expert-cache pool` **8 GiB** ⇒ **有 4.72 GiB 裝不進池，只能待在 SSD**。
而 SSD 比統一記憶體慢約 **40×**（3 vs 120 GB/s），所以只要一小部分讀取落下去，就把
9.76 ms 拉到 85.8 ms。這也是 `cb` 分量對記憶體水位敏感（74.18 vs 11.26，6.6×）的機制。

⇒ **「A3B 35B、10 多 GB，為什麼 16 GB Air 跑不到 25」的答案**：
不是算力不夠、也不是頻寬不夠（上限 102 t/s），而是 **12.72 GiB 的模型塞不進 16 GB 機器能給
的 8 GiB 池**，每 token 約兩成的權重讀取掉到慢 40× 的 SSD 上。

### 因此判決要改寫

- ~~「25 數學上不可達」~~ → **「25 在當前的每 token 讀取效率（11.4% 頻寬）下不可達」**。
- 它是**效率工程問題，不是物理限制**。§3 的 19.25 / 24.59 天花板是「`m`、`S0` 凍結」時的算術，
  而 `m`（每 draft token 46–59 ms）與 `S0`（85.8 ms）正是這個 miss 率的函數。
- **真正的槓桿排序（按量級）**：
  1. 讓模型整包進池：bpw 3.12 → **≤1.96**（IQ2_XXS 級），或模型 ≤ 8 GiB —— 單一最大槓桿，
     理論直達 ~100 t/s。
  2. 換 ≥ 19–24 GB 記憶體的機器（模型 12.72 GiB + KV + 系統）。
  3. 提高 prefetch／專家局部性命中（軟體，線 I 的 `cb` 儀器就在這個靶上）——把 20% 往下壓。
  4. 降每 token 激活參數（改配方）。
- 相較之下，kernel 融合／省 dispatch（G4 實測單次 dispatch 僅 0.0736%）量級完全不夠。

### caveats

- 120 GB/s 是 M4 Air 的**規格值**，未實測；若實為 100 GB/s，`t_ram = 11.7 ms`、上限 85 t/s、
  反推 `f = 19.6%` —— 結論不變。
- 每 token 1.171 GB 假設「激活 3B 全部要讀」；MoE 的 dense 部分是每 token 必讀、專家是 top-k，
  A3B 的 3B 已含此。若實際激活量不同，`bpt` 等比縮放，`f` 的結論不變。
- Metal 的 dequant、attention、dispatch 開銷未被單獨建模（併入等效 `f`）。

## 8. 「3（prefetch／局部性）與 4（改配方）有沒有機會」——用**實測 miss** 重算

§7 的 `f` 是反推的等效值；本節改用**直接量測**，結論因此改變。

### 8.1 結構與實測

讀 gguf 元數據：`qwen35moe`，**41 層 / 256 專家 / top-8 / expert FFN 512 / emb 2048**，
總參數 35.51 B，其中**專家 ≈ 33 B（93%）**、attn 1.06 B。
⇒ 每 token 專家讀取 = 41×8×3.1M = 1.017 B 參數 ≈ **381 MB**（佔 1.171 GB 的 33%），
dense（attn＋shared）≈ **790 MB，常駐 RAM、不受 miss 影響**。

- **實測 miss 率 22.4%**：`hits=28584 misses=8246`（與 §7 反推的 20% 互證）。
- 線 I 的 F1（`docs/F1_CB_MISS_REGRESSION_RESULT_2026-09-20.md`）：每 step **73.83 個 miss ×
  0.695 ms = 51.3 ms**（`cb` 的 77%）＋**每層 barrier 12.86 ms/step**（只要該層有 1 個 miss 就付，
  對照 m=0 → 0.01 ms）；有 miss 的層 **27.96 / 40**。
- ⚠️ **線 I 的更正**：邊際 miss 的 bytes 以 **1.6 GB/s** 流動 = page cache／RAM 拷貝速度，
  **不是磁碟**（該輪磁碟峰值僅 823 MB/s）。⇒ §7 用「SSD 3 GB/s × 全部 1.171 GB」是**錯模型**；
  miss 的成本是 **page fault ＋ 拷貝 ＋ 等待**，不是傳輸。

**新分解：單 token 85.8 ms ≈ 64 ms（miss 相關，75%）＋ 22 ms（其他）**
⇒ **miss 清零的理論上限 ≈ 45 t/s**（無 MTP）。25 在這個槓桿的射程內。

### 8.2 「3」有機會，但取決於 miss 的**種類**

工作集反推：`W = 8 GiB / (1 − 0.224) = ` **10.3 GiB**，而專家總量 ≈ **11.5 GiB**
⇒ 長序列 decode 幾乎摸遍 90% 的專家 ⇒ 這 22.4% 看起來是**容量 miss**（池裝不下），
**不是預取失敗。容量 miss 靠 prefetch 救不了**，只能「裝得下」或「訪問更少」。

- 決定性量測：**`n_miss_capacity` vs `n_miss_compulsory` 的比例**
  （`llama-expert-cache.cpp:932/934` 有計數，但 `final stats` 那行沒印分類）。
- **幾乎沒做過的旋鈕**：`-expert-cache` 用過 **109 次，全部是 8 GiB**；10 GiB 只出現在
  `Backup/bitident_ab.py`（非性能用途）。掃 **8 → 10 / 11 GiB** 值得做，但 16 GB 機器上
  （pool 8 ＋ dense 0.8 ＋ KV 0.64 ＋ 系統 ~2 ≈ 11.4 GiB）**pool 加到 11 只剩 ~0.5 GiB**
  ⇒ 很可能踩到 §EN-350 那個「`cb` 對水位敏感」（74.18 vs 11.26）的坑。要在窗口紀律下 A/B。
- 甜點只餘 barrier 的**階躍性**：把「有 miss 的層」從 27.96/40 壓下去有非線性收益。

### 8.3 「4」最確定 —— 而它的正確形式是「只壓專家」

§7 說「讓模型整包進池」是錯的形式：**dense 本來就常駐、不佔 pool，要進池的是專家 ≈ 11.5 GiB**。

| 專家 bpw | 專家總量 | 工作集 | miss | 單 token | t/s（無 MTP） |
|---:|---:|---:|---:|---:|---:|
| 3.0（現況） | 11.5 GiB | ~10.3 GiB | 22.4% | 85.8 ms | 11.7 |
| **2.5**（IQ2_XS 級） | 9.6 GiB | ~8.6 GiB | ~7% | ~40.8 ms | **24.5**（含 MTP ~26） |
| **1.94**（IQ2_XXS 級） | ≤8 GiB | ≤8 GiB | ~0 | ~21.8 ms | **~45** |

- **降專家 bpw 是雙重收益**：工作集變小（miss↓）＋ 每 token 位元組變少。
- **不要降 top-k**：8→4 只讓專家位元組減半，且質量代價遠大於降 bpw。
- 模型已是 `UD-IQ3_XXS-denseIQ4X`（混合量化）⇒ **工具鏈現成**，改專家 bpw 不需要新機制。

### 8.4 最務實的組合

**專家降到 ~2.5 bpw（工作集 ~8.6 GiB）＋ pool 能擠多少擠多少（8 → 10 GiB 試一試）**。
前者是確定的增益，後者是幾乎沒做過的低成本掃描（但要防 `cb` 水位坑）。
⇒ 25 在這個組合下是**可以談的**，不再是「不可達」。
