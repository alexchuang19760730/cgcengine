# K5 判決：45.6 µs/節點常數是「分攤恆等式」，不是發現

**日期**：2026-09-21 19:2x　**build 指紋** `28ae5fee…`（跑前跑後一致，**0 重建**）
**回答的問題**：`docs/K5_GRID_HYPOTHESIS_2026-09-21.md` 留的三選一候選
—— (A) grid 太小、(B) Metal per-kernel 固定成本、(C) `wcntw` 儀器口徑是假的。

---

## 0. 一句話

**(C) 成立：那個 45.6 µs 是儀器的代數恆等式，不是物理。**
K5 建立在它上面的「上界 30–38%」**全部作廢**，L2 歸零。
但換來一個更硬的東西：**61.3% 的 GPU 時間在每步 ~44 個「64 節點 command buffer」裡**
（`n_main = MAX(64, 0.1×n_nodes)` 強制打包的每段主 buffer）—— 這才是真正的主戰場，
而且它**不是** K5 假設的那個東西。

---

## 1. 第 1 步：`wcntw` 的定義（純讀碼，0 代價）

`ggml-backend.cpp:2421`：

```cpp
nsop_wns[q] += dur * ocnt[q] / owork;
//             ^buffer 時長  ^該 op 在這個 buffer 裡幾個節點  ^buffer 裡 work 節點總數
```

**它是把每個 command buffer 的時長，按節點數線性分攤給裡面的 op。**
分攤，不是測量。

### 1.1 三個獨立的佐證

| 佐證 | 讀數 |
|---|---|
| **`uni` 欄全是 `-1.000`** | `uni` =「那些只含單一 op 的 buffer」的精確 µs/node（`:2917`）。**44 種 kind 裡 0 個有值** ⇒ 從來沒有任何 buffer 只裝一種 op ⇒ **無從做精確除法** |
| **Σ`wcntw` 只覆蓋 87–93%** | step=1：Σ=131.02 / total=150.94（殘差 13.2%）；step=47：殘差 6.5% |
| **分攤指紋** | 同一個 step 裡 `CLAMP`(39)、`DIV`(39)、`GLU`(78)、`SUM_ROWS`(39)、`MUL_MAT_ID`(117) 的 µs/node **恰好都是 52.05**。節點數差 3 倍、運算完全不同，卻小數點後兩位相同 —— 這只能是「同一批 buffer 的同一個 `dur/n`」 |

### 1.2 為什麼「所有 op 的 µs/node 都一樣」是恆等式而不是發現

Σ_q wcntw[q] = Σ_b dur_b × (Σ_q ocnt[b][q]) / owork_b = Σ_b dur_b = 總時長。

⇒ `wcntw` 是總時長的**一個精確劃分**。只要 op 在 buffer 間分佈均勻（實測 `ub` 欄幾乎
每種 op 都是 75–86%，即「幾乎每個 buffer 都含有幾乎所有 op」），每一種 op 的
µs/node 就**必然**回歸到同一個值 = 總時長 ÷ 總節點數。

> **「每種 op 每個節點都花 45.6 µs」這句話，等於在說「45.6 = 總時長 ÷ 總節點數」。
> 它沒有攜帶任何 per-op 資訊。**

⇒ K5 §2 的「11 種 op 全落在 45.6±0.1 ⇒ 這是常數不是各自的工作時間」**論證方向反了**：
那些落在常數上的 op 是**資訊量為零**的；真正攜帶資訊的是**偏離**常數的
（`GATED_DELTA_NET` 188、`FLASH_ATTN_EXT` 120、`SOFT_MAX` 29 —— 因為它們集中在少數 buffer）。

## 2. 第 2 步：M 掃描**無法**區分 (A)/(B)

既有 `docs/M_WIDTH_CURVE_2026-09-21.md`（prod25、MTP off、reps 3）。

### 2.1 數學同形 —— 這是本輪最重要的方法論結論

- **(A) grid 太小**：`grid = ne11 = M`。M 小 ⇒ occupancy 低 ⇒ 每個節點有效吞吐低
  ⇒ 表現為「每個節點一筆與工作量無關的浪費」。
- **(B) Metal 固定成本**：每個 dispatch 一筆固定成本，與工作量無關。

**兩者在「改變 M」這個操作下的預測是同形的**：固定開銷被 M 攤薄 ⇒ ms/位置 下降。
⇒ **任何 M 掃描都分不出來。** 差別只在「(A) 可修、(B) 不可修」，而那要改 code 才知道。

### 2.2 但截距本身是真的（不依賴 `wcntw` 的獨立證據）

pool 路徑（M ≤ 8）最小二乘：`step ≈ 250.0 ms + 46.4 ms × M`，R² = 0.868。

| M | 1 | 2 | 4 | 8 |
|---|---|---|---|---|
| step ms（實測） | 229.3 | 406.7 | 457.3 | 602.9 |
| 殘差 | −67.1 | +63.9 | +21.6 | −18.4 |

⇒ **存在一個 ~250 ms、與位置數無關的每步成本。**

⚠ 但**不能**像 K5 那樣把它除以節點數當成「每節點固定成本」：M=1 時讀權重是必須的，
而權重讀取時間本身就與 M 無關 ⇒ 截距裡的最大一塊是**權重頻寬**，不是 dispatch 開銷。
（佐證：250 ms ÷ 3056 dispatch = 81.8 µs/dispatch，是 K3 實測**邊際**價 17.9 µs 的
**4.6×** —— 邊際價 ≠ 平均價，這個 4.6× 本身就是「截距裡混了別的東西」的證據。）

## 3. 正確的工具：`CGC_GPU_NODES_MATRIX=1`（已在 shipped binary，**0 重建**）

`ggml-backend.cpp:2438` 的註釋就是為這個問題寫的：

> `n_main = MAX(64, 0.1*n_nodes)` means EVERY segment's main-thread buffer holds >= 64
> nodes, so any kind living in it is divided by >= 64 by a count-weighted split …
> The model fitted offline is `dur_i = sum_k cnt_ik * t_k` … the small worker buffers
> isolate kinds the big ones cannot.

跑一次（cell 與 K3 同：`prefill250` + `-p 0 -n 128 -d 512 -b/-ub 512 -r 2`）得到
**47360 行**逐 range 的 `dur_ns` + 每種 kind 的節點數。原始檔：
`Backup/phase_decomp/K5/raw/nsm.stderr`。

### 3.1 每步的帳（47360 ÷ ~134 步 ≈ 353 buffer/步，與 `bufs=353` 吻合）

| nodes/buffer | 個/步 | mean dur | **佔步時** | µs/node |
|---:|---:|---:|---:|---:|
| 1 | 12.2 | 110.9 µs | 0.8% | 110.9 |
| 3 | 19.7 | 176.0 µs | 2.0% | 58.7 |
| 4 | 62.6 | 385.7 µs | 13.6% | 96.4 |
| 5 | 214.6 | 165.1 µs | 20.9% | 33.0 |
| 45 | 3.1 | 794.8 µs | 1.4% | 17.7 |
| **64** | **44.5** | **2334.1 µs** | **61.3%** | **36.5** |

### 3.2 三個直接推翻 K5 的讀數

1. **µs/node 不是常數**：17.7 – 110.9，**6× 跨度**。K5 的「45.6 ± 0.1」不存在。
2. **分佈是長尾的**：5 節點 buffer 的中位 58.2 µs、均值 165.1 µs（**2.8×**）
   ⇒ 用均值或中位數結帳會差 3 倍。
3. **64 節點的 range 每步 ~44.5 個，對上 `segs=40`** ⇒ 它就是
   **`ggml-metal-context.m:1099` 的 `n_main = MAX(64, 0.1×n_nodes)`**
   每段強制打包的主 buffer。**它一個人吃掉 61.3% 的 GPU 時間。**

### 3.3 per-kind 最小二乘**失敗**（要記下來，別再試）

`dur_i = Σ_k cnt_ik × t_k` 擬合結果：

- 全部資料：預測 122.7%、出現負的 `t_k`（`conv` −169 µs/node）⇒ 病態
- 只用 ≤5 節點的 buffer：fit 87.5%，但 `t_k` 從 4 到 613 µs/node

原因：**`CGC-NSM` 的 kind 是「張量名前綴」（`ffn_`/`attn_`/`cache`/`norm`…），不是 op 類型**，
且同一層的張量總是一起出現 ⇒ 設計矩陣嚴重共線性。
⇒ **想回答「ADD 一個節點多少 µs」，這個工具給不出來**（它回答的是另一個問題）。

## 4. 判決

| 項目 | 判決 |
|---|---|
| **45.6 µs/節點常數** | ❌ **作廢**。(C) 成立：它是 `wcntw` 分攤的代數恆等式 |
| **K5 的上界 30–38%** | ❌ **作廢**（完全建立在 45.6 上） |
| **(A) grid 太小** | ⬜ **未定** —— M 掃描在同形性下無法判定；要判需要 decode 形狀的 `ne`（**要重建**） |
| **(B) Metal 固定成本** | ⬜ **未定**，同上 |
| **L2（天花板分層裡的那一層）** | **歸零**（無支撐證據） |
| **P(25)** | **回到 <3%**（既有判決，回到 K5 提出之前的狀態） |

### ★ 換到的東西：61.3% 在 ~44 個大 buffer 裡 —— **但那是真實工作，不是浪費**

剛拿到時以為這是「人為打包造成的開銷」（64 是 `MAX(64, 0.1×n_nodes)` 硬湊的）。
**把大 buffer 的內容數出來之後，這個解讀是錯的**：

| 64-node range 的內容（佔其節點數） | |
|---|---|
| `ffn_moe_` | **25.9%** |
| `cache` | 9.6% |
| `ffn_moe_add` | 9.1% |
| `conv` | 8.2% |
| `node` | 7.1% |
| `ffn_` | 6.1% |
| （共 41 種 kind） | |

⇒ **裡面是 MoE FFN 的真實大計算，不是小 op。** 拆開打包**不會**省任何東西 ——
那 61.3% 是「讀專家權重」這件事本身，也就是 L4 頻寬問題（已判不可及）。

對比 5-node range 的內容：`cache` 13.0%、`q_conv`/`k_conv`/`gate`/`z-`/`norm`/
`linear_attn` 各 6.0%（每種剛好 8642 = 嚴格按層重複）⇒ **這才是小 op 群**，
佔 36.5%，分散在 ~300 個 buffer 裡。

⇒ **K5 原本瞄的「小 op 固定成本」確實只值 36.5% 的場子，而且這個 36.5% 是
「佔比」不是「可省」。** 大 buffer 那 61.3% 沒有槓桿。

## 5. 弱點（這份不能當結論用）

1. **per-kind 擬合失敗**（§3.3）⇒ 無法給出「某一種 op 的每節點成本」。
2. **儀器膨脹 1.93×**：本輪步時 177.3 ms vs 交付 91.79 ms ⇒ **只能引用百分比與比值**。
3. **n = 1**（單次採集，無重複）。
4. **步數是推算出來的 ~134**（`GPUTIME` 只印 37 步）⇒ 「個/步」的絕對量有 ~5% 誤差；
   **佔比不受影響**（它是相對量）。
5. 「64 節點 range = 每段 main buffer」是**由 `segs=40` 與 `n_main` 定義推得的對位**，
   沒有直接印證。
6. M 掃描那組 reps=3 且 M=8 的三次是 10.5/12.6/13.9（**單調上升，熱身漂移**）⇒ 截距 250 ms
   的不確定度可能到 ±30%。
