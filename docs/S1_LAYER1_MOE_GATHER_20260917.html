S1 定位：layer 1 的 MoE gather

2026-09-17 00:35 · 引擎層 · 兩臂 p25-gputime（host leaf）vs p25-slotgpu（S1 GPU table） · r8–r11，每輪兩臂各跑兩次，兩臂各自的同臂對照皆乾淨

先說結論，也先說它的狀態。 量測顯示：layer 1 的 MoE 在 pass 0 就讀到與另一臂「無關」的專家權重， 而同一層的 router（logits 與 top-k 權重）逐位元相同。 這指向「gather 本身」而不是「合成」。 但這件事與專案已知的 bit-identical 前提衝突（若層 1 的 MoE 在第一步就讀錯權重，token 流不可能 一致 30 個 pass），所以它是未裁決的矛盾，不是已成立的引擎缺陷。裁決方法見 §5。

1. 本輪又找到兩個儀器缺陷（都修了，都有判準）

缺陷 #5：mul_mat_id 的擷取把 n_tokens 丟掉了

呼叫點寫死 cgc_dst_capture(ctx, bid_dst, op, (int32_t) (ne0 * ne1))（MM 與 MV 各一處）。 mul_mat_id 的輸出是 3 維 [n_embd, n_expert_used, n_tokens] ⇒ 只讀 ne0*ne1 個元素＝token 0 的切片。

觀測簽名：同一個 n_embd=2048, n_expert_used=8, T=2 下，ffn_moe_down-1 報 ne=16384 而 ffn_moe_weighted-1（mul，全量）報 ne=32768——正好一半。

修法：拿掉 n_words 參數，cgc_dst_capture 一律用 ggml_nelements(op) ⇒ 呼叫點無法再截斷。修正後 ne 全部自洽（graph 1：gate 8192／down 32768／out 4096／weights_norm 16； graph 3：32768／131072／16384／64）。

連帶後果：§9.18.6 第一輪對 §9.18.4 的否證（「ffn_moe_down-1 的輸出相同」）是用 token-0 切片做的 ⇒ 該否證失效。

缺陷 #6（本輪自己造的）：TAIL=1 對任何 >32 元素的張量只寫哨兵

host 把 kargs 的 n_ids 傳成窗口長度（32），而內核的界是 j < args.n_ids、 j = n_skip + i ⇒ 只要 n_skip > 0（TAIL=1 且張量大於字數額度）每個元素都越界。

模式DST 列含真值全哨兵
head（n_skip=0，兩種語意重合）5335330
tail（TAIL=1）20517188

修法：arg_n = n_words——永遠傳張量元素數，窗口長度只記在 r.n_ids， 邊界交給內核（不動 .metal、無 ABI 變更）。修正後 246 列 / 246 含真值 / 0 全哨兵。

連帶後果：r5／r5b（tail 窗口）的讀數全部作廢。它們當時報「幾乎全部 never」， 不是因為相同，而是因為整列都是哨兵——而全哨兵列互相比較是「相等」， 一個壞掉的讀數因此出具了一個自信的「相同」。

2. 兩個讀法更正

  1. ids 不是專家選擇。 走池路徑時（n_tokens <= cgc_pool_max_tokens() = 8）， ffn_moe_gate-N 的 ids 是 ffn_moe_slots-N＝池 slot 索引 （llama-graph.cpp:2170-2180）；且 S1 的 GPU table 只給 il >= CGC_S1_MIN_IL（預設 1）， layer 0 仍走 host leaf。⇒ 跨臂比 ids 不構成「選了不同專家」的證據。 舊述句「專家選擇相同」要改成「top-k 權重相同」。
  2. ffn_moe_gate/up/down/weighted-* 一直可讀（既有 '*' 列舉各 40 個）。 先前報 ABSENT 是我的 NODES 沒請求它們（分析器 CHAIN 有、NODES 沒有）。 ffn_moe_gate_up-* 才真的不在列舉裡。

3. 結果（r10：全張量摘要；r11：窗口真值）

r10 與 r11 的同臂對照兩臂各自皆乾淨（p25-gputime 與 p25-slotgpu 都 「every captured node agreed in every compared graph」）⇒ 跨臂差異是可重現的真實差異，不是噪聲。

3.1 全張量摘要（r10）

摘要四字 = [sum, xor, wsum(=Σv·(i+1)), count]。sum／xor 對置換不變， wsum 會變——這是這一格能裁決「重排 vs 不同的值」的原因。

一個讀法陷阱，值得單獨記下。 只看 max相對差 ≈ 2.0 會以為是「取負」——因為 b ≈ −a 正好給 2.0。但整條分布否掉了它：b == −a 精確者 0/32， 相關係數 ~0.17。**一個極值可以偽造出一個不存在的形狀**（與 §EN-9.1 同一個教訓的另一面）。

4. 分段陷阱（判讀前必讀）

段界是 ffn_moe_gate-1；建圖序為 ffn_moe_logits_raw → ffn_moe_weights_norm → (gate_up) → gate／up → down → weighted → out。 ⇒ 段 i ＝ {pass P：gate 起 → 層 2..40} ＋ {pass P+1：層 0 ＋ 層 1 到 weights_norm}。 所以 ffn_moe_out-1／l_out-1 屬 pass P，而 ffn_moe_logits_raw-1／weights_norm-1 屬 pass P+1。 同段不等於同一 pass。

（本報告的「pass 0」判讀靠段 0：那是 pass 0 的層 0 ＋ 層 1 的 attention／router，全 SAME。）

5. 未裁決的矛盾與裁決方法

矛盾：若 layer 1 的 MoE 在 pass 0 就讀到無關的權重，token 流不可能一致 30 個 pass （CGC_MM_BITIDENT=1 三支柱；D5 的 M1/M2/M3 9/9）。兩個候選：
  1. 引擎的真缺陷：S1 臂的 slot 對映指到錯的專家（池內容／表內容不匹配）。
  2. 擷取位置的問題：某臂的 op->data 指到的不是 kernel 實際寫入的位置（pool 路徑下 dst 可能是另一個 view／offset），於是讀到「同形狀但不同位置」的資料——正好符合 §3.2 附帶觀察。

裁決用的現成手段（零改碼）：

  1. 先用 m123_oracle_gate.py 確認兩臂是否真的 bit-identical。 若是，則這份讀數必然是儀器問題——因為下游是確定性的，任何大幅擾動都會傳成不同的 token。 這是最快、也最省事的仲裁者，應該先跑。
  2. CGC_S1_KEEP_LEAF=1（建 S1 節點但讓 mul_mat_id 仍吃 host leaf）： 若變 SAME ⇒ 差異確實由 GPU table 造成；若仍 DIFF ⇒ 是擷取位置的問題。
  3. 輔助：把 off／ne 在兩臂都印出來對齊（目前 --windows 只印 A 臂）， 排除窗口錯位的可能。
