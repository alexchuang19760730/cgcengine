MTP 關鍵 Shape — 什麼樣子才能讓 MTP 發揮作用？

k=1 就不需要 MTP 了。那要什麼樣子，MTP 才真的有用？
🔴 你問到核心了
你說得對：k=1 就是不用 MTP。
但我們做了一大堆 MTP 相關的優化，結果 k=1 才是最好的 — 那 MTP 到底有什麼用？

問題不是「k 要設多少」
問題是「要什麼 shape，MTP 才真的能發揮作用」

現在 MTP 不工作，不是 k 值設錯了
是 shape 不對
是 MTP 的「工作方式」本身就有問題
🔍 為什麼現在 MTP 不工作？
從數據看，MTP 現在的問題是：
問題 數據 意味著什麼
Accept rate 隨 k 下降 k=2: 73.16%, k=3: 58.25% k 越大，accept 越低，mean_len 上不去
步時隨 k 增加太快 k=2: 218 ms, k=3: 266-314 ms (+31%) 多算一個 verify token，步時增加太多
token 增長不夠快 k=2→3: E 從 2.47→2.76 (+12%) 多了一個 k，只多換來 12% 的 token
沒有批次攤薄 第 2 個 token 的成本是第 1 個的 98% 每多算一個 verify token，幾乎要付全價
白話說：
現在的 MTP = 多跑一次模型來 verify
→ 多跑一次 = 多花一整份時間
→ 但只多換來 12% 的 token
→ 怎麼算都不划算

所以 k=1 最好 — 因為根本不該用 MTP
除非 MTP 的「工作方式」改變了
🎯 什麼 shape 才能讓 MTP 真的有用？
要讓 MTP 划算，必須滿足：
→ 多算的 verify token，每個的邊際成本要很低
→ 也就是：第 2 個 token 不能花第 1 個的 98%
→ 要降到 20-30% 才划算
Shape 是什麼 為什麼能讓 MTP 划算 難度
1. Batch verify（批次驗證）
→ 一次 verify 多個 token，不是逐個 verify
→ MoE gather 的成本可以批次攤薄 		→ 現在逐個 verify：每個 token 都要重跑整個模型
→ 批次 verify：多個 token 一起跑，MoE gather 成本可以攤
→ 第 2 個 token 的邊際成本從 98% → 20-30% 		高
2. 更好的 drafter
→ draft 模型更快更準
→ accept rate 更高
→ k 可以更大但 accept 不掉 		→ 現在的問題：k 越大，accept 掉越多
→ 如果 drafter 更準，accept 可以維持在高位
→ mean_len 就上去了 		中
3. Verify 跟 draft overlap
→ verify 不用等 draft 全部跑完
→ 邊跑邊驗 		→ 現在：先跑完 draft，再跑 verify
→ overlap：draft 跑第一個 token 的時候，verify 可以開始準備
→ 隱藏一部分延遲 		高
⭐ 關鍵中的關鍵：Batch Verify
💡 這才是 MTP 的正確打開方式
現在的 MTP（逐個 verify）：
→ 第 1 個 verify token：跑整個模型 = 100% 成本
→ 第 2 個 verify token：再跑整個模型 = 98% 成本
→ 第 3 個 verify token：再跑整個模型 = 98% 成本
→ 三個 token = 100% + 98% + 98% = 296% 成本
→ 換來 2.76 個 token
→ 平均每個 token 成本 = 296% / 2.76 = 107%
→ 比不用 MTP 還貴！
如果改成 Batch Verify：
批次 verify：多個 token 一起跑
→ 第 1 個 verify token：跑整個模型 = 100% 成本
→ 第 2 個 verify token：MoE gather 可以批次攤 = 20% 成本
→ 第 3 個 verify token：MoE gather 可以批次攤 = 20% 成本
→ 三個 token = 100% + 20% + 20% = 140% 成本
→ 換來 2.76 個 token
→ 平均每個 token 成本 = 140% / 2.76 = 51%
→ 比不用 MTP 便宜一半！
// 對比一下 // 現況（逐個 verify）： cost_per_token = (100 + 98 + 98) / 2.76 = 107% // ⇒ 比不用 MTP 還貴，所以 k=1 最好 // 理想（batch verify）： cost_per_token = (100 + 20 + 20) / 2.76 = 51% // ⇒ 比不用 MTP 便宜一半，MTP 真的划算 // 關鍵差異： // 第 2 個 token 的邊際成本：98% → 20% // 這就是「批次攤薄」的效果 // MoE gather 的成本，多個 token 一起攤
🧠 為什麼 Batch Verify 是關鍵？
因為現在 MTP 不工作的根本原因是：
→ 「沒有批次攤薄」
→ 第 2 個 verify token 的成本是第 1 個的 98%
→ 這個數字來自 MoE gather 的特性
MoE gather 為什麼沒有批次攤薄？
→ 因為每個 verify token 選的 expert 不一樣
→ 所以每個 token 都要重新 gather 一遍
→ 兩個 token 的 expert 重疊率很低
→ 所以沒法批次攤薄
那怎麼辦？
如果改成 batch verify：
→ 一次把多個 verify token 的 expert 全部 gather 回來
→ 不管它們是不是同一個 expert
→ 一次讀一大塊，總比逐個讀快
→ DRAM row buffer 命中率更高
→ 頻寬利用率更高

這就是「shape」：
不是改某個參數調大調小
是改「verify 的方式」
從「逐個 verify」改成「批次 verify」
