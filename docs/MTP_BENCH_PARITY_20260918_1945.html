llama-bench 的 MTP verify 走回生產路徑

2026-09-18 19:45　·　主題：llama-bench × llama-server 的路徑一致性（一個 src/ 缺陷：同一支儀器量了另一條程式路徑）　·　 本檔所屬 commit 見 §7　·　 姊妹檔 MTP_K_AB_2026-09-18.md（k 掃描與「只接了一半」的原始發現）、 MTP_LAUNCH_REQUIRED_PARAMS_2026-09-18.md（啟動必跑參數）、 HTTP_VS_BENCH_CALIBER_2026-09-18.md（口徑 A/B）

這份文件的定位：新主題 ⇒ 另開新檔（src/ 的修正，不是實驗記錄）。 MTP_K_AB 的 §3.1 把「llama-bench 的 verify 不走生產的 fast path」 寫成了「另一個洞，修它會動 src/，屬新一輪」；本檔就是那一輪，並把它修完、量完。

§1 一句話

llama-bench 的 MTP 一直沒走生產的 verify 路徑，而且沒有任何東西說出來。 fast path 的閘門是「呼叫端設的 phase」，而全樹只有 兩個呼叫者 —— server 與共用 spec 庫； 共用庫只碰 ctx_dft，所以 llama-bench 的 target ctx 永遠是 UNKNOWN（fail-closed） ⇒ 每一個 verify 批次都落到 exact ensure_batch。修法是在 verify decode 前後各加一行呼叫， 判準是那格計數器 verify: calls 從 0 變成 10183。

§2 問題：一個洞，三個症狀

2.1 症狀 A — 計數器直接寫 0

同一天、同一組旗標、兩邊都 MTP on，llama-bench 的 stderr 與 llama-server 的日誌各自印出： 

llama-bench  : MTP fast path: calls=395   verify: calls=0      draft: calls=395
llama-server : MTP fast path: calls=9497  verify: calls=8819                (18.69 experts/call)

verify: calls 是「那條路徑被走過幾次」。0 不是「很少」，是「一次都沒有」。

2.2 症狀 B — union/calls = 8.00 是指紋

bench 那 395 次全部落在 draft，而 draft 是 ctx_dft 的單 token decode ⇒ 每個 batch 的專家聯集正好等於 top-k（8）。8.00 這個「太整齊」的數字就是證據： multi-token 的 verify 批次不可能剛好 8.00。

2.3 症狀 C — 它讓兩份「矛盾」的量測同時成立

樹上一直有兩個看起來互相打臉的觀察：llama-bench 量到 MTP ≈ 1.0×（今天的 10 臂配對）、 llama-server 量到 ×0.695。它們不矛盾 —— 它們量的不是同一件事。 bench 走 exact 路徑（會 eager fill），server 走 fast path（只補 cold 的）。同一個洞解釋兩個數字。

§3 根因（原始碼，三處）

3.1 閘門在 llama-context.cpp:6065

const bool verify_fast = getenv("CGC_VERIFY_DECODE") != nullptr &&
    cgc_phase == CGC_PHASE_VERIFY &&
    cparams.ctx_type == LLAMA_CONTEXT_TYPE_DEFAULT;

cgc_current_phase 的預設是 CGC_PHASE_UNKNOWN，而同一處的註解逐字寫著 「UNKNOWN is the safe default: when caller forgets to set phase, we fall back to exact path」。 fail-closed 是對的設計；它只是在這個工具上被觸發了一整年而沒有聲音。

3.2 全樹只有兩個呼叫者

呼叫者設哪個 ctx設什麼 phase
tools/server/server-context.cpp:3897ctx_tgtclassify_batch_phase() 的結果（含 VERIFY）
common/speculative.cpp:303,369,1597,1733,1864只碰 ctx_dftDRAFT / CATCHUP / UNKNOWN
tools/llama-bench/—零（grep llama_context_set_cgc_phase 命中 0）

3.3 ★ 為什麼「讓 bench 改用共生庫」救不了

common/speculative.cpp 是共用的 spec 庫，但它本身不設 VERIFY —— VERIFY 只存在於 server 私有的 decode wrapper。洞在「共用庫」與「server 私有 wrapper」的交界上， 兩邊都能以為對方做了。這類交界最難被發現，因為它的症狀不是報錯，是「另一條路一直跑得很好」。

§4 修法（src/llama.cpp/tools/llama-bench/llama-bench.cpp，+40 行 / −0）

改動點內容為什麼
include #include "../../src/llama-ext.h" 與 server-context.cpp:19 同一個 staging API、同一條相對路徑
test_gen_spec 的 verify decode 之前 llama_context_set_cgc_phase(ctx, CGC_PHASE_VERIFY) 就是缺的那一行。set-then-decode 是 server 用的同一個配對（:3897 → :3904）
同一個 decode 之後 llama_context_set_cgc_phase(ctx, CGC_PHASE_UNKNOWN) fail-closed 重設，抄 common/speculative.cpp:1861-1864 的既有理由（「a missed marker can never accidentally ZERO-map an exact-path batch」）
為什麼「無條件設 VERIFY」是對的（含 0 個 draft 的回合）： 上面建出來的 batch 就是 verify 回合 [id_last, draft0..N-1]。server 標記同一件事的方式 （server-context.cpp:520-524）是先把 base token 推入 spec_i_batch、再把 drafts 推進去 ⇒ 1 token、0 個 draft 的回合仍然是 VERIFY。而 llama-context.cpp:6049 也明說 VERIFY 允許 n_tokens == 1（L4 會切）。
為什麼重設必須放在錯誤檢查之前：這個 context 跨 cell 重用，而 test_gen() 的 depth prefill（:2289）與單 token 步（:2311） 刻意不設 phase。失敗路徑若把 VERIFY 洩給下一個 rep，那些「普通 decode cell」會被 靜默移到 fast path 上 —— 而它們看起來完全正常。
為什麼「只此一處」就夠：test_gen() 的那兩處在 server 分別是 PREFILL 與 NORMAL_DECODE， 而閘門只放行 VERIFY／DRAFT ⇒ 兩邊都走 exact 路徑。所以 bench 的 UNKNOWN 與 server 的 PREFILL／NORMAL_DECODE 行為相同，不需要動。

§5 判準：怎麼知道真的接上了

不看旗標被不被接受（[mode] MTP ON 只證明這件事）。要看那條路徑自己被走過的次數。

計數器修好前修好後llama-server（同口徑）

verify union / call—（不存在）17.3918.69
draft: calls（8.00/call）395425（同 DRAFT 路徑）
verify-strict: refused / zero_mapped_selected0 / 00 / 00 / 0

最後一列是品質守門：它的定義是「被選中的專家被讀成零權重」的次數。 llama-expert-cache.cpp:2537-2541 逐字寫著它無條件印出、就是為了「不能再沉默」。 0/0 ⇒ fast path 沒有把權重丟掉。另外 CGC-COLD-GUARD … -> ensure_batch 在修好後 仍然會觸發（冷專家佔比超過 30% 時退回 exact）⇒ 第二層防護活著。

§6 速度：路徑統一了，但「同速」要分成兩組讀

先講可引用性：本節有兩組數字，只有第二組可以引用。 第一組落在 19:53:59 那次不乾淨重開機之前的窗內（`ResetCounter-2026-09-18-195408.diag`） ⇒ 標 不可引用。第二組是重開機後、環境閘門通過才跑的。

6.1 方法：怎麼在不換 binary 的情況下重現「修前」

fast path 的閘門是 cgc_fast_eligible = !warm_gate，而 warm_gate 由 CGC_WARM_NPAST 決定（llama-context.cpp:6081-6084）。把它設成天文數字 ⇒ 永遠 warm_gate ⇒ fast path 永不啟用 ⇒ verify 回到 exact ensure_batch， 也就是這個 commit 之前的行為。設定路徑是 run_server.sh:2035 的 CGC_SERVER_WARM_NPAST（已用 --dry-run 驗過它會進最終 env）。 其餘每一格（VERIFY／DRAFT 的許可、PREFILL_STREAM、GATHER_SLAB_CAP、模型、-b 512、 MTP n_max=3、8 GiB pool）都與 prod25-stream 逐字相同。

自我驗證（這一格是整節成立的前提）：控制臂的 stderr 完全沒有 MTP fast path 那一行 —— 因為 n_fast_calls == 0，那一行只在 > 0 時印。⇒ 它確實回到了修前行為， 不是「我以為它回去了」。

§8 沒做的（具名）

  • llama-bench 的取樣仍然是 temp 0.80（common_params_sampling 的預設）， 而 http_duo 送的是 temperature: 0.0（greedy）、launcher 的 --temp 0.4 是第三個值。三個不同的接受率 ⇒ 每步 token 數不同 ⇒ 跨工具比 t/s 時必須連同溫度一起報。llama-bench 沒有任何 CLI 能改它。
  • http_duo.py 的 prefill 半軸在 prod25 上必 400 （prompt 4500 token > ctx 4096）⇒ 本檔的 server 對照只有 decode 半軸。
  • 本檔沒有做「換回舊 binary」的 A/B：改用 CGC_SERVER_WARM_NPAST 覆寫 （見 §6）在同一個 binary 內重現修前行為 —— 少一次建置、也少一次「跨 build 比」的風險， 但因此不能回答「舊 binary 的絕對值是多少」。
  • 沒有動 run_server.sh 的那個死旗標（argv 有兩個 --temp）； 那是所有人共用的生產腳本，且屬另一條線的未提交修改檔。
