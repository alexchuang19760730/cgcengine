| `cache_s_lN`（ssm state） | `[524288, 0]` | **30** | 見 §3.3 |

### 3.2 B 臂（MTP off，`n_rs_seq=0`）

| 目標張量 | 形狀 | 數量 | 來源 |
|---|---|---|---|
| `conv_state_update-N` | `[24576, 1]` | **30** | `delta-net-base.cpp:487-499` 的 **if 分支**（`n_rs_seq==0`，每層 1 個） |

⇒ **MTP 專屬 = 210 − 120 = 90 個**，而且全部是 conv state（cache_r）：
`if` 分支 1 個/層 → `else` 分支 4 個/層，每層 +3，30 層 = +90。✓ 與 §EN-387 的機制描述一致。

### 3.3 ⚠️ 新發現：**60 個零位元組 CPY**

兩臂都出現，數量恆為 `30 + 30`（每層各 1 個，位於每層開頭，如 index 14／36），
形狀的第二維是 **0**：

```
CGC-GRPH[14] name=cache_r_l0 (view) (copy of ) op=35(CPY) ne=[24576,0]
CGC-GRPH[36] name=cache_s_l0 (view) (copy of ) op=35(CPY) ne=[524288,0]
```

- 元素數 = `ne[0] × ne[1]` = **0** ⇒ **搬 0 bytes**；
- 與 `n_rs_seq` **無關**（兩臂都在）⇒ 不是 MTP 造成的；
- 源張量**沒有名字**（`(copy of )` 後面是空的）⇒ 不是 `if` 分支那個有 `cb()` 命名的
  `conv_state_update`（那個在 B 臂確實有名字，見 §3.2）⇒ 是另一條未命名的 cache view 路徑。

> **【17:5x 更正】「它們仍然各付一次 dispatch」是錯的 ⇒ 見 §8：成本為 0。**
> 形狀與數量（每層 2 個、兩臂都有、`ne[1]=0`）的描述仍然成立，只有「付一次 dispatch」這句撤回。

## 4. 「冗餘」判定

### 4.1 bytes 那一腿：基本是空的

以 f32 上界計（`type_r`/`type_s` 是傳入參數，**本輪未實測類型**，故給 f32／f16 區間）：

| 項目 | 張量數 | bytes/步（f32） | @13.6 GB/s | 佔步時 112.84 ms |
|---|---|---|---|---|
| **MTP 專屬**（cache_r ×90） | 90 | 8.64 MiB | 0.67 ms | **0.59%** |
| conv state 基礎更新 | 30 | 2.81 MiB | 0.22 ms | 0.19% |
| **ssm state 基礎更新** | 30 | **60.0 MiB** | 4.61 ms | 4.09% |
| 零位元組 ×60 | 60 | **0** | 0 | 0 |
| **合計 210 個** | 210 | 71.4 MiB | 5.49 ms | 4.87% |

> 分母 112.84 ms 是 **server 口徑**（機制診斷用，**不得進 t/s 表**，§EN-393）。
> 13.6 GB/s 是 expert-cache 那一腿的實測有效頻寬；**GPU 內部拷貝應更快**
> ⇒ 上表是**上界**，真實值只會更小。

**判定：**

- **MTP 專屬的 90 個 ⇒ ≤0.6% 步時，而且不能刪。**
  §EN-387 已論證：4 個 copy 寫的是 4 個**不同 slot**（`s_slot = K-t`）、讀的是 4 個**位移 1 的不同來源窗**，
  是 recurrent-state 的 **rollback snapshot**；`common.cpp:1527`（`SEQ_RM_TYPE_RS`）＋
  `server-context.cpp:3261/4190` 的 partial rollback 以它為閘門，而今天 `mean_len 2.31/4`
  ⇒ 部分接受是常態 ⇒ **真的會被讀**。「冗餘」在強意義下**不成立**（與 §EN-387 同結論，本次只是把數量從 124 更正為 90）。
- **60 MiB 的 ssm state 寫回是基礎必要**（MTP off 也有）⇒ 不在 K2 的射程內。
- ⇒ **K2 的 bytes 腿：可省 ≤0.6%，判定為空。**

## 6. 本文弱點（不得事後補）

1. **`ne[1]=0 ⇒ 0 bytes` 是從 `CGC_GRPH_DBG` 打印的 `ne` 推得的，未獨立實測。**
   要坐實：直接讀該張量的 `ggml_nbytes()`，或用一次帶 bytes 欄的量測。
   （若 `ne[1]=0` 其實別有含義，§4.2 整節要撤回 —— 但它不影響 §4.1 的結論。）
2. **`type_r`/`type_s` 未確定**（是傳入參數，log 沒打出來）⇒ bytes 給的是 f32 上界；
   若為 f16，全部數字減半，**結論方向不變**。
3. **圖來自 prefill**（`CGC_GRPH_DBG` 的前 6 次預算）。prefill/decode 共用圖結構有交叉驗證
   （decode 步 `CPY nd=210`），但**沒有 decode 圖的逐節點原文**。
4. **零位元組 CPY 是否真的產生 dispatch，未驗證** —— ggml/Metal 可能對 0 元素張量直接跳過。
   若跳過，§4.2 的 4.4% 也是 0。
5. 全部是 **server 口徑**，不得換算成 t/s（§EN-393）。
6. n=1（每臂只跑一次），未配對。

## 8. 【17:5x 追加】零位元組 CPY 的坐實：**不產生 dispatch，成本 = 0**

純讀碼判定，**0 重建、0 行 kernel、0 次量測**。結論與 §6.4 列出的「未驗證」假設相反。

### 8.1 `ne[1]=0` 的確切含義 ⇒ `ggml_is_empty() == true`

```c
// ggml.c:1555
bool ggml_is_empty(const struct ggml_tensor * tensor) {
    for (int i = 0; i < GGML_MAX_DIMS; ++i) {
        if (tensor->ne[i] == 0) { return true; }   // 任一維為 0 即 empty
    }
    return false;
}
```

`ne=[24576,0]` ⇒ `ne[1]==0` ⇒ **empty**。這裡不需要再讀 `ggml_nbytes()`：
`ggml_nbytes = ggml_nelements × type_size`，而 `nelements` 含 `ne[1]` 因子 ⇒ 也是 0。
⇒ **§6.1 的疑慮解除**，方向與原假設相同（0 bytes），只是「0 bytes」不是重點。

### 8.2 兩道獨立的程式碼閘門，都在 dispatch 之前

| # | 位置 | 行為 |
|---|---|---|
| **①** | `ggml-metal-ops.cpp:68-74`（`ggml_metal_op` 構造函數） | `for (i = idx_start; i < idx_end; i++) { if (!ggml_op_is_empty(op) && !ggml_is_empty(node)) idxs.push_back(i); }` —— **empty 節點根本不進 `idxs`**，連遍歷名單都沒有 |
| **②** | `ggml-metal-ops.cpp:238`（`ggml_metal_op_encode_impl` 開頭） | `if (ggml_is_empty(node)) { return 1; }` —— 第二道保險 |

encode 主循環只用過濾後的長度（`ggml-metal-context.m:1476-1482`）：

```objc
ggml_metal_op_t ctx_op = ggml_metal_op_init(ctx->dev, cmd_buf, ctx->gf, idx_start, idx_end, ...);
for (int idx = 0; idx < ggml_metal_op_n_nodes(ctx_op); ++idx) {   // n_nodes() == idxs.size()
    const int res = ggml_metal_op_encode(ctx_op, idx);
    ...
}
```

且 `ggml_metal_op_init`／`ggml_metal_op_encode` 在整個 ggml 裡**只有這一處呼叫點**
（`ggml-metal-context.m:1463`／`:1476`）⇒ **沒有旁路能繞過過濾**。

注意 `ggml_op_is_empty(GGML_OP_CPY) == false`（`ggml-impl.h:90` 只列 NONE／RESHAPE／TRANSPOSE／
VIEW／PERMUTE）⇒ 過濾生效靠的是**形狀那一半**（`ggml_is_empty`），不是 op 類型那一半。這正好是這個案例的關鍵。

### 8.3 附帶修正：`CGC-GPUOPS` 的 `nd` **不是** dispatch 數

§3 曾用「decode 步 `CPY nd=210`」當成 prefill 圖的交叉驗證。查碼後這個交叉驗證**只能證
「圖裡有 210 個 CPY 節點」，不能證「發了 210 次 dispatch」**：

- `ggml-backend.cpp:2372-2379` 的第二趟統計是對 **圖節點索引** `nd ∈ [nd_a, nd_b)` 逐節點取
  `cgc_node_op()` 後計數（`nsop_nd[q] += ocnt[q]`），它**不知道 Metal 之後過濾了誰**；
- 同一行的 `work`/`NOOP` 欄只看 **op 類型**（`cgc_op_emits_work`），也**不看形狀**
  ⇒ 60 個 empty CPY 一樣被算成 `work`、一樣進 `nd`。

⇒ **「`nd` = dispatch 次數」這個讀法停用。** 真正的 dispatch 數是
`圖節點數 − empty 節點數` = **150**（MTP on）／**60**（MTP off）個真 CPY。

### 8.4 結論

| 項目 | 判定 |
|---|---|
| 60 個零位元組 CPY 是否產生 dispatch | **否**（兩道閘門） |
| 它們的 GPU 成本 | **0**（不是 4.4%） |
| §4.2 原推論 | ❌ **撤回** |
| **K3 上界** | **退回 5.3%**（最大集群 72 個 × 0.0736%），**不是 9.7%** |
| K2 bytes 腿的結論 | **不受影響**（那 60 個本來就算 0 bytes） |

**剩餘成本只剩主機側**：60 個空節點仍要被建圖／被 scheduler 走一遍。K4 已否證
（`gpu_union` 佔步時 92% ⇒ 主機側全部預算只 ~8%），而 60 個節點是圖的 ~1.5%
⇒ 不值得單獨立項。

### 8.5 這輪的真正價值

不是「找到 4.4%」，而是**省下一輪**：原本 §7.1 排的「加一行打印 + 等乾淨重建窗口」可以**整條刪掉**。
而且它示範了一件事：**「圖裡有這個節點」與「GPU 上發了這個 dispatch」是兩件事**，
凡是以 `nd`/節點數為分母的歸因，都要先問一句它有沒有被 `ggml_is_empty` 過濾掉。
（同一個疑問適用於 **K3 那個「最大集群 72 個」**：若 72 也是圖節點計數而非實測 dispatch 數，
它的 5.3% 上界還要再打折 —— **這是 K3 下一個該坐實的點**。）
