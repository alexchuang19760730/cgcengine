**Finding 1 — the rejection-sampling arm is a null BY CONSTRUCTION, not by plumbing.**
All three MTP-on arms produced the *same integers*: 309 drafted, 180 accepted. That is not a
coincidence and not a dropped environment variable (nothing in this engine prints
`CGC_MTP_REJECTION`, so the server log cannot settle it either way — the negative control is the
harness's own choice of sampler):

- `scripts/check/mtp_accept_ab.py:289` sends `"temperature": 0`.
- At temperature 0 both the target and the draft are greedy, i.e. one-hot. Then
  `min(1, p_t/p_d)` is 1 exactly when the two argmax tokens agree and 0 otherwise — the rejection
  rule *degenerates into* the exact-match test it replaces. `run_server.sh:1937-1939` says this in
  advance: *"with the greedy/gate configuration … the rule degenerates to the exact-match test it
  replaces"*, and *"the rule only bites under sampling (temperature > 0)"*.

So M4 work item 1 is **not measurable in this regime**, and an A/B run here can only ever return
0.000 — the same shape of instrument defect that was found and fixed in `phase_split_ab.py`
(a cell that manufactures a false negative). It must be re-run with sampling enabled to have any
decision power.

**Finding 2 — MTP-on ≥ MTP-off passes.** Paired within a single launch (a1): 6.14 vs 5.81 t/s
(+5.7%). Across launches: b 7.25, a2 6.36 vs 5.81 (+25%, +9%). The roadmap's "1.8× net loss" is
gone.

**Finding 3 — accept is 58.25%, i.e. 1.75pp short of the exit condition, and it is a property of
the (base, head) pair, not of the accept rule.** Under greedy, accept = argmax agreement between
draft and target. No accept-rule change can move it. Baseline repeatability is ±3.5%
(a1 6.14 → a2 6.36), which is smaller than the MTP-on/off gap but not by much: only paired
numbers should be quoted.

## 2. M3 — decode compute (exit: MTP-off ≥ 15 t/s, i.e. ≤ 66.7 ms/token)

Steady-state decode profile at HEAD, MTP off, 8 GiB pool (`/tmp/dsp_out/prof.json`, arm `prof`,
8 steps, `CGC_DECODE_PROFILE=1 CGC_DECODE_PROFILE_ALL=1 CGC_GPU_TIMING=1`):

| item | ms/step | share |
|---|---|---|
| **GPU span** (`union_sum`, Metal-side: max(end) − min(start) over the step's buffers) | **82.84** | 56% |
| **GPU idle** (`gap_sum`: Σ start_i − end_{i−1}) | **68.73** | 46% |
| CPU: wait for segment completions | 90.50 | — |
| CPU: top-k hook (slot mgmt + blocking fills) | 56.54 | — |
| CPU: submit | 6.79 | — |
| GPU busy (Σ(end−start), overlapping buffers counted twice) | 119.55 | — |
| **step total** | **148.43** | 6.7 t/s |

Cross-check that the attribution is closed: `union_sum + gap_sum = 151.6` vs total 148.4 (±2%),
i.e. **the step is exactly "GPU working + GPU waiting"**, and the waiting is the CPU hook/fill
serialization.

**The arithmetic that decides M3.** 15 t/s = 66.7 ms/step. Two independent bounds:

1. Remove the CPU serialization completely (`gap → 0`): step = 82.8 ms = **12.1 t/s**. Not enough.
2. The GPU span alone is 82.84 ms = **12.1 t/s ceiling** even with a zero-cost CPU.

⇒ **M3 cannot pass on overlap alone.** Doubling throughput requires the GPU span itself to fall
from 82.8 to ~40 ms — the roadmap's work items 2 and 3 (MoE gather fusion, batched-union gather),
not work item 1 (eval sync). Work item 1 is worth ~1.8× at best and is a *precondition* for
seeing work items 2/3, not a substitute for them.

Per-layer, the two addressable anomalies:

- **layer 0 carries 55.99 ms of GPU** — 47% of the step's GPU busy, against 1.3-2.7 ms for every
  other layer (its `union_ms` is 16.55 vs ~1.3). Not yet explained: it may be segment 0 absorbing
  the graph prologue, or a genuinely oversized first-union. It is the single largest item in the
  budget and the cheapest to investigate.
- **13 layers have `cb` spikes of 2.8-8.9 ms** (1, 6, 10, 12, 14, 17, 26, 28, 29, 33, 35, 38, 39)
  summing to ~52 ms of the 56.5 ms CPU cost — i.e. the CPU cost is concentrated in blocking
  expert fills, which is what `gap_sum` is measuring.

## 3b. `wait` split into GPU-busy vs GPU-idle (CGC_GPU_TIMING, 2026-09-17 23:11)

`wait` in the DECPROF line is a CPU-side window: it says the CPU was spinning for the GPU, and it
cannot say whether the GPU was **working** or **idle** during that window. Only `CGC_GPU_TIMING`
splits it, from the Metal command buffers' own GPUStartTime/GPUEndTime. Raw artefacts:
`/tmp/gpu_split4/{a,b}` (per-cell logs), `b.json`.

Cell: production profile `prefill250`, production decode shape `-p 0 -n 128 -d 512 -b 512`, MTP off.
Two disclosed deviations: **4 GiB pool instead of 8** and prod_matrix's memory floor lowered to 10%
(user-approved) — the 8 GiB configuration cannot launch on this box right now (`full-mtp` guard
requires free ≥ 40%, measured 35%). Launch label **NOMINAL/NOMINAL**, platform **6.15 t/s**
(samples 6.03 / 6.57 / 5.72). Steady state, 49 steps, first dropped, medians:

| reading | item | ms |
|---|---|---|
| CPU (DECPROF) | step total | 135.21 |
| CPU | wait 88.42 · cb 42.68 · submit 3.52 | |
| Metal (DECPROF, µs) | layer `gpu_sum` 138.08 · `union_sum` **86.75** · `gap_sum` **55.53** | |
| Metal (GPUTIME) | `wait` 100.89 · `busy_sum` 152.67 · `union` **101.25** · `gap` **55.31** | |

**The split, and it is the answer to the open question**: the GPU clock inside a step is ~101 ms of
span with ~55 ms of it **idle** — **GPU idle = 35.3%** of the GPU clock. The two independent
accumulations of `gap` agree to 0.4% (55.53 vs 55.31), and `busy_sum / union = 1.51` says the
command buffers overlap substantially (busy_sum counts overlapping buffers twice, so it is not a
duration).

Consequences:

- `wait` ≈ 88 ms is **not** "GPU busy". It is the CPU spinning while the GPU both works and idles.
- Even with **all** GPU idle removed, the GPU span alone is 87-101 ms ⇒ **10-11.5 t/s**. So M3's exit
  condition (15 t/s) still requires shrinking GPU work; the idle term is worth ~1.5×, not the 2.4×.
- The idle is **distributed**, not one stall: top gaps are L36 2.57, L34 2.50, L37 2.33, L1 2.23,
  L2 2.23 ms — consistent with per-layer hook serialization rather than a single hotspot.
- The 8 GiB-pool layer-0 anomaly from §2 (56 ms) does **not** reproduce at 4 GiB (L0 union 8.52 ms:
  still the largest, but 4× the median instead of 27×), so it is regime-specific, not a fixed cost.
