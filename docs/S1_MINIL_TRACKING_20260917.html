S1：分歧跟著 S1 的閘走，不跟著層號走

2026-09-17 02:45 · 引擎層 · 承接 S1_SLOT_OWNER_REFUTED_20260917.html · 觀測點移到「第一次 2-token 池路徑 pass」的 layer 0；新增 stage 選擇器；跑 r23–r25

結論（三句話）
  1. 在那個 pass 上，layer 0 整條鏈逐位元相同（15 個節點，含 router logits 與 gate/up/down/out-0），被消費的 ids 也相同（120/120）， 池佈局與被消費的專家集合也相同（40/40）。唯一不同的是 l_out-1。
  2. ★ 第一個分歧的層跟著 CGC_S1_MIN_IL 走：閘在 1 → 分歧在 l_out-1；閘移到 2 → 分歧變成 ffn_moe_out-2，而 l_out-1／ffn_moe_out-1 變回 SAME。 ⇒ 同一個層 1：host leaf 服務時逐位元相同，GPU table 服務時就不同。 「某一層壞了」與「從 layer 0 數值傳染」兩種讀法全部作廢。
  3. ⇒ 盒子裡只剩「gather 讀到的位元組不同」（ids 相同 ⇒ 反查相同 ⇒ 讀到的 slot 相同） —— 候選是 expert 權重運算元 src[2] 的指向／repoint。這是位址類缺陷， 與先前排除的數值／對映／時序不同類別。

1. 先把「哪一個 pass」釘死（上一輪我是用推的）

「第一次 2-token 池路徑 pass」必須是量出來的，不是猜的。三個坑：

坑實情
stage 標記是什麼 分析器的 stage ＝ 模型 pass，標記是 ids 列 name=ffn_moe_gate-1 （沒有 .dst）。我第一版用 .dst 找，整份 log 被當成 一個 stage
T 怎麼定 要用節點自己的 ne（l_out-0 的 ne / 2048）； 「graph 內 min ne 的比值」取決於該 graph 有哪些名字被捕捉到 ⇒ node set 一換，T 就變 （17 名 與 4 名兩種 node set 給出不同的 T 序列）
fragment capture 從 pass 中間開始 ⇒ stage 0 可能只有 1 列。選它會把 present=1 讀成 「另一臂缺這個節點」

量出來的形狀（`n_predict=12`、208-token prompt、池路徑 n_batch=8）： chunk 序列是 2,2,8×21,6,8,2,4,4，之後 11 個 T=1 的 decode； 引擎側 n_past 的 +6 然後 +8, +8, … 節奏與之一致。 ⇒ 第一次 2-token 池路徑 pass ＝ stage 1（stage 0 是 fragment）。

新工具：--select-t N（第一個完整的 T==N stage；「完整」＝列數等於該 T 的眾數）、--list-stages（先列每個 stage 的 T 與列數再選）。 判準是「永遠先 list 再 select」。

4. ★ r25：因果測試（零改碼）

問題：l_out-1 是「layer 1 壞了」，還是「第一個被 GPU table 服務的層」？ 把閘從 1 移到 2（CGC_S1_MIN_IL=2，臂 p25-slotgpu-l2 本來就存在）， 其餘完全不動，同樣看第一次完整 T=2 pass：

r25 的同臂對照兩個臂都乾淨（DST DIFF = 0）。

⇒ 第一個分歧的層跟著閘走，不跟著層號走。 同一個 build、同一步、同一個層 1： host leaf 服務時逐位元相同，GPU table 服務時就不同。

因此「某一層壞了」與「分歧由 layer 0 的數值傳染下去」都作廢。先前所有「第一個分歧 ＝ 層 N」的述句都要改寫成「第一個被 GPU table 服務的層」——這是一個措辭修正，但它改變了 下一步該去哪裡找。
