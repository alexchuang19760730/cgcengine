S1：時序被否，剩下「池的 slot 內容」

2026-09-17 00:50 · 引擎層 · 承接 S1_TIMING_SEGMENT_20260917.html · 只加一個量測（churn 區塊的圖邊界比對），並用它否掉時序假說

結論：你提的自變數（「消費點相對 publish 的位置」）已經量了，**答案是這一條路不成立**。 EQUIV-pool 在 1599 次 publish 全部 mismatch=0（同瞬），而新的 SEL-DRIFT 在每一張圖都是 entries=0 ⇒ 消費者讀到的每個專家，其對映在「publish → 讀取」之間完全沒動。 排除表上只剩「池的 slot 內容」。

1. 既有讀數：兩個都在「同一個瞬間」比較，答不了時序

讀數結果為什麼答不了
CGC-S1: EQUIV-pool …1599 次全部 mismatch=0 cgc_stable_e 就是表張量本身（cache_slot_table_tensors[il]）， 且比對發生在 publish 當下 ⇒ 兩個映射來自同一瞬間
TABLE-CHURN graph=N publishes=…每圖恰好 publishes=39 只說明「39 個受服務層各發布一次 ⇒ publish 與消費在同一步內」，沒有次序資訊

所以 EQUIV-pool 證明的是件好事（兩個函式在 publish 那一刻對被選中的專家是一致的）， 但它是「同瞬」的，結構上無法回答「讀的時候還是不是」。要回答它，必須在**另一個時刻**再比一次。

2. 新儀器：圖邊界的 SEL-DRIFT

churn 區塊的末尾有 prev.assign(now, now + n_expert) ⇒ 在圖邊界時， cgc_churn_last[layer] 正好是「上一張圖該層最後發布的表」。於是在邊界再問一次 slot_table_safe()，就能測「publish 之後、這一步結束之前，有沒有人動過」。

量測自身的教訓（第一版是錯的，寫下來以免重犯）。 第一版比對全部 256 個 entry， 得到 entries≈4410／39×256＝44.2%、max_per_layer≈115——而 publish 的 每層 clamp 數是 180687/1599 = 113，同一個量級。也就是說它量到的是 clamp（非常駐者：publish 寫 0、safe 回 −1，在 publish 那一刻就已經不同）， 不是種族。比對「沒人讀的 entry」在結構上不可能說明消費者的時序。

第二版只看「publish 當下被消費的 ids」（新增 cgc_churn_sel 快照）， 並且把 clamp 主導的全 entry 數字留在同一行列出來當對照：

CGC-S1: TABLE-CHURN graph=0 publishes=39 changed_entries=0   SEL-DRIFT layers=0 entries=0 max_per_layer=0 argmax_il=-1
                                        (all-entry drift, clamp-dominated, for contrast: layers=39 entries=4412)
CGC-S1: TABLE-CHURN graph=1 publishes=39 changed_entries=78  SEL-DRIFT layers=0 entries=0 …
…（graph 2..9 同）

SEL-DRIFT entries=0，每一張圖都是 0。

⇒ 消費者讀到的每一個專家，其對映在 publish 與讀取之間完全沒有移動。 既然 EQUIV-pool 已證「publish 那一刻的表就是池的活狀態」，而讀取前後它也沒動 ⇒ GPU 讀到的就是那個被正確發布的 entry。時序不是機制。

3. 累積的排除表（每一條都有量測支撐）

池的 slot 內容剩下以上全排除後，唯一還能讓「同 ids、同對映、不動」而 gather 出不同值的來源

p25-slotgpu-l20 也已不是「門檻外」哨兵（b84eea28 ≠ 錨 2d4e5099）， 所以「禍首在低層」那條推論也不再被支持。

4. 下一步（問題已換成「哪一個 slot 的內容」）

  • 量「池的 slot→expert 反查」（slot_owner）在兩臂是否相同。 前向對映（expert→slot）已被 EQUIV-pool 證明在 publish 時刻是對的且不動； 但若兩臂的填充把不同的專家寫進同一個 slot，那麼同一組 ids 就會 gather 到不同的權重 ——這正是 r11 那個「值域相近、方向無關」的形狀。
  • 具體做法：在圖邊界（已有現成的掛點）對每個受服務層 dump slot_owner 的一份摘要 （例如 [sum, xor, wsum(index+1), count]，與張量摘要同一個思路 ⇒ 可跨臂比對、且看得見置換）， 再與錨比較。這比逐 slot dump 便宜，且不會被「沒人讀的 entry」混淆。
  • 不要再加同形狀的分梯、不要再用 -l20；錨固定 p25-keepleaf。
