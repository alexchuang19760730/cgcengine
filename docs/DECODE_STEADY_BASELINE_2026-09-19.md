# decode 的稳态基线：13.98 t/s，以及 25 的缺口重算（2026-09-19）

**一句话**：生产路径（HTTP server）今天的稳态是 **13.98 t/s**，`llama-bench` 报的 ~10.2 **不是引擎的水平，是
仪器的欠读**。把基线从 10.2 换成 13.98 之后，25 的缺口从 2.45× 变成 **1.79×**，而瓶颈的算术也随之改变：
**制约项从「池喂不饱」变成「每步 633 个 command buffer 的空档」**。

---

| bench 形状 | avg_ts | platform_ts | σ |
|---|---|---|---|
| `-d 2025`（无种子） | 10.20 | 10.79 | 3.46 |

⇒ `--fixed-fill-seed` 把 σ 砍 68%（3.46→1.09），**建议设为 bench 默认**；但位准只 +4.6%，到不了 13.98。

### 1.4 已排除的候选（实测，不是推理）

| 候选 | 结论 |
|---|---|
| `CGC_PREFILL_STREAM` | 排除 —— bench 侧 `prod25-stream` 本来就带 |
| `batch` | 排除，**方向相反** —— 按服务器同款 `-b 2048 -ub 512` 得 **8.55/9.00**，比 `-b 512` 更慢（`-ub 2048` GPU OOM） |

## 2. 按 13.98 重算的分解

每 token 字节（模型标头直读 + 结构估计）：专家 347 MiB ＋ 稠密 ~1.45 GiB ≈ **1.92 GB/token**。

| 量 | bench 10.2 | **稳态 13.98** | **25 t/s** |
|---|---|---|---|
| ms/token | 98.0 | **71.5** | 40.0 |
| 有效带宽 | 19.6 GB/s | **26.9 GB/s** | 48.0 GB/s |
| 占 120 GB/s | 16% | **22%** | **40%** |

⇒ **25 t/s 只用 40% 的内存带宽，物理上仍然宽松**；缺口 **13.98 → 25 = 1.79×**（不是 2.07×，也不是 2.45×）。

### 2.1 真正的制约项浮出来了

实测（bench 形状）GPU 时钟跨度 ~101 ms，其中 **idle 55.3 ms（35.3%）**，来源是每步 **633 个 command
buffer / 3979 个节点** 之间的空档。

**假设**（需重测，见 §3）：这个 idle 是**每步固定**的（它是 per-buffer 的提交开销，与 token 无关）。
在此假设下：

| | bench 98 ms | 稳态 71.5 ms | 25 t/s 目标 40 ms |
|---|---|---|---|
| idle（固定） | 55.3 | 55.3 | **≤40（须减 15.3，−27.7%）** |
| busy | 42.7 | **16.2** | — |

两个直接后果：

1. **不去动序列化，天花板就是 `1000/55.3 = 18.1 t/s`。** 25 t/s（40 ms/token）**低于**当前的固定开销
   ⇒ **必须把 command buffer 的空档砍掉 ≥15.3 ms（≥27.7%）**，否则 25 在算术上不可能。
2. **暖池的价值被量化了**：bench 的 busy 42.7 ms → 稳态 16.2 ms，**暖池省掉 26.5 ms/token 的 busy**
   ⇒ 这就是 §EN-197 说的「结构性 thrash」的价格，也是任务 #3 的目标区间。

> ⚠ 这两点依赖「idle 是每步常数」这个假设，而它**只在 bench 形状（98 ms）上量过**。
> 在稳态 71.5 ms 上重测一次 GPU 时间分解，是本文件之后最该做的一支实验（见 §3）。

## 3. 下一步（按这个顺序）

1. **在稳态上重测 GPU 时间分解**（`CGC_GPU_NODES`）⇒ 判 §2.1 的假设。这是 25 能不能成立的**唯一分叉点**：
   idle 若确实 ≈55 ms 且常数 ⇒ 25 只能靠削序列化；idle 若随暖池一起降到 ~30 ms ⇒ 25 有第二条路。
2. **`--fixed-fill-seed` 设为 bench 默认**（σ −68%），并在报告里一律指名 `platform_ts` 还是 `avg_ts` ＋ `n_kept`。
3. **portal 拆成两个字段**：`decode_tps_cold` 9.99–10.2 ／ `decode_tps_steady` 13.48–13.98；
   KPI 基线取 steady ⇒ 缺口 **1.79×**。
4. 之后才是任务 #3（thrash 26.5 ms/token）、#4（prefetch 145/4、100% drain_cleared）、#5（MTP 接受率）。

## 4. 诚实边界（本文件不主张什么）

- **没有**解释 bench 为什么欠读 28%（§1.4 的五个候选都还没判）。
- **没有**在稳态上重测 GPU 时间分解 ⇒ §2.1 的第二个表是**在假设下**的算术，不是量测。
- 13.98 是**一次**启动的读数；跨启动离散（prefill 有 2.25× 的前例）**未排除**，要坐实需 ≥3 次启动。
- 本轮所有 run 都是 `build_commit efeade7e2 / build_number 279` ⇒ 同一 binary，可比。
