1. 為什麼需要這份文件：系統裡的模型是「兩槽」不是「一格」

這個 repo 有兩個地方在呼叫模型，它們的角色完全不同，而先前的討論把它們混在一起講過一次 （我把「換 B」講成「換 TokenHub」，但沒說清楚是換哪一格）。

槽變數誰在用角色
A TB_GEMMA4_* 容器內的 prime-agent（tb run / run_round.sh） 考生 —— 在任務容器裡解題的那個模型
B SFT_* ／ 新的 REFINE_API_* 見 §1.2 老師 —— 不在容器裡解題，用來蒸餾、或當另一個 agent

1.1 A 槽：容器內解題的模型

prime_agent_adapter.py:63-68 的解析順序是 「-k 參數 → 環境變數 TB_GEMMA4_* → 硬編碼預設」。 適配器再把這三個值以 TB_GEMMA4_BASE_URL/API_KEY/MODEL 注入容器內（_env），由 harness/extensions/gemma4-provider.ts 註冊成 provider local-gemma4。

容器裡的 localhost 不是這台 Mac base_url 是注入到容器內的，所以指向本機服務必須用 host.docker.internal:<port>/v1。 雲端 https 端點不受此限（容器有外網即可）—— 這也是把端點搬到雲端後，這條路不再與引擎線搶 GPU 的原因。

1.2 B 槽：SFT_* 被 10 個檔案讀，至少三種用途

用途誰本輪處置

③ 直接當 tb 的 agenttb_loop/agents/codebuff_api_agent.py 不動
為什麼「整槽換」會靜默弄壞 ③ —— 形狀相容 ≠ 語意相容 codebuff_api_agent.py 的 HTTP 形狀是 OpenAI 相容的 （:187 POST {base_url}/chat/completions ＋ :184 Authorization: Bearer），所以「base_url 指過去通不通」的答案是「會通」。 但它解析的是 codebuff 原生工具呼叫格式（:46 檔內註解自述 「codebuff agent 原生工具调用格式（DSML，标记是全角竖线）」，解析器在 :71 _extract_tool_commands）。普通模型不吐那種格式 ⇒ 請求成功、卻解析不出任何工具呼叫，而且沒有錯誤訊息。 判斷「能不能指過去」要看那支 client 怎麼解析回應，不是它怎麼發請求。

3. 量到的三個缺陷（都已修）

3.1 我自己的註解與程式順序不符（假宣稱）

--print-only 的註解寫著「擺在三道前置之前，所以它連 docker 都不問」， 而它實際排在 docker 檢查之後。沒有任何測試抓到，因為這台機器的 docker 一直是正常的。

「測不出來」與「沒有這個問題」不一樣 證明「它不碰 X」要用絆線：放一個假的 docker 進 PATH，被叫到就留痕。 第一版我試 PATH=/nonexistent bash <script> --print-only —— 結果 dirname: command not found ⇒ TB_LOOP_DIR 解析錯 ⇒ 死在更早的地方： 那是個無效測試，卻長得像一次失敗。 
T=$(mktemp -d); printf '#!/bin/sh\necho CALLED >> /tmp/tw.txt\nexit 1\n' > "$T/docker"; chmod +x "$T/docker"
PATH="$T:$PATH" bash <script> --print-only; cat /tmp/tw.txt   # 無痕 = 證明它不碰 docker

3.2 REFINE_API_MODEL 形同虛設（優先序被 config.env 釘死）

第一版寫成：

REFINE_MODEL="${TB_REFINE_MODEL_PATTERN:-freebuff-codebuff/${REFINE_ID}}"

而 TB_REFINE_MODEL_PATTERN 被 config.env 釘死 （source 是無條件賦值）⇒ 它永遠優先，新旋鈕永遠不生效。 症狀極具誤導性：探測已經打對新端點（沒有 WARN），模型字串卻還是舊的 ⇒ 執行時看起來像「端點說找不到模型」，而問題在我們這一側。 

# 修法：明確指定時就直接組
if [[ -n "${REFINE_API_MODEL:-}" ]]; then
    REFINE_MODEL="freebuff-codebuff/${REFINE_API_MODEL}"
else
    REFINE_MODEL="${TB_REFINE_MODEL_PATTERN:-freebuff-codebuff/${SFT_MODEL}}"
fi
一般化 source 一個 config 檔 = 無條件賦值 ⇒ 想用環境變數覆蓋它， 必須換一個它不認識的變數名。沿用同名一定被蓋掉 —— 這個 repo 已踩兩次 （TB_GEMMA4_* 一次、REFINE_API_MODEL 一次）。

3.3 完整金鑰出現在 ps 的命令列裡

診斷 smoke 時看到：tb run … -k api_key=sk-… —— 這台機器上任何本機使用者都看得到。

修法（已用哨兵值驗證）：適配器本來就支援環境變數回退，所以不要傳 -k api_key=， 改成 export TB_GEMMA4_API_KEY：

不傳 -k  → api_key=SENTINEL-KEY   base_url=http://sentinel.example/v1   model=sentinel-model
傳 -k    → api_key=EXPLICIT       base_url=http://explicit.example/v1   model=explicit-model
殘留（無法回溯修正） 那一輪已跑出去的行程，它的命令列已經被寫進本機 ps 的可見範圍。 要徹底乾淨就得輪換金鑰。能走環境變數就不要走 argv。

4. 兩個「先付 1 秒，省下數分鐘」的閘門

模式做什麼為什麼值得存在
--print-only 只印生效設定，不碰任何前置、不啟 tb 讓「三層優先序（環境變數 > config.local.env > config.env）」可被自測 —— 它壞掉的方式與正常運作長得一樣
--probe 用同一組 base_url/key/model 打一次真請求，分四類：200／401／403／404 key 打錯、範圍沒勾、model 名寫錯，在 smoke 裡都要等容器起來、prime-agent 裝完、 agent 第一次呼叫才顯形（數分鐘），而那時現場只剩「任務 Unresolved」； 401 與 403 在容器裡的現場一模一樣
401 與 403 不是同一件事 401＝key 本身不對（複製漏字／被停用／建在不同站台）。 403＝key 有效，但「可訪問範圍」沒勾到你要用的那個模型。 先在 host 上花 1 秒分辨，不要進容器才猜。

7. 誠實邊界（本文件不主張什麼）

  • smoke 還沒有結果。本白皮書產出時，tb run 仍在跑 （run-id=model_smoke_20260917_195218，日誌 /tmp/smoke_run.log）。 所以本文件不主張「PrimeAgentAgent ＋ 雲端模型這條路能跑完一題」—— 只主張到「key 與 model 可用（--probe 200）」。
    附帶一個觀測法的坑：tb 的進度表是即時終端顯示，重導到檔案不會渲染 ⇒ 日誌長時間停在 Starting harness run 是正常的，不代表卡住；判「還活著」要看 ps 的 etime 與 docker ps -a。
  • freebuff2api 在這台機器上不存在（不是「今天沒開」）。實測： refine_harness.sh:47 的探測回 rc=7（連線被拒）；127.0.0.1:1234 沒有 listener；專案不在 worktree／主 repo／~/Documents； app/cloud/freebuff2api/.env 不存在 ⇒ SFT_API_KEY 是空字串。
  • 回退那條在 host 上也是壞的：它指向 http://host.docker.internal:1234/v1， 而 host.docker.internal 只在容器內解析得到（/etc/hosts 無此條目、 curl exit 6），refine 卻跑在 host 上。⇒ 兩條分支都不通。未修。
  • 端點連不到時 prime-agent 是「卡住」而不是「報錯」。單變數實測： 127.0.0.1:1（可解析、沒人聽）→ TIMEOUT 25 s、零輸出； 127.0.0.1:18099（有人在聽）→ rc=0； TokenHub（可達、回 401）→ rc=1 秒回。 ⇒ 判準是「連得到（含回 4xx）＝快速返回；連不到＝卡住」。 機制（是否重試退避）未驗。
  • reasoning: false 與 maxTokens: 4096 刻意未改。V4.1-Flash 是深度思考 模型、最大輸出 384k，但 gemma4-provider.ts 仍宣告 reasoning:false／ maxTokens:4096。未驗證 harness 遇到「宣告無 reasoning、實際有」時的行為； maxTokens 是單次回覆上限、直接決定成本曲線 ⇒ 改它是決策不是修 bug。
  • contextWindow 的 128k 只影響「壓縮時機」，不影響正確性；且 TB 在 run 開始就把 harness 打包進容器 ⇒ 改動對「正在跑的那一輪」不生效，下一輪才生效。
  • 未跑 D5 的數值那一半（m123_oracle_gate.py）：本 commit 的 git diff --name-only 不含任何 src/ 檔，依 §2.4 的實務判準不適用。

8. 本輪的手法沉澱

手法用在哪為什麼有效
兩面夾 手上還沒有 key 時，證「B 的接線是通的」 假憑證打真端點（驗我方接線）＋ 真形狀打假端點（驗成功路徑）。 把「我方」與「對方」兩個未知項分開消掉，比「等條件齊了再說」多拿一倍資訊
絆線 證「某條路徑沒有被走到」 放一個「走到就會留痕」的替身去堵它。用「把依賴拿掉」的做法會連別的東西一起拿掉， 失敗點前移，而你讀到的失敗與你要問的問題無關
先問端點，不問文件 「這把 key 能用哪些模型」 GET /v1/models 回 121 個；文件與端點會不一致（已下線的模型仍在清單裡）
寫密文用編輯工具，不走 shell 把 key 寫進 config.local.env 不進命令列、不進 shell 歷史；核對只印長度與尾 4 碼
