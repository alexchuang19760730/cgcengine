1.1 一條 commit 什麼時候進入「可參考窗口」

判準不是時間，是這條 commit 有沒有把判決與身分一起帶上。四個條件同時成立才算：

  1. 帶身分：build 指紋非空。traces/schema/episode.schema.json 把它寫成硬閘門—— build == null ⇒ usable_as_evidence == false。理由不是「比較不準」，是不可比： 重建之後「兩個數字不同」有三種解釋（程式改了／環境變了／量測漂移），指紋缺席時無法收斂。
  2. 帶判決：message 裡報告 M1/M2/M3 的實際數字，而不是「應該不影響數值」。 這是可從 git body 讀出來的行為慣例：動到 src/ 的 2b284667f、2162e8cbd 都報告了；純 doc ／腳本的 a22ebe88e／6ceeb281b／57bd90801／e0152777d 0 個 src/ 檔案，因此不報告。
  3. 可比性先於數值：讀 M1/M2/M3 之前先讀 gate 的 comparable 欄位。 comparable=False（配置不同）時，那三個 9/9 是 printed for information, NOT a verdict；gate 會 exit 2（INVALID COMPARISON） 而不是 exit 1——跨配置的差異不是回歸，不得被報成回歸。
  4. 索引不漂移：index_assets.py --check 與 build_memory_index.py --check 同時綠。索引是 byte 級快照，不是內容摘要， 改一個字就漂移。

最貴的一個反例（此 window 為何必須被守）

build_fingerprint() v1 只手動雜湊三個檔（llama-server ＋ libggml-metal ＋ libllama），漏了 libggml-base—— 而 ggml-backend.cpp（排程器與 CGC_OA_ASYNC 閘門）就編在裡面。 後果：21:34（閘門讀「存在」）與 21:41（閘門已讀「值」）兩次跑帶完全相同的指紋， 被標成可比較。現改為 glob libggml*.dylib／libllama*.dylib， 8 鍵、鍵名不含版本號。⇒ v1（3 鍵）的歷史列在這一維上不可比，而這正是該改動存在的目的。

M1/M2/M3 生成之後的 commit 才可參考，機制上的理由是：從那個點起， 「改動 → 判決 → 身分」三者第一次被綁進同一條 commit——message 帶數字、cap_<tag>.json 帶解析後配置、manifest 帶資產 bytes。在那之前，數字缺指紋、參考檔缺 sidecar，二者的關係只能靠記憶維持。

這個窗口有兩個已知破口，必須一起說出來

(a) D5 的 dump 沒有 binary 指紋。cap_<tag>.json 只記 created／profile／resolved.{ARG,ENV,CGCENV}——沒有 md5、沒有 UUID。 若 gate 在 cmake --build 收尾期間起跑，那份 PASS 不可歸屬。 處置：重建完成後才跑 gate，並比對 created 與最新產物 mtime；重疊就換 tag 重跑。

(b) env 字串相同、語意不同，閘門看不出來。 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0 的三個讀者原本測「存在」， 所以 profile 的 =0 等於 ON，v3 是在 layer 0 不在池裡的狀態下 dump 的。 改成讀「值」之後 =0 首次真的生效（layer 0 進池、+142 resident slots、 +152 MiB），而解析後的 env 字串前後都是 "0" ⇒ 可比性檢查是字串比對 ⇒ 它會報一個普通的 M1 FAIL，而那是 category error，不是 regression。 對照組 CGC_SERVER_SKIP0=1 對 v3 得 M1/M2/M3/整列 fnv1a64 全部 9/9 ⇒ 同時證明 (i) v3 是 skip0 開啟時 dump 的，(ii) predicate 改動在其餘維度數值中性。 規則：凡是「env 相同、意義不同」的變更，一律主動換參照檔（--write-ref），不得沿用舊參照。

「資產測試交付」的具體形狀：不是測試程式，是被測試的資產本身有判決

  • 閘門互證：index_assets.py --check 與 build_memory_index.py --check 不驗快照（只驗原檔↔索引），所以兩者要一起重生； 而 MANIFEST 又記錄 INDEX 的 bytes/mtime ⇒ 順序固定為 先 build_memory_index.py，後 index_assets.py。

架構對「新功能」的態度是讓它可被否證，而不是讓它可被相信。落地的路徑是固定的四段，每一步都有出口：

線狀態落地的守護
S1 的 bit-identical 閘門 尚未通過值層面的解釋已全部排除；唯一剩下的候選是「消費的那一刻那個 buffer 裡是什麼」 三個既有儀器都答不了這個問題，而它們的共同病是「量的東西與宣稱量的東西不同一個」 ⇒ 這本身就是一條可重用的 lesson 形狀

新功能能落地的判準（本架構的一句話版本）

一個新功能「落地」＝ 它能被寫成一個 episode（帶指紋）、一條 decision （帶 ruled_out）、以及至少一條 lesson（換一個問題也適用）。 做不到這三件事的功能，在這個架構裡不算落地——它只是一個還沒被否證的相信。

5.3 目標三：產生 memory／與技能，並顯示記憶與隱式記憶

這個 harness 區分三種記憶，而它們的權威性與失效方式完全不同。

種類載體權威性失效方式
顯式記憶
敘述		 .workbuddy/memory/MEMORY.md（跨日事實）＋ YYYY-MM-DD.md（append-only 決策日誌） ＋ agent_harness/engine_loop/memory/INDEX.jsonl（段落級索引） 權威。要引用事實讀這裡 整檔讀取靜默截斷 ⇒ 截斷後的「沒查到」與「沒寫過」同形（這正是 INDEX 存在的理由）

為什麼「權重等隱式記憶」需要被顯式化

模型權重是最容易靜默改變的量：一個重新量化過的 GGUF、一個塌陷的 MTP head、 一個被換掉但同尺寸的檔案——它們不會出現在任何 diff 裡。所以本架構對權重的處理不是「記錄它」， 而是給它一個必須被引用才能使用數字的閘門：

  • 取了 model_stamp() 才敢說「兩欄量的是同一個模型」；
  • 取了 mtp_head_identity.fingerprint() 才敢說「draft 有跟上 target」；
  • 取了 build_fingerprint() 才敢把兩個 t/s 放在同一張表上。

反過來，SNAPSHOT.jsonl 是顯式記憶的隱式化：它把「這句話對應原檔哪一版」 變成 source_sha256 ＋ source_mtime——不靠猜、不靠人記得。 這兩個方向合起來，才是完整的「顯示記憶」：把敘述變成可驗證的數值，把數值變成可引用的敘述。

三個操作陷阱（違反會產生假綠燈）

1. index_assets.py --check 的結論行會被尾端那段 --out 說明包住—— 直接 tail 只看到說明文字。要濾 OK:／error 這兩類行。

2. INDEX.jsonl 的 drift 簽名是 mtime 而不是 bytes。 build_memory_index.py 每次都會重寫該檔（即使內容一字不變）； 看到 mtime 漂移就是順序問題，重跑一次「先 build_memory_index 再 index_assets」即可， 不要去找內容差異。

3. 收尾永遠是兩個 commit。 commit 的結果（hash、推送成敗、gate 實際輸出） 只有 commit 之後才知道，所以「把本輪收尾寫進當日日誌」結構上不可能塞進被提交的那個 commit。 第二個 resync commit 只動 MANIFEST.jsonl ＋ INDEX.jsonl， 沒有 src/，所以 D5 不必重跑——但 message 要寫明這一點。
