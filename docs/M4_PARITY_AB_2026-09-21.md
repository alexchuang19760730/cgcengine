## 判準（跑之前寫死）

決策變數是 **decode tok/s**（目標 25）。`mean_len`／accept 只當機制，不當判決 ——
G6 已實測「+11% mean_len 但 +14% step ⇒ 淨 −0.45 t/s」，mean_len 贏不等於速度贏。

| 條件 | 判定 |
|---|---|
| 全 rep 同號且最弱 \|Δ\| ≥ 0.50 t/s，為正 | CONFIRMED |
| 全 rep 同號且最弱 \|Δ\| ≥ 0.50 t/s，為負 | **REFUTED** |

採 **最弱的一致 rep**，不是中位數（2 rep 時中位數就是較大的那個）。

## 它為什麼是有效的實驗（不是對空氣施力）

三件事都驗過，缺一這個 REFUTED 就不能成立：

1. **M4 的 API 在產物裡**：`nm -gU libllama-common.0.0.279.dylib` 有
   `__Z31common_speculative_set_samplingP18common_speculativeRK22common_params_sampling`（`T`）。
2. **呼叫點也在**：`libllama-server-impl.dylib` 對同一符號有 `U`（未定義引用）
   ⇒ `server-context.cpp:1906` 那一行真的編進去了。
3. **旋鈕到了引擎**：server env witness 在 on 臂有 **27** 個 `CGC_*`、off 臂 **25** 個
   （差的就是 `CGC_MTP_SAMPLER_PARITY` 與 `CGC_SERVER_MTP_P_MIN`）。runner 把這條做成
   precondition —— 沒到就停，不讓「兩個一樣的臂」被讀成「沒差」。

## 最重要的單一觀察：G6 的警告被複現了

**rep0：accept 51.49% → 57.94%（+6.45 個百分點），而 t/s 13.10 → 12.19（−0.91）。**

這正是 G6 那個「accept 漲、step 漲更多、淨負」的形狀，在一個獨立的槓桿上再次出現。
⇒ **accept 從此只能當機制指標，不能當目標指標。** 任何「提 accept」的提案都必須同時報 step。

`mean_len` 則完全沒有分離：on 中位 **2.65** vs off **2.67**。

## 判決

- **M4 這條槓桿死了。** 它是最後一條「無損、已實作、從未測過」的 accept 槓桿。
- **25 正式下架。** 控制臂最佳 13.10 t/s，離 25 差 **11.9 t/s**；剩下能碰 accept 的手段
  都要動模型（換／重訓 draft head）或加 compute（tree／多候選驗證），兩者都不在
  「不動模型／不降精度／16 GB」的約束內。
- **建議目標改寫 14**（控制中位 12.82，指名槓桿 +5~10% ⇒ 13.5–14）。

## Caveats（都要跟著數字一起引用）

- **launch floor 降到 7000 MB**（documented 8000）。工具自己的註解說這台機器空載
  reclaimable 天花板只有 ~6.2–7.5 GB，**8000 靠等是等不到的**；本次以 `--need-mb 7000`
  下降並記入 provenance（`below_documented_floor=true`），未用 override 把它藏起來。
  本次實測 reclaimable 7666 MB。
- **Δ 單調惡化**（−0.91 → −1.74 → −2.73），且兩臂同時下降（off 13.10→12.82→11.91）
  ⇒ 有熱漂移成分。配對設計抵銷的是 launch order，不是箱子隨時間變慢。
  **方向可信（3/3 同號），量級不可當成效應大小引用。**
- **口徑**：這是 HTTP server 路徑（parity 的呼叫點在 request sampler 建立後，llama-bench 沒有
  per-request sampler ⇒ 旋鈕在那裡不可能生效）。兩臂同路徑故互可比，**不能與 12.57 的 bench
  數字直接比**。不過控制臂 12.82 與 12.57 接近，同形狀可比性尚佳。
- prefill 只有 12–39 t/s，是因為 HTTP prompt 很短（`prompt_n` 12–15），**不是 prefill 的數字**，
  別拿來對 250。

## 下一步
