一、問題與答案

問：4 個 zero region 是不是填充缺陷？也就是說，路由到 expert 252 的 token，在 layer 0 的 FFN 是不是被靜默算成 0 —— 恰好長成「輸出漂移但 argmax 跟得上」的樣子。

答：不是。那 4 個區域的內容就是檔案要求的內容。整個模型 31488 條 gate/up/down expert 列裡，有 10 列的前綴是零；池中那 4 個區域正好是其中 2 個「在池中」的 expert × gate/up 兩種。缺陷不在填充，在探針寬度。

一句話版本：警報與它的裁定工具都用「頭 4096 bytes 是否全零」判案，而這批列的零前綴 長 4592–13120 bytes —— 探針窗整個落在合法的零資料裡面。共享同一個盲點的兩件儀器， 永遠只會互相印證。

二、列的解剖：4096 落在哪裡

先把幾何講清楚。一條 expert 列是 335872 bytes（ne=[2048,512,256]、 nb02=335872，由 log 與 tensor 自身的 numpy view (256, 512, 656) 兩邊確認）。 零前綴是「整數條 656-byte 量化列」——不是任意長度的雜訊，是結構性的。

其餘 31478 條列的零前綴長度恰好是 0。所以這不是「很多列都很稀疏」，而是 10 條有明確零前綴的列。 ffn_down_exps 一條都沒有。

這些列也不是 dead expert：整列 17.8–47.0% 非零。舊說法「file itself has zero rows」、 裁定工具回報的 MODEL-ZERO，都只描述了那 4 KiB 的窗，不是整條列。

四、為什麼裁定工具看不見（本輪最貴的一課）

這是整個案子的關鍵：裁定工具用了與警報完全相同的 4096 bytes 寬度。對任何「前 4 KiB 為零」 的列，它只可能回 MODEL-ZERO。它 2026-09-15 寫下的「14 MODEL-ZERO / 0 ENGINE-ZERO」 不是量出來的，是結構上保證的。

五、認定鏈：slot 18 真的是 expert 252 嗎

三條互相獨立的來源指向同一格，缺一不可：

  1. 自斷言（pool 路徑、ne02=143 ⇒ id 是 slot）：ffn_moe_gate-0 … first_id=18
  2. teardown 掃描自己印出的對照：layer=0 slot=18 kind=0 owner_expert=252
  3. 同一份 log 的 slot table：CGC-POST: il=0 … st[252]=18 st[25]=25 …

第 3 條同時給出第二個候選 expert 25 —— 而 25 也在普查名單上。於是 layer=0 zero=4 of 142 resident slots 的四個 = {25, 252} × {gate, up}，數量吻合 （195、205 從未取得 slot ⇒ 沒被路由到 ⇒ 不在池中）。

六、真正會靜默丟專家的那個機制，讀數是 0

「路由到的 expert 貢獻被靜默丟掉」在這個引擎裡有專屬機制：pool 裡的保留 ZERO slot。 當被選中的 expert 尚冷時，remap 用 ZERO slot 代替它 —— mul_mat_id 就會乘到一片零。 這個計數無條件印出（llama-expert-cache.cpp:2211）：

llama_expert_cache: verify-strict: refused=1  zero_mapped_selected=0

refused=1 表示 verify-strict 前導正確地拒絕了一次 fast path （因為有 expert 仍冷），而 zero_mapped_selected=0 表示從來沒有任何 token 真的從 ZERO slot 讀到權重。也就是說：使用者擔心的那個形狀，有專門的儀器在守，而它讀 0。

八、這條結論「不」說什麼

誠實劃界，避免把這個結案讀成比它更大的東西：

  • 它不撤回 skip0 修復是數值變更這件事。M1 對 v3 仍是 4/9（漂移）。那個證據是 owner-set 的 5793 → 5935（差 142 = 恰好一層）與閘門本身，不是 zero-region 的 2 → 4。
  • 它說 zero-region 計數一直只是「內容讀數」，會隨 teardown 當下的 resident set 移動 （5935 = 40×142 + 255、5793 = 39×142 + 255、舊 build 的 5720 = 40×143 / 5577 = 39×143）。拿它當「layer 0 是否進池」的判別式本身就錯。
  • 它不保證 layer 0 進池沒有品質問題。零前綴是「每 token 都相同」的靜態性質； 池化 layer 0 改變的是別的東西（fill 身分 / 池佈局）。這條路仍需 M1 判別式 （slab 256/256 逐位元相同、partial pool 143/256 必分歧）。
  • 它沒有動 hook 是否改呼叫 precommit_e2e_gate.sh（09-09 的意圖）， 那會改變「哪一道閘門守 commit」，不搭這條便車。
