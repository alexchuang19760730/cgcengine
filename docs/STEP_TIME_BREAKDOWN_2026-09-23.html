🔍 每個大頭詳細分析
1. MoE Expert Gather
~34%
現況時間
~28 ms
頻寬利用率
~25%
為什麼只有 25%？
1. 讀取不連續：8 個 expert 分散在記憶體各處，跳來跳去，DRAM row buffer 命中率低
2. 平行度不夠：一次只讀一個 expert，沒有充分利用 DRAM 的多 bank 並行能力
3. Overhead 占比高：每個 expert 讀 170 MB，但 dispatch overhead 相對來說不算小
怎麼跑滿？
1. 批次讀：把多個 expert 的讀取合併成一次，讓讀取位置更連續
2. 提高平行度：同時讀多個 expert，填滿 DRAM 流水線
3. Prefetch：提前讀下一個 expert，隱藏 IO 延遲

預期效果：25% → 65%，時間從 28 ms → 11 ms（省 17 ms）
2. Dense GEMV（Attention + Layernorm + 其他）
~27%
現況時間
~22 ms
頻寬利用率
~76-77%
為什麼已經這麼高了？
Dense GEMV 的讀取模式是連續的（整個 weight matrix 一次讀完），所以頻寬利用率本來就高。

為什麼不能到 100%？
1. 不是純記憶體 bound：有一點計算（matrix-vector multiply），計算也需要時間
2. 一些小 overhead：kernel launch、dispatch 等
3. 理論上限就是 ~80-85%：因為不是純 copy，還有計算
怎麼再跑滿一點？
已經差不多到極限了。打滿也只 +2-3%，不值得投入太多。

預期效果：77% → 82%，時間從 22 ms → 20.7 ms（省 1.3 ms）
3. MTP Verify（Speculative Decoding 驗證）
~18%
現況時間
~15 ms

未知（待量測）
為什麼這裡也可能有問題？
MTP verify 其實也是在跑同樣的模型（只不過是 verify 多個 token），所以：
1. 也有 dense GEMV 部分（頻寬利用率應該跟上面一樣 ~77%）
2. 也有 MoE gather 部分（頻寬利用率應該也是 ~25%，因為是同樣的問題）
3. 如果 MoE gather 的問題解決了，MTP verify 的 MoE 部分也會一起變快
怎麼跑滿？
跟 MoE gather 是同一個問題，解決了 MoE gather，MTP verify 也會一起變快。

另外一個方向：k 值越小，MTP verify 的時間越短（因為 verify 的 token 少）
→ k=2 比 k=3 快 16.4%（待認證）

預期效果：MoE 部分一起省 50%，整體省 ~7 ms
4. KV Cache 操作
~12%
現況時間
~10 ms
頻寬利用率
未知（待量測）
KV Cache 在做什麼？
1. 讀取之前的 KV cache（attention 要用）
2. 寫入新的 KV cache

為什麼可能頻寬利用率不高？
1. 讀寫混合：一半讀一半寫，DRAM 讀寫切換有 penalty
2. 長度可變：context 越長，要讀的 KV 越多
3. 分散存取：attention 讀的位置可能也是跳來跳去的
怎麼跑滿？
1. KV cache 壓縮：用更緊湊的格式，減少要讀的 bytes
2. 分頁儲存：把 KV cache 分成 page，讀取時更連續
3. 優化 attention kernel：讓 KV 的讀取更有效率

預期效果：省 2-3 ms
5. Dispatch Overhead + 其他
~9%
現況時間
~8 ms
類型
CPU dispatch + 小 ops
這部分是什麼？
1. GPU kernel launch overhead：每個 kernel 都要 launch，launch 本身就要時間
2. CPU 端的準備工作：算參數、準備 buffer、切換狀態
3. 小 ops：一些很小的 elementwise operation
怎麼減少？
1. Kernel fusion：把多個小 ops 合併成一個，減少 launch 次數
2. 預先準備：把可以預先算好的東西提前算好

預期效果：省 2-3 ms（之前量過，大約 2.28%，已經接近極限）

🎯 結論
最大的槓桿還是 MoE gather
→ 光是 MoE gather 就能省 17 ms
→ 加上 MTP verify 的 MoE 部分（同樣的問題），又省 7 ms
→ 這兩個加起來就是 24 ms

其他部分加起來也只能省 5-6 ms
→ Dense GEMV 已經差不多了
→ KV cache 有一點空間
→ Dispatch overhead 也差不多了

所以：
1. 解決 MoE gather 的問題（讀取不連續），是最大的槓桿
2. MTP verify 會自動跟著變快（因為是同樣的 MoE 問題）
3. 其他小問題可以順手解，但不是主戰場

25 t/s 現實嗎？
→ 全部加起來，大概能到 18-20 t/s
→ 要到 25 t/s，還需要其他突破
→ 比如：更好的 k 值、更好的 expert cache、或者架構改變
