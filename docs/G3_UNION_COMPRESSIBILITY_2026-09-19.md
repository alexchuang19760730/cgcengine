## 1. 為什麼現在不能回答

`CGC-DECPROF all:` 的逐層欄位給的是**每層 GPU 工作的「時長」**（`gpu`、`union`、`gap`），
不是**「區間」**（start/end 時間戳）。於是「第 i+1 層的 GPU 工作有沒有壓在第 i 層上面」這個問題
**在現有讀數上不可表達**——你只能看到兩段各自的長度，看不到它們是否重疊。

而已知的事實恰好讓這個盲點變成關鍵：

| 讀數（E2b，184 個 decode 步，中位數） | 值 |
|---|---|
| `union_sum` | 104.60 ms（75.2%） |
| `gap_sum` | 34.76 ms（25.0%） |
| 逐層 union 分佈 | 29 層 × 2.81 ms ＋ 10 層 full_attn × 1.85 ms |
| `max/min` / `stdev` | 1.63 / 0.44 —— **差異全部由層類型解釋** |

⇒ union **沒有單層熱點可以修**。所以「−23%」不可能來自「找到那幾個慢層」，只能來自
「同樣這些層、但讓它們彼此重疊或變快」。這兩條路要用不同的證據區分，而現有儀器分不出來。

## 2. 缺的那一件儀器（小、可加、不動排程）

**那兩個值現在就在手上，只是被丟掉。** `ggml-backend.cpp:2117-2138`：

```cpp
int64_t g[5] = {0,0,0,0,0};
const int gns = cgc_gpu_take(split_backend, g);   // g[0]=busy g[1]=union g[2]=start g[3]=end g[4]=unsup
sg_busy = g[0]; sg_union = g[1];
if (g[2] > 0 && gt_prev_end > 0 && g[2] > gt_prev_end) {   // <-- g[2]/g[3] 只被用來算 gap
    gt_gap += g[2] - gt_prev_end;  sg_gap = g[2] - gt_prev_end;
}
if (g[3] > 0) { gt_prev_end = g[3]; }
```

逐層的 `dp_lay_*` 存了 `wait/cb/submit/gpu/union/gap`，**獨獨沒存 `g[2]`/`g[3]` 這一對**。
所以改動就是 `dp_lay_start[li] = g[2]; dp_lay_end[li] = g[3];` ＋ 印表機多兩個欄位
（`ggml-backend.cpp:1856-1858` 那段註釋自己說明了 Metal 的 `GPUStartTime/GPUEndTime`
就是這兩個值的來源）。**add-only：不碰段提交順序、不碰 remap、不改任何數值**，
所以它自己也要通過 §5 的閘門（預期 M1 884/884）。

⇒ 有了它，G3 從「不可表達」變成一個讀數：

- **時間軸**：相鄰層的區間是否相接（gap＝真的空檔）或重疊（已經 overlap 過）；
- **可壓空間**：把每層區間疊到同一條時間軸上，`span(全部) / Σunion` 就是**當前的並行度**；
- **決策**：若 `span(全部) ≈ Σunion`（並行度 ≈ 1），那 25% 的 gap 全是可回收的空檔 ⇒ G1 是主戰場；
  若 `span(全部) ≪ Σunion`，那 union 之間**已經在重疊**，gap 只是量測切法 ⇒ G4 必須靠**每層變快**。

## 3. 實驗本體（兩段，第二段才算 G3 的因果判準）

### 段 A —— 零改碼上界（**已在本輪戰役中，arm `ahead`**）

`CGC_SUBMIT_AHEAD=1` 刪掉「等前一段完成再提交下一段」的 CPU 窗（設計上就是錯的、racy，
只能當上界）。它一次把所有相鄰對都合併，所以它回答的是**整個家族的上界**：

| `ahead` 的觀測 | 意思 |
|---|---|
| `gap_sum/total` 大幅下降、`union_sum` 幾乎不動 | 可回收的確實是**序列依賴**（G1 的機制成立）；span 仍要靠計算變快 ⇒ G4 無機制 |
| `gap_sum` 不動 | 段提交不是瓶頸 ⇒ 整個 overlap 家族都不值得做 |
| `union_sum` 也下降 | 重疊會改變 union 讀數本身 ⇒ G3 的判準要改用時間軸，不能再用逐層 union |

⚠ `ahead` 的輸出**必然損壞**（`run_server.sh:1673` 自己寫明）。它只能給上界，**不是候選**；
G2 會否決它。

### 段 B —— 對照的 pair-merge（**需要線 B 的一處引擎改動**）

挑一對相鄰、且 `gpu/union = 1.00` 的層（`L4/L5`；備選 `L8/L9`），**只改這一對的提交方式**，
其餘 38 層不動，然後量同一批 decode 步的**時間軸**（不是 t/s）：

| 結果 | 判讀 |
|---|---|
| 該對的**聯合跨度 < 2 × 2.81 ms** | 重疊有效，且可外推到其餘 17 對 ⇒ G3 met，G4 有機制 |
| 聯合跨度 **= 2 × 2.81 ms**（只少了中間的 gap） | 重疊只回收 gap ⇒ G4 要靠「每層變快」，與 G1 是同一件事的兩面 |
| 完全不變 | 這兩層之間沒有排程餘地 ⇒ 換一對再試；全都不行則 G3 判死 |

**為什麼要段 B 而不是只用段 A**：段 A 是全對一起改，無法把「重疊有效」與「路徑被換掉」分開；
段 B 只動一對，是唯一的因果檢定。

## 4. G4 的門檻是 G6 的函數（這一格以前被寫成常數）

`t/s = mean_len × 1000 / total`，而 `total ≈ union + gap`。G1 把 gap 壓到 ≤5% 之後：

```
total ≈ union / 0.95        ⇒        25 = mean_len × 1000 / (union/0.95)
⇒  union ≤ 38 × mean_len  (ms)
```

從 E2b 實測的 `union = 104.60 ms` 起算：

| `mean_len`（G6） | 允許的 `total` | 允許的 `union` | 需要的 span 削減 |
|---:|---:|---:|---:|
| 1.80（今日實測） | 72.0 ms | 68.4 ms | **−34.6%** |
| 2.01（G6 的門檻） | 80.4 ms | 76.4 ms | **−27.0%** |
| 2.20 | 88.0 ms | 83.6 ms | −20.1% |
| 2.40（舊路線圖用值） | 96.0 ms | 91.2 ms | −12.8% |

⇒ **舊路線圖的「−23%」對應的是 mean_len ≈ 2.13，不是它自己寫的 2.4。** 這一格必須改成
「`union ≤ 38 × mean_len`」，否則 G4 的數字會隨 G6 的進展失效而沒人發現。

## 5. 驗收線（與 G2 共用）

任何 G3/G4 的改動都要通過：884 步長 probe 上 M1/M2 **884/884**，且同配置空對照維持
884/884（或 1003/1003）。儀器（段 A 的 §2 那一項）也要過同一條閘門 —— 它是 add-only，
預期通過；若不過，說明「印時間戳」本身有副作用，那它就不能當儀器。

## 7. 量過之後：段 A 的上界探針**是壞的**，而 G4 作廢的代價可以算出來

### 7.1 `CGC_SUBMIT_AHEAD=1` 在今天的 build 上不可用

`Backup/cgc_logs/llama_server_20260919_224333.log`（arm `ahead`）的 header 原文：

```
CGC-DECPROF: step=1 segs=41 layers=40 total=270.24 ms | wait=6.61 (2%) cb=250.73 (93%) submit=12.90 (5%) ntok=2 | layer gpu_sum=0.00 union_sum=0.00 gap_sum=0.00 ms (NO TIMESTAMPS)
```

三個獨立病徵，任一都足以讓「gap = 0%」變成假陽性：

| 病徵 | 讀數 | 後果 |
|---|---|---|
| GPU 側儀器死亡 | **25/28 個 decode 步帶 `(NO TIMESTAMPS)`**；median `union_sum = gap_sum = 0` | **沒有 union/gap 可讀** |
| MTP 失效 | **`mean len = 1.00`**（base 臂是 2.40/2.50）、`draft acceptance` 不印 | 每步只出 1 token |
| 工作量被換掉 | 生成被截到 **21 token**（base ~141） | **t/s 不可比** |

⇒ 那個臂的 t/s（6.59）**不是「變慢」**，是**不同的工作**（每步只接受 1 token 而非 2.40）。

**★ 但天花板重現了 —— 兩個臂跑的是同一種圖**：

| | 每步圖寬（ntok） | 每步 median `total` | server `mean_len` |
|---|---|---|---|
| base | **174/177 步 = 4** | **169.21 ms** | 2.40–2.50 |
| ahead | **28/28 步 = 4** | **99.39 ms** | 1.00 |

⇒ 步時比 **169.21 / 99.39 = ×1.702**，而認證值是 **×1.711**（差 0.5%）⇒ **重現**。
因為兩臂的 verify 圖寬都是 4（**同樣的工作**），差的只有那個 CPU 序列化窗
⇒ **序列化窗 = 步時的 41%**（`1 − 1/1.70`）⇒ **roadmap 第二階段有量測支撐**（此句更正我先前的誤述）。

⇒ **讀不出來的只有兩件，原因且不同**：

| 讀不到 | 為什麼 | 可不可以救 |
|---|---|---|
| `gap`/`union` 切分 | `(NO TIMESTAMPS)` 是**結構性**的：poll 點移到下一段提交之後，沒有完成的 buffer 可讀 | 要靠 §2 的時間戳；**不能把 0 讀成「gap 已消除」** |
| **t/s** | racy 讓 acceptance 從 2.40 崩到 1.00 ⇒ 探針自己的 t/s 只有 base 的 **0.709×**（**更慢**） | 它**證明不了** t/s 那一半：0.709 不是下界，是 racy 的損害讀數 |

⇒ **G1 的 t/s 報酬 ∈ [×1.0, ×1.70]** ⇒ 今天 regime（14.18 t/s）下是 **14.2–24.15 t/s**：
上界 `2.40/0.09939 = 24.15`（條件：acceptance 保住），下界 ×1.0 由 **G2** 保證
（正確實作不會讓 acceptance 更差）。⇒ 跨過 25 只需 `mean_len ≥ 2.485`（+3.5%）。

**gate 對這個臂的判決（G2）**：`oracle_long_ahead_20260919.jsonl.invalid` =
`{"reason":"non-finite values: 248320 of 248320","n_tokens":1,"n_vocab":248320}`
⇒ **racy 不是「數字不同」，是 logits 全 NaN** ⇒ 這是 G2 否決它最強的形式。

### 7.2 「union 可壓才有 G4」的代價

G4 作廢後，25 t/s 只能從 `mean_len` 來：`mean_len = 25 × total/1000`。
而 `mean_len = 1 + n_max × acceptance ≤ 1 + n_max`：

| `total`（同日兩次實測，差 23%） | 25 需要的 mean_len | n_max=3（上限 4.0）需要的 accept | n_max=4（上限 5.0）需要的 accept |
|---|---:|---|---|
| **171.1 ms**（本輪 base，三 rep 全 NOMINAL） | **4.28** | **>1 ⇒ 不可能** | 0.82 |
| 139.2 ms（E2b 那次） | 3.48 | 0.83 | 0.62 |

⇒ **在 n_max=3、且 G1 與 G3 都不成立、total 停在 171 ms 的情況下，25 是達不到的。**
⚠ **但 §7.1 更正後這個前提已不成立**：G1 的上界把 total 帶到 **99.39 ms**，此時
`2.40 / 0.0994 = **24.1 t/s**` —— 25 只差一點 mean_len（`2.50/0.0994 = 25.2`）。
⇒ **這張表是「兩個都不做」的退路，不是主線；G4 對 25 可能不是必要的。**
⇒ 仍然成立的是：`total` 在兩次實測間散 23%，**單獨就足以讓結論翻面** ⇒ 它是 gate 級問題。

### 7.3 這對三個 gate 的淨效果

| | 前 | 後 |
|---|---|---|
| **G1** | 等線 B 實作，上界用零改碼探針量 | **探針壞了 ⇒ G1 也卡在 §2 的儀器上**（先有時間戳，才談上界） |
| **G2** | 交件時的閘門 | **價值提高**：racy 臂不只是數值錯，而是**結構性毀壞**（儀器＋MTP 一起死） |
| **G3** | 需要 §2 的儀器 | **同一個儀器，從 nice 升為 blocking**（G1/G3 共用入口） |
