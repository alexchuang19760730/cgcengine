一句話結論：250 不是這個形狀的操作點。11 次獨立啟動中只有 1 次越過它， 而越過的那次不是任何被我量到的啟動狀態造成的 —— 同樣的啟動狀態重跑一次得到 179 t/s。

可引用的 band 是 155–184 t/s（18.5% 離散），不是 250。而「把記憶體水位當前置條件」 這條修法已經被實驗否證：我把 page cache 強制拉高 4.3 倍，吞吐沒有動。

1. 為什麼要做這個實驗

250 這個數字已經被達到過：09-14 的 264.78 tok/s （Backup/cgc_logs/llama_server_20260915_011146.log）、254.74、峰值 276.59。 它也被同一個命令錯過過：pp2048 @ -ub 6144 四次獨立啟動得到 276.59 / 198.84 / 176.18 / 122.68（2.25× 離散），而每次啟動內部的三個樣本 只差 2.08–15.41。

所以離散不是量測噪聲，是行程之間的狀態。一個 2.25 次才有一次命中的數字不是規格， 是抽獎；下游沒有任何東西能建在它上面。這個實驗就是把那個狀態找出來 —— 找到了，250 就變成「加上前置條件後可認證」；找不到，就該停止猜測。

1.1 儀器的來源是唯一的

命令不是手寫的：llama_bench_matrix.py 用 run_server.sh CGC_DUMP_ENV=1 取得 prefill250 profile 的 resolved env 與 argv，再餵給 llama-bench。 11 次啟動的實際命令逐字相同：

llama-bench -m …/Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf -ngl 99 \
  --load-mode none -t 8 -expert-cache 8589934592 --cache-type-k q8_0 --cache-type-v q8_0 \
  -b 6144 -ub 6144 -p 2048 -n 16 -d 0 -r 3 -o json

每次啟動前記錄 vm_stat，並且每次都換一個新行程。這就是「11 個獨立行程」的意思。

2. 第一輪：假設被否證，而且方向是反的

候選機制是啟動時的記憶體水位：16 GB 要同時裝 13.66 GiB 模型 + 8 GiB pool + 6144 寬 ubatch 的 compute buffer，而 run_server.sh:427-434 已經記載 pool 多 2 GiB 就足以把 6144 的 compute buffer 挤出 GPU（ command buffer failed with status 5 / Insufficient Memory）。形狀是超訂的， 所以抽獎抽的應該是「工作集有多少是常駐的」。

結果：spread 84.2%，rho(usable%, t/s) = −0.70 —— 記憶體越多反而越慢，而唯一達標的那次是記憶體最少的那次。

2.1 這個「反相關」暴露了我自己的儀器錯誤

我量的是錯的變數。 free + inactive 不是 page cache 的量度。 Pages free 低可以是「cache 很大」（macOS 會把閒置 RAM 填成 cache ⇒ 應該快）， 也可以是「別的行程佔住」（⇒ 應該慢）。這兩個方向相反，而我把它們平均掉了。

當場實測：free = 5.94 GiB，但真正的 cache（File-backed pages）只有 3.33 GiB，另有 3.82 GiB anonymous。兩者根本不是同一個量。

修正後，儀器改為記錄 File-backed pages（真正的 page cache）與 Anonymous pages，並加上 --warm-runs：在指定次數預先讀完整個模型檔， 強制把 cache 拉上去。這是打破「執行順序 ≡ 變數順序」這個混淆的唯一方法 —— 自然狀態下 cache 與 free 是一起動的，強制暖機則讓 cache 上升、free 下降。

3. 第二輪：cache 被強制拉高 4.3 倍，吞吐沒動

6 次啟動，第 2/4/6 次之前先把 13.66 GB 的模型檔完整讀一遍。

兩個假設都死了：不是 free memory（−0.14），不是 page cache（+0.09）， 也不是 anonymous（+0.14）。cache 從 2.32 拉到 9.96 GiB（4.3 倍）、free 掉到 0.06 GiB， 吞吐落在同一條 155–184 的帶上。

4. 而程式碼那邊：M1 不是「未實作」，是「已實作、已量測、已否決」

250/25 這條路的關鍵依賴是 M1（W3 解耦）。我上一輪說「沒有東西擋著」，這句話在程式碼面前是錯的， 而且錯得比「未實作」更重：

docs/M1_POOL_SPLIT_COST_2026-09-14.md
Status: implemented, measured, and rejected. The configuration is env-gated
        (CGC_POOL_SPLIT=1, default OFF) and now logs a loud warning at enable time.

兩個獨立的阻斷，各附精確的失敗簽名：

阻斷失敗簽名為什麼不是能修的 bug
A. 寬路徑是 Metal 已知讀不對的那個配置 CGC-POOL-SPLIT-GEOM: il=1 kind=1 ntok=16 mode=wide ne2=256 「wide」＝ Metal 透過模型權重緩衝讀一個 256-expert 張量，正是 loader 的 shrink 存在的理由 （plan §1.1 的 buffer is nil，以及 P1 mmap-stream 的 residency 爆炸）。 所以夾制被刻意保留。
B. 自有 pool 下 pool 路徑自己錯配 slot CGC-POST: il=1 st[0]=1 st[1]=1  ← 兩個 expert 共用 slot 1
CGC-HOOK: il=2 ids=[-1096546439 …]  ← NaN 位元模式		 remap 兩次讀同一區域 ⇒ 該層輸出 NaN ⇒ 傳到 il=2 讓 Metal encoder 出錯（SIGSEGV）。 舊路徑沒這問題是結構性的：那裡 pool「就是」張量自己的儲存， 所以「slot e 持有 expert e」在任何 fill 之前就字面成立。

結論欄自己說的話：「Reject work item 1 as specified. On this engine the pool must remain the expert tensor's own storage. Decoupling them is not a refactor of the pool; it is a rewrite of the ownership model (slot_owner / slot_table / batch_owned / prepopulate identity) and of how Metal is allowed to see expert weights, and the measured prize is not prefill throughput — the clamp survives either way.」

而 llama.cpp:424 在啟用時會印：

CGC_POOL_SPLIT is an EXPERIMENTAL, KNOWN-BROKEN configuration (degenerate routing + SIGSEGV)
- see docs/M1_POOL_SPLIT_COST_2026-09-14.md; do not benchmark or ship with it

順帶一提：阻斷 B 所在的那套記帳，正是本輪稍早我在讀的東西 （llama-expert-cache.cpp:827 的 slot_owner、CGC-POST 的 st[…] slot table、owner-set 掃描）。所以那一輪的工作不但沒清路，它緊鄰真正的障礙。

5. 修正後回答「250 / 25 還有機會嗎」

目標現在的實話障礙的種類
prefill 250 峰值達到過（286.67 / 264.78 / 276.59），但不是可重現的操作點： 1/11。可引用的是 155–184 t/s。 而「把記憶體水位當前置條件」這條路 已被實驗否證 —— 我強制把 page cache 拉高 4.3 倍，吞吐沒動。 未定位。既不是 free memory、也不是 page cache、也不是 anonymous。 剩下的候選在引擎自己的狀態裡（slot / fill 路徑、Metal buffer 重用）， 不在機器的記憶體計數器裡。
decode 25 9.05 t/s（最新 matrix），需 2.76×。roadmap 自己已把 M3 的離場條件 從 25 降到 15 t/s（MTP off），並標為「★ 最可能失敗」。 已量測的失敗。M1（W3 解耦）是宣告的關鍵依賴，而它 「implemented, measured, and rejected」，兩個阻斷各有簽名。 這比「還沒做」更貴：有人試過，而且 fault 了。

6. 我對自己上一輪那句話的更正

上一輪我說「250/25 那條路上現在沒有東西擋著了」。這是錯的，而且是三層的錯：

  1. 那份 zero-region 工作從來不在那條路上。 那個發現是關於探針寬度 （4096 B vs 長 4592–13120 B 的零前綴），是量測工具的問題，不是性能槓桿。 所以結束它不可能清空任何路 —— 在我開始之前那條路也同樣「沒有東西擋著」， 而 250/25 至今沒做到。我把「移除了一個干擾」講成了「移除了一個障礙」。
  2. 那條路的宣告第一依賴（M1/W3）不是未實作，是已否決， 附兩個精確的失敗簽名（§4）。這是比「未實作」更重的障礙。
  3. 兩個目標在同一個 16 GB 上互相競爭，而我上輪完全沒提： prefill250 要 ctx 8192 + ubatch 6144，prod25 是 ctx 4096 + 模型預設 batch； 兩者共用 8 GiB pool。要一個 server 同時做兩件事，就必須付 6144-wide compute buffer 的記憶體代價 —— 而那正是讓 250 不穩定的那個配置。

所以：不，我沒有信心。 這一份報告的可信度建立在它敢於否定自己上： 兩個候選機制被自己的實驗砍掉，一個數字（250）被自己的儀器降級為極端值。 唯一站得住的是三件可複查的事實：1/11、18.5% 的帶、以及 M1 的「已否決」狀態。

7. 下一步（按投報率）

  1. 把 286.67 那筆單獨追出來（最高投報率）。 它是唯一越過 250 的樣本， 而它的啟動狀態與另一筆 179.09 幾乎相同。兩者的差異只可能在引擎內部 ⇒ 用既有儀器（CGC-DECPROF / CGC-M2-FILL / CGC-DBUF / teardown pool integrity）把那 45 秒的 run 與 73 秒的 run 逐段對拆。這是唯一能把「抽獎」變成「規格」的路，且不需要新理論。
  2. 修 M1 的正確形狀已經被指出了，但不在 M1 的原始規格裡： 該文件的收尾說真正的槓桿是「wide tensors 作為讀取來源， 由 host 側供給 pool，而非作為 graph 能 dispatch 的張量」。 若要走這條路，起點是 ownership model（slot_owner/slot_table/ batch_owned），不是 loader。
  3. 不要再調 pool 大小或記憶體水位去追 250。 本輪已否證；那個旋鈕不在這條路上。
