# P0 vs P1/P2 — 慢的是哪一個？**今天的答案是「分不出來，而且『慢』沒有複現」**

**日期** 2026-09-25 19:45–20:33 · worktree `flashkv-devserver` · HEAD `65c76b8c7`
**引擎** `libllama-common.0.0.578.dylib = 2ac1cbb9cfcb130a`、`llama-bench = 28ae5feed73660da`（八臂同一顆）
**cell** llama-bench、`prod-new` profile、pool 8589934592（8 GiB）、`-p 2048 -n 128 -d 512 -r 3 --ctx-size 0`、`-b/-ub 5632`、q8_0 KV
**問題** 上一輪把 P0 與 P1/P2 綁成同一格（`p012`）量到「decode 慢」，本輪要把**慢歸屬到哪一個開關**。

---

## 0. 先寫死的判準與指紋（跑之前）

| 開關 | 機制 | 可否證指紋 |
|---|---|---|
| **P0** `CGC_EXPERT_SKIP_READRAW=1` | 載入時 skip-load expert 不 `read_raw` ⇒ 少一份匿名 CPU 副本（~10.9 GiB，swap 的來源）；權重只剩 pool／檔案那一份 ⇒ miss 付真磁碟 | **reads 略升**（白皮書 ctrl 43857 → p0 44589，+1.7%）；匿名駐留／swap 大降 |
| **P1/P2** `CGC_POOL_MADVISE=2` | fill 前 `DONTNEED` 將被覆蓋的頁；evict 時也丟（=2 涵蓋 P1+P2） | **reads 可降但每次 miss 的 I/O 時間升**（頁不再留在快取） |

**判定規則（driver 內寫死）**
```
m2only ≈ ctrl2   ⇒ 慢的是 P0
m2only ≈ p012    ⇒ 慢的是 P1/P2
兩臂都慢且都遠離 ctrl2 ⇒ 兩者都貢獻
```
（規則有一個隱含前提：**焊接臂本身要慢**。本輪那個前提不成立，見 §2。）

## 2. 判定：**規則的前提不成立 ⇒ 這個軸今天是「不可判定」**

| 檢查 | 結果 |
|---|---|
| 焊接臂是否慢？（規則的前提） | **不成立**：pass2 的 `p012` 10.17 是**該 session 最快**（vs ctrl2 9.27） |
| `m2only ≈ ctrl2`？（⇒ P0 才是慢的） | 平均 9.21 vs 9.27（**0.6%**）；steady 10.69 vs 9.92 ⇒ **一致偏快**，不是「等於」 |
| `m2only ≈ p012`？（⇒ P1/P2 才是慢的） | 平均差 9.4%，steady 幾乎相同（10.69 vs 10.60） |
| `p0only` 單獨 | **10.35**，且是當日**唯一樣本全穩的臂**（10.90/10.20/9.95，散度 8.7%、無冷值）⇒ 單獨開 P0 **沒有**付出白皮書那個 −25% |
| 焊接臂 vs 控制（pass2, steady） | **+6.9%**（10.60 vs 9.92）⇒ 方向與 pass1 **相反** |

⇒ **P0 與 P1/P2 都不能被指為「慢的原因」，因為在這台機的當前狀態下「開關會讓 decode 變慢」本身沒有複現**：
pass1（無 warm-skip、無冷卻）steady 上 `p012` 比 `ctrl2` 低 **13.7%**；40 分鐘後重跑（warm-skip 64、每臂冷卻），同一對變成**高 6.9%**。同一顆 binary、同一 cell、同樣 thermal HEAVY。

**可以指名的、跨全部八臂一致的只有一件事：`reads` 幾乎不動（82251–83277，散佈 1.2%）。**
⇒ 兩個開關都**不改變讀取量**；它們動的是「頁／副本留在哪裡」。所以任何以 reads 為主要論據的 P0/P1/P2 主張都不成立；唯一與機制方向相容的量測是**匿名駐留／swap**，而那不是速度。

## 3. 白皮書那句要降級

`docs/SWAP_P0P1P2_FIX_20260924_1400.html` 的「p0 7.60 ≈ p012 7.58、ctrl 10.20 ⇒ 慢的是 P0」**今天沒有複現**（p0only 10.35、p012 10.17，皆高於同 session 控制）。
那份是三臂 **n=1**、且它自己的 §7 已寫「P1/P2 單趟不可比、起點水位不乾淨」。⇒ 依 `ASSERTION_PROTOCOL`，它的 −25.5% 只能標成**單一 session 的觀察**，不得作為「P0 的代價」的通用值。

## 4. 本輪自己造成的三個協定缺陷（都寫進產物，不掩蓋）

| # | 缺陷 | 影響 | 修法 |
|---|---|---|---|
| 1 | pass1 的 driver 漏了 `--warm-skip 64`（`warm_skip=None`、`n_gen=128`） | pass1 三臂落在「冷啟動含在內」的舊口徑，不能與 run4/run5（11.64/11.22）併排 | pass2/iso 已補；**產物自證欄位**應該是 `warm_skip_applied = GEN − n_gen`（§3.3b 已提） |
| 2 | iso driver 的 idle 判準只看 `llama-bench`，看不到「正在冷卻」的 peer driver | 第一次啟動時兩支 driver 同時進入冷卻、會撞在一起（20:09）；已殺掉重啟 | 判準改成連 peer **driver** 一起看（已修，`p0_vs_madv_iso.py`） |
| 3 | 每臂之間啟動順序／冷卻不對稱 | pass2 的 `ctrl`（無冷卻）與 `p012`/`ctrl2`（冷卻後）不同源，我一度拿它當對照 | 判定只用**同協定**的臂（iso 兩臂＋pass2`ctrl2`） |

另外三個盒況事實：**八臂的 worst thermal 全是 HEAVY**、起跑 swap **3849–6004 MiB**（契約 §3.3 門檻 2048）、且本輪每臂 Δswap 都 > 500 MiB ⇒ 依 §5.1 **八臂全部踩污染門**，都只能當診斷價。

## 5. 要真的判定，需要什麼（依序，成本最低在前）

1. **一隻乾淨的窗口**：重開機後 swap ≈ 0、貫穿 NOMINAL；同 session 內 `ctrl / p0only / m2only / p012` **ABBA**，每臂 420 s 冷卻。
2. **`--fixed-fill-seed`**：今天八臂都在「有 warm-skip、無固定流」的**半套**約定上，所以會出現 6.26 / 6.57 這種冷 rep（該 rep 的計時窗自己付掉 compulsory fill）。固定流才讓「被計時的那段路由」在暖機時就被預熱。
3. **引擎側的 P0 專屬計數器**：P0 的作用是**記憶體**（匿名副本），唯一可引用的效果應該量成「載入後匿名駐留 −X MiB」而不是 t/s。目前引擎對 P0/P1/P2 **不印任何行**（`madvise` 靜默），所以日誌裡沒有任何「開關真的生效」的直接證據——本輪只能靠 `run_server.sh` 解析出的 `arm env {'CGC_EXPERT_SKIP_READRAW': '1', ...}` 加「env 非 0 會被轉傳」推論。
