一句話：CGC_POOL_MAX_TOKENS 不是「pool 的參數」，它是 prefill 的 chunk 大小。 llama-context.cpp 在 L4 pool 啟動時把 n_batch clamp 成 cap，而 n_ubatch = min(n_batch, params.n_ubatch)， 所以 cap 直接決定「每個 forward 處理幾個 token」。

四個結論

  1. cap 曲線是單調的，而且方向與直覺相反。 從 8 往上（16、32）prefill 下降； 從 8 往下（5、4、2）上升（cap=2 是 17.4 t/s，約 2.1×）。機制是 union 隨 chunk 超線性成長， 而常駐格數固定 —— union 是「工作集」槓桿，不是「分攤」槓桿。
  2. cap 不是可以自由調的旋鈕，它是 pool 的結果。 前提是 cap × top_k ≤ usable_slots；池子小到某個程度，能用的 cap 會撞到架構地板， 此時 pool 不是「變慢」而是完全不可用（loader abort）。
  3. cap invariance 的失效與 pool 佈局無關。 三臂實驗（只差 prefill step partition）產出三個不同答案； 而固定 cap 下 pool 2/4/6/8/10 GiB 全部 bit-identical。分歧已經在最後一個 prefill 輸出， layer 0 routing 三臂相同、layer 1 三分裂；三臂每一層 gather=0。
  4. 跨模型時，先斷的永遠是「槽位容量」這條前提，不是精度、不是佈局、不是 MTP。 它與 每 expert 位元組 × 層數 × top_k 成正比，所以換一顆每 expert 更大的模型， 同一顆 pool 的可用 cap 會先掉下來。

1. 三個被混用的名詞

這份白皮書一半的價值來自把三件事分開。它們在對話裡長期被當成同一個「pool 的設定」， 但它們的因果方向、代價、以及失效方式完全不同。

機制：union 是工作集，不是分攤量

原本的假設是：一個 chunk 的 union 被越多 token 共用，就越划算，所以 chunk 越大越快。 實測是否證。真正在發生的事是 ——

  • 常駐格數固定（8 GiB 下某些層 143 格、最緊的層 106 格，取 min_layer_slots）。
  • 一個 chunk 的 union 寬度 ≈ chunk × top_k，而且因為不同 token 會選到不同 expert， union 的成長實際上接近線性於 chunk、並且很快逼近上界（256 experts 中的大量集合）。
  • 當 union(chunk) 開始塞不進常駐格，每個 expert 每步都變成 cold fill： 付的是檔案讀取，不是計算。cap=32 的 0.37 t/s 就是這個狀態。
所以 cap 往下的速度紅利，本質是「把每步的工作集縮小到能全部常駐」。 它買到的不是算術效率，而是命中率 —— 這也解釋了為什麼它與 pool size 是同一條槓桿的兩端： 加大池子（容量）與縮小 chunk（工作集）都會提高命中率，而兩者都會動數值的前提條件（見 §4、§5）。

架構地板（不是調參選擇）

// src/llama.cpp/src/llama-memory-hybrid.cpp:85-89
// the trailing (1 + n_rs_seq) tokens of each seq must stay in the same ubatch
const uint32_t n_rs_seq = mem_recr->n_rs_seq;
ubatch = balloc.split_equal(n_ubatch, !unified, n_rs_seq > 0 ? n_rs_seq + 1 : 0);

// src/llama.cpp/src/llama-batch.cpp:609
GGML_ASSERT(n_ubatch > n_keep_tail);

也就是 n_keep_tail = (n_rs_seq > 0) ? n_rs_seq + 1 : 0，故 cap ≥ n_rs_seq + 2。

  • MTP ON：draft rollback 需要保留遞迴狀態尾窗，n_rs_seq = 3 → n_keep_tail = 4 → cap ≥ 5。實測 cap=4 載入即 abort，cap=5 HEALTHY。 harness 取 MIN_CAP = 6 作為餘裕。
  • MTP OFF：n_rs_seq = 0 → n_keep_tail = 0 → 沒有地板， cap=2 可以跑（也就是上表 cap=2 那 17.4 t/s 的來源）。

這條地板是遞迴/線性注意力層的語意，不是 expert cache 的設計選擇 —— 它與池子大小無關，卻直接限制 cap 能降到多低。

3. 為什麼 cap 不是 prefill 的旋鈕

(a) 因果方向反了：cap 是 pool 的結果

pool path 能運作的前提是「這個 step 的 union 全部能放進可用格數」：

cap × top_k  ≤  usable_slots   （= min_layer_slots − 1，ZERO slot 保留）

於是 cap_max ≈ usable_slots / top_k，而 usable_slots ∝ pool_bytes / (層數 × 每 expert 位元組)。 cap 是被池子與模型幾何推導出來的，不是可以獨立給定的自由度。 harness 的 cap 探測因此不是「調參」，而是「找出這個池子還走得通的最大 chunk」。

(b) 往上調不是變快，是崩掉

見 §2：cap 32 是 0.37 t/s（比預設慢 23×）。這不是「參數調壞了」，是工作集超過常駐容量後的相變 —— 從 compute-bound 掉進 per-expert cold fill。曲線上 8 就是那個拐點，而 8 恰好也是預設值。

(c) 往下調會撞到架構地板，而且撞到的時候 pool 是「不可用」

當 usable_slots / top_k 掉到 n_rs_seq + 2 以下，這個池子對這顆模型就完全不能用： cap 大到能塞進格數的 → 超過容量；cap 小到能塞進容量的 → 違反架構地板。沒有中間解。 harness 的診斷訊息就是這個狀態：

{"kind": "iq3", "pool_gb": 2, "cap": null, "min_cap": 6,
 "error": "pool 2GB holds 34 usable slots: cap 4*8 would fit but cap < 6 aborts at
           llama-batch.cpp:609 (GGML_ASSERT(n_ubatch > n_keep_tail)) during warmup.
           This pool is too small for topk=8."}

結論

prefill 的真正旋鈕不是 cap。 cap 只回答一個是非題：「pool path 還走不走得通，以及每步的工作集多小」。 prefill 的量級空間在另一件事上 —— 整層順序串流（M2 的 whole-layer prefill）， 也就是「一次把該層需要的 expert 連續讀進來」，把 1626 次隨機讀換成順序讀。 cap 曲線只能在這條曲線上移動一個點（而且往上一定更差）；它不是提升 prefill 的自由度。

4. cap invariance 失效的定位

問題是：「哪一步讓 logits 改變？把 pool path 與 gather path 的專家歸約順序統一（例如按 expert id 排序）會不會讓 cap invariance 回到 M1 = 100%？」

答案：分歧出現在第一個 chunk 大小不同的 prefill step，而上述修法完全無效。 以下是三臂實驗。

layer 0 routing 三臂完全相同，layer 1 就三分裂。 layer 0 是 GatedDeltaNet（線性注意力）層（full_attention_interval = 4）—— 序列掃描加上其周圍批次形狀相依的投影，正是 partition 敏感的那一塊。 擾動在 layer 0 的計算裡被引入：小到不足以翻掉 layer 0 自己的 router，大到足以翻掉 layer 1 的。

為什麼「統一歸約順序」無效

=== gather 使用量，每一臂的每一層 ===
  cap5:  407× "gather=0/8",  1× "gather=0/9"
  cap8:  391× "gather=0/8",  1× "gather=0/9"
  iso :  231× "gather=0/8",  1× "gather=0/9"
  1. gather=0 everywhere。 沒有任何一層走到 gather path。 cap5 最大 union 40、cap8 是 64，對上該層 143 可用格 （min_layer_slots 在 8 GiB 下是 106，最緊的層才是約束 —— 但即使取 106，64 也遠低於它）， 兩者都穩穩在 pool path。 → 沒有 pool↔gather 切換可以統一。
  2. 歸約順序已經是 cap 無關的。 llama-graph.cpp 的 moe_out = cur_experts[0] + cur_experts[1] + … + cur_experts[K-1] 沿著 k 序（router top-k 的順序）累加，不是 slot 序、也不是 sorted-union 序。 layer 0 三臂的 k 序完全相同。
結論：這個失效模式與 expert reduction 無關，也與 pool↔gather 無關。 按 expert id 重排歸約不會改變任何一個位元。

真正的機制鏈

CGC_POOL_MAX_TOKENS
  → clamp 到 n_batch → n_ubatch = min(n_batch, params.n_ubatch)
  → prefill 的 step partition 改變（5,5,5… vs 8,8,8… vs 5,3,5,3…）
  → 批次形狀相依的 kernel / 縮減順序改變
  → ulp 級差異
  → 某層 router 的 top-k 翻面（離散）
  → 隱藏狀態 ~0.1 相對差
  → ~1 logit 的輸出差 → 不同的 token → 生成完全岔開

注意：鏈條的前半段（partition → ulp）不是 bug，是「不同的 forward pass」。 模型的 forward 不對 partition 不變，這是模型與 kernel 的性質，不是 expert cache 能修的。

6. 跨模型：哪個前提先失效

把整個機制拆成四條前提，然後問「換一顆模型時，哪一條先斷」。答案不是靠推論，是靠 cap 探測的實測幾何。

四條前提

#前提形式斷掉的後果
P1槽位容量 cap × top_k ≤ usable_slots pool 不可用（不是變慢）
P2架構地板 cap ≥ n_rs_seq + 2（MTP ON 時 = 5） 載入即 abort
P3佈局無關 固定 cap，pool size 變化 → 位元相同 已成立（同一 build、兩個 cap 上各驗一次：117/117 與 103/103）
P4partition 無關 不同 cap → 位元相同 不成立，且跨模型都不成立（模型自身性質）

判讀

  1. 先斷的永遠是 P1（槽位容量）。 它與 層數 × 每 expert 位元組 × top_k / pool_bytes 成正比。 Ornith 在同一顆 4 GiB 池子上只拿到 cap 7（headroom +2），IQ4_XS 拿到 cap 6， 而 Nail IQ3 拿到 cap 8 —— 差別全在每 expert 位元組。 換一顆 expert 更大的模型，同一顆池子的可用 cap 會先掉。
  2. P1 斷掉的後果是「池子不可用」，不是「比較慢」。 Nail IQ3 在 2 GiB 是 cap = null：能塞進格數的 cap 違反架構地板，反之亦然。 這是離散的失效，沒有中間的降級解 —— 除非 gather/streaming 路徑可用（目前 gather=0，不可用）。
  3. P2 是硬地板，與池子無關，但 MTP 會把它從 0 抬到 5。 這意味著「開啟 MTP」會同時抬高 cap 下限（P2）與 union 需求（verify batch 4 tokens）， 所以小池子 + MTP 是最容易兩頭夾殺的組合。這是為什麼 cap 探測記錄裡 min_cap 全場都是 6。
  4. P3 目前成立，而且是唯一真正需要的。 但要注意它成立的前提是「cap 不變」—— 一旦 cap 因為池子變小而被迫下降（P1 逼的），P3 的實驗條件就不再是「只變池子」了， 這時候看到的差異是 P4（partition），不是佈局。這是跨模型最容易被誤讀的陷阱。
  5. P4 從來不成立，而且不可能靠 expert cache 修好。 它斷言的是「模型自身的 forward 對 step partition 不變」，而實測三種 partition 給三個答案。跨模型都一樣。
跨模型的正確問法不是「pool 4/6/8/10 是否 bit-identical」，而是 「在這個模型 + 這個池子上，usable_slots / top_k 是否仍 ≥ 5（MTP ON）」。 若否，這個 (模型, 池子) 組合根本不在可比較的範圍內，硬比就是在比兩個不同的模型路徑。

7. 決策建議

選項內容成本建議
A. 校正標籤 把 cap invariance 從「要求」改為「partition 敏感度報告」； pool-layout invariance（固定 cap、變池子）才是閘門。 已完成（閘門會印 partition + attribution） 採用
B. 解耦 partition 與 cap M1 工作項 1（CGC_POOL_SPLIT）的意圖，也是唯一能讓 P4 成立的架構路線。 已實作、已量測、已否證：full-width expert tensor 走 Metal wide path 會 fault； 且小池子在原理上不可能（一步的 union 必須整批放進池子）。 不做
C. 讓 forward 對 partition 不變 強制每個 per-token 縮減的結合順序與 batch 寬度無關（40 層，含 GDN 掃描）。 不是局部改動，且要付速度代價 不做
D. 固定 cap、只掃 pool 把 cap 視為由池子推導、不可獨立指定的量；實驗只掃 pool size。 零；這已經是通過的配置 採用（操作準則）
E. prefill 真正的槓桿 整層順序串流（把 1626 次隨機讀換成順序大讀）；這與 cap 曲線正交。 需要先修好 whole-layer 量測盲區 下一步

操作準則（給之後的每一次掃描）

  1. 先算 P1，再開機。 用 cap 探測（或 usable_slots / top_k）確認這顆池子走得通， 而不是先跑再說。
  2. 掃 pool 時把 cap 釘住。 若 cap 必須變（因為 P1 逼的），那次掃描就不是「pool 掃描」， 要在報告裡改名。
  3. PASS 只在 partn = same 時才有意義。 閘門已經會標。
  4. 不要把 cap = 5 那 +13–15% 當成可用的效能紅利。 它確實更快，但它換掉的是 partition，代價是 M1 1/391。

8. 誠實標註與重現

這份白皮書沒有主張的事

  • 沒有中間 activation dump。 「擾動起源於 layer 0」是從 「三臂 layer 0 routing 相同、layer 1 三分裂」推論的，不是直接量到的。 直接的因果位置（attention 還是 MoE、哪個 kernel）沒有量。
  • M1 只在 cap 6 vs 8、cap 5 vs 8 驗過，不是每個 cap。 cap=5 那格用的是舊的 ubatch 對齊（M1 3/82），已被正確對齊的 1/391、2/29 取代。 pool 不變性那組用的是 MTP ON 的既有 dump（既存產物，不是為本文件新跑的）， 其中主證（e50eb794，cap 8 與 cap 6 各三對）是同一個 engine stamp，但 不是同一個行程連續跑出來的 —— 每一格都是一顆新 server； 「同一 (cap, pool) 重跑兩次」的獨立行程對照由閘門的 8,8 控制組負責（35/35 PASS）。
  • 長文的定位與 harness 探針的 partition 形狀不同。 harness 探針較短，會出現 n_keep_tail 造成的長 4xN 尾巴 （例如 2x1,6x3,2x2,4x8），與 §4 的 2x1,5x11 不是同一串。 結論依賴的是方向（partition 不同 → 輸出不同；partition 相同 → bit-identical），兩份資料都支持這點。
  • cap 曲線是單一模型、單一池子（8 GiB）、MTP OFF 的量測。 cap=2 那格只在 MTP OFF 下存在（P2 地板）。曲線的形狀（8 是拐點）在 3 次獨立重測下可重現到 ~1%， 但沒有在別顆模型上重跑。
  • 六格矩陣的 prefill/decode 絕對值受機器狀態影響（page cache、swap、其他 agent）。 這份文件引用的是同一臂內的相對值與 bit-identical 判定，不是絕對 t/s 的排名。
