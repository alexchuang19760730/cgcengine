## 0. 一句話

我的模型把 **100% 的步時歸給權重流量**，而實測步時裡權重流量只佔 **9.2%**，
**80.0% 是 GPU busy**。模型在兩個標定點上「吻合」是因為它有 **3 個自由參數擬合 2 個點**——
那是必然吻合，不是預測成功。`-np 4` 沿著一個模型裡根本不存在的軸（job 大小／暴露與否）移動，
所以它錯 8 倍不奇怪，它壓根沒在描述那個東西。

## 1. 為什麼算的不同：三條獨立的原因

### 1.1 歸因錯了：步時裡 IO 只佔 9.2%

`Backup/phase_decomp/joint_capture_20260920_2144.json`（n=65 穩態 step，中位）：

| 分量 | ms | 佔 step |
|---|---|---|
| **union（GPU busy）** | **97.90** | **80.0%** |
| gap（GPU idle） | 23.52 | 19.2% |
| cb（專家 fill） | 11.26 | **9.2%** |
| wait | 105.64 | 86.3% |
| submit | 3.36 | 2.7% |

⇒ 即便把專家 IO 做到**完全免費**，步時也只從 122.39 → 111.13 ms，**t/s 只 +10.1%**。
一個只描述「讀多少 bytes」的模型，最多只能解釋這個 step 的 9.2%。

### 1.2 參數比標定點多：3 個自由參數擬合 2 個點

`step = (D + B·E) / BW_eff` 裡 **D、E、BW_eff 全部是反推出來的**（D≈790 MB、E≈381 MB/token、
BW_eff≈13.65 GB/s），而它只用來對過兩個點（B=1 → 85.8 ms、B=4 → 167.81 ms）。
自由度 3 > 約束 2 ⇒ **任何數據都會吻合**，這不是驗證。

而且那兩個標定點都在**同一條序列內**（batch 不會撐寬專家 union）——
也就是說模型從未在「job 結構改變」的軸上被檢驗過，`-np` 正是那個軸。

### 1.3 驅動項會換：N=1 是 GPU-bound，N=4 是 job-overhead-bound

| | N=1 | N=4 |
|---|---|---|
| 步時 | 166.4 ms（72.04 ms/tok × 2.31 tok/step） | ≈ 4 600 ms |
| GPU busy 佔比 | **≈80%** | 被 job 淹沒 |
| SSD bytes/step | 145 MB | 3.3 MB（**少 44×**） |
| jobs/step | 1 142 | **13 692** |
| 平均 job 大小 | **133 KiB** | **≈257 B** |
| 隱含 per-job 服務時間 | ~147 µs（含 GPU） | **~336 µs** |

⇒ 一個模型在 A 區（GPU-bound）標定、在 B 區（job-bound）外推，兩個區的驅動項不同。
**這不是參數沒調好，是模型少了一個維度。**

## 2. 新量到的：IO 粒度曲線（這條曲線本身是對的）

`scripts/check/io_granularity_curve.py run --threads 1 4`，對 16.36 GiB gguf 做隨機 offset
`pread`（`F_NOCACHE` 繞過 page cache）：

| request size | 1 thread GB/s | 1 thread µs | 4 threads GB/s | 4 threads µs |
|---|---|---|---|---|
| 256 B | 0.002 | **97.0** | 0.008 | 28.3 |
| 4 KiB | 0.037 | 103.6 | 0.116 | 32.8 |
| 64 KiB | 0.422 | 144.5 | 0.972 | 62.8 |
| **128 KiB（≈今天的 job）** | **0.609** | **200.5** | 1.468 | 83.2 |
| 512 KiB | 1.108 | 440.6 | 2.021 | 241.6 |
| 1 MiB | 1.342 | 727.7 | 2.126 | 459.4 |
| 4 MiB | 1.794 | 2 177.5 | **8.241** | 474.0 |

兩項擬合 `t = size/BW + tau`：**BW = 2.03 GB/s，tau = 136 µs**
（最小點實測 97 µs vs 擬合 136 µs ⇒ tau 並非常數，小 request 端實際更低）。

**三個結論：**

1. **一次 pread 的固定成本 ≈ 95–100 µs** —— 讀 256 B 要 97 µs，讀 4 KiB 要 103.6 µs。
   **在 4 KiB 以下，讀多大完全不重要，重要的是讀幾次。**
2. **128 KiB 單執行緒只有 0.609 GB/s**，而 4 MiB × 4 執行緒有 **8.241 GB/s** ⇒
   **同一顆 SSD 上，純粹因為（大小, 併發）可以差 13.5×**。
   與既有「M4 SSD ~7 GB/s 循序讀」的認知一致（4 執行緒 4 MiB 量到 8.24）。
3. **交叉驗證成功**：`llama-expert-cache.cpp:48` 的既有注記寫
   「measured on M4: serial **~204us cold** / 90us warm」，我獨立量到 128 KiB 單執行緒 **200.5 µs**
   ⇒ 兩個獨立儀器對上，**池的 job 確實是 ~128 KiB 的 pread，每次 ~200 µs 冷讀**。

⚠️ 邊界：本曲線給的是「裝置 + syscall」的上界。池的 fill 還經過 queue/mutex/thread
（`fill_segments_concurrent`：one thread per segment, joined before return），
所以**曲線不能拿來推「池今天實際多快」**，只能用來推「合併讀**理論上**有多少空間」。

## 3. 那 25 還有沒有機會？

### 3.1 預算：要的是 **GPU busy 快 1.8–2.2×**，不是 IO

- 現況：13.78 t/s（HTTP 口徑）＝ 72.04 ms/token ＝ **166.4 ms/step**（2.31 tok/step）
- 目標：25 t/s ＝ 40 ms/token ＝ **92.4 ms/step** ⇒ step 要 **快 1.80×**
- 拆開（用 §1.1 的佔比，total 122.39 ms）：
  - 若 gap（19.2%）不動 ⇒ **GPU busy 必須快 2.20×**
  - 若 gap 同比例縮 ⇒ **GPU busy 必須快 1.80×**

⇒ **25 是一道 GPU 題，不是 IO 題。** IO 那 9.2% 就算歸零也只有 +10.1%。

### 3.2 但硬體天花板遠在 25 之上——25 不是被物理擋住

每 step 必須走的 RAM 流量：dense **827 MB** ＋ 專家（命中 361 MB ＋ miss 148 MB）≈ **1.34 GB**。
GPU busy 97.90 ms ⇒ **實測有效頻寬 ≈ 13.6 GB/s，約 M4 統一記憶體峰值（~100–120 GB/s，
本機未實測）的 11%**。

| | ms/step | t/s |
|---|---|---|
| 實測 | 97.9（僅 GPU busy） | 13.78 |
| @100 GB/s 地板 | 13.4 | **≈172** |
| @120 GB/s 地板 | 11.1 | **≈207** |

⇒ **機器的記憶體頻寬地板約在 170–210 t/s，是 25 的 7–8 倍、是現況的 12–15 倍。**
25 不是撞牆，是**效率只有 11%**。

### 3.3 已知的槓桿全部加起來仍不到 25

`docs/G1_G7_SWEEP_2026-09-20.md`：G4 融合上界 11.5%（＜門檻 12.8%）、G1 不可達、
G6 實測淨負、G7 算術不可達（k=3 ⇒ 天花板 14.9）、只剩 victim rule −4~5%。
**全部 sums ⇒ 13.2–13.8 t/s。**（既有結論，未被本次推翻）

### 3.4 唯一還沒被量過、且理論空間夠大的槓桿：expert GEMV/MUL_MAT kernel 本身

- GPU busy 跑到 **11% 的記憶體頻寬** ⇒ kernel 效率是主要嫌疑。
- 形態是**瘦高 GEMM**：256 專家、top-8、batch 2–4 列、IQ3_XXS 即時 dequant。
  這種 shape 用通用 MUL_MAT 跑，落在大頻寬的 10% 是常見的。
- **前例（使用者另一專案 TurboFieldfare）：自寫 int4 GEMV 拿到 2.5–3.4×。**
  同一類工作在同一顆 M4 上做過 2.5–3.4×，所以「2.2×」不是瘋狂的數字。
- ⚠️ **但 GPU busy 裡 kernel 佔多少，今天沒有人量過**——G4 只量了「dispatch 數」
  （MUL_MAT 254/步＝23.1% 是**次數**不是**時間**；elementwise 376＝27.7% 也是次數）。
  **時間佔比是未知。**

⇒ **結論：25 在物理上可達（地板 ~7–8× 於 25），在已知槓桿上不可達（全部 ⇒13.2–13.8）。
唯一可能的路是 GPU kernel 效率，要先花一次量測把「MUL_MAT/專家 GEMM 在 GPU busy 裡的時間佔比」
量出來，否則 2.2× 只是一個願望。**

## 4. 下一步（按性價比排序）

1. **量 GPU busy 的時間構成**（新儀器或擴充既有 KIND×OP）：MUL_MAT／elementwise／
   attention／SSM／norm 各佔多少 ms。這是把 3.4 從「願望」變成「數字」的唯一入口，
   不起 server 也能做（讀既有 log）。**先做這個。**
2. **不要為 25 去動 IO**：N=1 的 fill 只佔 9.2%，上界 +10.1%。
   但 §2 的曲線要留著——**在 IO 被暴露的區間（冷池、長 ctx、`-np` ≥ 2）它是決定性的**，
   那裡 job 大小 133 KiB → 257 B 就是 27× 單流損失的直接成因。
3. **`-np` 維持「已排除」**（§EN-366、本次未翻案）。

## 5. 誠實邊界

- §1.1 的佔比來自 **HTTP 形狀**的聯合捕獲（total 122.39 ms），而 §3.1 的 13.78/166.4 ms 是
  另一個 run ⇒ **佔比與絕對值是兩個 run 混用**。方向（GPU 80%）穩，數字不該逐位引用。
  記憶既有約定：「聯合捕獲只引用閉合關係與佔比，不引用絕對步時」。
- 1.34 GB/step 的 RAM 流量是**從權重幾何算出來的**（dense 20.68 MiB/層 × 40、
  專家 1.083 MiB/個 × ~470 lookup/step），**未實測**。
- 100–120 GB/s 是 M4 量級的**引用值**，本機未實測 ⇒ 地板 172–207 t/s 是量級，不是承諾。
- 池的 fill 經過 queue/mutex/thread，`pread` 曲線是**上界**，不是池的現況。
