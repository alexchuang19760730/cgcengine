## 2. 25 t/s 的算術（兩軸，不是一軸）

`t/s = mean_len / step` ⇒ **25 t/s 的等值線是 `step = mean_len × 40 ms`**。

| mean_len | 25 需要的 step | 在地板 149.24 下的上限 | 在地板 97.90 下的上限 |
|---:|---:|---:|---:|
| 2.610 | ≤ 104.40 ms | 17.49 t/s ✗ | **26.66 t/s ✓** |
| 2.880 | ≤ 115.20 ms | 19.30 t/s ✗ | **29.42 t/s ✓** |
| 3.060 | ≤ 122.40 ms | 20.51 t/s ✗ | 31.26 t/s ✓ |
| 3.375 | ≤ 135.00 ms | 22.61 t/s ✗ | **34.47 t/s ✓** |
| 3.731 | ≤ 149.24 ms | 25.00 t/s（**地板上**） | 38.12 t/s ✓ |
| 4.000（k=3 硬頂） | ≤ 160.00 ms | 26.80 t/s | 40.86 t/s |

**讀法**：地板是 149.24 時，25 只在「ml ≥ 3.731 且 step ≤ 149.24（＝地板本身）」這個**角**成立；
地板是 97.90 時，可行域是「step ≤ 135 ms 且 ml ≥ 3.375」—— **而 3.375 已經量過**。

⇒ **「25 不可達」這個結論（§EN-341、§EN-348）用的是 149.24 那個地板。它今天被打了一個問號。**

## 3. ★ 為什麼地板還沒定：同一個量讀到兩個值

| 讀數 | 來源 | 當時的機器狀態 |
|---:|---|---|
| **union_sum 149.24 ms** | 交付 work row（023021） | 高 swap、`cb = 74.18 ms`（29.9%） |
| **union_sum 97.90 ms** | 聯合捕獲（214450） | 啟動時 free 84%、`cb = 11.26 ms`（9.2%） |

§EN-350 的直接發現：**`cb` 是水位敏感的，差 6.6 倍**（74.18 → 11.26）。而 `union_sum` 是
**GPU 時鐘上的段跨度**，理論上不該隨水位變 1.52× ⇒ 兩種可能都還活著：

- **(a) 形狀不同**：聯合捕獲是 HTTP 路徑、row 混了 `ntok=2/8`，不是交付的 `ntok=4` verify 步
  ⇒ 97.90 不是交付形狀的地板，**149.24 才是真的**。
- **(b) 水位真的會拖 GPU 段**：高 swap 下 GPU buffer 配置／缺頁拉長段跨度
  ⇒ 149.24 是「擁擠機器上的地板」，**乾淨窗口的交付地板可能接近 100 ms**。

**兩者今天都沒被判掉。** 而它們給出的結論相反：一個是「25 只在角上」，一個是「25 在量過的 ml 上就成立」。

## 4. 分支判決

### 分支 A（地板 = 149.24）— **不可達**
- 需要 step 從 247.98 → ≤160（−36%），即移除 **88 ms 的 95.17 ms gap（92%）**；
- 同時 ml 從 ≤3.375 → ≥3.731（+11%，且 3.731 是 k=3 上界的 93%，**從未被量過**）；
- 兩個軸都必須貼到物理極限 ⇒ **不是工程問題，是配方問題**。

### 分支 B（地板 ≈ 98）— **邊緣可達**
- 需要 step ≤ 135 ms（ml 3.375）或 ≤115 ms（ml 2.880）；
- 低水位那次實測 total **122.39 ms**（gap 只剩 23.52）⇒ 若交付形狀在乾淨窗口落在 ~122 ms，
  則 **ml ≥ 3.06 就過 25** —— 而 3.06 **低於**已量過的 3.375、只比 2.880 高 6%；
- ⇒ 在這個分支裡，25 的門票主要是「**把機器狀態做成乾淨**＋**ml 從 2.88 推到 ~3.1**」，
  而不是「寫一個 dispatcher」。

**25 需要 ×1.99。** ⇒ 已指名槓桿沒有任何一個在 3 倍以內；**只有分支 B ＋ 一個乾淨窗口才有這個量級。**

## 6. 唯一決定性的下一步（一支跑，不是三個月）

**一次「乾淨窗口 ＋ 交付形狀 ＋ 同臂」的聯合讀數**：`step`、`union_sum`、`gap`、`cb`、`mean_len`
五個數進同一份 log。判準預先寫死：

- 若交付形狀在乾淨窗口下 `union_sum ≈ 149` ⇒ **分支 A 成立，25 判死，目標應改寫（16 或改配方）**；
- 若 `union_sum ≈ 98–110` 且 `total ≈ 120–135` ⇒ **分支 B 成立，25 是「ml ≥ 3.06~3.4」的問題**，
  主戰場從 dispatcher 移到 **ml 軸（G6）與水位紀律**。

執行條件（照既有紀律）：哨兵認可的窗口（§EN-345/346）、`--reps 3` 固定、`prod25-stream` 口徑、
`lsof -nP -iTCP:8080` 與 `pgrep -fl llama-server` 先查空。**這支跑同時也是 G2/G5 的複查機會。**

## 8. 誠實邊界

1. **12.57 本身帶 ±27% 單臂噪音**，且下午三次重讀全落在 6–10 ⇒ 連基線都不穩。
2. **122.39 ms 是 HTTP 非交付形狀**（§EN-350 自註），只能拿來提問，**不能拿來當地板**。
3. `mean_len` 的 2.610／2.880／3.375 **分屬不同臂**，沒有一個與 step 的讀數同臂。
4. 分支 B 若成立，也只是「**可能**」——它還需要 ml ≥ 3.06 與一個穩定的乾淨窗口，兩者今天都沒有。
5. 本文沒有評估「改配方」（k、量化、模型）。k=3 寫在交付 argv 裡 ⇒ 改它等於改交付定義，不是優化。
