Ideal Shape — 從原理推導

不量測，從計算機結構原理 + 程式碼邏輯推導出理想形狀
1
基本原理：記憶體頻寬是怎麼浪費的？
DRAM Row Buffer Locality（行緩衝區局部性）
DRAM 有一個 row buffer（一行，通常 1-2 KB）。
讀取位元組如果在同一行：~10 GB/s（fast path）
讀取位元組如果跳到下一行：~2 GB/s（row activate penalty）

⇒ 頻寬利用率低的根本原因：讀取位置跳來跳去，每次都觸發 row activate
Memory-level Parallelism（記憶體層級平行度）
DRAM 有多個 bank，可以同時服務多個請求。
如果一次只讀一個 expert，讀完才讀下一個：流水線沒填滿
如果同時讀多個 expert：流水線填滿，頻寬利用率高

⇒ 頻寬利用率低的第二個原因：一次只讀一個 expert，平行度不夠
Amdahl's Law（阿姆達爾定律）
如果 kernel launch overhead 占了 10%，就算把計算速度提到無限快，整體也只能快 11%。
如果一次 dispatch 太小（讀的 bytes 太少），overhead 占比就高。

⇒ 頻寬利用率低的第三個原因：每次 dispatch 太小，overhead 占比太高

理想形狀：參數應該是什麼？
參數 現況 理想值 為什麼
Gather 方式 逐個讀 批次讀 一次把多個 expert 的讀取合併，提高連續性
每個 dispatch 的 bytes ~170 MB（一個 expert） ~680 MB（4 個 expert） 越大，overhead 占比越低，流水線填滿

Expert 佈局 分散儲存 分組/打包儲存 把常用 expert 放在一起，或把多個 expert 打包成連續區塊
Prefetch 無 有（提前讀） 提前讀下一個 expert，隱藏 IO 延遲

數學推導：為什麼 65% 就是 25 t/s？
// 基本常數 B_total = 120 GB/s // M4 LPDDR5 總頻寬 B_used = B_total × utilization // MoE 部分每步需要讀多少 bytes bytes_per_step = 8 experts × 170 MB = 1360 MB // MoE 部分的時間 = bytes / bandwidth t_moe = bytes_per_step / B_used // 現況：utilization = 25% t_moe_current = 1360 MB / (120 × 0.25) = 1360 / 30 ≈ 45 ms // 理想：utilization = 65% t_moe_ideal = 1360 MB / (120 × 0.65) = 1360 / 78 ≈ 17 ms // MoE 部分節省：45 - 17 = 28 ms // 總步時從 83 ms → 55 ms → ~18 t/s // 再加上 MTP、dense 等部分的優化 → 25 t/s
注意：以上是粗略估算，實際數字會因為以下因素變動：
1. Expert 實際大小（IQ2_S 是多少 bytes）
2. 其他部分（MTP verify、dense GEMV）也會影響總步時
3. L2 cache 命中的部分，不用讀 DRAM，不算在頻寬裡

但數量級是對的：MoE gather 的頻寬利用率從 25% 拉到 65%， 就是把 MoE 部分的時間減半以上，這是最大的槓桿。
5
結論：理想形狀是什麼？
理想形狀的核心：把 MoE gather 從「逐個讀」改成「批次讀」

具體來說：
1. 把多個 expert 的讀取合併成一次 dispatch — 不要一個一個讀
2. 讓讀取位置盡可能連續 — 提高 DRAM row buffer 命中率
3. 充分利用 memory-level parallelism — 同時讀多個 expert，填滿 DRAM 流水線
4. 盡量加大每次 dispatch 的 bytes — 降低 overhead 占比

這樣做完之後：
→ MoE gather 頻寬利用率從 25% → 65%
→ MoE 部分的時間從 ~33 ms → ~16 ms
→ 總步時從 ~83 ms → ~40-50 ms
→ 對應 20-25 t/s

這就是形狀世界模型的理想形狀。
不是某個 knobs 調大調小，而是整個 gather 的方式要改 — 從「串行逐個讀」變成「並行批次讀」。
