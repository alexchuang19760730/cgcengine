3. 不能說的話

這一節照 skill cgc-prefill-thermal-delivery §1 與 §2 寫，因為它是這份文件裡最容易 被下一個人誤引的一段。

不可以說為什麼
「250 t/s 隨時可重現」prefill 是機器狀態的讀數，不是產物性質。同一份 binary、同一 A11 指紋、同一組 [perf]，prefill 可以在 118 與 290 之間移動
「這是 COLD-STATE 的交付數字」本次標籤是 UNKNOWN-STATE（安靜區間未知）。COLD-STATE 的定義是距上一臂結束 ≥1800 s，本次不成立
「發射讀到 0 ⇒ 箱子是冷的」這是兩件事。2026-09-16 的同 binary 對照：COLD 得 254.29 / 282.38 / 265.27，HOT 得 167.41–200.58。0 只是閘門開
「安靜夠久 ⇒ 等級一定回 0」反例：安靜 18 s 的臂 req1 = 289.86，安靜 34 s 的臂只有 166.95。安靜秒數不是條件
「swap 是條件」它是果。相反順序的實測：289.86 t/s @ used 4975.06M，而 13:51 的慢臂 @ 5066.06M
把 decode 的 4.72 t/s 當異常那是 req1 的冷decode（第一次生成，金屬管線與頁面都還沒暖）。warm 的兩次是 16.95 / 17.15

與 4.1 的 12.62 不可直接相比，原因有兩個，而且都不是「哪個比較快」：

② 本節的 16.95 / 17.15 沒有做過熱條件，而 4.1 那張表它自己也標了熱沒控制。

⇒ 本節能被引用的述句是：「同一次載入、同一組 2873-token 請求之下，warm decode 是 16.95 / 17.15 t/s」。 不能引用為「decode 已經到 17」。

5. 為什麼 accept 下降而吞吐上升

4.1 那張表裡有一件反直覺的事：accept 從 73.81% 降到 58.25%，而 decode 從 8.62 升到 12.62。 兩個都是真的，而且不衝突 —— 修前 verify 批次的 token ≥ 1 是用別的 token 的專家算的， 所以「accepted」是拿錯的分布比出來的，而它把這個指標抬高了。

後果（這是本節存在的理由）：任何只看 accept的 M4 決策，都會 留住缺陷、退掉修正。M4 原本的離開條件之一寫的是「accept ≥ 60%」—— 在 2026-09-14 就已經量到 70.39%（超過），但那個數字屬於同一個被抬高的家族。

⇒ 這條判準應該作廢，改成「MTP-on ≥ MTP-off ＋ M1/M2 = 100% with MTP ON」。 並且修前記錄的每一個 accept 數字都屬於那個 regime（含 2026-09-14 的 70.4% 與 roadmap 的 19.9%）。

5.1 連帶的一條：修前的 M1 通過只證明「不變性」

ROUTING_TRACE §15.2 的原話是 cross-pool invariance (M1/M2) passed while the ids were wrong for all of them。缺陷在共用的程式路徑上，所以每一臂、每一個池大小都用同一種 錯誤方式路由 token ≥ 1，於是它們彼此一致。2026-09-14 那個「M1 117/117」屬於這一類： 它必須被引用為「那些池彼此一致」，永遠不是「那些數字是對的」。 後者只有對 v6 之後的參考才成立 —— 也就是本文件 §1.2 跑的那一個。

7. 同一天的相鄰裁定：M6 的池幾何

同一天在同一個 repo 上還有另一組結論，與本文件的 decode 數字共用同一台機器的同一段時間， 所以一併指向它而不複述：

  • docs/M6_QUANT_GEOMETRY_PLAN_2026-09-17.md §4.9：引擎自己印的逐層 miss 歸因 （compulsory／capacity／evictions／layers_distinct_over_slots／ worst=layer … distinct=… slots=…）在真實 decode 負載上量到 capacity 佔 miss 的 41.3–45.6%，而最差的層需要 239 個 distinct 專家 —— 遠高於「工作集 ≈149、149 個 slot 就蓋得住」的假設。
  • 同檔 §4.10：因此設定路線（花小額 slack 換 slot）不可交付，而 M6 的本體 （per-expert 1.769 → 1.122 MB）早已在出貨檔裡（實測 1.0703 MiB）⇒ 頭條價值已兌現、未被推翻。
  • 它與本文件的交集：同一個修正把 hit 由 57.1% 抬到 72.0%（與池無關） ⇒ 修前的 hit 不能當池幾何的 before。

8. 誠實邊界

這份文件不主張：

  • 不是交付級的 prefill 數字。熱標籤是 UNKNOWN-STATE；COLD-STATE （安靜 ≥1800 s）本次不成立。IDLE_BEFORE=0 意味著協定等待沒有被施加。
  • 不是 A/B。沒有對照臂，所以本文件的任何 t/s 都只是「這一臂的讀數」， 不是「這個設定的性質」。
  • decode 的兩個來源不可互相比較（形狀不同、熱條件不同，見 §4.2）。
  • 48 題品質套件今天沒有跑完一次。今天稍早的兩臂都中斷（一臂 GPU OOM、一臂被別的 session 的 run_server.sh preflight SIGTERM）⇒ 那份 invalid=True 的檔案不是分數。
  • 沒有碰 src/、沒有重建。本文件是量測與文件，不是引擎改動。

未跑的東西要明寫未跑：edge0head／graft carrier、6–10 GiB 的 prefill 格、--no-mmap 的 prefill 格、以及交錯 A/B 形式的 prefill 比較，本次都沒有做。
