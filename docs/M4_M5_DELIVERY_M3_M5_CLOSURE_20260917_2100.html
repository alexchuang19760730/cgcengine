2. M4：交付了什麼、怎麼判的

2.1 交付（三個工作項）

#工作項狀態位置
1拒絕取樣：min(1, p_t/p_d) 接受、被拒時從殘差 max(0, p_t − p_d) 重抽 已實作 common/sampling.cpp 的 cgc_rejection_accept()
2batched-union gather 套進 verify 未做（依賴已具備，非被擋）—
3三段拆解：accept／tokens/forward／ms/forward 已實作 common/speculative.cpp 的 CGC-MTP-PERF

2.2 兩個設計要點（寫在 code 裡，不是事後解釋）

  • RNG 隔離：接受判定用 common_sampler_get_seed() 另起一條確定性流， 不碰 sampler chain 的流。否則每一步 verify 都會推進鏈的 RNG，A/B 就從「比接受規則」 變成「比兩條不同的隨機軌跡」。
  • 殘差抽樣前按 token id 排序：unordered_map 的迭代序未定， 未定的抽取序會讓這條路徑不可重現。

一個可證的性質：在 greedy／gate 配置下 p 與 q 都是 one-hot 且同點 ⇒ min(1, p/q) 非 1 即 0 ⇒ 規則退化成正被它取代的精確相等。 所以 gate 臂不論開關都逐位元相同 —— 這正是 D5 兩臂都 9/9 的原因， 而機制只在取樣（temperature > 0）時咬人。

4. 一個不能讀成增益的 A/B

CGC_PREROUTER 開／關，各 4 個請求（prompt 208 token、decode 96–112 token）、 temperature = 0、同一顆 binary、池 8 GiB、開跑前熱狀態是 COLD （notifyutil -g com.apple.system.thermalpressurelevel = 0）、無其他量測行程：

A（CGC_PREROUTER 未設）B（=1）
decode t/s（按順序） 3.64 / 5.25 / 9.30 / 7.307.59 / 7.33 / 7.66 / 3.97
decode t/s 中位6.287.50（+19%）
prefill t/s（按順序） 17.6 / 24.2 / 22.0 / 31.628.9 / 39.6 / 41.7 / 38.3

這組數字不能用來判 overlap，而且它的結論是「功效不足」，不是「無差異」：

  • A 臂自己的散佈是 2.6×（3.64 → 9.30），而判準是 10% ⇒ 功效不足。
  • B 跑在 A 之後、環境更暖（prefill 17.6→31.6 對 28.9→41.7）⇒ 「+19%」與暖機方向一致， 是混淆不是增益。
  • 因此「B 的中位比 A 高 19%」沒有證據價值。寫在這裡的唯一目的是防止它日後被引成 「M5 有 +19%」。

原始讀數：Backup/cgc_logs/en_probe_m5ab-off1.json、 Backup/cgc_logs/en_probe_m5ab-on1.json（Backup/ 是 gitignored）。 驅動 /tmp/en_m4m5_probe.py 是一次性探針，不在版控內、也不適合當交付儀器： 它不交錯兩臂、每臂只起一次 server、也不報中位與 IQR —— 正好是本文判定為「功效不足」的那個形狀。

5. M3：失敗分支的結案

離開條件（docs/ROADMAP_PREFILL250_DECODE25_2026-09-13.md §M3 原文）： 成功 ⇒ decode（MTP off）≥ 15 t/s 且 M1/M2 = 100%；失敗 ⇒ 寫一份「找不到路」的結論， 附上 M0 的剖面表當證據。

判定未達（可引用值 10.78 t/s，16:49 的 NOMINAL 剖面，與 09-16 逐字吻合；15 需要 1.39×）。 失敗分支的交付物即 docs/M3_VERDICT_2026-09-17.md，它比 roadmap 要求的多做了三件事：

  1. 附了剖面證據（CGC-PHASE 的相位拆解 ＋ CGC-GPUTIME ＋ CGC-DECPROF）。
  2. 把三條路正式關閉：圖建構／alloc／inputs = 0.07%（0.023／0.037／0.026 ms 對比 compute 118.5 ms —— 差三個數量級，熱不可能改變）；IO／填槽 = fill_wait 0.000 ms。
  3. 把兩個儀器正式關閉：CGC_PHASE_TIMING（compute == gpu 逐位相同 ⇒ 拆不開）； CGC_VERIFY_OP_TIMING（目標判定含 node->src[2]->ne[1] > 1 ⇒ 只在 T>1 生效，而 M3 的判準是 T=1 ⇒ 對 M3 零輸出）

⇒ debug-verify-path-breakdown.md 那組逐型別數字（gate／up／down ≈ 0.8／0.8／1.0 ms） 不能移植到 T=1 的 decode。唯一活路是逐節點 GPU 時間（Metal counter sample buffer）， 因為 CGC-GPUTIME 的粒度只到 segment（＝層）。

正確述句：「M3 未達標，但失敗已按離開條件的另一支記錄成可稽核的結論， 並指名了能裁決它的量測。」不要把「M3 今天關掉了三條路」讀成「M3 有進展所以快達標」。

這份 D5 的歸屬與「commit 前重跑失敗」的交代（照實寫，不摺進「通過」）：

  • commit 前的重跑失敗：以 --tag en-m4m5-commit 重跑時，server 在 載入模型階段被 SIGTERM（run_server.sh: line 1992: … Terminated: 15）， 未寫出 summary、未取得判定。原因是記憶體壓力：vm_stat 的 Pages free 只剩 82 MB（5009 × 16384）， 而 vm.swapusage 是 used 10351.69 MB / 11264 MB、 Swapins 111695859 / Swapouts 131502717 —— 那是本輪連跑兩次探針（各載入一次 13 GB） 與兩次 gate 疊出來的 carried swap，正是 M3_VERDICT §D 記載的那個序列效應。
  • 它能不能代替？重跑晚於 run_server.sh 的兩處修正（19:39）。 那兩處是註解與兩個條件式 allowlist 塊（條件皆為 -n "${VAR:-}"， 分別是 CGC_PREROUTER／CGC_PREROUTER_TOP_K／CGC_MTP_REJECTION 與 LLAMA_EXPERT_CACHE_PREFETCH_DBG）⇒ 在 gate 的跑法（不設這些變數）下， SERVER_ENV 逐項不變。這是讀 diff 可確認的，不是推理的省略。

⇒ 本 commit 引用的 D5 是 en-m4m5-inert；它不是「當前 run_server.sh 上跑出來的」， 而是「同一顆 binary、gate 跑法下等價的 run_server.sh 上跑出來的」。兩者的差距已逐條列在上面。

第二臂（顯式開 M5）的數值也全是 9/9，但 gate 判 INVALID COMPARISON， 唯一的 config diff 是 ENV.CGC_PREROUTER: ref='<absent>' now='1'：

GATE en-m5-pre: INVALID COMPARISON -- reference was dumped under a different
  numerics-determining configuration (1 diffs).
  observed M1=9/9  M2=9/9  M3=9/9  n=9 (printed for information, NOT a verdict)

7. 不能說的話

  • 不能說「M4 的拒絕取樣已被證明有增益」 —— 2.3 節的兩個讀數不是配對實驗（n=2 輪、 分母不同、不同 server 啟動）。能說的是「方向與理論一致」。
  • 不能說「M5 量過了，沒差」 —— 4 節的 A/B 功效不足（A 臂散佈 2.6× 對判準 10%）。 能說的是「上界論證顯示增益 ≈ 0」（3.2 節），而不是「量出來是 0」。
  • 不能說「M3 有進展」 —— 它未達標，且今天沒有可執行的下一步； 今天的產出是「把路關掉」與「指名唯一活路」。
  • 不能把 12.57／9.59 當成 decode 的絕對值 —— 它們綁在 mtp_accept_ab.py 那個 harness（12–15 token prompt、熱狀態未控制）上， 與 10.78／12.62 那個家族不可比。可引用的是比值（+31%）。
  • 未做：M4 工作項 2（batched-union gather 套進 verify）；M1 的 6／10 GiB 池、 union-routable、chunk 2048、RSS @ 10 GiB；48 題品質； M5 的 decode-only gate 修正。
