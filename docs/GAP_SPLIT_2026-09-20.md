# The 95 ms gap: work or dependency? (instrument + pre-registered rule)

**Date** 2026-09-20 · carrier `Nail-…-IQ3_XXS-denseIQ4X`, MTP on k=3, pool 8 GiB, profile `prefill250`
· instrument gated on the existing `CGC_HOOK_SPLIT`

## 0. The one question

A delivery decode step is `247.98 ms` with an 95.17 ms window in which **the GPU has nothing to do**
(`CGC-GPUTIME: gap`, sampled in `hook_seg` as *previous segment's GPU end → this segment's start*).
Two readings demand opposite actions:

| if the gap is | then |
|---|---|
| **host work** — the host is executing code while the GPU waits | the dispatcher can hide it (segment-split submit, line A); L3 has a landing spot |
| **dependency** — the host is *waiting* for the GPU's own output | nothing can hide it; the `union_sum 149.24 ms` floor stands as unreachable and L3's 22.6 ceiling is not real |

This is the measurement that decides whether `docs/TARGET25_TWO_AXIS_2026-09-20.md`'s feasible band
exists at all, so its rule is fixed **before** the reading (below), not after.

## 1. The instrument

`CGC-GAPSPLIT`, one line per graph with ≥5 MoE layers, gated on the EXISTING `CGC_HOOK_SPLIT`
(the number is only interpretable next to the hook's own sub-split, so it reuses that switch rather
than adding a fourth name for the same cost):

```
poll      host blocked on segment i's completion            == dependency (not idle time)
hook      the top-k callback: ids + union + pool fill       == host work (see CGC-EBSPLIT/FSSPLIT)
tail      hook bookkeeping after the callback
submit    encode+commit of segment i+1 (reuses dp_last_submit_us; no new timer)
idle_host hook + tail + submit
gap       the GPU-clock idle window from CGC-GPUTIME
ratio     idle_host / gap
```

Placement is forced by the shipped order (`submit_ahead=false`): `hook_seg(i)` runs *before*
`submit_seg(i+1)`, so the callback executes while the GPU is genuinely idle — which is why the
callback's cost can appear in the gap at all.

`gap=unmeasured (CGC_GPU_TIMING off)` is printed as text, never as `0.00`: absence is not zero.

**Second level, same run.** `CGC_HOOK_SPLIT` also arms `CGC-EBSPLIT` (assign/collect/submit/wait/
publish inside `ensure_batch`) and `CGC-FSSPLIT` (submit/wait inside `fill_segments_pool`). Those are
what separate the two things `hook` lumps together: *processing the ids* (GPU output dependency) and
*waiting for expert bytes* (I/O — movable only if something else can carry them).

## 2. Pre-registered decision rule

```
ratio >= 0.80   -> the idle window is HOST WORK; L3 has a landing spot
ratio <= 0.40   -> DEPENDENCY/PIPELINE; L3 cannot reach the union floor
0.40 < r < 0.80 -> MIXED; report the split, claim nothing, and take a second regime
gap - idle_host < 0 -> INSTRUMENT DISAGREEMENT; neither number may be quoted
```

## 2b. Per layer: spread over the 41 segments, or owned by a few?

The aggregate ratio says *what* the window is. It cannot say *where* it lives, and the two answers need
different work: a per-layer hook problem is fixable in that hook, a per-segment round trip is not.

`CGC-GAPSPLIT-L` prints one row per layer, keyed exactly the way the decode profile is keyed (the
top-k tensor's `-<layer>` suffix), so the two tables join on layer identity. The GPU side is **reused**
from `dp_lay_gap` instead of measured twice -- which is why this table also needs
`CGC_DECODE_PROFILE=1`, and why the engine prints a line saying so when it is off, rather than a
silent table of zeros. `CGC_DECODE_PROFILE_ALL=1` is required for the verdict: without it the engine
prints only the top 8, and a top-8-only log cannot support a share-of-total claim (`gap_split.py`
refuses it as INVALID instead of computing a smaller denominator).

**Pre-registered concentration rule.** A uniform step over 41 layers puts 8/41 = **19.5%** of the idle
window in the top 8 rows, so that is the baseline, not a threshold:

```
top-8 share >= 40%   -> CONCENTRATED: those layers' hooks own the window -> fix the hook
 top-8 share <= 25%  -> SPREAD: near the uniform baseline -> per-segment structure;
                        a per-layer hook change cannot remove it
 in between          -> MIXED: report the table, claim neither
```

## 3. Prediction, and the third possibility the ratio cannot see

From the ledger's own cross-check (`gap 95.17 ≈ cb 74.18 + submit 10.09 + 10.9`), the prediction is
**ratio ≈ 0.89 ⇒ "host work"**. Two ways that prediction can be wrong, both of which the rule above
handles:

1. under swap the `hook` term absorbs page-fault stalls, so a below-floor run is **biased toward the
   answer that justifies building L3** — which is why the capture waits for the documented 8000 MB
   window instead of lowering the floor (`Backup/phase_decomp/gap_split_capture.py`);
2. `ratio ≈ 0.9` says the host is *working*, not that the work can be **moved**. If `CGC-FSSPLIT`
   shows the hook's cost is `wait` on expert bytes that are needed *by this very segment*, then the
   data dependency is on I/O rather than on the argsort, and a prefetcher cannot help — L1 already
   measured `issued=0` (no cold candidates) in this regime. That case reads as "host work" and is
   still not implementable, and it is exactly the F2 family's `treatment-application null`.

## 3b. The reading (2026-09-20 21:49, the capture that ran)

Window: the converged gate admitted (**reclaimable ~9.5 GB at launch, launcher `memory_pressure`
80-82%**, so both definitions agreed — the first run the single decision let through). Same build gated
first: `summary_gap_split_build.json`, **M1 9/9, M2 9/9, M3 9/9**. Arm: MTP on, k=3, pool 8 GiB,
temp 0.4, 119 work graphs of 40 segments.

```
poll 130.16   hook 51.29   tail 0.01   submit 4.10   idle_host 57.88 ms
                                            gap 64.35 ms   ratio 0.90   residual +6.47 ms
VERDICT: HOST WORK (90% of the gap is hook+tail+submit)
```

The pre-registered prediction (**ratio ≈ 0.89 ⇒ host work**) is confirmed on the first reading, at
0.90, and the residual (+6.47 ms, 10%) is the part the host accounting does not explain.

Same run's other arm (from the same capture, so same regime): step 188.00 ms, union 117.39, gap 64.26,
accept 66.20%, mean_len 3.170 ⇒ **12.73 t/s** — the numbers this split has to be read against.

**Per layer, the prediction is wrong.** Top-8 idle_host share = **33.9%** against the 19.5% uniform
baseline, which lands in the MIXED band: neither "a few layers' hooks own it" (≥40%, fix the hook) nor
"pure per-segment structure" (≤25%). So the `where` answer does not support changing a few layers'
hooks either — the window is somewhat top-heavy (L0 437.9, L1 405.5, L2 365.0, L38 344.7, L3 329.2 ms
over 119 graphs) but the mass is spread over 40 rows.

Two instrument facts found while reading that table, both now enforced rather than papered over:

1. **The per-layer GPU side is not measured.** Every row prints `gap=0.00` while the aggregate has a
   64 ms gap, so the per-layer `ratio` column was an absence printed as `0.00`; the parser now names
   it as NOT MEASURED and prints `ratio -`. Until `dp_lay_gap` is populated per layer, this table
   answers *where the host work is* and nothing about the GPU side.
2. **The first denominator was wrong, and it produced a wrong verdict.** The share divided the
   per-layer total by the aggregate *median* (×41) instead of by the aggregate total — a 112% "share"
   that printed as CONCENTRATED. Corrected (the two views now cross-check at 1.08x total / 1.00x hook,
   the residual being the per-layer submit attribution), the same log reads 33.9% ⇒ MIXED. A selftest
   now fails if the two totals disagree by more than 20%.

## 4. State of the evidence

- instrument built and **witnessed in the shipped artifact** (`src/llama.cpp/build/bin/libggml-base.dylib`:
  the aggregate line in both `ratio=` and `unmeasured` formats, the per-layer line, and the
  "needs CGC_DECODE_PROFILE" line); engine default unchanged, so no allowlist change;
- the per-layer arrays are cleared on **every** graph, not only the printed ones: a 2-segment draft
  graph returns before the print and would otherwise add its rows to the next decode step;
- `scripts/check/gap_split.py` — parser + both rules, **10/10 selftest**, including every way these
  lines could lie: no line at all (INVALID, not a pass), `gap=unmeasured` (refused, not zero),
  `idle_host > gap` (reported as instrument disagreement), a top-8-only log (the share verdict is
  refused), and no per-layer rows (INVALID rather than SPREAD);
- capture run behind the window: `m123_oracle_gate.py` **first** (same build — the instrument is
  default-off, but "should not change numbers" is not evidence), then the split. The reading is §3b;
  artifacts `/tmp/gap_split_capture/{gate,split,accept}.{log,json}` and the server log
  `Backup/cgc_logs/llama_server_20260920_214904.log`.
- what the reading decides: the host part of the gap is real (ratio 0.90), so §3's second caveat is
  the one that matters now — **host work is not movable work**. The per-layer table cannot separate
  "waiting on this segment's own expert bytes" from "reorderable host work" until fact 1 above is
  fixed, and the next step is `CGC-FSSPLIT`/`CGC-EBSPLIT` inside those rows, not a dispatcher change.

**Not measured, not claimed:** the split has produced no reading. Nothing here moves the 247.98 step
or the 13.61 t/s estimate, and the step floor remains `union_sum 149.24 ms`.
