# M-K5：decode 形狀實測，以及「30–38% 那一格」為什麼是高估

日期：2026-09-21 23:20–00:15　方法：0 重建（複用現有 binary）
結論三句：
1. **第 2 格根本不需要重建** —— 上次判斷錯了，改用 `CGC_ELEMW_CENSUS` 就能拿到 decode 形狀。
2. **(A)「grid 太小」的必要條件首次實測成立**：decode 的 elementwise dispatch 有 **42.2% 只有 ≤1024 個元素**，
   其中 75 個/4 步只有 **4 個元素**（連一個 SIMD group 都填不滿）。
3. **但一個 dispatch 的成本 ≈ 18–19.5 µs，而且幾乎全是固定開銷** ⇒ 撐 grid 動不了它
   ⇒ **30–38% 那一格是高估，M-K5 不值得做 C++**。

---

## 1. 工具更正：`CGC_ELEMW_CENSUS`（不是 `CGC_GRPH_DBG`）

上次說「M-K5 要重建」是只看了一個儀器造成的誤判。

| 儀器 | 門檻 | 上限 | 內容 |
|---|---|---|---|
| `CGC_GRPH_DBG`（`ggml-backend.cpp:2091`） | `static int cgc_grph_dbg_n < 6` | **6 個圖** | 只印 `ne[0], ne[1]` 兩維；歷史 raw 證實 5/6 是 `n_nodes=4116`（prefill） |
| **`CGC_ELEMW_CENSUS=1`**（`ggml-metal-ops.cpp:582`） | 每個 elementwise dispatch | **3000 行** | **`ne=[n0,n1,n2,n3]` 全四維 + name + op + unary sub-op** |

後者的配額是**行數**不是圖數 ⇒ prefill 吃掉一部分，剩下的落在 decode。
配合 `CGC_GPU_TIMING=1` 的 `step=` 行當錨點，就能切出純 decode 區間。

⚠️ 它的 `want` 清單是 `UNARY/MUL/GLU/SCALE/L2_NORM/DIV/CLAMP/SUM_ROWS`，**不含 ADD**
⇒ 小 op 家族裡最大的一支看不到。但它覆蓋的正好是 K3 的 cluster-1（SUM_ROWS+CLAMP+DIV）。

採集：`python3 Backup/phase_decomp/K5/elemw_census.py --reps 1`（27–31 s，0 重建）。

## 2. decode 形狀實測

錨點：`step=4` 在第 2991 行、`step=8` 在第 3422 行 ⇒ 其間 408 行 = 4 個 decode 步的純 decode。

- **102 個 elementwise dispatch / 步**
- op 分佈：`MUL 120, UNARY 112, GLU 56, L2_NORM 36, SUM_ROWS 28, CLAMP 28, DIV 28`
- 元素總數（`ne[0]*ne[1]*ne[2]*ne[3]`）分佈：

| 元素數 | 個數 | | 元素數 | 個數 |
|---:|---:|---|---:|---:|
| 1 | 9 | | 4096 | 9 |
| **4** | **75** | | 8192 | 61 |
| 8 | 3 | | **16384** | **95** |
| 32 | 25 | | 32768 | 18 |
| 128 | 57 | | 65536 | 25 |
| 512 | 3 | | | |
| 2048 | 28 | | | |

- **≤1024 元素的 dispatch：172 / 408 = 42.2%**
- 典型小者：`ffn_moe_weights_sum` / `ffn_moe_weights_sum_clamped` /
  `mtp_shared_expert_gate_sigmoid` 都是 `ne=[1,4,1,1]` ⇒ **4 個元素**
  （`ne[2]=4` 是 MTP draft 的 4 個 token；`ne[0]=8` 見 `ffn_moe_weights_norm` 的 top-8）

⇒ **(A) 的必要條件成立**：真的有一大批 dispatch 小到連一個 SIMD group（32 執行緒）都填不滿。

---

## 3. 但是：一個 dispatch ≈ 18–19.5 µs，而且幾乎全是固定開銷

`CGC-NSM` 的 **`nk==1` 的 buffer 就是單個 dispatch 的實測 GPU 時長**（現有 run，47360 行）：

```
single-node buffers: 1558
  ffn_moe_argsort   1490 個   中位 18.6 µs
  cache               68 個   中位 1334.4 µs   ← attention cache，另一類東西
```

`argsort` 的工作量是幾個元素等級 ⇒ **這 18.6 µs 幾乎不是執行時間，是固定開銷**。

**交叉驗證（兩個完全獨立的儀器）**：

| 來源 | 每個 dispatch 的成本 |
|---|---:|
| NSM 單節點 buffer（argsort）中位 | **18.6 µs** |
| K3 實測邊際價 `0.0195%` × 步時 ~100 ms | **19.5 µs** |

吻合在 5% 內。⇒ 「一個 dispatch ≈ 18–19.5 µs、且以固定開銷為主」這個數字可以引用。

⇒ **撐 grid（假說 A）只能動「執行部分」，動不了這 18 µs。**
所以 30–38% 那一格（=「小 op 群 36.5% 全部拿回」）是高估：**那 36.5% 裡的最大一塊是
dispatch 固定開銷，不是 grid 欠飽和造成的浪費。**

---

## 4. 沒做出來的事（誠實邊界）

1. **想把 36.5% 拆成「固定 vs 執行」，沒做成。**
   直接累加小 op 群的 `dur`（12.2×110.9 + 19.7×176 + 62.6×385.7 + 214.6×165.1）得 **64.4 ms/步**，
   而 K5 表說這幾組只佔步時 **37.3%**（≈37.3 ms）⇒ 分母對不上（64.4/0.373 ≈ 173 ms，
   而 `gpu_busy_sum` 是 121–140 ms）。**在分母搞清楚之前，這個拆分不能報。**
2. **同 run 對齊失敗**：`CGC_ELEMW_CENSUS` 與 `CGC_GPU_NODES_MATRIX` 同時開時，
   NSM **一行都沒印**（ELEMW 正常 3003 行）。已確認 NSM 的外層門檻是
   `ns_ops = CGC_GPU_NODES && CGC_GPU_OPS`（`:1873`/`:1889`）並補了這兩個 env，
   仍然 0 行 ⇒ **原因未定位**。所以「元素數 × 實測時長」的同 run 回歸目前做不了，
   上面的 18.6 µs 用的是**跨 run** 的 kind 對齊（同 cell，可接受但不嚴謹）。
3. `CGC_ELEMW` 不覆蓋 ADD ⇒ ADD 那支小 op 的形狀仍然沒有。

## 5. 判決：第 2 格不做

| | |
|---|---|
| 需要重建嗎？ | **不需要**（形狀已 0 重建拿到） |
| (A) 必要條件成立嗎？ | **成立**（42.2% ≤1024 元素） |
| (A) vs (B) 判得出來嗎？ | **判不出** —— 兩者在任何「grid 大小 vs 時間」觀測下同形，要判得改 kernel 的 threadgroup 配置做 A/B（真工程） |
| 值得做嗎？ | **不值得**。一個 dispatch 的 18 µs 是固定開銷，撐 grid 拿不回；上界遠低於 30–38% |

⇒ **M-K5 維持「未定 → 期望值按 (B) 佔優 = 0」的既有裁決，而且現在多了一條實測理由。**
里程碑表往後只剩 **M-W**（已判：機制真、端到端 ≈+1.7%，低於門檻）。

如果日後還想收窄，唯一便宜的一步是修好 #2（同 run 對齊），把 36.5% 拆成固定/執行——
但那只會把上界往下修，不會翻成「值得做」。
