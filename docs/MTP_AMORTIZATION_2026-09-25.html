同一顆 build 1ca685490、同一 cell（p2048 / n128 / d512 / r3 / b5632）、 單段提交 ＋ 凍結池（3 GiB，budget gate 逼的）。所有 step 為 run1 median（實測）， 不是擬合值。產物：Backup/s1_ksweep/20260924_225548/s1_ksweep.json、`Backup/seg_batch_s1_pairs/abba_212809.json`。

1. 算術：成本曲線與「每產出 token 成本」

⇒ 攤薄係數 ≈ 0。 每產出 token 的成本在 45.6 ~ 56.4 ms 之間，而 baseline 是 48.2 ms —— 加了 MTP 之後每 token 的成本幾乎沒變。這不是「MTP 效果小」，而是 verify 的邊際成本（42.03 ms/verify token）幾乎等於整個 baseline step（48.2 ms） ⇒ 同一批權重服務多個 token 這件事，在這台機器上沒有發生。

4. 兩大子目標（運營層）

S — 序列化消減（對應 docs/S1_TPOT_DECOMPOSITION_2026-09-25.html）
現況：上界已量 —— 41 段提交的同步 ≈ 36.3 ms（step 88.5 → 48.2，−45.5%）；其中 fill 3.96 ms 必須還回去。
驗收（可機檢）：交付 cell（8 GiB 池、MTP off）上 ① decode 不退步 ∧ ② 輸出正確性已驗（answer_md5 與參考臂相同）∧ ③ step 降 ≥ 20%。
現況判定：③a 階段性 —— ①② 未達（無 fill ⇒ 不能放生產）。
M — MTP on 加速
現況：攤薄係數 ≈ 0（本頁 §1）；⛔ 交付口徑 MTP off 9.82 → on 12.62 = +28.5% —— 此比值已作廢（HTTP 舊口徑、無 warm-skip；MEASUREMENT_CONTRACT §7）。
現行生產口徑 MTP off 已是 11.03~12.20（nf2_fill.json／nf_fill.json／mw_ctrl.json）； 交付 cell 的 MTP-on 讀數 = 缺量測（UNRESOLVED）。
驗收（可機檢）：交付 cell 上 ① step = c0 + m·T 的 m 相對 42.03 下降 ∧ ② t/s 相對 MTP-off 提升 ≥ 門檻（門檻待 operator 定；⛔ 原寫「目前 +28.5%」**已作廢** ⇒ 交付 cell 尚無配對讀數）。
⛔ 但「加速比 2」不可當驗收線—— 它要求 m ≤ 18 ms（−55%），與現況差一個數量級的策略。 建議改成可攻的兩條：(a) m：42.03 → ≤ 30 ms（−29%）；(b) acc：0.915 → ≥ 0.97（+6%）。

5. 引用與邊界

① 本頁的 step／mean_len／acc／t_draft 全是實測； c0=14.61、m=42.03 是四點擬合（k=1..4），外推到 T=1 不可信 （擬合給 56.6 ms，實測 48.2 ms）。
② 本頁數字的 regime 是「單段提交 ＋ 凍結池 ＋ 3 GiB」 —— 不是交付 cell。 絕對值不可與交付 12.57 併排；可搬的是結構（成本曲線、攤薄為零、draft/verify 佔比）。
③ 交付 cell 上缺同一條成本曲線（缺量測）⇒ 「交付口徑的 m 是多少」目前不知道， ⛔ 原寫「只知道端點 +28.5%」—— 該端點已作廢（契約 §7）⇒ 交付 cell 的 MTP 增益目前完全不知道。 要動 M 子目標，第一步是在交付 cell 上以 warm-skip 口徑掃 k（MTP on/off 配對）。
