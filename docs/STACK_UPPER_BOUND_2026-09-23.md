# 「ρ＋prebind 疊加 ⇒ +33%（16.76 t/s）」是真的嗎 —— 上界複核（2026-09-23）

工具：`scripts/check/window_joint_ev.py`（**selftest 39/39**，其中 7 項機械重現兩個既有文件發表的
每一個數字，誤差 < 0.03 t/s）
跑法：`python3 scripts/check/window_joint_ev.py --grid`

---

## 0. 三句話答案

1. **數字本身沒算錯，但它是「ρ 自己的樂觀上界」，不是「兩個機制相加」。**
   16.76 = 16.46（只做 ρ，+30.9%）+ **0.30**（prebind 的增量）。那 33% 裡有 31% 是 ρ 一個人的。
2. **它住在一個 2×2 表格的右上格**：cb=74.18 **且** 視窗=1.59 同時成立才成立。
   換回本次 ρ run **自己的** cb 口徑（42.04），同一個模型給 **14.50 t/s（+15.4%）**。
3. **「疊加」的邊際價值在所有實測格點上只有 +0.03 ~ +0.30 t/s**
   （`window_joint_ev.py` selftest 第 9 項把它當不變式檢查）⇒ **不要把兩個都做出來。**

## 1. 算式（可重現，不再手算）

```
tok/step  = 12.57 * 0.24798 = 3.1171            # 錨點反推，兩機制都不改變接受率
F         = cb / 40                              # 每層 expert fill 需求（ms）
單機制可藏 = min(lead, cov * F)                   # 提前量 vs 覆蓋到的量，取小
雙機制     = min(lead_rho, cov_rho * F) + (joint − cov_rho) * F
saving    = 可藏 * 40 − insert（ρ 付 4.76 ms/步 插 GPU 節點，prebind 付 0）
t/s       = 3.1171 / ((247.98 − saving) / 1000)
```

假設三條（沿用 `prebind_ev.py` 那一族線性代理，**沒有被實測支持的部分都標了**）：

| # | 假設 | 狀態 |
|---|---|---|
| A1 | 每層 fill 時間 = cb/40，且與 miss 數線性 | 未驗證；這是 cb 兩口徑分歧的一部分 |
| A2 | 提前發起的 pread 與 GPU 完全重疊、互不爭頻寬 | ⚠ **未定價**（既有註記：LRU 擾動、多餘 pread 頻寬也沒算） |
| A3 | prebind 的增量那一份有無限提前量（提前一整步），只有 ρ 那一份會被視窗限住 | 對 prebind 有利的假設 |

## 2. ★ 最主要問題：那個格點跨了 regime

`cb` 在本專案已經量到過 4 個值，飄 **6.6×**（既有結論：`cb` 對 swap 水位極敏感）：

| cb (ms) | 來源 | 結構上限（把 cb 全藏起來） |
|---:|---|---|
| 11.26 | 214450 log，startup free 84% | 13.17 (+4.8%) |
| 21.23 | E2b 暖，另一條線 | 13.75 (+9.4%) |
| **42.04** | **ρ run 的同 log 口徑** | **15.14 (+20.4%)** |
| 74.18 | 023021 log，high swap + `CGC_HOOK_SPLIT` | 17.94 (+42.7%) |

而本專案**已經為「跨 log 相加」寫過兩支工具**：`joint_reconcile.py`（所有分量必須出自同一支 log）
與 `cb_headroom_probe.py`（把水位變成 entry condition）。
⇒ **16.76 是把 +33% 的上界建立在本線自己禁用過的做法上。**
同一 regime 紀律下（cb 取 42.04）的答案是：

| 方案 | t/s | Δ |
|---|---:|---:|
| 只做 ρ | 14.38 | +14.4% |
| 只做 prebind qu3 | 14.33 | +14.0% |
| **疊加（joint=0.90）** | **14.50** | **+15.4%** |
| 結構上限（cb 全藏） | 15.14 | +20.4% |

## 3. 邊際價值：+0.03 ~ +0.30 t/s（selftest 機械檢查）

| cb | lead=1.30 | lead=1.59 |
|---:|---:|---:|
| 11.26 | +0.03 | +0.03 |
| 21.23 | +0.06 | +0.06 |
| 42.04 | +0.13 | +0.13 |
| 74.18 | +0.27 | +0.30 |

再看解析度（既有定價）：k=3 有專屬的 **launch 級項 13.16%**，配對扣不掉；
要把 `#3%` 定準要 **25 臂/組**。換算：

- 驗到「14.5 vs 12.57」這 **+1.9 t/s**：約 4~8 個獨立臂/組 ⇒ **可行**。
- 驗到「疊加的增量 **+0.13 t/s**」：需要三位數以上的臂 ⇒ **不可行**。

⇒ **就算 cb 真的站在 74.18，疊加那一層也是測不到的。** 做兩個不會讓你能宣稱第二個有用。

## 4. ★ 回答「下一個實驗是不是該量視窗」：視窗綁不綁，取決於 cb

```
每層 IO 需求 F = cb / 40
cb = 42.04 => F = 1.051 ms/層   而最悲觀的視窗估計 = 1.30 ms  => 視窗永遠綁不住
cb = 74.18 => F = 1.855 ms/層   cov*F = 1.584 ms              => 視窗 < 1.584 時綁住
```

- **cb=42.04 口徑下：即使 joint 覆蓋率到 1.0，`cov*F` 也只有 1.051 ms < 1.30 ms**，
  ⇒ 「視窗是主導項」這個命題**在這一格不成立**，遮多少只由覆蓋率與 cb 本身決定。
- **cb=74.18 口徑下：視窗從 1.59 掉到 1.30，ρ 就從 16.46 掉到 15.53（−0.93 t/s）**
  ⇒ 只有在這一格，視窗才是主導項。

⇒ **順序應該是：先同一支 log 把 cb 定讞，再決定要不要量視窗。** cb 不只決定絕對尺度
（+4.8% ~ +42.7%），還決定「下一個要量的是哪個」。這兩件事可以同一趟量（見 §6）。

## 5. ★ 一個必須先修的前提：影子分支目前在圖裡拿不到提前量

**這是本輪複核發現、且會直接決定那個實驗結果的東西。**

```
qwen35moe.cpp:187   inpSA = inpL                        <= inpSA 這裡就有了
               189  build_norm(...attn_norm...)         ┐
               200  build_layer_attn(...)                │  attn(L) 全部節點
               209  ggml_add(cur, inpSA)  attn_residual  │
               216  build_norm(... attn_post_norm ...)   ┘
               231    rho_pre    = build_norm(inpSA, ...)   <= 影子分支現在在這裡
               233    rho_logits = build_lora_mm(ffn_gate_inp, rho_pre)
               240  build_layer_ffn(attn_post_norm, il)  <= 真正的 gate/topk 在這裡
```

ggml 的執行順序 = node array 的建圖順序。影子分支建在 **attn(L) 全部節點之後**、
離真正的 gate 只差幾行 ⇒ **它相對真實 route 的提前量 ≈ 0**，而那幾行恰好就是我們在付的
4.76 ms/步插入成本。**現在這支 probe 只能量準度，拿不到任何窗口。**

⇒ 要先把它移到 `inpSA = inpL`（`:187`）之後、`build_norm(attn_norm)`（`:189`）之前。
數學完全不變（同一個 inpSA、同一組 norm + gate 權重，與 attn 無依賴），只是讓它在
node array 裡落在 layer L 的**最前面** —— 那才是 ρ 宣稱的那個「MoE core(L−1) 一結束就發起」。

⚠ 移了之後要重驗兩件我自己區裡的東西：
① `CGC_TD_CB` 的逐段轉發（它可能因此落進 L−1 的 segment）；
② `expert_cache_eval_cb` 的 stamp「有前進」判據。
⚠ **不修就直接去量百分位，你會量到 ~0，然後用一個建圖順序的理由把方向殺掉** ——
和上一輪 token-0 儀器 bug 是同一類錯誤。

## 6. 視窗百分位：儀器樹上已經有了，不用新寫

`ggml-metal-context.m` 已經有 **per-command-buffer 的 GPUStartTime/GPUEndTime + node range**
（`ggml_metal_cgc_gpu_take_cb`），`ggml-backend.cpp:1848+` 是消費者（關 `CGC_GPU_NODES`）。
預設 `n_nodes_0 = MAX(64, 0.1N)` 會讓第一個 buffer 吞掉約 64 個節點，ρ 節點被埋在裡面 ⇒
必須 **`CGC_CB_N_MAIN=1` + 大的 `CGC_N_CB`**，讓「一個 command buffer ≈ 一個 node」，
node 的時間軸位置才可解（該檔案自己的註解就是這麼寫的）。

```
讀法：  百分位 = (GPUStart(node) − seg_start) / (seg_end − seg_start)
        到期點 = 該層第一個 expert matmul 真正的 buffer start
注意：  只看 START，不要看 duration（全 VIEW/RESHAPE 的 buffer 沒有 GPU 命令，
        既有記錄：報出過 592 µs/node 的假值）
        一趟 「CGC_CB_N_MAIN=1 + 大 n_cb」會改變絕對時間 ⇒ 只取其序數含義，不引用 t/s
```

**建議一趟同時拿兩個數**：在同一支 log 裡既讀 cb（帶水位條件，照 `cb_headroom_probe.py` 的
entry condition），也讀百分位。這樣就不會再犯 §2 那個跨 regime 的錯。
⚠ 那一輪的 cb **不能**與未帶儀器的交付讀數並列（既有規則）。

## 7. 那 decode 到底還能往上提多少

| 情境 | 交付 decode |
|---|---:|
| 現在（錨點） | 12.57 t/s |
| **同一 regime 紀律（cb=42.04）：做其中一個** | **14.3 ~ 14.4（+14%）** |
| 同上，做疊加 | 14.5（+15.4%） |
| 結構上限：把 cb=42.04 全藏起來 | 15.14（+20.4%） |
| 需要「cb 其實是 74.18」才拿得到 | 16.5 ~ 17.9 |
| **絕對天花板**（cb=74.18 且完美預測且零插入成本） | **17.94（+42.7%）** |
| ⚠ 若移到前面之後還是拿不到提前量 | **12.33（−1.9%，淨虧）** |

⇒ **誠實回答：這個方向剩下的東西是 +14% ~ +15%（≈ 14.3~14.5 t/s），
且它的 +/- 完全取決於還沒定讞的 cb；16.76 是那個尚未證成的樂觀角，不是期望值。**

## 8. 行動順序（建議）

1. **[便宜，零 GPU]** 已做：把定價模型從手算搬進 `window_joint_ev.py`，讓「疊加 = +0.3」可驗。
2. **[必須先]** 移 `qwen35moe.cpp` 的影子分支到 layer 最前（§5）。不改數字，改它有沒有資格被量。
3. **[一趟]** 同 log 同時讀 `cb` + 影子節點的 GPU 百分位（§6）。
4. 按 cb 的定讞值決定槓桿在哪一格：
   cb ≈ 42 ⇒ 覆蓋率綁（且 ρ 已 0.854，剩下的是把 cb 吃乾淨，不是再去搶提前量）；
   cb ≈ 74 ⇒ 視窗主導，值得為「更早發起」改結構。
5. **不做疊加** —— 增量低於任何可負擔的量測解析度（§3）。選一個，另一個留著作為對沖：
   prebind qu3（14.33）不依賴視窗；如果第 3 步量到視窗 ≈ 0，prebind 就是全部的答案。
