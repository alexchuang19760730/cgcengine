三句話：

  1. 兩個儀器在 n≈128 上報 9.4 與 12.4，而同 env、同模型、同場交錯。不能互相引用。
  2. 那 1.32× 的大部分是「第一個 rep 是冷的」：llama-bench 的 tg warmup 原始碼上是 test_gen(ctx, 1, ...)——一個 token——而 context／專家池每 instance 建一次 ⇒ 池從空開始。 avg_ts 把那個 rep 平均進去，而 decode_bench --warmup 1 恰好丟掉對應的那一輪。 丟掉之後兩邊是 11.3 vs 12.4 ＝ 1.10×。
  3. 殘差不是攤銷問題：三個能調的旋鈕（reps 3→8、warmup 開→關、長度 128→256）都動不了 llama-bench 的 9.4。所以 n=24 那 2× 與 n=128 剩下的 10% 是兩個儀器在量不同的工作， 不是同一個量的兩種精度。

1. 實驗設計：怎樣才算「同一個 env」

問題起點：路線圖把 9.16 / 9.45 t/s 標成「llama-bench decode」，而 12.95 t/s 出自 decode_bench（HTTP）。在同一個專案裡把兩個儀器的數字並排， 正是這個專案反覆踩到的錯。所以要量的不是「哪個對」，而是差距有多大、由什麼構成。

配對的前提是 env 逐字相同，而 env 不是手寫的：llama_bench_matrix.py 支援 PROFILE:ENV=VAL 形式，於是

--arms 'prod25:CGC_SERVER_MTP=0;CGC_GPU_TIMING=1;CGC_DECODE_PROFILE=1'

就是 decode_sweep --arms p25-gputime 那一臂的 env，兩邊都經 run_server.sh CGC_DUMP_ENV=1 解析（單一真相）。乾跑確認兩邊的 model／ -expert-cache／-ngl／KV 型別完全一致：

llama-bench  -m …/Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf -ngl 99 --load-mode none -t 8 \
             -expert-cache 8589934592 --cache-type-k q8_0 --cache-type-v q8_0 -b 8 -ub 8 …
llama-server -m …/Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf -ngl 99 --load-mode none -t 8 -c 4096 \
             -np 1 --no-kv-unified -sps 0 --jinja -expert-cache 8589934592 --cache-type-k q8_0 …

一個必須先講清楚的副作用：MTP=0 會讓 profile 換模型。 run_server.sh:154 的 if [ "$SERVER_MTP" = "1" ] 才選 MTP 家族， 所以配對臂載入的是非 MTP 的 Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf，不是 Nail-…-denseIQ4X.gguf。兩邊一致 ⇒ 配對公平，但這意味著「prod25 的 decode 數字」 在本專案裡一直有兩個不同的模型在背後（MTP 開／關各一），引用時必須指名。

順序設計成 ABABAB（llama-bench → decode_bench → …），因為 prefill 的工作已證明 自變數是累積負載（序列裡第幾次啟動）而不是靜置時間，所以交錯比「先跑完 A 再跑 B」重要。 每一臂的發射前讀數由新增的 thermal_pressure.Sampler（2 Hz 背景執行緒）記錄； llama-bench 是一個獨佔 GPU 數分鐘的子行程，沒有「每個請求」可以掛讀數，這是它需要執行緒的原因。

3. 差距的大半：第一個 rep 是冷的

3.1 原始碼：warmup 只有一個 token

// llama-bench.cpp:2392 -- 這是整個 tg warmup
if (t.n_gen > 0) {
    bool res = test_gen(ctx, 1, t.n_threads);     // <-- 1，不是 n
}

// llama-bench.cpp:2400 -- 每個 rep 之前
for (int i = 0; i < params.reps; i++) {
    llama_memory_clear(llama_get_memory(ctx), false);   // 清 KV，不是清專家池
    …
}

context（連同 -expert-cache 的池）是每個 instance 建一次，所以池從空開始， 而 warmup 只碰了 1 個 token。這在日誌上有一個可對帳的指紋：warmup 1 個圖 ＋ 3×128 個 rep 圖 ＝ 385， 而 DECPROF 的閘門是 step%8==0 || step==1 || ntok>1 ⇒ 應印 385/8 + 1 = 49 行，實際正好 49。

3.2 逐 rep（DECPROF，只取 ntok=1，每 8 步印一次）

形狀rep1rep2rep3平台（rep≥2）rep1／平台
n=128 r=31208693891.35×
n=128 r=3（另一跑）1138990901.26×
n=256 r=31168787871.34×
n=24 r=818113297104（r4–r8）1.73×

單位 ms/token。n=128/n=256 的平台是 87–90 ms ⇒ 11.1–11.5 t/s， decode_bench 的暖值是 80 ms ⇒ 12.36 t/s。11.3 vs 12.4 ＝ 1.10×。

自我修正。我先前用「四個桶的中位數 103→94→89→85」說這是 「單調的暖機曲線」。那個說法太強。把 49 個樣本按序印出來看，樣本間散佈是 68–125 ms（±30%），桶中位數的 18% 落差大約只有 2 個標準誤。可用序列支持的是比較窄的一句： rep1 明顯慢（1.26–1.35×），第 2 個 rep 就進入平台，而 n=24 需要約 4 個 rep。 「池是不是每個 rep 重置」這件事，本文沒有解決（見 §4 第 1 列與 §8）。

4. 三個預測，兩個死掉

動手前寫下三個可以失敗的預測（寫在 Backup/run_instrument_compare_p2.sh 的檔頭）。

預測結果判定
-n 24 -r 8：若 reps 會把池養熱，8 個 rep 的均值必須高於 7.21 7.88 ± 1.12（+9%），且該臂在 HEAVY 下跑（本該更低） 不算證實
-n 128 --no-warmup：若 warmup 在養池，拿掉必須掉到 ~7 9.40 vs 9.38 ＝ 0.2%（且在 HEAVY） no-op：證實「warmup 只有 1 個 token」，並推翻 harness 自己 --no-warmup 說明那句「warmup 讓池變熱、所以預設更接近被服務的請求」
-n 256：若殘差是攤銷問題，加長必須升向 12.4 9.45 vs 9.38 ＝ +0.7%（且在 HEAVY） 否證：殘差不是攤銷

第二列是這輪最有價值的一個：它原本是要殺掉「冷池」故事的，結果反過來 證實了原始碼、同時把 harness 說明文件裡的一句話變成假話。 第三列則把「再加長就會追上」這條退路關掉：reps／warmup／長度三個旋鈕都動不了 9.4。

5. 結構性事實（讀原始碼）

5.1 llama-bench 對 MTP 是瞎的

$ grep -c 'sampler\|speculat\|draft\|MTP' tools/llama-bench/llama-bench.cpp
0

// 所以下一個 token 是這樣來的（llama-bench.cpp:2168-2183）
llama_token token = … llama_vocab_bos(vocab) … ;
for (int i = 0; i < n_gen; i++) {
    llama_decode(ctx, llama_batch_get_one(&token, 1));
    llama_synchronize(ctx);            // 每 token 一道硬柵欄
    token = std::rand() % n_vocab;     // 沒有取樣器
}

沒有取樣器 ⇒ 沒有 draft／verify／accept ⇒ 不可能執行投機解碼。 而 25 t/s 唯一剩下的乘數來源就是 MTP（draft_accept 只有 19.9%，MTP-on 目前是 1.8× 淨損失）。 第 7 臂量到的 8.75 只是「MTP 模型在不跑投機的情況下」，不是 MTP 的能力。 ⇒ llama-bench 不能當這個目標的 instrument of record。

另外那道每 token llama_synchronize 是伺服器產生迴圈 （server-context.cpp:3892 無同步點）沒有的，方向上是讓 llama-bench 偏慢—— 但它的量級本文沒有隔離（§8）。

5.2 兩個 token 流給專家池的壓力結構不同

同引擎、同池、同 envllama-bench（rand()%n_vocab）伺服器（連貫文本）

miss 組成compulsory 4437 / capacity 758（85.4% / 14.6%）compulsory 8874 / capacity 8522（51.0% / 49.0%）

「命中率解釋差距」已被這組數字殺掉：命中率高的那一邊反而慢 （96.0% → 9.4 t/s；92.6% → 12.4 t/s）。同時它也說明計數器不能跨行程比—— 它們是行程生命週期的累加器，而兩個行程累加的工作不同（一邊是自己的 warmup＋reps 的 tg， 另一邊是模型載入＋warmup 請求＋n_batch=8 的 prefill 分塊＋每一輪）。可比的只有行程內部 定義的比例（miss 歸因組成、超訂層數）。

5.3 兩個「生成」的視窗界線不一樣

// server-context.cpp:4085-4099

// here we have synchronized the llama_context (due to the sampling above), so we can do time measurement

於是 predicted_ms 跨的是 N−1 步，而 predicted_n 是 N ⇒ 系統性樂觀 N/(N−1)：n=24 時 +4.3%、n=124 時 +0.8%。 方向是讓 decode_bench 偏快，但量級不足以解釋 1.32×。另外 llama-bench 的 n_ctx = n_prompt + n_gen + n_depth ⇒ 這批是 128，伺服器是 4096。

6. decode 的散熱分離：本專案第一次量到

上午的白皮書（docs/DECODE_THERMAL_INBAND_20260916_1755.html）寫的是 「熱態樣本還沒取得 ⇒ 等級→吞吐的分離在 decode 端尚未量到，這支儀器現在只記錄、不閘門」。 本輪的交錯順序意外地補上了那筆：第 4 臂與第 6 臂是同 env、同模型、同 n， 只差發射時的讀數。

臂發射讀數過程decode t/s相對

#6 decode_bench n=128MODERATE (1)8/8 HEAVY10.64−13.9%

llama-bench 側（#5 → #7）是 9.32 → 8.75，但同時換了模型（MTP=1 ⇒ denseIQ4X） ⇒ 兩個變數同時動，不可歸因，本文不引用那 −6%。

與 prefill 的分離（發射讀 0 ⇒ 6/6 ≥250；讀 1 或 2 ⇒ 0/21）相比，decode 對熱壓的反應 小一個量級。每個等級 n=1 ⇒ 仍然只記錄、不閘門。

7. 對路線圖那張表、以及對 25 t/s 的意義

7.1 路線圖 §1 的標籤無法稽核

docs/REMAP_ROUNDTRIP_REMOVAL_PLAN_2026-09-15.md §1 的指令欄寫的是 decode_sweep.py --profile prod25 --arms p25-gputime,p25-submit-ahead --n-predict 120， 但表格那一列標成 「llama-bench decode　9.16 / 9.45 t/s」——表格與它自己的指令互相矛盾。

  • 今日 llama-bench n=128 的三次量測 9.42／9.32／9.38 把 9.45 夾在中間； decode_bench 讀 12.36–18.74。
  • ⇒ 那兩個值可重現為 llama-bench，不可重現為 decode_bench，所以標籤大概對； 但那份文件本身無法稽核這個歸屬（llama_bench_matrix.py 是 09-15 17:42 d3cbe9744 才引入的，文件沒記載用過它，也沒記儀器）。
  • 我上午的白皮書引用「那組出自 llama-bench」繼承了一個無法稽核的標籤。本文修正它。

7.2 對 decode 25 t/s

  • 本輪沒有動任何引擎程式碼（src/ 零變更），所以「距離 25 t/s 多遠」不變： 以 decode_bench 的可持續值 12.36–12.95 算，距離約 2.0×。
  • 但「要拿哪個數字去說距離」現在有規則了：報 llama-bench 必須附 rep 數與 warmup 規則， 報 decode_bench 必須附 round 數與 --warmup；兩者不得並排。
  • MTP 仍然是唯一的乘數來源，而它只能用 HTTP 路徑量（§5.1）。這一點讓 「llama-bench 是生產標準」（d3cbe9744 的標題）對 decode 而言不成立。

8. 誠實邊界：本文不主張什麼

  • 不主張差距已被完全解釋。n=128 的穩態殘差是 1.10×、 n=24 的穩態殘差約 2×，兩者都未歸因。候選有：每 token 的 llama_synchronize（§5.1）、隨機 token 造成的不可預取存取、n_ctx 128 vs 4096。 能裁決它們的實驗是讓其中一邊換成另一邊的 token 流（餵 llama-bench 連貫 token， 或讓伺服器吃隨機 token），本文沒做。
  • 不主張「池每個 rep 是否重置」已解決。第 1 列的 +9% 與 HEAVY 混淆， 而 llama_memory_clear 清的是 KV；逐樣本序列的雜訊 ±30% 不足以判定鋸齒或單調。
  • 不主張任何跨儀器的 hit%／miss／reads 比較（§5.2）。
  • 不主張熱壓對 decode 的係數已定：每個等級 n=1。
  • 不主張 09-15 的 9.16/9.45 與今日的 9.42 之間有任何改進或退步——不同日、不同 n、 不同文件記載程度 ⇒ 未歸因。
