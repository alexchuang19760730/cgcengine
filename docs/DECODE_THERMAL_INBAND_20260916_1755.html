1. 儀器接在哪、為什麼是那兩個位置

唯一的實作是 scripts/check/thermal_pressure.py（level() / label() / stamp() / worst() / histogram()）， 由 decode_sweep.py 與 decode_bench.py 匯入，不是各自抄一份 （本專案對「第二份會分叉的實作」有硬規則，見 agent_harness/CONVENTIONS.md）。

位置讀什麼為什麼是這裡
decode_sweep.py
（每臂）		 pre_kill / launch / post_bench / teardown launch 是發射前那一刻——prefill 端已證明「讀發射那一刻」才攜帶裁決 （讀 0 → 6/6 ≥250；讀 1 或 2 → 0/21）。刻意讀在模型載入之前：載入 13 GB 本身就是一次熱事件。
decode_bench.py
（每一輪）		 請求的兩側 thermal_before / thermal_after 一輪本身會把機器加熱，於是後面的輪次繼承前面的熱——只讀一次分不出「這輪冷」與「這輪熱」。

成本量測：notifyutil -g 呼叫 12 次共 0.02 s ⇒ 約 1.7 ms/次，比向 server 問一次還便宜，所以放進每輪迴圈是免費的。 輸出另存 rounds[]（每輪的 t/s 與兩側等級配對）與 thermal_hist（等級計數）——因為等級的中位數會藏住形狀： 「3 輪冷 + 3 輪熱」與「6 輪溫」的中位數相同，但它們不是同一個實驗。

2. 儀器自己的洞：notifyutil 對不存在的 key 回 0

實測（本機 macOS）：

$ notifyutil -g com.apple.system.thermalpressurelevel
com.apple.system.thermalpressurelevel 0          # exit 0
$ notifyutil -g com.apple.system.this.key.does.not.exist
com.apple.system.this.key.does.not.exist 0       # exit 0，形狀完全相同

-v 與 -q 都不改變這個行為（實測）。所以exit code 與輸出形狀 都無法區分「存在且為 0」與「不存在」。一個信任它們的解析器會在儀器整個缺席的機器上 回報 NOMINAL——那是「我們沒量到」穿著「一切正常」的衣服。

這一條是被 --selftest 當場抓到的（第一版把它寫成「未知 key → None」， 跑下去得到 0）。處置分三層，並且不假裝偵測得到偵測不到的東西：

  1. 模組只接受 SUPPORTED_KEYS（已實測過的 key）並拒絕其他 ⇒ 擋掉 typo 那一類， 那正是它擋得掉的。
  2. 把「無法偵測缺席」寫進 docstring，而不是用解析器掩蓋。
  3. 殘留的緩解在別處：這個 key 的活性是由它對負載的實測反應建立的 （靜止 0、持續負載 2、停後約 47 s 回 0）。所以「一條永遠是 0 的序列」是該起疑的簽名， 而檢驗它是負載測試，不是解析器。

它的 --selftest 有 10 條，其中三條就是為這個失效模式寫的 （unsupported key -> None (never 0)、stamp() of a refused key is labelled UNREADABLE、worst() of only-unreadable is UNREADABLE, not 0）。 固化為 lesson eng-gate-0039。

4. 被否證的假設，與兩個真正的來源

被否證的假設：「decode 基線那 2.4× 的散佈（6.6 / 9.75 / 10.24 / 16.17 / 6.95 t/s，09-15 同日同設定）是散熱造成的。」

為什麼它看起來像真的：prefill 端確實有這種分離（Nominal 6/6 ≥250、 非 Nominal 0/21），而 decode 的散佈同樣大。

實測推翻了它——至少在本日的樣本上：三次跑共 20 個等級讀數全部是 NOMINAL(0)，而散佈仍在（同一臂內 7.98 → 20.76）。⇒ 散熱不能解釋 日內的散佈。

真正的兩個來源：

  1. 生成長度。同一臂、同一 session、同 NOMINAL：n=24 讀 20.31， n=124 讀 12.95（1.57×）。短生成是短爆，長生成才是可持續值。 ⇒ 引用 decode t/s必須同時說出生成長度。
  2. 暖機輪被計分。--warmup 0 讓第一個請求的一次性成本落進一個評分輪 （§3.2）。⇒ decode_tps_min 在這種設定下不是機器狀態的訊號，而是製程暖機的訊號； 而 median 會把它吞掉（3 輪取中位 ⇒ 首輪隱形）。

固化為 lesson eng-mh-0038。

5. 對 decode 25 t/s 的意義

量值怎麼讀
可持續 decode（n=124、NOMINAL）12.95 t/s 本日、本 build、本臂下的可交付基準
距 25 t/s1.93×以 12.95 為分母
序列化上界（D0 探針）×1.78 該探針輸出損壞，只可引用上界性質與每步 ms，不可引用它的 t/s

不要把 §0 那個 20.31 t/s 當成「已經快到 25」——它是 n=24 的短爆，且 median 掩蓋了首輪的一次性成本。以可持續值讀，今天的距離是 1.93×，不是 1.23×。這也是為什麼這支儀器的第一件產出不是「一個更好的數字」， 而是「一組不會被誤讀的數字」。

6. 誠實邊界：本文不主張什麼

  • 不主張「decode 的散佈與散熱無關」。本日在 NOMINAL 下取樣，所以 沒有取得任何熱態樣本——「等級 → decode 吞吐」的分離在 decode 端 尚未量到。要取得它，得刻意把機器推熱（prefill 端是用 ARMS=2 bash Backup/run_thermal_gate.sh 與 2 Hz 序列做的）。在量到之前，不要用等級去放行或拒絕任何 decode 數字。
  • 不主張 09-15 的 6.6–16.17 與今天的 20.3 之間有改進。兩者同儀器（decode_bench）、 同長度（n=24）、同 --warmup 0，所以形狀上可比；但不同日、不同 build、 且當日沒有等級讀數 ⇒ 差異未歸因。今天的等級讀數讓下一次可以歸因，這一次不行。
  • 不主張與 docs/ROADMAP_PREFILL250_DECODE25_2026-09-13.md 的 9.3–10.5 t/s 可比。 那組數字出自 llama-bench（見 docs/REMAP_ROUNDTRIP_REMOVAL_PLAN_2026-09-15.md §1： llama-bench decode 9.16 / 9.45），本文出自 decode_bench（client 側）。 不同儀器的兩個數字放在一起比大小，正是本專案最常踩的那一類錯。
  • 不主張 predicted_n=124 是 160。請求 n_predict=160， 實際生成 124 個 token（提早結束）⇒ 上表所有長度都以 124 為準。
  • 沒有動 binary_stamp()、NUMERIC_SOURCES，也沒有動 src/。 本文的 D5 閘門是對既有 build 的認證，不是對新 build 的。
