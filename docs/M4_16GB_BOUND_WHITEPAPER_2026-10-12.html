0一句话结论 Executive Summary

2.1 Roofline 判据（decode 用）

decode 落在哪一区 算术强度 = 4.55 FLOP/byte　　拐点 = 101 FLOP/byte　　⇒ 差值 22×，落在带宽区深处

同一件事的第二种写法：roofline 比值 0.045。两种写法都说同一句话—— decode 是 GEMV（M=1），每读 1 个权重只做 2 次浮点运算，所以算力极度宽裕，瓶颈不可能在 ALU。

5Compute bound：decode 远远没顶到；prefill 顶到的是热/时脉 ALU / DVFS

5.1 decode：算力余裕 22 倍，不是瓶颈

  • Roofline：算术强度 4.55 vs 拐点 101（22×）；比值 0.045 ⇒ 落在带宽区深处。
  • 实测占比：GEMV / MoE kernel 全族在 in-situ 只占 GPU 忙碌的 3.4%， 全族天花板 ≈ 5%（gate/up 47.6 GB/s、down 27.9 GB/s 是它的单形状上界）。
  • 步时构成（joint_capture n=65 稳态中位）：GPU busy 80.0%、GPU idle(gap) 19.2%、 专家 fill(cb) 9.2% ⇒ 「IO 全免费」也只值 +10.1% t/s。
  • CPU 侧分段（E2b，139.16 ms 步）：wait 114.62 ms（82.4%） / cb 21.16 ms（15.2%） / submit 3.55 ms（2.6%）。

结论：decode 顶到的不是算力天花板。把 GPU 的 GEMV 全部变免费， decode 也只到 ~17.9 t/s（仍低于 20）——这正是「瓶颈不在算力」的直接证明。 真正的时间住在 GPU busy 的 80% 与 CPU 的 82.4% wait 这两件事上， 而它们是「谁在等谁」的问题，不是「算力够不够」的问题。

12外部引擎评估：Magnitude / Strata 能不能替代 llama.cpp 加速 decode External engines

问法很具体：改用 Magnitude（开源本机推理引擎）或 Strata（Niko1221/Strata）取代 llama.cpp，能不能加速本机的 decode？ 本节只回答这一件事，且只引用公开资料（§12.6），不含本机新增量测。结论先给：

§12 判词：就本机与本项目而言，不能——而且阻挡不是「性能不够好」，是「装不进来」 Strata：平台不存在。它只支持 Windows / Linux ＋ 独立 NVIDIA / AMD 显卡（≥12 GB VRAM）、≥32 GB RAM、约 80 GB 磁盘， 没有任何 macOS / Apple Silicon 版本 —— 在本机这条路上，讨论到平台层就结束了。

12.3 它确实命中我们唯一还有物理余裕的那堵墙 —— 作为证据，而不是作为替代

这一点必须说清楚，否则上面的否定会被误读成「外部引擎没有价值」：

  • 本机只有一块空间是「没顶到、又有物理余裕」的：§4.3／§4.4 指出 MoE gather 只跑到 Si 峰值的 29–50%， 根因是 IQ2_S／IQ3_S 的查表式访存 ＋ load-use 依赖链；§4.6 量出这个家族在 T=1 的收益天花板是 5.0 ms/步。 这与「算力」和「Si 带宽」都无关（§4.2 有效达成率只有 11.4%–22.3%；§5.1 算力余裕 22 倍）。
  • Magnitude 的全部论点正是这一块：「预先为整类硬件编译 kernel 不划算，改成在你的实际芯片上编译并调校」 ——它主张的不是新算法，而是 kernel 的设备内生成与调参（官方称调校约 1 分钟/模型）。 这正是「有效带宽」那一层的杠杆类型，也是它在 Apple Silicon 上拿到 +92% 的机制解释。
  • 但它没有在「IQ2_S／IQ3_S ＋ 专家卸荷 ＋ 长上下文 MoE gather」上给过任何数字： 它的对照是 4-bit、装得下、KV 量化的路径。所以它只能当「kernel 层确实还有空间」的外部存在性证据， 不能当作本机 §7.6 那个区间（＋21%～＋41%）之外的额外保证，更不可与本机的实测读数相加。
  • 顺手的一个反证：§7.1 里那些便宜的 kernel 型解法（TG 反转、COOP、NOGRID、NSG…）在本机逐条都被实测封死了。 这说明差距不来自「调几个 kernel 参数」，而来自一整套 kernel 生成＋自动调校系统 —— 那是一个引擎级工程，不是一次改动。

12.4 若真要试：能做的对照长什么样，为什么在 16 GB 上它不成立

  1. 唯一可比的做法：拿 Catalog 里同一个 Qwen 3.6 35B-A3B 4-bit，分别用 llama.cpp 与 Magnitude 测 decode。 这跟本项目的载体、口径、闸门都无关 —— 它测的是「引擎」，不是「我们的交付锚点」。
  2. 本机的第一步就会卡在拟合上：16 GB 统一内存装不下 4-bit 的 35B-A3B（数十 GB 量级）， 大概率得到的是 Discover 判定「装不下／改推荐更小模型」，而不是一个可与本机数据比较的读数。 也就是说：在有意义的对照里，本机根本不在实验条件内。
  3. 换引擎＝重写验收：检查 6–12、replay bench 的基准与记忆体阈值、provenance 全绑在 llama.cpp 服务器与 CGC_* 语义上。 要让它们继续有效，成本不是「装个 app」，而是「换一套验收体系」。这本身就是不做的充分理由。
  4. 因此正确的结论方向：本机到不了 25 的差距（§8）是三堵墙的交点， 其中容量墙与格式墙都不是换引擎能解的；真正能解的是「换机器」（§7.5）。

12.5 那么它在什么情况下值得再来看一眼

  • 把机器换到 48 GB 级（或换成带独立显存的 x86 服务器机），容量墙消失之后，kernel 层的差距才变成第一序的问题。
  • 它把 expert streaming 落地，并且开放自订 GGUF／自订量化（尤其 IQ2_S／IQ3_S 家族）—— 这两条任意一条成真，本节结论就需要重写。
  • 本项目的目标从「单一交付锚点」改成「同一模型家族下的引擎上限探索」时（那时 §7.6 的区间不再是标尺）。
一句话的可操作版本 不要用 Magnitude／Strata 替代 llama.cpp 来追本机的 decode 25。 可以把它们当作两个外部上限参照：Strata 证明「专家分层 ＋ 投机解码」这条路在别处能跑到几十 tok/s（但它在 Windows／Linux ＋ 独显上）； Magnitude 证明「设备内 kernel 调校」能撬动同一模型家族 92% 的 decode 差距（但在 48 GB、模型装得下、KV 量化的条件下）。 两者都不改变本机「23 270 MiB 对 16 384 MiB」这一个算术。

12.7.3 你要的「1.92 GB/token 更接近顺序扫描进 GPU」——最小可做方案

本机 decode 等效带宽只有峰值 ~16%，根因是权重取用样式破坏局部性（§4.3：动态 top-k → 8 路 gather、 多栏位 gather、SSD 换页），不是 DRAM 本身慢（§4.2 Si 带宽余裕）。所以目标是把 gather 改造成顺读。三条按成本升序：

  1. 专家亲和性重排（对应 Magnitude memory-adjacency；成本低，纯指针层，bit-identical 可保）： 在 load／度假时，按「同一 token 上共选频率」把 256 专家物理重排，让每 token 被选中的 8 专家在 DRAM 上更靠拢。 预期直接对治 §4.3 的「一半墙」（而不是勉强凑拾 kernel 参数，§12.3）。未量测
    事前上界：本条做不到「1–2 个连续区段」—— 重排只是置换，共选关系彼此重叠、不是固定分群， 8 个任意专家不会因此变成一段连续；离线量到的只是平均 slot 距离 identity 89.79 → perm 50.14（−44%，仍相隔约 50 槽， 且属权重量测、非 decode 读数）。而「专家被读得散」这一项 repo 已有实测上界：把 id 换成「所有 copy 都读同一批 8 专家」 （完美 locality 臂）对 cycled 只 +2.2%／+0.8%（iq2_s，T=1／T=4）、+3.7%／+1.4%（iq3_s），出处 docs/MOE_GATHER_BOUND_2026-09-22.md §4（实测·相对对比）。 ⇒ 本条的期望量级低于 5%，即低于它已预注册的 success 门槛（charters/e-expert-affinity-reorder-2026-10-12.yaml）。
  2. 两层 residency：hot 前几层（如 10 层）的 dense＋hot experts 常驻 GPU；cold 层（后 30 层）的 down 层 按层级用你已验的 merge-read 顺读预取进 GPU（不是「小读坍缩」那个判死的颗粒度，而是层粒度排程）。未量测
  3. embedding/head streaming：把 output head 这类大张量改为需求时循序读入，释放工作集给真正顺扫的 down 层。未量测
