2. 三個設計決定，與它們拒絕掉的更簡單做法

2.1 「能推導就不要維護」——這裡有四處是推導的

harness_engine/memories/engine/ 不是手寫的目錄，是 build_memories.py 從 traces/lessons.jsonl 產生的；兩份 SFT 從 traces/*.jsonl 產生； extensions 是指向而不是複本。理由是同一條：手寫的集合會在下一次有人新增 record 時被忘記，而「忘記」的失效方式是安靜的——一個沒被注入的 memory 與一個從沒寫過的 memory， 從外面看一模一樣。

同一輪稍早在 import_harness_snapshot.py 上已經量過代價：它的 SKILL_NAMES 與 MEM_FILES 是硬編碼清單，於是「新增一個 skill」與「單純過了一天」都會靜默漏掉。 那是同一條原則的另一個實例，所以這裡一開始就用推導。

2.2 兩份投影共用一個渲染器

sft_common.render_obs() 是唯一把 episode 印成文字的地方。 兩份投影若各自渲染，第一次改動就會分叉——而分叉之後兩份資料集都還是能建、都還是看起來對， 只有被訓練出來的模型是錯的。這與 PLAN §6.2 的原始要求（推論時看到的判準與訓練時逐字一致） 是同一件事。

渲染時把閘門一起印出來：usable_as_evidence 與 caveats 就在數字旁邊。 省掉它們等於教模型去引用那些 harness 自己拒絕引用的列。

2.3 「重建」而不是「重播」——而且每一筆都自己說出來

traces 裡沒有 tool call。episode 記的是某個臂產出了什麼，而它的 arm.env 足以重新生成產生它的那條命令；但「會產生這個的命令」不等於「當時跑的命令」。 所以每一筆 sample 都帶： 

"_provenance": {"reconstructed": true, "from": "dec-20260915-…", "episodes": [...],
                 "note": "the tool call is regenerated from the episode's arm.env; it is not a recorded command"}

一個把重建悄悄當成逐字稿呈現的資料集，與一個沒有附 build 指紋的數字是同一類錯誤。

3. 自測抓到的一個真缺陷（這一輪最有價值的產物）

distill/selftest.py 用一個假的 prime-agent 跑完整條蒸餾路徑。第一次跑，它在 「追加後仍通過驗證」那一項失敗： 

ERROR duplicate lesson_id eng-src-0009

根因不是測試寫壞。prompt 的證據區先列出 106 個已經在使用的 lesson id，而「你可以取用的 下一個 id」被放在文件最末。假的 agent 從文件中第一個看到的 id 取用——那正是任何讀者（模型或人）都會做的事。所以真實情況不是「偶爾撞號」，是撞號被設計成很可能。

版本prompt 的手遞方式後果
v1證據區列 106 個既有 id；可用 id 在文件最末，無標記 實測撞號duplicate lesson_id，整批輸出被 validate 擋掉
v2可用 id 用 NEXT-FREE-IDS 哨兵包起來；明文禁止重用證據區的 id； 且指示文字不得複製哨兵字面 通過；並留下回歸斷言

留下的斷言裡有一條是負向對照：文件中第一個出現的 id 必須不等於可用 id。 它把「這個 prompt 的設計缺陷」變成一個會自己復發警報的性質——否則下一次有人重排 prompt 的 章節順序時，同一個缺陷會無聲回來。

順帶抓到的第二個問題：儀器本身沒有隔離變數

closed_loop.py 的第一版把「e688f346e^ 的章程」對上「HEAD 的章程」， 而 --dry-run 的逐對 diff 顯示那一對是 +35/−3 行，其中大部分不是 D6 修訂，而是後來 E1 對 D1 的更新。⇒ 那一對同時量了兩件事。 沒有隔離變數的一對不是比較，是兩個改動穿著同一個標籤。 改成四臂後：A→B 是 +18/−0 行（D6 本體）、B→C 是 +18/−4 行（E1 的 D1）、 C→D 章程 0 行／memories +23,785 B。只有 A→B 回答欠帳。

5. 沒結清的兩件事（這是本文最重要的一節）

5.1 D6 的閉環欠帳：機制已建，模型半沒跑

CONVENTIONS.md §E 規定「改動憲章等於改動兩個 loop 的行為，每次改動都要走一次閉環對照」。 D6 的 2026-09-16 修訂聲稱「改變不到任何執行時行為」——而 §E 自己就是那個主張的檢驗條款。

不得宣稱已結清

closed_loop.py 已建、四臂已驗、--dry-run 已通過。 但模型半沒有跑，所以那句「改變不到任何執行時行為」目前仍然沒有產物支撐。 PLAN §9 的原文要求是「在對照跑過並留有產物之前，不得聲稱 D6 修訂已結清」。

未跑的理由是具體的，而且它不是「做不到」：

  1. 本機沒有模型端點（見 §4 的探測結果）。
  2. 而 llama-server 與本 repo 的 13.6 GB 模型都在，所以技術上可以起一個。
  3. 但那會與另一個 session 正在進行的 prefill/decode 量測互相干擾。 那個 session 此刻正在改 src/llama.cpp/ggml/src/ggml-metal/*， 而它的量測對 GPU 時脈與記憶體狀態極敏感（見 CONVENTIONS A16 的 τ 與熱暫態）。 起一個 13.6 GB 的 server 去回答 32 個問題，代價可能是對方整輪的數字作廢。

為了結清一條欠帳而弄壞另一條線的資料，不是結清。 要跑它的指令（在沒有併行量測的時間窗）： 

CLOSED_LOOP_MODEL_CMD='<讀 stdin 寫 stdout 的任何模型命令>' \
  python3 agent_harness/engine_loop/distill/closed_loop.py

跑完之後還要人工核對 closed_loop_questions.md 的承重點表格—— 字串相同只是自動部分；兩份答案可以字面不同而判準相同，也可以字面相同而都漏掉承重點。

另外一件事也因為 E2 而變了：§E 說「這份文件是 sft_pi/ 的 system prompt 與 harness_engine/memories/engine/ 的注入來源」——那兩個目錄以前不存在，現在存在了。 所以 D6 那句「改變不到任何執行時行為」不再能靠「沒有消費者」成立，它變成一個待驗證的斷言。

5.2 T1 沒接真實模型跑過

refine_engine.sh 的三條路徑（--dry-run、真跑、--accept） 都在假 prime-agent 下驗過，但沒有任何一次輸出是模型產生的。 REFINE_ENGINE_MODEL 刻意不給預設值——「用哪個模型蒸餾」是一個判斷， 腳本猜一個會把一個沒被檢驗過的選擇偽裝成慣例。

6. 與另一個 session 的併行（這一輪的實際工作條件）

這一輪開始時另一個 session（d3b97a6a，flashkv-devserver）是 completed；中途它回到 working，並在我工作期間推了三個 commit、 改了 scripts/check/decode_sweep.py、m123_oracle_gate.py、 run_server.sh，最後連 src/llama.cpp/ggml/src/ggml-metal/* 也在改。

因此這一輪的 commit 只 stage 自己的路徑，不用 git add -A。兩件必須揭露的事：

  • MANIFEST.jsonl 會吸收對方未提交的位元組。它的 drift 是 bytes／mtime 逐檔比對，而對方那三個 CURATED 檔案（ scripts/check/decode_sweep.py 58,186→58,990 B、 m123_oracle_gate.py 37,418→38,802 B、 run_server.sh 115,956→118,540 B）此刻是髒的。 重生 manifest 就等於把它們的中間狀態寫進去。對方的收尾一向會再重生一次， 所以它會自我修正——但這件事必須寫出來，不然它看起來像是我的資料。
  • 沒有起模型 server，理由見 §5.1；這是刻意的，不是遺漏。

7. 為什麼值得做（而不是「又多了一個目錄」）

E2 之前，這個 harness 累積了 122 筆觀測、38 個判斷點、106 條規訓——而它們只有人讀得懂。 E2 之後，同一批東西有三種機器可讀的形態，而三者都由 record 推導、都可 --check。

更關鍵的是 §3：這一輪的產物裡最有價值的不是那 121 個檔案，是一個被測試抓到的設計缺陷， 以及把它變成回歸斷言的那一行。如果沒有 selftest.py，那個 prompt 會一直 「看起來能用」——它會跑、會 exit 0，只是蒸餾出來的東西每次都被 validate 擋掉， 而人會以為是模型不好。
