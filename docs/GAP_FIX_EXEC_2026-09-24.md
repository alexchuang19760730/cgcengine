## 1. ★ ρ 已經不是「別碰」，是「已 commit」

來源：`docs/RHO_MAXQ_SETTLED_2026-09-23.md`（2026-09-23，prod-new 統一介面，同輪同環境）。

| 臂 | t/s | hit% | vs on |
|---|---:|---:|---:|
| base（MTP off） | 9.85 | 94.9% | +6.9% |
| on（MTP on，無 ρ） | 9.21 | **67.9%** | — |
| rho（無保險絲） | **4.62** | 88.9% | **−50%** |
| **rho-q16（MAXQ=16）** | **9.64** | **90.9%** | **+4.7%** |
| rho-q8 | 8.37 | 90.3% | −9% |
| rho-q4 | 7.00 | 87.2% | −24% |

**決定性證據**：rho-q16 臂 `#13 maxq_limit = 3249/3348` ⇒ 97% 的 drop 是保險絲做的
⇒ 干涉就是 −50% 的元兇，**ρ 機制本身淨正**。掃描單調 q16 > q8 > q4 ⇒ **MAXQ=16 是甜點**。

保險絲 `CGC_RHO_PREFETCH_MAXQ` 已 commit（079f2fe46）。
⇒ **白皮書 §8.1「提前 fill / 背景預取（含 ρ）｜ρ 實測 t/s −21%」這一行必須改判**：
−21% 是**沒有保險絲**那一臂；有保險絲是 **+4.7%**。

### 1.1 真正的根因（與白皮書 §3 的說法不衝突，但更精確）

白皮書 §3 說「把 IO 藏起來的五條路全滅」，判據是 `L3_WINDOW_ZERO`（MoE 永遠在 segment 第一個
buffer ⇒ 可遮窗口 = 0）。但 ρ 實測 **lead 1.31~2.27 ms > 需求 `cov·F` 0.904 ms**
（`RHO_STAGE0_RESULT` §9.3）⇒ **ρ 那一格的窗口實測不為 0**。

⇒ 兩句話要同時成立，就要分清楚：
- 「**MoE 在 segment 第一個 buffer**」⇒ 拿**同一個 segment 內**的 GPU 工作來墊 ⇒ 窗口 0。
- ρ 墊的是**上一個 segment 的尾巴**（MoE core(L−1) 之後發起 fill(L)）⇒ 窗口是真的。
⇒ **白皮書 §3 的「全滅」應限縮為「同一 segment 內的隱藏」，不含 ρ。**

### 1.2 ρ 失敗的真身是 IO shape（已被保險絲繞過）

| | MiB/job | 讀的位元組 | `fill_wait_us`（累計） |
|---|---:|---:|---:|
| base | 0.230（241 KB） | 8.80 GiB | 56~75 ms |
| rho（無保險絲） | **0.041（42 KB）** | **3.18 GiB（−64%）** | **15.4~20.0 s** |

`fill_wait_us` 是 `fetch_add` 的**累計**量（`llama-expert-cache.cpp:885/990/1120/1133`），
而且 `:990` 把**同步 demand fill**（`fill_pool_direct`）也包進去了 —— 既有註解說它「只算
prefetch 等待」與 `:990` 的實際行為不符，引用時以 `:990` 為準。

總位元組少 64%、時間卻從 ~0 變成 20 s ⇒ **IOPS／per-read 固定成本主導，不是頻寬**。

## 2. ★ 一個還沒人問的問題：ρ 的 hit 提升不是預取帶來的

```
on（無 ρ）      hit 67.9%
rho-q16（97% 的預取被保險絲丟掉）hit 90.9%
```

**丟掉 97% 的預取，hit 卻從 67.9 升到 90.9** ⇒ 這個 +23pp **不是預取量買來的**。
預取只能解釋 88.9 → 90.9（+2pp）。剩下 +21pp 的來源沒歸因過。

候選（未查）：① ρ 讓 ids 更早交給 `ensure`，slot 分配/去重更好；
② `CGC_RHO_FILL=1` 換了 fill 路徑；③ 保險絲的 drop 本身改變了池的內容（少踢換）。
⇒ **這是 ρ 目前最大的未歸因項，而且它比預取本身值錢。**

### 2.1 順帶發現：MTP on 讓 hit 崩了 27pp

| | hit |
|---|---:|
| base（MTP **off**） | **94.9%** |
| on（MTP **on**，無 ρ） | **67.9%** |

⇒ 交付形狀是 MTP on ⇒ **它天生就站在 hit 67.9% 這個坑裡**，而 ρ 把它拉回 90.9%。
⇒ ρ 的價值在交付 cell 上被放大（這也解釋了為什麼 ρ 在 MTP-off 對照裡看起來不值錢）。

## 3. A / B / M-S2 全部卡在 h，而 h 的兩個口徑被混用

### 3.1 口徑糾正（最容易錯的一步）

- **覆蓋率** cov = \|預測∩真實\| / \|真實\|：ρ 實測 **0.8542**（`RHO_STAGE0_RESULT` §2）。
- **全中率** h = P(未覆蓋數 = 0)：白皮書 §6 定價 A 用的**就是這個**。

**兩者可以同時是 0.854 和 ~0**：若每次固定錯 ~2.8 個 expert，cov = 0.854 而 h = 0。
已寫進 `scripts/check/idseq_h_curve.py` selftest case 2（8 個 id 每次換 1 個 ⇒ cov 恰 0.875、
**h 恰 0**）—— 這個 case 存在的理由就是防止有人拿 cov 當 h。

⇒ **白皮書 §6 那張敏感性表（33% → 13.53 … 100% → 16.01）沒有一個 h 有實測支撐。**

### 3.2 h 的硬上界（無需假設）

ρ 實測 `uni_avg`（真實 union）= **19.36**、cov = **0.8542**
⇒ 平均未覆蓋 = 19.36 × (1 − 0.8542) = **2.83 expert／次 hook 調用**。

A 要求未覆蓋 = 0，由 `E[X] ≤ (1−h)·X_max`：

```
2.83 ≤ (1 − h) × 19.36   ⇒   h ≤ 0.854
```

門檻 0.65 ⇒ **上界既不足以否證、也不足以支持 A**。
而且 `rho_tok` 與 `cov_uni` 代進方程後 **h 會被消掉** ⇒ 這兩個聚合數對 h **零約束力**
⇒ 要定案只能量 X 的**分布**。

### 3.3 不依賴 h 也能判的一條：A 贏不了「ρ 已落地的那格」

| 路線 | 藏掉什麼 | 值 | 需要 h |
|---|---|---:|---|
| **ρ（已 commit，MAXQ=16）** | cb 的 IO | **+4.7%（實測）／上界 14.39** | 否（cov 0.854 即可） |
| A | cb + submit | 15.99 | **是**（圖建錯要重建） |
| B / M-S2 | 整段邊界 | 17.36 / 19.0 | 更嚴格（miss = 0） |

A 的 15.99 = `gap 44.4 → 10`，未命中要**付原價加重建**：
`h=0.75 ⇒ 15.2`、`h=0.5 ⇒ 14.0`、`h=0.25 ⇒ 12.9`、`h=0 ⇒ 現狀以下`
⇒ **A 要贏過 ρ 的上界 14.39，需要 h ≥ 0.75**，而最強預測源（ρ 自己）覆蓋率才 0.854。

⇒ **在 h 有實測值之前，A 不該是第一順位。**
