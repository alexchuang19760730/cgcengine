§1 三個問題，以及為什麼「答案必須是一條指令」

問題來源為什麼不是一份文件

§2 四條硬規矩（每一條都對應一個已付過的學費）

規矩一：單一真相來源

閘門清單只在 agent_harness/portal/gates.json。Portal 顯示的「復現指令」與 --gates-only 實際跑的是同一份 ⇒ 結構上不存在「文件寫的指令已經不是實際跑的那條」。 兩份清單必然漂移，而漂移是靜默的。

規矩二：不假裝

需要 GPU／build 產物／docker／模型端點的閘門標成 cost=heavy， 在表上是 SKIP 並附前題，不會被畫成綠燈。 理由是本 repo 自己最著名的自欺路徑：check_build_tracked.sh 不帶 BIN_DIR 時 11 段全部 SKIP，卻仍然印 OK。 把跑不動的閘門畫成綠燈，比沒有閘門更糟。

規矩三：缺席要出聲

沿用 CONVENTIONS.md:7-14 的驗收形式：目標樹每一節要嘛有可解析的指針 （建議用 {"path": …, "contains": "…"} 形式 —— 它對行號漂移免疫，純 path 不然）， 要嘛有一行 evidence_note 明說它的證據形態。閘門同理：快速閘門沒有自測時要交代理由， 或它的 cmd 本身就是 --self-test。 缺口從來不是「沒有檔案」，是沉默 —— 而沉默與沒人管在讀者面前同形。

規矩四：可執行檔而不是形容詞

每一個主張都要能指到一個可重跑的指令；趨勢要落在只追加的 jsonl，不是落在 HTML 的時間戳。

三棵樹在頁面上共用一個右側面板，點任一節點都會回答四件事：為什麼、 什麼算完成、卡在哪、證據在哪。節點可折疊（▾）、 Ctrl/⌘ + 滾輪縮放 —— 這兩件事是「可復盤」的實際含義： 讀者要能在同一頁上從「目標」走到「哪一條決策被推翻了」。

§5 它第一次跑就抓到的四件事

5.1 兩條閘門在一棵乾淨的樹上就是紅的

閘門實測性質
derived-engine-memories memories/engine/ 156 檔 vs lessons.jsonl 179 條 ⇒ 缺 23 筆 衍生記憶落後教訓（system prompt 的注入來源比教訓本身舊）
derived-sft-prime train.jsonl 162 行，重推得 181 行 資料集 stale

兩條都不在提交閘門的 11 段裡 ⇒ 它們存在、跑得動、而且是紅的， 但沒有任何人在提交時會踩到。這是「閘門存在 ≠ 閘門被跑」最具體的形式。

刻意不順手重生它們
build_memories.py 一跑就會改變兩個 loop 的 system prompt（§E 的閉環對照義務）， sft_prime 同理 —— 那是決策，不是修 bug。兩者都已列進 portal 的欠帳頁， 各附一行可複製的修復指令。

5.2 決策 registry 的覆蓋落差

traces/decisions.jsonl 的最後一筆停在 2026-09-16， 而 09-17／09-18 的判準決定只存在於 .workbuddy/memory/*.md 與 CONVENTIONS.md 的修訂裡 ⇒ 它們不會進任何資料集 （sft_prime 只從三個 jsonl 投影）。這是「登記制 vs 日誌制」的結構性落差，不是 bug， 但它是可量化的：覆蓋停滯天數。

5.3 ★ 另一個 session 的 commit 留下了一個懸空引用

本輪進行期間，另一條線提交了 6e0cc0316（feat(sweep) + docs(memory,skill)）。 它包含 agent_harness/skills/README.md 與 agent_harness/skills/SNAPSHOT.jsonl， 而那兩處正是我這一輪的改動（新 skill 的成員表列 ＋ 匯入器為它產生的記錄）—— 他們跑 import_harness_snapshot.py 時把它的輸入一起收了進去。

後果是一個可機檢的懸空引用。實測：

SNAPSHOT 共 14 筆；不在版控的副本: ['agent_harness/skills/cgc-observer-portal/SKILL.md']

也就是說：SNAPSHOT.jsonl 已經提交了一列指向某個副本， 而那個副本不在版控裡。clone 出來的機器會拿到一份指著不存在檔案的清單。

為什麼每一道閘門都是綠的
import_harness_snapshot.py --check 印 -> OK: 快照與原檔一致（provenance 逐筆相符、集合相符、副本未被手改、README 成員表相符） —— 因為它驗的是磁碟上的副本與來源 sha256，而那個副本確實在磁碟上。 「索引／SNAPSHOT 綠」與「在版控裡」是兩個獨立的軸； 30 秒的判別式是對任何要引用的路徑跑 git ls-files --error-unmatch。 修法是純新增 git add（零內容改動）—— 本 commit 就做這件事。

5.4 兩條「輸入易變」的閘門

index-memory 與 snapshot-freshness 的輸入含 .workbuddy/memory/*.md —— 那是多 session 共寫的 append-only 每日日誌。 另一個 session 正在 append 的那一刻它們會紅，而那個紅是對的（快照／索引真的落後了）。 Portal 對這兩條會多一個 輸入易變 標籤， 並在 tooltip 裡寫明判準：看它印出來的檔名是不是別人在寫的那一天； 是 ⇒ 等對方寫完再刷新，不要在別人正在寫的時候重生 （§4：把對方未定稿的位元組烤進你的 commit）。

§7 三個我自己的錯，以及它們各自的一般化

7.1 我寫下了一個假宣稱

我量到「<code> 214 個、</code> 213 個」， 於是斷言「來源語料有不成對的標籤」，還把它寫進程式註解。那是假的。

真正的原因：內嵌 JSON 產生時會把 </ 轉義成 <\/ （防 </script> 提前結束），所以 payload 裡的 </code> 本來就是 0。還原轉義之後是 214/214。註解已改成實話，並保留「這一條是被一個假症狀引出來的」。 一般化：內嵌 JSON 的 HTML 不能直接數標籤，要分區數（HTML 本體／payload／JS）或先還原。

7.2 正確的陷阱，我犯在錯的地方

為了自動驗產物，我寫了 verify_output()——而它的第一版用 "<b" 當前綴去數標籤，於是命中 <br> 與 <body>， 印出一排假的「不對稱」。這個陷阱本 repo 已經記過一次（cgc-commit-gate §1.3 同族）， 而我把它犯在專門抓輸出缺陷的函式裡。第二版改用 "<div>"， 又因為 div 永遠帶屬性而數到 0。最終寫法是 「<tag 後面接空白或 >」的正則。 檢查器的錯與被檢查物的錯同形，是最貴的一種。

7.3 我的自我測試會污染真 repo

第一版忘了把 PA_PORTAL_REPO 傳給子行程 ⇒「跑自測」等於「在真正的 repo 原地產生一份 portal」（data.json 與 history.jsonl 真的被寫出來了）， 而 13 格 fixture 全部「通過」。已修，並加了第 O 格看門狗： 跑測前後比對真 repo 相關目錄所有檔的 (mtime_ns, size)。 自測有副作用是這個 repo 最不能接受的失效模態之一，所以它必須有自己的陰性對照。

同一族的第四個：同一個 dict 字面量裡重複的鍵
SKIP 那一列的「理由」我在 dict 裡寫了 "tail"，而同一段稍後又寫了一次 "tail": "" —— 後者勝，理由被靜默蓋掉。 症狀是那一格空白，看起來像「沒有理由」，而它其實有。 這與 7.1（量測假象）、7.2（前綴誤配）是同一個家族的第三次：輸出看起來像缺陷，或缺陷看起來像正常。

§9 誠實邊界（不主張什麼）

  • 不主張 heavy 閘門的狀態。它們在這一頁是未知，不是綠。要它們的狀態就得手動跑並看輸出。
  • 不主張排程已經在跑。自動化已建，但 automation_runs 尚無紀錄 ⇒ 只主張「機制已建 ＋ 15 格自測通過」。驗收是執行紀錄，不是它的存在。
  • 不主張目標樹的措辭正確。--check 只驗它有沒有指針、有沒有 acceptance；措辭對不對是人的判斷。
  • 不主張兩次執行可比較，除非輸入指紋相同（c9911078f39c36e1）。 指紋是六個檔的 sha256 前 12 位串接：三個 jsonl、CONVENTIONS.md、 gates.json、goals.json。
  • 不主張 D6 的閉環對照已結清。它仍未執行，狀態與本輪之前相同； 而本輪又新增了一個 skill（那是判準的載體），等於讓那條欠帳多一筆待對照的改動。
  • 本 commit 沒有刷新 skill 快照。理由：我在這一輪新建了 cgc-observer-portal，匯入器已經被另一條線跑過（6e0cc0316 帶進了它的 SNAPSHOT.jsonl 記錄），但副本沒進版控 —— 本 commit 補上副本本身， 而不再重跑匯入器：.workbuddy/memory/2026-09-18.md 此刻正被另一條線 append， 重跑會把對方未定稿的位元組烤進來（§4）。所以 snapshot-freshness 目前在磁碟上是綠的， 但它的「新鮮」對應的是另一條線跑的那一刻。
  • 資產數字是「本次掃描的那一刻」。記憶檔當天必變、另一個 session 也在寫； 要看最新請直接開 docs/AGENT_HARNESS_PORTAL.html（它每次產生都重掃）。
