錨點 log：`Backup/cgc_logs/llama_server_20260920_023021.log`（MTP on、`ntok=4` 的 work row，n=107）。

## 0. 一句話

**採納「做 L3」這個決定（它是唯一還有量級、且不需要預測器的槓桿），但把「40–50%」改寫成「最大 +37%、硬天花板 18.6 t/s」，
並且在第 1 支 run 就掛上它自己預註冊的否證規則。** 它的中心值 19 正好坐在天花板上，上緣 20 在算術上不可能。

## 1. 今天新做的：cb 到底是不是「同步」的（78 支 log、零成本）

判準很簡單：**如果 cb 已經部分被重疊掉，那 step 對 cb 的斜率應該 < 1；如果 cb 完全串在臨界路徑上，斜率 ≈ 1。**

對每一支有 ≥15 個 `ntok=4` work row 的 log，跑一次 `total ~ cb` 的組內 OLS：

| 統計量 | 值 |
|---|---|
| 可用 log 數 | **78** |
| 斜率中位 | **1.455** |
| 四分位距 | 1.234 – 1.644 |
| 斜率 ≥ 1.0 的比例 | **0.97**（76/78） |
| 斜率 ≥ 1.2 的比例 | 0.81 |

⇒ **cb 是滿額串行的，而且每 1 ms 的 cb 帶走 ≥1 ms 的 step**（>1 的那一段與線 A 的
`gap_L = 1.00·cb_{L-1} + 0.3 ms` 同源：cb 不只佔自己的時間，還在下一層製造 GPU idle）。

⇒ **「移除 cb ⇒ step 掉 ~cb」這個前提成立，甚至偏保守。** 方向上支持 L3。

⚠️ 誠實邊界：組內斜率是**觀察相關**，共同的因（該步的 cold miss 數）同時抬高 cb 與各分量 ⇒ 這是
因果斜率的上界，不是點估計。但它與結構事實同向：`ensure_batch` 是 `outstanding == 0` 才返回
（`F2R_OVERLAP_EXPERIMENT_DESIGN_2026-09-20.md` §6 自己也這麼寫）⇒ **構造上串行**，斜率應 ≈1。

另外，`cb = 74.18 ms` 不是孤證：今天的表裡 09-20 有 8 支 log 落在 60–80 ms，
20260920_120310/120537 是 137/156 ms ⇒ 74 這個量級在同樣配方下是可再現的。

## 2. 但「248 − 74 = 174 ⇒ 19.4 t/s」這一步是錯的：它穿過了 GPU busy 的地板

從同一批 row 直接讀到的三個數（`DECODE_STEP_ROW_POPULATIONS_2026-09-20.md`）：

```
total 247.98 = wait 159.77 + cb 74.18 + submit 10.09
layer totals（重疊跨度，不可與 total 相加）：gpu_sum 181.56  union_sum 149.24  gap_sum 95.17
```

**把 cb 藏在 GPU work 底下，step 不可能短於 GPU 的忙碌總量 `gpu_sum`。** 所以任何「純 async issue」的結果都落在
`[181.56, 247.98] ms` 區間裡：

| 情境 | step (ms) | t/s @ mean_len 3.375 | t/s @ mean_len 4.0 |
|---|---:|---:|---:|
| 今天實測 | 247.98 | 13.61 | 16.13 |
| **重疊做滿（硬天花板）** | **181.56** | **18.59（+37%）** | **22.03** |
| 對方的算法 `total − cb` | 173.80 | 19.42 | 23.01 |
| 25 t/s 需要 | ≤ 135.00 | 25 | — |
| 25 t/s 需要（accept 做滿 ml=4） | ≤ 160.00 | — | 25 |

⇒ **173.80 ms 在 gpu_sum 181.56 之下 ⇒ 在算術上不可達**，除非同時把 GPU busy 本身做小（那是 G4 的地盤，不是 L3 的）。
⇒ L3 的誠實區間是 **13.6 → 15–18.6 t/s**，對方的「17–20」應改成「15–18.6」；**上緣 20（168.75 ms）越過了地板。**

⇒ 也順帶把「25」再釘一次：**即使重疊完美 ＋ accept 做滿到 mean_len 4.0，也只有 22.0 t/s < 25**
（25 需要 ≤160 ms，仍低於 gpu_sum）。L3 不會改變「25 在現行配方下不可達」的結論，它只把缺口從 11.4 縮到 3.0。

## 3. 它自己的預註冊，今天為止一次都沒被量過

- `fill_wait_us`（唯一的 calling-thread 計數器，L3 預註冊的輸出）**在 decode 步驟上一次都沒出現過**；
  全庫只有 `Backup/cgc_logs/prefill_recover3min_20260916.log` 有它，而且是 09-16 的 prefill context。
  ⇒ **第一件事是先證明這個counter 會出現在今天的 decode row 裡**，否則 L3 跑完也沒有否證的證據。
- 該文 §6 自己寫的否證條件是「`fill_wait_us` 掉了但 `total` 持平，因為 `wait` 上升」——§1 的斜率 ≥1
  說明這條**正是**最可能發生的失敗模式（cb 的時間會搬家到 wait 裡），所以它不是形式主義，必須在同一支 run 裡三個數一起讀。
- **他們自己排的順序是 L1 → L3 → L2**，而現在在跑的是 **L2**（30 min、而且自帶 regime caveat 使它的 cb 不可與交付 cb 相比）。
  ⇒ 順序已經被打破了；L1 只要 ~15 min 且能把 prefetch 家族一次關掉，別為了省它而跳到 2–3 h。

## 4. 風險：L3 動的是數值安全閘門，不是純效能

`CGC_NO_PREFETCH` 存在的原因就是：**背景 fill 可以覆蓋 GPU 正在 verify 讀的 slot**。
⇒ L3 必須帶「free-slot-only」的 slot 紀律（layer-ahead 既有先例），並且把「與今天的輸出逐位元相同」
（線 A 的 G2/G5）當成合併條件，而不是事後檢查。

## 5. 採納條件（四條，缺一就不要寫那 2–3 h）

1. **數字改寫**：以 ≤181.56 ms（18.6 t/s @ml 3.375）為註冊上界，不以 19.4/23–24 為目標。
2. **第一支 run 就掛否證**：`fill_wait_us` ↓ **且** `total` ↓ **且** GPU idle 沒等量上升，三者同讀。
3. **數值閘門先於效能**：free-slot-only ＋ 同一 prompt 的 output md5 與今天相同，失敗即 revert。
4. **先付那 15 min 的 L1**（順便拿到 cb=74.18 的第二個樣本 —— 那個 HOOK_SPLIT 四段拆解目前只有一份 log 支撐）。

## 6. 誠實邊界

* §1 的斜率是觀察相關的上界；真正唯一的裁判是 L3 自己那支 run。
* `gpu_sum` 是跨層重疊跨度之和，把它當地板用時假設「層之間串行且 GPU busy 不可再壓」——若未來 G4 壓縮了 busy，地板會跟著降。
* 本文件沒有跑任何 server；所有 ms 都來自 `CGC-DECPROF` row，與 `DECODE_STEP_ROW_POPULATIONS_2026-09-20.md` 同源。
