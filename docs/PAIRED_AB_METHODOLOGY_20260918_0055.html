1. 問題：A/B/A 的兩個控制臂差 48%

2026-09-18 00:26–00:30 跑了一次看似標準的 A/B/A —— 同一個 build、同一個 profile、同一個 cell 形狀（-p 0 -n 128 -d 512 -b 512 -r 3）、8 GiB pool，只差 --spec-type draft-mtp：

兩個控制臂是同一個配置、同一個形狀，卻差 48%。而它們的池統計幾乎相同：

臂hit rateresidentfile_readsbytes
off196.6%6153.70 MiB 269254.88 GB
off296.7%6153.70 MiB 266854.79 GB

兩個推論。（一）漂移不是池、不是 IO（池的行為一致到 0.2%）⇒ 它是機器外部狀態 （熱、記憶體壓力、鄰居負載）。（二）既然控制臂自己就差 48%，那麼任何用「單一對」算出來的 比值（例如 on/off1 = 0.768 或 on/off2 = 1.136）都不可引用 —— 而它們的方向甚至相反。

這一輪之前所有關於 MTP 的 t/s 結論（本線的 −23%、另一條線的 +5.7%、更早的 +31%） 都建立在這一類比較上。它們全部因此失效 —— 不是因為誰算錯，而是因為方法沒有判別力。

2. 方法：配對交錯 ＋ 反序對

漂移是慢變數。慢變數的正確處理不是「等它停」（等不到），也不是「跑更久」（它會累積）， 而是讓它在對內互相抵銷：交替兩個臂、每臂短、在對內取比值。

2.1 設計

項目值為什麼
形狀-p 0 -n 64 -d 512 -b 512 -r 4 生產 decode cell 的形狀縮短；目標是比值不是絕對值
丟棄樣本sample 0 它帶著 depth prefill 與池的第一次填充（後續 rep 走 llama_state_seq_set_data 還原）
統計量每個臂 median(samples[1:]) 樣本內有離群值（實測 arm2 off 出現 3.85 t/s）；中位數對它穩健
臂間等待20 s 滿載後約 35–47 s 回 NOMINAL；20 s 是「不讓整輪太長」與「不讓熱累積」的折衷
env兩臂完全相同，除 --spec-type 刻意不開 CGC_GPU_TIMING／CGC_DECODE_PROFILE：那些開關自己有成本，配對比較必須固定其他變數
臂序正序 off,on×3 ＋ 反序 on,off×2 見 2.3 —— 這是本方法的核心，不是可選項

2.2 判準事先宣告

判準寫在驅動腳本的 docstring 裡（/tmp/en_mtp_pair.py），在跑之前：

WHAT WOULD COUNT AS AN ANSWER, fixed BEFORE the run:
  * paired ratio (on/off) median well below 0.95 with a tight IQR  => MTP is a net loss;
  * paired ratio IQR straddling 1.0                              => still undecidable on this box.
Either way it is a result; a mid-run renegotiation of the criterion would not be.

理由：如果判準可以在看到數字之後才定，「整體」這個詞就沒有意義了。這一輪的結果落在第二條 （見 §3），而它是事先就允許的結論之一。

2.3 為什麼一定要反序對

ABAB 的每一對裡，off 總是先跑。如果「臂的位置」本身有效應 （page cache 暖了、池的狀態、Metal shader cache、環境漂移的單調段），on 就被 系統性偏誤 —— 而且偏誤方向與 treatment 方向無法分離。

把順序反過來（on 先跑）就能分離：令 M 是真正要量的倍數、s 是順序效應，則

ratio_AB = M · s        （off 先跑，on 被高估 s 倍）
ratio_BA = M / s        （on 先跑，on 被低估 s 倍）
=>  M = sqrt(ratio_AB · ratio_BA)      s = sqrt(ratio_AB / ratio_BA)

也就是說：正序對與反序對合起來才構成一次完整的測量；只做其中一半得到的是一個 M·s 或 M/s，而它與 M 無從分辨。

3.3 配對比值與順序校正

對先跑後跑ratio (on/off)
AB-1off 8.493on 9.0931.071
AB-2off 8.060on 9.4341.171
AB-3off 8.387on 8.4931.013
BA-1on 9.420off 10.0390.938
BA-2on 7.158off 10.2050.701
正序中位 = 1.071         反序中位 = 0.820
M = sqrt(1.071 × 0.820) = 0.937      （只用平衡的 2+2 對 ⇒ 0.959）
5 對的範圍 = 0.701 .. 1.171

讀法：M ≈ 0.94–0.96，而單對的散布是 0.70–1.17。 所以「MTP 讓 decode 變慢 6%」這句話的誤差比它本身大 —— 正確的述句是 「MTP 的淨效果在 ±10% 內，與 0 不可區分」。

一個方法論上的不對稱，值得記住：正序與反序的對數不相等（3 對 vs 2 對）時， 「全部 5 對的中位」（1.013）不是 M 的估計 —— 它仍帶著 (3−2)/5 × s 的偏。只用平衡的部分（2+2 對 ⇒ 0.959）或直接取幾何平均（0.937）才是。 「把資料全部倒進同一個中位數」在這裡是錯的。

4. 五條定則（可直接照用）

  1. 量兩臂一律 ABBA（含反序對）。只做正序或只做反序，量到的是 M·s 或 M/s，與 M 無從分辨。報告裡要寫明誰先跑。
  2. 臂要短。單調漂移在一對之內走得越少越好。本輪每臂 -n 64 -r 4， 含模型載入約 45–55 s；先用 A/B/A 的那一輪每臂是 57–66 s，漂移就吃掉了整個訊號。
  3. 丟掉 sample 0，用中位數。第一個 rep 帶著 depth prefill 與池的第一次填充； 樣本內有離群值（實測一個 3.85 t/s 對同臂其他 7–10 t/s）。
  4. 計數器優於 t/s。accept／emit／池 hit rate 不受時間漂移影響（見 §5）。能用計數器回答的問題，不要用 t/s 回答。
  5. 判準事先寫定。寫進腳本的 docstring，不是寫在事後的分析裡。

三個仍然成立的觀察：

  • gen_tok_per_round 恆為 3.000 ⇒ 每個臂都吃滿 n_max=3， 沒有被模型的 MTP 訓練長度夾到（speculative.cpp:1417 的 clamp 只在 chain_heads（非共用記憶體）時生效）。
  • 池 hit rate：on 臂 93.7–94.8% 對 off 臂 96.0–96.1% ⇒ MTP 讓命中率降 2.2pp，與前兩輪獨立量到的 file_reads +62%／bytes +129% 同向。
  • accept 本身的散布是 0.626–0.795（27%） ⇒ 任何「accept ≥ 60%」這種 單次門檻的判別力比它自己的變異還小。

還有一個機制上的發現（代數吻合，非直接量測）：acc_tok_per_round = 2.023， 而 n_max = 3、acc_rate = 0.6744：

若接受是序列相依（第一顆不接受則後面作廢）：p + p² + p³ = 1.436        ×
若每顆獨立接受：                              n × p = 3 × 0.6744 = 2.023  ✓（逐位吻合）

⇒ MTP 的草稿是平行產生、各自與 target 比對的 ⇒ 加大 n_max 的邊際收益是 線性的（不像 chain 投機那樣衰減）。這讓 n_max 掃描成為一個有定義的下一件事。

6. 首個應用：MTP 的淨效果 ≈ 0

把 §2 的方法用在「MTP 對 decode t/s 有沒有貢獻」上，答案是沒有可測的。

  • 順序校正後的倍數 M = 0.937，95% 等級的散布是 0.70–1.17 ⇒ 與 1.0 不可區分。
  • 這與 served 路徑（HTTP，8 GiB）先前獨立量到的「平手」一致： baseline 12.087 vs mtp-off 12.031。
  • 而且它推翻了本線在同一天較早報出的 −23% —— 那個數字的分母（off1 = 10.049） 恰好落在漂移的有利端。

對 roadmap 的意義：25 t/s 需要 2.07×（served 基準 12.0–12.1），而 MTP 貢獻 ≈ 0 ⇒ 決定 25 的仍然只有 GPU span（8 GiB 側 75.66 ms/step）。MTP 的價值不能建立在 decode t/s 上。

7. 附帶案例：症狀會指向錯的地方

同一輪還修好了 llama-bench 的 MTP 路徑（讓 --spec-type draft-mtp 在 生產 cell 形狀上真的能跑完）。它的失敗方式是一個獨立的方法論教訓：

test_gen_spec: verify decode failed: ret=-1 n_tokens=4(pos 0..3) n_ctx=768 n_past=1 draft=3 n_batch=512
llama_bench: error: failed to run gen
CGC-M2-UNREPOINT: teardown restored 120 expert tensor(s) to their model storage before freeing 6 slab(s)
                  (a second context built from this model would otherwise read a freed buffer)

這些訊息把它指向三個錯的方向：Metal 資源、記憶體不足、「第二個 context 踩到 freed buffer」。 而真因是一個初始化：test_gen_spec 明確指定 batch 的位置，而 n_past 從 0 開始 —— 但同一個 rep 裡 -d 512 的 depth prefill 已經寫過 pos 0..511，llama_decode 因此回 -1，而且不印任何訊息。

觀察指向
-n 16 -d 0 過、-n 128 -d 512 掛與 depth run 有關
--no-warmup 也掛不是 warmup 留下來的狀態
把 draft context 的建立提前到 warmup 之前 ⇒ 仍然掛不是「第二個 context」的時機
非 spec 路徑（test_gen）不受影響差別在誰決定 batch 的位置

⇒ 定則：當錯誤訊息指向「資源」時，先問「是不是有一個輸入被算錯」。 而判別式是「換一個形狀會不會好」 —— 短形狀成功不代表邏輯對，可能只代表它沒走到那條路徑。

8. 誠實邊界

不主張的事：

  • 不主張 MTP 在任何配置下都無效。本輪量的是「prefill250 profile 的 decode cell 形狀、8 GiB pool、n_max=3、llama-bench 預設取樣」。 served 路徑的 prompt／取樣不同（實測 accept 38.5% 對本輪的 62.6–79.5%）， 而 n_max 沒有掃過。
  • 不主張 +12.5% 是「熱」造成的。它是一個觀察到的位置效應，方向在這一輪是 「後跑較快」，但同一台機器稍早的 A/B/A 裡是「先跑較快」（10.049 → 6.791）。 所以它不是一個穩定的物理常數，而是單調漂移的方向；ABBA 的價值在於對稱地抵銷它， 不需要知道它往哪邊走。
  • 不主張 0.937 是精確值。它只有 2+2 對的平衡資料支撐，散布 0.70–1.17。 要收窄需要更多對，而每一對都是兩次 13 GB 載入。
  • acc_tok_per_round = n × p 是代數吻合，不是直接量測；接受機制的 驗證要靠 n_max 掃描。
  • 本輪沒有動 src/ 的量測部分之外的東西；沒有掃 n_max、 沒有把 MTP 登記成 prod_matrix.py 的 cell（--cells decode 必須 維持 MTP-off 且逐位元可比）。
