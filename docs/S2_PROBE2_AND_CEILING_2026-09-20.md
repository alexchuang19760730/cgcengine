# S2：第 2 支探針的答案，以及**重算後的天花板 ≈ 18.7**（不是 19.0–22.9）

2026-09-20 13:3x，線A (ace)。零 GPU：讀 `llama-expert-cache.cpp` 的計數器定義 ＋
`Backup/cgc_logs/f1_cb_miss_regression_report.json`（另一條線 F1 的普查）。

## 0. 兩句話

1. **57.42% 的受害者分歧是「策略差異」，不是「數值差異」** —— 只要 (表, 擺放) 由**單一權威**決定，
   任一 victim 政策都會給出**逐位元相同**的輸出。**⇒ 裝置側不需要移植 host 的 FP EMA。**
2. **但 S2 的天花板因此從 19.0–22.9 掉到 ≈ 18.7** —— 因為**只有 31.9% 的段邊界可以免等**，
   其餘 68.1% 的層有 miss ⇒ 必須有人等那次 fill。**⇒ S2 不值得做。**

## 1. 第 2 支探針：分歧是量上的，還是策略上的？

### 1.1 先確認 `capacity` 的語意（這一步是決定性的）

`llama-expert-cache.cpp:796-805`：

```cpp
// [CGC miss attribution] first demand touch of this (layer, expert) = compulsory; a
// second touch means it was resident once and got evicted = capacity.
if (cache->ever_loaded[layer][expert] == 0) { cache->ever_loaded[layer][expert] = 1; ...
                                              cache->n_miss_compulsory++; }
else                                        { cache->n_miss_capacity++;   }
```

⇒ **`capacity ≠ 0` 的意義是：被驅逐的那個專家，後來真的又被「要」了**（而「要」＝
該層的 top-k 選中它 ＝ 它**被消費**）。長 run 的 `capacity` 份額是 **79.9%**（`§EN-323`）。

### 1.2 但「表不同」不等於「輸出不同」

這是本節真正的推論，也是**對 S2 有利**的一條：

- gather 算的是 `slots = get_rows(slot_table, selected_experts)`，然後讀 **slot 的那一列權重**。
- 所以任一組 **(表, 擺放) 一致**的配對，讀到的都是**該專家自己的權重** ⇒ 輸出逐位元相同。
- 兩個政策會給出**不同的表**（不同的 victim ⇒ 不同的 `-1` ⇒ 不同的再採用槽位），
  但**各自與自己的擺放一致** ⇒ **兩者的輸出相同**。

⇒ **受害者的身分本身不改數值。** 會改數值的只有一種情況：**表與擺放不一致**
（裝置說 e→s，而 host 把 e 放到了 s′）。那是**權威歸屬**問題，不是政策等價問題。

### 1.3 所以第 2 支探針的答案是

**策略差異，不是數值差異** —— **前提是 (表, 擺放) 只有一個權威。**

⇒ **S2 的裝置側可以採用任何 victim 政策（哪怕是最笨的），不需要移植 `spac_util` 的 FP EMA。**
`§EN-324` 的「必須帶 FP EMA」結論**據此修訂**為：**只有在「要求裝置複現 host 的受害者序列」這個
本來不必要的約束下才必須**。改成「**裝置是唯一權威、host 的 fill 照著做**」之後，那條約束消失。

**但被換進來的新要求是**：host 的 fill 必須**讀得到裝置的表**（共用緩衝），
而且**這一刻要用的專家必須已經填好** —— 也就是下面這件事。

## 2. 重算天花板：**只有 31.9% 的邊界可以免等**

### 2.1 為什麼免等的條件是「該層該步零 miss」

host 今天必須等 segment i 完成，唯一原因是**要拿到 ids 才能寫 `slot_table`**（計畫書 §3）。
若那一層選中的專家**全部已經在各自的槽上**，表**不變** ⇒ 表本來就對 ⇒ 那一次**不需要等**。

⇒ **可免等的邊界 ＝ 該層該步 `m = 0` 的邊界。**

⚠ 只有**裝置側持有表**時才能知道「m=0」而不必先拿 ids（裝置同時看得到 ids 與 residency）；
所以這是**裝置化之後**的可及份額，不是今天就能拿的。

### 2.2 份額（F1 的普查，`pairs = 3921`）

| 量 | 值 |
|---|---|
| `by_m.0.n`（該層該步零 miss） | **1251 ⇒ 31.9%** |
| `by_m.1.n` | 865（22.1%） |
| `≥2` | 餘下 46.0% |
| **`cb_share.pct_from_layers_with_miss`** | **99.775%**（零 miss 的層只貢獻 **0.22%** 的 `cb`） |
| `per_miss_linear` | intercept **0.4616 ms**、slope **0.6954 ms/miss**、r² 0.862 |

⇒ 零 miss 的邊界不只是「沒有 fill」，而是**真的閒**（`cb` 中位 0.01 ms）——
所以它們正是可以免等的那一群，這與 §2.1 的機制推論一致。

### 2.3 天花板的算術

`§EN-304(2)` 的「S2 完美」＝ `total → union`，把**所有**邊界的等待拿掉：
E2b 暖 `total` **139.46** → `union` **104.87** ⇒ 可拿掉 **34.59 ms** ⇒ **22.9 t/s**。

只拿 **31.9%** 的邊界（其餘必須等）：

```
可拿掉  ≈ 0.319 × 34.59 = 11.04 ms
新 total ≈ 139.46 − 11.04 = 128.42 ms
         1000 / 128.42 × 2.40 = 18.7 t/s
```

| 版本 | 引擎內部 t/s | 性質 |
|---|---:|---|
| 舊「S2 完美」（所有邊界） | 22.9 | 推算，**從未達成** |
| 舊「只有 submit 能搬」 | 19.0 | 推算 |
| **重算：只有 31.9% 的邊界可免等** | **≈ 18.7** | **推算**（本節） |
| 現況 | 17.2 | 同一個推算家族 |

⇒ **S2 的誠實天花板 ≈ 18.7（引擎內部口徑）＝ ×1.087**，**比記錄一直在引用的最保守格 19.0 還低**。
交付口徑的數字**未知**（兩台儀器之間沒有可用的校準），但按同一個比值只會更小。

### 2.4 這條算術的三個假設（明寫）

1. **可拿掉的等待與邊界數成正比**（34.59 ms / 39 個邊界）。實際上等待的**大小**可能與該層的成本相關，
   而零 miss 的層可能剛好是**便宜**的層 ⇒ 那麼可拿掉的會**更少**。⇒ 18.7 是**樂觀**值。
2. `mean_len` 2.40 與 `union` 104.87 都是 E2b 暖的模擬值（推算家族的老問題）。
3. 裝置側政策若與 host 不同，**miss 樣式會變** ⇒ m=0 的份額也會變。這一格**無法在實作前得知**。

## 3. 所以對 S2 的建議（工程判斷）

| | |
|---|---|
| **可及增益** | ×1.087（引擎內部；交付口徑未知且更小） |
| **成本** | 裝置側策略 ＋ 唯一權威的介面 ＋ **6.16% first-touch 的規則設計**（會動數值的那一項）＋ 一次逐位元閘門 |
| **對照** | `G4` 的空間是 **5.4×**（`union` 104.87 vs 權重地板 19.5 ms/步） |
| **而且** | 18.7 **仍然 < 25** ⇒ S2 單獨不達標，必須與 `G4`／`G6` 疊乘 |

⇒ **建議：不要把 S2 做完。** 把那份工程預算移到 `G4`（逐層無名長尾的歸因），
而 S2 保留為「**已量到天花板的備案**」，等 `G4` 把 `union` 壓下來之後再重估
（那時 `union/total` 會變，S2 的可及份額也會變）。

**如果仍要推進 S2**，下一個具體步驟（按風險排序）是：
① 唯一權威的介面（共用表緩衝 ＋ host 照表 fill）：**不動數值**，可先做；
② `m=0` 的判定裝置化（這一步才真的需要裝置看得到 residency）；
③ first-touch 的規則 ＋ 逐位元閘門（**會動數值，必須最後做**）。
