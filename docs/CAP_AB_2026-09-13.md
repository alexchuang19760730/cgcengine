## 1. 結論

**cap 是純品質旋鈕，速度代價是零。**

| | cap 6 | cap 8 |
|---|---|---|
| 48 題通過 | **0/48** | **9/48（18.8%）** |
| 瞬間失敗（`error 0.0s`） | **25 / 48** | **0 / 48** |
| prefill | 15.807 t/s | 15.840 t/s |
| decode cold / warm | 10.940 / 10.351 t/s | 11.199 / 12.437 t/s |
| 防護 env | `CGC_NO_PREFETCH=1 CGC_VERIFY_DECODE=1 CGC_DRAFT_DECODE=1` | 同上 |

prefill 差 **0.2%**、decode 差 **2.4%**（且方向不一，warm 反而 cap8 快）→ 在量測噪音內。
兩臂的防護環境完全相同，所以 cap 是唯一變數。

逐 profile：

| profile | cap 6 | cap 8 |
|---|---|---|
| qa-zh | 0/8 | **3/8** |
| longform-zh | 0/6 | 0/6 |
| coding | 0/11 | 0/11 |
| math | 0/8 | **2/8** |
| reasoning | 0/5 | **2/5** |
| writing | 0/5 | 0/5 |
| translation | 0/5 | **2/5** |
| **總計** | **0/48** | **9/48** |

失敗型態也不同，不只是分數：

- **cap 6**：短輸出、純回顯 —「簡短回答。 法國的首都是哪裡？？ 答：簡短回答。…」
  qa-zh 輸出長度 `[65, 59, 0, 163, 51, 511, 75, 0]`
- **cap 8**：內容大致對再複讀 —「台灣的首都是哪裡？」開頭就答「台北」然後重複；
  qa-zh 輸出長度 `[692, 91, 34, 43, 43, 129, 56, 69]`

## 2. cap6 那一臂的量測是**無效的**，這比 cap 本身更重要

`cap6: TOTAL 0/48` 這個數字有 25 題是**量在一個已經死掉的伺服器上**。

證據：

| 檢查 | 結果 |
|---|---|
| cap6 伺服器日誌的 distinct task 數 | **26**（suite 有 48 題） |
| suite 中 `error 0.0s` 的題數 | **25**，全部集中在第 26 題之後 |
| 日誌結束方式 | `13.43.085.525 I srv operator(): operator(): cleaning up before exit...` |
| 該訊息的來源 | `tools/server/server.cpp` 的 `clean_up`（signal handler 路徑，**不是** crash/abort） |
| cap8 伺服器日誌 | **51** 個 task、0 個瞬間失敗、沒有 exit 訊息 |

`clean_up` 只在收到 signal 時被呼叫（`server.cpp:429`，與 `fit-params/README.md` 記載的 `^Csrv operator(): cleaning up before exit...` 一致）。
判斷：**外部 signal**（這台機器同時跑多個 agent，先前已有同型事件；也可能是別的行程的 `pkill -f llama-server`），
不是引擎 crash，也不是我的 driver（driver 只在開臂前與收尾時 kill）。
成因未定案，但**沒有重現**（cap8 同樣 binary、同樣 pool、只差 cap，跑滿 51 個 task）。

真正該修的是**量測工具**：`bare_48.py` 在伺服器死後仍然一題一題往下跑，
把每一題記成 0 分，最後只印「0/48」。這正是這個專案反覆踩到的假結論類型
（見 `POOLSIZE_INVARIANCE_2026-09-13.md` §6 的 cap 靜默不一致）。

**已修**：`scripts/check/bare_48.py` 新增死伺服器防護。連續 `DEAD_SERVER_STREAK = 5` 題
「空內容且 elapsed < 1s」就中止，並在該次報告蓋上無效章：

```
!! 連續 5 題瞬間空回應（elapsed<1s）——伺服器已不在，中止於 qa-zh #5；此報告的通過率無效

總計: 0/4 (無效 — 連續 5 題瞬間空回應…)
```

JSON 也多了 `invalid` / `invalid_reason` 兩個欄位。用一個死掉的 port 實測過（立即中止、`invalid=True`）。

公平比較：扣掉 cap6 沒量到的 22 題，兩臂**都量到的 23 題**是 cap6 **0/23** vs cap8 **3/23**。
所以就算只看有效量測，cap6 仍然明顯較差 —— cap 的結論不依賴那 22 題。

## 3. 為什麼這件事改變了先前的結論

`POOLSIZE_INVARIANCE_2026-09-13.md` 的 pool 大小不變性（M1 103/103 逐位元、4/6/8 GiB）
**是在 `--pool-cap 6` 下證明的** —— 而 cap 6 正是模型退化到 0/48 的設定。

不變性本身沒有錯：它證明的是「pool 大小不影響數值」，這件事在 cap 6 與 cap 8 下都可以成立。
被影響的是**這份不變性的意義**：它是在一個模型答不出問題的形狀上取得的。
若 pool 佈局與 ubatch 形狀的交互在 cap 8（模型真的會作答的那個形狀）下不同，
先前的結論就沒有涵蓋它。

因此已啟動 `cap 8` 版的重做：新參考 + 4/6/8 GiB 三格，cap 全部釘 8。
驅動：`/tmp/poolsize_invariance_cap8.sh`；log：`/tmp/poolsize_inv_cap8.log`。
（cap 8 下的 preflight 已 PASS 且答對：`content='15+27 等於 42。'`。）

順帶修掉一個 API 障礙：oracle dump 原本**只在 `--oracle-ref` 存在時才寫**，
所以要產一份新參考必須先指向某份舊 dump —— 雞生蛋。已新增 `--dump-oracle`，
讓「只產 dump、不比對」成為一等公民。

### 過程中抓到的第二個前綴缺陷（已修）

第一次重做時，參考只有 **60 行**，而每個候選都有 **117 行**，`gate-oracle-final` 卻報 `M1 60/60` 完美。
真相：參考是候選的**嚴格前綴**（`ref-only keys = 0`、`cand-only keys = 57`）。
根因是我的新 `--dump-oracle`：`ask_probe()` 住在 `oracle_gate` 裡，那支探針正是把後續 57 個 step 追加進 dump 的東西；
參考產製時跳過 gate 就等於跳過探針，於是「完美 60/60」掩蓋了 57 個從未比對的 key。

這是 `POOLSIZE_INVARIANCE_2026-09-13.md` §6 那個前綴缺陷的**鏡像**（那次是候選被截、這次是參考被截）。
已修：`--dump-oracle` 現在也會送同一支索引探針，所以參考與候選覆蓋同一段步數。
修完後參考 = 117 行，`gate-oracle-final` 的 `n` 從 60 變 117 —— **n 本身現在是一個可用的健全性訊號**。

## 4. 誠實界線

- **單一 prompt 分布**：48 題是規則式 pass/fail（`required_any` + `length` + `forbidden` + `loop_phrase` + `finish_reason`），
  不是語意評分。cap8 的 9/48 是「在這個評分器下」，不代表模型能力。
- **cap8 的絕對值仍遠低於這支的既有 37/48**（`demo/sweet-spot-windows-fix @ 8eb570598`）。
  qa-zh 在那水準應該 6–8/8。所以還有一個獨立於 cap 的退化因子沒找到
  （cap8 的 #1 洩漏 `<think>` 且 692 字踩 `forbidden`）。
- **只有一顆模型**（iq3 欄位）；iq4 未跑。
- **cap6 的死因未定案**，只確認「不是引擎 crash、沒有重現」。
- 兩臂都是單次量測，沒有交錯輪替；速度差異在這個量級（0.2–2.4%）下不應被當成真實差異解讀。
- cap 的**數值**機制（為何 6 與 8 讓 logits 差這麼多）未追；這裡只量了行為層面的代價。
- cap-8 不變性只驗了 **iq3 一顆模型**；iq4 那欄未在 cap 8 下重跑，所以 `POOLSIZE_INVARIANCE` 的跨模型結論仍只在 cap 6 有證據。
- cap-8 的 117 個 step 來自**單一 prompt 軌跡**，證明的是 pool **大小**不變性，不是 prompt 分布不變性。
