pre-commit 檢查怎麼跑

scripts/check_build_tracked.sh 與 .git/hooks/pre-commit 使用說明 · 2026-09-16 · 分支 demo/sweet-spot-windows-fix
適用對象：拿到這顆 hook（或拿到一份乾淨 clone）的人，要知道它怎麼裝、怎麼手動跑、 哪些檢查預設不會跑、以及一個會讓你白裝的 worktree 陷阱。

先講最容易被忽略的一點：hook 檔案本身不在版控裡。 .git/hooks/ 從來不進 git。git clone 之後 沒有任何 hook 會自動跑——不管 clone 幾次都一樣。真正被版控的只有檢查本體 scripts/check_build_tracked.sh。所以要嘛手動跑它，要嘛用它的 --install-hook 把 hook 生出來。

1. 這顆 hook 是什麼：只是一個 6 行的轉發器

hook 自己不檢查任何東西，它只把工作轉給版控內的腳本。經 2026-09-16 修復後， --install-hook 產生的內容長這樣（703 bytes）：

#!/bin/bash
# generated by check_build_tracked.sh --install-hook (2026-09-16 00:56)
# 落點是 git 真正會讀的 hooks 目錄（common dir）⇒ 同一 repo 的所有 worktree 共用這一顆。
# 因此 REPO_ROOT 必須在「執行時」解析、不能寫死安裝當下的那一個：否則從別的 worktree
# commit 時會去驗錯的 repo（偽 PASS），這正是本檔案之前落到死路徑的原因之一。
# 每次 commit 前驗證 build/bin 的 dylib 與 rpath 都被 git 追蹤 + main⊆dev 包含性
set -euo pipefail
export BIN_DIR='src/llama.cpp/build/bin'
REPO_ROOT="$(git rev-parse --show-toplevel 2>/dev/null)"
exec "$REPO_ROOT/scripts/check_build_tracked.sh" --repo "$REPO_ROOT"

兩個值得注意的細節：

  • 它在執行時用 git rev-parse --show-toplevel 解析 repo，所以同一顆 hook 可以被多個 worktree 共用。這在修復後是必要條件而非選項：hook 落在 common 目錄， 若把安裝當下的 repo 寫死，從別的 worktree commit 就會去驗錯的 repo（偽 PASS）。
  • BIN_DIR 保持相對於 repo（src/llama.cpp/build/bin）， 腳本再自己接上 $REPO_ROOT，所以它同樣跟著 worktree 走。 不給參數時的預設是 build/bin；要對齊生產用 --install-hook src/llama.cpp/build/bin。

2. 裝上去（三種跑法）

情境指令結果
每次 commit 自動跑
推薦		 scripts/check_build_tracked.sh --install-hook 寫出 $GIT_DIR/hooks/pre-commit 並 chmod +x。之後 git commit 自動觸發。
指定 build 路徑安裝 scripts/check_build_tracked.sh --install-hook src/llama.cpp/build/bin 同上，但把 BIN_DIR 烘焙成指定值（hook 內 export BIN_DIR=…）。
不想裝、只想驗一次 RUN_REPLAY_BENCH=0 bash scripts/check_build_tracked.sh --repo "$PWD" 直接跑全部檢查。這就是專案慣例用的那一行。
快速診斷 rpath scripts/check_build_tracked.sh --list-rpaths 只列出關鍵 exe 的 @rpath，不跑其他檢查（otool 層級的排錯用）。

✅ 已修復（2026-09-16）：--install-hook 現在寫到 git 真的會讀的 hooks 目錄， 且蓋掉活 hook 前會自動留一份 .bak。

原本第 98 行用 --absolute-git-dir，在 linked worktree 裡給的是 worktree 私有目錄（<common>/.git/worktrees/<name>）， 而 git 找 hook 用的是 common 目錄。兩條路不一樣，所以 hook 是死的， 卻照樣印「已安裝 pre-commit hook: …」。

修的時候有個更深的陷阱：照字面改成 --git-path hooks 並不夠。 --git-path 在主 worktree 下會回相對路徑 .git/hooks， 而那個相對基準是 git 的 cwd（＝ $REPO_ROOT），不是這支 script 自己的 cwd。 沒錨定就直接寫 $HOOK_DIR/pre-commit，會落到 shell 當下的 <linked-worktree>/.git/hooks——而在 linked worktree 裡 .git 是檔案， 於是 mkdir／cat／chmod 全部失敗，腳本仍然印成功。 那比原來的 bug 更糟：從「寫到錯的目錄」變成「什麼都沒寫還說裝好了」。實測為 ls: …/.git/hooks: Not a directory。

修法：把 --git-path hooks 的結果錨定成絕對路徑（相對就接上 $REPO_ROOT/）， 並把產生的 hook 本體改成在執行時解析 REPO_ROOT。後者是必要的，不是順手： 落點在 common 目錄 ⇒ 全部 worktree 共用同一顆，若把安裝當下的 repo 寫死，從別的 worktree commit 時會去驗錯的 repo（偽 PASS），而那正是守護 dylib 追蹤的那道閘門。

用途這個 checkout 上的實際路徑
修復前會寫到（git 不讀） <…>/flashkv0516/.git/worktrees/flashkv-devserver/hooks/pre-commit
現在寫到（＝ git 會讀） <…>/flashkv0516/.git/hooks/pre-commit

附帶收穫——死雙胞胎偵測。安裝時若發現 git 不讀的私有 hooks 目錄裡還躺著 pre-commit，會跳一行 WARN。這正是 2026-09-09 那次事故的形狀：當時留在那裡的那顆 指向 scripts/check/precommit_e2e_gate.sh，意思是那次想切到 E2E gate 的意圖 靜默失效了 7 天，commit 一直走舊的 2026-09-04 那顆。

若手上是尚未修復的版本，以下兩個繞法仍然有效：

  • 在主 worktree（/Users/alexchuang/Documents/flashkv0516）裡跑 --install-hook。hook 放在 common 目錄 ⇒ 該 repo 的所有 worktree 共用同一顆。
  • 先產生再手動搬到對的位置： 
    scripts/check_build_tracked.sh --install-hook <BIN_DIR>    # 產生（可能生到錯的位置）
mv "$(git rev-parse --absolute-git-dir)/hooks/pre-commit" \
   "$(git rev-parse --git-path hooks)/pre-commit"           # 搬到 git 會讀的位置
test -x "$(git rev-parse --git-path hooks)/pre-commit" && echo ACTIVE

3. 11 項檢查在做什麼，以及哪些預設不會跑

檢查分兩類：靜態的（看 git 追蹤狀態、看原始碼字串）與重型的 （真的啟動模型）。重型那幾項預設關閉——所以「hook 通過」的精確意思是 「上面幾項通過、下面幾項沒被要求」。

編號檢查開關 / 預設狀態
1build/bin 內每個 *.dylib 都必須被 git 追蹤
背景：/build* 曾被 .gitignore 一刀切，版本化 dylib 一重建就永久遺失		 預設開
2必要 dylib 前綴（libllama. libllama-common. libmtmd. libggml.）至少各有一個已追蹤檔案 REQUIRED_DYLIB
3symlink（如 libllama.0.dylib）必須解析到已追蹤的目標 預設開
4關鍵 exe 存在且被追蹤（llama-simple llama-speculative-simple llama-bench） REQUIRED_EXES
5關鍵 exe 的 @rpath 必須指向本 repo 自己的 build/bin
背景：疏失 D——rpath 被改到別的 build 目錄，production 載入錯 dylib		 非 dev 分支時 SKIP
6main⊆dev 分支包含性：在 dev 上 commit 時，本地 main 必須已是 HEAD 的祖先 預設開
7a-7dCGC 專家快取死鎖防護（靜態原始碼檢查）：pick_slot 用精確 batch_mask、 batch_owned mask 在位、掛死看門狗在位、裸 bg_cv.wait 數 ≤ in_flight 守衛數 預設開
8原始碼 ↔ build 產物同步：改了 llama 原始碼就必須一起 staged 重建後的產物， 且 binary 不得比 staged 原始碼舊 ALLOW_STALE_BIN=1
ALLOW_ENV_GATED_BIN=1
9重型：生產驗收（短/長 prompt 無 0000 退化 + t/s 門檻） 預設關
RUN_CGC_PROD_ACCEPT=1
10重型：deploy-harmonyos macOS bundle 可重建 / 可啟動 預設關
RUN_DEPLOY_HARMONYOS_ACCEPT=1
11重型：replay benchmark regression（qa-zh / longform-zh / coding 三 profile × 4 指標，與 HEAD 的 .replay_bench_baseline.json 比）。 只對「代碼 commit」觸發，純文件 commit 不跑 需開著的 server
RUN_REPLAY_BENCH=0 可關

第 11 項為什麼要 RUN_REPLAY_BENCH=0：它需要一個正在跑的 llama-server（找不到 PID 就 FAIL）。專案慣例因此在提交指令前面掛這個環境變數：

RUN_REPLAY_BENCH=0 git commit -F Backup/cgc_logs/commit_msg_xxx.txt

注意：它是前置在指令上的環境變數，不會跨指令保留。上一條指令設過、 這條沒設，這條就是預設值（=跑）。

4. 逃生口（跳過檢查）與它們各自放棄了什麼

全部都是「前置環境變數」形式。用之前先確定你放棄的是哪一項——這些開關不會留痕， 下一個人從 log 看不出來你跳過了什麼。

變數跳過什麼什麼時候合理
RUN_REPLAY_BENCH=0第 11 項（replay benchmark） 沒有跑著的 server；或本輪沒有要驗效能回歸
ALLOW_REPLAY_BENCH_BASELINE=1第 11 項在 HEAD 沒有 baseline 時改成 SKIP 而非 FAIL bootstrap 階段（還沒建立 baseline）
ALLOW_STALE_BIN=1第 8 項「binary 不得比原始碼舊」 不建議——就是這個洞讓 29.85 t/s 的 build 一度救不回來
ALLOW_ENV_GATED_BIN=1第 8 項在「改了原始碼但 dylib byte-identical」時放行 改的是 env-gated dead code，重建後 dylib 完全相同
ALLOW_MISSING=1build/bin 或檔案不存在時不擋 還在本機建置環境的機器上
CGC_SERVER_PID=…不是跳過，是「告訴第 11 項 server 在哪」 第 11 項要用非預設 port 時

5. 完整可照抄的流程

新機器 / 新 clone

# 1) 先確認這台上有沒有 hook
test -x "$(git rev-parse --git-path hooks/pre-commit)" && echo "已裝" || echo "沒裝，下面裝"

# 2) 裝（在主 worktree 跑；worktree 陷阱見第 2 節）
scripts/check_build_tracked.sh --install-hook

# 3) 不想裝就想先看一遍現況
RUN_REPLAY_BENCH=0 bash scripts/check_build_tracked.sh --repo "$PWD"

提交（專案慣例）

# 檢查本體先單獨跑一次，把 FAIL 看清楚（hook 只給你 exit code 與摘要）
RUN_REPLAY_BENCH=0 bash scripts/check_build_tracked.sh --repo "$PWD"

# 開始提交（hook 會再跑一次，同一組檢查）
RUN_REPLAY_BENCH=0 git commit -F Backup/cgc_logs/commit_msg_xxx.txt

暫時不想要 hook

# 停用（保留檔案，改天再放回來）
mv "$(git rev-parse --git-path hooks/pre-commit)" \
   "$(git rev-parse --git-path hooks/pre-commit).disabled"

# 恢復
mv "$(git rev-parse --git-path hooks/pre-commit).disabled" \
   "$(git rev-parse --git-path hooks/pre-commit)"

一句話帶走：hook 只是轉發器，檢查本體在版控內。 所以永遠有兩條路——裝 hook 讓它自動跑，或 RUN_REPLAY_BENCH=0 bash scripts/check_build_tracked.sh --repo "$PWD" 手動跑。兩條路跑的是同一組 11 項檢查； 差別只在「你有沒有被提醒」。

本文件的兩個實測結論，值得單獨記住：

  • worktree 安裝陷阱（已修，2026-09-16）：--install-hook 曾用 --absolute-git-dir，在 linked worktree 內會寫到 git 不讀的位置， 且印出成功訊息。改成 --git-path hooks 之後還必須錨定—— 它在主 worktree 下回相對路徑，基準是 git 的 cwd 而非 script 的 cwd。 （本 checkout 的 .git 是檔案， 指向 …/flashkv0516/.git/worktrees/flashkv-devserver。）
  • hook 完全不在版控內：clone 的預設狀態是「沒有檢查、而且沒有跡象顯示這件事」。 把「檢查通過」與「檢查沒跑」在終端機上區分開來，是安裝 hook 的主要理由。
