交付 decode 步的被消費映射 churn 是 3.1%，不是 42.4%

事件率（publish-level）與條目率（entry-level）是兩個量，而 S3 的生死被前者的數字判過一次。
日期：2026-09-20 12:1x（+08）　·　作者：線A (ace)　·　 儀器：decode_sweep.py --arms p25-s1-churn（prod25、--n-predict 512、rounds 1） 與 m123_oracle_gate.py（D5）
兄弟檔：docs/S2_CHURN_COUNTER_SEMANTICS_2026-09-20.md（同一條線的上一段，純讀碼）、 docs/S2_IMPLEMENTATION_PLAN_2026-09-20.md

§1　一句話

同一次運行、同一個比較、同一批 ids，兩個儀器給出兩個量：ntok=4 的交付 decode 步上， publish 率是 42.4%（「有多少次發布裡至少一個被消費 id 換了值」），而 條目率是 3.1%（「有多少個被消費 id 換了值」）。被引用去判 S3 生死的是前者。

§2　兩個計數器、一次運行、同一批 ids

逐字原文（同一份 log 的 teardown，兩行相鄰）：

llama_expert_cache: S1 churn by ntok (consumed subset):  ntok=1 0/306=0.0%  ntok=4 1729/4080=42.4%  ntok=8 1863/2079=89.6%
llama_expert_cache: S1 churn by ntok (ENTRY granularity, numerator = consumed ids that moved)  overall 17454/266064=6.6%:  ntok=1 0/2448=0.0%  ntok=4 4090/130560=3.1%  ntok=8 13364/133056=10.0%
ntok是什麼步publish 率（事件）條目率一次「動的發布」平均動幾個
1draft（MTP draft 自己的步）0/306 = 0.0%0/2448 = 0.0%—（完全穩定）
4交付 decode（verify）1729/4080 = 42.4%4090/130560 = 3.1%4090/1729 ≈ 2.37 / 32
8cgc_pool_max_tokens()：chunked-prefill 塊1863/2079 = 89.6%13364/133056 = 10.0%13364/1863 ≈ 7.2 / 64
全部—17454/266064 = 6.6%—

這兩個數是可比對的，而且對得上。publish 側逐字複現了紀錄：本輪 ntok=4 42.4% 對紀錄的 42.3%、ntok=8 89.6% 對紀錄的 89.0%、ntok=1 兩邊都是 0.0%。⇒ 兩次運行是同一個配置的同一個比較，所以條目率那兩欄可以放進同一張表。

§3　為什麼 42.4% 會被讀成「42% 的映射變了」

因為那支計數器每次發布最多只 +1。它比較的是「這一層上一次發布的表」對「這一次發布的表」， 只在這一步被消費的 ids 裡走，而程式把條目數算出來了卻丟掉： 

long long consumed_moved = 0, consumed_total = 0;
for (int64_t j = 0; j < n_tokens * n_expert_used; ++j) {
    const int32_t e = ids[j];
    ...
    consumed_total++;
    if (prev[e] != now[e]) { consumed_moved++; }      // <- 條目級，算出來了
}
if (consumed_total > 0) {
    if (consumed_moved > 0) {
        cache->n_slot_table_consumed_changed++;        // <- 只留布林（每次發布最多 +1）
        ...

⇒ 一次發布裡「32 個中 1 個動了」與「32 個全動了」同形。而同一段程式碼自己寫的判準是 the question is whether it is 0/N or N/N —— 那個問題這支計數器答不了，而 G1.premise_b 的「the consumed mapping moves on 42% of the (step, layer) pairs」 就是把事件率讀成了條目率。

§4　對 S3／S2 的後果

  • 方向不變3.1% ≠ 0 ⇒ 被消費的映射不是常數 ⇒ 表的內容每一步都會動 ⇒ 「發布一次就好」不成立，S3（把 40 段收成 1）的前提仍然倒。
  • 量級 −13×但它的大小第一次有了出處：交付 decode 步上是 3.1%，而 42.4% 是「有多少次發布至少動一個」。
  • 新線索交付 decode 步上，平均每次發布只有 1.00 個被消費 id 換值 （4090/4080），而動的那次平均動 2.37 個（4090/1729，滿額 32）。⇒ 要更新的量是幾個 int， 不是 256 個。這正是 S2 想要的東西的一部分：發布若能做成增量，它就有機會塞進 GPU 忙的窗口 （而 cb 的量也會跟著掉）。

但不要把它讀成「發布可以只寫那幾個 int」。本輪只量到 被消費的條目；整表的變動只在 ntok=8 的圖上看到一次 changed_entries=452（該圖 40 層 × 256 ＝ 10240 條 ⇒ 4.4%）。 交付 decode 圖的整表變動本輪沒有量，而增量發布的成本由整表決定，不由被消費的子集決定。

§6　誠實邊界

  • 一次運行（--rounds 1）、一個 profile（prod25）、一顆 build。publish 側與紀錄相符 是「配置相符」的證據，不是 3.1% 可重複的證據。
  • 42.3% 那份紀錄自己就寫著「這是一次讀數，不是分佈」（同簽名下 37.2%–84.4% 散佈）⇒ 條目率同樣可能散佈，要分佈得跑多次。本檔只給一個點。
  • 本檔沒有量任何速度（t/s）；也沒有量交付 decode 圖的整表變動。
  • 被量到的「動」是發布值的差，不是「消費者讀到不同的 slot」—— 後者還要經過 ZERO-slot 與 clamp 的路徑；而 zero_mapped_selected=0 只保證沒有被 ZERO 映射的選中專家，不保證 發布值與讀值相同。
  • 本改動是 add-only，且只在 CGC_S1_TABLE_CHURN 開啟時執行 ⇒ 未設時一行都不跑（§5 的休眠臂就是它的數值證據）。
