# MTP verify 成本主項：expert traffic 不是主角
`docs/POOL_BUDGET_COST_DECOMP_2026-09-18.md` · 2026-09-18 · 只有既有數據，沒有重跑新實驗

## 0. 一句話結論

把 pool budget 當第二軸之後，**「expert 讀取量」對每步時間的彈性只有 0.10–0.17（有兩格甚至是負的）**；
真正吃掉 verify 成本的是**每一個 draft token 大約 46–59 ms 的固定代價**（baseline 一步才 106–133 ms）。
這**否決了我上一輪（`docs/MTP_VERIFY_OPT_2026-09-18.md`）把 thrash 排在第一位的排序**：
修 residency 最多拿回 ~15% 的 verify 懲罰，不是 1.3–1.9×。

一句話版本：**m ≈ 0.43–0.56 是「每個 draft token 的成本」，不是「每次 expert 權重流送的成本」。**

## 3. 決定性比較：同一個 k，只動 bytes（跨池）

這是 budget 軸存在的唯一理由 —— 它讓 **bytes 在 k 固定的情況下變化**，打破上一輪我自己點出的共線。

| k | bytes 倍率 (4G/8G) | 時間倍率 (4G/8G) | 彈性 = Δln t / Δln b |
|---|---|---|---|
| 0 | **4.68×** | 1.25× | **0.145** |
| 1 | 2.07× | **0.76×** | **−0.382** |
| 3 | 1.46× | 0.87× | **−0.379** |
| 5 | 2.46× | 1.09× | 0.096 |
| 7 | 2.83× | 1.19× | 0.165 |

> 對照：15 格 pooled 的 log-log 彈性是 **0.512** —— 但那個數字把「k 變大」也算進去了，
> 而 k 與 bytes 共線。**跨池、同 k 的 0.10–0.17 才是乾淨的估計。**

k=1 與 k=3 甚至出現負彈性：池子越小、每步讀越多，**反而越快**。這不是因果（見 §5 混淆），
但它足以判定：**bytes 與時間之間不存在接近線性的主導關係。**

## 4. 成本分解：誰解釋了 ms/step

response = `ms/step`，n = 36（每支 run 一筆）：

| 模型 | r² | 係數 |
|---|---|---|
| 只有 `k_eff` | **0.842** | 59.14 ms / draft token |
| 只有 `v_union/call` | 0.821 | 11.85 ms / union member |
| 只有 `bytes` | 0.651 | 2.043 ms / MiB |
| `k_eff` + `bytes` | **0.875** | 45.95 ms/token ＋ 0.693 ms/MiB |
| `k_eff` + `bytes` + drift(第幾支 run) | 0.876 | 47.05 ＋ 0.675 ＋ 0.484 |
| 只有 `k`（配置的窗口） | 0.784 | 38.83 ms / k |

讀法：

1. **`k_eff` 一個變數就吃下 84% 的變異**；bytes 只有 65%。
2. 把 bytes 加進去，R² 只從 0.842 → 0.875，而 **bytes 係數掉了 3 倍**（2.043 → 0.693）
   ⇒ bytes 與 k_eff 大致多餘，剩下的是 `k_eff` 的解釋力。
3. 加了「第幾支 run」的漂移項，係數幾乎不動（r² +0.001）⇒ 結論不是漂移假象。
4. **`k_eff`（實際 draft 出幾個 token）勝過 `k`（配置的窗口）**：0.842 vs 0.784
   ⇒ 成本是跟著「真的多做了幾個 draft token」走，不是跟著視窗大小走。

### 4.1 draft 側本身幾乎不搬專家

同一支 run 的 teardown（`spec_cost_p8gk7_r1_p512_n128_d0.stderr.log`）：

```
MTP fast path: calls=3084 union=71176 cold(ZERO)=0 (0.0%)
  verify: calls=2826 union=69112 cold=0 (0.0%)
  draft:  calls=258  union=2064  cold=0 (0.0%)
```

draft 佔 union 的 **3.0%**、calls 的 9.1%。⇒ **那 46–59 ms/token 不是 draft 自己去抓權重造成的。**

### 4.2 換算成 m

相對各自 k=0 baseline 的超額成本 `cost = ms(k)/ms(0)`，`m = (cost−1)/k_eff`：

| budget | k=1 | k=3 | k=5 | k=7 |
|---|---|---|---|---|
| 8 GiB | 1.508 | 0.850 | 0.520 | 0.548 |
| 6 GiB | 1.106 | 1.042 | 0.646 | 0.661 |
| 4 GiB | 0.519 | 0.455 | 0.411 | 0.488 |

（`k=1` 那格偏高是因為它含一次性的「進/出 spec 模式」開頭成本，不是漸進斜率。）
k≥3 的區間落在 **0.41–0.85**，與上午單軸擬合的 **m = 0.474** 同一量級 —— 兩條獨立路徑對上了。

### 4.3 「修 thrash 能拿回多少」的上界

8 GiB、k=7：baseline 106 ms，實測 375 ms，超額 **+269 ms**。
把超出 baseline 的 bytes（`65.35 − 7.69 = 57.7 MiB`）乘以拟合出的 byte 係數：

```
0.693 ms/MiB × 57.7 MiB ≈ 40 ms     = 超額的 15%
```

用 §3 的乾淨彈性交叉驗算：`8.5^(0.145) = 1.38` ⇒ `106 × 0.38 ≈ 40 ms` —— **同一個數字**。
⇒ **即便把 residency 修到完美，也只能拿回 ~15% 的 verify 懲罰**，剩下的 85% 在「每個 draft token」身上。

## 5. 這批資料的混淆（讀數字前必讀）

| 混淆 | 證據 | 影響 |
|---|---|---|
| **run 順序與 budget 完全混淆** | 每一個 (round, k) 裡的順序一律是 **8 → 6 → 4** | 無法把「池小」與「該回合第幾個跑」分開 |
| **系統性漂移（預熱）** | `ms/step` 對「第幾支 run」斜率 **−1.93 ms/run**；前 12 支中位 **268 ms**、後 12 支 **188 ms**（−30%） | 晚跑的看起來比較快 |
| **但漂移與熱態方向相反** | 熱態分布 NOMINAL 3 / MODERATE 11 / **HEAVY 22**；後段更熱卻更快 | ⇒ 漂移不是熱態，是 page cache / 模型常駐預熱 |
| **同格跨回合離散度很大** | 各格 max/min：1.03–**1.74×** | 絕對 t/s 完全不可引用；只有回合內比值勉強能用 |
| **round 3 被外部殺掉** | log 無錯誤直接斷在 run 中間 | k=3/5/7 只有 2 回合 |
| **明顯離群值** | `p4gk0 r3 = 4.69` vs 同格 7.64 / 7.53 | 該時刻有外部競爭 |

**結論：** 絕對 t/s 一律不可引用（對齊既有約定：只用 llama-bench、兩軸並列、且本輪 HEAVY 佔 22/36）。
本文件引用的都是**回合內比值、跨-同一-k 的 pool 比較、以及計數器**（後兩者是確定的數，不是時間）。

## 6. 由此翻轉的路線排序

上一輪（`MTP_VERIFY_OPT_2026-09-18.md`）的排序建立在「bytes 是主詞」的假設上，現在那個假設被否決：

| 上一輪排序 | 本輪判定 | 理由 |
|---|---|---|
| ① 重跑 pool × verify 矩陣 | **已完成，且把 ① 降級** | 答案是「bytes 彈性 ≤0.17」 |
| ② per-layer 非均勻配額 | **降為次要** | 上限只能拿回 ~15% 的 verify 懲罰 |
| ③ prefetch 開關 A/B | 降為次要（同上理由） | `CGC_NO_PREFETCH=1` 預設、本批全程關閉 |
| ④ batch 修復延伸到 verify | **升到第 1（待定）** | 見下 |
| ⑤ n-gram draft 當診斷 | **升到第 1（並列，零成本）** | 見下 |
| ⑥ 別做 dynamic-k | 維持 | oracle 上界 1.03–1.07× |

### 6.1 新的第 1 名有兩個，都很便宜，先做這兩個再做任何架構的事

**(a) 直接量 p_route —— 程式碼裡已經有探針，零開發**
`llama-context.cpp:5929-5937` + `llama-expert-cache.cpp:1799-1845`：

```sh
CGC_P_ROUTE=1  # 只在 verify 步驟（n_tokens>1）觸發，不需要額外 forward
```

會印 `RSL p_route: steps=… anchor_shrunk=… i=1 X% i=2 …`，`i=j` 就是
**P(top8_{t+j} ⊆ top8_t)** —— 正是我上一輪用 union 斜率反推、只能算不能量的那個量
（`q⁸ = 0.0083`）。跑一支 `--spec-type draft-mtp --spec-draft-n-max 7` 就有答案。

**(b) 用 n-gram draft 把「draft 前向」與「verify 每 token 成本」分開**
本 fork 支援（`common.h:367-386`）：`--spec-type ngram-map-k|ngram-mod|ngram-simple`。

同一個 k（verify 批次大小一樣是 k+1），但**完全沒有 draft 模型前向**：

- m 掉到 ≈0.1 ⇒ 那 46–59 ms 是 draft 前向 ⇒ 該做的是更便宜的 draft；
- m 仍在 ≈0.4 ⇒ 那 46–59 ms 住在 verify 的**每 token 路徑**上 ⇒ 主戰場回到
  「verify 批次 T=k+1 太小、per-token 工作沒有被攤薄」（與 prefill T=512 攤薄 10× 對照）。

### 6.2 對 2× / 3× 的含義

`S = E / (1 + m·k_eff)`，而 m 現在有了機械解釋（每 draft token ~46–59 ms）：

- 今天 `m≈0.474`、`E=1.3–1.9` ⇒ 全部 < 1；
- 只把 byte 那 15% 修掉 ⇒ `m≈0.40`，`k_eff=4.7` 時 `S = 1.88/2.88 = 0.65×`，**仍然虧**；
- 要 2× 需要 `m ≤ 0.21` ⇒ 得把**每個 draft token 的成本砍半以上**，或大幅提高 accept。
- `a → 1` 在 `m=0.474` 下只有 1.85×（k=7）⇒ **accept 單獨救不了，這點沒變。**

## 7. 若要重跑同一個矩陣，先修這三件事

1. **拉丁方輪換池順序**（本輪 8→6→4 永遠同序，順序與 budget 完全混淆）；
2. 工具加 **`--cooldown`**（本輪 HEAVY 22/36），否則絕對值繼續不可引用；
3. **產物要落 `Backup/phase_decomp/`（已被 gitignore），不要只放 `/tmp`**（`/tmp` 會被系統回收，本輪 36 支 run 全程在那裡）。

## 8. 可證偽性

本文任何一條都可以被單一實驗駁倒：

- 若 `CGC_P_ROUTE=1` 量到的 `i=1` 明顯 > 0.5 ⇒ RSL 那條路值得重估（但先重跑 §6 的交換率，因為
  「接受率掉得比成本快」的結論獨立於 p_route）；
- 若 n-gram 讓 m 崩掉 ⇒ §4 的「per-draft-token 固定成本」要改寫成「draft 前向成本」；
- 若有人能在拉丁方設計下量到 pool 對於 **絕對 t/s** 有 >20% 的效果 ⇒ §3 的彈性估計要丟掉（本輪離散度 1.74×
  使這一點不能被排除）。
