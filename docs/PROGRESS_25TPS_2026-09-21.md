# 进展说明：25 tok/s 目标里程碑（2026-09-21 收尾版）

> 给一句话：**25 t/s 这个目标在单流 decode、不碰 G2（不写大融合 kernel）的前提下，今天被实测判死。**
> 现在交付口径实测 **12.57 t/s**，到 25 需要 **+98.9%（×1.99）**；而所有存活杠杆加起来
> **中央情境 ≈ 14–15 t/s**，**P(25) < 3%**。
> 这不是「还没做」，是**做完四格实测之后**的结论——而且其中两格是当天先翻案、再自己撤回的。

---

## 1. 目标的口径先钉死

| 项 | 值 |
|---|---|
| 目标（G7.to） | **decode ≥ 25 t/s**，prefill ≥ 250 t/s |
| 量测口径 | `llama-bench`，`scripts/check/prod_profile.py` 的 `DECODE_SHAPE`，**reps=3**，全程 thermal **NOMINAL** |
| 当前基线（M-now） | **12.57 t/s**（±2.26） |
| prefill 基线 | 292.34（09-18 量测，此后 **三次未重验**） |
| 缺口 | **×1.99（+98.9%）** |

⚠️ 口径纪律：本项目所有比较都建立在「同一 cell、同一 build」上。**跨 cell 相乘会直接得到错的定价**——
这一点今天已经付出过代价（见 §3）。12.57 与 25 必须同口径比，否则整张表没有意义。

## 2. 阶梯账本：25 要靠什么凑出来

把「12.57 → 25」拆成五层，每层今天的实测状态：

| 层 | 内容 | 幅度 | 今天的状态 | 性质 |
|---|---|---:|---|---|
| **L0** | 现在交付 | **12.57** | ✅ 实测 | 基线 |
| **L1** | 算子融合（9-ADD 剩余 ＋ cluster-1） | **+1.33% ⇒ 12.74** | ❌ **结案不做** | 单价已实测，单项 0.76%/0.57% 全低于 3% 门槛 |
| **L2** | K5：elementwise 撑 grid | 原估 **+30～38%** | ❌ **判 0** | 见 §4 |
| **L3** | 把填池 IO 藏到 GPU work 底下 | 原 18.59 t/s（+36.6%） | ❌ **撤回为 0** | 可遮窗口实测 = 0 |
| **L4** | 理论带宽 | ~75 t/s | ❌ 不可及 | 需 6× |

**L0 + L1 = 12.74。** 其余三层全部归零 ⇒ **没有任何一格在供货**。

## 3. 今天做了什么：四格被实测改判（含一次自我撤回）

全程 **0 重建、0 写 C++**，只跑 llama-bench 与读码。

### 3.1 L3 归零（§EN-408）—— 最大的一格死在这里

原本 09-20 的表把 L3 写成「18.59 t/s，已量测」，是往后最大的一格。今天用已有的
`CGC_GPU_NODES_MATRIX` raw（47360 行逐 buffer 的节点区间 + 实测 `dur_ns`）重建 segment 内顺序：

- **5811/5811** 个含 MoE 的 segment，MoE core 就在**第一个** command buffer；MoE 之前的 duration 占比 **p10/med/p90 全 = 0.000**
- 派送器主循环：`hook_seg(i)` 等跑完 → 读 ids → `ensure_batch()` **阻塞** → 才 `submit_seg(i+1)`，而下一段第一个 buffer 立刻要读刚填好的 slots
- 交叉验证（同 run、两个独立仪器）：**`gap` 54.35 ms（GPU 空档）> `cb` 42.04 ms（CPU fill）**

⇒ **issue 与 await 之间没有任何 GPU 工作可垫**。**18.59 是 `step → gpu_sum` 的算术地板，不是可达值。**

### 3.2 背景预取：翻案 → 再自己撤回（§EN-409 → §EN-410）

这是今天最该记的一段，因为它演示了「同一个错误前提能骗两次」：

1. **翻案**：实到冷读吞吐 rand-1 MiB 1.19–1.80 GB/s vs 连续 3 MiB 4.09–4.78 GB/s（差 2.7–4×）
   ⇒ 判定 R=1 预取读的是「更便宜的字节」⇒ IO 时间 −30% ⇒ 预取净亏判决翻案。
2. **钉漏洞**：直读 GGUF 头发现每 expert = **1.0703 MiB，分在 3 支独立张量**（0.3203/0.3203/0.4297）
   ⇒ R=1 得到的是 **3 次各放大 3 倍的读**，**永远没有 3 MiB 读**。我用的探针尺寸两端都不在真实区间。
3. **探针自证伪**：同一 3 MiB/2 绪，背靠背交替得 `pread` 2.36 vs `preadv` 5.46 GB/s（**2.3× 仪器差**）
   ⇒ 12.72 GiB 档放在 16 GB RAM 上，页缓存装得下大半，`F_NOCACHE` 没隔离干净。
4. **撤回**：同仪器内 0.32→1.29 MiB 吞吐持平 ⇒ R=1 时间比 **1.87/2.24/2.62/3.05**（1/2/4/8 绪）
   ⇒ 步级 IO 309–429 ms ≫ GPU 阴影 159.77 ms ⇒ **装不进去**，原「净亏」判决恢复有效。

**绝对 GB/s 数字全部作废**；只保留同仪器内的相对比较。

### 3.3 L1 结案（不做）

复审：ADD 9-链已熔 61.8%，cap7→9 只值 **0.76%**；MUL 白名单 **0.57%**；DIV 全孤立 ⇒ 0。
合计 **1.33% < 3% 门槛** ⇒ 不写融合 kernel。

### 3.4 M-W：唯一还活着的（机制真，但端到端不够）

`LLAMA_EXPERT_CACHE_WORKERS=8 → 2`（经 `CGC_SERVER_WORKERS` 注入），交付 cell、5 个配对、10 臂全部 NOMINAL：

| 指标 | 中位 | 一致性 |
|---|---:|---|
| `pool_wait_us / misses` | **0.902（−9.8%）** | **5/5 配对同向，p = 0.031** |
| t/s | +6.0% | **只有 3/5 同向，幅度不可引用** |

两者分道扬镳的原因：`pool_wait` 只占步时 **≈ 16.7%** ⇒ 端到端 **≈ +1.7%（12.57 → 12.78）**。
信号 1.7% 对上 ±27% 噪音。**可以顺手改（零风险 env），但不要对外宣称收益。**

## 4. 为什么 25 的最后一格（K5）也不供货

原本 L2 是唯一还能把 25 拉回讨论范围的一格（+30～38%）。今天 **0 重建** 就把它量完了：

- 上次误判「必须重建」是因为只看了 `CGC_GRPH_DBG`（进程内只打 6 个图、只印 2 维、5/6 是 prefill）。
  真正的工具是 **`CGC_ELEMW_CENSUS=1`**（配额 3000 行、印 `ne[0..3]` 全四维）⇒ 用 `step=` 当锚点
  切出纯 decode 区间，**30 秒拿到形状**。
- **decode 首次实测形状**：102 个 elementwise dispatch/步；**≤1024 元素占 42.2%**；
  典型 `ne=[1,4,1,1]` ⇒ 4 个元素，**连一个 SIMD group（32 线程）都填不满**。
  ⇒ **(A)「grid 太小」的必要条件成立。**
- **但一个 dispatch ≈ 18–19.5 µs，且几乎全是固定开销**：
  NSM 单节点 buffer（argsort）中位 **18.6 µs**，与 K3 实测边际价 `0.0195% × 100 ms = 19.5 µs`
  **两个独立仪器吻合在 5% 内**。argsort 的工作量只有几个元素 ⇒ 这 18 µs 不是执行时间。

⇒ **撑 grid 只能动执行部分，动不了这 18 µs**。所以「小 op 群占 36.5% ⇒ 能拿回 30–38%」是错的：
那 36.5% 里最大的一块是 dispatch 固定开销。**L2 = 0。**

## 5. P(25) < 3% 是怎么来的

要过 25 需要 **+98.9%**。供给端：

| 来源 | 供给 |
|---|---:|
| L1 融合 | +1.33%（结案不做） |
| L2 K5 | 0（判 0） |
| L3 重叠 | 0（撤回） |
| M-W | +1.7%（机制真、不过门槛） |
| **合计（存活）** | **≈ +3% ⇒ ~12.9** |

⇒ **中央情境 ≈ 14–15 t/s**（把属「推算」、跨线的 S2 那端算进来，且已按乐观打折），
离 25 还差一个 **结构性** 的 ×1.7——**不是调参能补的**。

**要让 25 重新进入讨论范围，只能改变前提**，例如：① 换更大统一内存的机器（resident 全常驻，
`misses → 0`）；② 换更小的模型／更激进的量化；③ 多流/批处理（但那不是同一个交付口径）；
④ 放开 G2 写大融合 kernel（目前是禁区）。这四条没有一条是「继续优化现有引擎」。

## 6. 诚实边界（这份说明哪里不可信）

- **整张表只有一格是量测**（M-now = 12.57）。其余要么已撤回，要么是推算／外推。
- **M-W 的 t/s 幅度不可引用**（±27% 噪音，3/5 同向）；换 cell 后可能归零。
- **M-S2 / M-CB 属另一条线**（线 I），本线没有实测权，只标「需重述」，**没改数字**。
  其中 22.9 那端因今天的结论不可达，19.0 那端才是真上界；`gap ⊆ cb+submit` 的交叉检查以
  10.09 ms 失败 ⇒ 分量相加不闭合 ⇒ **不给数字**。
- **prefill 栏三次未重验**：任何 decode 侧改动落地后，prefill 必须同 commit 重验。
- 今天否证的**不是 S2**（S2 拿的是 wait + host 读 ids，不是 fill 的 IO）——这点最易误读。
