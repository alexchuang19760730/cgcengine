# IO 路徑 A/B：把 09-05 的 27.71 案例搬過來 —— 結論：NOT TESTABLE / NOT CONFIRMED

2026-09-21 00:10–00:20，乾淨窗口（哨兵前 282.27 / 285.49 t/s HEALTHY、thermal NOMINAL）。
工具 `Backup/phase_decomp/io_path_ab.py`（自測 7/7），判準**跑之前**寫死在檔裡。

## 假說（§EN-358）

09-05 量到 27.71 t/s（144 ms/step、3.99 tok/step，4 GiB 池）；今天同形狀 8.36–12.57 t/s。
用 09-15 同日對照表（MTP-on 144/3.99、今天 MTP-off 96/1.00、今天 MTP-on 496/3.21）解出
`F = 79.9 ms/step`、`V = 16.1 ms/token`：**09-05 的 draft token 邊際成本 ≈ 普通 token（m≈0）**，
今天是 63–130 ms（3.9–8.1×）。候選成因是 IO 路徑，不是量化：`reads/token` 13.5 → 95.6 → 475，
且 09-05 的統計行帶 `resident=0.00 MiB`。

## 判準（預寫）

| 判定 | 條件 |
|---|---|
| CONFIRMED | `tps(pool-off) ≥ 18.0` 且 `≥ 1.40 × tps(8 GiB)` |
| NOT CONFIRMED | `tps(pool-off) ≤ 13.0`（落在交付 12.57 的 ±27% 單臂噪音帶內） |
| NOT TESTABLE | 治療臂根本跑不起來（說得出死法） |

⚠️ **判準在跑之前就被改過一次，原因記錄在此**：原本提的決策變數是「`reads/token` 從 ~95 掉回 ~13」。
那是錯的 —— `file_reads`／`pread_usec`／`hits`／`misses` 是**池**的計數器（`llama-expert-cache.cpp`），
而 `llama.cpp:467` 在 `expert_cache_bytes > 0` 才建池，所以 `-expert-cache 0` 時這些計數器
**不存在**（不是讀到 0，是沒有）⇒「reads 掉到 0」是量測假象。決策變數改成**交付 t/s**。

### 死法（兩個 pool-off 臂都一樣）

```
ggml_metal_device_init: recommendedMaxWorkingSetSize  = 11453.25 MB
ggml-metal-context.m:904: CGC-METAL-FAIL: command buffer 8 failed
    (status 5, Insufficient Memory ...00000008:kIOGPUCommandBufferCallbackErrorOutOfMemory)
```

模型 12.72 GiB = 13,026 MB **單獨就超過 GPU 建議工作集 11,453 MB 約 1.5 GB**。
`--load-mode none`（匿名頁）16 s 就死；`mmap`（file-backed、OS 可回收）撐到 108 s 還是死。

## 三個結論

**① 池不是優化，是讓這支模型能跑起來的前提。** 關掉池在 16 GB 上物理不可行 —— 這也解釋了
為什麼 `CGC_SERVER_EXPERT_CACHE_BYTES=0` 在 `run_server.sh` 裡只出現在 OOM-safe（ctx 1024 / ngl 8）
這種縮小形狀的分支，從來沒有在 prod25 的交付形狀下用過。

**② 假說 NOT CONFIRMED：4 GiB 只給 +3.1%，而且小於控制臂自己的場內散布。**
4 GiB/8 GiB = 1.031。同一場內 8 GiB 控制臂自己從 8.36 量到 10.28（+23%）⇒ +3.1% 在噪音裡。
09-05「4 GiB 更快」不重現。

**③ miss 數不是 t/s 的驅動項 —— 這仲裁了上次那個矛盾。**
4 GiB 的 miss 數是 8 GiB 的 **1.91×**（19,447 vs 10,192），其中 capacity miss 是 **3.15×**
（11,372 vs 3,612，佔比 58% vs 35%）—— 池真的餓到了 —— 而 t/s 是 10.60 vs 10.28。
**miss 翻倍、t/s 不動。**

配套：`pread_usec` 4 GiB 是 1143 s、8 GiB 是 464 s（2.5×），而 t/s 一樣 ⇒ `pread_usec` 不是成本代理
（`llama-expert-cache.cpp:2432` 已註明它是 worker thread 的**加總**，不是牆鐘）。

⇒ 上次留下來的矛盾（線 I「miss ≈ step 的 35%、清零值 +54%」vs 池掃描「143→256 slots 只值 ≤+2.5%」）
現在有答案：**後者對。miss 是便宜的／被重疊掉的。**

## 對 25 的影響

上一輪我把「IO 路徑／改 residency」列為第一槓桿（§EN-358）。**撤下。**

- 關池：物理不可行
- 縮池：+3%，噪音內
- 減 miss：miss 翻倍而 t/s 不動 ⇒ 不是驅動項

三條都關掉之後，**25 在「不動模型、不降精度、16 GB」下沒有已知可執行路徑**。
可達區間仍是 **12.5–14**（交付 12.57，本場 8.36–10.28）。

剩下能翻案的只剩兩條，都不是本輪能證的：
1. **09-05 的差異來自模型檔而非池** —— 09-05 是 `Qwen3.6-35B-A3B-UD-IQ3_XXS.gguf`，
   今天是 `Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS-denseIQ4X.gguf`（dense 升 IQ4_XS）。
   27.71 在 09-16 已被標 `auditable=NO`，只能當假說來源。
2. **accept 軸**（佔損失 76%）—— 唯一有直接證據的是
   `CGC_RN_ROUTING=1 + CGC_WCOLD_EN=1` 曾實測 25.9 t/s / 98.7% accept，但 quality 0.3。
   速度路徑存在，擋路的是品質。
