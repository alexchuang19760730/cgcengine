📊 總覽

這份 roadmap 的目標是在 16GB 記憶體的機器上，讓 35B MoE 模型達到 prefill 250+ t/s 和 decode 25+ t/s，同時在每個里程碑都維持 M1/M2/M3 bit-identical。

核心洞察：W3（cap × top_k ≤ usable slots）是總開關，它同時造成 prefill 無法批次、以及 MTP verify 拿不到紅利。所以 M1 是所有事情的依賴來源，其他里程碑都不能繞過它。

依賴與排序

M0 量測 → M1 解耦 ★最關鍵 → M2 Prefill + M3 Decode → M4 MTP
M6 量化（可平行）    M5 Prerouter（可選，最後）

🚪 每個里程碑都必須通過的「不變閘門」

每個里程碑結尾都要重跑，缺一不可：

  1. oracle M1（bit-identical logits）= 100%，且與 M2 分開報告
  2. oracle M2（argmax 一致）= 100%
  3. oracle M3（top-k 集合一致）= 100%
  4. template（closed scaffold）· 5. buffer-nil · 6. preflight（knifeedge_matrix.py --gates-only）
  5. pool-size sweep 4 / 6 / 8 / 10 GiB 全部 M1 = 100%，而參考 oracle 必須用當下的 binary 重生
  6. RSS 必須在 4 / 6 / 8 / 10 GiB 四個 pool 都量，且 slab/scratch 分開報
重要原則：每個里程碑的 M1 失敗都優先於該里程碑的速度數字。這個專案的歷史就是「先有數字、後發現數字是假的」，所以閘門先於產出。
M0 — 先把量測能力建起來
前置 風險：低 投入：1-1.5 天

目標：讓「decode 的 100 ms/token 花在哪」變成一個可回答的問題，並讓 M1/M2 harness 能覆蓋 union > slots 這個目前完全沒有被測到的區域。

工作項

  1. decode 逐層剖面：把 T=1 的 100 ms/token 拆成 dispatch / gather / eval-sync / attention / MoE-math。最終輸出一張「41 層 × 各項 ms」的表。
  2. union-fit 閘門語義變更：現在它是硬性 PASS/FAIL，認證「pool path 不可能被觸發」。解耦之後 union > slots 必須是合法的（走串流），所以改成 union-routable：union ≤ slots 或串流路徑被走過。同時新增一個 union > slots 的 M1/M2 測試案例。
  3. 重生 8 GiB 參考 oracle 並更新 sidecar（commit、cap、模型 sha、source digest）。

離開條件

  • 一張表，各項相加 = 實測的 ms/token（誤差 ±5%）
  • 新增的 union > slots 案例：M1/M2 目前預期是 FAIL，並把失敗的 step/層記錄下來 —— 這是交付物，不是障礙
  • 新參考 oracle 生效，4/6/8 GiB 對它 M1 = 100%
M1 — 解耦 pool 與圖形（W3）★ 最關鍵
風險：高 投入：3-5 天 依賴：M0 數值閘門：已達成（117/117 @ 2/4/6/8/10 GiB）

目標：expert tensor 不再被縮小；pool 變成獨立的 cache buffer，只回答「哪些位元組已經在 RAM」；ubatch 寬度不再由 pool 大小決定。

2026-09-14 實際進度：這個里程碑有一半落地了，而且不是預期的那一半。
✅ 工作項 4（canonical order）證明本來就成立；union > slots 的數值正確性已修（host gather buffer → Metal slab，468 → 0 次 buffer is nil）， 並用 2 GiB 那格拉到 M1/M2/M3 = 117/117，union-routable 也從 FAIL 變成 PASS（mode=gather）。這是 decode 分支。
❌ 工作項 1（loader 全尺寸 expert tensor）與工作項 2（phase split）都還沒動 —— 而 prefill 的 batching 紅利、 以及 M2 頼以成立的整層 slab，都靠那兩項。所以 M1 不能宣告完成；正確的狀態是「數值地基已驗、架構解耦未做」。

工作項

  1. loader：pool 改成獨立配置的 Metal buffer；expert tensor（或它的可用視圖）保持全尺寸 256。
  2. graph 按 phase 分流，在建圖前決定（依 request 的 token 數，不看常駐）：
    • T ≥ T_prefill（先用 512 當起點）→ PREFILL GRAPH：整層 slab，256 experts
    • T ≤ T_decode（16 = floor(slots/top_k) 的上界）→ DECODE GRAPH：compacted gather
  3. cap 不再是從 slots 推導的常數：它退化成「decode graph 的寬度上限」。
  4. canonical gather order：compacted 之後的 expert 按 expert id 排序再進 batched matmul。這是這個新架構唯一的 M1 陷阱——slot index 是 pool 相關的，若累加順序跟著 slot 走，換 pool 大小就會改變舍入，M1 直接垮。
  5. 計數器：resident bytes vs pool capacity、per-layer slots、phase（prefill/decode）每請求各跑幾次。

三個結論，都是可量化的：

  1. head 存活修復有效且必要：Edge0 head 從 router 塌成常數（accept 無從發生）變成 26.81%。mean len 也跟著走（36.67 / 13.33 / 2.67）——兩個獨立指標一致。
  2. accept 是 (base, head) 配對的性質，而且是唯一被證明的版本：graft 用的是 與 nail 完全相同的 head（bc0cfecf… 與 219b27c4… 逐位元組互為同一 head 的 兩份拷貝，§M4 上方已證 rel_l2 = 0.00000），只換了 base，accept 就從 70.39% 掉到 0.61%（115×）。 所以「用官方 head 保證初始 accept」成立的前提是：那顆 head 要配它自己的 base。
  3. M4 的主要離開條件仍未過，但原因不是 accept：Nail 配對的 accept 70.39% ≥ 60% 已過；然而同一 carrier 的 MTP-on 6.74 t/s < MTP-off 8.87 t/s（0.76×）。也就是說在 70% accept 之下， draft＋verify 的固定成本仍然大於收益——這就是 roadmap 說的「MTP 額外成本 84% 在 verify 拿不到批量紅利」。 下一步的槓桿在 verify 批次的成本，不在 accept。
樣本量必須標註：每個 carrier 只有 3 個 prompt、每個 96 tokens、單次執行， 而且是 MTP ON 的 8 GiB pool。decode t/s 的絕對值會隨 page cache 與其他行程變動， 所以我只用它做同一 run 內的 MTP-on/off 比值，不跨 run 比較絕對值。
另外這 26.81% 是尚未實作 M4 工作項 1（拒絕取樣）的數字——也就是說 Edge0 這個配對的 26.81% 是「現行精確相等規則」下的值，還有工作項 1 的空間。
⚠ 一個會讓 accept 量測完全無意義的缺陷（2026-09-14 實測 → 已修）： Edge0-35B-Q4_0-MTP-edge0head.gguf 的 MTP head router （blk.40.ffn_gate_inp.weight，BF16 無損）數值上是死的—— min −3.26e−09 / max +9.31e−10 / std 7.74e−12， 而另外兩個 artifact 都是 std 0.00963、範圍 ±0.14。router 全零 ⇒ 每個 expert 的 logit 相同 ⇒ top-k 退化 ⇒ draft 分佈與 target 無關 ⇒ accept 必然塌成 0。
真因（已修）：那批位元組是 F16，標頭卻宣告 BF16。 把同一批位元組當 F16 解讀：peak 0.167969 / std 0.009695， 與 npz 權威值 rel_l2 = 0.000000、corr = 1.000000—— 也就是說檔案裡的數字是對的，標籤是錯的。因為 BF16 與 F16 都是 16 bit， nbytes 完全相同，所以大小、張量數、偏移、sha256 沒有任何一項看得出來； 唯一的症狀是每個權重被乘上約 2^−26。 修法 fix-encoding：把既有的 F16 值重新編碼成 BF16（round-to-nearest-even）， 就地、同長度寫回（標頭、偏移、檔案長度都不變），APFS clone 備份。 修好後 peak 0.167969、與 npz rel_l2 = 0.000000、 新身分 d29f7e9d…、degenerate = {}、check PASS。
而先前「F16 儲存型別是 0% accept 成因」的假設仍被證偽—— 兩個 Edge0 artifact 的 head 型別表完全相同（BF16=2 F32=7 IQ4_XS=7 Q2_K=2 Q3_K=1 Q4_0=1 Q8_0=1，各 575.8 MiB）； 真因不是「某個張量是 F16」，而是「標頭與位元組不一致」。 反面則是好消息：Edge0-35B-Q4_0-MTP.gguf（Nail head 移植）對 Nail 載體的每一個無損 head 張量 都是 rel_l2 = 0.00000，證明那次移植位元完美——它的 0.81% 純粹是 (base, head) 不匹配。
一則已撤回的誤判：本表初版把 shared_head_norm 的 ~1.0 偏移判成「少了 +1.0 norm shift」， 那是錯的——loader 明文 mtp.norm 不需要 shift（mtp_head_qwen35.py:190）， 那個偏移只是「Edge0 的 head 與 Nail 的 head 不同」。 merge_mtp_head_edge0.py 的註解早就警告過這個陷阱，我重犯了同一個錯。
細節與可重跑的證據：docs/MTP_HEAD_PROVENANCE_GATE_2026-09-14.md。

🔬 M1 實作與量測結果

日期：2026-09-14 · 分支：demo/sweet-spot-windows-fix · 機器：MacBook Air M4 16GB · 模型：Nail-Qwen3.6-35B-A3B-MTP-UD-IQ3_XXS（13.66 GB，混合量化）

結論：M1 的數值閘門已達成。2/4/6/8/10 GiB 全部 M1 = M2 = M3 = 117/117， 其中 2 GiB 是唯一一個 union > slots 的配置（走 compacted gather 路徑）。 也就是說「pool 大小只影響速度、不影響數值」現在有實測支撐，而且參考 oracle 與候選是用同一顆 binary 重生、 cap 兩側都固定 8（cap 會夾 n_batch，不固定就會把「形狀差異」誤讀成「pool 差異」）。

閘門命令（可重現）： --models iq3 --pools 2,4,6,10 --pool-cap 8 --oracle-ref Backup/knifeedge_matrix/oracle_iq3_pool8gb.jsonl --gates-only
--pool-cap 8 是必要的，不是裝飾：--pool-cap auto 的探針目標是「讓最小的 pool 也走 pool path」， 也就是主動把 union > slots 這個 case 挑掉 —— 預設值會讓你得到一个全綠、但從未測到該路徑的結果。

根因：buffer is nil 是兩個獨立的事實疊在一起

  1. gather 路徑把 wt->data 指到 host 的 std::vector。Metal 解析 tensor 的方式是 t->view_src ? view_src->buffer : t->buffer → ggml_metal_buffer_get_id()，純位址區間比對。 host 記憶體不落在任何 Metal buffer 的區間內 → 回報 nil（而不是報錯，這是重點：它不會 abort，它會靜默地讀到 nil）。
  2. 只搬 data 不夠。Metal 用 tensor 自己的 buffer 查找（不是掃全部緩衝區），所以 wt->buffer 必須一起搬； 而 Metal 的區間檢查用 ggml_nbytes(t)，後者隨 ne[2] 縮放，所以 wt->ne[2] = union 也必須一起設 —— 否則 union < capacity 時仍然 nil、union > capacity 時 mul_mat_id 的 ids 會越界。 三個欄位必須同時移動，這是第一次修（只搬 data）留下 468 次 nil 的原因。

修正方式

把 host 的 gather buffer 換成 Metal slab：用expert tensor 自己的 buft 配置（不是裝置預設， 因為 Metal 只在 use_shared_buffers && shared 時給 host-visible storage，否則 CPU 端填寫會寫進虛擬位址）， 固定容量 C = cap × top_k = 64（實測的 union 上限，不是平均 28.7），並以 kind 的最大 stride 定尺寸。

C 必須是常數，不能跟 pool 或觀測到的 union 走。若 slab 容量跟著 pool， 需要多趟的 union 其 pass 邊界也會跟著 pool 移動，每個 token 的 sum 就變成 pool 相關的外層 sum —— 正是這道閘門要抓的失效。也因為 C = 64 且 cap = 8，ceil(64/64) = 1， §3.2 的 pass loop 在 M1 可證明不需要（它是 M2 加寬 ubatch 時才需要）。

2026-09-13「三項早期驗證」的更正

2026-09-13 的早期結論查證結果
測試 1：累加順序按 slot index（pool 相關）→ 換 pool size 會改變舍入順序 → M1 直接垮 → 必須實作 canonical gather order 不成立 順序本來就不是 slot-dependent：4/6/8 GiB 在這次改動之前就已經逐位元組相同（117/117）， 而它們的 slot index 完全不同（143/71/107 格、LRU 命中順序各異）。所以「canonical gather order」不是待辦工作項，而是閘門項 —— 現在用 2 GiB 這個 union > slots 的 cell 釘住它。test_canonical_gather.py 找的是不存在的 CGC_CANONICAL_GATHER_ORDER，那是 scaffold 不是 test。
測試 2：union > slots 會 abort()（distinct experts exceed the usable pool slots） 只在一個分支成立，而且是比較好的那個 那兩個 abort 掛在 if (!in_flight)； 實際走到的分支是靜默算錯：2 GiB 舊行為 = 468 次 buffer is nil、M1 2/42、 第 2 步就分歧（該步 sum −335486.28 vs −519561.70，差 55%）。 比 abort 糟，而且不 grep 日誌看不出來。

為什麼「它會 abort」這句話很危險：如果照這個假設去排程，結論會是「等 M1 把串流路徑寫出來就好了」。 真的事實是現在這條路會回傳錯誤的數值、而且看起來像品質問題——2026-09-13 那次「M1 只有 2/42」被讀成 「pool 太小難免飄」就是這個。所以順序是：先讓寬 union 合法（slab），再收緊閘門。

Slab 幾何（實測，不是估算）

「slab 多大」不是常數，是模型的函數：這顆 GGUF 是混合量化，光是它就 8 個 (kind, stride) 組合 （gate/up 各 iq2_s|iq3_s|q2_K、down 為 iq3_s|iq4_xs）。所以「每 kind 一個固定大小」的估法在數學上就是不可能的。

設計採「每 kind 一個 slab、以該 kind 的最大 stride 定尺寸」——小 stride 的層可以共用為大 stride 配的 slab， 因為 ggml_nbytes = union × 本層 stride ≤ cap × max_stride = 配置大小。這也順帶避開一個真實的 bug： 按 (kind, stride) 逐層重配時，舊 slab 會被 free，而其他層的 wt->buffer 還指在裡面。

這裡要更正兩個數字，而且是兩個方向都錯：原 roadmap 寫的「64 × 1.122 MB ≈ 72 MB/kind、四 kind ≈ 288 MB」偏高約 4 倍， 錯在（a）1.122 MB 是三個投影的總和，不是 per-kind 切片；（b）沒有第 4 個 kind。
但實作留下一筆新的待清：目前 supersede（同 kind 之後出現更大 stride）是再配一塊新的， 舊的要等 context 解構才釋放 → 2 GiB 這個配置實測累計配置 157.5 MiB，而活著的邊界只需 75 MiB。 修法：first-touch 時就用該 kind 的全模型最大 stride 配置，或在 graph-build 的還原路徑釋放（那裡才安全）。

M2 的狀態：未開始，且它的前提還沒成立

M2 的離開條件寫的是「prefill 一次性 materialize 整層 slab」。但整層 slab 這條路徑今天還不存在 —— 本輪的 slab 是 decode 分支的 compacted gather（C = 64），C = 256 的整層版本要接的是 M1 工作項 2 的 phase split。 所以 M2 目前的正確狀態是「擋在 M1 的工作項 1/2 後面」，不是「等排程」。

唯一可以先做、而且現在就能做的一塊是量測：bytes/token、裝置 GB/s、load_wall 的拆解 （它們不需要整層路徑）。預算用實測幾何算：C = 256 的整層 slab 對 Nail 是 4× 的 C=64 值 ≈ 約 300 MiB （gate/up 各 110 MiB、down 136 MiB），double-buffer 後 約 600 MiB —— 在 4 GiB pool 上是 15%。
