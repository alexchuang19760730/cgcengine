1. 目標（逐條）

1.1 M1 — 解耦 pool 與圖 最關鍵

目標：expert tensor 不再被縮小；pool 變成獨立的 cache buffer， 只回答「哪些位元組已經在 RAM」；ubatch 寬度不再由 pool 大小決定。

五個工作項（roadmap §M1）：

  1. loader：pool 改成獨立配置的 Metal buffer；expert tensor（或它的可用視圖）保持全尺寸 256。
  2. graph 按 phase 分流，在建圖前決定（依 request 的 token 數，不看常駐）： T >= T_prefill（先用 512 當起點）→ PREFILL GRAPH：整層 slab、256 experts； T <= T_decode（16 ＝ floor(slots/top_k) 的上界）→ DECODE GRAPH：compacted gather。這一項未實作（src/ 裡沒有 T_prefill／PREFILL_GRAPH／DECODE_GRAPH，實查）。
  3. cap 不再是從 slots 推導的常數：它退化成「decode graph 的寬度上限」。
  4. canonical gather order：compacted 之後的 expert 按 expert id 排序再進 batched matmul。 這是這個新架構唯一的 M1 陷阱 —— slot index 是 pool 相關的，若累加順序跟著 slot 走， 換 pool 大小就會改變舍入，M1 直接垮。👉 已被實驗證明是必要而非審慎，見 §3-⑥； 規格已寫在 docs/M1_WORKITEM4_CANONICAL_GATHER_ORDER_2026-09-17.md。
  5. 計數器：resident bytes vs pool capacity、per-layer slots、phase（prefill／decode）每請求各跑幾次。

1.2 M4 — MTP 拒絕取樣 ＋ verify 真批次

目標：accept 從 19.9% 拉到 60–80%，並讓 verify 真的吃到批量紅利。

工作項：① 拒絕取樣（以 min(1, p_t/p_d) 接受、被拒時從殘差 max(0, p_t − p_d) 重抽）； ② batched-union gather 套進 verify（M1 的副產品）；③ 量 accept、tokens/forward、ms/forward 的三段拆解。

★ 離開條件要改寫。roadmap 寫的是「accept ≥ 60%；MTP-on ≥ MTP-off； M1／M2 = 100% with MTP ON」。

第一條（accept ≥ 60%）今天被證明是錯的判準：2026-09-14 就已量到 70.39%（超過）， 但那個數字屬於被缺陷抬高的家族 —— 修前 verify 批次的 token ≥ 1 是用別的 token 的專家算的， 「accepted」是拿錯分布比出來的。修好之後 accept 下降到 58.25%，而 decode 上升到 12.62。 ⇒ 任何只看 accept 的決策都會留住缺陷、退掉修正。正確的判準是 「MTP-on ≥ MTP-off ＋ M1/M2 = 100% with MTP ON」，而且修前記錄的每一個 accept 數字都屬於那個 regime（含 70.4% 與 roadmap 的 19.9%）。

1.3 M5 — prerouter 只當預取提示 可選 · 期望值低

目標：只做 decode、只做 L+1 的 8 顆、只影響時間 （PREFETCH_ONLY 語義：predictions 永不決定 routing）。量的是 overlap（ms），不是 hit rate。

離開條件：overlap 增益 ≥ 10% 才保留；< 10% 記錄為已排除的死路 並把旗標預設關閉；M1／M2 = 100%。

前置結論（已量測，roadmap 原文）：placement 天花板只 0.2pp （mass coverage 90.3% vs 最佳 90.5%）；start_layer = 7 → owner layers 6..38， 而 churn 最重的是 layer 1／2（distinct 250–253／256） ⇒ 最需要預測的層它沒有 head。 edge0 自己的成績：ON 有 1.5× 但品質 0.3、PREFETCH_ONLY 12/12 bit-identical 但增益未證實、 LRU 64 格／40 層 ＝ 1.6 格/層 → prefill hits=0。

實查：PREFETCH_ONLY 在 src/llama.cpp/src/ 與 scripts/ 底下 0 筆命中 ⇒ 這個機制在本 repo 完全不存在，不是「有旗標但沒開」。

3. 已經付過的學費：不要重新踩的九條

這一節是本文最有價值的一節。「為什麼原本是錯的」比「應該怎麼做」更省時間 —— 以下每一條都是這個 repo 今天或本週真的付過代價的。

  1. top-k 快照不是 nb-aware ⇒ T ≥ 2 的每一步都把 token ≥ 1 路由到 token 0 的專家。 涵蓋所有 prefill chunk 與所有 MTP verify 步，是預設路徑的缺陷（每一臂都中）。 已修（commit 8e9e830e5：row = data + t*nb[1]、第 j 個 id 在 row + j*nb[0]）。 做 M1／M4 時要記得：這是「共用的」路徑，任何在它之上的量測都受它影響。
  2. 修前每一次 M1 通過只證明「不變性」，不證明「正確」。缺陷在共用路徑上 ⇒ 每一臂、每一個池大小都用同一種錯誤方式路由 ⇒ 它們彼此一致。 ROUTING_TRACE §15.2 的原話是 cross-pool invariance (M1/M2) passed while the ids were wrong for all of them。2026-09-14 那個「M1 117/117」屬於這一類：引用時要說 「那些池彼此一致」，永遠不是「那些數字是對的」—— 後者只有對 v6_nbaware 之後的參考才成立。
  3. accept 是被抬高的指標。修前 verify 批次的 token ≥ 1 用別的 token 的專家算 ⇒ 「accepted」是拿錯的分布比出來的，而且它抬高了這個數字。 ⇒ 任何只看 accept 的 M4 決策會留住缺陷、退掉修正（§1.2）。
  4. D5 的 gate 會 self-report 它的可比性 —— 先讀 comparable，再讀 M1／M2／M3。 comparable=False 時那三個 9/9 印著 printed for information, NOT a verdict， 而 gate 會 exit 2（INVALID COMPARISON）而不是 exit 1。 跨配置比較要走「--allow-incomparable 讀差異 → --write-ref 重新基線」的固定順序， 而證據標準是「逐位元相同（md5）」不是「M1 = 9/9」（後者是弱述句）。
  5. DEFAULT_REF 會被重基線漏掉，而後果是「假的紅」。 §13.2 生了 v6 卻沒有移動 DEFAULT_REF ⇒ 所有不帶 --ref 的 gate 都對著一個已被修掉的參考報 M1 5/9 FAIL。已修（現在指 ref_iq3_pool8gb_M2_6144_bitident_v6_nbaware.jsonl，並留 dated 註解說明 這次重基線不是蓋章式——v2→v5 是蓋章，v5→v6 是數字真的動了）。 收尾清單第 4 步（改 DEFAULT_REF ＋ dated 註解）不能跳。
  6. M1 的工作項 4（canonical gather order）是必要的，不是審慎。 rev 探針（CGC_ADD_ORDER=rev）把同一個輸入的 hash 由 2d4e5099 變成 f6718d44 ⇒ 聚合對結合順序敏感。所以按 expert id 排序要先做， 否則工作項 2 做完才發現 M1 垮掉。規格 docs/M1_WORKITEM4_CANONICAL_GATHER_ORDER_2026-09-17.md 還附了一段不需要 GPU 的置換不變性驗證。
  7. 「載入期存活」不是充分條件。同一個 caps 字串：7.97 GiB 的池死在載入 （Killed: 9）；6.56 GiB 的池活過載入、死在第一個請求 （Metal kIOGPUCommandBufferCallbackErrorOutOfMemory，失敗在 MTP draft 圖的配置）。 ⇒ 任何記憶體形狀的驗收都要跑到真實請求，不能只看有沒有載完。
  8. 48 題這種 20–30 分鐘的協定需要「互斥」，單次起跑前檢查不夠。 run_server.sh 有一道強制 preflight（:638-740， [防護 1] 清殘留），會先把任何殘留的 llama-server SIGTERM 掉才起自己的 —— 目的是防「行程疊加」造成的 GPU OOM ret=-3 與 kernel panic。 實測：14:01:53 一個正在跑第 14 題的臂被別條線的 preflight 殺掉，而它的工具只在事後 把結果標成 invalid。⇒ 長跑要事先宣告窗口（§5）。
  9. prefill 的 t/s 是「機器狀態的讀數」，不是產物性質。同一份 binary、同一 A11 指紋、 同一組 [perf]，prefill 可以在 118 與 290 之間移動。閘門是 notifyutil -g com.apple.system.thermalpressurelevel 讀到 0， 但那只是閘門開、不是箱子冷：COLD-STATE 要「距上一臂結束 ≥ 1800 s」， 而 HOT-STATE 的數字依 skill 明文 不可當交付數字引用。 （若 M4／M1 要報 prefill，請走 Backup/run_req2_retest.sh，它把熱讀數寫在報告裡面。）

4. 建議的執行順序

4.1 第一步（可以在不需要 GPU 的情況下開場）：M1 工作項 4

理由：它是唯一被實驗指名為必要的前置（§3-⑥），而它的驗證有一段 不需要 GPU 的置換不變性檢查（規格 §3 的 A 段：「把 (貢獻, 權重) 成對置換 ⇒ 輸出必須逐位元相同」）。 ⇒ 你可以在我佔著機器做 M2 結清的時候，先把這一段做完並留下產物。這是本文最想促成的一次錯開。

4.2 第二步（需要機器、長窗口）：M1 工作項 2

T_prefill 先用 512 當起點；T_decode ＝ floor(slots/top_k) 的上界（16）。 建圖前決定、依 request 的 token 數、不看常駐。同時把 cap 從常數降級成 decode graph 的寬度上限（工作項 3）。

4.3 平行的零 GPU 工作

  • M5 的前置盤點：PREFETCH_ONLY 要從零實作，所以第一次落地就要把 「predictions 永不決定 routing」寫成可機檢的形式（否則它會退化成一個會影響 routing 的旋鈕， 而那種旋鈕的輸出損壞在別處已經踩過）。純讀碼＋設計，不需要 GPU。
  • M4 的 plain_match：先設計「batch verify 與逐 token 解碼的逐值比對」， 再上機器跑。它要回答的是「oracle 綠了，verify 路徑綠了嗎」。
  • 離開條件的重定：把 M1 的「decode 不得退步」與 M4 的「accept ≥ 60%」兩條 改寫成可量測且基準一致的形式（前者要對當天的 8 GiB 格、後者要作廢）。 這是純文字工作，但它是後面所有判決的前提。

4.4 M5 什麼時候做

只有當你在等靜置時間（COLD 要 30 分鐘）或等索引／等閘門的時候才做。 它的預期結果是否定，所以它的價值是「把它從不確定清單裡拿掉」，不是拿效能。

5. 機器窗口協定（共用的只有一顆 GPU）

這一節是硬性的。今天的四次碰撞全部發生在這一節沒寫的時候。

  1. 一次只有一條線持有 8080。起 server 前的檢查必須與起 server 在同一個分支裡， 而且非空就 exit 3（只印出來不算閘門）。要同時看兩件事： ① lsof -nP -iTCP:8080 -sTCP:LISTEN；② 別條線的量測行程。 比對 comm（執行檔 basename），不要用 pgrep -f —— 後者是命令列文字比對，會打到「命令列裡剛好提到那個路徑」的行程（本 repo 有三份獨立實作踩過這件事， 其中一份把計數餵給 memory guard，OTHER_LLAMA_SERVERS > 0 就直接擋掉一整臂）。
  2. 長跑事先宣告。任何 20 分鐘以上的協定（48 題、交錯 A/B、COLD 序列）先在日誌裡寫下 「我要佔 15:37–16:10」，另一條線在那個時段不碰 llama-server（§3-⑧）。
  3. COLD 窗口要保留 30 分鐘。想要交付級的 prefill 數字，就必須放棄中間的其他測量。
  4. 建置是對機器上所有正在跑的實驗的一次寫入。src/llama.cpp/build/bin/* 受版控且跨 session 共用 ⇒ cmake --build 會蓋掉別人正在 map 的 dylib （實測：11:29 蓋掉之後，他們那一輪 A/B 橫跨兩個 build，而本 repo 的所有比較都建立在 「同一個 build」上）。建置前用會 abort 的閘門。
  5. 索引重生只在各自收尾時各做一次，而且順序固定：先 build_memory_index.py、後 index_assets.py。顛倒的簽名是 INDEX.jsonl 的 mtime 漂移（不是 bytes），看到就重跑一次兩條。
