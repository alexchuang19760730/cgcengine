§4 狀態契約：為什麼是檔案，不是協議

§4.1 真正的約束

鴻蒙端與 Windows 端目前不在我們的網路上。這個約束推翻了一種很自然的設計：

不能用的做法：做一個「即時上報協議」，讓每個端點定時 POST 狀態進來。
理由是它只在端點連得上時成立——而那正是唯一不需要它的時候。端點離線時，這個協議 既不報錯也不出聲（它只是沒有流量），於是入口會顯示「沒有資料」，與「端點無事可報」同形。

所以在它真的離線時仍然成立的機制只有一種：store-and-forward —— 端點把狀態寫成檔案，靠既有的通道帶回來。

§4.2 契約的兩個設計選擇

  1. what_ran 不得是空陣列。一輪什麼都沒跑也要寫一句（例如「本輪沒有跑任何東西」）。 空陣列會被讀成「有跑，但沒東西可報」，而那是兩件不同的事。
  2. not_measured 逼你表態。空陣列是一個主張（「這個端點沒有未量的東西」）， 它不能由「使用者忘了填」推得。所以產生器要求二擇一：--not-measured <文字>（可重複） 或 --claim-nothing-unmeasured。兩個都不給 ⇒ 拒跑（rc=2）並印出理由。

§6 複用而不是重造

產品版入口不重新實作任何既有概念，它 import build_portal：

複用了什麼從哪來
動能（carried／replaced／refuted／orphan／pending）與它的紅綠判定build_portal.momentum_rows()／momentum_summary()
目標與綁定（targets.json）build_portal.load_targets()
轉義與自由文字（hesc／mdx）build_portal.hesc()／mdx()
契約規則（必填欄位、id 字元集、時間格式）report_endpoint_status.validate_record() —— 產生器與入口共用同一支
fixture 機制（PA_PORTAL_REPO）build_portal.REPO 的環境變數約定
為什麼這個複用是關鍵而不是方便：門檻一旦有兩份實作，就會漂移 —— 而本輪就真的差點這樣 （見 §7.1：我自己重算門檻，算出來的紅綠與 momentum_summary 相反）。 現在比率與紅綠一律只有一份實作，本入口只把比例轉成人看的百分比。

§7 本輪自己踩到的四個缺陷

這一節是這份文件最有用的部分：四個都是「檢查器抓到／我抓到」的真缺陷，而且症狀都長得像別的東西。

§7.1 門檻的單位差 100 倍（紅綠會反過來）

targets.json 的 momentum.declared_red 用的是 refuted_rate_gt: 0.25／orphan_rate_gt: 0.5 —— 比例，不是百分點。 我第一版自己去讀 refuted_rate／orphan_rate 這兩個不存在的鍵、 預設 25／50，於是顯示的門檻差 100 倍，而且 red 的判定會反過來。 修法：比率與紅綠一律取自 momentum_summary()，本入口只做比例 → 百分比的呈現。 守衛：自測第 16 格（宣告 0.5 ⇒ 顯示必須是 50.00% 而不是 0.50%，且判定為「動能不足」）。

§7.2 <date> 沒轉義：先以「表格欄數不對稱」出現

來源說明文字裡有 .workbuddy/memory/<date>.md。那段文字沒有 hesc()， 於是 <date> 被瀏覽器當成一個標籤吃掉，並讓後面所有 </td></tr> 全部錯位。 我先看到的症狀是「表格的欄數不對稱」，那是症狀不是原因。 修法：所有來自註冊表的文字一律 mdx(hesc(...))。 守衛：自測第 17 格（頁面必須含 &lt;date&gt; 且不含裸 <date>）。

§7.3 import html.parser 把參數 html 覆蓋成模組

在 verify_output(html) 裡面寫 import html.parser，會讓參數 html 變成模組，於是 feed(html) 餵進去的是模組 ⇒ TypeError: can only concatenate str (not "module") to str。 自測當場抓到（四格同時失敗）。修法：用別名 import html.parser as _hp。

§7.4 commit message 的 markdown 漏成殘留（我一度以為是「間歇性」）

頁面把 git subject 用 hesc() 渲染（只轉義、沒走 mdx）。而當時 HEAD 的 subject 是：

feat(node-names) + docs: `node` 再拆一層、pool6 裁決（不是記憶體壓力）、S1 上生產判決（解不開 n_segs）

於是產物自我檢查回報 markdown 殘留：'`node`' 並拒絕寫檔。 我當時把另一條線的下一個 commit（subject 不含反引號）當成「重現不出來」—— 其實它完全可重現， 條件只是「HEAD 的 subject 含反引號」。 修法：subject 走 mdx(hesc(...))。守衛：自測第 18 格（fixture 裡真的做一個含 `node` 與粗體的 commit）。

這一輪的另一個模式：我的「測試期望值」寫錯了兩次。 一次是把 append 語意的 --what-ran 當成覆蓋（期望 ["第二次"]，實際是累積）； 一次是把 pct() 的輸出 50.00% 寫成 50%。 兩次都是斷言錯、程式對。判準：自測失敗時，先問「是斷言寫錯還是程式錯」， 不要直接改程式去迎合斷言。

§9 誠實邊界：這一頁不主張什麼

  • 不主張四個端點「能力如何」。鴻蒙端與 Windows 端的每一條能力都來自 repo 裡的建置腳本， 不是實測 —— 那證明的是「我們寫了給它的建置流程」，不是「它跑得動」。兩端的 not_measured 就是這件事的逐條記錄。
  • 不主張心跳失敗等於端點壞了。本輪 mac-local 的心跳是 Connection refused、 cloud-host2 是 timed out —— 兩者都寫成 unknown。連不上只說明「現在不知道」。
  • 不主張 40–60 t/s 是實測值。那是 deploy-harmonyos/windows/README.md:49 的預期表， 本入口把它標成預期，不標成能力實績。
  • 不主張七日趨勢完整。六個來源的覆蓋是 7/7、4/7、4/7、4/7、1/7、1/7 —— 表上逐列印著。 入口自己的 history.jsonl 只有今天 43 分鐘的 15 筆。
  • 不主張門檻是定律。refuted_rate_gt: 0.25／orphan_rate_gt: 0.5 是 宣告的判準，可以被重新訴訟；且 orphan 不等於壞決策（它也可能是診斷的終點）。
  • 未跑的：沒有跑 D5 的數值那一半（本 commit 無 src/ 變更、建置產物沒動）； 沒有實際把任何端點接上（三個端點本來就離線）；auto_git_push.ps1 沒有實跑過。

§11 --export：給別的網站吃的那份契約

修訂紀錄：§1–§10 寫於 2026-09-18 13:30；§11 於同日 13:5x 追加 （同一個問題的下一段 ⇒ 就地追加，不另開新檔）。原文一字未刪。

§11.1 為什麼要匯出，而不是讓網站自己算

下游是 powerauto.ai 的 portal：super user 登入後要看到「端側 AI 的 prefill／decode 目標」 與「本機／跨機的資產能力進度復盤」。那些數字——動能、七日回填、目標綁定——只有在這個 repo 算得出來。

不能用的做法：在網站端重算一次。兩份實作必然漂移，而漂移是靜默的 —— 網站會忠實地顯示一組與這裡不同、且看起來一樣合理的數字。

所以網站端只吃匯出：

python3 agent_harness/portal/build_fleet_portal.py --export
  -> docs/fleet_export.json   （schema 1，約 9,950 B）

§11.2 匯出的形狀（schema = 1）

鍵內容來源（唯一真相）
sourcerepo／HEAD／branch／產生者／重跑指令本入口自己
endpoints四端的 id／平台／能力清單／未量測／狀態 chipfleet.json

把 honesty 放進資料裡（而不是只放進文件）是刻意的：下游渲染時拿得到那三句話， 所以不必重新推導一次「什麼算未知」。

§11.3 匯出沿用入口的三條規矩

  • 不假裝：心跳失敗與未上報都是 unknown／未上報，不是失敗。匯出照傳，不改成 false。
  • 缺席要出聲：每個端點的 not_measured 原樣帶出去 —— 下游看得到「我們不知道什麼」。
  • 無記錄 ≠ 0：缺日的格是 null（下游要顯示「無記錄」），不是 0。

§11.5 這一段的誠實邊界

  • --export 不寫 fleet_status.jsonl：那是「觀測」（只追加的趨勢），匯出是「轉述」。 兩者混在一起會讓趨勢檔摻進一堆重複的匯出紀錄。
