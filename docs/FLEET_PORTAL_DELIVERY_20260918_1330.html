§4 狀態契約：為什麼是檔案，不是協議

§4.1 真正的約束

鴻蒙端與 Windows 端目前不在我們的網路上。這個約束推翻了一種很自然的設計：

不能用的做法：做一個「即時上報協議」，讓每個端點定時 POST 狀態進來。
理由是它只在端點連得上時成立——而那正是唯一不需要它的時候。端點離線時，這個協議 既不報錯也不出聲（它只是沒有流量），於是入口會顯示「沒有資料」，與「端點無事可報」同形。

所以在它真的離線時仍然成立的機制只有一種：store-and-forward —— 端點把狀態寫成檔案，靠既有的通道帶回來。

§4.2 契約的兩個設計選擇

  1. what_ran 不得是空陣列。一輪什麼都沒跑也要寫一句（例如「本輪沒有跑任何東西」）。 空陣列會被讀成「有跑，但沒東西可報」，而那是兩件不同的事。
  2. not_measured 逼你表態。空陣列是一個主張（「這個端點沒有未量的東西」）， 它不能由「使用者忘了填」推得。所以產生器要求二擇一：--not-measured <文字>（可重複） 或 --claim-nothing-unmeasured。兩個都不給 ⇒ 拒跑（rc=2）並印出理由。

§7 本輪自己踩到的四個缺陷

這一節是這份文件最有用的部分：四個都是「檢查器抓到／我抓到」的真缺陷，而且症狀都長得像別的東西。

§7.1 門檻的單位差 100 倍（紅綠會反過來）

targets.json 的 momentum.declared_red 用的是 refuted_rate_gt: 0.25／orphan_rate_gt: 0.5 —— 比例，不是百分點。 我第一版自己去讀 refuted_rate／orphan_rate 這兩個不存在的鍵、 預設 25／50，於是顯示的門檻差 100 倍，而且 red 的判定會反過來。 修法：比率與紅綠一律取自 momentum_summary()，本入口只做比例 → 百分比的呈現。 守衛：自測第 16 格（宣告 0.5 ⇒ 顯示必須是 50.00% 而不是 0.50%，且判定為「動能不足」）。

§7.2 <date> 沒轉義：先以「表格欄數不對稱」出現

來源說明文字裡有 .workbuddy/memory/<date>.md。那段文字沒有 hesc()， 於是 <date> 被瀏覽器當成一個標籤吃掉，並讓後面所有 </td></tr> 全部錯位。 我先看到的症狀是「表格的欄數不對稱」，那是症狀不是原因。 修法：所有來自註冊表的文字一律 mdx(hesc(...))。 守衛：自測第 17 格（頁面必須含 &lt;date&gt; 且不含裸 <date>）。

§7.3 import html.parser 把參數 html 覆蓋成模組

在 verify_output(html) 裡面寫 import html.parser，會讓參數 html 變成模組，於是 feed(html) 餵進去的是模組 ⇒ TypeError: can only concatenate str (not "module") to str。 自測當場抓到（四格同時失敗）。修法：用別名 import html.parser as _hp。

§7.4 commit message 的 markdown 漏成殘留（我一度以為是「間歇性」）

頁面把 git subject 用 hesc() 渲染（只轉義、沒走 mdx）。而當時 HEAD 的 subject 是：

feat(node-names) + docs: `node` 再拆一層、pool6 裁決（不是記憶體壓力）、S1 上生產判決（解不開 n_segs）

於是產物自我檢查回報 markdown 殘留：'`node`' 並拒絕寫檔。 我當時把另一條線的下一個 commit（subject 不含反引號）當成「重現不出來」—— 其實它完全可重現， 條件只是「HEAD 的 subject 含反引號」。 修法：subject 走 mdx(hesc(...))。守衛：自測第 18 格（fixture 裡真的做一個含 `node` 與粗體的 commit）。

這一輪的另一個模式：我的「測試期望值」寫錯了兩次。 一次是把 append 語意的 --what-ran 當成覆蓋（期望 ["第二次"]，實際是累積）； 一次是把 pct() 的輸出 50.00% 寫成 50%。 兩次都是斷言錯、程式對。判準：自測失敗時，先問「是斷言寫錯還是程式錯」， 不要直接改程式去迎合斷言。

§9 誠實邊界：這一頁不主張什麼

  • 不主張四個端點「能力如何」。鴻蒙端與 Windows 端的每一條能力都來自 repo 裡的建置腳本， 不是實測 —— 那證明的是「我們寫了給它的建置流程」，不是「它跑得動」。兩端的 not_measured 就是這件事的逐條記錄。
  • 不主張心跳失敗等於端點壞了。本輪 mac-local 的心跳是 Connection refused、 cloud-host2 是 timed out —— 兩者都寫成 unknown。連不上只說明「現在不知道」。
  • 不主張 40–60 t/s 是實測值。那是 deploy-harmonyos/windows/README.md:49 的預期表， 本入口把它標成預期，不標成能力實績。

§13.4 ★ 一個會讓整合靜默失效的環境變數：HTTP_PROXY

環境裡若有 HTTP_PROXY=http://127.0.0.1:7897（本機實測就是）， urllib 會把 http://192.168.101.90:… 也丟進代理 ⇒ 去連我們自己的區網入口靜默失敗 —— 而失敗長得像「端點沒在跑」。

負向對照（測 LAN 位址 192.168.101.90，不是 127.0.0.1 —— 後者常被系統 no_proxy 放行）：
  urllib.urlopen（吃 HTTP_PROXY）            → 失敗（URLError）
  build_opener(ProxyHandler({}))（繞代理）    → 通

所以 URL 來源一律走 ProxyHandler({})，並加一格自測把 HTTP_PROXY 設成壞位址、斷言結果仍然正確。這一格是有辨別力的（上面那組負向對照就是證據）。

§13.5 ★ 另一件差點被靜默吞掉的事：host 缺 platform／arch

§14.1 端點那一步：edge_server.py --dump-status

離線端（鴻蒙／Windows）不在我們的網路上，所以我們沒辦法去抓它們的 /v1/edge/status。但它們能寫一份檔。新增的這條指令就是那一步：

python3 installer/edge_server.py --dump-status status.json --endpoint-id windows-rtx4090

產出的 schema 與 /v1/edge/status 完全相同（所以 harness 那側 --from-edge-status 吃檔案與吃 URL 是同一條路），只多一格 dump。 三個設計決定值得記下來：

  • 不起服務、不開埠、不需要模型、不需要 llama-server。 這個分支刻意被放在 模型檢查與 llama-server 解析之前。理由不是省事：離線端要的是一條 一定跑得完的指令，任何一個前置檢查都會讓它在目標機器上跑不動 —— 而跑不動的指令等於沒有這條路。
  • dump 那一格是語意標記，不是裝飾。 實測輸出裡 uptime_s 是 0.0、served 全是 0 —— 那是 這個 dump 行程自己的讀數（它剛被啟動），不是一個長期服務的統計。 不標這一格，下游會把「剛 dump 所以 uptime≈0」讀成「服務剛重啟」。
  • 沒給 --endpoint-id 會出聲（那時這份 dump 不知道屬於誰， 自動鏈會拒收）。

放的位置也有講究：agent_harness/portal/endpoints/dumps/<id>.json， 不是 endpoints/ 本身。原因是 §14.6 記的那個誤導症狀。

§14.3 三條硬規矩（第①條是這一輪挖出來的既有缺陷）

① 不偽造新鮮度 —— 這一條修的是 §13 留下的東西。
report_endpoint_status.py --from-edge-status 原本把 reported_at 取成 映射發生的時刻。手動跑時這個錯看不出來（人會看時間）；自動化會把它每小時抹平一次： 一個離線三天的端點，dump 今天才被通道帶回來，頁面上會顯示「它剛剛上報」。
現在 reported_at 取 edge 自己的觀測時刻，處理時刻另記在 mapped_at。兩個時刻都留著，不合併成一個。

② 同一份觀測只處理一次。 冪等判準就是 reported_at。沒有新觀測 ⇒ 不重寫檔案 （自測驗的是 mtime 不變，不是「內容一樣」），也不重生 fleet_export.json —— 否則 git 每天多出一堆只有時間戳不同的 diff，而「上次真的有變化是什麼時候」就看不見了。 匯出仍會在跨日時跑一次（七日趨勢與動能有機會變）。

③ 覆蓋時要保住人的工作 —— 這一條是實測踩出來的損失，不是預防性設計。
第一次端到端實跑，一台剛用 --no-worker 起來的 edge_server 覆蓋了 mac-local.json：它從「3 條能力 ＋ 3 個實測 metrics ＋ 3 條未量測 ＋ GPU 型號」 變成「uptime 2.6s、服務 0 次」—— 用零換掉實質。
現在覆蓋前會把只有人知道的東西接過來（what_ran／capabilities／ not_measured／gpu／build_profile／metrics）。 切分線是報告裡的 edge_derived（映射層寫下的邊界：前 N 條是 edge 導出的）； 沒有那一格 ⇒ 整份都算人工的。少了這條界線，自動化只有兩種下場： 把人的工作洗掉，或每跑一次讓報告長一截。

§14.7 這一節不主張什麼

  • 它不是「全自動」。 端點上的 dump（①）與通道（②）仍然要人／既有腳本。 absent 是最常見的結果之一，而它不是失敗。
  • 它不 commit。 只寫檔。這個 repo 有多條線同時在寫，自動 commit 會踩到別人的線。
  • 本機端點只在 edge_server 跑著時才有觀測。 服務沒跑 ⇒ absent。 這一輪沒有做「讓本機端點一直有資料」——那需要讓服務常駐，是另一個決定。
  • 排程只在 macOS 上裝了。 非 macOS 會印出 cron 行而不裝： 在別人的機器上偷偷多一條 cron，比不裝更糟。
  • 留痕與日誌會一直長大（auto_runs.jsonl 每輪一行、 launchd 的 log 是 append 無輪轉）。超過 2 MB 時 --run 會印一行提示， 但不自動刪 —— 自動刪歷史是危險動作，而「沒人記得它已經 4 MB」才是真正的問題。
  • 通道的對齊問題沒有被這一輪解決：auto_git_push.ps1 推的是 fusionroutemot，入口讀的是 demo/sweet-spot-windows-fix（§4）。 Windows 端的 dump 就算產出來了，在兩邊對齊之前仍然到不了入口。

§15 A2A 閘道：把 harness 與 pd 服務暴露成 agent，並讓「類別」在協議上可機檢（16:2x）

本節是新增，不取代前面任何一節。§1–§14 的結論全部仍然成立；§13.7 那句 「gpu 刻意留空」也仍然成立。本節處理的是另一條線的需求： 「agent harness ＋ pd 端雲端端服務要整合在一起」，而且要能區分 agent 屬於哪一類 ——開發（windows／鴻蒙移植）／運營（pd 網站 harness）／探索（宏觀決策）—— 並且把「宏觀決策」與「微觀能力」的分類放進 A2A 協議裡。

§15.1 為什麼是閘道，不是改 pd

動手前量到三件事：pd/ 是 gRPC 的 PD 推論子系統（KV cache ＋ DOPD handoff）， 它沒有任何 HTTP 服務發現層；tb_loop/agents/ 的三個 agent 是 terminal-bench 的執行器適配器（AbstractInstalledAgent）， 沒有「類別」的概念；而 a2a／agent-card／ well-known 在整個 repo 裡一次都沒出現過（命中的全是 terminal-bench 資料集裡的 無關字串）。

所以這一輪是從零加一層，而不是改造既有的：閘道在 harness 側， pd_server.py 一個字都沒動。pd 在這一層裡只是一個 backend —— 它變成 pd-inference 這個 agent 的對外身分。

§15.2 兩個維度：宏觀決策域與微觀能力

類別是什麼宏觀決策域（macro）微觀能力（micro）
developer把引擎移植到新平台並證明它跑起來 porting —— 移植目標與構建策略4 項
operator讓端／雲／端的服務持續可觀測、可部署 fleet-ops —— 機隊部署與可用性4 項
explorer解決宏觀決策：目標還成不成立、哪條路已封閉 decision —— 目標、路線與假設的取捨4 項

兩者刻意分開，而且不可互相推導。一個能跑 cmake 的 agent（micro） 不代表它有權決定「要不要移植到鴻蒙」（macro）。把它們併成一張清單， 下一個讀者就會以為「能執行」等於「有權決定」。

協議上的落點也因此分開：

  • 微觀能力 → A2A 標準的 skills[]（標準客戶端也看得懂）
  • 類別與宏觀決策域 → 擴展欄位 x-agent-class／x-macro-scope
為什麼不把類別也塞進 skills[]：A2A 的 skills[] 語意是 「可呼叫的能力」。把「類別」塞進去，標準客戶端會以為 class:developer 是一個 可以被呼叫的動作 —— 它會去呼叫它，然後失敗。類別與能力是兩個層次， 協議上就該分開。

§15.3 分類的實際作用：路由會因為它拒絕

只把類別寫在卡片上，它是一個標籤。真正讓它是分類的是這條規則 —— 把 explorer 的 skill 送給 developer agent：

code    = -32005
message = skill 'register-decision' 不屬於 developer 這一類（它是 探索 agent）
data    = {"agentClass": "developer", "skillOwnerClass": "explorer",
           "availableSkills": ["build-target", "port-and-verify", …]}

同一個道理另一條：沒指名 skill 也拒收（-32602）。 猜一個預設 skill 會讓打錯字的請求看起來像成功。

而 x-taxonomy.skill_owner（每個 skill 屬於哪一類的正本）就寫在卡片上 —— 對端可以自己核對我們宣稱的分類與能力歸屬一致，不必相信我們。

§15.6 這一輪踩到的兩個缺陷

① 同一個坑第二次：HTTP_PROXY 又把 127.0.0.1 的請求丟進代理。
第一次在 §13 的 report_endpoint_status.py --from-edge-status。這一次更貴， 因為它在產品路徑上：push 的 webhook 投遞用 urlopen，於是 「push 已設定」與「push 送不到」看起來一樣，而錯誤訊息指向代理 —— 下一個人會去查代理，而不是查這裡。修法是把繞代理做成一個共用函式 （_no_proxy_opener()），產品路徑與自測路徑都走它。
② 一個真的死鎖，而它的症狀指向錯的方向。
第一版在 with store.lock: 裡又呼叫了 store.get() （它也要同一把 Lock）⇒ 死鎖。症狀是：那個請求永遠沒有回應， 而且 server log 裡連一行都沒有 —— 因為死在 send_response 之前， 所以 log_request 根本沒被呼叫。從外面看像「連線沒建立」或「代理卡住」， 我當時正是先懷疑代理（見上一條），方向錯了。
修法有兩層：_stream 那處不必要的嵌套拿掉，並且 Store.lock 改用 RLock 當安全網。

§15.7 不主張什麼

  • 不是四個獨立部署。四個 agent 共用同一個閘道進程與同一份 registry —— 協議上是四個身分，部署上是一個服務。
  • pd 的 KV／DOPD 操作沒有全部映射過來。pd-inference 目前的能力是它的 身分，不是它的全部 rpc。說「整合完成」會是假的。
  • push 沒有重試。投遞失敗會留痕但不會重送 —— 重試需要「什麼算送達」的判準， 而那個判準目前不存在。
  • 沒有認證。閘道預設綁 127.0.0.1；要對外得先有 --api-key 這一層， 目前沒有（與 edge_server 的 --api-key 是兩套，未對齊）。
  • executor 是「讓每一格微觀能力真的能跑」而寫的，不是生產實作。 shell-allowlist 只放行白名單命令、不做管線與重導向 —— shell=True 在這個情境等於把閘道變成遠端 shell。
  • portal 的入口頁還沒有畫出 agent 分類。這一輪的接點是 registry.json 的 runs_on 對到 fleet.json 的端點 id （兩個正交的軸：fleet 回答「這台機器上有什麼」，registry 回答「誰在跑」）， 但頁面上還看不到它。

本節的產物：agent_harness/a2a/ 的 taxonomy.py（分類的單一真相）、registry.json、 agent_card.py、a2a_server.py、A2A.md。 所有數字都可在本機用 §15.5 的指令重跑。

§16 身分錨：session 屬於哪一類，以及那一類的四維（16:3x）

本節是新增，不取代前面任何一節。§15 建立了 A2A 閘道與「三類 agent」的分類體系； 本節補上它缺的那一半：一個 session 要怎麼知道自己屬於哪一類， 以及知道之後要整理什麼。需求原話是「每一個 session 的運營者 agent 需要區分這個是屬於哪個類別 然後再來整理對應的資產／能力／進度／復盤」。

「我屬於哪一類」如果靠 session 自己宣稱或靠標題，它就是一個不可機檢的宣稱。 最不會漂移的判準是它用哪一個帳號登入雲側（Supabase profiles）：

§16.4 憑證怎麼放（不要貼進 repo）

identity.py 的原始碼裡沒有任何 key（它連自己都測這一格 —— pattern 是拼出來的，因為寫成字面量會讓掃描命中自己的 pattern）。 憑證只從環境變數或 ~/.config/powerauto/supabase.env（repo 外、chmod 600）讀。

而且它刻意只用 anon key ＋ 使用者自己的 JWT，不用 Service Role Key —— 這樣讀到的就是那條路徑真的讀得到的東西，RLS 在雲側那一頭生效。 把 super key 放進一支「只是要讀四維」的工具裡，是拿最大的權限去做最小的事。

§16.5 不主張什麼

  • 它不驗 JWT 簽章。它只回答「這是誰」；授權是雲側的事（RLS 與 role 在那一頭）。 用未驗簽的 token 判身分，只在「後面還有真正的閘門」時才成立。
  • 已知缺口：docs/fleet_export.json 沒有導出 reaches （portal 的 export_payload() 的缺口），所以 identity.py 得自己回頭讀 fleet.json。一份「給別的網站吃」的資料少了判斷所需的欄位， 每個消費者都要多讀一個檔。
  • 非 macOS／沒有這個 repo 的環境跑不了 —— 它讀的是本機的 fleet_export.json 與 decisions.jsonl。
  • 它沒有「session」這個概念，只有「帳號」。一個帳號在同一時間開兩個 session （一個在做移植、一個在做運營）時，兩者會拿到同一類的四維 —— 要區分到 session 層，得再有 session 級的註冊，目前沒有。

§17 三個帳號同一把密碼，與「不做 session 註冊」的決定（17:0x）

本節是 §16 的直接續，不取代任何一節。§16 建立了身分錨（帳號 → 類別 → 四維）， 但留了兩件事沒收：(a) 開發者與探索者的帳號能不能用； (b) 同一帳號開兩個 session 時，「區分到 session 層」到底要不要做。 本節的結論是 (a) 三個都能登入，(b) 不做 —— 而且要把「為什麼不做」寫成可機檢的宣告，不是留一句口頭約定。

§17.1 「同樣的密碼」不是證據，登入才是

使用者說三個帳號用同一把密碼。這句話很可能是對的，但它是一個宣稱 —— 三個帳號可能根本沒建、密碼不同、或某一個被停用，而這三種情況的處置完全不同 （建帳號／問密碼／查停用）。所以新增 --probe-login：三個帳號各登一次。

它只讀：不建帳號、不改角色 —— 那兩件是寫操作，正是使用者原始文件裡 「驗證 API 是否正常」與「改動生產資料」的分界。實測：

  [OK] developer  developer@powerauto.ai     JWT 802 字
  [OK] operator   alexchuang@powerauto.ai    JWT 976 字
  [OK] explorer   frontier@powerauto.ai      JWT 800 字

三個帳號各有自己的 UUID，且全是 super_admin（與 §16 的實況一致 —— 所以 role 不承擔區分類別的職責，區分只在 email 上）。憑證檔因此改成一類一個帳號： POWERAUTO_EMAIL_OPERATOR／..._DEVELOPER／..._EXPLORER， 密碼共用同一把；命名由 taxonomy.classes() 派生，新增一類時鍵會自動出現。

為什麼是一類一個帳號，而不是一個帳號多個 token：分類的錨是帳號。 共用帳號會讓分類退回「自稱」，而那正是這一支在防的事。

§17.2 決定：不做 session 註冊，改用「出處」歸因

§16 留了一個具名缺口：它沒有 session 概念，只有帳號 —— 同一帳號同時開兩個 session（一個做移植、一個做運營）會拿到同一類的四維。 當時的結論是「要區分到 session 層，得有 session 級註冊」。

使用者的回覆是不需要：看得到同樣的本機檔案與 git 操作即可。 這個判斷成立，而且比「加一層註冊表」更強：

  • 能區分兩個 session 的東西（本機檔案、git 操作）本來就擺在那裡；
  • 而且兩個 session 看到的是同一份 —— 註冊表要多維護一份真相， 而那份真相會漂移（這個 repo 已經為「兩份真相」付過學費）；
  • 真正需要的不是「你是誰」，而是「你讀的是哪一版」—— 那件事出處就答得出來。

所以四維帶上出處，並把「不區分 session」寫成輸出裡的一格：

出處（★ 這不是身分，是歸因）：
    repo    /Users/alexchuang/Documents/flashkv-devserver
    HEAD    demo/sweet-spot-windows-fix 22e7cb9919d3
    最近提交 feat(a2a): 身分錨 --- session 屬於哪一類，以及那一類的資產／能力／進度／復盤
    未提交  8 筆（分不出是誰改的：多 session 共用一棵樹）
    錨文件  7 個讀得到、0 個讀不到
    讀數時刻 2026-09-18 17:07:56
    ★ 同一帳號的多個 session 會判到**同一類**（level=none, byDesign=True）

sessionDiscrimination.level 固定是 "none"， 而自測有一格釘住它 —— 免得之後有人偷偷加回一個註冊表、卻忘了改這個宣告。 「分不出是誰改的」那半句也是刻意的：它把 repo 的既有事實（多 session 共寫一棵樹） 放在讀者眼前，而不是讓那個 dirty 清單看起來像「我改的」。

錨文件是四維的來源清單（taxonomy.py／fleet.json／ decisions.jsonl／fleet_export.json／端側的 edge_server.py）。 缺檔也留在清單裡（標 exists:false）—— 從清單消失會讓 「還沒匯出」與「我忘了檢查」長得一樣。

§17.3 兩個順手挖出的缺陷

① cfg or load_cloud_env() 把「我給了空憑證」換成真憑證。 空 dict 是 falsy，所以一個想離線跑的呼叫端（明確傳 {}）會被靜默 換成真憑證，然後真的連出去。自測第 17 格就是這樣抓到的：它本來要驗 「沒憑證時 login_probe 要說『沒查』」，結果回報 probed=true、三個帳號都登入了 —— 自測想要離線，它卻連了網。修法是 None 判斷： 「我給了空設定」與「我沒給設定」不該同形。

② --check 不帶 --as-class 時傳了空字串。 於是「沒指定」變成「指定了一個不存在的類別」，錯誤訊息印成 「沒有  這一類的帳號（要 POWERAUTO_EMAIL_）」—— 像壞掉，而不像缺設定。 缺省改成 operator，錯誤訊息改成指出「哪一類缺、該給哪個鍵」。
