一句話結論：這不是一個「變快」的修復，而是一個「讓數字重新有意義」的修復。 LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0 的三個讀者長期測「存在」而非「值」， profile 寫 =0（意圖關閉）卻一直是開啟狀態 ⇒ 2026-09-09 的品質修復空轉六天，而這六天內每一份 cap 快照與 llama-bench env 區塊都記著 "0"，讀起來像「已關閉」。 本輪把它改成單一值語意 predicate 並重新基線；控制臂（skip0=1）對舊參照 M1 9/9、M2 9/9、M3 9/9、整列 fnv1a64 9/9，證明 v3 參照確實是 skip0 開啟時 dump 的， 且這個 predicate 改動在其餘維度上數值中性。

1. 這個 knob 的真身：一條「對齊 base 佈局」的開關

先把最貴的誤解拆掉。L4_SKIP_LAYER0 在專案文件裡有兩個互相矛盾的結論， 而它們都是對的——因為量測當時的 base 佈局不同：

  • §8.36（2026-08-16）：-ngl 30 下，base 的 blk.0 FFN 留在 CPU（ngl=30 offload 29 層 + output）。 把 blk.0 收進 pool 會把它搬到 Metal ⇒ 與 base 的 float 分歧。所以 skip0=1 才是 bit-identical， 並據此把「blk.0 排除 pool」立為修復。
  • 2026-09-09 品質調查：full-offload L4（ALLOW_NGL=1，全部 40 層都在 Metal）下， base 的 blk.0 本來就在 Metal。此時 skip0=1 反而把 layer 0 變成「Metal graph 讀一顆 CPU 全寬張量」 ⇒ 15+27 十連發只有 4/10；無 skip0 的甜蜜點是 90–100%。

推論：任何「skip0 該設多少」的句子若不寫出 base 的 ngl，就是一句無法證偽的話。 本輪把它寫成一條規則（見 §5）。

2. 六天的空轉：三個讀者測「存在」，profile 寫「0」

三個讀者全部用 getenv(...) != nullptr。"0" 這個字串是非空指標， 所以 gate 為真——0 等於打開。而 run_server.sh 把這個變數無條件塞進 SERVER_ENV，再由 env "${SERVER_ENV[@]}" 真正傳進子行程。

旁證（不是靠這個 knob 的值，而是靠推導量）：CGC-DECPROF 在六天內的 log 中 19 次全部報 layers=39、layers=40 零次——池只服務 39 層。 這正是 CONVENTIONS A9 的判準：快照記錄的是意圖，行為卻相反。

3. 修法：一個 predicate，三個呼叫點

三個站點分散在三個檔案，所以修法不是三份比較式，而是一份定義——放在三個 TU 都已經 include 的 llama-expert-cache.h，這樣它們結構上不可能再各自漂移。

// llama-expert-cache.h -- 唯一的「這個旗標是開的」定義
inline bool cgc_env_on(const char * name) {
    const char * v = getenv(name);
    if (v == nullptr || v[0] == '\0') { return false; }   // unset / 空字串 = off
    return v[0] != '0';                                   // "0"/"0x…" = off；其餘 = on
}
inline bool cgc_l4_skip_layer0_on() {
    return cgc_env_on("LLAMA_EXPERT_CACHE_L4_SKIP_LAYER0");
}

附帶把 run_server.sh 那行由字面值改成 ${CGC_SERVER_SKIP0:-0}：原本的字面值無法從外部覆寫 （env "${SERVER_ENV[@]}" 會蓋掉任何傳入值），所以控制臂根本跑不起來； 寫死的那一格就是會漂移的那一格（eng-gate-0006）。

4. 投報率：這條修復在優化什麼？

專案的方法論是「交錯 A/B ×3 + md5」，一個測量值的可用性可以寫成兩個因子的乘積：

可用的數字 ＝ 數字 × P（配置與它自稱的一致）

skip0 的缺陷把第二個因子壓到接近 0，而且沒有任何儀器會喊。 所以這條修復不是優化某個數字，而是優化「數字的產生器」。四個受益面，按槓桿排序：

1｜量測有效性（最高槓桿、會複利）

  • 六天內凡經 run_server.sh 啟動的 profile，其 cap_*.json 與 llama-bench env 區塊 都記 "0"，但實際行為是 ON。任何「prod25 vs X」的比較都夾帶一個未申報的隱變數。
  • 修完之後快照 = 行為。收益不隨時間衰減，且每一個未來測量都繼承—— 這是它投報率最高的真正原因：它修的不是一個數字，是產生數字的那台機器。

2｜品質（使用者可見，且驗證便宜）

  • 生產 profile 一直在跑 2026-09-09 判定為 4/10 的配置，而文件聲稱它是 90–100% 的甜蜜點。
  • 若該機制在當前架構仍成立，這是真實的品質缺陷，不是量測問題；驗證成本極低 （probe_skip0.py --shots 10 兩臂）。

3｜語意一致性：把矛盾的軼事換成一條規則

  • §8.36 與 2026-09-09 都對，差別在 base 佈局（-ngl）。修完後文件可以寫規則而不是兩則互相矛盾的歷史。
  • 價值在於防止第 N 次同類誤判——包含讓後續讀者不必再重跑一次六天的除錯。

4｜速度（次要，方向未定，禁止假設）

  • 39 → 40 層池化同時帶來成本與收益： 成本＝layer 0 的 142 個 resident slot 進駐 Metal（+152 MiB）、 layer 0 的 expert 改走 ensure_batch 填充（+396 次 pread 進關鍵路徑）； 收益＝layer 0 的 FFN 不再是「Metal graph 讀 CPU 全寬張量」（移除一個跨後端消費路徑）。
  • 淨號未定。本輪沒有量速度，也不主張任何速度結論。

與 CGC_OA_ASYNC 那次最關鍵的差別：這次閘門無法自己發現。

OA_ASYNC 那次改的是「值 → 解析方式」，resolved env 字串變了，所以閘門自動報 INVALID COMPARISON，四個 profile 被靜默改道時有人被叫醒。

這次前後的字串都是 "0"；差別在語意。閘門的可比性檢查是字串比對， 所以它會報一個 FAIL，而那是 category error。這是本輪必須由人宣告、 並且必須換掉參照檔（v3 → v4）的原因。

5. 兩臂實驗（同一顆 binary，只換 skip0）

設計上刻意的順序：先跑控制臂，用「舊參照 + 舊行為」去證明診斷， 再跑新預設臂並重新基線。控制臂是可證偽的預測：若 v3 真是 skip0 開啟時 dump 的， 則 skip0=1 應該逐位元重現它。

兩臂的 dump 都通過 gate 的 dump 有效性檢查（9 records, validated）， 探針應答都正確（'42'）——排除了「空回答 + 健康 dump」那個 Metal OOM 簽名。

旋鈕的值正是本次的嫌疑犯，所以不能拿它當證據。teardown 的池完整性掃描給出乾淨的判別式：

一條必須撤回的舊判讀：LAYER_CAPS total 5976 slots 兩臂都是 5976， 所以它不是 skip0 的判別量。它只是 LAYER_CAPS 的計畫總和 （40 層 × 143 ＋ MTP 層 256 ＝ 5976），與 layer 0 是否真的進池無關。

6. 新風險：layer 0 帶來 4 個 zero region

這輪最該被追下去的一項，而且它與「修復」是同一件事的兩面： A 臂的池完整性是 zero-regions=0 [OK: every resident slot holds non-zero bytes]； B 臂變成 zero-regions=4，且四個全在 layer 0 （first zero region: layer=0 slot=18 kind=0 owner_expert=252）。

為什麼這是風險而不是雜訊：一個 slot 被 owner-set 認領（宣稱持有 expert 252） 卻整段是零位元組 ⇒ 任何路由到它的 token，在 layer 0 的 FFN 貢獻會被靜默地算成 0。 這正好是「輸出會漂移、argmax 卻還跟得上」的形狀——與 §5.2 量到的 M1 4/9、M2 9/9一致。

但它同時可能是設計行為：本專案的 ZERO slot 是 MTP 快路徑的既定機制 （zero_slot == slots_l - 1，僅 MTP 快路徑啟用）。兩臂都開了 MTP，A 臂卻是 0， 所以「設計行為」不足以解釋。本輪不下結論，列為第一優先待量項。

7. 下一步（依槓桿排序）

  1. 量 layer 0 的 4 個 zero region 是不是壞值。最小實驗：skip0=0 下固定路由到 layer=0 slot=18 expert=252，比較該 slot 的位元組與 GGUF 中 expert 252 的原值。 若是「填充沒落地」就是真實品質缺陷，且會直接解釋 §5.2 的漂移。
  2. 歸因 step 1 的「應該分歧卻相同」。需要的是 layer 0 在那一步的 route 觀測 （哪些 expert、被映射到哪些 slot），而不是更多 logits。
  3. 品質十連發兩臂（probe_skip0.py --shots 10，只有 skip0 不同）。 這是唯一能結案「4/10 vs 90–100%」的量測，成本一次 server launch。
  4. 同族掃描的其他兩個站點：全庫 67 個 presence 讀者中，另有 CGC_DBUF 與 CGC_SPAC 在 scripts/run_p1_mmap_stream.sh 被寫成 0（= 開啟）。同一條 predicate 可直接複用。
  5. 速度：39 → 40 層池化的淨號（+142 resident slot、+396 pread vs 移除跨後端消費） 需獨立量測，且必須在新的 v4 基線上量。
