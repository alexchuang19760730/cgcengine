S1：slot→expert 反查量完 —— 「同一個 slot 裝了不同專家」被否證

2026-09-17 01:25 · 引擎層 · 承接 S1_TIMING_REFUTED_20260917.html · 新增兩個引擎側讀數（SLOT-OWNER / SLOT-SEL）＋一個比較器；跑 r18–r22

結論（三句話）
  1. 你要量的事情量了，答案是否定的：wrong = 0 且 owner == ids 在 440/440 格、每一個臂都成立 ⇒ 被消費的專家，它落到的那個 slot 裡裝的就是 它自己。「同一個 slot 裝了不同專家 ⇒ 同一組 ids 讀到不同權重」不成立。
  2. 池的佈局確實不同，但那是後果：錨 vs S1 臂的 SLOT-OWNER 438/440 不同 （且 PERMUTED=0 ⇒ 常駐專家的集合不同，不只是重排）——因為 兩臂從第一個 1-token 步的 layer 0 起路由就不同。
  3. 我自己的讀數有一個設計缺陷，一併說清楚：因為 wrong=0， 「把 slot 反查回專家身分」在數學上是恆等式 ⇒ SLOT-SEL 的摘要等於 ids 的 摘要。它量的是路由，不是池。

兩個都是關於對映的述句。剩下沒人問的是池的內容：兩臂都同意 「slot s 屬於專家 e」時，s 裡裝的到底是不是 e 的權重。 slot_owner[layer][slot] 就是那個反查表，而且它由另一條程式路徑寫入 （llama-expert-cache.cpp:827 的 pick_slot／prefetch_slot 寫 owner， 而 publish 只讀 slot_table）——同一個指派、兩份表示、兩個寫者，正是先前那些漂移的形狀。

兩個新讀數（都 gated on CGC_S1_TABLE_CHURN=1，只印、不進任何 gate）

讀數取樣欄位
CGC-S1: SLOT-OWNER graph=G il=L …整層 slot 向量 sum, xor, wsum, n, owned
CGC-S1: SLOT-SEL graph=G il=L ntok=T …只取被消費的 ids，反查回專家身分 sum, xor, wsum, n, wrong, unowned, idsum, idsxor, idwsum

摘要沿用內核側張量擷取的四字方案，理由相同：sum 與 xor 只依賴多重集， 而 wsum = Σ v·(i+1) 依賴位置 ⇒ 「同一組專家換了位置」與「內容真的不同」 可以分開；n 是 slot 數（形狀不能冒充相同）；owned 是佔用數 （sum 會被自由 slot 的 −1 抵銷，單看它看不出佔用）。

比較器：Backup/compare_slot_owner.py（SAME / PERMUTED / DIFFERENT / SHAPE， 外加 wrong 的絕對閘與 degeneracy 控制）。新臂 p25-gputime-churn／ p25-keepleaf-churn／p25-slotgpu-churn。

2. 兩個儀器陷阱（都踩到了，都已修）

① 掛點必須選「兩臂都跑到」的地方。 第一版掛在 churn 區塊（publish 路徑 cgc_publish_slot_table_counted）⇒ 錨臂輸出零行、S1 臂 390 行——因為那個函式 只有裝了 GPU table 的臂才會被呼叫。比較的一側是空的。 移到 expert_cache_on_topk（兩臂的 CGC-HOOK trace 各 80 行）才可比。
② 取樣點必須在「填充之後」。 第一版在 hook 開頭取，讀到的是本步尚未填充的表 （slot_table[e] = -1），於是 unowned ≈ 每格 1（≈12%，正是冷專家率）， 會被讀成「讀到沒人擁有的 slot」這種損壞。移到池路徑 publish 之後（verify-strict 已讓所有 被選專家常駐）⇒ unowned = 0。

兩者都是「儀器本身的位置也是儀器的一部分」這個家族：前一個是誰跑到，後一個是何時跑到。

5. ★ 否證：被消費的專家，slot 裝的就是它自己

wrong = 0，且 owner == ids[j] 在 440/440 格、每一個臂都成立。 以 slot_table[e] 取出 slot、再查 slot_owner[il][slot]，得到的永遠是 e 本身。

⇒ 「同一個 slot 索引在兩臂指向不同的專家權重」這條機制不成立。 「gather 靜默讀到另一個專家的權重」（publish 路的註解擔心的那件事）在被消費的子集上從未發生。 §9.18.4 以「池/slot 的權重內容」的形式，這條路走完了。

6. ★ 自我修正：SLOT-SEL 的摘要在池自洽時是恆等式

邏輯很直白：若 wrong == 0 且 unowned == 0，則 o == e 逐元素成立 ⇒ 對 owner 取摘要，等於對 ids 取同一個摘要。所以我在同一行加了 idsum/idsxor/idwsum（對 ids 本身的摘要）作為這個讀數自己意思的控制：

CGC-S1: SLOT-SEL graph=0 il=0 ntok=1 sum=1187 xor=217 wsum=4539 n=8 wrong=0 unowned=0  idsum=1187 idsxor=217 idwsum=4539
                                                                                        ^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                                                                        s_* == i_*  ⇒ 退化

比較器的 degeneracy 控制報 A=440/440、B=440/440 ⇒ 每一格都退化。 ⇒ SLOT-SEL 唯一有資訊的欄位是 wrong／unowned，而它們是 0。 「把 slot 反查回身分」在池自洽時是恆等式——這條要進 skill，因為它是「測一個自己造出來的恆等式」的典型。

7. ★ 真正的讀數：路由不同，且從第一個 1-token 步的 layer 0 就不同

既然那個摘要等於 ids 的摘要，它的跨臂差異就是被消費的 top-k 專家不同。逐項查：

檢查結果
兩臂各自的 ids 摘要多樣性各 440 個互異（440 格 / 440 格）
兩臂的 ids 摘要集合交集只有 1 個
A 的 graph 0（40 層整組）是否等於 B 的任何一個 graph否 ⇒ 不是圖索引位移
graph 0 逐層il = 0..5 全部 DIFF

而且 CGC-HOOK 的前 80 行全部是 ntok=2（兩趟 × 40 層） ⇒ 那兩趟是 2-token 的池路徑 prefill chunk，之後的 1-token 步才被 SLOT-SEL 記到。 每個 graph 恰好 40 層（il 0..39）、兩臂都是 11 個 graph ⇒ 配對有效。

⇒ 池不是載體，路由才是；而路由的差異在 prompt 處理階段就已經存在。 這與內核側 r5b/r6/r7 的「prefill 的 ffn_moe_* DIFF@1」方向一致—— 兩個獨立儀器現在互相支持。

8. 這改變了什麼

  • 排除表再加一格：額外節點 ／ clamp 成 slot 0 ／ 對映錯誤 ／ 時序・race ／ slot 反查錯（本輪）。S1 的載體不在池。
  • 問題換位置：不再是「哪一層」也不是「哪一段時序」，而是 「prompt 處理階段的那個 2-token 池路徑 pass 裡，哪個節點先分歧」。
  • 下一步的具體做法：把內核側觀察點放到第一次 2-token 池路徑 pass 的 layer 0 ——注意不能再用 --decode-only（T 由 ne 自校準推出），那一步是 T=2。
  • 可複用：Backup/compare_slot_owner.py ＋兩個 *-churn 臂 已經是可重跑的哨兵組合（p25-keepleaf-churn 應永遠等於錨）。
