2.2 三條寫進 docstring 的設計規則

  1. 窗口，不是一次啟動。只有全部請求都回來的臂才記成 done； 被中斷的一律重排、永不當成資料。
  2. 只對自己的 port 發訊號。窗口要求「完全沒有 llama 行程」； 清理只針對自己的專用 port。pkill -f llama-server 在這裡殺過別條線的 server 一次。
  3. 基線夾住測試。Lane A 跑 b1 / b0 / b1b， 兩個 BITIDENT=1 基線之間的差就是門檻；小於門檻一律 INCONCLUSIVE， 不會被四捨五入成結論。

第四條（在 drift lane 的 docstring 裡）。這台機器沒有可讀的溫度探針 （pmset -g therm 不記錄、powermetrics 要 root）。 它的處理方式是把溫度從變數變成設計條件：相鄰時間的臂共享熱狀態， 所以同一區塊內的配對差值會抵銷漂移；而區塊間交替順序， 把「慢升溫會固定偏向某一臂」變成配對能消掉的東西。

4. Lane A — item 1：small-batch mat-mv 是不是 2.28× 的成因

4.1 預測為什麼是「微分」的

預測：原始碼說 ne11=1 本來就不在 small-batch 家族裡， 所以 BITIDENT=0 應該只動 ntok=4、不動 ntok=1。 這個預測無法用這顆載體檢驗，因為（見 §3 的 DESIGN GAP） MTP 開啟時每一個 base step 都是 4-wide 的 verify batch，不存在 ntok=1 的 plain step 可以當對照。

4.2 判定

比較值判定
兩基線展幅17.5%（門檻 5%）超標
BITIDENT=0 對 verify step 的效果−8.1%落在基線展幅內
結論NOT SUPPORTED（underpowered，不是 negative）

讀這條時最常犯的錯。它的 ms/token 欄不能跨臂比較 （BITIDENT=0 破壞 bit-identity ⇒ token 流與接受率都不同）， 這是它自己標的 CAVEAT。能比的是固定形狀的每步成本： ntok=4 的 total / wait / cb。上表就是照這個比法。

5. Kernel family eligibility：item 1 的前提本身不成立

這一節不跑量測，直接讀真的 GGUF。理由寫在它的說明裡： small-batch 家族（mul_mv_ext）只接受兩份互斥的型別白名單， 其餘型別一律落到 mul_mv/mul_mm；在那裡 batch size 不改變每列的歸約， 所以 CGC_MM_BITIDENT 對它們不可能有任何效果。

6.1 冷與暖是兩個製程，不是雜訊

同一個臂內 rep1_cold 與 rep2_warm： 118.08 → 73.71 ms/token ＝ 1.60×。而且連 step cb 也一起變 （22.20 → 5.19），step wait 則幾乎不動的量級不同（76.59 → 63.03）。 ⇒ 冷的那一個請求慢了 60%，這比 harness 想判的任何旋鈕效應都大一個量級。

6.3 一次 pass 就恢復 ⇒ 「prefill 後重新暖」是充分修法

7. Drift lane — 交錯配對的解析度

這一條問的不是 BITIDENT，而是兩個完全同配置的臂能不能在 5% 內一致。 第一次跑它們差 17.5%，所以那個結果只能報成 underpowered。逐層證據（原文）：

逐層證據：b1/b1b 的 wait 比值中位 1.121、最小 1.020（沒有一層更快）、
而 cb 比值 0.974 => 全域 GPU 側因子（時脈/熱），不是 pool。
所以這條線交錯時序並輪替區塊內順序，讓配對差值抵銷漂移。

讀這一節要知道的三件事。

(1) block 2 的 b1b=337.2 與 b0=133.6 相差 86.5% ——同一個 b1b 臂在 block 1 是 392.5、block 2 是 337.2， 而 b0 在同一小時內出現 345.3 與 133.6。這不是 kernel 的形狀， 是共享 GPU 的形狀（它自己的判決原文也是這樣寫的）。

(2) 因此「配對設計」的成敗要看區塊內臂展幅，不是看配對比值好不好看： block 1 的 18.8% 剛好在 20% 門檻內（可用），block 2 的 86.5% 直接判成不在同一個 regime。

8. 把噪音底接回 bench 與 HTTP 的差距

本專案目前有一個懸而未決的問題：llama-bench 的 decode 平台約 10.8–11.6 t/s，而同樣載體的 HTTP server 平台約 13.1–14.0 t/s， 缺口約 15%。把 harness 的噪音底放進來看，這張圖是這樣的：

結論。bench 與 HTTP 之間待解釋的 15%，與這台機器同配置兩臂的離散 （17.5%）是同一個量級 ⇒ 在目前的儀器與次數下，這個缺口判不出來。 這不是「找不到槓桿」，是「解析度不足」——而 harness 對 item 1 用的字眼完全適用： underpowered, not negative。

8.1 一個獨立的交叉檢查

harness 的 Lane B 暖態是 73.71 ms/token ＝ 13.57 t/s（非 MTP 模型、短 prompt）； 本線在 MTP 載體、2025-token prompt 上量到的 HTTP 平台是 13.13 t/s。 兩個不同儀器、不同載體、不同 prompt 形狀
落在同一個帶狀區間（13.1–13.6），與 harness docstring 自己記的 「the first request of a fresh server is a different regime (8.5-9 t/s vs 13.3 t/s)」一致。

12. 這一輪：把 decode 25 t/s 拆成 gate 鏈

25 不是一個數，是兩個欄位的乘積條件：t/s = mean_len x 1000 / step_cost_ms。 所以「離 25 多遠」這種問法本身沒有鑑別力 —— 必須先回答哪一個因子是綁住的。這一輪把它拆成 G0–G7（agent_harness/portal/targets.json 的 decode-25）， 其中只有中間幾格是結構量或計數器，最後一格（交付讀數）刻意不當判準，因為 15–20% 的 run-to-run 噪音讓單一 t/s 讀數決定不了任何事。

13. ★ 更正一：ntok 是「圖寬」，mean_len 是 2.40

先前的錯：本線曾用「http_duo 的 t/s ÷ DECPROF 的步/秒」反推出 mean_len ≈ 1.80，並據以宣稱「1.80 之下到不了 25」。那個 1.80 是窗口與算術的產物， 不是任何儀器讀出來的數。

定義（ggml-backend.cpp:2493-2500）：DECPROF header 的 ntok 是被 profile 的那張圖的 token 維度（ttopk->ne[1]），註釋自己寫 「ntok=2048 ⇒ prefill、ntok=1 ⇒ decode」。它很好用當判別器， 但 MTP 開啟時它幾乎恆等於 1 + n_max。

來源值是什麼
server 自己的計數器（per request）mean len = 2.40、 draft acceptance = 0.46541 由 acceptance 導出：1 + n_max x 0.465 = 2.40 ✓（這才是 mean_len）
DECPROF ntok 直方圖（同日實測）174/177 步 = 4 圖寬（draft 寬），不是接受數 ⇒ 不能拿它算 mean_len

後果：G4 的需求從「−34.6%」變成 union ≤ 38 x mean_len 這個函數 （mean_len 1.80 ⇒ −34.6%、2.40 ⇒ −12.8%）。把門檻寫成常數，會在夥伴欄位移動時默默過期。

14. ★ 更正二：CGC_SUBMIT_AHEAD 是「半死」的探針

它是專案指定的「唯一零改碼上界探針」（run_server.sh:1673 的註釋原文如此）。 同日實測它只對一半：

欄位baseahead能不能讀
每步圖寬4（174/177 步）4（28/28 步）相同 ⇒ 每步工作一樣
每步 median total169.21 ms99.39 ms 可讀：比值 ×1.702，與認證的 ×1.711 差 0.5% ⇒ 重現
mean_len（server）2.40–2.501.00 不可讀 t/s：acceptance 崩掉 ⇒ 探針自己的 t/s 只有 base 的 0.709×
gap/union可讀 25/28 步印 (NO TIMESTAMPS) 不可讀：poll 點移到下一段提交之後 ⇒ 結構性，不是「gap 已消除」

⇒ 合法的讀數只有步時比：序列化窗 = 步時的 41%（1 - 1/1.70）， 所以 total 從 169.2 → 99.4 ms，而 t/s 上界 = 2.40/0.09939 = 24.15 （條件是 acceptance 保住），下界 ×1.0 由 G2 保證。⇒ 跨過 25 只需 mean_len ≥ 2.485 （+3.5%，accept 0.465 → 0.495）⇒ G4 可能根本不需要。

⚠ 本線當天在這一格連續犯了兩個相反方向的錯：先說「探針全壞、×1.711 無法重現」， 再說 t/s 報酬是「[1.41, 1.70]」—— 兩個都是錯的。正解是逐欄位判定合法性，不是整體判死活。
