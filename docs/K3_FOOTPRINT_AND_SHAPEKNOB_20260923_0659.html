一句話。這一輪沒有讓 decode 變快，它做的是把「為什麼量不出來」這件事變成可機讀、可拒答的介面： （一）「量測工具吃太多記憶體」這個假設被否證——降 footprint 真的量得到（−26.4%）， 但它比真正的原因小 20 倍以上；（二）「k=3 會飄 1.43×」被拆成兩層變異數， 發現 k=3 有一個專屬的 launch 級項（13.16%，F=4.49），而 k=2 沒有； （三） k=2 與 k=3 其實不是乾淨的 A/B——ntok=4 會跨過一個 kernel 門檻把 PSO 換掉。 三件事的共同結論：接下來最便宜的一步不是多跑 arm，是把一個已經存在於樹上的計數器打開。
本文件的地位。它是進展文件，不是里程碑文件。它同時收錄 09-22 已完成但從未提交的引擎改動 （shape knob 的輸入／輸出兩半、dense GEMV 的 NSG 延伸、載體型別探針），因為那些改動與這一輪的產物 共用同一顆 build（libllama.0.0.578），拆成兩個 commit 會讓 check 8 的原始碼↔產物同步檢查失去意義。

2. Q1：半步 (B) 做完了，答案是否定的

2.1 先要有活能量

沒有任何東西能回答「一次 probe invocation 到底吃掉多少」，所以先寫 scripts/check/shape_probe/footprint_ab.py（selftest 26/26）。 它把 footprint 拆成三個彼此分離的成分，因為砍錯一件就白砍：

成分用什麼調是不是我們能砍的
分配量（pool / bank / host fill buffer）--pool-mib是（但 bank 不行）
持續時間（熱頁被摸多久）--target-ms是
幾何（bank 本身多大＝模型的 256 experts）--experts不是——砍它就是換一個模型在量

2.3 實驗二、三：帶著瘦池去跑，以及那 6 GB 去哪了

只加 --pool-mib 0、同一顆 build（dylib 650dd9d1d9fb89a4）重跑 joint sweep： null cell 從 241.5% 進步到 26.2%，但仍然讀不到，離 ≤5% 還差 3–5 倍。 而 sweep 標頭寫 usable 1.25 GiB、單次 invocation 只掉 ~0.4 GiB，中間少了 6 GB。 所以加了 --sequence 模式（每臂連打 12 次、三臂交錯、追蹤每次的出發點）： 

arm A  pool 320 MiB  target 1500 ms  baseline 9368 -> 8235 MB  DRIFT -1133 MB
arm B  pool 146 MiB  target 1500 ms  baseline 9470 -> 8216 MB  DRIFT -1254 MB
arm C  pool 320 MiB  target  100 ms  baseline 9392 -> 8179 MB  DRIFT -1213 MB

三種 footprint 掉的量一模一樣 ⇒ 那 ~1.2 GB 不是我們能調的那兩個旋鈕造成的。

2.4 真兇：盒子自己會甩 8.5 GB，而且甩的時候常常有別人

圖 1：三個量級放在同一個線性尺度上。0.13 GB 那一格刻意只畫成一條細線——它就是這麼小，把它畫大會騙人。
Q1 的結論。不要動 NEED_MB=8000，而且現在有更好的理由：不是「預設如此」，是「量過了， 降 footprint 換不到可讀性」。正解是第三條路——共用視窗真的 admit 的時候才准跑，跑完再問一次。 shape_knob_search.py 上一輪已接這個閘門，mmid_shapes.py 本輪補上 （原本只會印不會擋，所以它會把兩分鐘的量測浪費在別人的載入過程裡）。

3. Q2：把「飄」拆成兩層之後，它變成兩個問題

一 arm ＝ 一 launch ＝ 3 個 counted request（逐 request 的 decode_tps 已存在 Backup/k_abba_2026-09-23/），所以單因子隨機效應可以直接套： 

MS_within  = SS_within  / (n(m-1))    期望 = σ²_within
MS_between = SS_between / (n-1)       期望 = σ²_within + m·σ²_launch
σ²_launch  = max(MS_between − MS_within, 0) / m

max(…, 0) 是刻意的地板：MS_between < MS_within 會偶然發生，意思是「沒測到」，不是「負變異數」。

單一 request 的噪音每次 launch 被指定的基準arm mean 的總散佈
k=210.54%0.00%（F=0.62 < 1，95% 上界 9.98%）6.09%
k=312.21%13.16%（F=4.49，df 4/10，臨界 3.48）14.93%
這直接解釋了為什麼 ABBA 配對買不到東西。配對只能扣掉兩組共有的項，而這一項是 k=3 獨有的 ⇒ 配對 sd 只能等於 √2 × 單臂 sd。實測 2.28 vs 2.18 t/s —— 吻合。

3.1 順便量到：arm 自己把自己跑熱

3 個 request 單調下滑的比例first→last 跌幅
k=24/517 / 2 / 22 / 18 / 24 %
k=31/57 / 21 / 18 / 6 / 23 %

一條 arm 的 ~70 s 自己就在發熱（最多掉 24%），所以在 launch 之內還有漂移，任何 launch 前的閘門都管不到它。

4. k=2 與 k=3 不是乾淨的 A/B：ntok=4 換了一顆 kernel

server-context.cpp:4158 的 GGML_ASSERT(slot.spec_i_batch.size() == n_draft + 1) ⇒ k=3 是一個 verify step 4 個 token，k=2 是 3 個。而 4 這個數字會跨過一道門檻：

類型群mul_mv_ext 進入條件行號
F32 / F16 / BF16 / Q8_0 / IQ4_NL / Q4_0 …ne11 >= 2 && ne11 <= 8ggml-metal-ops.cpp:2569-2581
Q4_K / Q5_K / Q6_K / Q2_K / Q3_Kne11 >= 4 && ne11 <= 8ggml-metal-ops.cpp:2583-2590

這個模型有 Q2_K×2、Q3_K×1、Q6_K×1 ⇒ Q_K 家族在 ntok=3 走不到 ext，在 ntok=4 才進得去。 而且同一個 ext kernel 內部也換 PSO：nxpsg 由 ne11 < 3 決定 （:2607-2612，3→16、4→8）、r1ptg 由 ne11 決定 （:2618 預設、case 4: 在 :2627）。

結論。任何 k2−k3 的 t/s 差都把兩件事混在一起：「寬 verify 划不划算」與「那顆 PSO 好不好」。 所以 k 本身不是一個乾淨的 knob，k=2 上量到的排名不能直接搬去 k=3（反之亦然）。
順帶：ggml-metal-ops.cpp:2604 的 nsg = 2 是寫死的，CGC_MMV_NSG 摸不到這條路。

4.1 兩個已經被否證的假設（寫下來是為了讓下一個人不用再查）

  • 相位閾值：不是它。llama-cgc-phase.h:133-143 用 n_tokens <= decode_width 選 DECODE／PREFILL，若 width==3 那會是天差地遠的兩張圖。但 09-23 log 實測 CGC-SHAPE … width=8 routable=142 ⇒ 3 和 4 都 ≤ 8，同一張 DECODE 圖。
  • SYNCFILL 計數相同 ≠ 沒有 IO。llama-context.cpp:6497 印的 cold_filled 是請求數（cold.size()），不是落盤讀取數；真正的讀在 llama-expert-cache.cpp:35 的 pread，服務時間取決於 OS 頁快取。 ⇒ 「175 次請求四次 arm 都一樣」與「每次請求的服務時間差 1.43×」完全可以並存。

4.2 最便宜的下一步：一個已經在樹上、卻沒被打開的計數器

llama-expert-cache.cpp:418  static void rig_snapshot(int mode)
llama-expert-cache.cpp:432  "CGC-RIG-SNAPSHOT mode=%d reads=%zu read_bytes=%llu pread_usec=%llu ..."
llama-expert-cache.cpp:446  llama_expert_cache_refresh_prefill_protect()   // 唯一呼叫點
llama-expert-cache.cpp:447  getenv("CGC_PREFILL_PROTECT_FILE")             // 未設就直接 return

grep CGC-RIG-SNAPSHOT 在 09-23 的全部 log 裡零命中——就是因為沒設那個 env。 而 pread_usec 正是把「池 IO 服務時間」這個假設（H1）從假設變成數字的那個量。 而且它不用 rebuild：設 CGC_PREFILL_PROTECT_FILE 指向一個內容是 "0" 的檔即可（prefill-protect 維持關閉＝目前預設行為，但 rig 照樣 snapshot）。

兩個陷阱：(1) 不要用 CGC_PREFILL_PROTECT env —— cgc_prefill_protect_on() 用 getenv(...) != nullptr，所以 =0 也會把它打開； (2) docs/O1_PREFILL_PROTECT_RERUN_2026-09-19.md:87 寫的 CGC_RIG_SNAPSHOT=1 在 src 裡不存在（已 grep 確認），別照抄。

k=2 平均比 k=3 快 16.4%，但這個數字沒有被認證，而且 k=3 是雙峰（3/5 掉到 8.59–10.72）， 不是單純的吵。所以把它寫成一份事先登記的協定（docs/K3_PAIR_CERT_2026-09-23.md）：

6. 這一輪更正自己的六句話

原本寫的更正毛病屬於哪一族
swapfile 推到 6.1 GiB「不會自動縮回去」 錯，它會。實測 total 回到 4096 MiB（used 3348），期間沒做什麼特別的事。 把暫態當成本質
「這台機器今晚沒有 8 GB 空檔」 錯，它有，只是不穩定。02:1x 實測六次連採都在 9364–9428 MB，admits=True。 把一次樣本當成分佈
「4 臂／組」 那是標準誤（SE）不是信賴區間。k=2 實際是 4 臂（SE 3%）／16 臂（95% CI 3%）。 SE 與 CI 混用
k=2 的 launch 項「0.00%」 那不是證明為零，是沒測到。F 檢定的下尾反解給出 95% 上界 9.98%。 把「未測到」讀成「不存在」
「再 2 對就夠（n=7）」 太緊，改成 n=8（t=2.64 vs 臨界 2.365，而不是 2.47 vs 2.447）。 用同一份 sd 去規劃抽那份 sd 的實驗
「pread_usec 要 rebuild」 不用。讀碼發現它受 CGC_PREFILL_PROTECT_FILE 這個 env 閘控制。 沒有讀碼就先報價

7. 本 commit 一併落地的 09-22 引擎改動

以下四項在 09-22 已完成實測但從未提交，與本輪產物共用同一顆 build，因此一起進版控。

7.1 shape knob 的輸入與輸出兩半（llama-shape-knob.{h,cpp}，新增）

  • INPUT cgc_shape_knobs()：所有形狀 env 只 parse 一次 ＋ 跨軸驗證 ＋ 每軸狀態 （APPLIED/CLAMPED/CONFLICT/ABSENT/REFUSED）。cgc_pool_max_tokens() （llama-graph.h）與 CGC_N_CB（llama-context.cpp:495） 都改由這張表供值，行為不變（default 8、[2,64] clamp）⇒ 被施加的值與 report 印的值不會 disagree。
  • OUTPUT cgc_shape_report_{init,final}()：每相位一行 CGC-SHAPE v=1 …， 含實收幾何（width/union/fits/pool_cap_slots/slots_layer）＋ cache counter ＋ 品質哨兵 zero_mapped/verify_refused/inv_viol（任一非零 ⇒ 該 row 做的不是同一份工，t/s 不算量測）。
  • 實測：M 上限 17 確認（routable 是 142 不是 143，因 ZERO slot）； capacity miss 只佔 miss 的 6~7% ⇒ 143 slot/層不是容量飢餓，「處方反了」——該試的是縮池 把 RAM 還給 dense page-cache。

7.2 GDN 軸（#7）：operator 存在，但從沒被執行

ggml_gated_delta_net 與 Metal pipeline kernel_gated_delta_net_<type>_<nsg> 真的存在，K（狀態快照數）是 function constant ⇒ T=1 與 T>1 同一顆 kernel。 但加了 builder 自己的旁證 gdn_saw_fused／gdn_saw_manual 之後發現： default 與 ablation 兩者皆 0/0 ⇒ build_delta_net 在這個 server 歷程裡一次都沒被呼叫。

這意味著：GDN 相關的量測到目前都是在量 0。「關掉 ablation 之後 logits 逐位元相同」本來會被讀成 「兩條實做數值一致」——那是假結論，相同的原因是「沒有東西可比」。這條軸可以體面收掉。 ⚠ MTP 陷阱：spec decode 時 n_seq_tokens>1 走 chunking 分支，只關 GDN_AR 會完全看不見 ⇒ 要 ablation 就 AR/CH 都關。

7.3 dense GEMV 的 NSG 延伸（P1-3d）與載體型別探針

  • ggml-metal-device.cpp：CGC_MMV_NSG 現在能觸及 dense GEMV 的 IQ4_XS / Q6_K / Q8_0（此前那些形狀完全沒有 runtime tile dimension）。位元同一性理由與 IQ2_S 相同： 每一列的 dot product 留在單一 simdgroup 內 ⇒ nsg 改變不了化簡順序。
  • tests/test-backend-ops.cpp：補上 IQ3_S 的載體型別探針——交付載體的 ffn_down_exps 是 IQ3_S（41 層中 37 層，另 3 層 IQ4_XS、1 層 Q3_K）， 不是 IQ3_XXS；兩個形狀都留著才能在同一幾何下比型別，而不是從另一個型別推論。
