# 現在的 shape 能到 decode 25 t/s 嗎 —— 判決：**不能**（2026-09-23 22:4x）

> 起因：承接 `docs/EXPERT_IO_SHAPE_FIRST_PRINCIPLES_2026-09-23.md`（§EN-471）之後，
> 使用者問「你認為現在的 shape 能優化到 25 tok/s 嗎」。
>
> **本篇 0 次 benchmark**（無重建、無起 server）。全部由已量測數字結帳：**誰都沒有再跑一輪的必要**，
> 因為結論不受任何單一口徑影響 —— 見 §4 的四源收斂。

---

## 0. 一句話

**不能。差 22%（20.5 vs 25），而且缺口在 GPU 算力、不在 IO／shape。**

shape 優化的**全部價值**是把 `cb` 藏起來，其極限 = **20.5 t/s**（樂觀口徑）／**16.3 t/s**（舊 `gpu_sum` 口徑）。
要走到 25 t/s，`GPU busy` 必須從實測的 **142.6 ms 壓到 ≤115.2 ms** —— 那是**壓 kernel 本身**，
不是 paralysis of shape 能碰的東西；而壓 kernel 的那條唯一主線（K5）在 09-21 已被判「(C) 成立 ⇒ 上界作廢 ⇒ L2 歸零」。

---

## 1. 先把標的換成同一個單位

交付 cell（`prod_profile.py`，reps=3，NOMINAL）：**12.57 t/s，step 247.98 ms**。

```
每 step 產出 token = 12.57 × 0.24798 = 3.117 token   (= 接受率 77.9%，k=3 上限 4)
```

⇒ **25 t/s 在「接受率不變」下要求：**

```
step ≤ 3.117 / 25 = 124.7 ms        ← 這是總預算，含 GPU busy + IO + submit
```

這個 124.7 ms 是下面所有判決的尺。

---

## 2. GPU busy 已經超過整份預算

| 來源 | GPU busy / step | vs 預算 124.7 ms | 判決 |
|---|---:|---:|---|
| **細切**（`DEVICE_BUSY_ATTRIBUTED` §1.2，T=4 n=48，`CGC_CB_N_MAIN=1`） | **142.6 ms** | 超 **14.4%** | ❌ |
| 舊 `gpu_sum`（`CEILING_STACK` L3 的基石） | **181.6 ms** | 超 **45.6%** | ❌ |

⇒ **就算 IO 完全免費、一毫秒都不花，今天這個 GPU 也算不到 25 t/s。**
⚠ 這不是「重疊做得不夠」的結論 —— 重疊做到滿也只是把 `cb` 拿掉，`GPU busy` 一分不少。

---

## 3. shape 的極限，算給你看

細切 decompose（同一個 verify step）：`wait=142.6`（GPU 忙）＋ `cb=81.1`（IO）＋ `submit=9.5` ≈ `total 234.6 ms`。

| 情形 | step | t/s |
|---|---:|---:|
| 今天 | 234.6 ms | 13.3（該輪，非交付 cell） |
| **cb 完全藏起來（shape 的天花板）** | 142.6 + 9.5 = **152.1 ms** | **20.49** |
| 同上但用舊 `gpu_sum` | 181.6 + 9.5 = 191.1 ms | 16.31 |

**⇒ shape 能給的上限是 20.5 t/s，距離 25 還差 22%。**

反解也很清楚：要 25 t/s，`GPU busy ≤ 124.7 − 9.5 = 115.2 ms`
⇒ GPU 本身要比細切實測**快 19.2%**、比舊 `gpu_sum` **快 36.6%**。

## 4. 四條獨立線索全部落在 16~21.7，沒有一條碰到 25

| 日期 | 產物 | 極限 t/s | 方法 |
|---|---|---:|---|
| 09-19 | `DECODE_25TPS_TWO_ALGORITHMS` | **21.7** | 「快取無限快也只有 21.7」—— GPU busy 46 ms/token 是硬牆 |
| 09-21 | `CEILING_STACK` L3（重疊做滿） | **18.59** | `gpu_sum 181.56 ms` |
| 09-23 | `DEVICE_BUSY_ATTRIBUTED` 細切 | **20.49** | `wait 142.6 + submit 9.5` |
| 09-23 | 本篇（今天第一性原理的延伸） | **20.49** | IO 通道餘量僅剩 21% |

> 09-19 那份文件的標題就是「把 decode 從 8.9 推向 **20–25**」，而它自己在同一份裡寫下了否決自己的算式（21.7）。
> 兩天後獨立的三條路忍耐 👇🏻 同一區間。**沒有新事證，就不要再結這個案。**

## 5. 「乾脆不要 cache，全部常駐」—— 被內存堵死

```
模型 12.72 GiB = 專家 10.70 GiB（40×256×1.0703 MiB） + dense 2.02 GiB
機器總內存 = 16.00 GiB（M4，統一內存）
```

⇒ 全常駐已佔 **79.5%**，只剩 **3.28 GiB** 給 macOS + GPU working set + KV cache（ctx 4096）。
⇒ 必然進 swap。而 **swap 已知是致命的**：實測 swap 5301 MiB 時 hit% 68.7→57.2、base **12.57 → 4.62**。

⇒ **expert cache 不是優化選項，是被 16 GiB 強制的物理約束。**

---

## 6. 唯一一條理論通路，以及它為什麼是幻影

要把芒同時滿足**兩個不可達條件**才夠得到：

| 條件 | 現狀 | 可達嗎 |
|---|---|---|
| 接受率打到 k=3 滿值 **4.0** | 3.117（77.9%） | ❌ 滿接受率不是能「優化」出來的 |
| `cb` 100% 隱藏 + `GPU busy` 取**樂觀**口徑 142.6 | cb=81.1 ms 未藏 | ❌ 見 §5、§EN-471（通道餘量 21%） |

⇒ 兩者同時成立：**26.30 t/s**（恰好過線，邊際僅 +5.2%）
⇒ 任一個不成立：跌回 16.3~20.5。

而唯一能真正壓 `GPU busy` 的線 —— **K5 / L2**（「壓每節點固定成本」）—— 已在 09-21 結案：
`K5_GRID_HYPOTHESIS` **§2 數字不可引用** ⇒ **判決 (C) 成立，30–38% 上界作廢** ⇒ **L2 歸零** ⇒ **M-K5 不做**。
（`MEMORY_PERF.md` §「K0–K5 結案總表」，§EN-406／§EN-414）

若 K5 的上界還活著，帳會長這樣 —— **這是唯一曾經存在的通路，但它已被證偽**：

```
GPU busy 142.6 × (1−30%) =  99.8 ms ⇒ step 109.3 ⇒ 28.5 t/s   ✅
GPU busy 142.6 × (1−38%) =  88.4 ms ⇒ step  97.9 ⇒ 31.8 t/s   ✅
```

---

## 7. 判決

| 問題 | 答案 |
|---|---|
| shape（IO／重疊／並行／粒度）能到 25 t/s 嗎 | **不能，上限 20.5**（-22%） |
| 瓶頸是 IO 嗎 | **不是**。cb 全藏也只到 20.5 |
| 真瓶頸 | **GPU busy 142.6~181.6 ms > 預算 124.7 ms**（差 19.2~36.6%） |
| 能繞過嗎（全常駐） | **不行**，16 GiB 内存容不下 12.72 GiB 模型（§5） |
| 還剩的路 | **無**。K5 已判 (C) 成立 ⇒ L2 歸零 ⇒ M-K5 不做 |

**⇒ P(25 t/s) 維持 `MEMORY.md` 既有結論：< 3%。**

---

## 8. 若要設一個誠實的 target

不是 25，而是 **`cb` 隱藏程度的百分比**：今天 IO 吃 81.1/234.6 = **34.6%** 的 step，完全沒藏。

把 §EN-471 的結論接上來 —— **隱藏率每上升一點就有一點，但上限就是 20.5**：

| cb 隱藏率 | 有效 step | t/s |
|---:|---:|---:|
| 0%（今天） | 234.6 ms | 13.3（該輪） |
| 60% | 176.6 ms | 17.65 |
| 85% | 163.7 ms | 19.04 |
| **100%（不可達）** | **152.1 ms** | **20.49** |

⇒ **再往上要動的是 kernel（GPU busy），不是 shape。**
