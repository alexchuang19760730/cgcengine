Shape Overlap — 疊起來跑更快

你說得對：既然知道會跑什麼，為什麼不能疊起來跑？
💡 你的洞察
我們已經知道每一步會跑什麼：
→ 先跑 dense GEMV
→ 再跑 MoE gather
→ 再跑 MTP verify
→ 最後跑 KV cache ops

既然都知道了，為什麼不能疊起來跑？
→ 在等 MoE gather 讀記憶體的時候，dense GEMV 的計算可以繼續跑
→ 在 dense GEMV 算的時候，MoE gather 的記憶體讀取可以先開始
→ 兩個疊在一起 = 總時間更短

🔬 為什麼可以疊起來跑？
因為不同的部分，瓶頸不一樣：
部分 瓶頸是什麼？ 同時做另一個 能不能疊？
Dense GEMV 記憶體頻寬（77%） MoE gather 讀記憶體 不行 — 都是記憶體 bound，會搶頻寬
Dense GEMV 記憶體頻寬（77%） MoE gather 計算 可以 — 一個讀記憶體，一個計算，不搶資源
MoE Gather 記憶體頻寬（25%） Dense GEMV 計算 可以 — 一個讀記憶體，一個計算，不搶資源
MoE Gather 記憶體頻寬（25%） 另一個 MoE gather 讀記憶體 不行 — 都是記憶體 bound，會搶頻寬
關鍵洞察：
如果一個 kernel 是「記憶體 bound」，另一個是「計算 bound」，
那它們可以疊在一起跑 — 一個用頻寬，一個用算力，互不搶資源。

但如果兩個都是「記憶體 bound」，那就不能疊 — 它們會搶頻寬。
🎯 實際上能疊什麼？
我們來看每個部分，是記憶體 bound 還是計算 bound：
部分 是什麼 bound？ 能不能跟別的疊？ 能省多少？
MoE Gather 讀取 記憶體 bound（25% 頻寬） 可以跟「計算 bound」的東西疊 省很多
MoE Gather 計算 計算 bound（其實很少） 可以跟「記憶體 bound」的東西疊 省很多
Dense GEMV 記憶體 bound（77% 頻寬） 已經很滿了，疊不了多少 省一點
MTP Verify 混合（有讀有算） 部分可以疊 省一些
KV Cache 寫入 記憶體 bound 可以跟計算疊 省一點
最好的組合：
→ MoE gather 在讀記憶體的時候（記憶體 bound），
→ 同時跑另一個 kernel 的計算部分（計算 bound）
→ 這樣就把「閒置的算力」用起來了

這就是「shape overlap」：
不是改某個 kernel 變快，
而是讓多個 kernel 的時間軸疊起來，
→ 總時間就變短了
🛠️ 要怎麼做到？
要把 shape 疊起來跑，需要做幾件事：
步驟 要做什麼 難度
1 知道每個 kernel 是什麼 bound
→ 哪些是記憶體 bound？哪些是計算 bound？
→ 量測出來，才知道怎麼疊 		中
2 把 kernel 拆成「讀取」和「計算」兩部分
→ 先發出讀取請求（async）
→ 然後去跑別的計算
→ 等讀取完了，再繼續算 		高
3 調度器要知道什麼時候可以疊
→ 不是所有 kernel 都能疊
→ 調度器要知道哪兩個可以同時跑
→ 然後安排它們的時間軸 		高
🎯 結論
你的洞察是對的：
既然知道會跑什麼，就應該疊起來跑。

為什麼之前沒做？
1. 之前一直在優化單個 kernel，沒有想過「整體調度」
2. 不知道每個 kernel 是什麼 bound，不知道怎麼疊
3. 要做 kernel fusion + async dispatch，工程難度很高

這跟 MoE gather 的優化是什麼關係？
→ 是兩個不同的優化方向：
→ 方向 A：把 MoE gather 本身變快（提高頻寬利用率）
→ 方向 B：把不同的 kernel 疊起來跑（overlap）

兩個都做，效果最好：
→ 先把 MoE gather 本身優化（25% → 65%）
→ 再把不同的 kernel 疊起來跑（overlap）
→ 兩個加起來，就能到 25 t/s 以上
