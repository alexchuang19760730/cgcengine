01

背景与问题定义

CGC MoE Engine 当前在端侧已达到 20 tok/s decode。本方案的唯一目标：在不掉速的前提下，把专家缓存（expert cache）显著缩小，为 16GB 统一内存设备腾出 KV、系统与多模型共驻空间，并降低整机内存压力。

1.1 现状基线：为什么现在的缓存缩不动

串行 decode（无 MTP 批量验证）下，每输出 token 需要读取的权重字节由「每层激活专家 × 层数」决定：

W_serial = 48层 × (8 top + 1 shared) 专家 × 1.7 MB + attention ≈ 1.2 GB / token （Qwen3.6-35B-A3B，IQ3_XXS ≈ 3.06 bit/param）

在带宽方程约束下，串行保持 20 tok/s 需要命中率 h ≥ 0.83（M4 Max）~0.88（Air M4），即专家几乎全驻留——缓存缩小空间 ≈ 0。这不是实现问题，是物理带宽问题：SSD 带宽（~5 GB/s）比内存带宽（105~430 GB/s）低一个数量级，只要每 token 需要从 SSD 读的字节超过约 0.2 GB，20 tok/s 在数学上就不可能成立。

1.2 问题陈述

在满足以下三约束的前提下，将专家驻留比例从 ≥83% 降至 ≤30%：

C1 · 速度保持：decode 吞吐 ≥ 20 tok/s（TPOT ≤ 50 ms），且不被 SSD 读延迟拖慢。
C2 · 内存收缩：专家常驻内存（hot set）≤ 30% 权重字节，其余专家按需从 SSD 流式读入。
C3 · 质量不降：GSM8K / HumanEval / MBPP 相对自然路由的精度损失 ≤ 0.5 pp。

1.3 关键洞察：预取隐藏延迟，Union 摊薄带宽

业界常把「预取」当作万能药，但预取只解决延迟隐藏（把 miss 的 SSD 读变成后台 IO 与计算重叠），不减少总读取字节。真正能把缓存缩小的物理杠杆只有一个：MTP 批量验证的层内 Union 摊薄——N 个 draft token 一次性验证，每层 router 只跑一次、按专家集合 Union 读取，摊到 N×接受率 个输出 token：

W_eff = ( Σ_层 U_l × E_expert + attention ) / (N × α)  ≈  0.23 GB/token （N=8, U=12, α=0.75）

这是本方案与"单纯加预取"的本质区别：Union 摊薄把每输出 token 的读取需求降 5 倍，等价地把"保持 20 tok/s 所需命中率"从 0.83+ 拉低到 0.03~0.33——缓存缩小空间由此打开。

风险预告：Union 摊薄的收益有两个前提——每层 Union 不膨胀（U 控制在 12 左右）且接受率 α 不塌（≥0.75）。draft 质量差时 U 会涨到 20+、W_eff 反超串行，这正是本方案引入 Verifier-Side 集合裁剪的原因（见 §3.2），也对应 S²-MoE 与 AcceptMoE 论文中观察到的同一问题。
02

方案总览：三层联动架构

三个模块各自解决一个约束，缺一不可：Union 聚合预取保 C1（延迟隐藏 + 带宽摊薄），Verifier-Side 集合裁剪保 C1+C3（压住 Union 膨胀、控制精度），Per-Layer Hot Cache 保 C2（按层独立预算，只驻留高频专家）。

示意：MTP 批量验证 → 层内 Union 聚合 → Verifier 集合裁剪 → 按层预取与验证的完整流水线（非真实工程图）

2.1 与 CGC 现有 prefetch + MTP 机制的关系

CGC 已有「prefetch + MTP」骨架。本方案不是推翻重来，而是把预取从单 token 粒度升级为MTP Union 粒度，并新增一个验证端裁剪模块：

能力项CGC 现有（单 token 预取）本方案（Union 聚合预取）
预取触发时机当前 token router 结果到达后MTP 一次取得 N 个候选后，逐层批量 router
预取对象单 token 的 top-k 专家N 个 token 的专家集合 Union U
带宽摊薄无（每 token 独立读 8 专家）union/N 摊薄，每输出 token 读取降 5×
专家集合选择自然路由 top-k（会散射）commitment 加权 + self-sizing 裁剪（§3.2）
缓存管理全局共享缓存per-layer 独立预算 + hot set（§3.3）
03

核心算法设计

3.1 层内 Union 聚合预取

每个验证轮：draft 一次产出 N 个候选 token → 对每一层执行批量 router（N 个 token 的 hidden state 一次前向）→ 取本层被激活专家集合的 Union → 与当前 resident 集求差得到待预取集合 → 后台异步读入。预取读入与「上层验证计算」重叠，miss 不再阻塞流水线。

# 每验证轮（伪代码，对接 CGC Engine 调度层）
draft = draft_model.generate(prompt, N=8)          # MTP 一次 N 个候选
for layer in 1..L:
    logits = router(layer, draft.hidden)      # 批量 router：N 个 token 一次
    U  = union_topk(logits, k=8)           # 本层候选专家集合（目标 |U|≤12）
    if offload_enabled:
        U = prune_nonresident(layer, U)        # residency-aware 移除（§3.2.4）
    to_fetch = U - resident(layer)
    async_prefetch(to_fetch)                   # 后台 pread → per-layer cache
    U_c = verifier_select(layer, U, P_commit)  # 集合裁剪（§3.2）
    verify_batch(layer, draft, U_c)            # 只读 U_c，批量验证 N 个 token
update_lru_stats(draft.accepted)               # 回写每层命中统计

为什么按层聚合而不是按模型全局：MoE 的专家局部性只存在于层内——同一层内 token 间专家重叠高，跨层无重叠。逐层独立 Union + 独立缓存预算，避免跨层专家互相抢占缓存（MoE-Infinity 已验证的分层缓存结论）。

3.2 Verifier-Side 集合裁剪（AcceptMoE 式）

Union 摊薄的前提是 U 不膨胀。若 draft 质量差，N 个 token 的专家集合会散射到 20+ 个/层，W_eff 反超串行。裁剪模块在验证前把每层可读专家集合 U_c 收敛到「对输出贡献最大」的子集：

3.2.1 Commitment 概率加权

对每个 draft 位置 t，离线统计它被最终输出接受的边际概率 P_commit(pos_t)（按 draft 深度单调递减，浅层高、深层低）。专家 e 的验证需求分 = 各 token 的 router 分数 × 该 token 被接受的边际概率：

score(e) = Σ_t router_t(e) × P_commit(pos_t)   // 越靠近根的 token 权重越高

3.2.2 Root Anchor

根 token（已验证、必然进入输出的位置）的自然 top-k 专家恒保留——它们是本轮验证正确性的锚点，不可裁剪。

3.2.3 Self-Sizing 集合大小

按 score 降序保留非锚专家，保留数量由需求集中度自适应：需求集中（少数专家拿到大部分分）→ 集合小；需求分散 → 集合大。公式化为带 重路由预算约束 的集合选择（取自 AcceptMoE 的 m⋆ 规则）：

m⋆ = max{ m : Σ_{j≤m} v_π(j) ≤ a(S), |S| − m ≥ k }   // 裁剪不越过自然 top-k 下界与重路由代价上界

3.2.4 Residency-Aware 移除（offload 场景）

非驻留专家按 LRU 命中历史从集合中移除，被移除 token 重路由到保留专家；代价受「集合形成时的自然分配位移 a(S)」约束，避免裁剪引发不可控的重路由漂移。

# verifier_select：commitment 加权 + self-sizing（伪代码）
def verifier_select(layer, U, P_commit):
    anchor = root_token.natural_topk            # 3.2.2 根锚点恒保留
    demand = {e: Σ_t router_t(e)·P_commit[t] for e in U - anchor}   # 3.2.1
    ranked = sort(demand, desc)
    k_self = size_by_concentration(demand)   # 3.2.3 自适应集合大小
    U_c = anchor ∪ ranked[:k_self]
    if offload: U_c = residency_prune(U_c)   # 3.2.4 LRU resident 约束
    return U_c

与 S²-MoE 的关系：S²-MoE 的 routing-aware pruning 在 draft 侧裁剪扩展树（只保留预期收益大于验证成本的候选），本模块在验证端裁剪专家集合——两者正交，可叠加。预期组合收益：draft 树更紧凑（U 更小）+ 验证集合更收敛（命中率更高）。

3.3 Per-Layer Hot Cache

3.3.1 离线 Hot-Set 识别

用代表性语料（代码 + 数学 + 通用混合）跑 N_tok = 5 万 token 采样，统计每层每个专家的激活频率，按层排序取 top 30% 为 hot set（常驻 RAM），其余 70% 专家放 SSD。驻留比例是 POC 扫描变量（10%/30%/50%/80%），hot set 随比例截断。

3.3.2 在线 LRU 与预算

每层独立 LRU 缓存对象，独立字节预算 B_l = per_layer_expert_bytes × 驻留比例。命中不换位（仅读）、miss 读入放 MRU 端、超出预算从 LRU 端驱逐。驱逐策略提供 LFU / LFRU 两个可插拔后端（对标 llama.cpp moe-hot-cache 的分层命中统计）。

集成点与全栈模块插件化适配

方案按「算法层 / 调度层 / 后端抽象层」分层，算法层（裁剪、union、hot-set）与后端无关；调度层负责流水线重叠；后端抽象层以插件形式适配各硬件。下表为全栈模块 × 后端适配性总表：

模块Metal（M4 Max/Air）CUDA（4090/5090）昇腾 NPUHexagon NPU + UFS
Per-Layer LRU 缓存原生 mlx 数组 + 分层字典原生 页式显存驻留适配 权重页管理适配 页粒度驻留
Union 聚合 + 批量 router原生 mlx batch 前向原生 CUDA 批量 GEMM适配 aclrt 异步适配 QNN 批量张量
异步预取调度原生 后台 pread + Metal 队列原生 CUDA Streams 重叠适配 aclrt 流适配 UFS 命令队列
Verifier 集合裁剪纯算法层 · 后端无关（commitment 表 + 排序）
Hot-Set 离线识别离线工具链 · 与后端无关（采样统计）
量化感知字节口径按 IQ3_XXS / MXFP4 计算，裁剪权重以字节计

适配性结论：算法与调度层可 100% 复用，各后端只需实现 4 个抽象接口——load_expert(layer,id)、batch_router(layer,hidden)、verify_batch(layer,draft,U_c)、async_prefetch(list)。Mac 端（Metal）与 CUDA 端可先行落地，NPU 端为插件化第二期。

08

风险与边界

R1 · Union 膨胀（高优先）：draft 质量差 → U 涨到 20+/层 → W_eff 反超串行。缓解：Verifier 集合裁剪（§3.2）+ draft 侧 routing-aware 裁剪（S²-MoE）叠加；阶段 0 必须先测 U 分布，U 基线 >16 时本方案收益上限收缩。
R2 · 接受率塌陷：α < 0.5 时摊薄失效。缓解：Context-aligned self-speculation（draft 与 target 共享已确认 KV，降低上下文偏差）；α 作为阶段 0 关键出口指标，不达标先调 draft 对齐再谈缓存。
R3 · SSD 带宽被高估：Mac 内置 NVMe 顺序读 5~6 GB/s，但 1.7MB 粒度小块随机读实测可能 2~4 GB/s。带宽模型对 B_ssd 高度敏感（每差 1 GB/s ≈ ±4 ms/token），阶段 0 必须实测，禁止用厂商标称。
R4 · 裁剪引入精度漂移：约束验证集合 = 改变模型分布。缓解：root anchor 恒保留 + 精度漂移 ≤0.5 pp 硬门槛；若超限，优先放宽集合大小（self-sizing 上限）而非放弃裁剪。
R5 · 16GB 统一内存的整机约束：系统 + KV + hot set + 双模型（draft 与 target）共驻。hot set 30% ≈ 4 GB 级（IQ3_XXS 13.4GB × 30%），加 draft 与 KV 后需实测内存峰值；若超限，驻留比例降档至 20% 并重跑 Go/No-Go。
R6 · 正确性边界：本方案只允许改变「验证阶段读取的专家集合」，不允许改变已接受 token 的输出分布。所有消融必须跑 bit-identity 校验：同一 seed 下，裁剪方案的已接受前缀与自然路由逐 token 一致。

A · 带宽模型（推导口径）

t_token = W_eff·(1−h)/B_ssd + W_eff·h/B_ram + t_compute （预取理想 → 带宽受限；单位 GB, GB/s, ms）
W_serial = 48 × 9 × 1.7/1024 + 0.4 ≈ 1.2 GB； W_eff = (48·U·1.7/1024 + 0.4)/(N·α)

示例值：E_expert=1.7MB（4.4M params × 0.383 B，IQ3_XXS）；attention+常驻 0.4GB；N=8，U=12，α=0.75 → W_eff≈0.226GB；U=14，α=0.65 → W_eff≈0.291GB。保持 20 tok/s 所需命中率：串行 h≥0.83（Max）/0.88（Air）；MTP 理想 h≥0.03/0.12；MTP 保守 h≥0.25/0.33。所有数值为建模口径，阶段 0 实测后替换。
