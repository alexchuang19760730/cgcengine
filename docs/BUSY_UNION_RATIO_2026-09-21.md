# `gpu_busy_sum` 的 1.22 加倍因子：判明（不成立，真实 ≈1.51）

日期：2026-09-21 · 线 A（ace）· **0 重建、0 写 C++、未起 server**
日志：`§EN-417`

---

## 0. 一句话

**1.22 不成立。实测 `gpu_busy_sum / gpu_union` 的中位是 1.510**（286 行、7 个独立 run 一致；
p25–p75 = 1.455–1.561）。**1.22 落在观测分布的第 5.9 百分位**，基本可以排除。

但**这不是本次最重要的发现**。判明过程暴露了一个更大的问题：
**地板读数在 run 之间差到 1.75×**，远大于 1.22 vs 1.51 的差距（1.24×）。
⇒ **用任何一支历史 run 的数字给「25」定案都不行**，必须做一次干净的交付 cell 量测（第 ② 步）。

## 1. 两个量的真实定义（读码确认，不是猜）

`ggml-metal-context.m:545-583` `ggml_metal_cgc_gpu_take()`：

```c
for (i = 0; i < n_cb + 1; ++i) {          // 一个 segment 的全部 command buffer
    busy += e_ns - s_ns;                  // out[0] = Σ buffer duration
    s_min = min(s_min, s_ns); e_max = max(e_max, e_ns);
}
out[1] = e_max - s_min;                   // union = 段内墙钟跨度
```

`ggml-backend.cpp:2149-2174`（`hook_seg` 内）逐 segment 累加，`gt_busy += g[0]`、`gt_union += g[1]`。

| 量 | 含义 | 段内并发时 |
|---|---|---|
| `gpu_busy_sum` | **Σ buffer duration** | 并发的 buffer **算多次** |
| `gpu_union` | **Σ 段内墙钟跨度** | 并发**只算一次** |
| `gap` | 段与段之间的 GPU 时钟空档 | — |

⇒ 比值 = **段内平均并发度**。**1.22 这个数低估了它。**

口径（易错点，已确认）：`CGC-GPUTIME` 一行 = **一个 decode 主图**
（`segs=40 bufs≈352`），不是 4 步。`gt_nseg` 在每次打印后被重置（`:3028`）。

**pooled（n=286）**：中位 **1.510**，p05=1.199 p25=1.455 p75=1.561 p95=1.650

稳健性检查（两条都过了）：

1. **`skipped` 不是主因**。代码注释（`ggml-backend.cpp:3003`）明确要求 `skipped==0`「否则整行无意义」，
   而这 7 支 run 的 `skipped` **全部非零**（0–15）。但按 `skipped` 分四层后比值仍稳定在
   **1.42–1.84**，且**高 skipped 层反而略低** ⇒ 缺失时间戳没有把比值推高。
2. **仪器一致**。7 支 run 分属 4 个不同 cell（prefill250 / prod25-stream / elemw census），
   比值全部落在 1.49–1.55 ⇒ 不是某个 cell 的偶发。

⇒ **1.22 判为不成立**（它在分布的第 5.9 百分位）。记忆 `MEMORY_PERF.md:693` 那条
「比值 1.22」应改记为 **1.51**。

## 3. 但这笔修正改变了什么：地板不是「181.56」

`docs/CEILING_STACK_2026-09-21.md` 的 L3 = `18.59 t/s` 是用 **`gpu_sum 181.56`** 当
「重叠做满的硬天花板」算的。既然 `gpu_busy_sum` 把段内并发算了 1.51 次，
**它就不是墙钟**，用它当地板是**低估可达上限**。

按「gap 能不能消除」分两种地板：

| 口径 | nsm | iopath | five_224615 | 说明 |
|---|---:|---:|---:|---|
| `busy`（旧算法） | 188.57 | 138.10 | 231.41 | ❌ 并发算多次，非墙钟 |
| `union + gap` | 216.49 | **123.78** | 230.99 | gap 不可消除时的地板 |
| `union` | 121.35 | **88.53** | 147.70 | gap 可消除时的地板（L3 已判不可消除） |

⚠️ **run 间差 1.75×**（123.78 vs 230.99）—— 这才是主导不确定性。
单看 iopath，`union+gap = 123.78 ms < 135 ms`（25 t/s 在 ml 3.375 下的预算）
⇒ 那支 run 上 **25 是够的**；单看 five_224615（230.99）则**远远不够**。

⇒ **1.22 vs 1.51 只是 1.24× 的分歧，run 间的 1.75× 才是真正无法定案的原因。**

## 4. 顺带钉死的两个数字（0 重建，直读 GGUF 头）

第 ② 步要用「每 step 权重流量 / GPU 墙钟」算有效带宽。记忆里的
**1.34 GB/step 是几何推算、未实测**（`2026-09-21.md` §EN-366 自己标了）。用
`gguf_expert_layout.py` 直读 header + offset 差算出精确值：

```
expert（41 层 × 256 专家）  11372.00 MiB  → 每专家 1.0834 MiB
embed/output                  795.71 MiB   （每步不读）
attn                          548.59 MiB
other_blk                     154.76 MiB
shared_expert                 148.25 MiB
norm                           10.85 MiB
```

⇒ **每 step dense = 862.5 MiB**（attn + norm + shared_expert + other_blk）
⇒ **每 step expert(topk=8) = 355.4 MiB**
⇒ **合计 1217.8 MiB = 1.189 GB/step**（topk=6 → 1.103；topk=10 → 1.276）

记忆的「dense 827 MB」与实测 862.5 吻合 4%；「expert 509 MB」对应 topk≈11.5，
偏高（可能把 MTP draft 的额外层算进去了）⇒ **改用 1.189 GB/step（topk=8）**。

用这个分子配 `union` 当分母的**有效带宽**（这是第 ② 步要量的东西的预先估算）：

| run | union (ms) | 有效带宽 (GB/s) | 占 M4 峰值(~100 GB/s) |
|---|---:|---:|---:|
| iopath | 88.53 | **13.4** | 13% |
| nsm | 121.35 | **9.8** | 10% |
| five_224615 | 147.70 | **8.1** | 8% |

（记忆 §EN-366 的 13.6 GB/s 是用 1.34 GB ÷ 97.9 ms 算的，与 iopath 的 13.4 对上 ⇒ 两个口径互证。）

## 5. 对第 ② 步的修正（重要）

① 的答案**直接改了 ② 的设计**：

- ❌ 旧设计（我上一轮提的）：分母用 `gpu_busy_sum 181.56` ⇒ 有效带宽 ~25 GB/s
- ✅ 修正后：分母用 **`gpu_union`**（墙钟）⇒ 有效带宽只有 **8–13 GB/s**

⇒ 判准「有效带宽 25 → 33.5 GB/s」的**起点不是 25，而是 8–13**。
  需要的是 **×3.4–×4.2**，不是 ×1.345。

⇒ 而且因为 run 间差 1.75×，**② 必须自己在同一次 run 里读 `union` 与 `gap`**，
  不能沿用任何历史 run 的分母。

## 6. 判决与下一步

| 项 | 结论 |
|---|---|
| 1.22 成立吗 | **不成立**，真实 **≈1.51**（286 行 / 7 run，1.22 在 p5.9） |
| 需要重建吗 | **不需要**（全部来自既有 raw + 读码） |
| `18.59 t/s` 这个 L3 天花板 | ⚠️ **分母口径错**（用了非墙钟的 `busy`）⇒ 应重新表述 |
| 能给「25」定案吗 | **不能** —— run 间差 1.75×，必须用干净交付 cell 重测 |

**第 ② 步（唯一能推进的）**：交付 cell（`prod_profile.DECODE_SHAPE`、reps=3、NOMINAL 窗口）
一次跑，把 **step total / wait / cb / submit / busy / union / gap** 读进**同一份 log**，
再用 **1.189 GB/step ÷ union** 算有效带宽。与阈值 33.5 GB/s 比，过不了就停（不写 kernel）。

⚠️ 诚实边界：本文件所有 `union`/`gap`/`busy` 都来自 **7 支不同 run**，
彼此不同 cell、不同 swap 状态；`skipped` 全部非零（代码注释说这种行「无意义」，
但按 skipped 分层后比值稳定，故采信其**比值**而非绝对值）。
