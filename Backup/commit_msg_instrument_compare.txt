feat(measure): 兩個 decode 儀器的差距被量出來了，而它大半不是「引擎快慢」——是「第一個 rep 是冷的」

起因：路線圖 §1 把 9.16 / 9.45 t/s 標成「llama-bench decode」，而 12.95 出自 decode_bench
（HTTP）。在同一個專案裡把兩個儀器的數字並排，正是這個專案反覆踩到的錯，所以直接量。

## 配對的前提：env 逐字相同，而且是解析出來的

`llama_bench_matrix.py` 已支援 `PROFILE:ENV=VAL` 形式，所以

    --arms 'prod25:CGC_SERVER_MTP=0;CGC_GPU_TIMING=1;CGC_DECODE_PROFILE=1'

就是 `decode_sweep --arms p25-gputime` 那一臂的 env，兩邊都經
`run_server.sh CGC_DUMP_ENV=1` 解析（單一真相，不是手抄第二份）。順序 ABABAB 交錯，因為
prefill 的工作已證明自變數是累積負載（序列裡第幾次啟動），不是靜置時間。

## 差距的大半：第一個 rep 是冷的

llama-bench 的 tg warmup 原始碼上是 `test_gen(ctx, 1, ...)`——**一個 token**（llama-bench.cpp:2392），
而 context／`-expert-cache` 池每 instance 建一次 ⇒ 池從空開始，第一個 rep 付 compulsory 冷填
（它自己的 miss 歸因：compulsory 4437/5195 = 85.4%）。`avg_ts` 把那個 rep 平均進去；
`decode_bench --warmup 1` 恰好丟掉對應的那一輪。

逐 rep（DECPROF，只取 ntok=1）：

    n=128 r=3   r1=120  r2=86  r3=93  -> 平台 89 ms  (rep1/平台 = 1.35x)
    n=256 r=3   r1=116  r2=87  r3=87  -> 平台 87 ms  (1.34x)
    n=24  r=8   r1=181  r2=132 r3=97  -> 平台 104 ms (1.73x，要 ~4 個 rep)

⇒ 平台值 87–90 ms/token = 11.1–11.5 t/s，對 decode_bench 的暖值 80 ms / 12.36 t/s 是
**1.10×**，不是標題的 1.32×。（自我修正：先前用四個桶的中位數說這是「單調暖機曲線」，
那個說法太強——逐樣本散佈 68–125 ms、±30%，可支持的只有「rep1 明顯慢、rep2 進平台」。）

## 三個寫下來的預測，兩個死掉

1. `-n 24 -r 8` 會把均值推上去 —— 只 +9%（7.21→7.88），且該臂在 HEAVY 下跑 ⇒ 不算證實。
2. `-n 128 --no-warmup` 會掉到 ~7 —— **9.40 vs 9.38 ＝ 0.2%**：no-op。它證實了原始碼讀到的
   「warmup 只有 1 個 token」，同時**推翻 harness 自己 `--no-warmup` 說明**那句「warmup 讓池變熱、
   所以預設更接近被服務的請求」。
3. `-n 256` 會升向 12.4 —— **9.45 vs 9.38 ＝ +0.7%**：**否證**。reps／warmup／長度三個旋鈕
   都動不了 9.4 ⇒ 殘差**不是攤銷問題**，而是「兩個儀器在量不同的工作」。

## 結構性事實（讀原始碼，可證）

- **llama-bench 對 MTP 是瞎的**：`sampler|speculat|draft|MTP` 在 llama-bench.cpp **零命中**，
  token 是 `std::rand() % n_vocab`，且每 token 一道 `llama_synchronize`（伺服器產生迴圈
  `server-context.cpp:3892` 沒有）。沒有取樣器就沒有投機迴圈 ⇒ 25 t/s 唯一剩下的乘數來源
  只能用 HTTP 路徑量 ⇒ llama-bench **不能當 decode 目標的 instrument of record**。
- **兩個 token 流給池的壓力結構不同**：隨機 id → hit 96.0%、**compulsory 85.4%**、超訂層 **7/40**、
  讀 5.48 GiB；連貫文本 → hit 92.6%、**compulsory 51.0% / capacity 49.0%**、超訂層 **40/40**、
  讀 **18.35 GiB**。**命中率高的那一邊反而慢** ⇒ 「hit% 解釋差距」被殺掉，也說明計數器
  不能跨行程比（生命週期累加器，累加的工作不同）。
- **`predicted_ms` 的視窗起點是第一個「取樣完成」的 token**（server-context.cpp:4092 在
  `n_decoded == 1` 內）⇒ 用 N 除以 N−1 步 ⇒ 樂觀 N/(N−1)（n=24 時 +4.3%）。
- llama-bench 的 `n_ctx = n_prompt + n_gen + n_depth` ⇒ 這批 128，伺服器 4096。

## 附帶：decode 的散熱分離（上午白皮書說「還沒量到」的那一項）

llama-bench 側 9.32 → 8.75 同時換了模型 ⇒ 不可歸因，不引用。每個等級 n=1 ⇒ 仍只記錄、不閘門。

## 修掉的一個真缺陷

`llama_bench_matrix.py` 把 stderr 日誌寫成 `llama_bench_<tag>.stderr.log`，而 `PROFILE:ENV=...`
形式下 tag 就是整個 spec 字串 ⇒ `-n 24` 與 `-n 128` 撞同一個檔名，先跑的那份**被靜默覆蓋**
（那正是專家池自己計數器的唯一落點）。已改成 tag 淨化 ＋ 形狀後綴。`--json` 每臂路徑不同，
所以 JSON 證據沒受影響——這正是它沒被提早發現的原因。
