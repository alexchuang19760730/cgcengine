## §EN-2. 「10+ t/s」不是記錯——是 depth ≥512 那一格（2026-09-16 18:5x）

使用者問：「no-spec 慢 1.15×（7.48 vs 6.52）我記得之前最高是 10+ tok/s?」

**是，而且那不是另一個儀器。** 從 `Backup/llama_bench/` 的原始 matrix 抽出來（`prod25-stream`、
`-p 0 -n 128 -r 3 -b 512`）：

| 今天重跑（18:38） | depth 0 | depth 512 | depth 1024 |
|---|---|---|---|
| avg_ts | **9.52** ±1.17 | **10.89** ±0.21 | ~~7.26~~ ±2.92 **作廢** |
| 09-15（兩跑） | 9.65 / 9.79 | 12.83 / 10.79 | 10.14 / 13.18 |

**⇒ depth 0 是唯一恆定 <10 的格子**（9.52 重現 9.65/9.79，誤差 1.5–3%）；`d≥512` 才是 10–13。
**「10+」與「§W 的 9.4」是同一個儀器、同一個臂、不同的 depth，不是矛盾。**

**d=1024 那格作廢的理由要寫出來**：那是我自己犯的錯——三個 depth 連續跑約 3 分鐘，
發射是 NOMINAL 但過程 `{NOMINAL:118, MODERATE:73, HEAVY:120}`，最後那個 instance 吃到 HEAVY，
stddev 2.92 就是它的簽名。**這正是我今天稍早記下的「每臂之間要等讀數回 0」那條**，我自己在同一天又犯一次。

### 兩條獨立路徑給出同一個「暖值」

- §W 的逐 rep 平台（丟掉冷的第一個 rep）：**87–89 ms/token ＝ 11.3 t/s**
- 本次 `-d 512`：**10.89 t/s**

兩者差 4%，而它們是**不同的機制**（一個是 rep 2+ 的累積，一個是 instance 自己的 depth 前置填充掛在
`t_start` 之前不計時）。⇒ **這台引擎的 llama-bench 暖值 ≈ 11 t/s**；要講「距 25 多遠」，
分母應該是 **11**，不是 depth 0 的 9.4。

### 機制**未確立**（我的第一版猜測被自己的資料削掉）

我原本寫「depth 就是免費的池暖機」。**不足**：09-15 的協定是每個 depth 一對
（pp 512 先、tg 128 後），所以 `tg@d0`（#2）前面**也有一個 pp-512**（#1）——
池的暖度對 #2 與 #4 是一樣的，可是 9.65 vs 12.83。可存活的候選：
實例**自己**那份不計時的前置填充（d≥512 有、d=0 沒有）／行程內的序列位置／
隨 context 長度改變的 kernel 或池行為。**未解。**

### 對「統一用 llama-bench」的直接影響

標準不能只報 `-d 0`。本 repo 的既有協定（`llama_bench_matrix.py` 預設 `0,512,1024,2048,4096`）
才是歷史可比的那一組；§W 那些配對臂用的是 `--depths 0` ⇒ **它們量的是最冷的格子**，
拿它去跟記憶中的 10+ 比是比錯了格子（不是誰錯）。

**可稽核出處表**：`Backup/cgc_logs/instr_compare/decode_tps_provenance.tsv`（43 列；
llama-bench 的部分由 `Backup/llama_bench/*.json` 重新產生，其餘每列附來源路徑與
`auditable` 欄）。其中 **3 列標 NO**：`10.43 vs 6.48`（文件沒指名儀器）、
`22.2 vs 8.1–8.9`（只是 `llama-context.cpp:5817` 的一條註解，且當時旗標不在 allowlist）、
以及 25.17／27.71（舊日不同配置）。**這三格不該被當成結果引用。**
