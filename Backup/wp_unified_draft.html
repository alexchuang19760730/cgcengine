CGC MoE Engine · 2026-09-16 · 這份文件同時是「規格變更」與「變更後的重量結果」。 規格已改（scripts/run_server.sh:335）；量測結果見 §4–§7。

一句話：把 CGC_SPAC=1 / CGC_SPAC_ALPHA=0.75 寫進 prefill250， 於是一個 profile 同時服務 prefill 與 decode。原則是「剩下的槓桿住在哪個形狀裡」，不是現在的 t/s （§2）。加了之後 D5 對 v4 報名目上的 INVALID COMPARISON，處置是重新基線 v5，而證據是 jsonl 逐位元相同、不是「M1 = 9/9」（§3）。SPAC 的兩個作用點都在 prefill 的熱路徑上 （§1），所以 prefill 250 必須在同一個 commit 內重量（§4）。

1. 這次改了什麼

scripts/run_server.sh 的 prefill250 區塊加了兩行（其餘一字未動）：

[ -z "${CGC_SPAC+x}" ]       && CGC_SPAC=1
[ -z "${CGC_SPAC_ALPHA+x}" ] && CGC_SPAC_ALPHA=0.75
解析後（CGC_DUMP_ENV=1 實測）
CGC_SPAC=1、CGC_SPAC_ALPHA=0.75，其餘與 v4 參考檔一致
可覆寫
CGC_SPAC=0 ./scripts/run_server.sh 回到 09-15 GA 的形狀（profile 只補預設，不寫死）
其他 profile
prod25 本來就有（不變）；qa-zh / off 仍然沒有 SPAC

SPAC（llama-expert-cache.h:605-619）不是一個新的快取，而是三個既有機制的來源切換：

  • 每個 routed step 更新每層的 EMA 專家效用向量（llama-context.cpp:4739）；
  • 逐出時改用「效用最低」選受害者，而不是 LRU（llama-expert-cache.cpp:473, 789, 1306）；
  • 步與步之間把池重新瞄準 EMA top-K 的非駐留專家（llama_expert_cache_spac_prefetch）。

換句話說，SPAC 決定的是 哪些專家駐留，不是「數值怎麼算」。§3 把這句話量成了可稽核的事實。

2. 判準：不是 t/s，是「剩下的槓桿有沒有地方跑」

三個候選臂（prod25 / prod25-stream / prefill250）的 resolved env 只差 6 項，其中 4 項只是「寬 prefill 走哪條路」，真正有語意的只有兩項：CGC_SPAC 與 CTX。 所以選誰的問題可以化簡成「哪個形狀裝得下還沒做的優化」。

而那個判準在原始碼裡，不在數字裡。池路徑的批寬被夾住，夾具的註解自己把它綁在 MTP 上：

// llama.cpp/src/llama-graph.h:18-37
// Default 8 covers MTP n_max up to 7 (verify = n_max+1).
// Tunable via CGC_POOL_MAX_TOKENS (clamped to [2, 64]).
// Note: larger values may increase memory pressure.
// llama.cpp/src/llama-context.cpp:286-291
if (pool_capacity > 0 && n_batch > 1 && !cgc_prefill_stream) n_batch = pmax;
//   ... so speculative/MTP verify batches (n_max+1 <= cap) flow through the pool path
//   The clamp is NOT lifted for an owned pool.

⇒ prod25（不帶 CGC_PREFILL_STREAM）把池路徑鎖在 n_batch <= 8； 放寬它就要在 143 slots/layer 裡裝下更寬的 expert union（容量壓力熱點： worst layer 248 distinct vs 143 slots）。而 M1（batched-union gather）與 M4（MTP verify 真批次） 住在「寬 batch」的世界，需要 whole-layer slab（ne[2]=n_expert，裝得下 256 個） ——只有帶 CGC_PREFILL_STREAM 的臂有。

臂whole-layer slab
M1/M4 的住處		decode 駐留
SPAC		prefilldecode 歷史
prod25✗（夾在 8）✓差（被夾）9.4（d0）
prod25-stream✓✓111–1209.65 → 13.18
prefill250✓✗ ← 唯一缺的250+（已交付）從未量到

prod25-stream 是「為了 decode 的 ~15% 放棄 2.2× 的 prefill」，那個交易不對稱； prefill250 只缺一個旋鈕。所以選後者 —— 但那個旋鈕不是免費的，見 §4。

3. D5：名目上不Comparable、行為上逐位元相同 ⇒ 重新基線 v5

第一次跑閘門（--tag spac_unified --allow-incomparable）的輸出：

GATE spac_unified: INVALID COMPARISON -- reference was dumped under a different
  numerics-determining configuration (2 diffs).
config_diffs:
    ENV.CGC_SPAC:       ref='<absent>'  now='1'
    ENV.CGC_SPAC_ALPHA: ref='<absent>'  now='0.75'
  observed M1=9/9  M2=9/9  M3=9/9  n=9 (printed for information, NOT a verdict)

這是預期的：CGC_SPAC 不在 DIAGNOSTIC_KEYS 裡，而 gate 的 可比較性檢查是「resolved env 的字串差」。它與 2026-09-15 的 CGC_OA_ASYNC 那一輪是 同一個形狀（見 gate 檔頭 v3/v4 的記載）。

3.1 證據是逐位元相同，不是「M1 = 9/9」

閘門自己 2026-09-16 的檔案說明寫得很清楚：一致性必須由 logits 建立，而「同一條路徑會落在同一個 錨點 digest 上」才是可稽核的。這裡有更強的一條：重新基線完的 v5 與舊的 v4 md5 完全相同。

$ md5 -q Backup/knifeedge_matrix/ref_iq3_pool8gb_M2_6144_bitident_v5_spac.jsonl
a0a0ca742ca94e843c54b39981742738
$ md5 -q Backup/knifeedge_matrix/ref_iq3_pool8gb_M2_6144_bitident_v4_skip0off.jsonl
a0a0ca742ca94e843c54b39981742738
「M1 = 9/9」是弱述句（「我看的時候是 9/9」）；md5 相同才是強述句（「這份檔案沒有被 重推導，只是被重新蓋章」）。兩者的差別在於：前者允許「剛好這次一樣」，後者排除了它。

刻意沒有做的事：沒有把 CGC_SPAC 塞進 DIAGNOSTIC_KEYS。 那個集合會把鍵從 config_stamp 濾掉 ⇒ .cap 從此不再記錄它 ⇒ 下一個讀者 分不出 SPAC-on 與 SPAC-off 的基線。CGC_SLOT_TABLE_GPU 的前例不適用：那是「整條主張 就是 bit-identity」的實驗旋鈕，不是生產預設。

副產品：SPAC 的主張被量化了。它改變「哪些專家駐留」，而在這個 pool 幾何、 這 9 列探針上不改變數值。若哪一天它真的動了數值，閘門會在 M1 對 v5 失敗 —— 正是它該失敗的地方。

4. SPAC 的成本路徑（為什麼 prefill 必須重量）

這一節是這次修改唯一真正的風險，而它由引擎自己的註解指出，不是我推測的：

// llama.cpp/src/llama-context.cpp:4736-4741
if (cgc_spac_on()) {
    llama_expert_cache_spac_update(cache, (uint32_t) il, routes.data(), routes.size());
}
// "Fires on every path that reaches here -- large prefill, MTP draft (ctx MTP) and
//  trunk verify alike ... Unpooled layers update a row spac_prefetch never reads."
  1. EMA 更新在每個 routed step 都跑，而且含大 prefill；每次呼叫取 cache->m 這把鎖 （llama_expert_cache_spac_update 內），因此與 8 個 worker 的填充分執行有競爭可能。
  2. spac_prefetch 的預設節奏是 CGC_SPAC_REFRESH=1，即每一步對每一層的 非駐留專家做 partial sort 並排入 prefetch（llama-expert-cache.cpp:1739+）。

兩者都在 prefill 的熱路徑上。所以「prefill 250 還在」是量測，不是假定 —— §5 就是那個量測。

5. prefill 250 的重量：交錯 A/B/A/B

6. 完整 depth 矩陣（0 / 512 / 1024 / 2048），含順序效應控制

-d N 讓 llama-bench 在 t_start 之前先把 context 填 N 個 token （test_prompt 在 t_start 之前），所以它量到的是「池被那 N 個 token 弄成什麼狀態之後」 的 decode。它是唯一讓「同儀器、同臂」從 9.5 走到 13.2 t/s 的軸，所以不是細節。

但歷史協定（09-15）把 0,512,1024,2048,4096 全放在同一個行程的遞增順序裡， 而池是行程級的 ⇒ depth 效應與序列位置混淆。這份文件因此跑三種形狀：

形狀它回答的問題
單行程、遞增 （歷史可比）與 09-15 那組能不能對照
單行程、遞減asc − desc 就是順序／累積效應的大小
每個 depth 各自一個行程移除行程內的預熱 ⇒ depth 軸本身

7. ctx 8192 上的 CGC_SPAC_ALPHA 重掃

alpha = 0.75 是 2026-09-06 用 11 點掃描在 ctx 4096 / 8 GiB pool / DBUF+SPAC 調出來的 （llama-expert-cache.h:620-625：alpha 0.75 給最佳中位 25.87 t/s、2/3 跑次 > 25）。 但 alpha 是「每層專家效用」的 EMA 衰減率，而填進那個 EMA 的是每一步 routed 的專家集合 —— context 長度改變會改變它（駐留歷史不同 ⇒ router 統計不同；暖池的 depth prefill 大小也不同）。 所以「0.75 在 8192 還是對的」在被量之前只是假定。

8. 副作用盤點：pin 一個 env 鍵會靜默重解析誰

這是這次改動最容易被忽略的部分：--profile 不是被動預設，它 pin 旋鈕。 把鍵加進 prefill250 之後，每一個「預設 profile 就是它」的工具都被重新解析。

盤點指令
grep -rn '"--profile", default=' scripts/check/*.py
實際清單
decode_sweep.py（預設 prefill250）、m123_oracle_gate.py（同）、ab_interleave.py（prod25，不受影響）
不吃 --profile 但寫死 profile
llama_bench_matrix.py 的 prefill250 臂、prefill_certifiability.py 的 --arm prefill250、run_thermal_gate.sh → run_req2_retest.sh（交付數字那條路）
不受影響
run_native_baseline.sh（直接 exec 二進位，不經 profile）

最需要指名的兩條：

  • decode_sweep.py 不帶 --profile 的跑次，從此取得 SPAC=1。先前記錄的 decode 散佈（6.6–16.17 t/s）用的是 --profile prod25，那個本來就是 SPAC=1，所以那些數字不受影響； 但「下一跑」與「那一跑」若一個帶 --profile 一個不帶，就會悄悄變成兩個配置。已在 decode_sweep.py 的 ARMS 註解寫明。
  • spac-on 這個臂退化了。它在新基準上與 baseline 同義 （prod25 一向 pin SPAC=1，prefill250 從今天起也是）。真正的 SPAC A/B 要用 --profile prod25 --arms baseline,p25-nospac，或 prefill250:CGC_SPAC=0。

10. 誠實邊界：這份文件不主張什麼

  • 不主張「SPAC 不改變數值」是一條普適定理。它是在這個 pool 幾何、這 9 列探針、 這份 build 上量到的（md5 逐位元相同）。換幾何要重量。
  • 不主張 prefill 250 的條件式交付被推翻。交付述句一直是「發射時讀到 0 的那一臂， 其 req1–req3 全部 ≥250」，不是「250 隨時可重現」。改了 profile 就要在新的 profile 上重新建立這個述句（§5）。
  • 不引用不同 depth 的數字互比。「10–13 t/s」與 9.4 是同儀器、同臂、不同 depth， 不是矛盾也不是進步（Backup/cgc_logs/instr_compare/decode_tps_provenance.tsv）。
  • 不主張這件事讓 decode 更接近 25 t/s。它改變的是「剩下的槓桿有沒有地方跑」， 不是把現有的 t/s 推上去；decode 距離仍未歸因的殘差保留在 §6 的表裡。
  • docs/PREFILL250_CONFIGURATION_GUIDE_2026-09-15.html §2.1 列的是 09-15 的 8 個旋鈕 （BATCH=6144、無 SPAC），與現在的 profile 預設不同（5632 ＋ SPAC）。 那份文件是 dated 快照，依慣例不就地改版；這裡只指出它的落差。
